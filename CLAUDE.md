# Watchtower — Developer Notes

**Project:** `watchtower` (Go module: `watchtower`)
**Backend:** Go 1.25, SQLite via `modernc.org/sqlite` (`database/sql`), see `go.mod`
**Desktop:** SwiftUI macOS app (Swift 5.10 language mode, macOS 14+; building requires a Swift 6+ toolchain / Xcode 16+ — the FluidAudio dependency's manifest declares swift-tools 6.0), GRDB.swift, see `WatchtowerDesktop/Package.swift`

## Feature Notes

### Inbox Secretary + Secretary Dashboard (v73+, replaces Inbox Pulse pinned model; dashboard replaces the two-tier feed)
- `internal/inbox/` — `Pipeline.Run` phases in order: detectors (slack / jira / calendar / watchtower) → full-stream triage (`inbox.triage`, cheap model tier) → implicit learner → auto-resolve → **compose** (`inbox.compose`, `compose.go`/`runCompose`) → **situation cards** (`inbox.situation_card`, `situation_card.go`/`runSituationCards`, strong model tier) → archive → unsnooze. See `pipeline.go`'s `Run` for the authoritative order.
- Triage (`triage.go`) reviews every new trigger item plus a chunked scan of ordinary channel traffic (`cfg.Inbox.MaxTriageMessages` per cycle), assigning tier (action/ambient) and priority. It may only downgrade a trigger item's class, never upgrade one (INBOX-01, reworded for the dashboard in the 2026-07-06 changelog entry). Hard-muted sources are skipped before reaching the AI call.
- Two item classes still exist on signals: `actionable` vs `ambient` (auto-seen, auto-archive after 7 days; actionable stale after 14 days) — but they no longer drive two visual sections. Both feed the composer, which clusters triaged signals plus track/target updates into **situations** (`situations` + `situation_signals` tables, `internal/db/situations.go`): merging into an existing open situation when one already covers the story (DASH-01), never duplicating.
- The old pinned-selection AI call and `inbox_items.pinned` column were **removed** (migration 00010). The **per-item secretary card** stage (`inbox.card`, `card.go`) is now **also retired** — migration 00012 deregisters its prompt row; per-item cards are replaced by situation cards (`inbox.situation_card`) generated once per situation instead of once per inbox item.
- Situation cards (`situation_card.go`, `runSituationCards`) generate why-it-matters / summary / chronology for each situation via a stronger model, capped per cycle. Per-situation failures set `card_status='failed'` and the pipeline continues to the next situation; compose/card AI failures leave existing situations, ranks, and cards untouched and never advance the compose watermark (DASH-02) — the inbox watermark (INBOX-09) is unaffected since compose/cards run after triage has already committed.
- Converting a situation into a Target or Track (Desktop "Target"/"Track" buttons) sets `status='converted'` and stamps `converted_target_id`/`converted_track_id` — a link, not a delete, so the situation's history stays reachable (DASH-03).
- Watermark advance (INBOX-09): a detector error always freezes `inbox_last_processed_ts`; a triage error or cap advances it only to the last fully-triaged message, never past an unprocessed one — see `Run`'s watermark-decision block and `docs/inventory/inbox-pulse.md`.
- `workspace.secretary_profile` — a free-text brief the user writes about themselves, injected into the triage, composer, and situation-card prompts via `buildSecretaryBrief` so AI judgment reflects real context. Edited from the Desktop "Profile" tab (`SecretaryProfileView`).
- `inbox_learned_rules` table (implicit + user_rule sources) — `source='user_rule'` is protected from implicit overwrite. Rules are injected into AI prompts via `buildUserPreferencesBlock`. Mechanics unchanged from the pinned-era design.
- `inbox_feedback` table records raw 👍/👎 + reason; `inbox.SubmitFeedback` in Go maps (rating, reason) → rule upsert or class downgrade.
- Desktop: `InboxFeedView` now hosts the Dashboard tab — a Catch-Up-style master-detail screen (`SituationRow` list left, `SituationReviewPane` right with sources block linking Target/Track/Slack, secretary card, member-signal bubbles with per-message Slack links, action bar with comment feedback), replacing the in-feed card expansion — plus the unchanged "Learned" tab (rules management) and "Profile" tab (secretary brief). Dashboard is the app's start screen (`AppState.selectedDestination` defaults to `.inbox`, labeled "Inbox" in the sidebar — naming-only change, see the 2026-07-07 secretary-dashboard UX fixes).
- Discuss chat (`SituationDiscussSection` / `SituationChatViewModel`, `chat_conversations.context_type='situation'`) — collapsed per-situation secretary chat with an intent-draft contract: the user states WHAT to reply and the secretary renders it in the owner's voice (via `workspace.style_profile` + counterparty people-card briefs + a register sample of the owner's own recent messages), adding no content the user didn't state; no unsolicited drafts. The input bar docks outside the pane's ScrollView (`SituationDiscussInputBar` — nested-NSScrollView collapse). Style profile generated by `watchtower inbox style-sample` (`inbox.style_sample`, strong tier), edited in the Profile tab (`SecretaryProfileViewModel` in `AppState`).
- Desktop feedback path: Swift `InboxFeedbackQueries.record(...)` mirrors the Go rule derivation logic so UI is immediately consistent. The `watchtower inbox feedback` CLI subcommand and DASH-04 enforce that comment-less 👍/👎 never invoke the AI interpreter — both paths derive rules directly, making bare thumbs fast and local.
- See `docs/inventory/dashboard.md` for the DASH-01/02/03 behavioral contracts and `docs/inventory/inbox-pulse.md` for INBOX-01..09.

### Meeting Transcriber (v74+)
- **Pluggable transcription providers:** The transcription engine is pluggable via `TranscriptionProviderRegistry` (single list in `WatchtowerDesktop/Sources/Services/Transcription/`). One active provider is chosen in Settings via two pickers: **Engine** (`@AppStorage("transcription.provider")`, default `"whisperkit"`) and **Model**. New installations default to WhisperKit; absence of the provider key preserves existing behavior. Adding a provider = one line in `TranscriptionProviderRegistry.all` + one file in `Providers/*.swift` conforming to `TranscriptionProvider`.
- **Built-in providers:** `WhisperKitProvider` (on-device, default, `large-v3-v20240930` turbo default, supportsLive=true — its `WindowedTranscriber`/`StreamingTranscriber`/`resolveWindowLanguage` and the live↔batch pin test `StreamingTranscriberTests.testMatchesBatchOnSameSamples` are Whisper-internal); `ParakeetProvider` (FluidAudio, batch-only, Apple-Silicon-gated); `Qwen3Provider` (soniqo/speech-swift, Apple-Silicon-gated; batch AND live both decode through `Qwen3Windower` — WindowPlanner windows over one shared loop, bounded memory, no sticky language: forced hint or per-window auto-detect, segments labeled "auto"); `AppleProvider` (SpeechTranscriber, macOS 26+, batch-only, no Ukrainian).
- Record a meeting from the Calendar tab (event-linked or ad-hoc): Swift captures mic + system audio natively (CoreAudio process tap + private aggregate device, macOS 14.4+, no BlackHole/ffmpeg — `SystemAudioRecorder`), transcribes on-device via the active provider with windowed ru/uk/en sticky language detection (WhisperKit only; Qwen3 live/batch uses its own per-window auto-detect via Qwen3Windower; Apple and Parakeet are batch-only), orchestrated by `MeetingRecorderCenter` on AppState (survives navigation; the audio file survives every failure).
- Go owns persistence + AI: `meeting_transcripts` table (migration 00020; `event_id` `ON DELETE SET NULL` — transcripts outlive events), CLI `watchtower meeting-prep transcript save|recap|list|show` (transcript passed via `--transcript-file`, never argv), recap via `Pipeline.GenerateTranscriptRecap` reusing the `meeting.recap` prompt — event-linked recaps land in `meeting_recaps` (existing UI renders them) *unless the event already has a recap* (collision guard mirroring Swift `linkToEvent`: the existing row is never overwritten; the generated recap goes to `summary_json` instead), ad-hoc in `meeting_transcripts.summary_json`. `save` exits 0 if the transcript persisted even when the recap failed (envelope `recap_ok`/`recap_error`; retry via `transcript recap <id>`).
- Window boundaries are planned by the shared `WindowPlanner` (silence-snapping: the cut lands on the quietest 20 ms frame within ±`transcription.boundarySnapSec` (default 2.5 s) of the nominal end; 0 disables). Both transcribers consume it, so the live↔batch equivalence invariant covers boundaries too (`testMatchesBatchWithSnappingOnSameSamples`).
- Speaker roles (v75+): after Stop, a diarization post-pass (FluidAudio pyannote/VBx behind the `SpeakerDiarizing` seam, `FluidAudioDiarizer`) maps `TranscriptionOutput.segments` (timestamped, from `WhisperWindowEngine.transcribeWindow`'s `[TranscribedSegment]`) to speaker clusters and renders `[Я]`/`[Speaker N]` prefixes into the same transcript text (`RoleAssigner`, pure). The «Я» label comes from the `rec_X.activity` sidecar (per-100 ms mic/system RMS written by `SystemAudioRecorder`; swept by the Go orphan cleanup like any `rec_*` file). Any diarization failure saves the plain transcript — never `.failed`; toggle `transcription.diarization` (default on). Go/DB unchanged: roles are line prefixes in `meeting_transcripts.text`.
- Live (in-progress) transcription (WhisperKit and Qwen3): while recording, `MeetingRecorderCenter` loads the provider at start and runs `StreamingTranscriber` over the recorder's live 16 kHz sample stream (`AudioRecording.liveSamples`, tapped from `SystemAudioRecorder`'s downsampled `outBuffer`), showing finished 20 s-window chunks in the `RecordingIndicatorView` expandable panel. The Qwen3 engine's live path runs its own `Qwen3Windower` loop over the same live sample stream (no sticky language; single-pass save on Stop and the batch-from-file fallback apply the same way). Single-pass: the live result is saved directly on Stop (no re-decode); the engine loaded at start is reused for the fallback. The `.caf` file stays the source of truth — engine-load/stream failure silently drops to the engine's batch path from the file (`WindowedTranscriber` for Whisper, `Qwen3Windower` for Qwen3), which also serves crash recovery/retry. `StreamingTranscriber` and `WindowedTranscriber` share `resolveWindowLanguage` and MUST stay behaviorally equivalent (pinned by `StreamingTranscriberTests.testMatchesBatchOnSameSamples`, Whisper-internal). Same model as Settings (`transcription.model`).
- Both AI generators pass user messages > 32 KB via stdin (`digest.StdinThreshold`) to stay clear of ARG_MAX — claude gets bare `-p` + stdin, codex gets `exec -`.
- Daemon phase `phaseTranscriptAudioCleanup` deletes audio past `transcripts.audio_retention_days` (default 30) and NULLs `audio_path`; transcript text is permanent. It also sweeps `transcripts.recordings_dir` (default `~/Library/Application Support/Watchtower/recordings`) for orphaned `rec_*` files older than the window that no `audio_path` references. MCP tools `list_transcripts`/`get_transcript` expose transcripts to the secretary chat.
- **Recordings tab & single-view (v75+):** The Calendar screen has an Events | Recordings segmented control (`CalendarMode` in `CalendarEventsView`). Recordings (ad-hoc + event-linked) live in a master-detail list (`RecordingsView`/`RecordingsListView`/`RecordingDetailView` + tab views in `RecordingDetailTabs.swift`): the master uses the lightweight `RecordingListItem` projection (`fetchRecordingList` — never selects `transcript_text`/`summary_json`, only a 200-char snippet + booleans — perf guard), the detail fetches the full row async on selection and has four tabs (Recap / Notes / Transcript / Chat), chat VM created lazily. Recap resolution: the event's `meeting_recaps` row wins, falls back to the transcript's `summary_json`; decoded once in `load()`, never in row builders.
- **Persistent segments & utterance view (D1):** `meeting_transcripts.segments_json` (migration 00045) — JSON array of per-utterance segments (`RoleAssigner.assign`'s merge units: idx/start_sec/end_sec/speaker/text/deleted; NULL for legacy rows). Load-bearing invariant: when non-NULL, `transcript_text = render(segments where !deleted)` — **one canonical renderer per side, a deliberate dual-path like `saveNotes`**: Go `internal/meeting.RenderTranscriptSegments` (CLI `transcript save` validates the invariant — including idx == array position — and NULLs the column on any missing/malformed/mismatched `--segments-file`, exit-0 envelope semantics preserved, the drop reported via `segments_ok`/`segments_error` envelope fields per the `recap_ok` precedent) and Swift `TranscriptSegments.render` (UI edits via `MeetingTranscriptQueries.setUtteranceDeleted`, the transactional `segments_json` + `transcript_text` rewrite behind the Transcript tab's soft delete + undo toast; no hard deletion). The Swift save path writes a `--segments-file` temp file next to `--transcript-file` (live, batch fallback, and sidecar-retry paths alike); equivalence pinned by matching fixtures in `internal/meeting/segments_test.go` ↔ `TranscriptUtteranceTests.swift`. `RecordingTranscriptTab` renders the utterance list (speaker + timecode headers) when segments exist, the legacy flat text otherwise; `fetchRecordingList` never selects `segments_json` (perf guard). Spec: `docs/superpowers/specs/2026-07-31-transcript-stack-design.md`.
- **Meeting notes:** `meeting_transcripts.notes_md` (migration 00021) — publishable markdown. Generated by `watchtower meeting-prep transcript notes <id>` (`meeting.notes` prompt, strong tier, transcript in the user message / stdin path like the recap; exit 1 on failure, nothing persisted — unlike `save`). Edited in the Notes tab (debounced direct GRDB write via `MeetingTranscriptQueries.saveNotes` — a dual-path with the CLI writer; the editor is `.disabled` while generation runs so a finishing run can't clobber mid-run edits). Generation state lives in `TranscriptNotesCenter` on AppState so it survives navigation.
- **Meeting chat:** per-recording secretary chat, `chat_conversations.context_type='meeting'`, `context_id=transcript id` (`MeetingChatViewModel` — the streaming skeleton is a deliberate third copy of the Target/Situation chat VMs, house pattern). System prompt inlines a capped transcript excerpt (12k chars) and points the model at the `get_transcript` MCP tool for the full text.
- **Delete:** Swift-only transactional delete (`MeetingTranscriptQueries.delete`): transcript row + meeting chat (+messages) in one write; returns `audio_path` for post-commit best-effort file removal (missing file = success — retention may have swept it). The event's `meeting_recaps` row is NEVER deleted with the recording.
- Design/plan: `docs/superpowers/specs/2026-07-13-meeting-transcriber-design.md`, `docs/superpowers/plans/2026-07-13-meeting-transcriber.md`; live transcription: `docs/superpowers/specs/2026-07-14-live-transcription-design.md`, `docs/superpowers/plans/2026-07-14-live-transcription.md`; recordings tab: `docs/superpowers/specs/2026-07-15-recordings-tab-design.md`, `docs/superpowers/plans/2026-07-15-recordings-tab.md`.

### Secretary Memory (Phases 0–5 slice 4)
- `internal/memory/` — a durable memory vault at `Config.WorkspaceDir()/memory`: markdown nodes (entities/episodes/rollups/beliefs, YAML frontmatter + `[[id|label]]` wiki-links) in a go-git repo. **Files + git history are the source of truth**; the SQLite index (`memory_nodes`/`memory_aliases`/`memory_node_stats` + `memory_fts` FTS5) is derived and rebuildable via `watchtower memory reindex` (MEM-02). Obsidian can open the vault, but nothing requires it.
- Consolidation is a daemon phase (`phaseMemory`, after `phaseInbox`, before `phaseNextStep`), **off by default** (`memory.enabled`). `Pipeline.Run` order (`pipeline.go`): owner-edit commit (MEM-03) → index reconcile → mechanical seeding (people/channels/Jira keys, no AI) → situations ingest (episode nodes aliased `situation:<id>`) → raw-text episode extraction (`memory.extract_episodes`, light tier, chunked per-channel windows against the `workspace.memory_last_extracted_ts` watermark, MEM-01/04) → **semantic tier** → mechanical `index.md` + `map.md` render.
- **Semantic tier (Phase 3, `memory.semantic.enabled`, dark by default)** in `runSemantic`: dedupe → concept promotion → strong-tier entity-page rewrite (`memory.entity_rewrite`) → belief pass (`memory.revise_beliefs`) → aging → eviction. Beliefs carry rank/hysteresis math (`belief_math.go`): the model only proposes ops; Go disposes (MEM-08). Owner-rank evidence protects a belief from auto-flip (MEM-06); eviction/merge never thin provenance (MEM-07). Strong-tier steps stop launching once output tokens pass `memory.semantic.output_budget`.
- **Surfaces (Phase 4), each dark by default behind `memory.surfaces.{chat,briefing,disputes,reflection}`** — the read/write-back layer on top of the semantic tier: (1) **chat** — the Desktop Discuss prompt gains a MEMORY block (Swift, `SituationChatViewModel`) and owner turns typed in Discuss become owner-rank belief evidence (`chat_ingest.go` stages `role='user'` situation turns; the belief pass mints `- owner …` lines from validated `chat:<id>` refs). (2) **briefing** — `internal/briefing` adds a *Memory revisions* journal of notable belief transitions (`briefing.daily` v6). (3) **disputes** — the inbox watchtower detector reads `dispute_pending` beliefs and mints `decision_made` dashboard situations. (4) **reflection** — a weekly strong-tier `memory.reflect` pass (`reflect.go`, tail of `runSemantic`, deterministic per-workspace stagger) over the vault git log + `## History` churn flags flapping beliefs and appends entity `## Current` notes.
- **Owner rank is code-authored, never model-inferred (MEM-09):** owner-rank evidence is minted only from `role='user'` chat turns or `memory(owner-edit)` commits; the belief-op JSON carries no rank field. **Disputes ride the standard inbox, not a memory write (MEM-05/10):** memory only sets the `memory_dispute_flags` side table; the inbox detector mints and clears the item. **Surfaces are read-only over history (MEM-11):** the briefing journal and reflection never mutate a belief's confidence/status — reflection writes only dispute flags + entity `## Current` notes; all belief math flows through `applyBeliefOp`.
- **Universal substrate (Phase 5 slice 1)** — the enabling refactor plus two independently-dark sources. **Provenance-resolver registry (MEM-12, `provenance.go`):** every write-time provenance check routes through one `ProvenanceRegistry` (one `ProvenanceResolver` per ref scheme: `""`/message, `chat`, `mail`, `act`); a ref of an unregistered scheme is rejected at write, generalizing MEM-01 from two hardcoded checks. **Gmail source (`memory.sources.gmail`, default false, `gmail_extract.go`):** each Gmail thread → one episode with `mail:<message_id>` provenance, senders seed as person entities (email-alias identity stitching), own watermark `memory_gmail_last_extracted_ts` (a third watermark, distinct from Gmail sync + Slack extraction); prompt `memory.extract_email_episodes` (light tier). **Mechanical interaction ingest (`memory.sources.actions`, default false, `action_ingest.go`, in `runSemantic`):** folds owner 👍/👎 (`inbox_feedback`, floor-driven on `memory_last_interaction_id`) + terminal situation verdicts (idempotent re-scan) into episode-mirror `## Outcome` annotations + per-entity `memory_engagement` aggregates + staged `act:` refs — no AI, no preference beliefs yet (deferred to semantic 5D). The belief math gains an **`owner-action`** rank (weight 0.8, between `observed` and `owner`), code-minted only for a validated `act:` ref and **non-protecting** (MEM-15 — `hasFreshOwnerSupport` still keys on `rankOwner` only). Retention importance now consumes `memory_engagement` (`RetentionInputs.Engagement`), the first live feed for Phase-3's stubbed input.
- **Universal substrate (Phase 5 slice 2)** — a third independently-dark source plus a generalization, both extending existing contracts (no new numbered contract). **Calendar source (`memory.sources.calendar`, default false, `calendar_ingest.go`/`runCalendarIngest`, Run step 3b — mechanical, NO AI call):** one ended `calendar_events` row → at most one episode built from the structured row, with a `meeting_recaps` row folded into Story/Outcome where it exists (reused, never re-synthesized); idempotent via the `calevent:<event_id>` alias + content-equality no-op; recurring series → `calseries:<recurringEventId>` entities (`seedCalendarSeries`); own **fourth** watermark `memory_calendar_last_extracted_ts` with a 2-day bounded-lookback re-scan for late recaps against the sync's ~24 h retention. **MEM-12 extended** with a `cal` scheme resolver (`calResolver`/`CalendarEventExists`); the builder validates via a cal-only scoped registry. **Internal-dialogs generalization (`memory.sources.chats`, default false):** the Phase-4 situation-chat ingest widens to **target/track** Discuss chats — the allowed `context_type` set (`chatContextTypes`) is `{"situation"}` off (byte-identical to Phase 4, **MEM-09 unchanged**) and `{"situation","target","track"}` on, gating `ListOwnerChatTurns` and `chatResolver.contextTypes` in lockstep. **The "remember this" command** (`parseRememberCommand`, case-insensitive `remember:`/`remember this:`) is the opt-in staging trigger for target/track chats (an ordinary drafting turn there is consumed-not-staged); situation chats still stage every owner turn. **MEM-09 extended** — owner rank now also code-mints from a validated target/track `role='user'` turn (still authored, no new write author, MEM-11 preserved). Onboarding chats are out (never persisted).
- **Render-inversion begun (Phase 5 slice 3, dark compare-mode)** — the secretary is starting to render its digests from the memory substrate instead of raw messages. **Channel-digest render (`digest_render.go`/`renderChannelDigest`, prompt `memory.render_channel_digest`, cheap/haiku tier):** a Slack channel's digest rendered from the memory episodes overlapping a time window (episode Story/Outcome + provenance first, raw coverage-gap messages only for what the episodes miss), returning the legacy `digest_topics` JSON shape. **MEM-13 (render fidelity):** every `key_messages`/decision `message_ts` the model emits is kept only when episode-cited (in the input episodes' `## Provenance` set) or a resolving raw gap-message ts; an invented ref is dropped-and-counted (`render_refs_rejected`), never written — the hallucinated `key_messages` class dies by construction (memory 100% valid vs the audit's ~0.6% legacy). **Episode-window substrate:** a derived `memory_provenance(node_id, scheme, channel_id, ts_raw, ts_unix)` index (populated wholesale-per-node inside `UpsertMemoryNode`, one parse site `parseProvenanceRefs`, queried by `ListEpisodesForChannelWindow`) — rebuildable from files, so it lives **inside MEM-02** (the reindex-equivalence guard was extended to dump it) and is cleared by `DropMemoryIndex`. **Dark compare-mode (`digest_compare.go`/`CompareDigests`, behind `memory.renders.digest_compare`, default false, tail sub-step of `phaseMemory` after extraction):** for each recently legacy-digested channel it renders the window from episodes, writes the render + coverage + rejected-ref count to `memory_digest_shadow` (memory-owned side table, **never** `digests`/`digest_topics`), and computes a field-by-field diff (topic count, `key_messages` ref-validity, coverage, length ratio). `watchtower memory digest-compare [--since --out]` runs it on demand and writes a branch report. **The legacy digest pipeline is unchanged and stays authoritative** — the compare is a pure reader (MEM-05/14, proven by `TestDigestCompare_LegacyTablesByteIdentical`); the actual switch off legacy is a later slice, gated on the owner's hand-review.
- **Entity mirrors + read surfaces + preference beliefs (Phase 5 slice 4)** — **5C:** target/track entity mirrors (`mirror_ingest.go`/`runOperationalMirrors`, Run step 3c, mechanical, no AI call) alias targets and tracks into the vault as long-lived entities (`target:<id>`/`track:<id>`, `## Current` replaced wholesale each refresh, `## Open loops` — its first writer — populated while non-terminal and cleared on terminal, `## Links` conversion cross-links to the originating `situation:<id>` episode), gated `memory.sources.operational`; re-scan + content-equality with **no watermark** (small mutable tables, the `interactionRescanWindowDays` precedent) — **MEM-14 "mirror, don't absorb"**: memory never becomes the write path for `targets`/`tracks`/`day_plans`/`day_plan_items` (guard dumps them byte-identical across a full gates-on run). Two read surfaces copy the Phase-4 `gatherMemoryRevisions` shape verbatim: the **day plan** (`internal/dayplan`) folds memory open loops into `day_plan.generate` (v2→v3) behind `memory.surfaces.day_plan`, complementing (never duplicating) its direct `targets` read; **meeting prep** (`internal/meeting`'s `PrepareForEvent`) folds attendee entity pages + beliefs into `meeting.prep` (v3→v4) behind `memory.surfaces.meeting_prep`. Both are sentinel-gated prompt slots (gate off → a fixed placeholder string, byte-identical output, the `briefing.daily` v6 precedent) and pure readers — no vault write, no vault git-log move. `targetSubjects`/`trackSubjects` (`chat_ingest.go`) now also prepend a bare target/track Discuss chat's own mirror alias to its subject refs, so a chat with no linked track finally stages once its mirror exists (a no-op when mirrors are off). **5D semantic:** the ordinary belief pass (`ReviseBeliefs`) gains a gated **OWNER ACTIONS** user-message block (`memory.semantic.preferences`) rendering this run's staged `act:` interaction refs plus per-subject `GetEngagement` aggregates, so the model can propose preference beliefs about the owner ("the owner does not care about X-alerts") through the SAME propose-new/confirm/weaken/shake/retire ops and rank machinery — no new rank (reuses slice-1's `owner-action`, MEM-15 unchanged: still non-protecting, still keyed off `rankOwner` for fresh-owner support), no new prompt id (`memory.revise_beliefs` stays v1 — the block rides the user message like the OWNER SAID precedent, so gate-off is byte-identical).
- MCP read tools in `internal/mcp/memory.go`: `memory_map`, `memory_open`, `memory_recall`. CLI `cmd/memory.go`: `status`, `reindex`, `open <ref>`, `recall <query>`, `consolidate`, `index`, `seed [--dry-run]`, `digest-compare [--since --out]`.
- See `docs/inventory/memory.md` for MEM-01..15 and the known v1 limitations. Migrations: 00018 (semantic tier), 00019 (`memory_dispute_flags`, index `subject`/`confidence`, `memory_chat_turn_floor`), 00022 (`memory_gmail_last_extracted_ts`, `memory_last_interaction_id`, `memory_engagement`; renumbered from 00020 past the transcriber stack's 00020/00021), 00023 (`memory_calendar_last_extracted_ts`), 00024 (`memory_provenance` episode-window index, `memory_digest_shadow` compare telemetry). No migration in slice 4 — mirrors are vault nodes keyed by alias, no new schema.

### Google Multi-Account (sub-project 1 of 3 of the multi-account initiative, 2026-07-30)
- `google_accounts` table (migration 00043) replaces the old single-account model: one row per connected Google account (`email`, `label`, `client_id`, `calendar_enabled`/`gmail_enabled`, `status`/`error`, its own `gmail_last_internal_date` Gmail-sync watermark, its own `memory_gmail_last_extracted_ts` memory-extraction watermark). `calendar_auth_state`/`gmail_auth_state` singleton tables and the `gmail.account_email` config key are retired; `gmail_messages` gains `account_id` (PK `(account_id, id)`), `calendar_calendars` gains a nullable `account_id` (NULL for CalDAV/ICS rows), `calendar_events` gains `ical_uid` (dedup enabler, unused in v1). A pre-multi-account install migrates in place: the goose migration seeds account #1 from existing data; `ensureLegacyGoogleAccount` (`cmd/google_legacy.go`) finishes the job in Go (renames `google_token.json`/`gmail_token.json` → `google_token_1.json`, fills `email`) and is idempotent — called from daemon sync wiring, `google login`/`gmail login`/`calendar login` (the legacy aliases, now thin wrappers over account #1), and `google add` (seed-only; `add` still always creates a NEW account after).
- Per-account token (`google_token_<id>.json`) and optional custom-OAuth-client credential (`google_credentials_<id>.json`, non-secret `client_id` mirrored to the DB row for display, secret file-only) stores. `wireGoogleSyncers` (`cmd/sync.go`) iterates `ListGoogleAccounts` and builds one `calendar.Syncer`/`gmail.Syncer` per enabled account (gated by the global `cfg.Calendar.Enabled`/`cfg.Gmail.Enabled` daemon-phase switches, same as every other sync phase) — one account's auth failure records only *its* `status`/`error` and never blocks the others (the `wireImapSyncers`/`wireCalDAVSyncers` fan-out pattern). Calendar stale-cleanup is scoped per `account_id` so account A can never delete account B's calendars.

### Slack Multi-Account (sub-project 2 of 3 of the multi-account initiative, 2026-07-31)
- `slack_accounts` table (migration 00048) replaces the single-org `workspace.current_user_id`/`search_last_date` fields: one row per connected Slack organization (`team_id`, `team_name`, `team_domain`, `label`, namespaced `current_user_id`, `status`/`error`, `enabled` soft on/off, its own `search_last_date` search-sync watermark). `workspace.current_user_id`/`search_last_date` columns are dropped; `workspace.id/name/domain` stay as a frozen legacy snapshot of account #1 (nothing reads them by key). **Namespaced string ids, not a composite PK** (unlike `gmail_messages`): `channels.id`/`users.id`/`messages.channel_id`/`messages.user_id` — and every table that copies those values (digests, `tracks`, `situations`/`situation_signals`, `feedback`, `channel_settings`, `jira_slack_links`, memory `""`-scheme provenance) — hold `"<accountID>:<rawSlackID>"` (the `gmail:<acct>:...`/`imap:<acct>:...` precedent). Column types are unchanged, so every downstream query treating these as opaque unique strings keeps working with zero signature changes; only live-Slack-API callers and cross-account-ambiguous renderers resolve the account. `slack.Namespace(accountID, rawID)` / `slack.SplitAccountID(id)` (`internal/slack/namespace.go`) are the single pack/unpack points.
- A pre-multi-account install migrates in place: the goose migration seeds account #1 from the `workspace` row and rewrites every scalar TEXT id column to the `"1:"` prefix; `ensureLegacySlackAccount` (`cmd/slack.go`/`cmd/slack_test.go`) finishes it in Go (moves the `config.yaml` `workspaces.<team>.slack_token` into `slack_token_1.json`, blanks the config token) and is idempotent — called from daemon sync wiring, `slack add` (seed-then-create), and the `auth login`/`auth logout` legacy aliases (now thin wrappers over account #1).
- Per-account token store `slack_token_<id>.json` (0600, `internal/slack/token_store.go`) — secrets out of the DB and out of argv, matching `google_token_<id>.json`. `wireSlackSyncers` (`cmd/sync.go`) iterates `ListEnabledSlackAccounts` and builds one `sync.Orchestrator` per account (`NewOrchestrator(database, client, cfg, accountID)`, namespacing at every DB write, stripping the prefix only at live-Slack-API call sites) — one account's auth failure records only *its* `status`/`error` via `SetSlackAccountAuthState` and never blocks the others (the `wireImapSyncers` fan-out pattern); zero-accounts is a clean no-op.
- CLI: `watchtower slack add [--label L] [--no-open] [--app-return]` (OAuth → new row + token file), `slack login --account <id>` (re-consent), `slack accounts` (list), `slack enable <id>`/`slack disable <id>` (soft on/off — disabled skips sync, synced data stays queryable), `slack remove <id>`. **`slack remove` is NON-destructive** (deliberate departure from `google remove`'s cascade): it deletes the token file and sets `status='removed'`/`enabled=0` but keeps the `slack_accounts` row (for label/domain attribution of historical permalinks) and does NOT cascade-delete channels/messages/digests/tracks/situations/memory.
- Inbox: Slack inbox items reference `messages.channel_id` directly, so namespacing is inherited for free (no special channel_id construction, unlike Gmail). Own-message suppression is a direct string compare — `messages.user_id` and `slack_accounts.current_user_id` are both `"<acct>:<Uxxx>"`; `db.ListOwnerSlackUserIDs()` feeds `ListStreamCandidatesSince(ownerIDs, ...)` so every connected account's owner id is excluded. The system prompt lists all connected workspaces via `db.FormatConnectedWorkspaces` (`internal/ai/context_builder.go`); permalink/deeplink rendering resolves each message's account from its `channel_id` prefix (`ai.response_renderer.go`). See `docs/inventory/inbox-pulse.md` INBOX-09 for the shared-watermark note.
- **Documented v1 identity-scoping decisions (deliberate, not oversights):** (1) `db.GetCurrentUserID()` (Jira detection, style-sample, people-card lookup, `cmd/profile.go`) stays pinned to account #1 — the app is conceptually single-owner; only Slack ingestion, inbox stream-candidate exclusion, and own-message suppression are genuinely multi-account. (2) JSON-embedded id columns (`tracks.channel_ids`/`participants`, `people.starred_channels`, config `shared_channel_ids`) and the memory vault's markdown files are NOT rewritten by the migration — only scalar TEXT id columns are; pre-migration blobs keep bare ids as frozen historical text. (3) `slack remove` non-destructive (above).
- Desktop: Settings → Slack is greenfield (no prior account-management screen) — `SlackAccountsViewModel` + `SlackAccountQueries` (GRDB) drive an account list (row = label/team + status + Enable/Disable + Remove); "Add Slack Account" sheet (`AddSlackAccountView`) runs `slack add --app-return` through the same in-app WKWebView OAuth flow Google/Gmail use.
- Design/plan: `docs/superpowers/specs/2026-07-31-slack-multi-account-design.md`, `docs/superpowers/plans/2026-07-31-slack-multi-account.md`. Non-goals (v1): cross-account message/channel dedup, concurrent OAuth flows, per-account sync schedules, cascading deletion on removal. Unrelated to the pre-existing `active_workspace` mechanism (fully-isolated Watchtower profiles keyed by team name), which is left untouched.

### Jira Multi-Account (sub-project 3 of 3 of the multi-account initiative, 2026-08-02)
- `jira_accounts` table (migration 00049) replaces the config-singleton site model (`jira.cloud_id`/`site_url`/`user_display_name` in config.yaml, now frozen — nothing reads them): one row per connected Atlassian site (`cloud_id`, `site_url`, `site_name`, `label`, `status`/`error`, `enabled` soft on/off, its own `memory_jira_last_extracted_ts` memory-extraction watermark, moved off `workspace`). **Composite PKs, not namespaced strings** (the google_accounts route, deliberately unlike Slack): issue keys ("PROJ-123") are user-visible and live in regexes (key detector ×3 copies), prompts (`"jira:PROJ-123"`), `targets.source_id`, memory `jira:` refs, and MCP args — prefixing them would break all of that. Every site-scoped table gains `account_id NOT NULL REFERENCES jira_accounts(id) ON DELETE CASCADE`: `jira_boards`/`jira_sprints`/`jira_custom_fields`/`jira_issue_links` `(account_id, id)`, `jira_issues (account_id, key)`, `jira_board_field_map (account_id, board_id, field_id)`, `jira_sync_state (account_id, project_key)` (shared project keys no longer clobber watermarks), `jira_releases (account_id, id)` + `UNIQUE(account_id, project_key, name)`. `jira_user_map` (Atlassian ids globally unique) and `jira_slack_links` (text-detected keys are site-ambiguous by nature) are deliberately NOT scoped. **Bare-key readers keep their signatures** — a key shared by two sites resolves to an arbitrary site's row (documented v1 ambiguity, the `mail:`/`gmailthread:` precedent); only writers and board/sprint-scoped readers gained an `accountID` param (models carry `AccountID`, upserts read it from the struct).
- A pre-multi-account install migrates in place: the goose migration seeds account #1 when synced Jira data exists (empty `cloud_id` — SQL can't see config); `ensureLegacyJiraAccount` (`cmd/jira_legacy.go`) finishes in Go (guard = legacy `jira_token.json` **file** existence, the Google C1 lesson; fills identity from config, renames token → `jira_token_1.json`) and is idempotent — called from daemon wiring, `jira add` (seed-then-create), and the `jira login`/`logout`/`status`/`sync` legacy paths.
- Per-account token store `jira_token_<id>.json` (`jira.NewTokenStore(dir, accountID)`; `Load` keeps its error-on-missing contract, wiring gates on `Exists()`). `wireJiraSyncers` (`cmd/sync.go`) iterates `ListEnabledJiraAccounts` → one `jira.Syncer` per account (`NewSyncer(..., accountID)`) with its own per-account `BoardAnalyzer`/`FieldDiscovery`; a broken account records only *its* `status`/`error` (only flipping a currently-`ok` account) and never blocks the others. Daemon: `SetJiraSyncers([]*jira.Syncer)` (was singleton), `phaseJiraSync` loops accounts, aggregates board-analyzer usage into one `jira-boards` run, `SyncJiraTargetStatuses` once after a clean pass; `cfg.Jira.Enabled` stays the global phase switch.
- CLI: `watchtower jira add [--label L] [--site URL] [--no-open]`, `jira login [--account N]` (re-consent, prefers the account's current site; account #1 created on first use), `jira accounts`, `jira enable <id>`/`jira disable <id>`, `jira remove <id>` — **non-destructive** (Slack precedent: token deleted, row `status='removed'`, synced data kept). `jira logout` = remove account #1 — deliberate behavior change: the old logout wiped all `jira_*` tables via `ClearJiraData`, which is deleted. Per-account commands (`boards`/`sync`/`fields`/`boards analyze`/`override`) take a persistent `--account` flag defaulting to the single enabled account.
- Memory: `runJiraIngest` loops enabled accounts (the `runGmailExtract` precedent), each against its own `jira_accounts.memory_jira_last_extracted_ts`; `jira:<KEY>` provenance and `jiraissue:<KEY>` aliases stay account-unscoped (documented v1 limitation mirroring `mail:`) — see `docs/inventory/memory.md`.
- Desktop: Settings → Jira is an account list (`JiraAccount`/`JiraAccountQueries`/`JiraAccountsViewModel`/`AddJiraAccountView`/`jiraSettingsSection` — structural copies of the Slack four); browse-URL resolution moved off the frozen config keys: `JiraConfigHelper.readSiteURL()` reads the first enabled account's `site_url` from the DB (pool wired in `AppState.initJiraAccounts`), yaml as pre-migration fallback — per-issue site resolution is a documented v1 non-goal. `JiraQueries.isConnected()`/`JiraAuthService` accept any `jira_token*.json`.
- Design: `docs/superpowers/specs/2026-08-02-jira-multi-account-design.md`. Non-goals (v1): cross-site issue-key dedup/disambiguation, per-issue Desktop browse links, concurrent OAuth flows, per-account sync schedules, per-account custom OAuth clients, cascading deletion on removal.

## Database & Migrations

Schema changes use **goose** migrations — numbered SQL files in `internal/db/migrations/` (`0000N_<name>.sql`, each with `-- +goose Up` / `-- +goose Down`), auto-discovered via `//go:embed` and applied on `db.Open`. There is **no** hand-edited "schema version" int and PRAGMA `user_version` is legacy (Swift uses it only as a floor check). `CurrentSchemaFormat` in `internal/db/migrations.go` is the migration-engine version, not your schema version — do not bump it for ordinary changes.

When adding a table/column/CHECK, also mirror it into `internal/db/schema.sql` (embedded and injected into the AI prompt), add new tables to `TestAllTablesExist`, and regenerate the snapshot (`go test ./internal/db/ -run TestSchemaGolden -update`). SQLite has no `ALTER TABLE ... ADD CONSTRAINT`, so expanding an enum CHECK (`feedback.entity_type`, `targets.source_type`, `inbox_items.trigger_type`) requires the table-recreation dance — see `internal/db/migrations/00002`/`00003`.

The repeatable dev flows (migration, new AI prompt, new pipeline end-to-end, new Desktop tab) are documented as project skills in `.claude/skills/` (`add-migration`, `add-ai-prompt`, `add-pipeline`, `add-desktop-feature`). Use them; they encode the load-bearing steps and gotchas.
