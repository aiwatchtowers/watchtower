## Findings

### High

**H-1 — Any chat message starting with `-` fails before reaching the model (main chat and every Discuss chat).**
- `WatchtowerCore/Services/WatchtowerAIService.swift:101` builds `["ai", "query", prompt, …flags]` — prompt is a bare positional, no `--` separator, flags come *after* it.
- `cmd/ai.go:41` (`cobra.ExactArgs(1)`), `:92` (`prompt := args[0]`); no `DisableFlagParsing`/`SetInterspersed(false)` on the command.
- Downstream the same token is again a raw argv value: `internal/ai/client.go:107` (`"-p", userMessage`) — the `reference_claude_cli_argv_leading_dash` class, now at two layers.
- Intended: the chat accepts whatever the owner types (`docs/review/review-rules.md` chat contracts; CLAUDE.md "Target Brief Chat" — Enter sends the composer text as the first owner message).
- Actually: cobra rejects `"-hello"` with `unknown shorthand flag: 'e' in -ello` and `"--summarize this"` with `unknown flag: --summarize this` (observed with a non-existent config; the parse happens before `RunE`). Surfaces as `WatchtowerAIError.exitCode` → `errorMessage` (`ChatViewModel.swift:193-196`).
- Scenario: the owner pastes a bullet list ("- check the deploy\n- ping QA") into the target composer and presses Enter → the target row is created (mechanical path, TGT-BRIEF-02 holds) but the brief never reaches the assistant; the chat shows a CLI error. Same for a `--- notes ---` header in main chat.
- Contract: none numbered; UX-breaking on the two action surfaces. `ask "<question>"` (`cmd/ask.go:26`) has the identical exposure.
- No test covers a dash-leading prompt (`Tests/Core/WatchtowerAIServiceTests.swift:10-89` use `"hello"`/`"hi"`).

**H-2 — `ai.provider: ollama` is silently remapped to Claude in the Desktop main chat.**
- `App/AppState.swift:258-259`: `let provider: AIProvider = configProvider == "codex" ? .codex : .claude` — `AIProvider` has `.ollama` (`ChatViewModel.swift:20-33`) but the config mapping never produces it.
- Consequence chain: `ChatViewModel.swift:70` `toolsAvailable = selectedProvider != .ollama` → true; `:142` passes `--provider claude` (overriding the yaml); `:147,286-289` emits `--tools chat`; the system prompt advertises tools. On an Ollama-only machine every turn fails with "claude CLI not found" (`internal/ai/client.go:412-414`) until the owner re-picks Ollama in the picker — per session, the choice is not persisted.
- Target chat decides from config correctly (`TargetChatViewModel.swift:150` via `Constants.aiProviderID()`), so the two surfaces disagree.
- Intended: CLAUDE.md "Model & Provider Registry" — Ollama is a first-class provider; AGENT-04's `testOllamaSendsNoToolModeAndHonestPrompt` (`ViewModelTests.swift:738`) injects `.ollama` directly and never exercises this mapping.
- Not the owner's live config (claude), so latent for them, but it is the exact "feature never fires" shape the audit is after.

### Medium

**M-1 — Prompt version auto-upgrade is only partially honest.**
- Mechanism: `internal/prompts/store.go:108` upgrades when `existing.Version < defaultVer && !existing.Customized`. `prompts.version` is bumped by **every** edit (`internal/db/prompts.go:73` `UpdatePrompt`, `:37` `UpsertPrompt` = `max(existing+1, p.Version)`), so it counts edits AND stands for the shipped default version.
- (a) **Reset strands the row:** `Store.Reset` (`store.go:205-211`) writes `customized=false` but bumps version (`UpdatePrompt` +1). Row seeded v1 → edited (v2, customized) → reset (v3, not customized) → a later default bump to v2 is `3 < 2 = false` → never applied. The doc comment promises the opposite ("putting the row back on the default lineage so a later default-version bump auto-upgrades it again", `store.go:202-204`).
- (b) **No backfill in 00055:** `internal/db/migrations/00055_prompt_customized_flag.sql:8` adds `customized DEFAULT 0` and does not mark rows whose `prompt_history` carries a non-seed reason. Every tuner apply / manual edit made before 00055 is still on the "one later bump then clobbered" path the migration's own comment describes (`:2-5`).
- (c) Upgrade runs only from `db migrate` (`cmd/db.go:26-30`) and `watchtower prompts …` (`cmd/prompts.go:317`); the daemon never calls `Seed` (no hit in `cmd/sync.go`/`internal/daemon`). The Desktop runs `db migrate` on every launch (`DatabaseManager.swift:137-158`), so Desktop installs upgrade at launch; a CLI-only daemon install upgrades only when someone runs a migrate — and `Store.Get` (`store.go:125-138`) returns the stale DB row, not the new default.
- Stale comment: `defaults.go:99-102` still says customization is "detected by comparing template text".
- Scenario: the owner customised `digest.channel` in the Prompts tab before 2026-08 (pre-00055). `DigestChannel` is at v5 (`defaults.go:104`); the next bump to v6 overwrites their text at the next app launch. Conversely, a prompt they reset after editing will never pick up future improvements.

**M-2 — `targets.extract` and `targets.link` prompts are editable but dead.**
- Seeded/listed: `internal/prompts/store.go:38-39`, `defaults.go:30-31,124-125,174-175`; shown in Settings → Prompts and `watchtower prompts list`.
- Never read: `internal/targets/extractor.go:136` formats `ExtractPromptTemplate` (`internal/targets/prompts.go:10`), `linker.go:46` formats `LinkPromptTemplate` (`:69`); no `Store.Get(prompts.TargetsExtract|TargetsLink)` anywhere (grep over `internal`/`cmd`, non-test: zero hits).
- Intended: "DB-backed prompts + tuner" (`reference_feedback_prompt_system`, `add-ai-prompt` skill): every prompt row in the store is the live template.
- Scenario: the owner tunes `targets.extract` to stop the extractor inventing due dates → the Extract button keeps using the compiled constant; the edit and its history are inert.

**M-3 — Wave-2 tools leak into the target chat (owner decision).**
- `internal/tools/tracks.go:23,30`, `ideas.go:29`, `remind.go:29`, `brief.go:28` register with no `Surfaces`; `Registry.List` treats empty as "every surface" (`registry.go:181-190`); `cmd/mcp.go:79-84` mounts `reg.List(surface)` for `--surface target` too.
- `create_target` is main-only precisely because "the target chat's mandate forbids creating work outside its vertical line, TGT-BRIEF-01 axis 3" (CLAUDE.md "Agent Actions"; `tools/targets.go:88`). `create_track` and `create_idea` create work outside that line just the same; `create_idea`/`remind_me`/`brief_context` are seeded `execute` (00064), so in the target chat they run with no Approve at all.
- The wave-2 spec chose "Surfaces unset (chat-visible where relevant)" (`docs/superpowers/specs/2026-09-06-reaction-commands-wave2-inbox-action-strip-design.md:83`) without reconciling it against TGT-BRIEF-01. Contract-adjacent → flagged, not resolved.

**M-4 — Tier table gaps put cheap feedback/learning calls on the strong tier.**
- `internal/digest/models.go:19` lists the light sources. Tagged-but-unlisted → strong: `inbox.situation_learn` (`internal/inbox/situation_feedback.go:114`), `catchup.learn` (`internal/catchup/learn.go:62`), `targets.next_step` (`internal/targets/nextstep.go:81`). Untagged → strong and logged as `source:"unknown"`: meeting recap/notes/prep/extract-topics (`internal/meeting/recap.go:63`, `transcript_recap.go:50`, `transcript_notes.go:49`, `pipeline.go:227`, `extract.go:56`), `tasks.generate/update` (`cmd/targets_ai.go:420,548`).
- Under the live config strong = **opus**, so every 👍/👎-with-comment on a situation or catch-up topic, and every next-step refresh, is an opus call. Correctness is unaffected; cost/latency is. The meeting ones are probably intended strong — but they should be tagged so `sessions.log`/usage attribution stops reading `unknown`.

### Low

**L-6 — `InboxFeedView` is dead code.** `Navigation.swift:203-204` routes `.inbox` to `ActionStripView`; `InboxFeedView(` is never instantiated. Known and flagged in-code for the demolition follow-up (`ActionStripView.swift:5-7`).

**L-7 — Test artefact in source tree.** `internal/repl/watchtower.db` (0 bytes, gitignored) — a test opens the DB relative to the package dir.
