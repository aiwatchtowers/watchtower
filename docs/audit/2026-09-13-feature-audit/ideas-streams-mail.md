## 2. Findings

### Critical

None that crashes or corrupts the registry. The most severe item (F1) is silent data loss in stage 1, which I rank High because it violates a numbered contract rather than Critical because the registry itself stays consistent.

### High

**F1 — Stage-1 Gmail/Jira floors advance past material that was dropped for prompt budget (IDEA-01 stage-1 clause violated).**
Refs: `internal/ideas/email_digest.go:156-182` (`renderEmailBlock` `break`s at budget, dropping the thread from block AND tags), `:248` (500-message load), `:285-293` (`maxTS` computed over ALL `msgs`), `:307` (`SetIdeasEmailFloor(acct.ID, maxTS)`); `internal/ideas/jira_digest.go:43-92` (`renderJiraBlock` stops at budget), `:173` (300-issue load), `:182-188` (`maxUpdated` over ALL issues), `:239` (`SetIdeasJiraFloor(acct.ID, maxUpdated)`); budget default `internal/config/defaults.go:42` (60 000 chars).
Intended: `docs/inventory/ideas.md` IDEA-01 — "When the input cap truncates a run, floors advance only past the rows actually included… The same contract applies one level up, per stage-1 source"; spec `2026-08-07-ideas-registry-design.md` §6.3 ("chunked; one light-tier call per chunk") and §7 ("overflow carries to the next run by not advancing the floor past the last included row").
Actual: one call per account per pass, and the per-account floor is set from the full loaded window, not from the rendered subset. A thread/issue left out of the block is also left out of the valid-ref set (IDEA-02 is fine), but it is never shown to any model again.
Concrete failure: the daemon was off over a weekend; Monday's first `phaseStreamDigests` loads the 500 oldest unseen Gmail messages (~350 threads at 240-byte excerpts ≈ 100–150 K chars); `renderEmailBlock` fits roughly the first 120–150 threads into 60 K and breaks; `SetIdeasEmailFloor` jumps to the newest of all 500. The remaining ~200 threads are never mined. For Jira the arithmetic is worse: an issue renders up to 500 + 20×500 ≈ 10.5 K chars, so a 300-issue window (a normal 6 h of activity on a multi-project corporate site) may render only 6–20 issues before the floor jumps past all 300, project groups after the first budget-exhausted one being dropped entirely (`jira_digest.go:80-82`). Because ordering is by `updated_at ASC` but rendering is grouped by project in first-seen order (`:44-51`), the floor can even advance past an issue in a *later* project whose `updated_at` is lower than rendered ones.
The backfill drain (`backfill.go:125-176`) repeats this every cycle, so a month-long "Find Ideas" over a busy mailbox mines a minority of its threads while reporting a clean run.
Guard gap: `internal/ideas/stage1_bounds_test.go:69-131` asserts only block/tag membership, never the floor. **Implicates IDEA-01 — needs owner decision** (fix shape: floor = max ts/updated_at of the rendered units only, or chunk into multiple calls as §6.3 designed).

**F3 — Gmail/Jira "stream digests" in the Digests tab are not digests; the feed shows unread, empty rows by design.**
Refs: prompts `internal/prompts/defaults.go:1457-1469` and `:1477-1489` ("extract IDEAS and DECISIONS … not routine mail … empty is the common and correct answer"); `internal/ideas/email_digest.go:48-59` (`validateRefs` drops every topic with no surviving candidate); `:295-302` / `jira_digest.go:227-234` (a row is inserted whenever `len(msgs) > 0` / `len(issues) > 0`, even with `topics == []`); Swift `StreamDigestQueries.fetchAll` (`StreamDigestQueries.swift:5-11`, no emptiness filter), `DigestListView.swift:553-599` (row renders badge + date only when `topics.first` is nil; `scope` is always `''` per spec §6.4), `StreamDigestDetailView.swift:21-23` ("No topics in this digest.").
Intended: spec `2026-08-12-decisions-split-cross-source-digests-design.md` Goal 3 ("Digests tab shows all streams… one feed, grouped by day, labeled by source") and B2 ("Row shows scope/period + topic titles; detail renders topics_json (title, summary, ideas[], decisions[])"). CLAUDE.md calls them "Gmail/Jira stream-digest rows".
Actual: the substrate was designed (2026-08-07 §4) as an idea-candidate pre-digest, and `validateRefs` strips any topic that carries only a title/summary. So the Digests tab receives, every 6 h per Gmail account with any new mail and per Jira account with any updated issue, a row that is usually contentless yet flagged unread (`read_at IS NULL`, counted into `unreadStreamCount`, `DigestViewModel.swift:283`, and the tab badge `DigestListView.swift:925-929`).
Concrete failure: with `gmail.enabled` and `jira.enabled`, the owner opens Digests and sees, per day, up to 4 Gmail + 4 Jira rows with a blue unread dot, no title, no topics; opening one shows "No topics in this digest." — the exact "features don't work" impression. Not a contract violation; **WORKS DIFFERENTLY vs. the 2026-08-12 spec. Needs owner decision** (skip inserting/showing empty rows, or give the prompt a real summary duty).

**F4 — Owner-preference block is polluted by mined decisions (feedback loop degraded).**
Refs: `internal/ideas/preferences.go:15-38` (`ListIdeaVerdictExamples(20)`, `status == "active"` ⇒ LIKED); `internal/db/ideas.go:364-385` (`WHERE owner_rating != 0 OR status IN ('rejected','dropped','active') ORDER BY updated_at DESC LIMIT 20`, no `kind` filter); `internal/ideas/consolidate.go:706-710` (every mined decision is born `active`); Swift `createManual` births notes `active` (`IdeaQueries.swift:318-336`).
Intended: spec §5.1 — "the consolidator prompt receives a preferences block built from recent rejected/disliked and approved/liked examples"; §2 — "👍/👎 with optional comment trains the miner".
Actual: since 2026-08-12, `active` no longer means "owner approved" for decisions (and never did for notes). The 20 newest verdict examples are dominated by born-`active` mined decisions (the spec itself cites 49 in the owner's registry), each rendered under "LIKED/APPROVED". Genuine owner rejections older than the 20 newest decision headlines fall out of the block entirely.
Concrete failure: the owner rejects five Slack ideas on Monday; by Tuesday the daemon has minted 20+ decisions (all `active`, all newer by `updated_at`), so `=== OWNER PREFERENCES ===` shows only "LIKED/APPROVED: <20 decision titles>" and none of the rejections — the consolidator is taught the opposite of the owner's taste. Not a numbered contract, but it hollows out spec Goal §2.

### Medium

**F5 — Consolidator dedup context is capped at 300 open items and decisions never leave `active`.**
Refs: `internal/db/ideas.go:333-344` (`ideasForPromptLimit = 300`, `status IN ('proposed','active','not_now') OR updated_at >= -60d`); `consolidate.go:749-751` (`attach_mention` to an id outside the slice is silently skipped), `:711-715` (`similar_to` likewise); decisions terminal only via owner Supersede/Reverse (`DecisionDetailView.swift:288-297`).
Actual: once the registry holds >300 open items (decisions accrue monotonically at a few per day), the stalest fall out of the prompt; a repeat sighting of one of them can only surface as `new_decision`, and IDEA-05 cannot catch it (different ref). Concrete failure: a recurring "we agreed to freeze deploys on Fridays" decision from March is re-minted in September because its row is #301 by `updated_at`; the ledger shows two entries. Spec §2 dedup goal degrades silently; no log line.

**F6 — IMAP/Outlook mail is invisible to stream digests, the registry, Catch-Up "streams", and memory.**
Refs: consumers of `imap_messages` are only `internal/inbox/imap_detector.go` (grep over `internal/`, `cmd/`); `runEmailDigests` iterates `ListGoogleAccounts()` only (`email_digest.go:197-203`).
Intended: spec `2026-08-07` §2 "mines ideas and decisions out of all connected streams"; 2026-08-12 Goal 3 "shows all streams". Neither spec names IMAP as in or out of scope.
Actual: an owner whose work mail is Outlook (the IMAP path exists precisely for that) gets inbox triggers but no email pre-digest, no email-sourced ideas, and no email rows in Digests. **Needs owner decision** (scope statement or a second email source).

**F7 — Transcript lane loses recaps once the calendar event ages out (14 days) — hits backfill and any long daemon outage.**
Refs: `internal/db/ideas.go:815-819` (`LEFT JOIN meeting_recaps mr ON mr.event_id = mt.event_id`); schema `internal/db/schema.sql:990` (`meeting_recaps.event_id … ON DELETE SET NULL`) and CLAUDE.md (transcripts' `event_id ON DELETE SET NULL`); calendar stale-delete window `internal/calendar/sync.go:47,186` with `EffectiveHistoryDays` default 14 (`internal/config/config.go:178-183`, `defaults.go:71`); `consolidate.go:342-350` (recap-less + not recent ⇒ floor advances, no AI call).
Actual: after the event row is deleted both `event_id`s become NULL, the join can never reconnect them, and event-linked recaps are not mirrored into `summary_json` (collision guard only). The consolidator then treats the transcript as recap-less, and since it is older than 48 h it is consumed silently.
Concrete failure: "Find Ideas" over the last quarter mines zero ideas from any event-linked meeting older than two weeks, and reports nothing about it (`TranscriptForIdeas.RecapJSON` is `''`). Forward path: a daemon outage ≥ 14 d has the same effect on that fortnight's meetings. (The same join shape backs the Recordings tab's recap resolution — flagged for the calendar/recordings auditor.)

**F8 — Gmail sync drops a message permanently on a transient `GetMessage` failure.**
Refs: `internal/gmail/sync.go:100-104` (`continue` on fetch error), `:137-147` (watermark = max over successes). The IMAP syncer has a `stalled` guard for exactly this (`internal/imap/sync.go:124-125`); Gmail does not.
Concrete failure: a 5xx on one message in the middle of a batch; later messages upsert and push `gmail_last_internal_date` past it; the next cycle's `after:<watermark>` never lists it again. Low probability per message, but permanent.

### Low

**F9 — Desktop backfill summary hides the honesty counters.** `IdeasViewModel.swift:384` renders only proposed/cycles/deduped; `capped`, `slack_refs_dropped`, `refs_rejected` from the envelope (`cmd/ideas.go:114-133`) are parsed (`IdeaBackfillEnvelope`) but not shown, so the owner cannot tell "window empty" from "window capped at 50 cycles" or "every candidate discarded" — the very distinction IDEA-02's 2026-08-10 changelog says must be owner-visible on every path.

**F10 — Flagless `ideas mine` (and the Catch-Up top-up `cmd/catchup.go:166`) run stage 1 without the backfill lock.** `cmd/ideas.go:243-262` never calls `AcquireBackfillLock`; a CLI run overlapping `phaseStreamDigests` races the same per-account floor — two `stream_digests` rows for one window (duplicate feed rows), registry protected by IDEA-05.

**F11 — Jira floor init/lower in `+0000` vs site-offset strings.** `jira_digest.go:161` and `backfill.go:359` write `FormatJiraTime(UTC)`; `ListJiraIssuesUpdatedSince` compares raw strings (`internal/db/ideas.go:936-954`). For a site whose API returns a negative offset, the first window after init/lower misses up to |offset| hours until the first issue self-consistently re-seeds the floor; for positive offsets it re-reads up to |offset| hours (dedup-safe). One-time, per init.

**F12 — Merge does not refresh the survivor's `last_mention_at`.** `IdeaQueries.merge` (`IdeaQueries.swift:274-287`) re-parents mentions but leaves the target's `last_mention_at`/`updated_at` untouched, so the ledger/list ordering ignores the absorbed history.

**F13 — Spec §8 deep links for Gmail and meeting mentions are absent by design.** `IdeaDetailPane.swift:306-324` returns nil for `.gmail`/`.meeting` (documented in code). `digest_topics.ideas` is never rendered in the Slack digest UI (spec §12.5 follow-up still open; no Swift consumer of the column).

**F14 — Flagless CLI copy is stale.** `cmd/ideas.go:33-34` still describes `ideas mine` as "Gmail/Jira pre-digests, then consolidation" while `pipeline.go:154-160` says `Run` "no longer touches the Gmail/Jira passes" — true for the daemon, but `runIdeasMineIncremental` does run both, so the CLI is right and the `Run` doc comment is the misleading one. Cosmetic.

## 3. Needs owner decision

1. **F1 (IDEA-01 stage-1 clause):** accept the loss as a documented v1 limitation, or fix by (a) chunking stage 1 into multiple calls per pass as spec §6.3 designed, or (b) advancing the per-account floor only to the newest *rendered* unit. Either changes a guarded contract's surface; the inventory text currently claims the protection exists.
2. **F3 (Digests tab stream rows):** decide whether `stream_digests` is (a) an ideas substrate that should *not* appear in the Digests feed when empty, or (b) a real per-source digest, which requires the prompt to also summarise routine activity and `validateRefs` to keep summary-only topics. Today the tab implies (b) while the pipeline is (a).
3. **F4/F5:** whether `active` decisions should count as "approved" examples (`ListIdeaVerdictExamples`) and whether the 300-item registry slice should exclude decisions or use a smarter window now that decisions are a journal.
4. **F6:** explicit scope statement for IMAP/Outlook mail vis-à-vis stream digests / registry / memory.
5. **F7:** whether event-linked recaps should be mirrored into `meeting_transcripts.summary_json` (or the join keyed on transcript id) so recaps survive calendar retention — cross-cuts the transcriber module's collision-guard contract.
