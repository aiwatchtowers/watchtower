## 2. Findings

### Critical
None found. No contract (TGT-BRIEF-01..03) is violated by production code.

### High

**H-1 — Briefing ignores the DB-backed prompt registry (tuning/rollback/role variants are no-ops).**
`internal/briefing/pipeline.go:277-282` reads the store only `if p.promptStore != nil`, but neither wiring site ever sets it: daemon `cmd/sync.go:506` (`d.SetBriefingPipeline(briefing.New(...))`, no `SetPromptStore`) and CLI `cmd/briefing.go:139`. Every other tunable pipeline is wired (`cmd/sync.go:508,517`, `cmd/ideas.go:82`, …).
*Intended:* "Feedback & Prompt system — DB-backed prompts + tuner" (`prompts` CLI `cmd/prompts.go:57 tune`, `:50 rollback`); `briefing.daily` is registered (`prompts/store.go:23`) and auto-upgraded (`store.go:107-118`).
*Actual:* `getPrompt` falls to `prompts.Defaults[id]` (`pipeline.go:290`) and stores `PromptVersion: 0` on every row (`pipeline.go:252`).
*Scenario:* owner runs `watchtower prompts tune briefing.daily` (or edits it), `prompts show` displays the customized row, yet tomorrow's briefing is byte-identical to the shipped default; the `Customized` flag also blocks the v7 auto-upgrade for that row while the pipeline keeps using v7 anyway — the registry and the runtime disagree silently. No numbered contract, but it defeats a headline feature.

**H-2 — Day plan: a failed generation is retried on every daemon tick for the rest of the day (strong-tier cost, no backoff).**
`runDayPlanPhase` sets `d.lastDayPlanDate` only on success (`daemon.go:1388-1393`); `shouldRunDayPlan` re-arms whenever `GetDayPlan` is nil (`daemon.go:1360-1361`); `dayplan.Pipeline.Run` writes no row on AI/parse failure (`pipeline.go:122-139`). Poll interval is 15 min (live config).
*Scenario:* if the model returns malformed JSON (or the CLI errors) at 08:05, the daemon fires another `day_plan.generate` (strong tier, `models.go:20-22` default → opus in live config) every 15 minutes until midnight — up to ~64 wasted strong calls/day, each logged only as `dayplan: generation failed`. The briefing phase has the same shape (`daemon.go:1144-1151`, `lastBriefing` set only on `id > 0`) but is cheaper to notice because the Briefings tab shows nothing. Owner sees: an empty Day Plan tab plus an unexpectedly high Usage tab.

**H-3 — `jira.features.*` role defaults are never applied; in the live config every Jira feature toggle is `false`, so the briefing/day-plan/dashboards run without their Jira sections.**
`config.DefaultJiraFeatures(role)` (`defaults.go:130-178`) is referenced only by `jira features` (list/reset) in `cmd/jira.go:1200,1305`; `internal/config/config.go` sets **no** `v.SetDefault("jira.features.*")` (grep: zero hits), and neither `jira add/login`, onboarding, nor the Desktop seed it (`rg` over `WatchtowerDesktop/Sources/Views/Onboarding` → nothing). A fresh install therefore has every toggle off; the live config's 11 explicit `false` keys are consistent with a single `jira features enable/disable` call having serialized the whole struct (`cmd/jira.go:1268 v.Set("jira.features", features)`).
*Readers that go dark:* briefing `my_issues`/`awaiting_input`/`iteration_progress` (`internal/briefing/jira.go:31,38,45`); `internal/guide/jira.go:28`; `internal/jira/{workload,blockers,project_map,release_dashboard,epic_progress,without_jira}.go`; the four CLI dashboards return an error when off (`cmd/jira_dashboards.go:52-53,138-139,249-250,410-411`) while the sidebar keeps Workload/Blockers/Project Map/Releases always visible (`SidebarDestination.swift:99-110` — `requiredFeatures` nil for them).
*Scenario:* owner connects Jira, sees a green account, and the daily briefing never mentions their assigned issues (only the always-on stale/overdue block, `jira.go:52`); the Workload tab fails with "team_workload feature is disabled" because nothing ever ran `jira features reset`. Cross-domain (Jira auditor) for the dashboards; the briefing half is mine. **Needs owner decision** (auto-seed role defaults on `jira add`? seed viper defaults? or document that the toggles are opt-in).

**H-4 — TargetBriefCenter is a single slot: a second Enter-create silently cancels the previous target's running brief.**
`TargetBriefCenter.startBrief` begins with `task?.cancel(); vm?.cancelStream()` (`TargetBriefCenter.swift:55-57`) and `markFailed` does the same (`:99-102`). `cancelStream` persists the partial assistant text and, per `executeStream`, a cancelled stream skips action parsing (`TargetChatViewModel.swift:451-454`) and does **not** append a failure system message (`:438`, cancellation branch). The spec's §6/§7 describe abort only on *app close* (`2026-08-19-target-brief-chat-design.md:54,58`) — no single-slot rule.
*Scenario:* owner types a brief for target A, presses Enter, immediately creates target B with Enter (a normal "dump three tasks" flow). A's run is cancelled mid-stream: A's chat shows the owner's message plus a truncated reply, no cards, no banner (`phase` now says `.briefing(B)`), and no execute-mode action for A was ever applied. Owner sees "I briefed it and nothing happened". Contract-adjacent (TGT-BRIEF-02 promises the row + a *visible* error on failure; a cancelled brief shows neither). **Needs owner decision**: queue briefs (the `MeetingRecorderCenter` FIFO shape) vs keep single-slot but mark A `.failed("superseded")`.

### Medium

**M-1 — `jira_issues.assignee_slack_id` / `reporter_slack_id` were never rewritten to the namespaced form; issues not re-synced since migration 00048 are invisible to "my issues" lookups.**
Migration 00048 rewrites `jira_user_map.slack_user_id` (`00048_slack_accounts.sql:87`) but has no `UPDATE jira_issues SET assignee_slack_id …` (grep over the file: none). `BackfillJiraSlackIDs` only fills rows where the column is `''` (`internal/db/jira.go:429-432`). New/changed issues pick up the namespaced id from the map at sync (`internal/jira/sync.go:501-520`), so only Jira issues untouched since 2026-07-31 keep bare `Uxxx`. Readers pass `GetCurrentUserID()` = `"1:Uxxx"`: day plan `gather.go:169`, briefing `jira.go:22,105`, `internal/db/jira.go:928-958`.
*Scenario:* a long-open assigned issue last updated in June never appears in the day plan or briefing "MY JIRA ISSUES" even after `my_issues` is enabled, while a ticket touched yesterday does. Bare-vs-namespaced class (CLAUDE.md Slack multi-account §"Documented v1 identity-scoping decisions" lists six JSON columns backfilled by 00054 — this scalar column is not among them).

**M-2 — Day plan and briefing require Slack account #1; a Google/Jira-only install never gets either.**
`GetCurrentUserID` reads `slack_accounts WHERE id = 1` (`internal/db/workspace.go:44-54`). `shouldRunDayPlan` returns false on `""` (`daemon.go:1356-1359`), `runDayPlanPhase` likewise (`:1376-1379`); briefing `RunForDate` logs "no current user set, skipping" and returns `0, nil` (`briefing/pipeline.go:126-129`), so `lastBriefing` is never set and the phase re-evaluates every tick (cheap, but the log line repeats every 15 min). Documented as "conceptually single-owner" for `GetCurrentUserID` in CLAUDE.md, but the Day Plan / Briefings tabs stay visible (`SidebarDestination.swift:104-105` gate only on the feature id) and the Desktop "Generate" button then errors (`cmd/day_plan.go:298`). LIMITATION with user-visible malfunction → listed.

**M-3 — Registry prompt rows `targets.extract` and `targets.link` are dead: the extractor/linker use compiled-in templates.**
Registered and seeded (`prompts/store.go:38-39`), shown by `prompts list`, but `prompts.TargetsExtract`/`TargetsLink` are referenced nowhere outside the prompts package (rg over `internal cmd`: only `store.go`/`defaults.go`). The pipeline uses `ExtractPromptTemplate` (`internal/targets/prompts.go:10`, `extractor.go:93`) and `buildLinkPrompt` (`linker.go:25`); `targets.New` has no prompt-store hook (`pipeline.go:28-40`). Same class as H-1 with a smaller blast radius (extraction is user-triggered).

**M-4 — Target delete dual-path drift: Swift delete skips the parent-progress recompute.**
Go `DeleteTarget` recomputes the parent's progress after the delete (`internal/db/targets.go:321-333`); Swift `TargetQueries.delete` is a bare `DELETE` (`TargetQueries.swift:468-470`) called from `TargetsViewModel.deleteTarget` (`:442-450`). Spec 2026-04-24 lists "parent progress recomputed" as shared behaviour (`…targets-delete-design.md:27`).
*Scenario:* parent with 2 children, one done (50%); owner deletes the done child in the Desktop → parent stays at 50% (should be 0%) until some other write triggers a recompute.

**M-5 — Dead `targets.*` config keys.**
`targets.extract.max_per_call` (default 10, `defaults.go:102`) — the cap is hardcoded `10` in `extractor.go:177-184`; `targets.extract.model` (`defaults.go:104`, seeded `config.go:530`) — never read (the call routes `SourceLight`, `pipeline.go:97`); `targets.resolver.slack_enabled`/`jira_enabled` (`defaults.go:106-107`) — never read (only `MCPTimeoutSeconds` and `ActiveSnapshotLimit` are, `cmd/targets_ai.go:76`, `pipeline.go:86`, `nextstep.go:111`). Note `ActiveSnapshotLimit` doubles as the next-step batch cap (`nextstep.go:110-113`) — a resolver knob silently sizing an unrelated strong-tier batch.

**L-1 — `internal/briefing/prompt.go:5-19` documents 14 format verbs; the template and `Sprintf` now carry 15** (`pipeline.go:184-198`, `memRevisionsCtx` added). Doc rot only — arg count matches (verified: 15 `%s` in `defaults.go:456-543`).

**L-2 — Next-step system prompt is a Go constant** (`nextstep.go:47-69`), not a registry prompt — untunable, and its `digest.WithSource(ctx, "targets.next_step")` (`:81`) is not listed in `TierForSource` (`models.go:16-24`) so it lands on the strong tier by the default arm — intended per the comment (`:71-73`) but implicit.

**L-3 — `--text`/`--feedback` travel on argv** (`TargetExtractService.swift:21`, `DayPlanViewModel.swift:196`). Cobra handles a leading `-` value after a flag, and the Go generator switches to stdin above 32 KB, so this is cosmetic unless a pasted message exceeds ARG_MAX.

**L-4 — Every Desktop mutation bumps `updated_at`** (`TargetQueries.swift:256-459`), so each Approve / Approve-all / execute-mode batch marks the target stale and the daemon regenerates its next step once on the following tick (`GetTargetsNeedingNextStep`, `internal/db/targets.go:165-171`) — one strong-tier call per edited target per cycle, up to `ActiveSnapshotLimit` (100) targets × 4 workers (`nextstep.go:110-128`). Expected per the design, but it is the main hidden AI-cost driver of the Targets tab.
