## 2. Findings

### CRITICAL

#### C1. The 11 `jira.features.*` toggles are written under keys the reader cannot see — the whole Jira feature surface is permanently OFF and cannot be turned on from CLI or Desktop
- **Refs:** writer `cmd/jira.go:1265-1269` (`v.Set("jira.features", features)` with a `config.JiraFeatureToggles` struct) and `cmd/jira.go:1307-1311` (`reset` — same shape); struct tags `internal/config/config.go:203-215` (`mapstructure:"my_issues_in_briefing"` … — **no `yaml` tags**); reader `internal/config/config.go:417ff` (viper `Unmarshal`, no `SetDefault` for any `jira.features.*` key); gate `internal/jira/context.go:164-172` `IsFeatureEnabled`; 22 gated call sites listed in the status table.
- **Intended:** `docs/specs/jira-integration-roadmap.md:8,30,90-96` — "Any user can enable/disable any feature", "Desktop App → Settings → Jira Features: toggle switches", "On first connection: defaults based on user role", "AI prompts only account for enabled features". Phase 0.7 marked ✅ DONE.
- **What happens:** viper's `WriteConfigAs` marshals the raw struct with `gopkg.in/yaml.v3`, which — absent `yaml` tags — lowercases the Go field name: `MyIssuesInBriefing` → `myissuesinbriefing`. On the next `config.Load`, mapstructure looks for `my_issues_in_briefing` (exact, then `EqualFold`) and does not match `myissuesinbriefing`, so every flag decodes to its zero value. **Reproduced** against the module's own viper via `go run -overlay` (scratchpad `vipercheck/main.go`): file after `Set` reads `features: { myissuesinbriefing: true, awaitingmyinput: true }`, and `Unmarshal` returns `{MyIssuesInBriefing:false AwaitingMyInput:false}`. This is exactly the 11-key all-`false` block in the owner's live config (`awaitingmyinput`, `blockermap`, `epicprogress`, …) — the bug's fingerprint.
- **Also never implemented:** the roadmap's "defaults based on user role on first connection" — `DefaultJiraFeatures` is only ever *written* by `jira features reset` (`cmd/jira.go:1305-1310`, into the same dead keys); `jira add`/`jira login` never seed it (grep: no other caller). So even a pristine install has all 11 flags `false`.
- **Concrete failure scenario (owner's today):** the owner opens Boards → Jira Features, sees every toggle off with orange "differs from role default" dots (the Desktop compares `features[key]` (all false) with `defaults[key]` from `jira features --json`, `JiraFeaturesSettingsView.swift:211-213`), flips "Team Workload" on → CLI writes `teamworkload: true` → reopening the sheet shows it off again; the daily briefing never gains MY JIRA ISSUES / AWAITING MY INPUT / SPRINT PROGRESS (`internal/briefing/jira.go:31-49`); `watchtower jira workload` answers "team_workload feature is disabled; enable with 'watchtower jira features enable team_workload'" (`cmd/jira_dashboards.go:53`) forever; Desktop digest detail never shows "without Jira" warnings (`Utilities/JiraKeyExtractor.swift:173` reads `without_jira_detection`, which is never written).
- **Blast radius:** everything behind `IsFeatureEnabled` — briefing Jira context (3 sections), people guide `my_issues` (`internal/guide/jira.go:28`), CLI `tracks`/`digest` Jira badges and `--jira/--no-jira` filters (`cmd/tracks.go:187,508`, `cmd/digest.go:200-201,249-250`), the four CLI dashboards, `trends` epic progress + without-Jira (`cmd/trends.go:168,280`), `internal/jira/{workload,blockers,epic_progress,project_map,release_dashboard,without_jira}.go` library gates. The Desktop Delivery tabs are **not** affected (they read tables directly).
- **Not covered by tests:** no `_test.go` references `jira.features`, `setJiraFeatureToggle`, or a config round-trip (grep). `internal/config/defaults_test.go` only asserts the role tables.
- **Inventory contract:** none numbered. Fix is a design choice (see D2): add `yaml` tags mirroring `mapstructure` tags, or `Set` a `map[string]bool` keyed by the mapstructure names, plus a one-time config repair for installs carrying the dead keys, plus (optionally) applying role defaults on first connect as the roadmap promised.

### HIGH

#### H1. Jira key detection is dead code — `jira_slack_links` has never been populated, so every "linked Slack ↔ Jira" surface silently shows nothing
- **Refs:** `internal/jira/key_detector.go:14-124` (`NewKeyDetector`, `ProcessMessage/ProcessTrack/ProcessDigestDecision`); hooks `internal/digest/pipeline.go:185-189,1372-1375` and `internal/tracks/pipeline.go:131-135` (`SetJiraKeyDetector`); **no caller** of `NewKeyDetector` or `SetJiraKeyDetector` in `cmd/` or `internal/` outside tests (grep), and none ever existed (`git log -S"SetJiraKeyDetector" -- cmd` is empty; introduced in `deddd91f`). Only writer of the table is `internal/db/jira.go:533` `UpsertJiraSlackLink`, called solely from the detector.
- **Intended:** roadmap 0.6 ✅ DONE `docs/specs/jira-integration-roadmap.md:83-87` — "Pattern PROJ-123 in Slack messages is automatically detected and linked … Links are available for all downstream features"; CLAUDE.md dev-surface: `get_task_context` resolves "linked Slack threads via `jira_slack_links`".
- **What happens:** the three regex copies agree (`internal/jira/key_detector.go:14`, `cmd/digest.go:707`, `Utilities/JiraKeyExtractor.swift:13` — identical `\b([A-Z][A-Z0-9_]+-\d+)\b`), but none of the Go detectors run in the daemon. Readers: `internal/db/tracks.go:228-230` (`--jira`/`--no-jira` filter → every track is "no Jira"), `internal/db/jira.go:545-570` + Swift `JiraQueries.swift:251-309` (track/digest "Linked Jira Issues" always empty), `internal/mcp/taskcontext.go:54` (`get_task_context` never returns Slack threads → the "watchtower-task-context" skill degrades to ticket+comments only), `internal/jira/without_jira.go:98-115` (step 3 excludes channels with links — none → every active channel flagged), `internal/jira/who_to_ping.go:69`.
- **Concrete failure scenario:** a Slack thread discussing `PAY-123` for a week; the owner asks the coding agent for `get_task_context PAY-123` → no `slack_threads` section; opens the track in Desktop → no linked issue badge; `watchtower tracks --jira` → empty.
- **Inventory:** touches the DEV surface's promised data (`docs/inventory/dev-surface.md`) but does not violate DEV-01..05 (still read-only) — a completeness failure, not a contract breach. Needs owner decision D3 (wire the detector into `runSyncDaemon` next to `pipe.TrackLinker`, or retire the table and its readers).

#### H2. Desktop "Sync now" / "Resolve users" for Jira break as soon as a second Jira site is connected
- **Refs:** `Views/Settings/JiraSyncInfoView.swift:90` runs `["jira","sync"]`; `cmd/jira.go:314-339` `resolveJiraAccount` errors "multiple Jira sites connected — pass --account <id>" when >1 enabled account and no flag.
- **Intended:** CLAUDE.md Jira multi-account: "Per-board actions are account-scoped end to end … both boards screens pass `--account` on every CLI action, and the boards refresh runs `jira boards --account <id>` once per enabled account."
- **What happens / scenario:** with two enabled `jira_accounts`, the Boards → Sync Info button surfaces the CLI error every time; the daemon still syncs both accounts, so data is fine — the manual button is what fails. Single-site owner unaffected (today's owner appears single-site).

### MEDIUM

#### M1. `jira_sync_state.last_error` is never persisted — per-project Jira sync failures are invisible to `jira status`
- **Refs:** `internal/jira/sync.go:134-141` sets `syncState.LastError/LastErrorAt` then calls `UpdateJiraSyncState(accountID, projectKey, lastSyncedAt, issuesSynced)`; `internal/db/jira.go:485-495` writes only `last_synced_at`/`issues_synced`; readers `internal/db/jira.go:499-503,515-524` scan the never-written columns.
- **Scenario:** a board's project JQL starts 400-ing (renamed project). `Syncer.Sync` logs, `continue`s, returns nil (`sync.go:134-141`) → account status stays `ok`, `jira status` shows no error → the owner sees stale issues and no explanation.

#### M2. Google `status` is a shared last-writer-wins cell between the calendar and gmail syncers
- **Refs:** `internal/calendar/sync.go:214-236` and `internal/gmail/sync.go:151ff` both write `SetGoogleAccountAuthState(accountID, …)` (`internal/db/google_accounts.go:127-137`) — `"ok"` on every clean pass, `"error"` on any fetch error.
- **Scenario:** Gmail API returns a transient 503 while Calendar is fine → the row alternates `error`/`ok` each cycle depending on phase order; the Settings badge flickers and the `error` text belongs to whichever service last failed. Cosmetic, but it is the only per-account health signal the Desktop has.

#### M3. Gmail watermark can skip a message permanently after a transient per-message fetch failure
- **Refs:** `internal/gmail/sync.go:100-104` (`GetMessage` error → `continue`), `:137-139` (`maxSeen` raised by later messages), `:143-147` (watermark advanced to `maxSeen`).
- **Scenario:** cycle N lists ids [a,b,c] oldest-first; `GetMessage(b)` times out; `c` upserts → watermark = c → next cycle's `after:<c>` never lists `b` again. Bounded loss (one message per hiccup), but silent.

### LOW

- **L1. New accounts added via CLI are invisible to a running daemon until restart** — `cmd/sync.go:317-321,523-539` wire Slack/Jira/Google syncers once; `google add`/`slack add`/`jira add` don't restart the daemon (the Desktop VMs do: `ViewModels/GoogleAccountsViewModel.swift:119,179,231`, `SlackAccountsViewModel.swift:185`, `JiraAccountsViewModel.swift:192`). Worth a printed hint in the CLI success message.
- **L2. `who_ping` and `write_back` toggles gate nothing** — no `IsFeatureEnabled(cfg,"who_ping"|"write_back")` caller anywhere (grep); `internal/jira/who_to_ping.go` runs ungated. They exist only in the toggle list/UI. `BuildFeatureContext` (`internal/jira/features.go:62-91`, "AI prompts adapt to enabled features") has **no callers** — the roadmap's "AI prompts only account for enabled features" was never wired.
- **L3. Revoked Google/Jira accounts re-attempt every poll and re-stamp status** — `wireGoogleSyncers` (`cmd/sync.go:685-721`) wires every row regardless of `status`; `recordAuthResult` rewrites `revoked` + `updated_at` each cycle (`internal/calendar/sync.go:229-235`); same for Jira in `phaseJiraSync` (`daemon.go:545-550`). Log noise + wasted calls, no data harm.
- **L4. Stale `gmail.account_email` key in live config is dead** — no reader in Go or Swift (grep); harmless, could be dropped by a config tidy.
- **L5. `JiraQueries.isConnected` cross-workspace false positive** — `JiraQueries.swift:115-132`; known (memory `project_jira_isconnected_cross_workspace_bug`), listed for completeness.

## 3. Needs owner decision

- **D1. `GetCurrentUserID()` pinned to `slack_accounts.id = 1`** (`internal/db/workspace.go:44-54`; documented v1). If the owner ever `slack remove`s account #1 and reconnects the same workspace as #2, Jira detection, briefing Jira context, style-sample, people-card, profile role (and thus `jira features` role) all keep using the removed account's `current_user_id` — the `users` rows for both accounts share emails, so `UserMapper.ResolveAll` (`internal/jira/users.go:61-66`) may bind Jira users to either prefix. Decide: keep pinned (document the "never remove #1" rule) or resolve "owner account" = lowest enabled row.
- **D2. How to repair C1** — (a) add `yaml:"…"` tags equal to the mapstructure tags on `JiraFeatureToggles` (or `Set` a map keyed by mapstructure names), (b) one-time migration of the dead keys in existing configs (the owner's file carries all 11), (c) whether to finally apply `DefaultJiraFeatures(role)` on first Jira connect as the roadmap promised, or drop the role-preset story. Any of these changes what the owner's briefing/digests render, so it is a product call, not just a bug fix.
- **D3. Key detector (H1): wire or retire.** Wiring it (`jira.NewKeyDetector(database)` → `pipe.SetJiraKeyDetector` / `tracksPipe.SetJiraKeyDetector` in `runSyncDaemon`, `cmd/sync.go:500-504`) would start writing `jira_slack_links` from digest decisions and tracks only — note `ProcessMessage` (per-Slack-message detection, the roadmap's actual acceptance criterion) has no hook at all in `internal/sync`, so a message-level backfill would be new work. Alternatively retire the table and the five reader surfaces.
- **D4. Toggles that gate nothing (L2)** — remove `who_ping`/`write_back`/`BuildFeatureContext` from the UI and registry, or implement their gates.
