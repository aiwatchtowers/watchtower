## 2. Findings

### Critical
None found.

### High

**H-1. Recap and notes prompts still tell the model "speakers are not labeled" although every diarized transcript now carries speaker labels.**
- Refs: `internal/prompts/defaults.go:894` (`defaultMeetingRecap`: "…automatic single-track audio transcript (speakers are not labeled…"), `internal/prompts/defaults.go:932` (`defaultMeetingNotes`, same sentence), `internal/meeting/transcript_recap.go:47` (user message: "Below is the full single-track meeting transcript (speakers are not labeled)").
- Intended: CLAUDE.md "Speaker roles (v75+)": roles are rendered as `[Я]`/`[Speaker N]`/person-name line prefixes into `meeting_transcripts.text`, with `transcription.diarization` default ON; voice prints and the whole «Я» tie-break stack exist so that transcripts are attributable. The recap is then generated from that same `transcript_text` (`cmd/meeting_transcript.go:399`).
- Actual: the system prompt and the user message both assert the opposite of what the data contains. The model is primed to treat `[Я]`, `[Anna K.]` as noise ("ignore obvious mis-transcriptions") rather than as attribution.
- Concrete scenario: the owner records a 1:1, diarization renders `[Я]` and `[Speaker 2]`; `transcript save` runs the recap and the Recap tab shows action items with no owner — "decided to ship Friday" instead of "Speaker 2 committed to ship Friday" — even though the transcript tab visibly shows who said it. `transcript notes` produces attribution-free notes for the same reason. The chapters prompt (`meeting.chapters`) does receive speakers via segments, so chapters and notes disagree on attribution for the same recording.
- Contract: none numbered (no inventory). A prompt-default fix requires a version bump per the house rule so customized rows are not clobbered → **needs owner decision** on whether recap/notes should attribute to speakers (and how `[Я]` should read in the output language).

### Medium

**M-1. `MeetingPrepViewModel` is view-local `@State`, so a running prep dies with the view (the async-state house rule).**
- Refs: `WatchtowerDesktop/Sources/Views/Calendar/CalendarEventsView.swift:27` (`@State private var meetingPrepVM = MeetingPrepViewModel()`), `Views/DayPlan/DayPlanView.swift:10,79` (a second, separately created VM), `ViewModels/MeetingPrepViewModel.swift:85-136` (`Task.detached` holds `self`, writes `result` back into the discarded VM).
- Intended: `docs/review/review-rules.md` house rule (and the `[Async-стейт переживает навигацию]` memory) — long-running CLI/AI runs live on AppState or a Center so "start → leave → come back" shows the result. Every other long AI run in this domain does this (`TranscriptNotesCenter`, `TranscriptChaptersCenter`, `SpeakerGuessCenter`, `MeetingRecorderCenter`).
- Actual: prep is a strong-tier call (tens of seconds). Switching sidebar tab tears down `CalendarEventsView`, the VM is released from the view graph; on return a fresh VM shows nothing and the user must press Prepare again. Mitigation: the CLI wrote `meeting_prep_cache` (`cmd/meeting.go:119-126`), so the second press returns instantly — the owner sees "it didn't work, then it worked at once", which reads as flakiness.
- Scenario: press Prepare on a 10:00 event, jump to Inbox, come back at 09:58 → empty prep pane, spinner gone, no error.

**M-2. Meeting prep cache has no TTL and ignores context freshness.**
- Refs: `cmd/meeting.go:99-107` (`GetMeetingPrepCache(eventID)` short-circuits whenever a row exists), `:119-126` (written once).
- Intended: `meeting.prep` v5 promises talking points from *recent* Slack/Jira/memory activity (`internal/meeting/pipeline.go:205-221`).
- Actual: a prep generated 6 days early is served verbatim the morning of the meeting unless the user presses Regenerate (`MeetingPrepView.swift:48,159` pass `forceRefresh`). Recurring events have per-instance ids so each instance is fresh, but a one-off event prepped early goes stale silently and the UI marks `isCached = false` regardless (`MeetingPrepViewModel.swift:126-128`).
- Scenario: prep a Friday review on Monday; a blocker thread erupts Thursday; Friday's Prepare shows Monday's talking points with no hint they are stale.

**M-3. 14-day calendar history silently detaches every event-linked recording older than two weeks.**
- Refs: `internal/calendar/sync.go:47` (`timeMin = now − EffectiveHistoryDays()`), `:181-191` (`DeleteStaleCalendarEvents` per calendar), `internal/config/defaults.go:71` (14), `internal/db/schema.sql:990,1016` (`meeting_recaps.event_id` and `meeting_transcripts.event_id` are `ON DELETE SET NULL`); list badge `MeetingTranscriptQueries.swift:72-73` computes `has_recap` via `r.event_id = t.event_id` only.
- Intended: spec `2026-07-31-informative-calendar-design.md` §6 — history window 14 days for the *event list*; CLAUDE.md "transcripts outlive events". Both hold — the rows survive.
- Actual (user-visible): after 14 days the event row is deleted, so the recording becomes an ad-hoc item in the unified list (its `title` is preserved), the `LinkedEventHeader` degrades to a plain label (`RecordingDetailView.swift:292-294`), attendee-scoped voice-print pools and the rename picker lose their attendee list (`:300-301` → `[]`), and the master-list `has_recap` badge goes false for a recap that is still reachable by `transcript_id` in the detail (`:285`). Memory's calendar ingest (`calevent:<id>`) and `get_task_context` meeting mentions also lose the join.
- Scenario: open Calendar three weeks after an all-hands recording — it shows as an untitled-event "recording" at its timestamp with no attendee chips and no recap badge, while the Recap tab still renders the recap. Looks like data loss; is retention. **Needs owner decision**: raise `calendar.history_days`, or exclude events that have recordings/recaps from stale-delete, or accept and document.

**M-4. No automatic pre-meeting prep exists anywhere; prep is click-only.**
- Refs: `internal/daemon/daemon.go` — the only `meeting` references are the audio cleanup (`:659-741`); `cmd/meeting.go:69` is the sole producer.
- Intended vs actual: CLAUDE.md never claims auto-prep, and the specs (`2026-04-27-meeting-recap-design.md`, informative-calendar) do not promise it either, so this is not drift — but the owner's "features don't work" perception may include expecting the assistant to have prep ready when the reminder fires. Listed so the gap is explicit; not a bug.

**M-5. Orphan sweep vs. recovered-but-unprocessed recordings (>30 days).**
- Refs: `internal/daemon/daemon.go:698-741` deletes any `rec_*` file whose mtime is older than the cutoff and whose exact path is not in `meeting_transcripts.audio_path`; the Swift recovered list is opt-in and never auto-processes (`MeetingRecorderCenter.swift:116-127,1229-1234`).
- Actual: a crash-recovered recording (has `.meta`, no DB row) left untouched for 30 days is deleted together with its `.meta`/`.activity`/`.txt`/`.json` sidecars; the "recovered" pill vanishes on the next launch and a Retry pressed from the still-loaded UI fails on decode ("file not found") as a failed job. A *queued* job in the current session cannot be hit (its file is minutes old). Design-consistent (`dismissRecovered` doc at `:1211-1216` explicitly leans on the sweep), but it is the one path where the sweep destroys something the user was still offered. Low-probability; flagged because the brief asked.
- Whether the sweep is deleting anything on the live install cannot be confirmed read-only; by code it deletes iff the daemon runs `runSync` and files are >30 days by mtime. Paths match: Swift `defaultRecordingsDirectory()` (`MeetingRecorderCenter.swift:1721-1725`) and Go `RecordingsDir()` (`internal/config/config.go:688-697`) both resolve to `~/Library/Application Support/Watchtower/recordings`, and Swift saves `job.audioURL.path` (`:1456`) which equals Go's `filepath.Join(dir, name)`.
