# C1 — One Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One Inbox list and reading pane over every kind that needs the owner — the day card (briefing + day plan), tracks, ideas, `inbox_items` messages, and B's proposals / reminders / automation cards — with the filter segments All · Day · Messages · Tracks · Ideas · Automations; the Briefings, Day Plan, Tracks and Ideas screens leave the sidebar and every old way in lands on the matching Inbox card.

**Architecture:** The producers keep running as today's Go daemon phases; C1 is a Desktop view over today's tables plus one Go registry path. WatchtowerCore gains the card types, one pure-read query (`InboxFeedQueries.read`) and the list builder over all kinds. The AppState-owned `ActionStripViewModel` stays the Inbox's one view model (its name and guard tests stay). The reading pane reuses the moved screens' views and view models: `BriefingDetailView` sections, `DayPlanViewModel` + `DayPlanItemRow`, `TrackDetailView` + `CustomTrackTimelineView`, `IdeaDetailPane` + `IdeasViewModel`. A custom track's proposed target change stops going through the Swift `TargetActionExecutor`: the card button runs `watchtower actions propose --approve` with a new owner-only tool `apply_track_action` (spec §6.2, gap 17).

**Tech Stack:** Go 1.26 (`internal/tools`, `internal/db`, `cmd`), SwiftUI macOS 14 + GRDB (WatchtowerCore + WatchtowerDesktop), the DesignKit.

**Spec:** `docs/superpowers/specs/2026-10-22-inbox-built-in-automations-design.md` (§6, §7, §9, §10 C1). Read §6 in full before any Inbox task. Earlier Inbox spec: `docs/superpowers/specs/2026-10-21-automations-panel-and-inbox-design.md` §B.

## Global Constraints

- UI copy is English; filter titles exactly `All`, `Day`, `Messages`, `Tracks`, `Ideas`, `Automations`; section titles exactly `Needs your decision`, `Today`, `Earlier` (B's).
- New Desktop UI uses the DesignKit only (`docs/design/desktop-style-guide.md`): `.kitPrimary` (at most one per card), `.kitSecondary`, `.kitQuiet`, `.kitDestructive`, `.kitIcon(isOn:)`, `KitSegmentedPicker`, `SectionHeader`, `.card()`, `.kitRow`, `.textFieldStyle(.kit)`, `Spacing`/`Radius` tokens, `Tone` colours. No `Divider()` between rows.
- No sheets and no popovers in any Inbox card or header (in-panel only). Every former sheet/popover the moved views carried becomes an inline row in the pane (the Reset pattern of spec §5.2: an inline row with the verb and Cancel). The one exception is B's existing workbench picker popover of Hand to Agent… (a small picker anchored to its control, allowed by the style guide), reused as is.
- "Add" actions are `+` icon buttons (`Image(systemName: "plus")`, `.kitIcon(isOn: false)`, `.help`/`.accessibilityLabel` carry the word).
- Swift tasks: `make test-swift FILTER='<Class>|<Class>'` for the touched test classes and `make lint-swift` (lint-diff is Go-only). Prefer tests in `Tests/Core` for WatchtowerCore code.
- Go tasks: `go test ./internal/<pkg>` for the touched packages (plus the `cmd` tests named in the task with `-run`) and `make lint-diff`.
- No full gate per task; the controller runs it once in the last task.
- Legacy view files that are reused stay at their paths (the SwiftLint baseline is path-keyed); only the removed screens' files are deleted. A legacy violation that shows up as new after an edit is fixed, never re-baselined.
- Guard tests (`Test<Module>NN_…`, `test_<MODULE>_NN_…` and every test an inventory file names) keep their names and assertions; a guard whose call site moves keeps both. A change that would weaken one is a stop-and-ask to the owner.
- STRIP-02 holds: `ActionStripViewModel.refresh()` stays one pure read inside one `dbPool.read`.
- Public repo hygiene: fixtures and docs use `acme`, `example.com`, `<owner-slack-id>`-style placeholders; no real ids, names, domains or local paths.
- Parallel lanes only where a task says `Depends on`; independent Swift tasks run in parallel lanes too (each lane its own worktree; tell each lane which files the others touch).

## Review Focus

1. **A double press on a track card's Apply** (or a press while another process already applied the event) must change the linked target once: the second press is refused with "This change was already applied." and the target is unchanged — pinned in Task 1 (`TestApplyTrackAction_SecondApplyRefusedTargetUnchanged`) and Task 6 (`testPressWhileWaitingRunsOnce`).
2. **A row that vanished between refresh and press** (an `inbox_items` row auto-resolved by INBOX-02, a track dismissed or a briefing deleted elsewhere): Done/Hide/Snooze is quiet success, the card leaves on the next refresh and the selection moves to the next row — pinned in Task 5 (`testMessageDoneOnAResolvedItemIsQuiet`, `testSelectionMovesWhenTheSelectedRowVanished`).
3. **A day with only one half** (briefing feature off, or the plan made without a briefing, or a briefing with no plan) still shows one day card with the half it has; a date with neither shows none — pinned in Task 3 (`testDayCardsJoinBriefingAndPlanByDate`).
4. **Volume and noise** — hundreds of read tracks and an active channel: All shows only unread tracks and today's day card, one message card per `inbox_items` row (INBOX-09 one per channel), Messages capped at 200 — pinned in Task 2 (`testAllShowsOnlyUnreadTracks`) and Task 3 (`testMessagesReadIsCappedAndOnePerRow`).
5. **An old `watchtower-nav://briefings|dayPlan|day-plan|tracks|ideas` link or a persisted old destination while the Inbox itself is hidden** (no source connected): the link does nothing and nothing crashes; with the Inbox visible it opens that filter — pinned in Task 11 (`testOldNavHostsRouteToInboxFilters`, `testOldNavHostIgnoredWhileInboxHidden`).

## Rulings this plan makes (spec silent or ambiguous)

- **R1 Badge.** The one badge formula (C2 cites it, never restates it): Badge = Needs your decision (proposals awaiting the owner incl. pending `save_automation`, plus ideas awaiting a verdict) + unread Messages cards + 1 when the latest day card's briefing is unread + due reminders + built-in upgrade notices (C2: one per `failed` `builtin_migrations` row, 0 in C1). Due reminders stay in the badge (B's rule; spec §6.1 excludes only track and automation cards). Unread automation outputs and track cards leave the badge (spec).
- **R2 What All shows.** All = Needs your decision + today's day card (pinned first in Today until Done) and earlier day cards whose briefing is unread + unread tracks + open messages + B's reminders and open automation outputs. Each filter shows its whole kind: Day = the last 30 dates with a briefing or a plan (**Show older** loads 30 more); Messages = open `inbox_items`; Tracks = every non-dismissed track (TRACKS-07); Ideas = the registry of kinds `idea` and `note`, every status but `merged`; Automations = proposals, reminders, automation outputs. Decisions stay in Digests' ledger (spec non-goal) and are not Inbox cards.
- **R3 Day card Done.** Opening the day card writes `briefings.read_at` (CATCHUP-01's surface). **Done** only unpins today's card: it stores the date in `UserDefaults` key `inbox.dayCardDone` (a per-viewer convenience, no DB column); the card then sorts by its time in Today.
- **R4 Track Done.** Opening a track card writes nothing. **Done** = `TrackQueries.markRead` (TRACKS-04 cascade) + every event of the track read. **Stop watching** (⋯) = `TrackQueries.dismiss` (TRACKS-07); for a custom track also `TrackQueries.setEnabled(false)`, so the daemon stops spending tokens on it — through the `CustomTrackControlling` seam (Task 9), which C3 swaps for the watch recipe. A custom track keeps **Delete** in ⋯ (inline confirm row).
- **R5 Messages.** Messages = `inbox_items` with Home's predicate (`status='pending'`, `item_class='actionable'`, not archived, not snoozed, Home's trigger list) without Home's 72 h window, newest `MAX(created_at, mentioned_at)` first, limit 200. Opening writes `inbox_items.read_at` only (Desktop write, the CATCHUP-01 precedent). Done/Hide/Snooze go through the CLI (`inbox resolve|dismiss|snooze`), as Home does. **Snooze ▾** offers `Tomorrow` (`1d`), `In 3 days` (`3d`), `Next week` (`1w`).
- **R6 Track action press (gap 17).** New tool `apply_track_action` on a new surface `inbox`: owner-only (no MCP server or chat mounts it), `AlwaysAsk`, args `{"event_id": N}` only — the change itself is read from the `track_events` row (no invented provenance). The press runs `watchtower actions propose … --approve`: one `agent_actions` row, proposed and approved by the owner's one press, applied through `Registry.Apply`'s claim (AGENT-05). The prompt grammar allows four kinds (`update_status`, `update_progress`, `update_notes`, `add_sub_item`); the tool accepts only those. The Target Watch tab's Apply uses the same press, so `TargetActionExecutor` is no longer used for track events. `surface='inbox'` rows are left out of the strip and the badge: the card shows the outcome.
- **R7 Learned and Profile.** B's top segmented control (Actions · Learned · Profile) gives way to the filter. Learned rules and Assistant profile move into the list header's ⋯ menu and open in the reading pane.
- **R8 Six segments.** The filter uses `KitSegmentedPicker` with six segments (the style guide says 2–5; the owner-approved spec names six). Flagged in the owner review.
- **R9 Creating things.** Ideas filter header: `+` opens an inline New idea row (replaces `IdeaCreateSheet`) and ⋯ → **Find Ideas in Past Messages…** opens an inline range row (replaces `IdeaBackfillSheet`). New custom tracks stay in Automations → Tracks → **New track** (until C3; C3 replaces it with Watch for something). A briefing item's or track's **Create Target** sheet becomes **Make a Task** in the card's ⋯: it creates the target from the same prefill and opens it in Targets.
- **R10 Plan block.** The day card lists plan items with `DayPlanItemRow` (time blocks in time order, then the backlog); the timeline graphic (`DayPlanTimelineView`) leaves with the Day Plan screen. **+ Add** and **Regenerate with feedback…** show on today's card only.
- **R11 Onboarding.** Goal → feature mapping (`OnboardingFeaturePlan`) is unchanged in C1: the goals still turn the features on, and their output now lands in the Inbox. Only docs and copy change (C2/C3 turn built-ins on).
