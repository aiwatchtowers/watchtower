## Facts that shaped the design

- Our hooks live in the workbench folder's `.claude/settings.local.json`, one group per event, no `matcher` (`internal/devpack/workbench_settings.go:41-47` `sessionStartSpec`/`stopSpec`, `upsertOurHook` :381 writes `{"type":"command","command":…,"timeout":N}`). An entry is ours by command suffix after a `watchtower` binary (`looksLikeOurHook` :265), legacy `project … --project N` too. `eventGroupsOf` :214 refuses the whole file when any event we own has the wrong shape (PROJ-04). Install/remove/status go through `installWorkbenchHooks` (`internal/devpack/workbench.go:398`), `RemoveWorkbench` :285, `StatusWorkbench` :320; `integrate status --json` reports `stop_hook` (`cmd/integrate_workbench.go:272`); resync reports `hooks_added` (`cmd/workbench_resync.go:55`).
- The Desktop starts every `claude` row's process with `WATCHTOWER_TERMINAL_SESSION_ID=<row id>` (`TerminalLaunch.sessionRowEnv`, Go `terminalSessionEnv` in `cmd/workbench_brief_session.go:20`). The SessionStart hook already reads the stdin payload under that variable (`recordTerminalSessionID` :55): read the row first, write only on change, 1 s busy timeout, panic recovered, one stderr line on failure, exit 0. A nested headless `claude -p` the agent runs **inherits the variable** (:43-45) — it must not move the row's state.
- `readHookInput[T]` (`cmd/workbench_check.go:243`) decodes stdin with a deadline and a 1 MiB cap. The Stop hook `runStopHook` :194 reads only `stop_hook_active`, prints `{"decision":"block","reason":…}` when git certainly disagrees with the board, and otherwise prints nothing; every failure path returns silently (PROJ-07). `db.SetTerminalClaudeSessionID` (`internal/db/terminal_sessions.go:58`) is the single-statement, guarded `UPDATE` pattern to copy.
- Claude Code hooks (code.claude.com/docs/en/hooks, read 2026-10-03): common input `session_id`, `transcript_path`, `cwd`, `hook_event_name`, (`permission_mode`, `prompt_id`, … on some events). Notification adds `message`, `title`, `notification_type` ∈ `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `agent_needs_input`, `agent_completed`, `quota_auto_resume_*`; a group with no matcher gets every type. Stop adds `stop_hook_active`, `last_assistant_message`. **Stdout of a `UserPromptSubmit` (and `SessionStart`) hook is added to the agent's context**; for other events stdout goes to the debug log. Exit 2 on `UserPromptSubmit` blocks the prompt. All matching hooks of an event run **in parallel**. `"async": true` runs a command hook in the background without blocking, and Claude Code then does not enforce its `timeout`. `PostToolUse` (after a tool call succeeds) and `StopFailure` (a turn ended by an API error) exist; the docs name no hook for an Esc/Ctrl+C interrupt.
- `terminal_sessions` (migration `00084`, `internal/db/schema.sql:2226`) has no state column; the Desktop writes every column, Go only `title` and `claude_session_id`. Swift `TerminalSession` (`WatchtowerCore/Models/TerminalSession.swift`) is a Codable `FetchableRecord` cached per workbench in `WorkbenchesViewModel.terminalSessions`.
- **GRDB ValueObservation never sees writes from another process** (`DigestViewModel.swift:130`, `WorkbenchNotificationCenter.swift` "a 30 s poll — the agent writes from another process"). The hook is another process, so observation is out; a poll is the only path.
- Liveness is `TerminalCenter.liveIDs` (`Services/TerminalCenter.swift:93`, from `states`); `start` :219 sets `.running`, `onExit` sets `.exited`. Nothing records when a process started. `hasLiveClaudeSession` is PROJ-10's — not touched.
- Dots: `SessionLiveDot(isLive:)` (`Views/Workbench/WorkbenchSessionsPanel.swift:108`, green/hollow), used by the panel row :81, `SessionSwitcherButton` :50, `SessionSwitcherPopover` :104, `GoToPalette` :201/:209. `SessionSwitcherPresentation.State` is `running | notStarted` and its caption is nil for a running row (`WatchtowerCore/Services/SessionSwitcherPresentation.swift`).
- Notifications: `NotificationService.sendWorkbenchNotice` posts `type: "project"`, `projectId`, `pane`, `subjectId` (`Services/NotificationService.swift:272`); `NotificationDelegate.routeWorkbench` → `AppState.navigateToWorkbench` → `WorkbenchesViewModel.reveal` (`ViewModels/WorkbenchesViewModel.swift:428`), whose `.terminal` pane opens the live-else-latest session and ignores `subjectID`. The forwarding allowlist already carries those keys (`App/NotificationForwarding.swift:52-60`). `willPresent` shows banners even while the app is active, so the "window not active" gate is at post time. Settings toggle `projects.notifications` + `quietHoursEnabled` (`WorkbenchNotificationCenter.sending`).
- Migrations end at `00096` on main; `origin/feature/onboarding-v2` already holds `00097_slack_account_roster_synced_at.sql`.
- Inventory `docs/inventory/workbench.md`: PROJ-02 (delete/remove takes our hook entries away), PROJ-04 (the install adds "exactly one `SessionStart` entry and one `Stop` entry"; malformed → byte-identical), PROJ-07 (the Stop hook's stdout/exit contract), PROJ-10 (`hasLiveClaudeSession`).

## Decisions (fixed for this plan)

1. **States.** Stored `agent_state` ∈ `working`, `waiting`, `approval` (NULL = never reported). Shown only for a running session: `working` → green dot, caption "working"; `waiting` → orange dot, "waiting for you"; `approval` → orange dot, "needs approval"; running with no trusted state → green dot, no caption (today). Not running → hollow dot, "not started · <age>" (today).
2. **Event mapping** (one Go function, `cmd`): `UserPromptSubmit` → `working`; `Stop` → `waiting` unless that same Stop run blocks the stop (drift found, decision 5) — then no write; `Notification` with `notification_type` `permission_prompt` or `elicitation_dialog` → `approval`, `idle_prompt` → `waiting`, any other type or a missing one → no-op; any other `hook_event_name` → no-op.
3. **Approval clears on the next tool result** *(owner approved 2026-10-03, Q1 → A)*: `PostToolUse` → `working`, applied **only when the stored state is `approval`** (an approved tool ran). Without it a granted permission keeps "needs approval" on screen until the turn ends. `StopFailure` → `waiting` (an API error ended the turn; no Stop fires). Both are one `hookSpec` each — dropping either is deleting that spec and its tests.
4. **One new hook command** for every event but Stop: `<watchtower> workbench session-state --workbench N`, installed as its own entry under `UserPromptSubmit`, `Notification` `PostToolUse` and `StopFailure`, each with `"async": true` and `"timeout": 5`. The command reads `hook_event_name` from stdin, so the same command line serves every event; recognition stays per event (`hookSpec.event` + suffix). No legacy spelling (the hookSpec's empty `legacySubcommand` must match nothing — guard against `" " + "" + " N"` matching).
5. **Stop: the existing entry is extended, not a second one.** `workbench check --stop-hook` (and the legacy `project check --project N --stop-hook`) records the state itself after its drift decision. Why: Claude Code runs an event's hooks in parallel, so a separate Stop entry would write `waiting` while our own drift check is blocking the stop and the agent keeps working; only the process that makes the block decision knows whether the turn really ended. It also needs no reinstall — every folder gets the Stop half when the binary updates. PROJ-07's contract is unchanged: stdout is byte-identical in every case (the block JSON or nothing), exit 0, panic recovered; the state write runs after the drift output is encoded, under its own 1 s busy timeout, and its failure is one stderr line. `stop_hook_active` (today: return before the DB is opened) now still records `waiting` when the env var is set — the continued turn ended. Without the env var the Stop hook does exactly what it does today (no DB open on the `stop_hook_active` path).
6. **Which row, and when not to write.** No `WATCHTOWER_TERMINAL_SESSION_ID` → exit 0 at once, stdin not read (external terminals are not tracked, v1). Otherwise the write happens only when every one holds: the env value is a positive integer; the payload `session_id` is a canonical UUID (`terminal.IsSessionID`); the row exists, is workbench N's, `kind='claude'`, and **its stored `claude_session_id` equals the payload's `session_id`** (a nested `claude -p` that inherited the variable has another id and is ignored; after `/clear` the SessionStart hook has already moved the stored id); the new state differs from the stored one (a repeat keeps the transition time); and the event time is later than the stored `agent_state_at` (an async write that lands late never overwrites a newer state). Read first, so the common no-change case never takes the write lock; the write is one guarded `UPDATE` (autocommit, no transaction), busy timeout 1 s.
7. **Hook command safety.** `session-state` never writes stdout (a `UserPromptSubmit` hook's stdout becomes agent context), always exits 0 (exit 2 would block the prompt), recovers panics, has no root config pre-run and whitelists unknown flags (the `check` precedent), reads stdin with a 1 s deadline, and reports a real failure as one stderr line. It never applies a deadline to `db.Open` (a migration must not be cut off — the PROJ-07 precedent); being async, it never delays Claude Code.
8. **Storage.** Migration `00098_terminal_session_agent_state.sql` (`00097` is taken on `feature/onboarding-v2`; the implementer re-checks `origin` branches before committing and takes the next free number): `ALTER TABLE terminal_sessions ADD COLUMN agent_state TEXT CHECK (agent_state IN ('working','waiting','approval'))` and `ADD COLUMN agent_state_at TEXT`; Down drops both (a column-level CHECK does not block `DROP COLUMN`). No index (primary-key reads only). Go is the only writer of both columns; the Desktop never writes them. `agent_state_at` is UTC with milliseconds, fixed width (`2026-10-03T12:34:56.789Z`), so string order is time order; the Swift parser pins UTC too (review-rules dual-path datetime rule).
9. **Trust rule (no stale state, no reset writes).** `TerminalCenter` records `startedAt[id]` when `start` launches a process. The Desktop trusts a stored state only while the row is in `liveIDs` **and** `agent_state_at ≥ startedAt[id]`. Exit, crash, Restart, relaunch or an app restart therefore never show a previous run's "waiting": the new run shows plain running until its first hook. No staleness timeout: a turn can legitimately work for an hour.
10. **Desktop observation: an AppState-owned `SessionAgentStateCenter`** (`@MainActor @Observable`, built in `AppState.initWorkbenches`, so it survives navigation and runs with the window closed). A 1 s loop; when no live `claude` session exists it reads nothing. Otherwise one read, `TerminalSessionQueries.fetchAgentStates(db, ids:)` — `id`, `project_id`, `title`, `agent_state`, `agent_state_at`, and the workbench name (join `projects`) for the live claude ids — applies decision 9 and publishes `statuses: [Int64: SessionAgentStatus]`, assigned only when it changed (no view churn). Latency ≤ 1 s after the hook's write. Read failures are logged once per error streak and keep the last map.
11. **Presentation.** `SessionSwitcherPresentation.State` becomes `notStarted | running | working | waitingForOwner | needsApproval` with `isLive`; `rows(…)` takes the status map. `SessionLiveDot` takes that state (green / orange / hollow; accessibility labels "Running", "Working", "Waiting for you", "Needs approval", "Not running"). Every dot site uses it: panel row (caption under the title, `#id` stays), switcher button, switcher popover, palette (current-workbench rows through the presentation; other-workbench rows through a VM helper `sessionState(_:)` reading the same center). No counters in the workbench switcher, no sidebar badge (owner declined).
12. **Notification.** On a transition into `waiting` or `approval` (the effective status changed since the previous poll and this `(session id, agent_state_at)` was not announced before), post one when `NSApp.isActive` is false and the workbench notifications toggle is on and quiet hours are off. Title "<session title> is waiting for you" / "<session title> needs approval", body the workbench name. Identifier `workbench-session-<id>`, so a newer state of that session replaces its older banner; when the session goes back to `working` or stops being live, the delivered one is withdrawn. Payload = the existing workbench push (`type: "project"`, `projectId`, `pane: "terminal"`, `subjectId: <session id>`), so the delegate and the forwarding path need no new case. The decision is a pure Core policy (`SessionAgentNoticePolicy`); the center only feeds it and posts.
13. **Click → that session.** `WorkbenchesViewModel.reveal` for `.terminal` with a `subjectID` that names a session of that workbench: drill the panel into the workbench and show that session the way a panel row click does (`open(_:placement: .show)`); an unknown or deleted id falls back to today's live-else-latest.
14. **Rollout to existing workbenches.** The Stop half arrives with the binary (decision 5). The new entries arrive through Re-run Setup / `workbench resync` / `integrate claude-code --workbench N` — additive, PROJ-04 rules. `integrate status --json` gains `state_hooks` (true only when every new entry of decision 4 is present); the Desktop's `WorkbenchInstallStatus` decodes it (absent → true, the `stop_hook` precedent) and offers Repair without it, and the page's install line names it ("state hooks on/missing").
15. **Not in v1** (feature note's v1 limits): sessions in external terminals and standalone terminals (no workbench hook); an Esc/Ctrl+C interrupt fires no hook, so the row says "working" until the next prompt; a Stop hook of the owner's own that blocks the stop shows "waiting" until the continued turn ends; a Stop whose drift check runs long (≤ 8 s git budget) shows "waiting" that much later; a session whose SessionStart write failed after `/clear` keeps the old stored id, and its states are ignored until a relaunch.

## Contracts

- **Hook entries** (`settings.local.json`, one group each, no matcher):
  `UserPromptSubmit`, `Notification` , `PostToolUse`, `StopFailure`: `{"type":"command","command":"<bin> workbench session-state --workbench N","timeout":5,"async":true}`. `Stop` unchanged: `<bin> workbench check --workbench N --stop-hook`, timeout 15, sync.
- **Stdin fields read:** `hook_event_name`, `session_id`, `notification_type` (Notification), `stop_hook_active` (Stop). Unknown fields ignored; a missing field is a no-op, never an error to the agent.
- **Columns:** `terminal_sessions.agent_state` (`working|waiting|approval|NULL`), `agent_state_at` (UTC ms ISO-8601, `Z`). Writer: Go `db.SetTerminalAgentState(id, workbenchID int64, sessionID, state string, at time.Time, onlyFrom string) (bool, error)` — the guards of decision 6 in the `WHERE`, `onlyFrom` for the PostToolUse rule. Reader: Swift `TerminalSessionQueries.fetchAgentStates`.
- **Effective status (Swift, pure, Core):** `SessionAgentStatus.effective(live:, stored:, storedAt:, startedAt:) -> SessionSwitcherPresentation.State` — decision 9.
- **Status JSON:** `integrate status --json` adds `state_hooks: bool`; resync's `hooks_added` also turns true when a state entry was added.
- **Push payload:** `type "project"`, `projectId`, `pane "terminal"`, `subjectId` = `terminal_sessions.id`; identifier `workbench-session-<id>`.

## Risks and assumptions

- **Payload drift.** Field names are from the hooks reference as of 2026-10-03; the parser reads four fields, ignores the rest, and treats anything missing as a no-op, so a rename degrades to "running" — never an error. `notification_type` is newer than the Notification event; an older Claude Code that omits it yields no `approval`.
- **`async` on an older Claude Code** that does not know the key: assumed ignored (the hook then runs synchronously, ≤ ~100 ms, still bounded by `timeout: 5`). If an old version rejected the settings file instead, the owner would see a settings error — the manual check runs on the owner's current version.
- **Cost of `PostToolUse` (Q1):** one short `watchtower` process per tool call (binary start + `db.Open`, read-only in the common case), async, so it never delays the agent; on a loaded machine it is still extra CPU per tool call.
- **AskUserQuestion / plan-mode prompts** — whether they raise `permission_prompt`, `elicitation_dialog` or nothing is undocumented; if nothing, such a wait shows "working" until Stop. Checked in T5's manual run and recorded.
- **Clock:** Go and Swift read the same machine clock; the trust rule compares a hook time with the Desktop's start time, so a backwards clock jump between them could hide one state until the next event (accepted).
