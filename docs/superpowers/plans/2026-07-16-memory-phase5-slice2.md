**Scope (this plan covers ONLY):**
1. **5A Calendar source** — a **mechanical** past-event → episode builder over `calendar_events` (no new AI call in this slice): one ended event → at most one episode, participants resolved to person entities, narrative taken from the event metadata and — where it exists — the already-AI-produced `meeting_recaps` row (resolved ambiguity #1: the LLM boundary is "reuse the recap the meeting pipeline already made; synthesize nothing new"). Recurring series → entities (`seedCalendarSeries`). The `cal:<event_id>` ref scheme (a new resolver in the MEM-12 registry). Its own extraction watermark `workspace.memory_calendar_last_extracted_ts`. Behind the dark flag `memory.sources.calendar`.
2. **5A internal-dialogs generalization** — Phase 4's situation-chat ingest (`ingestChatStatements`, MEM-09) extends to **target** and **track** Discuss chats (resolved ambiguity #4: **onboarding is OUT** — onboarding chat is never persisted to `chat_conversations`, so there is nothing Go-side to ingest). Per-`context_type` subject mapping (`situationSubjects` → `chatSubjects`). Behind the dark flag `memory.sources.chats`; MEM-09 stays **byte-unchanged** when the flag is off (only `situation` turns, exactly as today).
3. **The "remember this" command** — a Go-side prefix convention (`remember:` / `remember this:`, case-insensitive) on an owner `role='user'` chat turn. It is the **opt-in ingestion trigger for the generalized (target/track) chats** (resolved ambiguity #5): an ordinary target/track chat turn is a drafting instruction, not a world statement, so only a "remember this" turn stages as owner-rank evidence there; situation chats keep ingesting every owner turn (Phase-4 behavior, unchanged). Owner statement → owner-rank evidence via the SAME `chat:` ref + MEM-09 resolver path (code-minted; MEM-09 unchanged). No new vault write author (resolved ambiguity #6).

**Everything else is OUT of this plan:** Jira (gated on the sync repair, per the spec), 5B render inversions, 5C internal-entity mirrors, any new calendar AI prompt / narrative synthesis, the semantic 5D preference-belief pass.

**Architecture (extends the Phase-0–5-slice-1 pipeline; nothing in the existing order changes):**
- **Calendar is mechanical, like `IngestSituations` — not an AI extractor like Slack/Gmail.** `internal/memory/calendar_ingest.go` builds an episode per **ended** event (`end_time < now`) straight from the structured `calendar_events` row (title, description, start/end, location, organizer, attendees) and, where a `meeting_recaps` row exists, folds that recap's summary/decisions/actions into the episode Story/Outcome. No `memory.extract_*` prompt, no `internal/digest/models.go` / `internal/codex/models.go` change. It runs as a new **mechanical Run step (3b)**, after `SeedEntities` (participants + series must be seeded first) and before Slack extraction, gated `memory.sources.calendar`.
- **Calendar idempotency is alias-keyed** (the `gmailthread:` precedent): every calendar episode carries a stable `calevent:<event_id>` alias, so re-processing an event (a re-sync, an event edit, a recap landing AFTER the meeting) UPDATES the episode in place — same node id, provenance refs unioned, Story/Outcome refreshed. A content-equality check makes an unchanged re-scan a no-op (no empty git commit — the interaction-ingest `dirty` precedent).
- **The `cal:` resolver** joins the MEM-12 registry as a scheme (`cal`), `CalendarEventExists(id)` its lookup. The calendar builder validates its `cal:<event_id>` refs through a **cal-only** scoped registry (`newProvenanceRegistry(calResolver{p.db})`), exactly as the Gmail extractor uses a mail-only registry — a `cal:` ref that no longer resolves (the event was swept from the DB, MEM-01) is dropped-and-counted. Register `calResolver` into the pipeline registry too (so a belief-pass op could later cite a `cal:` episode ref; harmless when calendar is dark).
- **Recurring-series entities** fold into the existing mechanical `SeedEntities` fan-out as `seedCalendarSeries` (gated `SeedConfig.Calendar`): one entity per distinct Google `recurringEventId` (parsed from `calendar_events.raw_json`), titled from the series' event title, alias `calseries:<recurringEventId>`. A calendar episode of a recurring instance links to its series entity (the channel-entity precedent).
- **Chat generalization is a set-widening, not a rewrite.** `ListOwnerChatTurns`/`OwnerChatTurnExists` take an **allowed-context-type set**; the pipeline builds it from `memory.sources.chats` (`{"situation"}` off — byte-identical to today; `{"situation","target","track"}` on). The chat resolver (`chatResolver`) carries that same set so MEM-09's authenticity check widens in lockstep (a target/track owner turn "resolves" only when the flag is on). `situationSubjects` generalizes to `chatSubjects(contextType, contextID)`: `situation` → its signals' channels+members (today's path, unchanged); `track` → `tracks.channel_ids` + `participants[].user_id` + assignee/requester/owner user ids resolved via aliases; `target` → the target's linked track(s) (`tracks.linked_target_id`) unioned, else no subject (consumed-not-staged — the existing graceful path).
- **"remember this"** is a pure `chat_messages.text` prefix check in the ingest loop. A situation turn ingests regardless (Phase-4). A target/track turn ingests **only** when it matches the prefix; the prefix is stripped for the verbatim statement text. Everything downstream (the `chat:` ref, the MEM-09 resolver, the belief-pass owner-rank mint) is unchanged — "remember this" changes only *which* turns are staged, never *how* owner rank is minted.

**Tech stack:** unchanged. Go 1.25, `modernc.org/sqlite`, goose migrations, `digest.Generator` (only the existing Slack/Gmail steps call it; calendar makes no AI call). No Swift in this slice (target/track/situation chats and their `context_type` already exist in the Desktop app; the "remember this" prefix needs no UI — the owner just types it).

## Resolved ambiguities (for reviewer attention)

1. **Calendar's LLM boundary = none new; reuse the meeting recap.** Event metadata is structured, so the episode Story/participants/date are built mechanically from the `calendar_events` row. Where a `meeting_recaps` row exists (already an AI product of the meeting pipeline), its summary/decisions/actions fold into Story/Outcome. No `memory.extract_calendar_episodes` prompt, no `models.go` change, no re-synthesis. An event with no recap gets a metadata-only episode (still a real story arc). Narrative synthesis when no recap exists is deferred (a future slice may add an optional cheap-tier pass) — the "mechanical-first" reading of the spec.
2. **`cal:` ref shape = `channel_id="cal:<event_id>"`, `ts=<start_time unix seconds>`.** The resolver keys existence on the event id (`calendar_events.id`); the `ts` carries the start time for age math, not re-validated (the `mail:` shape — identity is the id). `calendar_events` is migration-guaranteed, so a lookup failure is a genuine error (step freeze), not a clean miss.
3. **Calendar idempotency + watermark = `calevent:<event_id>` alias + a bounded-lookback re-scan.** A watermark (`memory_calendar_last_extracted_ts`, a fourth independent watermark) advances over `end_time` behind committed episodes (MEM-04), but the loader re-scans a bounded lookback overlap (`calendarReprocessLookbackDays`, a code const) so a recap or event-edit landing after the watermark passed the still-present event refreshes its episode via the `calevent:` alias update-path; a content-equality check keeps an unchanged re-scan a no-op (no empty commit). The calendar sync retains only ~24 h of past events (`timeMin = now-24h` + `DeleteStaleCalendarEvents`), so an event must be captured while present — documented as a known limitation, not a bug (a longer memory-specific retention is a future enhancement).
4. **Onboarding chats are OUT — nothing to ingest.** The spec names "target/track/onboarding chats", but the onboarding flow (`OnboardingChatViewModel`) never persists to `chat_conversations` (verified: no `ChatConversationQueries.create` call; it produces `custom_prompt_context` instead). With no persisted `context_type='onboarding'` rows, the generalization covers `target` + `track` only.
5. **"remember this" = the opt-in ingestion trigger for target/track chats; a prefix convention.** Case-insensitive leading `remember this:` / `remember:` on an owner `role='user'` turn. Situation chats keep ingesting **every** owner turn (Phase-4, unchanged); target/track chats ingest **only** a "remember this" turn, because an ordinary target/track chat turn is a drafting instruction, not a world statement — the command gives the owner an explicit, low-noise way to pin a fact from those chats. The prefix is stripped for the verbatim statement text.
6. **"remember this" produces owner-rank EVIDENCE, not a direct entity note.** The remembered statement stages as a `chat:` owner-rank belief-evidence turn (the MEM-09 code path); the "entity note" the spec mentions is the belief pass's ordinary rendered result on the entity page, NOT a separate vault write. A direct entity-page write was considered and rejected: it would create a second belief/note write author and strain MEM-11 (surfaces read-only over belief history). Owner rank stays authored, never inferred (MEM-09), and single-authored through the belief math.
7. **Target-chat subject mapping = via the linked track; no target entity mirror in this slice.** Targets carry no channels/members of their own, and their memory entity mirror is 5C (out of scope). So a `target` Discuss chat's owner statement maps to the entities of the target's linked track(s) (`tracks.linked_target_id`); a bare target with no linked track maps to no entity and is consumed-not-staged (the existing graceful path). This keeps the generalization mechanical and honest without pulling 5C forward.
8. **`memory.sources.chats` is a distinct flag; situation ingest stays on `memory.surfaces.chat`.** The Phase-4 situation-chat ingest keeps riding `memory.surfaces.chat` byte-unchanged (MEM-09). The NEW target/track widening + "remember this" ride `memory.sources.chats` (default false, independently dark). The generalized ingest requires the surface machinery (`memory.surfaces.chat`, which gates the `ingestChatStatements` call) AND the source flag (which widens the context-type set); with `memory.sources.chats` off the set is `{"situation"}` and the path is byte-identical to slice 1.
