# First run P1 + P4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **House override (owner rule):** this plan has no code bodies. It gives
> exact type and function signatures, the named test cases and what each
> asserts. The implementer writes the bodies TDD-style from these.

**Goal:** Every tab tells a new user what will land there, when, and what to
do now (P1). A fresh install produces its first people cards, briefing and
day plan in the first cycle instead of a day later (P4).

**Architecture:**
- **P1.**
  - A pure readiness evaluator in WatchtowerCore (`FeatureReadiness`). It
    turns a snapshot of the daemon, sync, feature, source, run and content
    state into one `Readiness` per tracked feature.
  - `ReadinessCenter` on `AppState` (Desktop) assembles the snapshot and
    re-evaluates it on DB changes, daemon polls and a 60 s tick.
  - One shared `FeatureEmptyState` view renders a static copy table
    (`EmptyStateCopy`, Core) plus the live readiness line. It replaces the
    tabs' private empty states.
- **P4.**
  - The daemon's briefing and day-plan hour gates are bypassed once on a
    fresh install. Fresh means no row ever exists for that output.
  - The people-cards phase stops stamping `last_people.txt` when the
    pipeline found nothing to work on yet.

**Tech Stack:** Go 1.26 (`internal/daemon`, `internal/guide`, `internal/db`), SQLite; SwiftUI macOS 14+, GRDB, XCTest + ViewInspector (existing `ViewRenderProbe` pattern).

**Spec:** `docs/superpowers/specs/2026-10-14-first-run-home-design.md` (§1, §2, §5 P1/P4, §6 decisions 1 and 2). P2/P3 (Home, Try this) are **out of scope**. They wait for the Home mockup (#784).

## Global Constraints

- UI text is English only. Board, asks and comments are in Russian; the repo is English.
- Public repo hygiene: no real Slack/Google/Jira ids, corp domains or names in tests, fixtures or docs (`acme`, `example.com`, "colleague A").
- No new AI call anywhere in P1. P4 adds no run per day; it only moves the first run earlier.
- ETA wording never shows a countdown or a minute value other than the poll interval ("within ~15 min").
- `preparing` requires a running daemon **and** a `running` row whose `started_at` is under 2 h old.
- Readiness precedence is fixed: `off` > `needsSource` > `ready` > `preparing` > `error` > `waitingForSync` > `scheduled`.
- Fresh-install rule (Go and Swift must agree, dual-path):
  - **briefing:** no `briefings` row at all and no `last_briefing.txt`;
  - **day plan:** no `day_plans` row at all.
  - It is never derived from the onboarding flag.
- The attempt budgets (`maxDailyAIAttempts`, `*_attempts.txt`) are unchanged. They are the strong-tier cost fixes (`docs/features/strong-tier-cost-fixes.md`).
- Turn on from an empty state goes through `FeatureManagerService.enableNow([id], restart:)` + one daemon restart, never the staged Settings → Features path.
- Async state lives on `AppState` (`ReadinessCenter`), never in a view. It must survive tab switches (review-rules "Lifecycle & state").
- Inner loop only per task:
  - `go test ./internal/<pkg>` (no `-count=1`);
  - `make test-swift FILTER=<Class>`;
  - `make lint-diff`.
  - The full gate runs once per phase by the controller.

## Review Focus

1. **Daemon killed mid-run.** A `running` row stays in `pipeline_runs` up to 24 h (`stalePipelineRunAfter`), and the tab must not say "Preparing now" all that time. It falls through to `error`/`scheduled`. Pinned in Task 4: `testRunningRowOlderThanTwoHoursIsNotPreparing`, `testRunningRowWithoutDaemonIsNotPreparing`.
2. **Reset LLM data on an old install** (`DaemonStampFiles.clear`) wipes `last_briefing.txt` while `briefings` rows remain. This must not trigger an early briefing, and Swift must not show "fresh" timing. Pinned in Task 2: `TestShouldRunBriefingAt_StampWipedRowsExistKeepsHourGate`. In Task 4: `testBriefingStampMissingButContentPresentIsReady`.
3. **The app stays open across the briefing hour or midnight.** "Today at 08:00" must become ready/`nextCycle` or "tomorrow at 08:00" without a relaunch. Pinned in Task 6: `testTickReevaluatesWithNewNow`. In Task 4: `testBriefingAfterHourWithTodaysStampSaysTomorrow`.
4. **Turn on fails.** If Settings → Features is mid-apply (`busy`) or the restart throws, the user sees why. The button must not silently do nothing. Pinned in Task 8: `testTurnOnBusyShowsMessage`, `testTurnOnRestartFailureShowsError`.
5. **A garbage or missing stamp file, a table missing mid-migration, or an unreadable `sync_progress.json`.** These read as "no stamp / no content / no sync". They never show an error and never crash. Pinned in Task 5: `testMissingTableReadsAbsent`. In Task 6: `testGarbageStampReadsNil`.

## Spec corrections found while planning

These are decided here and carried into `docs/features/first-run.md`:

1. **Day plan is tracked in `pipeline_runs`.** Its name is `"day_plan"` (`daemon.go:2039`). Spec §1.2 says it is not, and that it is "never preparing/error". The plan treats it like the other pipelines. Calendar is the one untracked feature.
2. **`lastDayPlanDate` is in memory and lost on restart.** Day-plan freshness is therefore DB-only (`HasAnyDayPlan`). It is not "no `lastDayPlanDate` and no row".
3. **Briefing freshness is owner-agnostic** ("no `briefings` row at all"). `shouldRunBriefing` has no owner in scope, and a workspace has one owner. Spec §2 said "the owner has no row".
4. **Briefing content is "any `briefings` row", not "today's row".** With "today's row", an install with yesterday's briefing would show the tab as not ready at 07:00 while the list has content. "Today's" stays a P2 (Home) concern.
5. **`SidebarDestination` lives in the Desktop target, not WatchtowerCore.** The copy table is keyed by raw value, and the CaseIterable sweep test lives in the Desktop test target.
6. **`FeatureManagerService` is Desktop-side.** Turn on goes through a new `AppState.turnOnFeatureFromEmptyState`, modelled on `acceptFeatureSuggestion`, not straight from Core.
7. **`shouldRunBriefing` reads the wall clock.** It is split into `shouldRunBriefingAt(now)` so the new tests don't depend on the hour they run at.
