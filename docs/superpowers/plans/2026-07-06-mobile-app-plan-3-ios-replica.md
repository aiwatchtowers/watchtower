# Watchtower Mobile — Plan 3: Transport Hard Gate, Replica, iOS Skeleton

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the CloudKit transport production-readiness gate, build the mobile replica layer in `WatchtowerKit`, and ship the `WatchtowerMobile` iOS app skeleton with read-only Today/Inbox/Tasks/Tracks tabs fed from the replica.

**Architecture:** Three phases. (1) `CloudKitTransport`/`TransportStore` grow CK system-field persistence (`.serverRecordChanged` resolution), account-change reset, and retention — the hard gate from `2026-07-06-mobile-app-plan-3-notes.md`. (2) `ReplicaStore` + `ReplicaHydrator` in the Kit: a GRDB mirror of DataZone hydrated through the same `CloudSyncTransport` seam, decoding rows via `RowPayloadCoder` into the existing models — fully unit-tested against `InMemoryCloudTransport`. (3) `WatchtowerMobile/` — an xcodegen-generated iOS 17 app target depending on the local Kit package: TabView, per-tab list views over `ValueObservation` of the replica (mobile owns its replica writes, so observation works here — unlike the desktop/daemon split), sync-status footer. Read-only: actions/chat are Plan 4.

**Tech Stack:** Swift 5.10+, SPM, GRDB 7.x, CloudKit, SwiftUI (iOS 17), xcodegen 2.45.4, XCTest.

**Spec:** `docs/superpowers/specs/2026-07-05-mobile-app-design.md`
**Binding carry-over:** `docs/superpowers/plans/2026-07-06-mobile-app-plan-3-notes.md` — the hard-gate section is Tasks 1–2 of this plan; the "smaller items" section maps to Tasks 3–4.

### Task 1: Transport hard gate A — CK system-field persistence and `.serverRecordChanged` resolution

**Files:**
- Modify: `WatchtowerKit/Sources/WatchtowerKit/CloudKitTransport/TransportStore.swift`
- Modify: `WatchtowerKit/Sources/WatchtowerKit/CloudKitTransport/CloudKitTransport.swift`
- Test: `WatchtowerKit/Tests/WatchtowerKitTests/TransportStoreTests.swift` (extend), `WatchtowerKit/Tests/WatchtowerKitTests/CloudKitTransportMappingTests.swift` (extend)

**Interfaces:**
- `TransportStore` gains a `system_fields(record_name TEXT, zone TEXT, data BLOB, PRIMARY KEY(record_name, zone))` table with `func saveSystemFields(_ data: Data, recordName: String, zone: CloudZoneID) throws`, `func systemFields(recordName: String, zone: CloudZoneID) throws -> Data?`, `func deleteSystemFields(recordNames: [String], zone: CloudZoneID) throws`.
- `CloudKitTransport`:
  - `ckRecord(from:in:)` becomes an instance-path builder that seeds from archived system fields when present: `static func ckRecord(from record: CloudRecord, in zoneID: CKRecordZone.ID, systemFields: Data?) -> CKRecord` — decode via `NSKeyedUnarchiver` + `CKRecord(coder:)`; nil/undecodable → fresh record (current behavior). Payload/kind/modifiedAt always overwritten from `CloudRecord`.
  - Delegate: on fetched record-zone changes AND on `.sentRecordZoneChanges` saved records → archive `encodeSystemFields` and `saveSystemFields`; on deletions/tombstones → `deleteSystemFields`.
  - On failed save with `.serverRecordChanged`: extract the SERVER record from the CK error's userInfo (`CKRecordChangedErrorServerRecordKey`), persist ITS system fields, and re-nudge — policy comment: this device's payload wins (desktop is source of truth for DataZone; for RelayZone the write-back/chunk author wins by protocol design); the retry now carries the server change tag so it succeeds instead of looping.
- Behavior to pin by tests: system-fields round-trip through the store; `ckRecord(from:in:systemFields:)` with archived fields preserves the original `recordID`/metadata (build a CKRecord, archive its system fields, rebuild — assert recordName/zone match and payload is the NEW payload); undecodable blob → fresh record, no crash.

**Steps:** TDD as usual (failing tests → implement → green), then full Kit + desktop suites, lint, commit `fix(kit): persist CK system fields; resolve serverRecordChanged instead of looping`.

### Task 2: Transport hard gate B — account-change reset, zone eviction, retention

**Files:**
- Modify: `WatchtowerKit/Sources/WatchtowerKit/CloudKitTransport/TransportStore.swift`, `CloudKitTransport.swift`
- Modify: `WatchtowerDesktop/Sources/Services/MobileHub/MobileHubService.swift`, `HubSyncState.swift`
- Test: extend the respective test files (Kit + `WatchtowerDesktop/Tests/MobileHub/MobileHubServiceTests.swift`)

**Interfaces:**
- `TransportStore.wipe() throws` — clears events, pending, system_fields, engine_state in one transaction (schema stays).
- `CloudKitTransport` handles `.accountChange`: call `store.wipe()`, drop + relaunch the engine with fresh state, and record the fact — `public private(set) var accountResetCount: Int` visible via a new protocol-surface method or the existing `availability()` flow; plus `public var onAccountReset: (@Sendable () -> Void)?` (set before `start()`).
- `MobileHubService` wires `onAccountReset` → clears `HubSyncState` slice hashes + relay token + processed set (new `HubSyncState.wipeSyncState() throws`) so the next publisher cycle re-pushes the full slice and the relay re-reads safely (idempotency set survives being empty because desktop-authored echoes are skipped by status).
- `TransportStore.compactEvents(in zone: CloudZoneID, keepSince token: CloudChangeToken) throws` — deletes events with `seq <= token.value` for the zone; owners call it with their own floor (RelayProcessor after persisting its token; the Task 4 hydrator likewise). `HubSyncState.pruneRelayProcessed(olderThan: Date) throws` wired into the daily hygiene pass.
- `pendingBatch` unmappable-zone rows: evict + `os.Logger` warning instead of silent `continue`.
- Tests: wipe clears all four tables; compactEvents respects the floor and zone isolation (a consumer at its stored token sees identical `changes()` results before/after compaction — pin that equivalence); prune removes only old processed entries; hub reset path with a stub transport (onAccountReset → hashes empty → next publishOnce re-pushes everything).

**Steps:** TDD, suites, lint, commit `fix(kit,desktop): account-change reset, event compaction, processed-set retention`.

### Task 4: ReplicaStore + ReplicaHydrator (Kit)

**Files:**
- Create: `WatchtowerKit/Sources/WatchtowerKit/Replica/ReplicaStore.swift`
- Create: `WatchtowerKit/Sources/WatchtowerKit/Replica/ReplicaHydrator.swift`
- Test: `WatchtowerKit/Tests/WatchtowerKitTests/ReplicaTests.swift`

**Interfaces:**
- `public final class ReplicaStore: Sendable` (GRDB `DatabasePool` — the mobile UI reads it via ValueObservation, which needs WAL/pool):
  - `public init(path: String) throws`, `public static func inMemory() throws -> ReplicaStore` (DatabaseQueue-backed variant acceptable for tests — pick one mechanism and document), `public var reader: DatabaseReader` (for ValueObservation).
  - Schema: one table `slice_records(record_name TEXT PRIMARY KEY, kind TEXT NOT NULL, payload BLOB NOT NULL, modified_at REAL NOT NULL)` + index on `kind`; meta table `replica_meta(key TEXT PRIMARY KEY, value TEXT)` for the data-zone change token.
  - `public func apply(_ batch: CloudChangeBatch) throws` — upsert changed (records whose `zone == .data` only; relay records ignored here), delete `deletedRecordNames`, persist `batch.newToken`; one transaction.
  - `public func storedToken() throws -> CloudChangeToken?`
  - Typed reads for the UI: `public func fetchAll<T: FetchableRecord>(_ type: T.Type, kind: SliceKind, orderedBy sql: String? = nil) throws -> [T]` — decode `payload` via `RowPayloadCoder.row(from:)` → `T(row:)`; undecodable payload rows are skipped and counted (`public func corruptCount() -> Int` or log — never a crash mid-list).
- `public actor ReplicaHydrator`:
  - `public init(transport: any CloudSyncTransport, store: ReplicaStore)` plus a pull hook: the CloudKit transport's `pull()` — accept `pullable: (any HubPullable)?`... keep it simple: `public init(transport: any CloudSyncTransport, store: ReplicaStore, pull: (@Sendable () async throws -> Void)? = nil)`.
  - `public func hydrateOnce() async throws -> (applied: Int, deleted: Int)` — optional `pull?()`, then `transport.changes(in: .data, since: store.storedToken())` → `store.apply` → call `TransportStore.compactEvents` equivalent through... NO: compaction is the store-owner's concern; the hydrator only exposes its floor. Skip compaction wiring here; note it for the app's owner loop.
  - `public func start(interval: Duration = .seconds(30))` / `stop()` — the established Task-loop pattern.
- Tests against `InMemoryCloudTransport` end-to-end with REAL payloads: build rows with `RowPayloadCoder.payload(from: Row([...]))` for a target and an inbox item, push as `.data` CloudRecords, hydrate, `fetchAll(Target.self, kind: .target)` returns a decoded `Target` with the right field values; token advances (second hydrate applies nothing); delete propagates; relay-zone records are NOT ingested; a corrupt payload is skipped without failing the batch; `ValueObservation` on `reader` fires after `apply` (one async observation test).

**Steps:** TDD, suites, lint, commit `feat(kit): ReplicaStore + ReplicaHydrator — mobile DataZone mirror over the transport seam`.
