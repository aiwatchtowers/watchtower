# Tuning chat — tune Watchtower prompts, skills and agent instructions from Analytics

Board #1517. Builds on the agent coach (`docs/features/agent-coach.md`, COACH-01), agent analytics (`docs/features/agent-analytics.md`, AGENTLOG-01..07), the LLM usage ledger (`docs/features/llm-usage-ledger.md`) and the embedded chat (`docs/features/embedded-chat.md`).

Mockups: `docs/design/mockups/tuning-chat/` (DesignShotCatalog renders, light and dark, one per state in §4.4).

## 1. Why

**Discuss in Chat** on the workbench Analytics pane opens the ⌘/ help popup with the period's totals and its top three hints pasted into the composer. That chat cannot read the report, the sessions, the LLM spend, the prompts or the skills, and it cannot change anything. Its answers are generic. The owner wants a place to tune their whole LLM setup: Watchtower's own prompts and their Claude Code and Codex setup (skills, instruction files, allow rules). Tuning there means asking why something costs or fails, getting a concrete edit, and keeping it only if it works (the coach's 14-day verdict). That includes the instruction files and skills committed in the workbench's own repository, as a change the owner commits (ask #1165).

## 2. Goals, non-goals, anti-goals

Goals:
- G1. A tuning chat in a right-side panel of the Analytics pane, opened by the button that is now **Discuss in Chat**.
- G2. The chat reads what it needs: the agent report and sessions of this workbench (Claude Code **and Codex**), the LLM ledger (`llm_calls`), Watchtower prompts with their additions and versions, global skills, the Watchtower skill pack and the owner's overlays, `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, the Claude allow list and the Codex rules, and the workbench folder's `CLAUDE.md`, `AGENTS.md`, skills and `.watchtower/workflow.md` (§4.3a). It reads no company source text (D62).
- G3. The chat never writes. It proposes an edit, which lands as an ordinary coach proposal (`coach_proposals`, origin `chat`). The owner presses **Accept** on the card in the chat. The coach then does what it does today: compare-and-set, **Roll Back**, and the 14-day verdict. A workbench repository file is written by Accept into the workbench folder and committed by the owner; Watchtower never runs a git write (§4.3a, D66).
- G4. Removed from v1 (D61, ask #1164): the A/B replay of prompt additions moves to a later plan. Prompt additions stay (D65).
- G5. Codex sessions appear in agent analytics beside Claude Code sessions. Main imports them already (row by row per workbench, AGENTLOG-04 as amended under asks #507, #514, #519); this feature adds the gaps of §4.7: prices, sub-agents, the agent filter, the per-agent coach measurement, the cache-write mapping and the `codex_usage_mismatch` counter (D49).

Non-goals (v1):
- Editing a prompt template itself. Prompts change through additions only (ask #995).
- A/B replay of prompt additions (a later plan, D61): every edit, a prompt addition included, is measured only by the coach's 14-day verdict after Accept.
- Repository files other than the five of §4.3a, files outside the workbench folder, and any git write (add, commit, stash, checkout): the owner commits the change (D66, D67).
- Model or tier choice per purpose.
- Codex sessions not started from a Watchtower workbench terminal (a plain shell, `codex exec` runs, Watchtower's own children): they have no terminal row, so main's AGENTLOG-04 never reads them (§4.7, D49).

Anti-goals (a failure even if it works):
- Any file or setting changed without the owner's Accept.
- A shipped prompt or pack upgrade silently stopped by an owner edit.
- A tuning tool that reads company source text (Slack, mail, Jira, Linear, transcripts): the chat would then need the removal machinery that v1 drops (§4.5, D62).
- A repository file written over uncommitted changes, or any git command that writes (D67).
- Watchtower's own model calls counted as the owner's Codex sessions.

## 3. What the owner sees

1. The Analytics pane header: **Discuss in Chat** becomes **Tune** (icon `slider.horizontal.3`). It toggles a right side panel, placed beside the pane's content with the design kit's `PanelSplit` (the style guide's side panel, not the Workbench's overlay): `PanelSplitWidth` 460 by default, range 360–720, remembered as `analytics.tuningPanelWidth`; Esc in the panel closes it. While it is open **Tune** has the selected look.
2. The panel has a title row ("Tuning", the conversation picker **New** / recent tuning chats of this workbench) and a chat feed with a composer.
3. The empty state shows the period's figures in one line and up to four starter prompts built from the report. Examples: "Why did cost per task grow?", the top hint's finding, "Which prompt costs the most?", "Tune a skill". The text of the starters is defined in the model and tested.
4. While the chat answers, the feed shows the usual streaming row. Tool calls show as quiet lines ("Read the 7-day report", "Read prompt digest.channel").
5. A proposal appears in the feed as the coach's card: **CoachProposalCardView** with chips, why, diff and budget, and the buttons **Decline**, **Edit…**, **Accept**. The same proposal also shows in the pane's **Proposed edits**. After Accept it is listed in **Accepted edits**, where it is measured and can be rolled back like any coach edit. For a workbench repository file the folded line says the file was written and that the owner commits it (§4.3a, §4.4).
6. The period picker, the hints and the coach sections stay where they are. The panel reads the period the pane shows.

## 4. Design

### 4.1 Chat surface `tuning`

- A new tool surface `tuning`. A chat surface is declared in six places, all changed together (a test asserts the Go and Swift lists agree, §4.9): a const in `internal/tools/registry.go`, the `cmd/mcp.go` allowed list, `cmd/ai.go` help, `internal/chat/actions_contract.go` with a pinned `testdata/actions_contract_tuning.txt` and its Swift twin in `AgentToolsContract.swift`, and `AssistantToolSurface`. Quick Connections are skipped on it, as on `automation_editor`.
- The Desktop builds it on `EmbeddedChatEngine` with a `TuningChatSurface` spec. The spec has `.actions(surface: "tuning")`, `persistence: .database(conversationID)`, `ownerInstructions: true` and context `analytics_tuning` with the workbench id. The system prompt is the tuning rules block, the actions contract and `ChatQuestionsContract`. The turn prompt carries the pane's period and the workbench id on every turn. Every turn runs `ai query --purpose tuning.chat`, so its calls are recorded in `llm_calls` under purpose `tuning.chat` and Usage shows the tuning chat as its own line ("Tuning chat", D53, ask #1132); `tuning.chat` joins `spec_review.discuss` in `ai query`'s accepted purposes. Under ollama the spec is `.draftOnly`, and the panel says that tuning tools need Claude or Codex: the tuning chat stays without tools on an HTTP provider even though main runs tools on ollama elsewhere (the main chat's runtime B, automation `agent()`), because the tuning tools write proposal rows through the MCP child's `DirectApply` binding, which only a provider that runs an MCP child has (D52, ask #1132). The Desktop decides it with `AIModelCatalog.isKnownCLI` (the `AutomationEditorChatSurface.toolsAvailable` shape), and `ai query` refuses `--surface tuning` on the runtime-B path as a second guard.
- A `TuningChat` controller (`@Observable`, the `AutomationEditorChat` shape) owns the engine and calls `markShown`/`markHidden`. It has no `AgentActionFeed`: the surface has no call waiting for approval (next item).
- **Write calls and `agent_actions`.** `propose_tuning_edit` (§4.2) is the surface's only write tool. It is not External and writes only a proposal row, so the `tuning` binding applies it inline, as the workbench binding does (`DirectApply`, DEV-06): the owner's approval is **Accept** on the card, not a second Approve of the tool call (D47, kept in part). Each call lands in `agent_actions` as an applied row (AGENT-01), as on every surface; its `result_json` holds only the proposal id and status. A conversation deleted by hand keeps its `agent_actions` rows as any chat's do: the chat reads no company source text (D62), so the rows hold nothing that must go with a source. Tests: a proposal call writes one applied `agent_actions` row of surface `tuning` whose `result_json` has only `proposal_id` and `status`; a `main` chat's rows are untouched.
- Conversations: chat rows of context type `analytics_tuning`, one context per workbench. **New** starts another one, and the picker lists the last 10. They are opened from the tuning panel only and are not listed in the Chats panel, which lists no embedded chat (D48).

**Failure paths on the surface.** Each path has a test, named in §5.

| What fails | What happens | Who writes, who wins |
|---|---|---|
| The MCP child (`mcp --chat --surface tuning`) exits mid-turn | The tool call returns an error to the provider, and the turn ends with the engine's existing error line and **Retry**. A proposal row committed before the exit stays and shows in the feed on its next read. On Retry the same proposal is refused by fingerprint as "already proposed as #N", so no second card appears. | The proposal row comes from the MCP child. The fingerprint UNIQUE decides. |
| The provider process dies, or the Desktop quits mid-turn | The interrupted turn is handled as embedded chats handle it today: the owner's message is kept and the answer is marked interrupted. On reopen the conversation replays from the database, with no `--resume` (CHAT-04). | Chat rows are written by the Desktop only. |
| The CLI does not know the `tuning` surface (a stale CLI binary) | Today `ai query` does not check `--surface`: it passes it to the MCP child, which refuses, and the provider may run the turn without tools. Two guards: (1) `ai query` gains the check itself (`tools.KnownChatSurface`), so from this release an unknown surface fails before the provider starts, and the panel shows the engine's start error with **Retry**; (2) for a CLI older than that check, the tuning rules block tells the model: if no tuning tool is in its tool list, answer only "Tuning tools are not available in this Watchtower build — update Watchtower." and propose nothing. No proposal can be written without the tools, so nothing is lost. | — |
| The provider changes to ollama mid-conversation | The next turn runs as `.draftOnly`, and the panel shows the "tuning tools need Claude or Codex" line. Existing cards stay actionable, because Accept goes through the CLI, not the chat. Mockup `tuning-chat-no-tools-midway`. | — |
| The bulk-read limit is hit (READ-01) | The read tool refuses in plain words, and the chat says so. The session key is `conversation:<id>`, so **New** starts a fresh budget. | — |
| A tool names a workbench, prompt or skill that is gone | The tool returns "not found" as a tool error. Nothing is written. | — |
| The workbench is deleted while the panel is open | The Analytics pane leaves that workbench, and the panel closes with it. The conversations follow the embedded-chat rule for a deleted context. Its proposals go with it (`coach_proposals.workbench_id` cascades); a repository file already written stays in the folder as the owner left it (§4.3a). | — |
| Accept is pressed on a card while the chat proposes an edit to the same destination | Accept and the new proposal race on the "one open proposal per destination text" rule. Accept's compare-and-set moves the first proposal out of OPEN, and the new proposal is then checked against the changed file, so its `find` either matches once or is refused. | Accept runs in the CLI, the proposal in the MCP child. The compare-and-set and the validation order decide. |
| The same conversation is open on a second screen | `EmbeddedChatCenter` keeps one engine per conversation, as today, and a second view attaches to it. | Chat rows are written by the Desktop only. |

### 4.2 Tools on `tuning`

Read tools (all `CompanyData` where they return content, within the bulk-read limits):

| Tool | Returns |
|---|---|
| `get_agent_report` | `agents report --workbench N --days D` JSON, both agents, optionally `agent: claude\|codex` |
| `list_agent_sessions` / `get_agent_session` | sessions with cost, time and trouble; one session's report |
| `get_llm_usage` | `usage llm` sections and per-purpose rows for a period |
| `list_prompts` / `get_prompt` | prompt ids with their purposes, spend over 30 days, version and additions; one prompt's resolved template, additions and history |
| `list_skills` / `get_skill` | global Claude skills, global Codex skills, the pack skills with their overlays, and the workbench folder's `.claude/skills` and `.agents/skills` (§4.3a); one skill's text |
| `get_agent_instructions` | `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, the Claude allow list and the Codex rules file, and the workbench folder's `CLAUDE.md`, `AGENTS.md` and `.watchtower/workflow.md` with their git state (clean, changed, not a git repository; §4.3a), each with its budget |
| `list_coach_proposals` | the coach's open, accepted and declined proposals (so the chat never repeats a declined one) |

Proposal tool (it writes only a proposal row, never a destination):

| Tool | Does |
|---|---|
| `propose_tuning_edit` | `{destination, workbench_id?, prompt_id?, skill?, kind, find?, replace?, after?, title, why, metric}` → `coach.ValidateChatProposal` → `db.InsertChatCoachProposal` with `origin = 'chat'`, `conversation_id` = this conversation, and evidence `[{kind:"chat", ref:"c<conversation>"}]` plus the refs the chat cites |

`ValidateChatProposal` is the coach's `Validate` minus the two weekly gates: no 3-source floor and no 3-open cap (the owner asked for it in the chat). Everything else stays: the destination must be allowed, `find` must match once in whole lines, the budget per destination, `SafeAllowRule` and its Codex twin, fingerprint uniqueness against every earlier proposal, and one open proposal per destination text. A chat proposal does **not** count toward the weekly proposer's 3-open cap, but the weekly proposer still sees it as OPEN (the "one per destination" rule holds across both). The refusal reasons go back to the chat as tool errors in plain words, so it can fix and retry. A `prompt_addition` to a prompt that takes no additions is refused: a prompt in `prompts.MovedToBuiltin` (the morning brief, the day plan, tracks, ideas consolidation, reactions) with "<prompt> belongs to a built-in automation" (its text is tuned in that automation's recipe, and an addition would never reach it), and a prompt not loaded through `prompts.Resolve` (today the custom-track prompts `TrackRun`, `TrackShortlist`, `TrackCompose`, read by `customtracks.promptFor` straight from the row) with "<prompt> does not take additions". Both lists live in one function, `prompts.TakesAdditions(id)`, which `ValidateChatProposal` and Accept call; a guard test checks that each prompt id the custom-tracks pipeline loads is outside it.
- **Coach code changes the new destinations need** (found in `internal/coach`):
  - `keyOf(dest, wb, prompt)` decides "one open proposal per destination text". It does not know `skill`, so an open edit of one skill would block an edit of another. It becomes `keyOf(dest, wb, prompt, skill)`, and `skill` is kept only for the per-skill destinations (the two user skills, `pack_overlay`, and the two workbench skills of §4.3a). The fingerprint already includes it (§4.4). Test: two open proposals for two different Claude skills both pass; two for the same skill do not.
  - `writeCut` (the 14-day judge's removal proposal) counts every open proposal against `maxOpen` (3) and skips only `claude_settings_allow`. It changes in three ways:
    - It counts only proposals with origin other than `chat`, as `Validate` will.
    - It also skips `codex_rules_allow`, which is grow-only too, so no cut that Accept would refuse is filed, and the five workbench repository destinations (§4.3a, D67).
    - A cut of a chat edit is a weekly proposal (`origin = 'weekly'`, `conversation_id` NULL, the original's destination and `skill` copied) with today's cut title, `why` and evidence (D64).
    - Tests: a cut is written while 3 chat proposals are open; no cut is written for a `codex_rules_allow` or a `repo_claude_md` proposal judged `no_effect`; a cut of a chat edit has `origin = 'weekly'`, no `conversation_id` and the original's skill.

### 4.3 Destinations

The coach's v1 destinations stay. New ones:

| Destination | File or row | Edit | Budget |
|---|---|---|---|
| `prompt_addition` | `prompt_additions` (existing) | add/cut a line | `prompts.MaxAdditionRunes` 600 |
| `claude_skill_user` | `~/.claude/skills/<name>/SKILL.md` | exact-text replace, add or cut | current + 2000 runes, never past 20 000 |
| `codex_skill_user` | `~/.agents/skills/<name>/SKILL.md`, else `~/.codex/skills/<name>/SKILL.md` | the same | the same |
| `pack_overlay` | new table `skill_pack_overlays(skill, text, proposal_id)` | add/cut a line | 1000 runes per skill |
| `codex_agents_md_user` | `~/.codex/AGENTS.md` | exact-text replace; created when absent (before = "") | current + 400, never past 4000 |
| `codex_rules_allow` | `~/.codex/rules/default.rules` | append `prefix_rule(...)` lines from the safe table only | grow only |

Rules for every file destination are the same as `writeClaudeMD`. The file is read only when it is a regular UTF-8 file up to 256 KB, never through a symlink. The write is atomic and re-reads the file just before the rename. Accept compares against `before_text`, and Rollback restores it or returns the diff with `ErrChangedSince`. For `codex_skill_user` the copy Codex reads wins: the builder confirms Codex's precedence when a name exists in both folders and pins it in one function (`codexSkillPath`); `list_skills` shows both copies with "Codex reads this one" on the winner, and only the winner is a destination. A skill must already exist: the chat never creates a new skill folder in v1 (a "make me a skill" request gets the skill text in the chat, to save by hand). Only `AGENTS.md` may be created, as an empty `before_text`. A rollback of a created `AGENTS.md` writes it back as an empty file and does not delete it.

**Pack overlays.** A pack skill (the workbench skill, the flow skill and the `Skills()` pack) is installed as the shipped bytes plus, when the owner has an overlay, a block after the frontmatter: `## Owner additions (approved by the owner)` followed by the lines. `installSkill` computes the `.watchtower-shipped` digest over the rendered bytes, so an overlay is not drift. A pack upgrade re-renders shipped bytes plus overlay, so upgrades keep coming (ask #995). An overlay change re-renders every installed copy the next time the folder's pack is checked (`integrate`, workbench open, the daemon's drift check). Accept also runs that re-render for the folders of the owner's workbenches at once, and the result says how many copies changed. An installed copy the owner edited by hand stays drifted, as today (DEV-04), and the overlay does not reach it. The card says so ("1 copy is edited by hand and was not updated").

**Codex rules table.** It is `SafeAllowRule`'s list in Codex form: `prefix_rule(pattern=["cat"], decision="allow")` … `["go","test"]` …. It lives in one Go table, and a test keeps it equal to the Claude table. The Codex file is append-only for us. Rollback removes only the lines this proposal added.

### 4.3a Workbench repository files (owner, ask #1165; D66, D67)

The chat may also edit five instruction files inside the workbench's own folder, as a change the owner reviews and commits. They are chat-only destinations: the weekly proposer's `textDestinations` stay as they are, so the weekly pass never proposes a repository file (COACH-01's weekly rule holds).

| Destination | File, relative to the workbench folder | A missing file | Measured on (§4.7) |
|---|---|---|---|
| `repo_claude_md` | `CLAUDE.md` | created (before = "") | Claude |
| `repo_agents_md` | `AGENTS.md` | created (before = "") | Codex |
| `repo_claude_skill` | `.claude/skills/<name>/SKILL.md` | refused | Claude |
| `repo_codex_skill` | `.agents/skills/<name>/SKILL.md` | refused | Codex |
| `repo_workflow` | `.watchtower/workflow.md` (`workbenchmethod.FileRel`) | refused | both (All) |

- **One destination per kind** (D67), in the existing const style, rather than one `repo_file` with a path column: the path is derived from the destination, the workbench folder and the skill name, so neither the model nor a stored row can ever name another file; `keyOf(dest, wb, prompt, skill)` already identifies each text (`workbench_id` = the panel's workbench, never 0; `skill` for the two skill kinds); `AgentFor` maps by name; and no column is added. The skill name follows `validSkillName` (no `/`, no `..`).
- **Which folder.** The workbench's own folder (`projects.folder_path`), never a session worktree: a worktree is another session's branch in progress that cleanup may remove (#535), the Analytics pane and its numbers are per workbench, and a worktree created later starts from the folder's HEAD, so the edit reaches new sessions once the owner commits it. **Branch.** The edit lands on whatever is checked out in the folder, so the card names it: before Accept the open card's diff caption reads "<path> · on branch <branch>" (read live at list time: `coach proposals --json` gives each open `repo_*` proposal a `folder_branch` key, read in `cmd/coach.go` through the existing read-only `workbenchgit.ReadStatus` on the workbench folder; a detached HEAD reads "on a detached HEAD (<short sha>)"), and Accept stores the branch it wrote on in a new `coach_proposals.written_branch` column. The folded line names both path and branch. If the branch in the folder changed between the card's render and Accept, Accept still writes (the dirty check guards the file, not the branch) and the stored and shown branch is the one at the write.
- **File rules** are §4.3's: a regular UTF-8 file of at most 256 KB, no symlink at the file or at any folder between the workbench folder and it (each component lstat'ed), an atomic replace that re-reads the file just before the rename, the mode kept. Budget: the skill rule for all five (current + 2000 runes, never past 20 000; a file already past that may shrink or keep its size). `CLAUDE.md` and `AGENTS.md` may be created as an empty `before_text`; a rollback of a created one deletes the file again, but only while it still equals what Accept wrote (the compare-and-set below); a file changed since gives `ErrChangedSince` with the diff and is not deleted (owner, ask #1169; the D14 rule — no file deleted in the owner's home folders — stays for `~/.codex/AGENTS.md`). A skill must exist (D14), and a pack copy (the devpack marker) is refused with "<name> is a Watchtower pack skill: propose a pack_overlay". `.watchtower/workflow.md` must exist: creating it would switch the folder's methodology (`internal/workbenchmethod`), a bigger change than a text edit, so the chat gives the text to save by hand.
- **Git.** Watchtower only reads git state here, through one new read-only helper `workbenchgit.PathStatus(ctx, Options{Folder}, rel)` running `git status --porcelain=v1 -z -- <rel>` in the folder; it never runs add, commit, stash, checkout or any other command that writes. Accept refuses when that status lists the path at all (modified, staged, untracked, conflicted), with "<path> has uncommitted changes — commit or discard them, then press Accept again.", so a half-edited file or another session's work is never mixed into the change. A path git ignores lists nothing and counts as clean. A folder that is not a git work tree, or a Mac with no git, refuses the five destinations at propose and at Accept with "This workbench folder is not a git repository: Watchtower changes files here only where you can review and commit the change." (without git there is neither the dirty check nor a commit to review).
- **Accept** reads the workbench's folder (a gone workbench refuses with "workbench <N> not found"), runs the dirty check, reads the file, compares it with `before_text`, writes atomically (re-read before rename) and then moves the status by compare-and-set. The dirty check is not repeated after the write, which makes the path dirty itself. The CLI result gains `written_path` (relative). The card in the feed folds to "Accepted · wrote <path> on <branch> — commit it yourself" (`TuningChatTexts.acceptedRepoFile`, mockup `tuning-chat-proposal-accepted-repo`) and, once the commit is seen (Measurement below), to "Accepted · committed · measuring for 14 days".
- **Roll Back** runs no dirty check (the file is expected to show Accept's own change, committed or not). It restores `before_text` only while the file still equals `after_text`, the compare-and-set every file destination uses; when the owner committed the edit unchanged it still works on the working tree, and the owner commits the revert. A file changed since gives `ErrChangedSince` with the diff, as today. After a rollback of a repository file the Accepted edits row says "Rolled back · restored <path> — commit it yourself" (`TuningChatTexts.rolledBackRepoFile`).
- **Measurement.** Baseline and verdict use the proposal's workbench and the agent the file serves: `CLAUDE.md` and `.claude/skills` → Claude, `AGENTS.md` and `.agents/skills` → Codex, `workflow.md` → both (`coach.AgentFor`, §4.7).
  - **The 14 days start at the commit, not at Accept.** Sessions in their own worktrees branch from the folder's HEAD, so an uncommitted edit reaches only a session started in the folder itself. The baseline is still the 14 days before Accept. The verdict window starts at a new `coach_proposals.measure_from`: once a day the daemon's coach phase checks each accepted `repo_*` proposal with no `measure_from` through a read-only `workbenchgit` helper (`git show HEAD:<rel>` in the folder) and, the first time the file at HEAD equals `after_text`, sets `measure_from` = now with a compare-and-set on `measure_from IS NULL`. The judge reads `measure_from` (for every other destination it is `accepted_at`, so nothing changes for them). Until then the accepted row says "Accepted · waiting for your commit"; 30 days after Accept without the commit the verdict is `too_little_data` and the row says "Not committed in 30 days — not measured". Sessions in worktrees created before the commit, or on a branch without it, still run without the edit; the verdict mixes them, a stated v1 limit.
  - **Writers and races.** Only the daemon writes `measure_from` (the compare-and-set makes a second pass a no-op); Rollback before the commit leaves it NULL and the proposal leaves accepted, so the check skips it; a commit of a changed text never matches `after_text`, so it is never measured, and the row stays "waiting for your commit" until the 30-day `too_little_data`; the folder gone or not a git work tree any more → the check skips the row that day and the 30-day rule ends it.
- **Failure paths.** A live agent writing the file between the dirty check and the rename → the re-read gives stale, the agent's text is kept. The folder deleted or moved before Accept → "workbench folder not found", nothing written. The folder stops being a git work tree after Accept → Rollback still works on the file (it runs no git command); measurement as above. Accept killed after the write and before the status compare-and-set → the next Accept of the same card finds the file equal to `after_text`, not `before_text`, so it is stale and the card closes; the file keeps the edit, which the owner sees in `git status` and keeps or reverts — the same rule as every file destination (§4.3). Tests for each are in §5.
- **The judge's cut** is never filed for these five (D67): a committed edit is shared through the repository, and sessions of other people who use it are not in the coach's numbers. The verdict still shows on the accepted row, and the owner rolls back or asks the chat.
- **Writers and races.** A live agent session editing the same file: before Accept, the dirty check refuses; between the check and the rename, the re-read sees the change and Accept ends `stale` with the session's text kept. A second Accept of the same proposal loses the status compare-and-set; a second proposal on the same text is refused by "one open proposal per destination text", and after the first Accept its `find` is checked against the new file. The workbench deleted: its proposals go with it (`workbench_id` cascades); a delete between the write and the status write makes that compare-and-set find no row, and the existing undo restores the file.
- **COACH-01 amendment** (owner, ask #1165): a repository file is a destination only as one of these five, only inside the workbench's own folder, only by the owner's Accept on a chat proposal, and Watchtower never runs a git write.
