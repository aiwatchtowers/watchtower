## COACH-01 — nothing is applied without the owner's Accept, and a repository file only on the owner's Accept

**Status:** Enforced (Go).

**Observable:** The weekly pass and `coach run` only store proposals (`coach_proposals`, status `open`); every destination — the owner's session, procedure and chat texts, a prompt's additions, `~/.claude/settings.json`, `~/.claude/CLAUDE.md` — is unchanged until `Applier.Accept` (the owner's `coach accept`) writes that one proposal. `coach accept`, `decline`, `rollback` and `run` are refused under an AI agent's environment markers and otherwise need the owner's confirmation in the running Desktop (AGENT-07, ask #659). The weekly pass's destination set is the owner's own setup: a repository file (the repo `CLAUDE.md`, `.watchtower/*`, `.claude/skills/`, a project `.claude/settings.json`) is never one of its destinations, and the two files under the home folder are `<home>/.claude/settings.json` and `<home>/.claude/CLAUDE.md`. A model-proposed destination outside the set is dropped by `Validate`. (Chat proposals, below, add destinations; the weekly set is unchanged.) CLI additions that relax nothing: `coach status --days N` (1..90, default 14), `coach run` fails with code `busy` while another pass holds `<workspace>/coach.lock` (the daemon's weekly pass skips then), and with `--json` every failure object is also written as one JSON line on stderr (Execute() adds a prose line after it; a reader takes the last line that decodes as an object).

**Chat proposals (board #1517, tuning chat; spec `docs/superpowers/specs/2026-11-03-tuning-chat-design.md`, approved in ask #1112, COACH-01 amendments in asks #1018 and #1165):** the tuning chat files a proposal with `propose_tuning_edit` (`origin = 'chat'`, `conversation_id`); `coach.ValidateChatProposal` checks it and `db.InsertChatCoachProposal` stores it `open`, like any other proposal — nothing is written until the owner's Accept on the card, and the chat itself never writes a destination. A chat proposal may also name five global destinations under the owner's home folders, none per-workbench: `claude_skill_user` (`~/.claude/skills/<name>/SKILL.md`), `codex_skill_user` (the one of `~/.agents/skills/<name>/SKILL.md` and `<CODEX_HOME>/skills/<name>/SKILL.md` that holds the skill; a skill in both is refused, D71), `pack_overlay` (`skill_pack_overlays` lines rendered into Watchtower's pack skills, DEV-04), `codex_agents_md_user` (`<CODEX_HOME>/AGENTS.md`, the one file Accept may create there) and `codex_rules_allow` (`<CODEX_HOME>/rules/default.rules`, append-only through the same safe-rule table as Claude's allow list). The home folders may be symlinks to a real directory; nothing below them may (D71). Chat proposals take no weekly slot and pass no weekly floor or cap (D10), but one open proposal per destination text holds for both origins (`ErrCoachTextBusy`, `already proposed as #N`). The weekly pass never proposes a chat-only destination.

**Workbench repository files (owner, ask #1165, D66):** A chat proposal may edit five files of a workbench's own folder — `CLAUDE.md`, `AGENTS.md`, `.claude/skills/<name>/SKILL.md`, `.agents/skills/<name>/SKILL.md`, `.watchtower/workflow.md` — and no other repository file; the weekly pass never proposes one. Watchtower never runs a git command that writes. Since context actions (amendment 1 below) a repository file changes only through a workbench session the owner's Accept starts; until then Accept wrote the file only when `git status` listed no change for it and the folder was a git work tree, and the owner committed the change. **Exception (owner, ask #1236):** a `pack_overlay` Accept or Roll Back re-renders the installed copies of a Watchtower pack skill in each workbench folder (`.claude/skills/<skill>/SKILL.md`, `.agents/skills/<skill>/SKILL.md`, `rerenderPack` → DEV-04's `RerenderFolderSkill`) with no git check, as `integrate` and opening a workbench already do; a copy edited by hand is left as it is (drifted) and a missing copy is not created.

As shipped with the tuning chat (asks #1169, #1173, #1229; D67, D68, D72; the Accept write path and the HEAD measurement in this paragraph now hold only for rows accepted before sessions, `via_session = 0` — their Rollback is kept): one destination per file kind (`repo_claude_md`, `repo_agents_md`, `repo_claude_skill`, `repo_codex_skill`, `repo_workflow`), the path derived from the workbench's own folder (never a session worktree, never through a symlinked folder) and the skill name, so no stored row names a path. `coach accept` refuses with code `dirty` (`git status` lists the path: modified, staged, untracked or ignored) or `not_git` (the folder is not a git work tree, or git is not installed), and reports `written_path` (relative) on success; the git state reaches `internal/coach` only through the `RepoState`/`RepoBranch` seams, filled by `cmd`, the daemon and `internal/tuning` with the read-only helpers `PathStatus`, `ReadStatus` and `FileAtHead` (git `status`, `rev-parse`, `show` only); a failed git read refuses, never counts as clean. A path git ignores (`.gitignore`, `.git/info/exclude`, or a file inside an ignored folder) is refused as `dirty` too (owner, ask #1236): `PathStatus` asks `git status --ignored=matching`, so its local text, which git does not hold, is never overwritten; an ignored file that does not exist yet holds nothing and may be created (`CLAUDE.md`/`AGENTS.md`), but its edit never reaches HEAD, so its verdict ends `too_little_data`. Only `CLAUDE.md` and `AGENTS.md` may be created; skills and `workflow.md` must exist. An Accept killed after the write and before its status write leaves the file uncommitted, so the next Accept is refused as `dirty` and the card stays open; once the owner commits the edit, Accept finds the file already holding the edit and records the proposal as accepted. This recovery holds for an Accept of the proposed text only: after a killed Accept of an owner-edited text, the next Accept finds a text other than the proposal's and closes the card `superseded`. Rollback runs no git check; it deletes `CLAUDE.md`/`AGENTS.md` whose `before_text` is empty (created, or empty before) only while the file still holds Accept's text — a changed file is kept even under force — and gives any other file its before-text back. The card names the branch the edit lands on (`written_branch`), and the 14-day verdict window starts at the first daily check that sees the edit at the folder's HEAD (`measure_from`); 30 days without the commit give `too_little_data`. No judge's cut is ever filed for these five.

**Context actions (feature #1087; spec `docs/superpowers/specs/2026-11-12-context-actions-design.md`, three amendments approved with the spec on 2026-11-12, plan ask #675):** Watchtower still writes no git (`internal/coach` imports no `workbenchgit` and no `os/exec`), and still applies nothing without the owner's press.

1. **A `repo_*` Accept starts a session instead of writing the file.** Every `repo_*` proposal, of any origin (weekly, chat or context) and from any surface (the Analytics Context block, a **Proposed edits** card, the tuning panel, Home), is accepted by the Desktop starting a workbench session with `coach brief` and then recording it with `coach accept <id> --session <sid>` (`Applier.AcceptWithSession`: one compare-and-set `open → accepted` storing the session). The session works in its own worktree, runs the project's pre-PR review and opens a PR it does not merge; the owner merges. `Applier.Accept` refuses every `repo_*` destination, and `claude_memory_index`, with "Accept it in Watchtower — it starts a session", reading and writing nothing; `coach accept` without `--session` is refused with code `refused`. The memory index (D4) is changed by such a session only after the owner approves the diff through `ask_owner`; its Rollback writes the Accept-time copy back only while the index still holds what the session wrote. A `via_session` repository row has no Rollback ("Roll it back with a session: Watchtower opens one"); **Revert…** starts a session that opens a revert PR. Rows accepted before sessions (`via_session = 0`) keep their file Rollback.
2. **Repository measurement starts at the merge, not at the folder's HEAD.** A `repo_*` row accepted through a session gets `measure_from` when the daily check sees its session branch's PR merged (the session report's cache; the merge time, never before the Accept); a PR closed unmerged, or 30 days without a merge, gives `too_little_data`. Legacy rows keep the HEAD rule.
3. **A third origin, `context`, with its own destination set** beside the weekly and chat sets: `claude_plugin_off` (`enabledPlugins["<id>"]` of `<home>/.claude/settings.json`), `claude_mcp_server_off` (`mcpServers["<name>"]` of `<home>/.claude.json`, the entry saved 0600 in `<workspace>/coach-undo/<id>.json` for Rollback), `claude_connectors_off` (`env.ENABLE_CLAUDEAI_MCP_SERVERS` of `<home>/.claude/settings.json`) and `claude_memory_index` (the project's auto-memory `MEMORY.md` under `<home>/.claude/projects/`, through a session), plus `repo_claude_md` restructures (through a session, as in 1). The settings three are global (user scope) and written by a per-key compare-and-set that leaves every other key's value as it was; none is a weekly or chat destination, none is a repository file, and every path is under the home folder. Proposals are filed mechanically (no model call) and stored `open`. Never proposed, and refused on Accept of a hand-made row: Watchtower's MCP servers `watchtower-workbench` and `watchtower` in both the Claude (`-`) and the Codex (`_`) spelling, every pack skill, and the plugins a Watchtower skill depends on (`superpowers`, `pr-review-toolkit`). `claude_connectors_off` never reaches the Watchtower chat, which loads no user settings and sets the variable itself.

**Judge's cut (asks #1018, #1169; D35, D67):** `writeCut` files no cut for `claude_settings_allow`, `codex_rules_allow` (grow-only: Accept would refuse a cut) or a workbench repository file, and counts only weekly proposals against the three open slots, so open chat proposals never stop a cut; a cut of a chat edit is an ordinary weekly proposal (D64).

**Per-agent measurement (board #1517, ask #1018, ask #1196):** A proposal is measured, baseline and verdict, on the agent its destination serves: Codex destinations on Codex rows, `pack_overlay`, `session` and `procedure` on both agents, every other destination on Claude rows. The workbench repository files follow the same rule: `repo_agents_md` and `repo_codex_skill` on Codex rows, `repo_workflow` on both, `repo_claude_md` and `repo_claude_skill` on Claude rows (`AgentFor`). A baseline taken on mixed rows before this rule is measured again once, at daemon start, for accepted proposals with no verdict or a `too_little_data` verdict.

**Why locked:** The coach turns an agent-visible signal into edits of the text every agent reads next. An edit applied on its own, or into a file a team shares, is a prompt injection path and a surprise for the owner (spec D3, D6).
