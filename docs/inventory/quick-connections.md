# Quick Connections — Behavior Inventory

**Module:** `internal/db/external_connections.go`, `internal/externalmcp/`, `internal/ai/client.go` (config merge + allowlist), `cmd/connections.go`, `WatchtowerDesktop/Sources/ViewModels/ExternalConnectionsViewModel.swift`, `WatchtowerDesktop/Sources/Views/Settings/{ConnectionsSettings,QuickConnectionsDetail,AddExternalConnectionView}.swift`
**Spec:** `docs/superpowers/specs/2026-09-09-quick-connections-external-mcp-design.md`
**Last full audit:** 2026-09-09

## QC-01 — Native untouched

**Status:** Enforced

**Observable:** Adding, enabling, disabling, or removing a Quick Connection touches only the `external_connections` table (and its `mcp_secret_<id>.json` file) — no native sync phase, pipeline, memory extraction, or digest is read or written. `Client.buildMCPConfig()`'s `watchtower` server entry and `allowedToolsFlag()`'s base `mcp__watchtower` token are unchanged regardless of how many connections exist; with zero enabled connections the whole config and allowlist render byte-identical to the pre-feature output.

**Why locked:** Tier 2 (Quick Connections) is deliberately kept out of the pipelines — it has no watermark, no stable provenance ref, no idempotency key, none of the four guarantees `internal/memory`'s MEM-12 registry and every daemon phase are built on (spec §2). Letting a Quick Connection touch native state, even incidentally, would blur the Tier 1/Tier 2 boundary the spec exists to draw.

**Test guards:** `internal/ai/client_test.go` `TestBuildMCPConfig_ZeroExternalUnchanged` (zero connections ⇒ a single `watchtower` server in the config, byte-identical to pre-feature output), `TestBuildMCPConfig_MergesExternalServers` (an enabled connection adds its own `mcpServers` entry alongside — not in place of — `watchtower`); `internal/db/external_connections_test.go` `TestExternalConnections_CRUD` (registry CRUD touches only its own table); `cmd/connections_test.go` `TestConnections_AddListEnableDisableRemove`.

**Locked since:** 2026-09-09

## QC-02 — Read-only, no auto-execute

**Status:** Enforced

**Observable:** External MCP servers are surfaced only as `mcp__<name>` tools the vendor CLI's own tool loop dispatches directly — they never enter `internal/tools`' `Registry` (no `Propose`/`Apply` row, no `agent_actions` entry, no trust level). `cmd/actions_registry.go`'s `buildToolRegistry` — "the ONE place the assistant's tools are assembled", shared by `mcp --chat`, `actions …`, `jira create`, and the runtime-B loop — registers exactly the built-in write tools (`tools.NewCreateTarget()`, `tools.NewCreateJiraIssue(...)`) plus `tools.ReadTools()`; nothing there reads `external_connections`, so an owner-added connection cannot add a registry tool, no matter how it's enabled.

**Why locked:** AGENT-01..06 (`docs/inventory/agent-actions.md`) hold only for tools dispatched through the registry. An external tool executes silently the moment the vendor CLI calls it — there is no propose/approve step to intercept a write. Until runtime B lands (a Go-owned loop that can route an external call through `Registry.Propose`), the only safe posture is read-only: no external tool may mutate a third-party system, and no code path may make one look like it went through the registry's approval machinery.

**Test guards:** `cmd/connections_test.go` `TestConnections_AddListEnableDisableRemove` (a connection row carries no trust/registry state, only `enabled`/`status`) — there is no dedicated registry-side guard in v1 beyond "the registry never grows a tool from `external_connections`" holding by construction, since `buildToolRegistry`'s tool list is a fixed literal with no `external_connections` read in it. Spec §6 records the reasoning.

**Locked since:** 2026-09-09

## QC-03 — Secrets never on argv

**Status:** Enforced

**Observable:** A connection's credential (env vars for stdio, headers for http) is never a table column and never a CLI flag value — `connections add --secret-stdin` reads it as a JSON payload from stdin and `internal/externalmcp.SecretStore.Save` writes it to `mcp_secret_<id>.json` at `0600`. At chat-launch time, `Client.hasSecret()` detects any external server carrying a non-empty `Env`/`Headers` map and routes the **entire** mcp-config JSON — not just the secret value — to a `0600` temp file (`writeMCPConfigTempFile`) passed via `--mcp-config <path>`; only when no connection carries a secret does the config go inline on argv as before. A temp-file write failure omits `--mcp-config` entirely rather than falling back to inline JSON — a degraded chat beats a leaked secret.

**Why locked:** Argv is visible to every other local process via `ps` (and process-list APIs). A secret is only as safe as `google_token_<id>.json`/`slack_token_<id>.json` if it is stored the same way — 0600, file-based, never argv — end to end, including the moment it's *delivered* to the subprocess, not just at rest.

**Test guards:** `internal/externalmcp/secret_store_test.go` `TestSecretStore_RoundTrip` (0600 file round-trip); `cmd/connections_test.go` `TestConnections_AddHTTPWithoutSecretStdinCreatesNoSecretFile` (no `--secret-stdin` ⇒ no secret file at all); `internal/ai/client_test.go` `TestMCPConfigDelivery_SecretGoesToFileNotArgv` (a secret-carrying connection never appears inline in `buildArgs`'s returned argv, only as a `--mcp-config <path>` pointing at a 0600 file), `TestMCPConfigDelivery_NoSecretStaysInline` (no secret ⇒ config stays inline, unchanged from pre-feature behavior).

**Locked since:** 2026-09-09

## QC-04 — Fresh-or-visible

**Status:** Enforced

**Observable:** An OAuth-backed connection (its secret carries an `oauth` block) reaches the chat subprocess only with an access token Go verified or refreshed immediately before launch — with one named exception below — `cmd/generator.go`'s `loadExternalMCPServers` calls `mcpoauth.EnsureFresh(ctx, grant, now)` per enabled connection before building its `ai.ExternalMCPServer`. A token that cannot be refreshed never reaches the subprocess: the connection is skipped for that launch and the failure is written to the row (`database.SetExternalConnectionStatus(id, "revoked", err.Error())`), which Settings surfaces (the status dot + "Sign in again"). The derived `Authorization: Bearer …` header is computed into a local copy of the headers map and is never written back into `secret.Headers` — a stale bearer can never be persisted as if it were a static secret. A rotated refresh token is persisted (`store.Save(secret)`) **before** the new access token is handed to the caller; if that save fails, the connection is skipped rather than handing out a token whose refresh half cannot be recovered on a later run. A connection whose grant carries a known expiry that is still comfortably ahead triggers zero network calls.

**The one exception, stated plainly:** a grant whose `expires_at` is zero (the server returned no `expires_in`, so the lifetime is unknown) is treated as "must verify": it is refreshed on **every** launch when a refresh token is present — so such a grant is never silently stale, at the cost of one token-endpoint call per launch. But when the lifetime is unknown **and** there is no refresh token either, there is nothing to verify against: the stored access token is handed over unverified, and a server-side revocation will surface only as opaque tool-call failures inside the vendor CLI while the row still reads `ok`. Requesting a scope that yields a refresh token (`connections oauth <id> --scope "offline_access …"`, no default — this is a generic client) removes this case. It is documented rather than engineered away because no local check can distinguish a live token from a dead one without asking the server, and probing the resource server on every launch would trade this gap for a latency and rate-limit cost the owner did not ask for.

**Why locked:** A Quick Connection's OAuth token is short-lived (Atlassian's expires in about an hour) and the chat subprocess is headless — it can neither complete a browser handshake nor refresh mid-conversation. Without this contract a launch could silently hand the model a dead bearer token (the tool calls would then fail opaquely inside the vendor CLI) or, worse, a crash between refresh and persist could burn a rotated refresh token and strand the connection with no way back except a full re-sign-in.

**Test guards:** `cmd/generator_test.go`: `TestLoadExternalMCPServers_OAuth_Fresh` (fresh grant ⇒ zero network calls, header set from the stored token), `TestLoadExternalMCPServers_OAuth_Expiring` (expiring grant ⇒ refreshed, persisted, header set from the new token), `TestLoadExternalMCPServers_OAuth_InvalidGrantRevokesAndSkips` (refresh failure ⇒ connection skipped, row `status='revoked'` + `error`, other connections unaffected), `TestLoadExternalMCPServers_OAuth_RevokedConnectionRecoversToOK` and `TestLoadExternalMCPServers_OAuth_FreshGrantRevokedRowRecoversToOK` (a previously-revoked row flips back to `status='ok'` once refresh/use succeeds again), `TestLoadExternalMCPServers_OAuth_SaveFailureSkipsConnection` (persist-before-use: a save failure after a successful refresh skips the connection rather than using the unsaved token), `TestLoadExternalMCPServers_StaticSecret_HeadersAndEnvPassThrough` (a non-OAuth connection's static `env`/`headers` are unaffected by any of this). Plus the pre-existing `internal/ai/client_test.go` `TestMCPConfigDelivery_SecretGoesToFileNotArgv`, which covers the bearer header's delivery into the `0600` mcp-config file rather than argv once QC-04 has produced it. Underlying refresh mechanics (skew boundary, rotation, missing-refresh-token, `invalid_grant`, and both halves of the unknown-expiry exception — `TestEnsureFresh_UnknownExpiryWithRefreshToken_AlwaysVerifies` and `TestEnsureFresh_UnknownExpiryNoRefreshToken_HandedOverUnverified`) are pinned in `internal/mcpoauth/refresh_test.go`'s `TestEnsureFresh_*` cases; the secret file's atomic write is pinned by `internal/externalmcp/secret_store_test.go`'s `TestSecretStore_SaveIsAtomic`.

**Locked since:** 2026-09-10

## Known v1 limitation

External connections are only wired for the claude provider (`*ai.Client.SetExternalMCPServers`, dispatched from `cmd/generator.go`'s `newQueryClient` via the `externalMCPConfigurable` type-assert) — the codex provider and the ollama/runtime-B in-process tool loop have no equivalent wiring, so a configured Quick Connection is ignored on those providers. Since 2026-09-10 this is **surfaced, not silent**: `connections add`/`enable` print a non-fatal stderr warning when the configured provider is not claude (`warnIfProviderIgnoresConnections`, keyed on the frozen `ConfiguredProviderID()`), and the Desktop Quick Connections card shows a matching caption (`QuickConnectionsProviderNotice`). The wiring gap itself is unchanged.

## Changelog

- 2026-09-10: OAuth sign-in wave (`docs/superpowers/specs/2026-09-10-quick-connections-oauth-design.md`). New contract **QC-04** (fresh-or-visible). A new `internal/mcpoauth` package implements the generic MCP-spec OAuth client (discovery with RFC 9728/8414 fallbacks, dynamic client registration with a BYO client-id fallback, PKCE S256 authorization-code flow over a plain-HTTP 127.0.0.1 loopback on ports 18541-18550, refresh, revoke); the grant lives in the connection's existing `mcp_secret_<id>.json` under an additive `oauth` key (`internal/externalmcp.Secret.OAuth`) — no schema change. `cmd/generator.go`'s `loadExternalMCPServers` runs the pre-launch refresh (QC-04) and is now the first place `external_connections.status`/`error` get written (`db.SetExternalConnectionStatus`) — QC-01/QC-02/QC-03 are untouched by this (no new table, no registry tool, the bearer header still only ever reaches the subprocess via the `0600` mcp-config file). CLI: `watchtower connections oauth <id> [--app-return] [--no-open] [--client-id] [--client-secret-stdin]`; `connections list` gains an `auth` column (`oauth`/`static`/`none`); `connections remove` best-effort revokes the grant when the server advertised a `revocation_endpoint`, before deleting the secret. Desktop: the add sheet offers "Sign in with OAuth" for http connections, and a `revoked` row shows "Sign in again" — both drive the same CLI command. Known limitation: the pre-launch refresh is sequential and synchronous, up to 30 s per stale connection (`httpClient.Timeout` in `internal/mcpoauth/discovery.go`), so several dead connections can delay a chat launch — bounded, not unbounded; still claude-only per the existing v1 limitation above, unchanged by this wave.
- 2026-09-10: close-v1 wave (`docs/superpowers/plans/2026-09-09-quick-connections-close-v1.md`). No contract change. (1) The http-transport config shape `{"type":"http","url","headers"}` is now pinned by `internal/ai/client_test.go` `TestBuildMCPConfig_HTTPServerShape`/`_OmitsEmptyHeaders` — previously asserted only by the source (owner-notice #3 of PR #147). (2) The claude-only limitation above is surfaced by a CLI stderr warning + Desktop caption instead of failing silently. (3) The add-sheet's raw-JSON secret field became a kind-adaptive key/value editor (`ExternalConnectionSecretBuilder`, field names match Go's `Secret` verbatim) and arguments are tokenized quote-aware (`CommandArgsTokenizer`); the secret still reaches the CLI via `--secret-stdin` only, so QC-03's guards are untouched.
- 2026-09-09: file created with QC-01..03, all Enforced, by the Quick Connections feature (Tier 2 of the connection taxonomy in `docs/superpowers/specs/2026-09-09-quick-connections-external-mcp-design.md`). Tier 3 (the pipeline bridge) is specced but not built — no contract yet.
