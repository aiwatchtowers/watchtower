## IDEA-01 — Floor honesty

**Status:** Enforced

**Observable:** A consolidator run (`internal/ideas.Consolidate`, prompt `ideas.consolidate`) advances the `workspace` floors (`ideas_digest_floor`, `ideas_stream_digest_floor`, `ideas_transcript_floor`) only when the whole run applied cleanly. An AI generator error, malformed/unparseable JSON, a reply missing the `ops` key, a mid-apply error, or a floor write that matches no `workspace` row advances no floor and writes no row — stage-1 material (fresh `digest_topics`, `stream_digests`, `meeting_transcripts` rows) is never consumed without being applied. When the input cap (`ideas.max_prompt_chars`) truncates a run, floors advance only past the rows actually included in that truncated input, so the carried-over remainder is picked up by the next run.

The converse also holds — a floor never *stalls* on material that was genuinely consumed. A run with zero new material is a clean no-op (no floor movement, no AI call), but a run whose units were all inert (empty `stream_digests` rows — pre-2026-09-13 ones only, stage 1 no longer writes any; stale recap-less transcripts; a unit larger than the whole prompt budget) makes no AI call and still persists its advanced floors, so the same rows are not re-read forever. **Both cut points are tie-safe**, because every reload is strictly greater-than over a coarse timestamp: at the loader's row cap, `ListJiraIssuesUpdatedSince` and `ListGmailThreadsForExtract` drain the whole boundary timestamp rather than cutting inside it; at stage 1's prompt-budget cut, the claim is trimmed back below the first dropped unit's timestamp, and when that leaves nothing the whole boundary group is rendered instead (see the stage-1 clause below). A cut that lands inside a timestamp and still advances past it buries whatever ties there.

The same contract applies one level up, per stage-1 source: the Gmail (`ideas.digest_email`) and Jira (`ideas.digest_jira`) pre-digest passes advance their own per-account floors (`google_accounts.ideas_email_floor`, `jira_accounts.ideas_jira_floor`) **only past material actually rendered into that pass's prompt**, and treat a reply missing the `topics` key as a failure. The prompt budget (`ideas.max_prompt_chars`) truncates the rendered block, so "loaded" and "rendered" differ: the floor is derived from the renderer's own tag set — the threads/issues put in front of the model, which is by construction the same set a candidate may cite (IDEA-02) — and stops at the first unit the budget dropped, never at a plain maximum over the rendered ones (`renderedEmailWindow`, `renderedJiraFloor`). Both source windows arrive oldest-first while the Jira block is grouped by project and the Gmail block by thread, so a dropped unit can be older than a rendered one; stopping at the first drop is what keeps it above the floor. Stopping there is not sufficient on its own: since both reloads are strictly greater-than over a coarse timestamp (Gmail's `internal_date` is second-granular; one Jira bulk edit stamps many issues at once), a rendered unit **tying** with the first dropped one would leave the floor sitting exactly on a timestamp that still holds unmined material, so the trailing tie is trimmed off the claim. When trimming leaves nothing — the cut landed wholly inside one timestamp — the pass instead **renders that whole boundary group** and advances past it. A group sharing one timestamp is all-or-nothing (both reloads are strictly greater-than, so the floor cannot stop part-way through one), which is why the drain's ceilings are sized to be **out of reach of ordinary bulk activity** rather than to trim a typical load. There are two, in different dimensions, and they share one disposition: `maxTieDrainUnits` (1000 units, above a Jira bulk change's own 1000-issue maximum and above both loaders' per-pass caps) and `tieDrainCharCeiling` (600 000 chars — ten times the **default** prompt budget, pinned to it in both directions so neither lowering nor raising `ideas.max_prompt_chars` moves the protection: five times a 200-issue bulk edit, while staying inside a light-tier context). The byte ceiling exists because a ceiling out of reach in units gives no protection in the dimension that actually fails: an over-context drain makes the call *error*, so the floor never advances and the same oversized drain is rebuilt every cycle, losing the tie group **and everything above it**. Either ceiling stopping a drain is a fault, not a statistic — the undrained remainder goes under the floor, so the pass logs an ERROR naming the account, the timestamp, how many units were not rendered, and both ceilings against the block it built. Neither ever retreats: a drain that stops without advancing is a permanent stall. Gmail's per-thread `maxMessagesPerThread` cap keeps a thread's OLDEST messages because Gmail's floor is **message**-granular: the claim stops at the first message the cap dropped, so a thread's excluded tail holds the floor below itself and is mined next run. **Jira's floor is issue-granular, and this clause does not extend to Jira comments** — see the limitation below. The pass's `stream_digests` `period_to` is derived from the same value, so a row's period describes what it summarizes. **A pass always renders at least one unit** — its oldest, overshooting the cap when that unit alone exceeds it, with the overshoot logged naming the unit and the cap: rendering nothing would be honest about the floor and still lose the window, since a floor that cannot advance makes the account re-read the same un-renderable unit forever while mining nothing. The overshoot is bounded at one unit.

**Known limitation — Jira comments past `maxCommentsPerIssue` (stated, not fixed).** The clause above is about whole units. One level down, `renderedJiraFloor` matches **whole issues** against the tag set, so nothing can hold the floor below a rendered issue's own `updated_at`: an issue with more new comments than the cap (20) renders its newest 20, the floor passes the issue, `ListJiraIssuesUpdatedSince` reloads on a strict `>` and does not return it, and `ListJiraCommentsSince` therefore never sees the remainder. Those comments are not re-listed. The direction of the cap cannot fix this — either half is lost, and the newest are the half worth keeping for a decisions miner — so it keeps the newest, unlike Gmail's message-granular cap, which genuinely can hold the floor below its own tail. What IS always rendered is the issue itself (key, summary, status, description), so what the cap loses is supplementary context, never a whole unit. Making the Jira floor comment-aware is the real fix and needs `internal/digest`'s `advancesWindow` invariant ported across packages first — otherwise an issue whose comments alone exceed the prompt budget stalls forever.

A stage-1 pass whose validated topics are empty writes **no `stream_digests` row** — an empty row is a digest with no content, which badges the Desktop Digests feed unread for nothing and marks a window covered on the strength of material it does not carry — but still advances its floor over the rendered window: the window was genuinely mined, it just had nothing worth recording (the converse clause above, one level up). Coverage is therefore evidenced only by rows that carry content: `HasStreamDigestCovering`'s backfill skip can no longer fire for such a window, so a re-backfill over it pays for one more stage-1 AI call — cost, never correctness (IDEA-05 dedups the re-mine), and for Gmail that check is already largely decorative (GB12).

Floors are seeded at install time: migration 00050 stamps the three `workspace` floors at the current top of each source table, so the registry starts from material mined after it shipped instead of backfilling all of history on the first run. The per-account stage-1 floors self-initialize on their first run instead, since an account connected later has no migration to seed it.

**Feature Manager extension (2026-08-16):** re-enabling a feature writes these floors from outside the pipeline — an explicit owner action, not consolidator logic. `features enable ideas` stamps the three `workspace` floors at the current top of their source tables (exactly migration 00050's install-time seeding); `features enable stream-digests` stamps the per-account `ideas_email_floor`/`ideas_jira_floor`. The two hooks are disjoint on purpose: the toggles are independent, so enabling one must never advance the other's floors. Nothing is consumed-without-being-applied here — the owner is choosing not to back-fill the window the feature was off, and `watchtower ideas mine --from <date>` remains the way to mine it. See `docs/inventory/features.md` FEAT-03.

**Why locked:** The consolidator is the only place ideas/decisions get created from raw material; if a floor could advance on a failed or partial run, that cycle's candidates would be silently lost — the exact "nothing gets lost" promise this feature exists to deliver would break on its own error path.

## IDEA-02 — No invented provenance

**Status:** Enforced

**Observable:** Every mention `ref` the consolidator emits is validated against the refs actually present in that run's stage-1 input (Slack `<channel_id>|<ts>`, `transcript:<id>`, Gmail `gmail:<account_id>:<thread_id>`, Jira issue key). A ref that does not resolve is dropped; if an op loses all of its mentions this way, the whole op is discarded and a `refs_rejected` counter increments — nothing invented is ever persisted. A mention's stored `source` is likewise *derived* from the ref that survived validation, never copied from the model's own `source` token (which is ignored entirely). The same validation applies one level up: the Gmail and Jira stage-1 passes reject a hallucinated ref before it ever reaches `stream_digests`, and a unit dropped for prompt budget is dropped from the valid-ref set too, so nothing can be cited that the model was never shown.

Slack refs get the same treatment at the layer where they are first assembled, because a digest topic's `message_ts` is itself model-emitted: `renderTopicUnit` resolves every idea/decision candidate's ts against a real, non-deleted `messages` row in that channel (one batched existence-only `db.FilterExistingMessageTS` per topic, exact string match — no normalization, no prefix repair, the MEM-13 strict-set precedent) at material-assembly time. An unresolvable candidate is dropped from the rendered unit AND from the run's valid-ref set, so the model is never shown evidence nobody could follow and can never cite it; a topic whose candidates all drop renders empty and is consumed like a candidate-less one (its floor still advances, IDEA-01). The `messages` read failing is an infrastructure error that fails the run — never a verdict that every candidate was invented. Drops are counted and surfaced, not log-only: the pipeline accumulates `slack_refs_dropped`/`refs_rejected` (the `AccumulatedUsage` pattern), and they appear on the `ideas mine` output line, in the backfill envelope, and in the daemon log — so "no Slack ideas this run" and "everything was discarded" are distinguishable to the owner.

The validation has a write-time twin one layer down, so the exact-match gate is satisfiable in the first place: `formatMessages` renders each message's raw Slack ts (`ts=` tag) into the digest prompts — before this, the model only ever saw `HH:MM` and *constructed* every `message_ts` (measured on the production DB: 43 of 3233 decision refs resolved) — and `blankInventedMessageRefs` (internal/digest) blanks any `decisions[].message_ts`/`ideas[].message_ts` not present among the messages actually rendered into that prompt, at digest write time, keeping the item and killing only the fake ref. Historical digest rows written before the renderer fix remain unverifiable and are dropped by the consumer-side check above; `ideas mine --from` can re-mine any window once new digests cover it.

**Why locked:** This is the MEM-13 pattern applied to ideas — an idea whose only evidence is a model-invented Slack timestamp or Jira key would be unverifiable and would corrupt the chronology the whole registry is built around.

## IDEA-03 — Links, not deletes

**Status:** Enforced

**Observable:** Converting an idea to a Target (`converted_target_id`) and merging one item into another (`merged_into_id`) are both *links*, never deletes — the original `ideas` row survives with its status changed to `converted`/`merged`.

- **Convert** keeps everything on the row: the idea, its `idea_mentions`, and its Discuss chat all stay exactly where they are, plus a `converted_target_id` pointing at the new Target.
- **Merge** re-parents the merged item's `idea_mentions` onto the surviving idea, which becomes their single canonical home, and leaves behind a `merged_into_id` link. Nothing is deleted; the mentions move rather than being duplicated or dropped. The consolidator follows that link, so a later sighting of a merged-away item lands on the survivor instead of resurrecting a duplicate.

Neither Go nor Swift ever cascade-deletes mentions or chat on a status transition.

**Why locked:** The registry's chronology and the target/track/situation history it feeds are the point of mining ideas in the first place; a delete-on-convert or delete-on-merge would discard exactly the provenance trail the owner triaged.

## IDEA-04 — Resurfacing respects the verdict

**Status:** Enforced

**Observable:** When the consolidator attaches a repeat mention to an item whose status is `not_now`, `dropped`, or `rejected`, it inserts the mention row and sets `needs_review=1` with a `review_reason` ("brought up again in #channel") — but never changes `status`. The item surfaces in the Desktop "For review" section, but only an explicit owner action moves it out of its verdict status.

The flag must always be *clearable*: every Swift owner action — `setStatus`, `snooze`, `merge`, `supersede`, `markConverted` — clears `needs_review`/`review_reason` in the same write, and the detail pane offers at least one such action for every status a resurfacing can flag (including `rejected` and `dropped`, which get "Activate" alongside "Merge"). An idea that could be flagged but not unflagged would sit in the review queue forever.

**Why locked:** A repeat mention silently reversing the owner's earlier "not now" or "rejected" call would make triage decisions non-sticky — the owner would have to re-litigate the same idea every time it comes up again, defeating the point of triaging it once. The clearability half is the same contract from the other side: a flag with no way out turns the review queue into a graveyard.

## IDEA-05 — Re-mining idempotency (ref-level dedup)

**Status:** Enforced

**Observable:** Re-mining any already-mined material never duplicates registry state. Mechanically: (1) an `attach_mention` whose ref already exists on the target idea inserts nothing; (2) a `new_idea`/`new_decision` op whose mention refs ALL already exist anywhere in `idea_mentions` creates nothing (the material was already mined — `mentions_deduped` counts it); a partially-known op keeps only its unknown refs. The check runs inside the apply transaction against `idea_mentions.ref` + source. "Already exist" for clause (2) means **known before this consolidation pass began** ([OWNER] ruling, 2026-08-08, GB6) — a ref minted by an EARLIER op within the SAME apply pass does not count, so a single message can still mint two distinct new ideas that both happen to cite it: `applyConsolidateOps` tracks refs it has itself inserted this pass and excludes them from the known-set check for every later op in the same pass.

The check is a lookup per mention inside `applyConsolidateOps`, backed by `idx_idea_mentions_ref ON idea_mentions(source, ref)` (migration 00051) — it protects the everyday pipeline too, not only the backfill re-mining path that motivated it, since floor manipulation of any kind can no longer double-mint. Clause (2) (`new_idea`/`new_decision`) uses `db.IdeaMentionRefsKnownTx`, a ref -> idea_id map lookup, since it only needs to know whether a ref is known ANYWHERE. Clause (1) (`attach_mention`, GB5) uses a dedicated `db.IdeaHasMentionRefTx(tx, ideaID, source, ref)` instead of the same map: a ref can legitimately be recorded on more than one idea (a message that separately evidences two already-tracked ideas), and `IdeaMentionRefsKnownTx`'s ref -> idea_id map can only ever report ONE owning idea per ref — whichever a query happened to return last, nondeterministically. The attach path needs a deterministic, target-scoped answer to "does THIS idea already have this ref", which only the dedicated query gives. `mentionsDeduped` is threaded up through `applyConsolidateOps`'s return and surfaced on the consolidator's log line next to `refs_rejected`.

**IDEA-05 x IDEA-04:** when an `attach_mention` is dropped because its ref is already recorded on the target idea, `needs_review` must NOT be set even if the target's status is `not_now`/`dropped`/`rejected` — a deduped attach carries no new evidence, so it must not resurface a verdict the owner already made. IDEA-04's needs_review flag is reserved for a mention that actually lands.

**Why locked:** The backfill feature (spec `docs/superpowers/specs/2026-08-08-ideas-backfill-design.md`) deliberately re-mines material the ordinary pipeline may have already seen — a lowered floor, a re-run over an overlapping window, or a retried cycle after a crash. Without ref-level dedup, any of those would silently double-mint ideas/decisions or duplicate mentions, corrupting the registry's chronology and counts.

## Changelog

- 2026-09-13 (audit fix wave 2, owner decision 8): the consolidator's owner-preference block no longer offers **decisions** as examples of owner taste. `ListIdeaVerdictExamples` had no `kind` filter, and since the 2026-08-12 split a mined decision is born `active` with no owner act at all — so every decision the assistant ever recorded satisfied the status arm, and on a real workspace they outnumber owner-rated ideas enough that `LIMIT 20 ORDER BY updated_at DESC` let them dominate the LIKED/APPROVED list, teaching the miner that the owner approves of everything. The query now carries `kind != 'decision'`, ANDed *outside* the rating/status disjunction so a decision rated in the Digests ledger cannot slip in through the `owner_rating` arm either. `buildPreferencesBlock`'s bucketing is unchanged: the bare `status = 'active'` LIKED arm **stays** ([OWNER] ruling), because with decisions excluded the only ways an idea or note reaches `active` are the Desktop Approve button and `CreateManualIdea` — both explicit endorsements. No numbered contract is affected (IDEA-01..05 say nothing about the preference block) and no prompt id or version changes, since the block rides the user message.
- 2026-09-13 (audit fix wave 2, controller ruling on the same day's entry below): the stage-1 rendered-floor rule gained its **bounded single-unit overshoot**. The first version of the fix froze the floor when the prompt budget fitted no unit at all — honest about the floor, but it left such an account re-reading the same un-renderable unit forever and mining nothing, which loses the window exactly like a dishonest floor does; "unreachable at the default cap" is not an answer, since an operator-set cap is a supported configuration. Both renderers now always render their **oldest** unit, overshooting `ideas.max_prompt_chars` when that unit alone exceeds it, and the pass logs the overshoot naming the unit and the cap so an operator can see why the prompt is bigger than they asked for. The two guards added the same day are renamed accordingly (`TestIdeas01_EmailNothingRendered_NoCallNoRowFloorUnchanged` → `TestIdeas01_EmailOversizedThread_RenderedAnywayFloorAdvances`, and the Jira twin), keeping their `TestIdeas01_` prefix and pinning the replacement rule — including the log line — rather than the retracted one. The zero-rendered branch that remains in each pass is now an unreachable invariant check that fails the account's pass loudly instead of claiming a floor from a zero value.

  **Whole-branch review follow-up (final-review §3, §4, §9).** Three closing changes. (1) The drain gained a **byte ceiling** beside its unit ceiling (`tieDrainBudgetFactor`, ten times the prompt budget, floored at the default). A byte bound was rejected in the round below on the grounds that stopping short re-creates under-floor loss; that reasoning was wrong, because the unit ceiling already stops short and already advances — the bound is not different in kind. What the no-byte-bound path actually produced was *worse*: an over-context drain makes the call error, so the floor never advances and the same oversized drain is rebuilt every cycle, losing the tie group **and everything above it** while paying for a failing multi-megabyte call each time. The byte ceiling inherits the unit ceiling's disposition exactly — advance anyway, counted `ERROR:` fault, never a retreat — and the fault line now names both ceilings against the block it built, so which one stopped the drain is readable. It is pinned to the **default** prompt budget in both directions (A5): a lowered `ideas.max_prompt_chars` must not shrink the protection, since the drain bypasses that knob by design and a model's context does not shrink with a cost setting, and a raised one must not grow it — at 120 000 a budget-relative ceiling would reach 1.2 MB ≈ 300k tokens, past a 200k context, raising the protection out from under itself and restoring the stall it exists to prevent. (2) Jira's `maxCommentsPerIssue` was flipped to oldest-first by analogy with the Gmail thread cap and then **reverted in the same wave** (final-review A4): the analogy does not transfer, because Gmail's floor is message-granular — a thread's excluded tail holds the floor below itself — while Jira's is issue-granular, so nothing can hold the floor below a rendered issue's `updated_at` and *either* direction loses the comments past the cap. The flip changed only which 20 survive, and the newest are the half a decisions miner wants. Worse, this file had meanwhile been edited to promise the guarantee explicitly, which turned an overstated contract into a stronger overstatement. The cap keeps the newest, and the limitation is now **stated** in IDEA-01 above instead of papered over — a contract that admits a limitation being worth more than one that promises what the code cannot do.   **Same-day follow-up (review finding T5-B1): the prompt-budget cut is now tie-safe, like the loader cut beside it.** Stopping at the first dropped unit still left the floor ON the boundary timestamp whenever a rendered unit tied with the dropped one — and both reloads are strictly greater-than over a coarse timestamp (Gmail's `internal_date` is second-granular; one Jira bulk edit stamps several issues at once), so that tie-mate was never read again. Reproduced on both sources: a two-project bulk edit where `BBB-1` never rendered and the next run returned only `AAA-2`, and two Gmail threads sharing a second where the next run returned nothing. It was a residual, never a regression — pre-fix those rows were buried along with the whole window — but the reworded contract promised a guarantee the code did not deliver. The claim is now trimmed back below the first dropped unit's timestamp (`trimPartialBoundarySecond`'s rule at the second cut point), and when trimming leaves nothing the whole boundary group is rendered and the floor passes it — the escape, bounded by `maxTieDrainUnits` (the `db.BoundarySecondRowLimit` precedent). That ceiling was set at 50 in the first cut of this fix and **raised to 1000 in the same wave** on review: a tie group is all-or-nothing, so anything the ceiling trims is lost, and at 50 a 60- or 200-issue bulk edit — the very scenario the blocking reproduction used — would have quietly gone under the floor, reinstating the defect on a rarer branch. 1000 sits above a Jira bulk change's own 1000-issue maximum, above a plausible one-second Gmail burst, and above both loaders' per-pass caps (300 issues / 500 messages), so only the loaders' unbounded boundary-drain re-read can produce a group that big. Hitting it is therefore treated as a fault: an ERROR log naming the account, the timestamp and the count of unrendered units, rather than a quiet residual. Two smaller items rode along: Gmail's `maxMessagesPerThread` cap now keeps a thread's OLDEST messages and the floor tracks rendered MESSAGES rather than rendered threads, so a capped thread's tail stays above the floor instead of being buried (it is the same contract violation in miniature — and with the newest-N direction the honest floor could not advance at all); and IDEA-01's "tie-safe at their cap" sentence, which described only the loader cut, now names both. **Cost note for the owner:** because a stage-1 floor now advances only over what fitted in the prompt, `internal/ideas/backfill.go`'s `drainStage1` needs one AI call per budget-sized chunk instead of converging in about two cycles per source, so a long "Find Ideas" backfill costs more calls and can hit `backfillMaxCycles` (50) and report `Capped` where it used to converge — honest and surfaced, but a real change to what that button costs.
