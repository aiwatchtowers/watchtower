## AGENT-01 — The model never writes

**Status:** Enforced

**Observable:** Every write-tool call that reaches the chat-mode MCP server becomes one `agent_actions` row and nothing else. With trust `ask` (the default) no data table changes on the call; trust is per (tool, surface) — `tool_trust` is keyed by both and `Propose` reads only the row for the binding's own surface, so an `execute` granted on one surface (an owner's `actions trust … --surface reaction`, say) never applies a call of the same tool from another surface (main chat, runtime B) inline — the 00065 seeds (`create_idea`/`remind_me`/`brief_context` = `execute`) were fanned out to every surface the tool is on by migration 00112, so the upgrade changed nothing observable (owner decision 2026-10-14, ask #118: upgrade keeps today's behaviour); the workbench surface is no trust place (`SetTrust` refuses it, DEV-06); the tool's `Execute` runs only from `Registry.Apply`, which the Desktop drives after the owner approved. A validation failure writes no row at all. This holds identically on the **runtime-B in-process loop** (`internal/agentloop`, the Go tool loop for HTTP providers): a write-tool call there routes through `Registry.Propose` (records a proposal), never `Execute` — the loop has no path that executes a write tool. A workbench session's `send_slack_message` (External, `ProposeUnderDirectApply`) is the AGENT-01 path too: a pending row the owner approves in the Desktop (2026-10-02, DEV-06 rule 3). **Exception (2026-09-29, DEV-06):** on the `project` surface under `Binding.DirectApply` — reachable only through `watchtower mcp --workbench N` (or its legacy spelling `--project N`) — a write is applied inline like an execute-trust call, without a per-call owner approval: still exactly one `agent_actions` row (`trust_at_create='execute'`), still through `Apply`'s claim, never an `External` tool, never a tool that does not name the `project` surface. See `docs/inventory/dev-surface.md` DEV-06. **Automation surface (Automations P2):** a write an automation run makes is the same path — `Registry.Propose` with `Binding{Surface: "automation", AutomationRunID: <run>}`, one `agent_actions` row with `context_type='automation_run'`, `context_id=<run id>`, pending with trust `ask` unless AGENT-03's automation auto grant or a `tool_trust(tool, 'automation')` row decides execute; an automation binding never takes `DirectApply`, a dry run never reaches `Propose` (the SDK records a `dry_run` step and no row, AUTO-12), a run's context (`AutomationRunID` or `context_type='automation_run'`) is refused on every other surface, and chat-mode `mcp --context-type automation_run` is refused. A workbench automation's run writes the same way (Automations P5, spec §13): its row carries the run, not the workbench, so `Propose`, `Approve` and every `Apply` of an `automation_run` row — inline and `actions apply` alike — resolve the workbench from run → `automations.project_id` (`Registry.automationWorkbench`) and run `WorkbenchAlive` and the tool's `Scope` against it; a binding whose `WorkbenchID` is not its run's workbench is refused with no row; a row whose run no longer exists — deleting a workbench cascades its automations and runs — fails closed (`ErrAutomationRunGone`): `Propose` writes no row, `Approve` leaves it pending, `Apply` lands it `failed` and `Execute` never runs. A write of a live workbench applies; one whose workbench was deleted after the propose fails at Apply. (P2–P4 refused every workbench automation write with `ErrWorkbenchAutomationWrite` until this resolution existed; P5 removed that gate and the SDK's matching `NotAvailable`.) `actions trust <tool> execute` without `--surface` does not touch the automation surface — an automation-wide level is set only with an explicit `--surface automation`. **`agent()` (Automations P6):** an `agent()` loop of an automation — runtime B in process, or the claude/codex CLI child through `watchtower mcp --chat --surface automation --automation-run N` — is the same path: a write tool call is `Registry.Propose` with `AutomationAgent` set, proposals only (always ask, even under a grant or an `execute` trust row, AGENT-03), and the loop has no path to `Execute`.

**Why locked:** This is the whole premise of giving the assistant write tools at all — "model proposes, code disposes" (MEM-08) applied to actions. If a write tool ever executed on propose, every prompt-injection payload in synced Slack/Jira text would become an unreviewed write.

## AGENT-02 — Dev surface untouched

**Status:** Enforced

**Observable:** `watchtower mcp` without `--chat` or `--project` registers no write tool and no `get_action`, and keeps `PRAGMA query_only=ON`. (`--project N` is DEV-06's project-bound mode: it mounts only the `project` surface's tools plus `get_action`, never a chat write tool.) The chat mode is a separate entry point (`--chat`) that only the Desktop's `ai query --tools chat` launches. `--chat --surface automation --automation-run N` (Automations P6) is another chat-mode server, launched only by an `agent()` CLI child: it mounts the run's effective tool set plus `get_action` (its rows only), and the dev server is unchanged.

**Why locked:** The dev-surface server is handed to external coding agents via `watchtower integrate`; DEV-01 promises them a read-only knowledge base. A proposal tool on that server would let a foreign agent file actions into the owner's app.

**Test guards:** `internal/mcp/actions_test.go` `TestAgent02_DevModeRegistersNoWriteTools`; `internal/mcp/server_test.go` `TestAllToolsAreReadOnly`, `TestNoToolMutatesDatabase` (dev mode).

**Locked since:** 2026-09-04

## AGENT-03 — External tools never auto-execute

**Status:** Enforced

**Observable:** `Registry.SetTrust(tool, execute)` returns `ErrExternalExecute` for a tool with `External: true` (`create_jira_issue`, `connect_jira_board`, `send_slack_message`, …); `watchtower actions trust` surfaces that error; the Settings toggle is disabled for external tools. The same lock covers a local tool marked `AlwaysAsk: true` (`dismiss_tracks`, a bulk write): `SetTrust` returns `ErrAlwaysAsk`, `Propose` records it pending even from a persisted `execute` trust row, a direct-apply session refuses it, and the Settings toggle is disabled for it (`always_ask` in `actions tools --json`).
**Exception — the automation auto grant (owner-approved 2026-10-14 in ask #265; in code with Automations P2):** on the `automation` surface only, a call made by an automation run is applied without a per-call Approve — External tools included, AlwaysAsk tools never — when an `automation_tool_grants` row exists for (that automation, that tool) whose `grant_hash` equals both the automation's current `approval_hash` and the run's `recipe_hash`. Such a grant is written only by `watchtower automations auto <id> <tool> on --hash <sha>` from the Desktop, refused under an AI agent's environment markers (AGENT-07) and refused for a hash other than the current one; the grant is active only while the recipe's `approval_hash` equals the granted hash — any change to the recipe's script or permissions (by anyone, the assistant included) deactivates it, and only the owner granting the new hash or a return to the exact granted text re-activates it. An auto write is still one `agent_actions` row (`trust_at_create='execute'`, `context_type='automation_run'`) applied through `Apply`'s claim (AGENT-05), logged as an `auto=1` step of its run and shown in the Inbox as applied. No other surface, binding, trust row or grant can execute an External tool.
In code (`Registry.resolveTrust` → `resolveAutomationTrust`), first match wins on the `automation` surface: `AlwaysAsk` → ask; a call made inside an automation's `agent()` (`Binding.AutomationAgent`, spec §6.5) → ask, even under an active grant or an `execute` trust row (pinned by `TestTrustOrder_AutomationSurface`; since Automations P6 `agent()` sets `AutomationAgent` on both runtimes); an active grant → execute (`Receipt.Auto` true only when that execute applied); `External` → ask; else `tool_trust(tool, 'automation')`, ask when absent. An execute whose tool's `Ready` rejects the stored args (several pinned candidates) is recorded pending with `trust_at_create='ask'` instead, never applied-then-failed. Every other surface keeps its order unchanged.

**Why locked:** An external write cannot be undone by the app. The owner's click is the only thing standing between a model mistake and a ticket in a shared tracker — or, for `connect_jira_board`, a board selected against the live site and pulled into every digest. The owner decided (ask #265) that a reviewed automation is the click: approving the exact code and permissions once is a stronger review than approving each scheduled post blind; the hash binding keeps that review from being reused for code the owner did not see.

**Test guards:** `internal/tools/registry_test.go` `TestAgent03_ExternalToolCannotBeExecuteTrust`; `internal/tools/slack_send_test.go` `TestSendSlackMessage_ExternalCannotBeExecuteTrust`; `internal/tools/jira_board_test.go` `TestConnectJiraBoard_ExternalCannotBeExecuteTrust`; `internal/tools/tracks_dismiss_test.go` `TestDismissTracks_NeverExecutesWithoutApproval` (AlwaysAsk); `cmd/actions_test.go` `TestActions_TrustAndTools`; automation exception (P2): `internal/tools/registry_automation_test.go` `TestAgent03_AutoGrantAppliesExternalOnlyOnAutomationSurfaceWithMatchingHash`, `TestAgent03_AutoGrantNeverCoversAnotherAutomationOrSurface`, `TestAgent03_RecipeEditMakesAutoGrantInactive`, `TestAgent03_AlwaysAskIsNeverAuto`, `TestTrustOrder_AutomationSurface` (incl. its `AutomationAgent` rows), `TestAutoGrant_NotReadyRecordsPending`, `TestAutoGrant_FailedExecuteIsNotAuto`; `cmd/automations_session_test.go` `TestAutomationsCLI_SessionCommandsRefusedUnderAgentMarkers` (per marker: both commands refused, the step still waiting, no wake); `cmd/automations_auto_test.go` `TestAgent03_AutoGrantRefusedUnderAgentMarkers`. `agent()` (P6, the `AutomationAgent` branch now live): `cmd/automations_agent_test.go` `TestAgent_WritesStayProposals`; `cmd/mcp_automation_test.go` `TestAgentMCPServer_WriteIsPendingProposalWithRunContext` (a write through the automation-run server is a pending row carrying the run context).

**Locked since:** 2026-09-04

## AGENT-04 — Draft-only surfaces see no tools

**Status:** Enforced

**Observable:** Only the main AI Chat (`ChatViewModel`), the target chat (`TargetChatViewModel`, whose `ChatSurfaceSpec` is `.actions("target")` while tools are available, so its `EmbeddedChatEngine` builds the tool mode) and, since 2026-10-16 (Automations P3, spec §14.5, D11, approved in ask #270), the automation editor chat ("Change in words" and the "New automation" sheet's **Describe in words**, `AutomationEditorChatSurface`, `ChatSurfaceSpec` `.actions(surface: "automation_editor")` for an existing automation and `.actionsWithoutContext(surface: "automation_editor")` for a new draft) pass a `toolMode` to `WatchtowerAIService`. The `automation_editor` surface carries only `draft_automation` (a read), `save_automation` (the only write tool mounted, `AlwaysAsk`) and the read tools: no other write tool, no tool with empty `Surfaces` that writes, and none of the owner's Quick Connections external MCP servers (`newQueryClient` skips them on that surface — they may hold writes); under ollama that chat is `.draftOnly`. Everything else stays draft-only: meeting, idea and track chats declare `.draftOnly` in their `ChatSurfaceSpec` (so `EmbeddedChatEngine` sends `toolMode: nil`) and the setup chats call the convenience overloads that forward `toolMode: nil`, so their `ai query` never carries `--tools chat` and the model there never sees a write tool.

**Why locked:** review-rules "The assistant & chat contracts": draft-only surfaces never act on the world. A copied VM that silently inherits the tool mode would give a draft-only surface an action path.

**Test guards:** `WatchtowerDesktop/Tests/Core/WatchtowerAIServiceTests.swift` (`testBuildArgsWithoutToolModeNeverEmitsToolsFlag`, `testBuildArgsEmitsChatToolModeFlags`); `WatchtowerDesktop/Tests/ViewModelTests.swift` (`testSendPassesMainChatToolModeWithFreshTurnID`, `testOllamaSendsNoToolModeAndHonestPrompt`); `WatchtowerDesktop/Tests/TargetChatViewModelTests.swift` (`testSendPassesTargetToolModeWithContext`); and the `toolModes == [nil]` assertions in `MeetingChatSurfaceTests`, `IdeaChatSurfaceTests`, and `TrackChatSkillsPromptTests` (each surface's `ChatSurfaceSpec` is `.draftOnly`; `ChatSurfaceSpecTests.testDraftOnlyNeverBuildsAToolMode` pins that `.draftOnly` yields no tool mode). ## AGENT-05 — Apply exactly once

**Status:** Enforced

**Observable:** `Registry.Apply` **claims the row before it runs the tool** — a conditional `approved|failed → executing` update — so of two overlapping applies only one ever reaches `Execute`; the loser is refused with `ErrBadTransition` BEFORE its side effect, not after it. `Apply` runs a tool only from `approved` or `failed`; `applied` and `rejected` are terminal, and a row already in `executing` is refused too. `watchtower actions approve` moves `pending → approved` with a conditional update, so two concurrent approves cannot both execute. An apply whose process dies mid-flight leaves the row in `executing`, reclaimable only through `watchtower actions apply <id> --force` (which marks it `failed` first, so the reclaim is a visible event and not an implicit retry).

**Why locked:** External writes are not idempotent; a double apply is a duplicate Jira issue. A check-then-execute-then-record `Apply` satisfies every status assertion and still files the ticket twice — the claim is what makes "exactly once" true of the side effect and not just of the row.

**Test guards:** `internal/tools/registry_test.go` `TestAgent05_ConcurrentApplyExecutesOnce` (two goroutines, one blocking `Execute`: the loser is refused before it runs and the tool executes exactly once), `TestAgent05_RejectDuringExecuteCannotStealTheClaim` (a decision landing while `Execute` is in flight no longer matches the claimed row, so the apply that is already writing finishes and records it), `TestApply_ExecutesOnceAndRecordsResult`, `TestApply_FailureLandsFailedAndIsRetriable`, `TestApply_ExecutingIsNotApplicable`, `TestApply_RowGoneOnReReadIsNotFound` (a row deleted before `Apply`'s re-read is reported as `ErrNotFound`, never silently treated as success); `internal/db/agent_actions_test.go` `TestAgentActions_TransitionIsConditional`; `cmd/actions_test.go` `TestActions_RejectAndTerminalStates`, `TestActions_ApplyForceReclaimsAnInterruptedApply`.

## AGENT-06 — Chat mode is writable only for proposals

**Status:** Enforced

**Observable:** `watchtower mcp --chat` skips `SetReadOnly` — the connection stays writable so the registry can INSERT its `agent_actions` rows. Every read tool in the guard's call list still runs there without touching any data table: the same read-tool call list AGENT-02's dev-mode guard runs, plus `get_action`, leaves `guardTables` row counts unchanged on the chat session.

**Scope:** the call list is `readOnlyGuardCalls`, shared with DEV-01's `TestNoToolMutatesDatabase`, and it does not contain the memory tools. Their telemetry writes — `memory_open`'s `memory_node_stats` access bump, `memory_recall`'s retrieve shadow — are the documented deliberate-write exception DEV-01 already records, covered by their own tests in `internal/mcp/memory_test.go`; on the chat connection those writes actually land (on the dev surface `query_only` silently refuses them). On the `automation` surface neither lands: `memory_open` skips the bump there and `buildAutomationRegistry` mounts `memory_recall` without the shadow handle (Automations P1, ask #277; `TestMemoryOpen_NoAccessBumpOnAutomationSurface`, `TestBuildAutomationRegistry_AddsMemoryTools`). They are outside this guard by design, exactly as under DEV-01. The contract is "no read tool in the shared list writes", not "no read tool anywhere writes". A second deliberate write outside the list (2026-10-03): the workbench read tool `get_ask` moves an `answered` owner ask to `delivered` (guarded `WHERE status='answered'`) with no `agent_actions` row — reading the answer is the delivery receipt. It is mounted only on the workbench surface (`watchtower mcp --workbench N`), never on `--chat` or the dev surface, so it is not in `readOnlyGuardCalls`; DEV-06 rule 2 records it (`dev-surface.md`), and `TestGetAsk_OpenAnsweredAndAnotherWorkbench` (`internal/tools`) covers it.

**Why locked:** The `query_only` fence is gone exactly where the model also holds write tools. On the dev surface SQLite itself refuses a handler's write, so `TestNoToolMutatesDatabase` cannot tell a genuinely read-only handler from one whose write is being silently swallowed; on the chat surface nothing but the handler stops it. A read tool that started writing here would be an unreviewed write on the one connection the model can reach — AGENT-01 without a row to review.

**Chat-only reads (2026-10-16, Automations P3):** `draft_automation` is a read tool on the chat connection (surfaces `main` and `automation_editor`, not in `tools.ReadTools()`, so not in the shared list): it dry-runs a draft in memory and writes no row of any table, even for a script that calls `llm`, a write tool, `state.set` and `output.inbox`. The guard runs it from its own `chatOnlyReadGuardCalls()` list with a fake generator, measuring `guardTables` plus the five automation tables plus `agent_actions`, and asserts the dry run succeeded and the generator was called (so it cannot degenerate into measuring a parse error). Its editor draft cache (`<workspace>/automation-drafts/<conversation id>.jsonl`, written only on `automation_editor` with a conversation id) is a file beside the database, not a table — a UI cache of the tool's result, not a store of record.

**Test guards:** `internal/mcp/actions_test.go` `TestAgent06_ChatModeReadToolsDoNotWrite` (asserts the connection really is writable first, so the guard cannot degenerate into re-measuring `query_only`; since P3 it also runs `chatOnlyReadGuardCalls`); `internal/automations/authoring/draft_test.go` `TestDraftAutomation_WritesNothing`; the call list is shared with `TestNoToolMutatesDatabase` via `readOnlyGuardCalls` so a tool can never be covered by one guard and missed by the other.

## AGENT-07 — Only the owner approves

**Status:** Enforced

**Observable:** `watchtower actions approve`, `watchtower actions apply` (with or without `--force`) and `watchtower actions trust <tool> execute` refuse to run — exit non-zero, nothing written — when the process carries an AI agent's environment marker: `CLAUDECODE` (Claude Code), `CODEX_THREAD_ID` or `CODEX_SANDBOX` (Codex), `WATCHTOWER_TERMINAL_SESSION_ID` (an agent launched in a Watchtower workbench terminal; a plain shell terminal does not get it), or `WATCHTOWER_AUTOMATION_RUN_ID` (`automations.RunEnvMarker`, a child an automation run starts — set from P5's `shell()`/`session()` and P6's `agent()`). Any non-empty value counts. The same refusal covers the automation owner gestures (Automations P1, ask #271): `automations confirm`, `automations save --confirm-hash` (the file is not written) and `automations dry-run` of a recipe that is not confirmed yet (no run row is written; a confirmed recipe dry-runs under markers too) — AUTO-06 in `docs/inventory/automations.md` — and, owner-only since ask #293, `automations enable` and `automations delete`, refused before anything is read or written (the row stays as it was, the recipe file stays) with the hint "enable and delete are owner-only" (after `refuseUnderAgent`'s own "the owner decides in Watchtower Desktop (or runs this from a plain Terminal)"). Since Automations P2 (spec §6.4), `automations auto <id|slug> <tool> on --hash <sha>` — the only writer of an automation auto grant (AGENT-03's exception) — is refused the same way, before the automation is looked up, and no grant row is written; `automations auto … off` stays open. Since Automations P5, `automations session-launched` and `automations session-ended` — the Desktop's reports for a `session()` step — are refused the same way before anything is read or written: only the Desktop reports. `automations disable`, `cancel`, `run` (of a confirmed, enabled recipe), `rescan` and a plain `save` stay open (they only reduce activity or run what the owner already confirmed); removing a recipe file by hand is outside the CLI and not covered. `actions reject`, `trust <tool> ask`, `list`, `show` and `tools` stay open. Approval happens from the Desktop (`AgentActionFeed` shells out to the same CLI from the app's own environment, which `Constants.resolvedEnvironment()` already strips of `CLAUDECODE` and which never carries the terminal session variable). An approval is also bound to the args the approver read: `Registry.ApproveSeen` (and `actions approve --args-sha256 <hex>`) refuses with `ErrBadTransition`, leaving the row pending, when the given sha256 of `args_json` does not match the stored args; with or without the digest, the approve lands in one conditional update on the args it read (`db.ApproveAgentActionWithArgs`), so a no-patch approve never approves args rewritten between its read and its write.

**Known limit:** the markers are environment variables, so an agent that deliberately unsets them (`env -u CLAUDECODE …`) is not stopped by this check alone; it closes the direct path (an injected instruction running `watchtower actions approve <id>` under an allow rule such as `Bash(watchtower:*)`) without a prompt. The Desktop passes `--args-sha256` on every approve (`AgentActionFeed.approve(_:shownArgs:patch:)`, the digest of the card's rendered `args_json`, single and Approve all alike); the flag stays optional for a direct CLI call. The Desktop's resolved environment drops all five markers (`Constants.agentEnvMarkers`), so an app launched from an agent's shell can still approve for the owner.

**Why locked:** A workbench agent proposes an External write (`send_slack_message`, `edit_confluence_page`, a Jira write) and the receipt names the action id; without this, a prompt injection in a synced message could make the same agent approve and execute it through the CLI, turning AGENT-01/03's "the owner's click is the only thing standing between a model mistake and the outside world" into a formality.

**Test guards:** `cmd/actions_test.go` `TestAgent07_CLIApproveRefusedUnderAgent` (per marker: approve, apply and execute trust refused with no status change, no execution, trust still `ask`; reject and `trust … ask` still work), `TestActions_ApproveArgsSHA256MustMatchTheStoredArgs`; `cmd/automations_test.go` `TestAutomationsCLI_ConfirmRefusedUnderAgentMarkers`, `TestAutomationsCLI_SaveIsAtomicAndIndexes` (`--confirm-hash` under a marker), `TestAutomationsCLI_DryRunUnconfirmedRefusedUnderAgentMarkers`, `TestAutomationsCLI_EnableDeleteRefusedUnderAgentMarkers` (enable and delete refused, row still disabled and present, file still there; disable, rescan and run still open; without markers both work) (each runs over every marker of `agentEnvMarkers`); `cmd/automations_auto_test.go` `TestAgent03_AutoGrantRefusedUnderAgentMarkers` (per marker incl. `WATCHTOWER_AUTOMATION_RUN_ID`: `auto … on` refused with the recovery hint, no grant row; `auto … off` still works); `internal/tools/registry_approve_test.go` `TestAgent07_ApproveBindsToTheArgsTheOwnerSaw` (a stale digest is refused; a no-patch approve overtaken by an args rewrite is refused; the current digest approves); Desktop: `Tests/Core/AgentActionFeedTests` `testApprovePinsTheShownArgsDigest`, `testApproveAllPendingForTurn` (each row's own digest), `Tests/Core/ConstantsAgentMarkersTests`.
