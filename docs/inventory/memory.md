## MEM-01 — Validated provenance: no ref is written anywhere without resolving against its source of record

**Status:** Enforced (2026-07-20 owner review: generalized source-agnostic; absorbs MEM-13)

**Observable:** No provenance ref of ANY scheme (`""`/Slack message, `chat:`, `mail:`, `act:`, `cal:` — dispatched via the MEM-12 registry) is written to ANY memory artifact — an episode/entity/belief node, a rollup gist, or a rendered digest (`renderChannelDigest` → `memory_digest_shadow` today; the authoritative `digests` after the future legacy switch) — unless it resolves against its source of record at write time (e.g. a Slack ref: `SELECT 1 FROM messages WHERE channel_id=? AND ts=? AND is_deleted=0` — a tombstoned message would 404 for the owner just like a hallucinated one). The disposition is uniform at every write site:
- an invented ref (a year-shifted ts, a wrong channel, a ghost row) is dropped and counted (`refs_rejected` / `RenderRefsRejected`), never "fixed up" to a nearby real row;
- a unit whose refs ALL fail — an episode, a render topic — is discarded whole, never written ref-less;
- a lookup ERROR is not an invalid ref: it propagates and the write site freezes/isolates (the extraction window fails with the watermark frozen and re-extracts next run; situation ingest skips-and-logs that situation and continues; the render isolates the whole channel) — never a silent drop. Only a positive not-found drops and counts;
- situation ingest re-validates signal refs before copying them into `## Provenance`, even though detector-written refs resolve ~100% in practice; its rejected count is logged too.

Render clause (ex-MEM-13): a ref already present in an input episode's `## Provenance` set is trusted transitively with no DB round-trip — it was validated when the episode was written; a raw coverage-gap message ts still resolves through the registry's message checker. This keeps the render-inversion's go/no-go claim — 100% valid refs by construction versus legacy's ~0% — structural, not prompt-dependent.

**Why locked:** Provenance is the memory's trust anchor — every fact in the vault or a rendered digest must link back to a real row the owner can open, whatever the source. One hallucinated link that 404s poisons trust in every other link; silently repairing refs would be worse, attributing a claim to a source that never said it. Drop-and-count keeps the vault verifiable and makes hallucination measurable; conflating a failed check with a failed ref would silently discard verifiable provenance whenever the DB hiccups — the error path must freeze, not drop.

## MEM-02 — Rebuildable index: files are the source of truth

**Status:** Enforced

**Observable:** The SQLite index (`memory_nodes`, `memory_aliases`, `memory_fts`, and — **Phase 5 slice 3** — `memory_provenance`) is purely derived state. Dropping all memory index tables and running `watchtower memory reindex` (`memory.Rebuild`) reproduces an index equivalent to the one maintained incrementally across many `Reconcile` passes with edits, alias changes, and file deletions in between — the guard test compares full table dumps (ignoring `indexed_at`). `memory_provenance` (the episode-window index — each episode's `## Provenance` refs, classified by scheme and decoded to `ts_unix`) is **inside** this comparison: it is parsed wholesale-per-node from the body inside the existing `UpsertMemoryNode` transaction (the alias/FTS replace precedent), rebuildable from files, and cleared by `DropMemoryIndex` — so the slice-3 extension **strengthens** MEM-02 (more coverage) rather than weakening it. `memory_node_stats`, `memory_entity_hints`, `memory_dispute_flags`, and `memory_engagement` remain deliberately excluded: they are runtime telemetry / floor-passed accumulation not derivable from files.

**Why locked:** "Markdown + git is the memory, SQLite is a cache" is the architecture's core promise — it is what makes owner edits in any editor safe and the vault portable. If the index ever accumulated state not reproducible from the files, reindex would silently lose data and the files would stop being trustworthy as the canonical copy.

## MEM-03 — Owner edits are sacred: separate commit, never mixed

**Status:** Enforced

**Observable:** At the start of every consolidation run, if the vault working tree differs from HEAD (the owner hand-edited files in Obsidian or any editor), the diff is committed *first* as its own `memory(owner-edit): manual changes` commit before any machine write of that run. A subsequent machine commit's tree diff contains only machine-written paths — owner changes never ride along inside a machine commit, and machine writes never land in the owner-edit commit. A clean tree produces no owner-edit commit.

**Why locked:** The vault is advertised as owner-editable ("open it in Obsidian, fix what the secretary got wrong"). If a machine commit could swallow the owner's uncommitted edits, `git log` could no longer distinguish what the owner asserted from what the AI wrote — which destroys both auditability and the future Phase 3/4 features (reflection, belief revision) that read the commit history to know whose statement a line is.

**Test guards:**
- `internal/memory/vault_test.go::TestMemory03_OwnerEditsSeparateCommit`

## MEM-04 — Chunk atomicity: watermark freezes on AI failure

**Status:** Enforced

**Observable:** The extraction watermark (`workspace.memory_last_extracted_ts`) advances only past messages whose window's vault commit succeeded — never past a failed or still-pending window (`safeWatermark` in `pipeline.go`). A failed AI call freezes that window's messages above the watermark (re-extracted next run) while committed windows stay behind it; the run still completes `done`, the failure isolated to its `pipeline_steps` row (`status='error'`). A crash between a vault commit and the watermark write re-processes the chunk rather than skipping it — better a duplicate than a hole (semantic dedupe mops the duplicates).

Hardening, one line each (details: changelog + `docs/specs/memory-e2e-report.md`):
- shape-degenerate replies (JSON parses, every episode ref-less) freeze like an AI error, never read as routine chatter; a genuinely empty `[]` advances cleanly; counted in `RunStats.Malformed`;
- quiet channels group into one AI call (`groupWindowsIntoBatches`, caps `memory.batch_max_channels`/`memory.batch_max_messages`, default 20/1500) — freeze is then per-batch, an owner-approved trade-off (2026-07-15); a window already at the message cap still gets a solo batch, so busy channels keep per-channel isolation;
- a chunk cap cutting inside one whole-truncated second drains the entire second (`ListMemoryExtractMessages`), so same-second rows can never be skipped forever;
- one window holds at most `memory.max_window_messages` (default 200) messages; a later window never advances the watermark past an earlier failed window of the same channel;
- windows order by FIRST message ts and the watermark is written after EVERY committed batch (E2E fix 2026-07-16: the earlier last-ts ordering silently suppressed every per-batch advance, so a killed run lost the whole run's progress) — an interrupted run now loses at most the in-flight batch plus the uncovered tails of windows overlapping it.

**Why locked:** The watermark only ever moves forward, so any window it skips is lost to memory forever. Freezing trades a cheap re-extraction for zero lost windows — the same freeze discipline INBOX-09 established for the inbox watermark. The same reasoning covers degenerate shapes (a prompt-schema drift would otherwise silently discard every episode while looking like healthy quiet channels) and the second-boundary drain (a cut inside one busy second would silently drop the rest of that second forever).

## MEM-05 — Memory is a pure reader: it writes only the vault and memory-owned tables

**Status:** Enforced (2026-07-20 owner review: absorbs MEM-10 and MEM-14)

**Observable:** No memory step writes an operational table or moves a foreign watermark — every memory-side write lands in the vault, the derived index, or a memory-owned `memory_*` side table. Concretely, across a full consolidation run with every gate on:
- the inbox set (`inbox_items`, `situations`, `situation_signals`) stays byte-identical and `inbox_last_processed_ts` never moves; ingest bookkeeping lives in vault aliases (`situation:<id>`), never in columns on foreign tables — all INBOX-01..09 / DASH-01..07 contracts untouched;
- the operational set (`targets`, `tracks`, `day_plans`, `day_plan_items`) stays byte-identical with the slice-4 gates on — the mirror step and both read surfaces are pure readers, and the mirror read helpers in `internal/db/memory.go` are SELECT-only;
- symmetrically, the read surfaces (day-plan open loops, meeting-prep context, briefing journal) never write the vault: `OpenExistingVault` (degrade-silently on `ErrVaultNotInitialized`), no git-init, vault git log byte-unchanged.

Dispute flow (ex-MEM-10): memory marks a dispute-worthy belief only in its own `memory_dispute_flags` side table. The `decision_made` trigger item (`channel_id="memory"`, `message_ts="dispute:<belief_id>"`) is minted exclusively by the inbox pipeline's watchtower detector (`detectMemoryDisputes`), which clears the flag in the SAME transaction — a dispute surfaces exactly once (cap ≤2 per cycle, `memoryDisputeCap`) and from there is an ordinary detector item under every INBOX/DASH contract.

**Why locked:** Memory is a consumer bolted on; its whole safety argument is "it cannot break what exists." One write into a foreign table — or a watermark nudge — entangles two pipelines' failure modes and violates the other module's contracts from outside its guard tests. The three-layer split (raw stream / semantic vault / operational UI tables) dies the moment the vault becomes a second unaudited author of operational state: mirrors reflect state INTO the vault and must never flow back.

## MEM-06 — Owner-rank belief protection: observation never auto-flips an owner belief

**Status:** Enforced (Phase 3, `memory.semantic.enabled`)

**Observable:** A belief node carrying non-decayed owner-rank evidence (owner-authored support younger than the 180-day decay horizon) is never automatically retired or flipped by observed/inferred contradiction. In the belief pass (`ReviseBeliefs` → `applyOp`), a model `retire`/flip op against such protected owner support is downgraded — the belief lands `shaken` at most, never `retired`, regardless of how much observed contradiction accumulates. Since 2026-07-26 every rank's weight decays with a shared exponential half-life (`w = base × 2^(−age/180d)`, no floor — curve C, owner-approved); the PROTECTION window is a separate 180-day constant (`ownerFreshWindowDays`), so fresh owner support blocks retirement absolutely regardless of weight arithmetic, and only once the support ages past the window does a retire apply. A `shake` is always allowed (active → shaken) — protection blocks retirement/flip, not the softer "buffer" transition. Owner-rank protection requires the owner support to be written as a **canonical evidence line** (`- owner for <channel_id> <ts>`); a prose evidence bullet does not parse (it is logged and ignored by `parseBeliefEvidence`), so it carries no rank weight and cannot protect a belief.

**Why locked:** The owner is the authority on their own world. If a run of AI-observed contradictions could silently retire a fact the owner asserted, the memory would quietly overwrite the owner's own statements with model inference — the exact inversion of MEM-03's "owner edits are sacred." Asymmetric hysteresis (cheap to shake, expensive to flip, impossible to auto-flip over fresh owner support) keeps the belief graph anchored to what the owner actually said.

- `internal/memory/belief_math_test.go::TestApplyOp*` / `TestOwnerRankWeight` (exhaustive pure-math coverage of the rank/decay/downgrade rules)

## MEM-07 — Provenance never thins: eviction and merge preserve every ref

**Status:** Enforced (Phase 3, `memory.semantic.enabled`)

**Observable:** No consolidation step ever drops a provenance ref — of any scheme (the same refs MEM-01 validated at write). Eviction (`EvictEpisodes`) collapses a cold closed long-tier episode into a per-channel-per-month rollup (`sum_*`) whose gist line carries **every** provenance ref of the evicted episode verbatim; the episode file becomes a tombstone redirecting to the rollup (the resolver chases old `[[ep_*]]` links, the rollup line stays FTS-searchable), and its aliases move to the rollup. Nothing is deleted. Dedupe (`DedupeEpisodes` → `Merge`) is the same discipline for merges: a partial-overlap merge unions the loser-only refs into the winner's `## Provenance` before the merge, so a merge never thins provenance either. A second eviction into the same channel-month appends to the existing rollup rather than duplicating it.

**Why locked:** Provenance is the memory's trust anchor (MEM-01). Compression that silently loses even one ref would break the promise that every retained fact links back to its source of record — and eviction/merge, which touch the OLDEST records (least likely to be re-derived), are exactly where a dropped ref would be unrecoverable. Rollups trade episode-level narrative for space while keeping the audit trail intact.

## MEM-08 — Model proposes, code disposes: AI output reaches the vault only through validation

**Status:** Enforced (Phase 3, `memory.semantic.enabled`)

**Observable:** No strong-tier AI output ever mutates the vault directly. Belief ops from `memory.revise_beliefs` are applied only when the Go rank/threshold math (`applyOp`) permits the transition — the model proposes an op (`confirm`/`weaken`/`shake`/`retire`/`propose-new`) but never sets confidence/status/stability (extra JSON keys the op schema does not carry are ignored; birth confidence is computed and capped at 0.6). An op whose cited evidence refs are all invented (absent from the run's supplied episodes) is dropped and never reaches `applyOp`. Provenance markers from `memory.entity_rewrite` are validated the MEM-01 way — a marker not present in the input episode set is dropped and counted, never written. A `propose-new` whose subject does not resolve to an existing entity is rejected.

**Why locked:** The semantic tier lets a strong model rewrite pages and revise beliefs — far more consequential than the light-tier extractor. If the model's self-reported confidence or an invented citation could land in the vault unchecked, a single confident hallucination would corrupt the belief graph with fabricated certainty and unverifiable provenance. Keeping every AI output behind a code-side gate makes model influence auditable and bounded by the same provenance discipline as everything else.

## MEM-09 — Owner rank is authored, never inferred

**Status:** Enforced (Phase 4, `memory.surfaces.chat`)

**Observable:** Owner-rank belief evidence (`- owner <for|against> chat:<conversation_id> <ts>`) is minted **exclusively by code**, only for a `chat:` evidence ref that resolves to a `role='user'` turn in a Discuss conversation whose `context_type` is in the allowed set (`OwnerChatTurnExists`), or from a `memory(owner-edit)` vault commit. The belief-op JSON schema (`beliefOpJSON`) carries **no rank field**, so no model output can name, introduce, or upgrade evidence to owner rank — the model only cites a ref and chooses a direction; `newEvidenceLines` elevates a validated `chat:` ref to `rankOwner`, every other ref stays `rankObserved`. A `chat:` ref the model cited but that was never staged this run, resolves to a `role='assistant'` turn, points at a conversation whose `context_type` is not in the allowed set, or hits absent chat tables (headless daemon) is dropped and counted like an invented episode ref (`validateChatRefs`, MEM-01 discipline) — never minted at owner rank.

**Slice-2 extension (context-type set widening, `memory.sources.chats`, default false):** the allowed `context_type` set is **flag-derived, and gates the ingest read and the resolver authenticity check in lockstep** (`chatContextTypes` in `pipeline.go`): `{"situation"}` when the flag is off — **byte-identical to the Phase-4 situation-only path, so every pre-existing `TestMemory09_*` guard passes unchanged** — and `{"situation","target","track"}` when on. Owner rank is still **code-minted from an authored `role='user'` turn only** — the widening adds context types, never a new minting author or a model-nameable rank. What turns *stage* additionally depends on the "remember this" opt-in: a `situation` turn stages every owner turn (Phase-4, unchanged); a `target`/`track` turn stages **only** when it opens with a case-insensitive `remember:` / `remember this:` prefix (`parseRememberCommand`, prefix stripped for the verbatim statement) — an ordinary target/track chat turn is a drafting instruction, not a world statement, so it is consumed by the floor but never staged. If a model could mint or claim owner rank, a confident hallucination would forge the owner's own voice and permanently protect a fabricated belief — the exact inversion of MEM-03/MEM-06. Keeping the elevation a pure code path keyed on `role='user'` provenance makes "the owner said this" verifiable, never inferred.

## MEM-11 — Surfaces are read-only over belief history

**Status:** Enforced (Phase 4, `memory.surfaces.briefing`/`memory.surfaces.reflection`)

## MEM-12 — Provenance-resolver registry: every ref scheme has a registered validator, or it is rejected at write

**Status:** Enforced (Phase 5 slice 1)

**Observable:** MEM-01 generalized from two hardcoded checks to a resolver registry (`provenanceRegistry`/`provenanceResolver`, unexported, `internal/memory/provenance.go`), which dispatches a ref to the resolver registered for its scheme — `""` (Slack message, `MessageExists`), `chat` (owner Discuss turn, MEM-09), `mail` (a `gmail_messages` row), `act` (a whitelisted owner-interaction row, MEM-15), and — **Slice 2** — `cal` (a `calendar_events` row, `CalendarEventExists`, `calResolver`) and — **Jira source, 2026-07-22** — `jira` (a non-deleted `jira_issues` row, `JiraIssueExists`, `jiraResolver`). `Validate` returns `(ok, registered, err)`; a ref whose scheme has **no registered resolver** (`registered == false`) is dropped and counted exactly like an invented ref (`validateRefsVia`/`validateChatRefs`), never written.

There is **no single global registry**: each write site validates through a registry SCOPED to the schemes valid there, so a scheme can never be smuggled in where it does not belong. The Slack extractor uses a message-only registry (`extractorRegistry`, built from the `checkMsg` seam so the MEM-01 lookup-freeze test still bites); the Gmail extractor a mail-only registry (built once per run); the mechanical **calendar builder a cal-only registry** (`newProvenanceRegistry(calResolver{p.db})`, built once per calendar step, so a calendar episode can carry only `cal:` refs); the mechanical **jira builder a jira-only registry** (`newProvenanceRegistry(jiraResolver{p.db})`, so a Jira episode can carry only `jira:` refs); **situation ingest a message+jira registry** (jira-detector signals mint `jira:<KEY>` refs instead of dropping against `messages` — the 2026-07-20 owner-review finding closed); the belief surface the pipeline's registry (`p.registry`, which now also registers `calResolver` and `jiraResolver` so a belief-pass op could later cite a `cal:` or `jira:` episode ref — harmless when either source is dark; `validateChatRefs` still only routes `chat:`/`act:`, and episode/mail/cal/jira refs pass that surface untouched). The registry unifies the *lookup* only — each caller keeps its disposition: the episode extractor freezes the batch on a lookup **error** (MEM-01/MEM-04), the calendar builder freezes its step on a `cal:` lookup **error** but drops-and-counts a positive non-resolution (an event swept from the DB between load and validate, the episode then discarded ref-less), the jira builder freezes its step on a `jira:` lookup **error** but drops-and-counts a non-resolution (an issue swept from the DB), the belief pass soft-drops a `chat:`/`act:` lookup error (dropped `chat:`/`act:` refs are logged at their resolver, one consistent site). Folding existence AND authenticity (the chat resolver's `role='user'` check) into one seam keeps "does this ref resolve?" a single auditable question.

## MEM-15 — Owner-action rank is code-minted from a real interaction row, and confers no owner protection

**Status:** Enforced (Phase 5 slice 1, `memory.sources.actions`)

**Observable:** The `owner-action` evidence rank (belief math weight 0.8, between `observed` 0.6 and fresh `owner` 1.0) is minted **exclusively by code** (`newEvidenceLines`), only for an `act:<table>:<row_id>` evidence ref that a registered resolver confirmed points at a real **whitelisted** owner-interaction row (`inbox_feedback` / `user_interactions` / `decision_reads` / `situations`, `InteractionExists`). The belief-op JSON schema carries **no rank field** (MEM-08), so no model output can name, forge, or upgrade a rank — the model cites a ref and chooses a direction; the code derives the rank from the ref scheme. An `act:` ref to a non-existent or non-whitelisted row is dropped and counted like an invented ref (`validateChatRefs`). Decisively, `owner-action` does **NOT** trigger MEM-06 fresh-owner protection: `hasFreshOwnerSupport` keys on `rankOwner` exactly, so an owner interaction can weigh a belief but can never permanently shield it from retirement the way the owner's own words do.

**Why locked:** An owner interaction (a dismiss, a conversion) is authentically the owner but **non-propositional and ambiguous** — a dismissal has many readings. It should outweigh a third-party observation, but if a model could mint it, or if it conferred MEM-06 protection, a confident hallucination could forge an "owner action" and permanently protect a fabricated belief — the exact inversion MEM-09 guards against, one rung down. Keeping the mint a pure code path keyed on a validated interaction row, and explicitly denying it retirement-protection, bounds how much an ambiguous mechanical signal can move belief state.

## MEM-16 — Importance snapshot vs live retention score

**Status:** Enforced

**Observable:** `memory_nodes.importance_score` is a persisted snapshot of `ComputeImportance`'s owner-override-or-computed value (no recency factor), refreshed on every index write path — `Reconcile`/`Rebuild` (two-phase: scan, then a refinement pass that runs AFTER the deletion loop, making importance scan-order-independent within one call) and `merge.go`'s `upsertIndexNode` (the second write path, ~16 call sites) — for future retrieval ranking. `evict.go`'s `RetentionScore` always recomputes importance live per eviction candidate (plus recency) and never reads the column. The two answer different questions ("worth surfacing now" vs "worth compressing") and must not be collapsed into one stored value without owner review. Refinement is delta-complete one hop out: an untouched node's score refreshes when a touched node's body newly links to it OR stops linking to it (prior-body capture on edit and on deletion), and the owner-touch git signal is memoized once per batch call (`ownerEditedMemo`). Full gap-fix history (5 real gaps across three whole-branch reviews): changelog entries 2026-07-18/19.

An accepted staleness class: a node's persisted `importance_score` can lag engagement deltas (including stale-too-HIGH after a dismissal) until the node is next touched or delta-refined, since engagement bumps in `action_ingest.go` mutate `memory_engagement` without touching the node's file — this is bounded because engagement is dark-by-default (`memory.sources.actions`), the contribution is clamped (±3, weight 2.0 = max drift of 6.0), eviction always recomputes live regardless, and entity-page rewrites opportunistically heal it over time.

**Why locked:** The two consumers have different freshness needs: eviction needs a live number for a small bounded candidate set each run; retrieval ranking needs a persisted number it can sort over without recomputing per-node signals vault-wide on every read. Merging them would either make eviction score against a stale snapshot or make every `Reconcile` pay eviction's live-computation cost across the whole vault. They share only the pure `ComputeImportance` primitive — which is also where the accepted owner-steerable salience input (2026-07-20 design task, see MEM-15's future note) will land, so both consumers see it. Correctness here spans ALL index-write paths, not just `Reconcile` — that is exactly where the shipped gaps hid.

## Known v1 limitations (not contracts, but do not "fix" silently)

- **Cache-token split is approximated.** `pipeline_runs` records cache reads and cache creation in separate columns (migration adding `cache_read_tokens`/`cache_creation_tokens`), but `digest.Usage` only exposes a combined API total — so the pipeline records the residual (total API tokens minus prompt tokens) under `cache_read_tokens` and leaves `cache_creation_tokens` at 0 until `Usage` grows the real split (`completeRun` in `pipeline.go`). Numbers in the two columns are an estimate, not provider truth.
- **Access stats never count today.** `memory_open` bumps `memory_node_stats` with an ignored error — but every production MCP surface runs the database in read-only (query_only) mode, so the write always fails there and the counters simply never increment. The columns are dead telemetry in v1, not an under-count: Phase 3 (retention scoring, eviction) must NOT build on them until a writable stats path exists.
- **MEM-02 diverges on quarantined files.** Incremental `Reconcile` preserves the last-good index row of a file it quarantines (parse failure after an owner edit), but a full `Rebuild` drops the index first — the quarantined node then has no row at all until the file is repaired. The reindex-equivalence contract is stated for healthy vaults; with quarantined files present the two paths intentionally differ (stale-but-searchable vs absent).
- **MEM-03 has a crash window.** The owner-edit commit is not atomic with the machine writes that follow: if the process is killed between a machine file write and its commit, those machine-written files sit uncommitted in the worktree and the NEXT run's `CommitOwnerEdits` sweeps them into a `memory(owner-edit)` commit — machine text mislabeled as the owner's. Rare (requires a kill inside a narrow window) and self-limiting, but `git log` attribution is not crash-proof; do not present it as such, and do not "fix" it casually — a proper fix needs a staging/journal step.
- **Vault text is framed as model-mediated (shipped in Phase 4).** Episode bodies and entity rewrites are AI summaries of third-party messages — model-mediated hearsay with provenance links, not the owner's own notes. The Phase-4 surfaces present vault content as such: the Swift Discuss MEMORY block is labeled "notes the secretary has built from Slack/Jira — model-mediated, not the owner's own words," and the briefing revision journal frames each line as "notes derived from Slack/Jira, model-mediated." Only `chat:` owner evidence (MEM-09) and `memory(owner-edit)` commits carry owner-asserted text. Do not reword these surfaces to imply the owner authored vault prose.
- **`memory_dispute_flags` is runtime side-table state, excluded from MEM-02, self-healing on reindex.** A belief flagged dispute-worthy — by the weekly reflection pass, OR by the belief pass itself when MEM-06 owner-rank protection downgrades a model retire/flip to shaken (design §4 case (a), M4: `applyExistingOp` calls `SetDisputePending` on the downgrade so the conflict surfaces promptly, not only a week later at reflection) — is recorded in `memory_dispute_flags(node_id, flagged_at, reason)`, not on the `memory_nodes` row — the same runtime-state precedent as `memory_node_stats`, so it is outside MEM-02's dump comparison and `DropMemoryIndex`/`Rebuild` clears it. Resetting the flag on reindex is safe: a still-conflicting belief is re-flagged by the next reflection/belief pass (self-healing). The inbox watchtower detector reads and clears the flag (MEM-10); the flag is consumed exactly once per surfaced dispute.
- **The chat-turn floor advances on a completed pass even when the model cited nothing (by-design).** `ingestChatStatements` stages owner Discuss turns; the belief pass consumes them. The `memory_chat_turn_floor` advances only after the belief pass ran to a clean commit AND was not truncated by the `beliefs_max` cap — a belief-pass error, a budget-skip, or a cap-break holds the floor so the same turns re-stage next run (a cap-break may leave a staged owner ref uncited). But a pass that *completed* without a cap-break advances the floor even if the model declined to cite a staged owner ref: the turn had its chance and is not re-scanned forever (it can still be re-derived from a later restatement or an owner vault edit). `RunStats.ChatTurnsIngested` counts a staged turn only once the floor actually advances (a held floor never counts it), so a re-scan is not double-counted. A genuine DB error mapping a turn's situation freezes the whole ingest (the turn is not consumed); a turn that maps to no memory entity is consumed (floor advances) but stages nothing, logged. (M3, 2026-07-16.)
- **`chat:` evidence grammar depends on Swift-owned tables.** Owner Discuss turns become belief evidence via a `chat:<conversation_id>` channel-id in the canonical evidence line, resolved against `chat_conversations`/`chat_messages` — tables the Desktop app creates lazily (GRDB) the first time the owner opens a Discuss chat. On a headless daemon they are absent; both `ingestChatStatements` and the belief pass's `validateChatRefs` treat their absence as an empty read (never an error), so the chat surface is a clean no-op until the app has created them. Turn identity is `chat_messages.id` (the ingest floor); turn ts is `chat_messages.created_at` truncated to whole seconds.
- **Failed-window re-extraction can duplicate episodes (now mopped up by dedupe).** Per MEM-04, a failed window is re-extracted next run — but extracted episodes get fresh ULIDs, so a window that partially succeeded before failing (or a crash between vault commit and watermark write) can produce near-duplicate episode nodes. Since the 2026-07-16 first-ts-ordering fix the exposure on an interrupted run is bounded to the in-flight batch plus the uncovered tails of windows overlapping it (previously a mid-run kill could lose the WHOLE run's advance and duplicate every committed batch — the E2E incident). A long-spanning window's tail above the last safe advance still re-extracts as a tolerated duplicate: the scalar watermark prefers duplicates over skips by design. Phase 3's `DedupeEpisodes` (behind `memory.semantic.enabled`) now mops these up mechanically — provenance-ref overlap within one channel merges the newer duplicate into the older (MEM-07 unions provenance on merge). Write-time dedupe against prior extractions/situation coverage is still deferred; duplicates remain accepted at write time, cleaned on a later semantic pass.
- **`memory_entity_hints` is runtime accumulation, excluded from MEM-02, and survives reindex.** Unresolved extractor entity hints are persisted (`hint`, `episode_id`) for concept-entity promotion once a hint recurs across enough distinct episodes. Like `memory_node_stats` it is NOT derivable from vault files, so it is excluded from the MEM-02 reindex-equivalence comparison. Unlike `memory_node_stats` it is deliberately **not** cleared by `DropMemoryIndex`/`Rebuild`, so a reindex never resets promotion progress — a design choice, not a leak.
- **Retention/eviction does not use access stats.** Phase 3 retention scoring (`RetentionScore`) intentionally excludes `memory_node_stats` access counters (write-dead in production, per the access-stats limitation above): importance is `links-in + situation-origin bonus + owner-touch bonus`, where owner-touch is computed lazily from `git log` for the bounded eviction-candidate set only. `RetentionScore` itself is still recomputed on demand, never stored — but see **MEM-16**: since Slice A of the memory-importance-score redesign, the SAME importance arm (`ComputeImportance`) is separately persisted as `memory_nodes.importance_score` for future retrieval ranking, refreshed by `Reconcile`/`Rebuild` (and `upsertIndexNode`) rather than recomputed live. The two are deliberately independent; do not read this bullet as contradicting MEM-16.
- **Raw episodes age before they can be evicted.** Extracted episodes are minted active/short and only *situation-finalized* episodes reach closed/long through ingest — so a raw non-situation episode is never closed by extraction and would never become an eviction candidate. A mechanical aging pass (`AgeEpisodes`, runs in `runSemantic` before eviction) transitions an active short-tier non-situation episode (no `situation:*` alias — those age through ingest) whose newest provenance event is older than `memory.semantic.age_after_days` (default 14) to closed/long; the 45-day `evict_after_days` window then applies to the now-closed episode. So the two windows compose: a raw episode ages at ~14 days, then is eligible for eviction ~45 days after its last event. Situation-aliased episodes are deliberately untouched by the aging pass (their lifecycle belongs to ingest), and the pass counts into `RunStats.Aged`.
- **`map.md` is hard-capped at ~2 KB; `index.md` is the full listing.** The two-tier world map splits the old unbounded `map.md` into a mechanical `index.md` (full per-entity listing, never injected, the browsing surface behind `watchtower memory index`) and a strong-tier hot `map.md` (5–8 areas + notable beliefs, the MCP `memory_map` read target). The strong render is truncated code-side at a line boundary to ~2 KB (`capMapBytes`) — the prompt asks for brevity but cannot be trusted to obey a byte budget (the pre-split render hit 56 KB at 447 entities). With the semantic tier off, `map.md` is still produced mechanically so `memory_map` always has a target.
- **Boundary drain can exceed the chunk cap.** When `memory.max_chunk_messages` cuts inside one busy second, the loader intentionally loads the whole second (see MEM-04), so a run may consume slightly more than the cap — bounded by one second of traffic. The per-window cap (`memory.max_window_messages`) still bounds each individual prompt.
- **Malformed count is run-level only.** Shape-degenerate episode counts surface in `RunStats.Malformed` and logs; `pipeline_steps` has no dedicated column for them (the failed window's step row carries `status='error'`). Adding a column is a schema change deferred until the count proves useful.
- **Malformed `internal_date` gmail rows are silently excluded.** The gmail extract/seed scans filter `internal_date != ''` and decode it with `strftime('%s', internal_date)`; a row whose `internal_date` is not RFC3339 yields a NULL/garbage unix value and is effectively skipped. Acceptable because the Gmail sync guarantees an RFC3339 `internal_date` — there is no defensive parse. (Deferred, 2026-07-16 slice-1 review; inventory note only.)
- **Authorless messages fall back to the raw user_id.** Messages whose author has no `users` row (deleted/ex-employee, never synced) are extracted with the Slack user ID as the author label — the extractor sees `U0ABC123:` instead of a display name until the user table catches up.
- **`memory_engagement` is runtime side-table state, MEM-02-exempt, and survives reindex.** Per-entity owner-engagement aggregates (`engaged_count`/`dismissed_count`/`last_interaction_at`, migration 00022) are derived from interaction rows the interaction floor may already have stepped past, so — like `memory_entity_hints`, NOT like `memory_node_stats` — they are excluded from `TestMemory02_ReindexEquivalence` AND deliberately **not** cleared by `DropMemoryIndex`/`Rebuild` (a reindex must not lose accumulation the floor cannot re-derive). It is a separate, writable table from the write-dead `memory_node_stats` access counters — the first LIVE feed for Phase-3's stubbed retention-importance input (`RetentionInputs.Engagement`, weight 2.0; only a positive net raises importance, a net-dismissed entity never scores below the un-engaged baseline).
- **A third independent extraction watermark.** `memory_gmail_last_extracted_ts` (migration 00022) is the Gmail episode-extraction watermark, distinct from `gmail_last_internal_date` (Gmail API *sync*) and `memory_last_extracted_ts` (Slack episode extraction). It advances only behind fully-committed thread batches (MEM-04) and never couples to the sync watermark. Email thread grouping key is `thread_id` (one thread → one episode).
- **Gmail thread idempotency is alias-keyed; DedupeEpisodes is Slack-scoped.** Every Gmail episode carries a stable `gmailthread:<thread_id>` alias, so re-extracting a thread (a reply in a later run, or a thread straddling the chunk cap) UPDATES the existing episode in place — same node id, provenance refs UNIONED (a thread's provenance only ever grows), Story/Outcome refreshed from the new extraction (the situation-ingest update-path discipline). Because gmail idempotency is guaranteed at WRITE time by the alias, `DedupeEpisodes` deliberately SKIPS mail-ref episodes (its provenance-overlap keying is Slack-only — a gmail episode's unique `mail:<message_id>` first-ref never shares a dedupe bucket anyway). A poison thread (more than `memory.max_window_messages` messages) is truncated to its NEWEST N messages for the prompt (a prompt note records the omission), while its watermark still trails EVERY loaded message so the dropped older ones are never re-loaded.
- **Gmail-sender seeding is gated and noise-filtered.** `seedGmailSenders` is a no-op unless `memory.sources.gmail` is on (threaded through `SeedConfig.Gmail`), so the source is literally dark when off. Two noise gates keep the person graph clean: the same `SeedConfig.MinMessages` floor people use (a one-off sender is not a person), and a machine-sender local-part filter (`no-reply`/`noreply`/`notifications`/`mailer-daemon`/`postmaster`/`bounce`/… — a code const list) dropping automated senders regardless of volume.
- **Retention engagement contribution is clamped.** The net owner-engagement fed into `RetentionScore` is clamped to `[-3, +3]` before scoring, so one runaway `memory_engagement` counter cannot pin an episode in memory forever; only a positive net raises importance (a dismissed entity never scores below the un-engaged baseline).
- **`gmail_messages` is migration-guaranteed, so its helpers propagate errors.** `GmailMessageExists`, `ListGmailThreadsForExtract`, and `seedGmailSenders` no longer tolerate a "no such table" error as a clean empty read (00016 always creates the table after `db.Open`); a query failure propagates (freezing the Gmail watermark / failing the extract batch's MEM-01 validation) rather than being masked — unlike the Swift-owned chat tables, which are legitimately absent on a headless daemon.
- **`owner-action` decays like every rank since 2026-07-26, and is still non-protecting.** The rank orders `observed (0.6) < owner-action (0.8) < owner-fresh (1.0)` at every age (shared half-life preserves ratios); `owner-action` never confers MEM-06 fresh-owner protection (MEM-15).
- **The mechanical 5D interaction ingest forms NO preference beliefs, and runs as its OWN Run step.** Slice 1 folds owner interactions into episode-mirror outcome annotations + `memory_engagement` aggregates + staged `act:` refs only (`action_ingest.go`/`runInteractionIngest`, Run step 4c behind `memory.sources.actions`). It is NOT a semantic-tier sub-step: the annotations and engagement aggregates land even with `memory.semantic.enabled` off (its staged `act:` refs are simply unused then — until `memory.semantic.preferences` renders them in the belief pass's OWNER ACTIONS block, slice 4). Deriving durable preference beliefs from owner actions is 5D semantic — shipped in slice 4 (the mechanical staging above is unchanged; only the belief-pass render is new).
- **A fourth independent extraction watermark, and the calendar builder makes NO AI call.** `memory_calendar_last_extracted_ts` (migration 00023) is the calendar episode-build watermark, distinct from the Slack (`memory_last_extracted_ts`), Gmail (`memory_gmail_last_extracted_ts`), and interaction-floor (`memory_last_interaction_id`) watermarks. The calendar source (`memory.sources.calendar`, default false) is **mechanical** (`calendar_ingest.go`/`runCalendarIngest`, Run step 3b after `SeedEntities` and before Slack extraction): one ended `calendar_events` row becomes at most one episode built straight from the structured row (title, time, organizer, attendees, location, description), and — where a `meeting_recaps` row exists — that already-AI-produced recap's summary/decisions/actions fold into Story/Outcome. It **reuses** the recap, never re-synthesizes; an event with no recap gets a metadata-only episode (a real story arc). The builder asserts the generator is never called (guard `TestRunCalendarIngest*` with `noCallGen`). Idempotency is alias-keyed (`calevent:<event_id>`, the `gmailthread:` precedent): a re-scan UPDATEs the episode in place, a content-equality check makes an unchanged re-scan a no-op (no empty git commit). A `cal:` lookup **error** freezes the step; a positive non-resolution (an event swept from the DB) drops-and-counts, the episode discarded.
- **Calendar past-event retention is ~24 h; the builder re-scans a bounded lookback.** The calendar sync retains only ~24 h of past events (`timeMin = now-24h`, then `DeleteStaleCalendarEvents`), so an event must be captured into an episode **while it is still present**. To catch a recap or event-edit that lands after the watermark has passed a still-present event, `ListCalendarEventsForExtract` re-scans a bounded lookback overlap (`calendarReprocessLookbackDays = 2`, a code const) below the watermark, and the `calevent:` alias + content-equality check keep that re-scan a no-op when nothing changed. Consequence: a daemon offline **> ~24 h misses the interim events** — they age out of `calendar_events` before any run sees them. A memory-specific longer calendar retention is a future enhancement, not this slice — do not "fix" it by widening the sync's `timeMin` (that couples the memory source to the inbox calendar sync's cost/volume).
- **A recurring-series entity keys on the Google `recurringEventId` parsed from `raw_json`.** `seedCalendarSeries` (gated `SeedConfig.Calendar`) makes one `calseries:<recurringEventId>` entity per distinct series among currently-synced recurring events (`is_recurring=1`); the id is parsed from `calendar_events.raw_json`'s `recurringEventId` key (`parseRecurringEventID`). A non-recurring event, or a recurring event whose `raw_json` carries no `recurringEventId` (malformed/absent), yields **no** series entity and is a clean skip (the Gmail `internal_date` defensive-skip precedent), not an error. A calendar episode of a recurring instance additionally links to its series entity (the channel-entity precedent).
- **Onboarding chats are not ingested.** The Slice-2 chat generalization covers `target` + `track` Discuss chats only. Onboarding chat (`OnboardingChatViewModel`) is never persisted to `chat_conversations` — it produces `custom_prompt_context` instead — so there is no Go-side row to ingest (resolved ambiguity #4). Do not add a `context_type='onboarding'` branch to `chatSubjects`; there is nothing for it to read.
- **"remember this" is the opt-in ingestion trigger for target/track chats.** An ordinary `target`/`track` Discuss turn is a drafting instruction, not a world statement, so it is **consumed by the chat-turn floor but never staged** as belief evidence; only a turn opening with a case-insensitive `remember:` / `remember this:` prefix (`parseRememberCommand`, prefix stripped for the verbatim statement) stages as owner-rank evidence there (resolved ambiguity #5). `situation` chats are unchanged — they still ingest **every** owner turn (Phase-4), and a `situation` turn may carry the command harmlessly (the prefix is stripped either way). "remember this" changes only *which* turns stage, never *how* owner rank is minted (MEM-09 code-mint) and introduces **no second vault write author** (the statement is owner-rank *evidence* consumed by the belief pass; the entity-page note is the belief pass's ordinary rendered result, MEM-11 boundary preserved — resolved ambiguity #6).
- **A bare target chat maps to nothing (slice 2) — resolved when `memory.sources.operational` mirrors exist (slice 4); unchanged when off.** Targets carry no channels/members of their own, so in slice 2 `targetSubjects` mapped a `target` Discuss chat only to the entities of the target's linked track(s) (`tracks.linked_target_id`), unioned — a target with **no** linked track mapped to no entity and its owner statement was consumed-not-staged. Slice 4 resolves this: `targetSubjects`/`trackSubjects` prepend the context's OWN mirror alias (`target:<id>`/`track:<id>`) to the refs list, so once the operational mirror exists a bare-target `remember this:` turn finally stages, subject-mapped to the mirror entity. When `memory.sources.operational` is off (no mirror) the alias never resolves and the behavior is byte-identical to slice 2 (`resolveSubjectRefs` skips an unresolved alias silently) — no new gating; the behavior keys off mirror existence.
- **The digest render-inversion is shadow-only compare-mode; the legacy pipeline stays authoritative.** Behind `memory.renders.digest_compare` (default false, structurally requires `memory.enabled` — the compare runs as a tail sub-step of `phaseMemory`, so no memory phase → no compare), the daemon renders each recently legacy-digested channel window from its memory episodes and writes the render to `memory_digest_shadow` ONLY — never a `digests`/`digest_topics` row, never a UI read, never a digest bound/watermark move (MEM-05/MEM-14; `memory_digest_shadow` is memory-owned throwaway compare telemetry keyed by (channel, period) that self-overwrites, so it is NOT cleared by `DropMemoryIndex` — leaving it avoids losing a report's input mid-validation, and it is not vault-derived so it is outside MEM-02). The legacy digest pipeline is byte-untouched and remains the authoritative consumer until the compare wins the owner's hand-review; the actual **switch** off legacy is a later slice, explicitly out of scope here. `watchtower memory digest-compare` runs it on demand and writes the branch report.
- **Compare coverage reflects extraction lag, not a fabricated miss.** The compare runs AFTER the episode extractor in the same cycle (resolved ambiguity #5), so the current window's episodes exist — but the extraction watermark may still trail the digest window's newest messages. Those trailing messages surface as **coverage gap** (fed raw into the render, cited only if they resolve — MEM-13), and the `coverage` metric (`covered_ts / total_window_msgs`, using the same bot/muted-filtered message set the extractor consumes) reports them as uncovered, never as a hallucinated miss. A window with **no** overlapping episodes records a coverage-0 shadow row and makes NO generator call — rendering from only-raw gaps would merely re-run legacy at cost. `coverage` is the reported fidelity input for the hand-review, not a correctness gate.
- **Interaction-ingest annotations on still-open situations are best-effort; engagement is the durable signal.** The step appends a dated owner-action bullet to a situation's episode-mirror `## Outcome`. For a **terminal** situation (converted/dismissed/done) IngestSituations finalizes then floors past it, so the annotation is durable; for a situation still **open**, the next `IngestSituations` pass regenerates the mirror body and may refresh the bullet away. The durable owner-action signal is the `memory_engagement` aggregate, not the annotation. There are TWO floor-driven feedback sources (M8, 2026-07-18): `inbox_feedback` (per-item, floor `memory_last_interaction_id`) and `feedback(entity_type='situation')` (the dashboard's situation-level thumbs since bda8032, floor `memory_last_situation_feedback_id`, see 00026, ref scheme `act:feedback:<id>`, `feedback` whitelisted in `interactionTables`); both are append-only, `InteractionsIngested` counts DISTINCT feedback ids per source (a 👍 on an item in N situations is one interaction), and per-(feedback,entity) bump dedup means a shared entity is bumped once. Situation verdicts have no floor: they are folded by a bounded idempotent re-scan whose novelty key is the situation id + verdict **TEXT** (not the movable `updated_at` date, so an `AttachSignal` `updated_at` bump never double-annotates/double-bumps; a genuinely changed verdict still appends), bounded to a 14-day `updated_at` window (a code const) so the terminal backlog never rides every run. **Only OWNER verdicts fold** (M7, 2026-07-17 final validation): `ListInteractionSituations` admits `status='converted'` (owner-only by construction) and done/dismissed rows whose `resolved_reason` is the Desktop's `user_done`/`user_dismissed` — the inbox pipeline's auto-resolve (`signals_resolved`) is a system action and must never mint owner annotations, engagement, or `act:` refs (`TestIngestInteractionsSystemAutoResolveNeverFolds`). Engagement bumps for a run are applied in ONE transaction (`BumpEngagements`): if any bump fails the batch rolls back and the feedback floor is HELD, so the re-scan is clean (transient-error semantics, no double-count); `last_interaction_at` is the interaction's RFC3339 `created_at`. Same MEM-05 discipline as ingest: inbox/situation tables are read only.
- **Target/track mirrors are re-scan + content-equality with NO watermark AND NO time window (slice 4; window dropped in the round-1 review, F1/F3/F13).** Unlike the four episode-extraction watermarks, the operational-mirror step (`runOperationalMirrors`, Run step 3c behind `memory.sources.operational`) keeps no cursor: `targets`/`tracks` are small, mutable, non-append-only tables where a floor would miss in-place edits, so the step re-scans **every** row (`ListTargetsForMirror()`/`ListTracksForMirror()` take no window arg) every run and decides per row against the existing-mirror alias set (`db.MirrorAliasNodeIDs()`, one SELECT loaded once): the implemented skip predicate is that a **terminal** row (target done/dismissed; track dismissed) with **no existing mirror** is never mirrored — it is skipped immediately, before `conversionLinks`, before any body work (the `ingestNewSituation` terminal-skip precedent, now keyed on the missing mirror alias, not on an `updated_at` window); every other row (active, or **terminal WITH an existing mirror**) is built/refreshed against its preloaded node id, and a byte-equality check on the deterministically-rendered entity body makes an unchanged refresh free (no empty git commit — the `calevent:`/`gmailthread:` no-op precedent). A terminal row's mirror therefore always tracks the terminal transition (its `## Open loops` clear, `## Current` shows dismissed/done) no matter how long ago the row settled — the deleted 14-day window used to strand a stale-dismissed track's mirror at `Status: active` forever (track dismissal stamps `dismissed_at` but not `updated_at`, so it fell out of the window immediately). **Known limitation:** the predicate is broader than "terminal before the source was ever enabled" — a target/track created AND driven terminal between two pipeline runs never gets a mirror (no existing alias at scan time); its story still reaches memory via the situation episodes, a conservative default with no counter (revisit only if it proves lossy in practice). A read/resolve DB error fails the step (`MirrorsFailed`, logged, never fatal to the run — the calendar-step isolation contract); a clean miss is a skip.
- **`## Open loops` gains its first writer and its first reader (slice 4).** The `entitySkeletonBody` `## Open loops` section had been an empty skeleton since Phase 0. The mirror step is its FIRST writer — a target/track mirror renders its open sub-items + a ball-on/due line there while the row is non-terminal, and clears the section (heading kept, empty) when terminal. A **snoozed** target's loop bullets are each tagged ` (target snoozed)` (round-1 review, F6): snoozed targets are deliberately absent from the day plan's ACTIVE TASKS, so without that status context the day-plan model has nothing to dedupe against and could resurface deliberately-deferred work. The day-plan surface is its FIRST reader — `gatherMemoryOpenLoops` lists each active entity's non-empty `## Open loops` bullets (capped ~10 lines). The `## Links` conversion cross-link (a mirror → its originating `situation:<id>` episode) makes a converted target/track mirror `linkedEpisodes`-eligible, so its subject enters the **belief** scope (the belief pass ranges over the mirror entity) — but the entity-page **rewrite** tier explicitly **EXCLUDES** mirrors (round-1 review, F2): `RewriteEntityPages` skips any node whose id is in the mirror alias set (`db.MirrorAliasNodeIDs()`, the FIX-A helper reused). Mirrors are maintained mechanically, so a strong-tier rewrite of `## What`/`## Current` would be reverted — and its `Provenance:` marker deleted — by the very next mechanical re-scan, a permanent churn loop. Beliefs are unaffected (the mirror stays a BELIEF-scope subject; only the rewrite selection changed).
- **The day-plan and meeting-prep memory blocks are sentinel-gated prompt slots, framed model-mediated (slice 4).** Each new prompt block is a Sprintf slot that always receives a string: the day plan's 16th arg (`MEMORY OPEN LOOPS`, `day_plan.generate` v2→**v3**) and meeting prep's 11th arg (`MEMORY`, `meeting.prep` v3→**v4**) — the `briefing.daily` v6 gated-placeholder precedent. Gate off (`memory.surfaces.day_plan` / `memory.surfaces.meeting_prep` false) → the sentinel (`(no memory open loops)` / `(no memory context)`), and the prompt is byte-identical to the **v3/v4-with-sentinel** render. Note (round-1 review, F14): this is NOT "byte-identical to slice 3 apart from a version label" — the bumped default templates carry the new sentinel-bearing `MEMORY OPEN LOOPS` / `MEMORY` sections themselves, so gate-off differs from slice-3's v2/v3 templates by that whole (sentinel-filled) section, not merely the version number. Both blocks are framed model-mediated ("open loops the secretary tracks — model-derived, verify before acting" / "notes and beliefs the secretary derived from Slack/mail/calendar — model-mediated, not the attendee's own words"). The day plan keeps its direct `gatherTargets` read authoritative for schedulable targets; the memory block adds cross-universe open loops with an explicit dedupe instruction, so the model never double-schedules a target.
- **A reflection `## Current` note on a mirror subject is ephemeral (slice 4, round-1 review F5 — deferred).** The weekly reflection pass appends a dated bullet to a flapping entity's `## Current` section (MEM-11). For an ordinary entity that note persists (the rewrite tier preserves non-contradicted content), but a target/track **mirror** regenerates `## Current` **wholesale** from the operational row on every re-scan, so a reflection note landed on a mirror subject is wiped by the next mirror run — the same best-effort caveat as the interaction-ingest annotation on a still-open situation (which `IngestSituations` refreshes away). This is a known ephemeral-annotation limitation, NOT a fix in this slice: routing the note to `## Facts` (which the mirror leaves untouched) instead of `## Current` would touch MEM-11 semantics (which surface writes which section), so it is documented rather than changed. The durable preference signal for a mirror subject is the belief graph + `memory_engagement` aggregate, not a `## Current` note.
- **Preference beliefs are ordinary beliefs (slice 4).** Behind `memory.semantic.preferences` (structurally requires `memory.enabled` + `memory.semantic.enabled` + `memory.sources.actions`; no staged actions → no block), the belief pass renders this run's staged `act:` interactions + per-subject `GetEngagement` aggregates as an **OWNER ACTIONS** user-message block (`buildReviseBeliefsPrompt` gains the parameter; the system template `memory.revise_beliefs` stays byte-untouched at **v1**, so gate-off is byte-identical by construction — the OWNER SAID precedent), letting the model form preference beliefs about the owner through the SAME propose-new/confirm/weaken/shake/retire ops. No new rank, no new machinery, no new prompt id: a preference belief is born ≤ 0.6 like any other; its `owner-action` evidence NEVER confers MEM-06 fresh-owner protection (`hasFreshOwnerSupport` keys on `rankOwner` exactly — MEM-15); and it is journal-visible and dispute-visible generically. The staged refs, the `actResolver` validation (MEM-15), the mint (`newEvidenceLines`), and the 0.6 birth cap are all unchanged from slice 1 — slice 4 only makes the model SEE the act refs it may cite.
- **`RetrieveBySubject`'s short-term half is confirmed non-functional on real data (MEM-17, Slice B, found by Task 13's real-data verification, 2026-07-21).** `gatherMemoryContext` (`internal/meeting/memory_context.go`) and any other future caller pass an attendee's entity ID (`ent_...`) as `RetrieveBySubject`'s `subjects` parameter — correct for `ListBeliefsForSubjects` (`memory_nodes.subject` genuinely stores entity ids) but the SAME slice is reused verbatim for `ListShortTierEpisodesForAliases`, which filters `memory_provenance.sender_id` — a disjoint ID space (Slack user IDs / email addresses, populated by Task 3's `senderResolver`). Nothing in the current call chain resolves an entity to its Slack/email aliases before this call, so the short-tier lookup can never match on a real subject regardless of how much real short-tier content exists. Confirmed empirically: 13/13 real meeting-prep subjects in a production snapshot returned zero short-term episodes despite 374 available short-tier episodes and 98% `sender_id` coverage on provenance rows. Not a regression (the feature never shipped live — `memory.retrieve.meeting_prep_compare` stays dark) and not something Task 13 itself was scoped to fix; a future re-verification pass should resolve entity→alias (already available via `memory_aliases`/entity frontmatter) before calling `ListShortTierEpisodesForAliases`. See `docs/specs/2026-07-21-slice-b-retrieve-compare-report.md`.
- **`CompareRecall`'s `coverage_ok` metric is methodologically pessimistic relative to what a switched `memory_recall` would actually return (MEM-17, Slice B, found by final whole-branch review, 2026-07-21).** The compare's `legacyIDs` are the live handler's actual combined alias+FTS result, but `newIDs` come from `RetrieveByQuery` alone, which is documented as pure-FTS and "knows nothing about aliases" (`internal/memory/retrieve.go`) — the design's own intent is that the switched handler keeps prepending the alias-exact hit ahead of `RetrieveByQuery`'s window (design spec §2), but the CLI's offline compare never re-adds it before diffing. So `coverage_ok` reports `legacy(alias+FTS) ⊆ new(FTS-only)`, not `legacy ⊆ new(alias+FTS-reranked)` — a query whose only legacy hit was an alias match will always show `coverage_ok=false` even though the real switch would preserve it. This errs in the safe direction (can only under-report coverage, never over-report a bad switch as clean) and did not affect Task 13's actual verdict (the two person-name relevance-regression cases spot-checked in the report were independently confirmed to be non-alias FTS matches on both sides, so the metric bias doesn't explain them) — but a future re-verification pass reading the aggregate `coverage_ok` percentage should account for this before treating it as a strict pass/fail gate.
- **A fifth independent extraction watermark, and the jira builder makes NO AI call.** `memory_jira_last_extracted_ts` (migration 00030) tracks parsed `jira_issues.updated_at` (unix); the source (`memory.sources.jira`, default false) is mechanical (`jira_ingest.go`/`runJiraIngest`, Run step 3d): one updated issue → at most one episode built from the structured row (status/people/sprint/epic + a 1500-byte description snippet), alias-keyed `jiraissue:<KEY>` with update-in-place and content-equality no-op; a done+resolved issue is born (or refreshed) closed/long, a reopened one flips back. **No backfill (owner scope-B):** the first gated run initializes the watermark to the newest synced `updated_at` and builds nothing; there is deliberately NO owner/assignee filter — like the Slack source, the trail is workspace-wide. No bounded lookback: rows are permanent and every change lifts `updated_at` itself. An unparseable `updated_at` skips the row (the Gmail `internal_date` precedent); Jira's `+0100`-style offsets defeat SQLite's strftime, so all time math happens in Go (`db.ParseJiraTime`). The live workspace's Jira sync is currently dead (newest row 2026-04-24) — the source sleeps behind its gate until the sync revives. A row that arrives from a delayed sync with updated_at already at-or-below the watermark is missed until the issue's next real update — acceptable while re-enablement re-inits from max; revisit if the revived sync backfills history.
