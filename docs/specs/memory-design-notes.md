# Память секретаря — заметки с брейншторма

> Статус: черновик-конспект брейншторма (2026-07-15). Не спека — фиксация концепции и решений «в первом чтении».

## Концепция

Ортогональный к сырым данным слой — **память**, устроенная по аналогии с человеческой: вытесняемая, самоорганизующаяся, оптимизированная под чтение LLM. Не справочник источников и не поиск по 2ГБ сообщений, а дистиллят, в котором секретарь ориентируется за миллисекунды и килобайты контекста.

Потребители первой итерации: **AI-чаты Watchtower и MCP**. Triage/compose-пайплайны память в v1 не читают (INBOX-контракты не затрагиваются).

## Слои (аналогия с памятью человека)

| Слой | Аналог | Что это в WT |
|---|---|---|
| Сырой поток | «мир» | `messages` и прочие синк-таблицы; память на них только ссылается (provenance) |
| Эпизодическая | «что происходило» | сжатые эпизоды с участниками, исходом, ссылками на сырьё |
| Семантическая | «что я знаю» | живые страницы сущностей + убеждения |
| Рабочая | «о чём думаю сейчас» | корневая карта мира (килобайты, инжектится всегда); родня существующих `situations` |

### Два яруса: кратковременная и долговременная

Поверх слоёв — двухъярусная модель (аналог комплементарных систем обучения, гиппокамп/кора):

- **Кратковременная** — текущее операционное состояние: что в работе, что поможет сейчас. Подвижная, перестраивается каждый цикл, вытесняется агрессивно и без церемоний (самокорректируется пересборкой — аппарат ревизий ей не нужен). Маленькая и горячая → **инжектится целиком** в каждый чат. В значительной части — не новая база, а дистиллированная страница поверх существующего (situations, targets, day plan, running summaries) + свежие эпизоды.
- **Долговременная** — знания о компании, процессах, людях; устоявшиеся догмы. Инертная: меняется только через консолидацию, не вытесняется, а **ревизуется** — весь аппарат гистерезиса/shaken/журнала/спора относится к ней. Не инжектится — по ней навигируют. Это и есть новое, что строим.

Ключевые решения по ярусам:
- **Одно пространство узлов, ярус — атрибут узла**, не два хранилища с разными схемами: контент течёт снизу вверх (эпизод в работе → закрылся → факты в страницу → догма), и переход не должен порождать дубликаты. Стабильность — число внутри узла; чем дольше живёт и чаще подтверждался, тем больше evidence нужно на переворот (инерция догм = бесплатный гистерезис).
- **Инертность несимметрична**: догму тяжело сдвинуть шумом наблюдений, но прямое противоречие (слово владельца, явно опровергающий эпизод) мгновенно переводит её в shaken, минуя накопление. Инерция защищает от флаппинга, но не от фальсификации — иначе тихо протухшие догмы (реорг, сменился процесс) станут источником уверенной ерунды.
- **Консолидация = мост между ярусами**: перенос кратковременного в долговременное — её основная работа («сон переносит из гиппокампа в кору»).

**Консолидация = сон**: периодическая фаза демона. Свежие эпизоды → извлечение фактов → мерж/дедуп/разрешение противоречий → переписывание страниц сущностей → обновление корневой карты.

**Вытеснение ≠ удаление**: retention-score `importance × recency × access_count`; обращение к узлу его подкрепляет (чтение из чата/MCP «нагревает»). Холодный эпизод схлопывается в одну строку родительской сводки, provenance-ссылки на сырьё сохраняются — «помню, что что-то было, могу поднять переписку».

## Структура данных

Не векторная база и не таблица фактов, а **дерево связных markdown-узлов** со стабильными ID и явными ссылками. LLM не ищет — *навигирует*: корневая карта (~2КБ) → узел сущности → эпизод → при нужде сырые сообщения. Плюс FTS5 поверх узлов как «вспоминание по ключевому слову». Никакой векторной инфры; SQLite уже есть.

Масштаб: 2ГБ сырья за ~2 месяца → семантический слой при агрессивной дистилляции — единицы-десятки МБ, глубина иерархии 3–4 уровня.

## Типы узлов

1. **Эпизод** — время-ограниченная история (участники, исход, ссылки). Иммутабелен после закрытия; прошлое не переписывается, только сжимается при вытеснении.
2. **Сущность** — живая страница проекта/человека/системы/процесса. Единственный тип, который консолидация переписывает целиком. Секции: что это, текущее состояние, устойчивые факты (прозой, с provenance-маркерами), связи, open loops (ссылки на targets/situations — отдельный тип «проспективная память» в v1 не делаем). 
3. **Сводка** — время-агрегат (неделя/месяц), куда деградируют вытесненные детали.
4. **Убеждение** — вывод, не факт. Ось «наблюдал vs вывел» держим жёстко: факт живёт в странице сущности (provenance = сообщение), убеждение — отдельный узел (provenance = рассуждение над evidence). Атрибуты: confidence, evidence «за»/«против», история ревизий («раньше считал X, после эпизода Y пересмотрел»).

## Механика ревизии убеждений

Рассмотрены три чистые модели: молчаливая само-ревизия (не масштабируется доверие: невидимая смена мнения, тихое распространение ошибок, флаппинг), спрашивать владельца (секретарь-викторина, владелец часто сам не знает, блокировка ревизии), и «shaken»-буфер (честно, но без выхода вырождается в кашу неопределённости). Итоговый гибрид:

- **Само-ревизия по умолчанию + гистерезис**: противоречие сначала расшатывает (`shaken`); переворот требует накопленного перевеса evidence, заметно большего, чем нужно для создания убеждения. Флаппинг убит.
- **Журнал ревизий вместо вопросов**: заметные смены мнения — строчкой в утреннем брифинге, с причинами. Прозрачность без интеррапта; поверхность (брифинги) уже существует.
- **Ленивые вопросы в контексте**: секретарь не пингует по каждому сомнению, но когда тема всплыла в Discuss — вставляет сомнение репликой. Неотвеченный вопрос ничего не блокирует (убеждение живёт в shaken).
- **Спорящий секретарь — проактивно через inbox**: серьёзный спор («ты говорил X, я вижу обратное») — это trigger-item детектора `watchtower` → обычный конвейер triage → ситуация на дашборде с evidence-ссылками. Сомнения секретаря конкурируют за внимание на общих основаниях: мелочь — ambient, спор — actionable; капы и 👎-фидбек защищают от графомании бесплатно. Ответ владельца в карточке (feedback/Discuss) = разрешение конфликта в памяти.
- **Ранги evidence с затуханием**: сказанное владельцем в AI-чатах > наблюдённое в Slack/Gmail > выведенное консолидацией. Убеждение с owner-рангом нельзя молча перевернуть наблюдениями — только расшатать и вынести в журнал/inbox (аналог защиты `user_rule` от implicit-перезаписи). Owner-ранг течёт со временем: свежие слова — почти абсолют, полугодовые — просто сильный evidence. Настоял на своём в споре → закрепление свежим owner-рангом, но затухание продолжает работать.

Правило одной строкой: **спрашивать до ревизии — никогда; показывать после — всегда, когда смена заметная.**

## Входы памяти (по убыванию доверия)

1. Прямые слова владельца в AI-чатах (Discuss и др.) — высший ранг.
2. Наблюдения из синкованных источников (Slack, Gmail, Jira, Calendar).
3. Выводы консолидации.

## Доступ

Один интерфейс на обоих потребителей: `memory_map` (корень), `memory_open(node_id)`, `memory_recall(query)` — MCP-инструменты рядом с `list_people`/`list_targets`; чат использует их же агентно, плюс автоинжект рабочей памяти (карта + релевантные убеждения) в системный контекст.

## Адресация узлов

Вики-модель (перебраны альтернативы: контентная адресация, git-vault, иерархические пути, адресация естественным языком, натуральные ключи, безадресные эмбеддинги — большинство под требованием «ссылки переживают merge/rename» сходятся к «стабильная ручка + подвижный слой имён»):

- Канонический ID стабильный, с типовым префиксом: `ent_*`, `ep_*`, `bel_*`, `sum_*` (тип виден в ссылке до разыменования).
- Slug'и — алиасы (many-to-one таблица); rename добавляет алиас, старые живут как редиректы.
- В тексте ссылки вида `[[ent_7f3a|биллинг-переезд]]` — читаемо для LLM без разыменования, стабильно для резолвера; протухшую подпись освежает консолидация при переписывании страницы.
- Merge = tombstone с редиректом, O(1); ссылки переписываются лениво консолидацией; цепочки редиректов схлопываются при переписывании (path compression).
- Split = disambiguation-узел; входящие ссылки разруливает консолидация по контексту, лениво.
- `memory_open` принимает ID/алиас/надгробие, следует редиректам, возвращает канонический узел с текущим ID (самоизлечение внешних потребителей).
- **Натуральные ключи как алиасы**: внешние ID (`C0123`, `PROJX`, email) — строки в той же таблице алиасов → кросс-источниковая склейка идентичностей = два алиаса на один узел, отдельный механизм не нужен.
- Опция: контент-хеш как ID иммутабельных эпизодов (дедуп бесплатно) — отложено, не обязательно.

## Журнал изменений и рефлексия

- **Журнал — append-only лог всех мутаций** всех узлов (не только убеждений): `(ts, node_id, операция: create/update/merge/tombstone/promote-tier/evict/revise, дифф/сводка, причина: прогон консолидации | реплика чата | правка владельца, evidence)`. Причина обязательна — каждая мутация отвечает «почему». Это аудит для доверия и сырьё для отладки.
- **Рефлексия — консолидация второго порядка**: периодическая фаза читает журнал за окно. Ловит: флаппинг (→ поднять гистерезис узла — самонастройка), нестабильные зоны («память об X переписана 5 раз» — сигнал в брифинг), перегрев/омертвение областей, аномалии прогонов. Выходы: строчки брифинга, мета-наблюдения как обычные узлы-убеждения, подкрутка параметров. Метакогниция поверх собственного лога.

## Хранилище: файлы + git первично, SQLite — индекс

Дизайн узлов конвергировал с Obsidian-vault (markdown + wiki-ссылки + алиасы в frontmatter) — используем это:

- **Первичное хранилище — папка markdown-файлов под git**: текст узлов, frontmatter (ID, тип, ярус, алиасы), история. Git-коммит консолидации = транзакция со structured message «почему» → **журнал изменений = git log бесплатно**, рефлексия читает диффы.
- **SQLite — пересобираемый индекс**: FTS, метаданные для механики (confidence, retention, access_count), счётчики. Правило: текст и история — в файлах, числовое и производное — в индексе; индекс можно грохнуть и пересобрать без потерь.
- **Правка владельца руками** (в Obsidian или любом редакторе) — вход с высшим рангом: демон видит дифф через git и принимает как «босс сказал». Канал обучения без нашего UI.
- **Obsidian — совместимость, не зависимость**: WT не требует его и не зовёт его API; просто vault открывается в Obsidian красиво (graph view, backlinks, mobile — бесплатно).
- Известные издержки: вотчер/пересборка индекса как подсистема; подкрепление при чтении видно только из чата/MCP (не из Obsidian); осторожность с одновременной записью демона и Obsidian Sync.

**Принцип самодостаточности: внешних инструментов на машине не предполагаем.** Всё нужное встроено, внешнее только улучшает опыт:
- git → **go-git** (чистый Go, без системного бинаря; тот же приём, что `modernc.org/sqlite`). Vault — обычный совместимый git-репозиторий; системный git/remote — опция power-user'а. Ручные правки детектятся диффом рабочего дерева против HEAD на прогоне консолидации; демон сам делает checkpoint-коммит «правка владельца» (owner-ранг) — пользователю git знать не нужно.
- Вотчер → в v1 без него: сверка vault ↔ индекс в начале каждого прогона (mtime/хеши против HEAD). fsnotify (чистый Go) — если понадобится живее.
- FTS → FTS5 внутри уже используемого `modernc.org/sqlite`.
- План Б (если go-git не взлетит): journal.jsonl + снапшоты vault — худший вариант (нет диффов и git-совместимости), только запасной выход.

## Расписание и экономика консолидации

**«Ночь» — метафора, не механика.** Работа консолидации — API-вызовы, не локальный компьют; машине достаточно быть включённой. Вместо ночного крона — **микро-сны**:

- Фаза демона срабатывает **по долгу, не по часам**: долг = непереваренный вход с последнего прогона (свой watermark). Долг > порога → откусить капнутый чанк (аналог `MaxTriageMessages`), переварить, закоммитить, отдать управление.
- **Чанк = транзакция = git-коммит** с продвинутым watermark. Обрыв (sleep, выключение) теряет максимум один недокоммиченный чанк — переварится заново. Требование — идемпотентность и резюмируемость, а не время суток.
- Машина была выключена → при включении большой долг догоняется серией чанков (как sync догоняет Slack). Отставание безвредно: кратковременный ярус живёт на situations/targets (обновляются дневными пайплайнами), долговременный инертен по дизайну.
- Уступка «ночности»: тяжёлое редкое (полные переписывания, рефлексия) предпочтительно при «на питании + idle» (pmset/IOKit) — оптимизация против конкуренции за rate limit, не корректность.

**Экономика** (темп владельца: 2ГБ/2мес ≈ 33МБ/день сырой базы ≈ 3–6М токенов/день текста):

1. **Сильная модель никогда не читает сырьё.** Воронка: сырьё → дешёвый тир (haiku-класс) выжимает эпизоды (компрессия 10–20:1) → сильный тир (sonnet-класс) читает только дистиллят для фактов/убеждений/страниц → рефлексия читает только журнал.
2. **Не платить дважды**: существующие пайплайны (triage, дайджесты, running summaries, situations) уже прогоняют сырьё через дешёвый тир — консолидация питается их выхлопом как заготовками эпизодов, в сырьё ныряет точечно. Первый (дорогой) проход уже оплачен текущим бюджетом WT; надбавка = сильный тир поверх ~100–300К токенов дистиллята в день → **порядка десятков центов — доллара в день**.
3. **Дельты по умолчанию, переписывание по расписанию**: чанк дописывает дельты к узлам; полное переписывание страницы — при накоплении N дельт или staggered (сущность — раз в неделю, размазанно); корневая карта перерисовывается из страниц (дёшево). Капы на прогон + учёт в `pipeline_runs`.

## Границы против существующего (не мержить!)

- **`inbox_learned_rules`** — «как реагировать»; память — «что я знаю». Правила могут ссылаться на узлы, живут отдельно.
- **Channel memory (running summary)** — волатильное «что происходит в канале» для дайджестов; страница сущности — стабильное «что это такое». Разные жизненные циклы.
- **`people_cards`** — остаются своей базой; узлы-сущности типа «человек» ссылаются на people_card, не дублируют.
- **`situations`/`targets`** — рабочая память и open loops; узлы ссылаются, не поглощают.

## Открытые вопросы

- Порог «заметности» смены мнения для журнала брифинга (confidence × важность сущности?).
- Нужен ли пятый тип узла «проспективная память» после обкатки open loops на targets.
- Точная стыковка консолидации с выхлопом существующих пайплайнов (какие из digests/situations/summaries годятся как заготовки эпизодов, чего не хватает).
- Механика вотчера/пересборки SQLite-индекса из vault; поведение при конфликте демон ↔ ручная правка.

Решено в ходе брейншторма: адресация (вики-модель, см. секцию), кросс-источниковая склейка (натуральные ключи как алиасы), хранилище (vault+git первично, SQLite — индекс), журнал+рефлексия (см. секцию).

## MVP-срез (первая итерация)

1. Таблицы узлов + FTS5, типы: эпизод / сущность / сводка / убеждение.
2. Фаза консолидации в демоне (ночная): эпизоды из чатов → факты/убеждения → страницы → карта.
3. MCP: `memory_map` / `memory_open` / `memory_recall`.
4. Инжект рабочей памяти + агентный доступ в Discuss-чате; слова владельца из чата пишутся в память owner-рангом.
5. Журнал ревизий в брифинге; спор-ситуации через детектор `watchtower`.
