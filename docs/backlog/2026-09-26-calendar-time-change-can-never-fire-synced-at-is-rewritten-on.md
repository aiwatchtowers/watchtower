**Where:** internal/inbox/calendar_detector.go:94,105 (plus internal/db/calendar.go:101,150, internal/calendar/client.go:277)
**Confidence:** high

The detector treats `updated_at > synced_at` as "modified after first sync". But the upsert sets `synced_at=excluded.synced_at` to the current time on every sync, while `updated_at` is Google's `item.Updated`, which always comes before the sync that fetched it. So `updated_at > synced_at` is false on every real row, and a rescheduled meeting never produces an item. For the same reason, `e.syncedAt > sinceISO` is true for every event on every cycle, so the "newly arrived" test for `calendar_invite` is really just "currently needsAction". The only thing stopping repeats is the (event, updated_at) dedup. `TestCalendarDetector_TimeChange` passes only because its fixture freezes `synced_at` at a first-sync time that production never keeps. Fix direction: persist a first-seen timestamp (or compare against the previous `start_time`/`end_time`), and reseed the tests through `UpsertCalendarEvents` twice.

Resolution: migration `00079` adds `calendar_events.time_changed_at`, stamped by the shared upsert clause (`calendarEventUpdateSet`, both the single and batch upserts) with the pass's `synced_at` only when `start_time` or `end_time` actually moved; a first insert and a detail-only re-sync leave it alone. `DetectCalendar` fires `calendar_time_change` when that stamp falls inside the window and dedups on it, so a later detail edit is not a second item. `TestCalendarDetector_TimeChange` now seeds through `UpsertCalendarEvent` twice with the start moved (the old fixture froze `synced_at` at a first-sync time production never keeps); its assertion is unchanged. Also pinned by `TestCalendarDetector_ResyncWithoutTimeChange`, `TestCalendarDetector_TimeChangeBeforeWindowIgnored` and `internal/db`'s `TestUpsertCalendarEvent_TimeChangedAt`. **Auto-resolve (owner decision 2026-09-29, an approved INBOX-02 amendment):** before this change, `autoResolveCalendar` resolved any time-change item whose owner RSVP was already answered, in the same Run that minted it. Now a `calendar_time_change` item resolves only on an RSVP given after the reschedule, or once the event has ended. The same migration adds `calendar_events.rsvp_changed`, a per-attendee JSON of the pass stamps at which the sync saw each response change (`mergeRSVPChanges`). The item resolves when the owner's RSVP is an answer that changed at or after its reschedule stamp.
Provider behaviour: Watchtower never rewrites an RSVP itself. Google's Calendar API does not document whether a time change keeps or resets guests' `responseStatus`. RFC 6638 lets a CalDAV organizer's server reset attendees' PARTSTAT to NEEDS-ACTION on a change that needs re-confirmation. The rule works either way. If the RSVP is kept, the item stays pending until a fresh answer or the event's end. If it is reset, the invite case (checked first) surfaces the reschedule as a `calendar_invite`, which resolves on the owner's answer.
