## 1. Executive Summary

**Overall rating: Strong MVP with room for growth**

Watchtower demonstrates a mature architecture, good code quality, and sound engineering decisions. The core product (Slack sync → AI analysis → CLI/Desktop) works reliably. Main risks: credential storage security, inconsistent error handling, and a significant gap between the strategic plan and the current implementation (~35-40% of the roadmap).

| Area | Rating | Key risk |
|---------|--------|---------------|
| Architecture | 8/10 | God-package `db/`, circular import risk |
| Go Backend | B+ | Inconsistent `sql.ErrNoRows` handling |
| Swift Desktop | Excellent | Error suppression in catch {} |
| Security | MEDIUM | OAuth creds in .env, plaintext tokens |
| Documentation | 70% | Chains/Guide undocumented |
| Strategy | 35-40% | Enterprise/multi-LLM/Teams not started |

## 2. Architecture

### 2.1 What's done well

- **Clean CLI / Desktop separation** via a shared SQLite DB (single source of truth)
- **WAL mode** properly configured for concurrent reads between CLI and Desktop
- **Pipeline architecture** is consistent: digest, tracks, chains, guide — all follow a single pattern (Pipeline struct + Run() + Generator interface)
- **Subprocess-based AI** — the Claude CLI is invoked as a subprocess, which simplifies auth and lets both components work independently
- **Worker pool** with priorities and context cancellation — a sound concurrency model

### 2.2 Findings

#### CRITICAL: Circular import risk

`chains/pipeline.go` imports `digest`, and `digest/pipeline.go` uses a `ChainLinker` interface for the callback. If chains ever needs types from digest directly, the cycle will break the build.

**Recommendation:** Create `internal/types/pipeline.go` with shared interfaces (Generator, ChainLinker, ProgressFunc).

#### HIGH: God-package `internal/db/`

- 50+ functions per file, 27 struct models, all in a single package
- Files: db.go (800+ lines of migrations), models.go, digests.go, tracks.go, channels.go, and others

**Recommendation:** Split into subpackages: `db/slack/` (users, channels, messages), `db/analysis/` (digests, tracks, chains), `db/people/` (analyses, guides). Or introduce a Store interface pattern (as in prompts.Store).

#### HIGH: Daemon throttle state is not persisted

`lastPeople` and `lastTracks` in daemon.go are in-memory variables. On daemon restart, the timers reset, which can trigger a re-run of the daily pipelines.

**Recommendation:** Persist the timestamps in a checkpoint table or a JSON file.

#### MEDIUM: Chains prompt is hardcoded

Unlike digest/tracks/guide, the chains pipeline does not use `prompts.Store`. The user cannot tune the chains prompt via `watchtower prompts edit`.

**Recommendation:** Add `chains.linking` and `chains.team_summary` to `prompts.Defaults`.

#### MEDIUM: Inconsistent error handling across pipelines

- Digest pipeline: logs the error, continues processing the remaining channels
- Tracks pipeline: stops on the first error
- Guide pipeline: stops on the first error

**Recommendation:** Unify the behavior. Add a `ContinueOnError` config option or an `OnError` callback.

#### MEDIUM: Schema migration complexity

800+ lines of sequential migrations in db.go (v1 → v28). No rollback, no tests for migration idempotency.

**Recommendation:** Move migrations into separate files. Add forward-migration tests.

## 3. Go Backend

### 3.1 What's done well

- **Error wrapping**: 501 occurrences of `fmt.Errorf("...: %w", err)` — excellent traceability
- **Goroutine management**: all 9 goroutines in production code correctly manage their lifecycle (defer wg.Done, context cancellation, channel closing)
- **SQL security**: all user-derived values go through parameterized queries (`?` placeholders)
- **Transaction handling**: the `defer tx.Rollback()` + explicit Commit() pattern is correct
- **Rate limiting**: token bucket + exponential backoff + jitter for the Slack API
- **Subprocess management**: Claude CLI with graceful shutdown (SIGINT → 5s → SIGKILL), stderr capped at 64KB

### 3.2 Findings

#### MAJOR: Inconsistent `sql.ErrNoRows` checks

Two patterns are used in parallel:
- `errors.Is(err, sql.ErrNoRows)` — correct (in workspace.go, profile.go)
- `err == sql.ErrNoRows` — unsafe under error wrapping (in 13+ files)

**Affected files:**
- `internal/db/tracks.go:165`
- `internal/db/channels.go:124`
- `internal/db/user_analyses.go:130, 1058`
- `internal/db/prompts.go:20, 62, 90, 144`
- `internal/db/sync_state.go:20`
- `internal/db/digests.go:117`

**Recommendation:** Globally replace with `errors.Is()` across all files.

#### MINOR: Mix of log.Logger and slog.Logger

Most of the code uses `log.Logger`, but `prompts/store.go` uses `slog.Logger`. Not critical, but inconsistent.

#### MINOR: Dynamic SQL in two places

- `messages.go:97` — `msgColumns()` + `fromTable` (safe, hardcoded values)
- `db.go:785` — `fmt.Sprintf` for column names in a migration (safe, hardcoded slice)

There's no real vulnerability, but the pattern is atypical for idiomatic Go.

## 4. Swift Desktop

### 4.1 What's done well

- **MVVM architecture**: clean separation of Models → Queries → ViewModels (@MainActor, @Observable) → Views
- **GRDB integration**: DatabasePool with WAL, Sendable conformance, thread-safe queries
- **Memory management**: correct use of `[weak self]` in Task closures, cancellation patterns
- **Subprocess security**: JSONSerialization for MCP config (prevents injection)
- **Onboarding**: state machine with persistence via UserDefaults, good UX

### 4.2 Findings

#### CRITICAL: Widespread error suppression

Numerous `catch {}` blocks without logging:

- `ChatHistoryViewModel.swift`: lines 46, 60, 73, 83, 94
- `ChatViewModel.swift`: line 202 — comment "silently ignore"
- `DashboardViewModel.swift`: line 45

**Impact:** Makes debugging extremely difficult. Errors disappear without a trace.

**Recommendation:** Replace all `catch {}` with `catch { NSLog("[Component] error: \(error)") }`.

#### MAJOR: Shell subprocess at launch

`Constants.swift:114-150` — `resolvedEnvironment()` spawns a shell subprocess to obtain PATH. There is a 5-second timeout, but it runs synchronously. If the shell hangs, the app will freeze.

**Recommendation:** Move it to a background thread with lazy initialization.

#### MAJOR: Regex compiled on every frame

`MessageTextView.swift:27` — `NSRegularExpression` is compiled on every call to the body view.

**Recommendation:** Move it into a `static let` property.

#### MINOR: Static shared AppState for notifications

`WatchtowerApp.swift:11` — `NotificationDelegate.sharedAppState` is set in `.onAppear`. If a notification arrives before `.onAppear`, the reference will be nil.

#### MINOR: Missing VoiceOver labels

Icon-only buttons (TracksListView, DigestListView, etc.) lack accessibility labels.

#### MINOR: No timeout on the Claude CLI subprocess

Unlike the DB migration (30-second timeout), the Claude stream has no timeout. It can hang indefinitely.

## 5. Security

### 5.1 What's done well

- **SQL injection**: all queries are parameterized, FTS5 is sanitized via `sanitizeFTS5Query()`
- **Command injection**: `exec.CommandContext` with an argument array (not a shell string)
- **File permissions**: config 0o600, logs 0o600, PID 0o600, DB directory 0o700
- **Path traversal**: workspace name is validated with the regex `^[a-zA-Z0-9][a-zA-Z0-9_.-]*$`
- **OAuth CSRF**: the state parameter is correctly validated
- **TLS**: the OAuth callback uses TLS 1.2+, Slack API over HTTPS
- **Process security**: PID reuse detection, stale PID cleanup, exclusive file locking

### 5.2 Findings

#### CRITICAL: OAuth credentials in the repository

The `.env` file contains plaintext credentials:
- `WATCHTOWER_OAUTH_CLIENT_SECRET=f50df2...`
- `CODESIGN_IDENTITY="Developer ID Application: ..."`

`.gitignore` excludes `.env*`, but if the repo is ever published, the credentials would be compromised.

**Recommendation:** Immediately rotate the OAuth client secret in the Slack App settings. Use environment variables exclusively in CI/CD.

#### HIGH: Slack token in plaintext config

`~/.config/watchtower/config.yaml` stores `xoxp-*` / `xoxb-*` tokens without encryption. The file has 0o600 permissions (good), but a compromised home directory means full access to the Slack workspace.

**Recommendation:** Adopt the macOS Keychain for token storage. Keep config.yaml for non-sensitive settings only.

#### HIGH: SQLite DB is not encrypted

The database contains all Slack workspace messages in plaintext. Physical access to the device means a full leak of corporate correspondence.

**Recommendation:** Integrate SQLCipher or the SQLite encryption extension. Derive the key from the Keychain.

#### HIGH: Self-signed TLS cert for OAuth

The OAuth callback server uses a self-signed certificate. The user must manually trust the certificate (`watchtower auth trust-cert`). Potential MITM if the SSL warning is ignored.

**Recommendation:** Use ASWebAuthenticationSession on macOS for a native OAuth flow.

#### MEDIUM: Sensitive data in logs

Daemon logs (`~/.local/share/watchtower/{workspace}/watchtower.log`) can contain Slack message content on API errors. Permissions are 0o600 (good), but the content is not filtered.

**Recommendation:** Add structured logging with redaction for message content.

#### LOW: Lock file permissions

`cmd/sync.go:209` — the lock file is created with 0o644 (world-readable). Should be 0o600.

#### LOW: Parent directories at 0o755

`daemon/pidfile.go:22` — `os.MkdirAll(..., 0o755)`. Other system users can read the directory listing.

## 6. Documentation and UX

### 6.1 What's done well

- **Technical documentation** is excellent: llm-pipelines.md, onboarding-flow.md, plan.md, desktop-app.md
- **Config schema** is fully documented in usage.md
- **Onboarding flow** is described in detail with a state machine and edge cases
- **CLI flag conventions** are consistent: `--workspace`, `--config`, `--verbose`

### 6.2 Findings

#### CRITICAL: README is outdated

- Line 44: `watchtower actions` → should be `watchtower tracks`
- Line 196: "Actions" tab → "Tracks"

#### HIGH: Chains feature is undocumented

Implemented: `internal/chains/`, `cmd/chains.go`, ChainDetailView, ChainsListView. Documentation contains only a technical mention in llm-pipelines.md. Missing:
- What is a "chain"?
- How are chains created?
- CLI workflow (`watchtower chains generate/archive`)
- User guide

#### HIGH: Guide feature is undocumented

Implemented: `internal/guide/`, `cmd/guide.go`, GuideViewModel, GuideView/. The `docs/guide-analysis.md` documentation is nearly empty. No explanation of what it is, why it exists, or how to use it.

#### HIGH: No user guide for the Desktop app

`docs/desktop-app.md` is an excellent technical spec, but not a user guide. Missing:
- Quick start for desktop
- Description of navigation and tabs
- Feature tutorials

#### MEDIUM: "Decisions" vs "Chains" — unclear terminology

`watchtower decisions` and `watchtower chains` are two different CLI commands. The relationship between them is never explained. Users don't understand when to use which.

#### MEDIUM: Undocumented config keys

`digest.language`, `digest.min_messages` — used in the code, but not described in the config reference in usage.md.

#### MEDIUM: No troubleshooting.md

Common issues (database locked, claude not found, daemon issues) are scattered across different docs. There is no single guide.

### 7.3 Strategic gap

The product is positioned as a **"multi-source organizational intelligence platform"**, but is in fact a **"single-workspace Slack analytics tool"**.

**Estimated lag:** 8-12 weeks behind the roadmap. The enterprise server — a key monetization component — has not been started.

**A strategic decision is required:**
- **Option A**: Full strategy execution → 3-4 engineers for 6 months, raise capital
- **Option B**: Focus on freemium/pro for small teams ($10/user/mo) → current team, smaller TAM
- **Recommendation**: Option A with incremental validation. Start with an LLM abstraction layer + enterprise server MVP.
