# Google Multi-Account (sub-project 1 of 3 of the multi-account initiative, 2026-07-30)

- `google_accounts` table (migration 00043) replaces the old single-account model: one row per connected Google account (`email`, `label`, `client_id`, `calendar_enabled`/`gmail_enabled`, `status`/`error`, its own `gmail_last_internal_date` Gmail-sync watermark, its own `memory_gmail_last_extracted_ts` memory-extraction watermark). `calendar_auth_state`/`gmail_auth_state` singleton tables and the `gmail.account_email` config key are retired; `gmail_messages` gains `account_id` (PK `(account_id, id)`), `calendar_calendars` gains a nullable `account_id` (NULL for CalDAV/ICS rows), `calendar_events` gains `ical_uid` (dedup enabler, unused in v1). A pre-multi-account install migrates in place: the goose migration seeds account #1 from existing data; `ensureLegacyGoogleAccount` (`cmd/google_legacy.go`) finishes the job in Go (renames `google_token.json`/`gmail_token.json` → `google_token_1.json`, fills `email`) and is idempotent — called from daemon sync wiring, `google login`/`gmail login`/`calendar login` (the legacy aliases, now thin wrappers over account #1), and `google add` (seed-only; `add` still always creates a NEW account after).
- Per-account token (`google_token_<id>.json`) and optional custom-OAuth-client credential (`google_credentials_<id>.json`, non-secret `client_id` mirrored to the DB row for display, secret file-only) stores. `wireGoogleSyncers` (`cmd/sync.go`) iterates `ListGoogleAccounts` and builds one `calendar.Syncer`/`gmail.Syncer` per enabled account (gated by the global `cfg.Calendar.Enabled`/`cfg.Gmail.Enabled` daemon-phase switches, same as every other sync phase) — one account's auth failure records only *its* `status`/`error` and never blocks the others (the `wireImapSyncers`/`wireCalDAVSyncers` fan-out pattern); a missing or unreadable token file flips only a currently-`ok` account to `error`, so it neither stays silently green nor churns an already-flagged row. Calendar stale-cleanup is scoped per `account_id` so account A can never delete account B's calendars.
- CLI: `watchtower google add [--calendar --gmail] [--label L] [--client-id X --client-secret-stdin] [--no-open] [--app-return]`, `google login --account <id>` (re-consent), `google accounts` (list), `google remove <id>` (transactional: row delete CASCADEs `gmail_messages`, best-effort post-commit file cleanup).
- Inbox: the Gmail detector's `channel_id` is `gmail:<accountID>:<threadID>` (the `imap:<acct>:...` precedent, not a bare thread id); own-message suppression compares a message's sender against its *source account's* email. See `docs/inventory/inbox-pulse.md` INBOX-09 for the watermark-scoping note.
- Memory: Gmail episode extraction iterates every connected account against its own `memory_gmail_last_extracted_ts` (moved off the `workspace` row); `mail:<message_id>` provenance format is unchanged, and both the `mail:` resolver and the `gmailthread:<thread_id>` idempotency alias are account-unscoped by design (documented v1 limitation) — see `docs/inventory/memory.md`.
- Desktop: Settings → Google shows an account list (row = email/label + Calendar/Gmail badges + status + Remove) replacing the old single "Connect Google" block; "Add Google Account" sheet (label, Calendar/Gmail toggles, collapsed custom-OAuth-client advanced section) is the shared entry point from both the Gmail and Calendar account cards.
- Design/plan: `docs/superpowers/specs/2026-07-30-google-multi-account-design.md`, `docs/superpowers/plans/2026-07-30-google-multi-account.md`. Non-goals (v1): cross-account event dedup, concurrent OAuth flows, per-account sync schedules, multi-Slack/multi-Jira (sub-projects 2–3, specced separately, reusing these conventions).
