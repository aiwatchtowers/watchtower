# Google Multi-Account (sub-project 1 of 3 of the multi-account initiative, 2026-07-30)

- `google_accounts` table (migration 00043) replaces the old single-account model: one row per connected Google account (`email`, `label`, `client_id`, `calendar_enabled`/`gmail_enabled`, `status`/`error`, its own `gmail_last_internal_date` Gmail-sync watermark, its own `memory_gmail_last_extracted_ts` memory-extraction watermark). `calendar_auth_state`/`gmail_auth_state` singleton tables and the `gmail.account_email` config key are retired; `gmail_messages` gains `account_id` (PK `(account_id, id)`), `calendar_calendars` gains a nullable `account_id` (NULL for CalDAV/ICS rows), `calendar_events` gains `ical_uid` (dedup enabler, unused in v1). A pre-multi-account install migrates in place: the goose migration seeds account #1 from existing data; `ensureLegacyGoogleAccount` (`cmd/google_legacy.go`) finishes the job in Go (renames `google_token.json`/`gmail_token.json` → `google_token_1.json`, fills `email`) and is idempotent — called from daemon sync wiring, `google login`/`gmail login`/`calendar login` (the legacy aliases, now thin wrappers over account #1), and `google add` (seed-only; `add` still always creates a NEW account after).
- Per-account token (`google_token_<id>.json`) and optional custom-OAuth-client credential (`google_credentials_<id>.json`, non-secret `client_id` mirrored to the DB row for display, secret file-only) stores. `wireGoogleSyncers` (`cmd/sync.go`) iterates `ListGoogleAccounts` and builds one `calendar.Syncer`/`gmail.Syncer` per enabled account (gated by the global `cfg.Calendar.Enabled`/`cfg.Gmail.Enabled` daemon-phase switches, same as every other sync phase; both default off, and `google add`/`google login` turn on the switch for every service the consent granted — `recordGoogleConnection`, #740; a re-consent counts too, so reconnecting turns back on a switch the owner had turned off (owner decision 2026-10-14), a service left ungranted keeps its switch as it was, and a failed switch write is a warning, not a failed connect — so every connect surface syncs; the Desktop `ConfigService.save()` writes a switch only when its own instance changed it, so a stale Settings window cannot turn it back off) — one account's auth failure records only *its* `status`/`error` and never blocks the others (the `wireImapSyncers`/`wireCalDAVSyncers` fan-out pattern); a missing or unreadable token file flips only a currently-`ok` account to `error`, so it neither stays silently green nor churns an already-flagged row. Calendar stale-cleanup is scoped per `account_id` so account A can never delete account B's calendars. `FetchCalendars` reads the whole calendar list (all pages, `showHidden=true`); a calendar hidden in Google is listed but starts unselected, and since `is_selected` is written only on first sight the owner's Watchtower selection always wins.
- CLI: `watchtower google add [--calendar --gmail] [--label L] [--client-id X --client-secret-stdin] [--no-open] [--app-return]`, `google login --account <id>` (re-consent), `google accounts` (list), `google remove <id>` (transactional: row delete CASCADEs `gmail_messages`, best-effort post-commit file cleanup).
- Inbox: the Gmail detector's `channel_id` is `gmail:<accountID>:<threadID>` (the `imap:<acct>:...` precedent, not a bare thread id); own-message suppression compares a message's sender against its *source account's* email. See `docs/inventory/inbox-pulse.md` INBOX-09 for the watermark-scoping note.
- Memory: Gmail episode extraction iterates every connected account against its own `memory_gmail_last_extracted_ts` (moved off the `workspace` row); `mail:<message_id>` provenance format is unchanged, and both the `mail:` resolver and the `gmailthread:<thread_id>` idempotency alias are account-unscoped by design (documented v1 limitation) — see `docs/inventory/memory.md`.
- Desktop: Settings → Google shows an account list (row = email/label + Calendar/Gmail badges + status + Remove) replacing the old single "Connect Google" block; "Add Google Account" sheet (Calendar/Gmail toggles, collapsed custom-OAuth-client advanced section) is the shared entry point from both the Gmail and Calendar account cards.
- Account labels (2026-10-14, #742): the connect never asks for a label — the Desktop sheets (Slack, Jira, Google, Outlook/IMAP, CalDAV/ICS, onboarding included) have no field and pass no `--label` (the CLI flag stays for scripts). `internal/db/account_labels.go` is the one rule: `SlackAccountLabel` (team name, else team domain), `JiraAccountLabel` (host minus `.atlassian.net`, else site name), `MailAccountLabel` (domain lowercased, IDN in Unicode; the whole address on a public mail domain; an IMAP login without `@` → the server host), `CalDAVAccountLabel` (host, `www.` dropped), `ICSAccountLabel` (the feed's `X-WR-CALNAME`, else its host — passed in as `CalendarAccount.LabelHint`, the feed URL is never stored); `UniqueAccountLabel` adds " 2", " 3" on a case-insensitive clash within one table, removed Slack/Jira rows not counted. It runs in the write that resolves the identity — `Update{Slack,Jira,Google}AccountConnection`, `Create{Email,Calendar}Account` — best effort right after the identity is saved (its own transaction; a failure is logged and never undoes the connect or a sync), and only while `label = ''` (an owner's or earlier automatic label is never replaced, so a later team rename keeps the old label). `FillEmptyAccountLabels` backfills older accounts oldest first at daemon start, one transaction per account (old ICS feeds stay empty → the Swift `displayName` fallback). Rename: `watchtower <slack|jira|google|imap|outlook|caldav> rename <id> <name>` (`db.RenameAccount`; an empty name and a removed Slack/Jira account are refused); the Settings rows' **Rename…** alert runs it through `AccountRename` (WatchtowerCore, args `-- <id> <name>` so a leading "-" is not a flag), no daemon restart (the CalDAV/ICS syncer re-reads its label each cycle, so `calendar_calendars.name` follows a rename on the next sync).
- Design/plan: `docs/superpowers/specs/2026-07-30-google-multi-account-design.md`, `docs/superpowers/plans/2026-07-30-google-multi-account.md`. Non-goals (v1): cross-account event dedup, concurrent OAuth flows, per-account sync schedules, multi-Slack/multi-Jira (sub-projects 2–3, specced separately, reusing these conventions).
- Source deletions (2026-10-17, board #640): `google_accounts.deletions_checked_at` is the per-account daily stamp for the Gmail deleted-mail check; see [source-deletions.md](source-deletions.md).
- Own Google project (2026-11-18, #1887 Task 18): `google add --client-id X --client-secret-stdin` signs in first, then stores the client as a `personal` company bundle (`company.SavePersonal`: named after the signed-in Gmail address, else "My Google project"; the same client reuses its bundle, a name held by a company or another project gets " (2)", " (3)"…) and ties the account to it like `--company` (the row of the same address is re-tied; a cancelled sign-in stores nothing). An own-project account is a `personal` bundle's or an untied legacy `google_credentials_<id>.json` (`company.IsOwnProject`). `AllowOwnGoogleProject = false` refuses the add before the secret is read (and `--company` of a personal slug), refuses its re-login and `gmail|calendar sync`, and stops it in the daemon (not wired at start; a wired one skipped per cycle through `Daemon.SetAccountSyncAllowed`, backfill waiting, purge lease held) with row and data kept; an account stopped at daemon start stays stopped (lease held) until the next start wires it, even once allowed. `company.OwnProjectWeeklyRelogin` holds spike S2's answer (false until the day-8 check).
- Use my own Google project page (2026-11-19, #1887 Task 26, company screens spec §5): the Google detail's page (`OwnGoogleProjectModel` on `AppState.ownGoogleProject`, `OwnGoogleProjectPage`) replaces Add Google Account's "Advanced: custom OAuth client". It runs `google add --app-return --calendar --gmail --client-id X --client-secret-stdin --json` (secret on stdin only); `--json` (only with `--client-id`) ends with one `company check`-shaped line: `ok` (+ `account_id`, `email`, `slug`), or a classified sign-in failure (`rejected` with the vendor's code, `network`, `cancelled`, a refused re-tie as `rejected`/`grant_too_narrow`|`purge_running`) at exit 0, with nothing stored. `google accounts --json` rows carry `own_project` (`company.IsOwnProject`), which the Desktop uses for the "Your own Google project" group (an untied legacy own-credentials account no longer lands under the shared app) and the §5.4 lock: the group's rows read "Stopped by your organization — data kept" with no Re-login, then the lock card; the page closes when the policy turns it off. A shared-app Gmail row that must sign in again offers **Use my own Google project** (or **Paste a company code** under the lock) instead of a Re-login the shared app refuses (D11). The weekly re-login frame stays off while `OwnGoogleProjectModel.weeklyReloginShipped` / `company.OwnProjectWeeklyRelogin` are false.
