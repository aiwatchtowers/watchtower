# "Not clear?" — a chat about one question or step of an ask (2026-11-24 #2355, per item 2026-11-27 #2412)

Specs: `docs/superpowers/specs/2026-11-24-ask-explain-chat-design.md` (the chat), `docs/superpowers/specs/2026-11-27-ask-explain-per-item-design.md` (an entry and a chat per item, the item card; it overrides 2026-11-24 D1). Plans: `docs/superpowers/plans/2026-11-24-ask-explain-chat.md`, `docs/superpowers/plans/2026-11-27-ask-explain-per-item.md`. Mockups: `docs/design/mockups/ask-explain-per-item/` (DesignShotCatalog `ask-explain-*`, `AskExplainItemsMockShotFixtures`; the 2026-11-24 set in `docs/design/mockups/ask-explain-chat/` stays as that spec's record); the same states from the built views are `ask-explain-built-*` (`DesignShotFixtures+AskExplain.swift`, `DesignShotsTests/testAskExplainBuiltShotsRender`). User guide: `docs/guide/features/workbench/asks.md` ("Ask the assistant what a question means").

## Summary

On a question or check ask (open or closed; never a review ask, never without a CLI: `AskExplainPresentation.showsEntry`) each question ends with a quiet **Not clear?** and each check step has a small **?** on its row. Pressing one turns the ask drawer's body and answer bar into an embedded chat about that item: a compact card of the item pinned under the strip, and a first, hidden turn that explains it in plain words. **‹ Back to question** / **‹ Back to check** (or Esc unless a focused composer holds text) returns to the question view exactly as it was. Mac only.

## Chat identity

- `chat_conversations.context_type = 'owner_ask_explain'` (`db.AskExplainContextType`, `AskExplainKey.contextType`), `context_id = "<workbench id>:<ask id>:<item>"` (`AskExplainKey.contextID(workbenchID:askID:item:)`), `<item>` = `q<N>` (a question) or `s<N>` (a check step), N the item's 1-based position in the payload (`AskExplainItem`, `.token`), never the agent's free-text `id`; title "Ask #<id> · Question N" / "Ask #<id> · Step N" (`AskExplainKey.title`). One conversation per item, found or created by `AskExplainSurface.conversationID(ask:item:…)` through Go's `chat.new` with `reuse: true` (two windows or two clicks get one conversation). Go (`db.AskExplainWorkbenchID`) accepts the 3-part id and the legacy 2-part `<workbench>:<ask>`, every number canonical (`q0`, `q01`, `Q1`, `x1`, four parts: refused).
- **Positions are stable** (2026-11-27 D18): an ask's questions and checklist are never rewritten after filing; the only payload write after filing is the merge's folder-ask `$.other_bench`. `TestAskPayloadItemsAreNeverRewritten` (`internal/db/ask_payload_guard_test.go`) fails on any other SQL that writes `owner_asks.payload`, `TestMergeLeavesQuestionAndCheckPayloadsAsTheyWere` pins the merge, and `AskExplainTests.testOwnerAskHasNoRecordWrite` keeps `OwnerAsk` free of GRDB persistence. Rewriting a payload would need a re-key of its item chats in the same transaction.
- **Legacy chats** (2026-11-27 D4): a whole-ask chat made by 0.29.5 (`<workbench>:<ask>`, `AskExplainKey.legacyContextID`) on an ask with exactly one item (`AskExplainItem.isOnlyItem`) becomes that item's chat: the open's first read (one snapshot with the workbench and folder) looks it up (`AskExplainSurface.legacyConversationID`) and, when found, uses it without `chat.new`, keeps its title and keys the engine by the legacy context id (its queued drafts keep their key). On an ask with several items the legacy chat gets no entry; it stays unseen and still goes with its workbench and follows a merge.
- `AskExplainSurface.spec` (`Sources/Services/ChatSurfaces/`): persistence `.database`, `toolAccess: .draftOnly`, the config's provider at its strong tier, `purpose = ask.explain` (`queryPurposes` in `cmd/ai.go`; the usage ledger names it "Ask explanations", see `llm-usage-ledger.md`), `readFolder` = the ask's folder (`AskExplainSurface.readFolder`, read at each open: the folder its filing session was started in — `terminal_sessions.workbench_folder_id` —, else `owner_asks.doc_folder_id`, else the home folder; only a live folder of the ask's own workbench counts, so a removed folder or another bench's falls back to the home folder; a session being deleted counts as gone for an open — marked for its cleanup, in its delete's 5-second Undo window, or past it while its `delete_requested_at` write settles (`OwnerAsksViewModel.hiddenSessions` = `WorkbenchesViewModel.deletingSessionIDs`); an open after Undo reads its folder again. A chat already open keeps the folder it read at open until the next open — still a live folder of the same workbench, read only; `ai query --read-folder` accepts any live workbench folder) only for a provider that reads files (claude, codex; never ollama, whose `ai query` refuses `--read-folder`; an unread catalog gives none).
- System prompt (`AskExplainPrompt.system(ask:item:target:)`, rebuilt from the ask and sent with every turn by `EmbeddedChatEngine.makeStream`; only the hidden `firstTurn(item)` request is first-turn only): outside the fence, one line naming the item by kind and number ("question 2 of the ask below", "step 2 of the check below"); inside it, the whole ask: its title, summary, changes since the previous round, the "Look at" (focus) items, questions with options, descriptions and recommended marks (or the checklist steps and hints), and the target's title and intent, all fenced as untrusted data with a fence longer than any backtick run inside. Asks store no reason, so none is sent. Rules: answer in the ask's language, explain but never decide or pick, never change anything, the folder is read only. The hidden first turn is `AskExplainPrompt.firstTurn`.

## Desktop

- `OwnerAsksViewModel`: `explainOpen: [askID: AskExplainItem]` (the drawer's mode, per ask, at most one item; in memory; closing the drawer forgets it, the chat stays; `isExplaining(askID)`, `explainItem(askID)`); every other explain state — surface, open error, final failure, the open in flight, the reopen it must re-read for, the rebuild count — is keyed by `AskExplainSubject` (ask + item). An open whose subject is no longer the mode when it returns (Back, or Back and another item's entry) drops its result. `openExplain(ask, item:)` (an item not in the ask, `AskExplainCard.make` nil, opens nothing; reads the workbench, finds the conversation, `ensureExplainEngine`, then `startFirstTurnIfEmpty(hidden:)`, else `offerRetryOfStoredReply` unless the owner stopped that reply; an open asked while one runs — Back, then reopen before `chat.new` answered — makes the running one read again, so one conversation, one engine and one hidden turn carry the latest read), `closeExplain` (also forgets the ask's surface, error and rebuild count; an open still finding the conversation when Back is pressed drops its result, makes no engine and starts no turn — the engine itself stays in the center, D5), `explainEngine(for:item:)` (read only, safe in a body), `ensureExplainEngine(_:item:)` (rebuilds an engine the center let go while idle, from `.task`; moves an engine a merge left under the old key to the new one, `EmbeddedChatCenter.adopt`), `explainErrors` (a failed open), `explainFinal` / `explainOffersRetry(subject)` (a gone workbench: no Retry), seams `explainConfigProvider` / `explainCatalog`.
- Entries: `AskExplainEntry(item:action:)` (`questionmark.circle`, `KitQuietButtonStyle(label: .secondary)`, caption). A question's is **Not clear?**, trailing at the foot of its block under the Other… field, drawn through `ChatQuestionDraft.decorate` (inside the keyboard cursor's outline; `AskExplainItem.forQuestion(id:in:)` maps the question to its position); a step's is the bare icon at the trailing end of its text row in `OwnerAskChecklistBody`, tooltip "Ask the assistant about this step". Every entry's accessibility label names its item ("Not clear? Question 2", "Not clear? Step 3"). No key opens an item's chat.
- Chat views: `AskExplainPane.layout(_:subject:card:…)` puts `AskExplainItemHeader(subject:card:onBack:)` on top of every state — spinner while finding, "Couldn't explain: <reason>" while the open failed, else `AskExplainChatView` (`EmbeddedChatRows`, `EmbeddedChatComposer` compact with the item's placeholder, Esc back). The header is the strip (**‹ Back to question** / **‹ Back to check**, then "Question N" / "Step N") and `AskExplainItemCard(card:)` with the subject as its id, so expansion resets per item.
- The card (`AskExplainCard.make(ask:item:)`, from the payload, no read): a question in semibold inline Markdown with one row per option (circle, label on one line, the ask card's **Recommended** mark; no descriptions), or "N." with the step's text and hint; callout. `AskExplainCardLayout.mode`: whole up to `clampHeight` (76 pt), else clamped with a fade mask and **Show more**; expanded, whole up to `expandedMaxHeight` (180 pt), past it a scroll view of that height, with **Show less**. `askExplainCardStartsExpanded` (environment, default false) is the expanded design shot's seam only. `OwnerAskDrawer` keeps the question layer in the tree under the chat (`OwnerAskDrawerExplainLayers`): opacity, hit testing and accessibility off, so picks, the note draft and the scroll survive (`ask-explain-built-back-scrolled` pins the scroll). While the chat shows, the drawer's bare keys (`OwnerAskDrawerKeys`) are off and ⌘↩ does not answer.
- Copy: `AskExplainCopy` (entry, entryAccessibilityLabel, entryHelp / stepEntryHelp, back / backToCheck, placeholder / stepPlaceholder, itemLabel, showMore, showLess, recommended, errorPrefix, retry, emptyHint).

## States and indicators (decided during implementation)

- **One indicator per state** (spec D10): Loading shows the feed's own live row, Queued the composer's own queued status ("Queued — waiting for a free assistant slot", Cancel). The mockups' "Explaining…" and "Waiting — other chats are answering." lines are not built.
- **Errors** (D11): a turn that fails once its reply row exists shows the shared ChatUI error card with its Retry. "Couldn't explain: <reason>" with **Retry** is only for a failed open (`explainErrors`, e.g. "This workbench no longer exists."). A hidden first turn that failed before it started (`engine.hiddenTurnNotStarted`, no row) shows the engine's own banner text with **Retry** and no prefix, since the banner already says what failed ("Couldn't send: …"; `AskExplainChatView.failureLine`); its Retry opens the chat again. The composer's status line leaves that failure out (`EmbeddedChatComposer.hidesError`, set only here), so it shows once. A failed open on a deleted workbench ("This workbench no longer exists.") is final: no Retry; **Back to question** leaves it.
- **Finding** (D13): before the engine exists the pane shows the strip and the card over a centred spinner; a failed open keeps the card too (2026-11-27 D13).
- **Retry after a restart** (D12): offered for a quit-partial first turn or a retryable error, never for a non-retryable code such as quota (no replay by contract), and never for a reply the owner stopped. Stop and quit store the same `partial` row, so the stop is remembered on the Mac: `EmbeddedChatEngine.onOwnerStop` (opt-in, set only by this surface) records the turn's id (a random UUID, the reply row's `turn_id`, so it never matches a reply of another workspace's database or of a recreated one) in the preferences (`askExplain.stoppedTurnIDs`, newest 200); no other chat's persistence changes.

## Writers, deletion, merge

The conversation row: `chat.new` only, which refuses an explain chat of a workbench that is gone, checked in its creating transaction (`db.WorkbenchExistsTx`): with `db.DeleteWorkbench` taking the same write lock, whichever commits first, no conversation of a deleted workbench remains. Its `context_id` changes only in `reKeyChats` inside a workbench merge (`<from>:<ask>[:<item>]` → `<into>:<ask>[:<item>]`, the shape kept; with `code_question` and `spec_review_thread`; `TestMergeReKeysTheChats`); an engine still held under the old key (a turn may run) is moved to the new key by the next open, so the chat never has two engines. Messages: each turn's `ai query --persist` process and the Mac's `chat.reply.finish` / `chat.message.append`, one turn at a time per key (the existing embedded chat rules). Deletion: only `db.DeleteWorkbench`, which drops `owner_ask_explain` conversations with the `<id>:` prefix and, in the same transaction, their queued follow-ups in `chat_queued_drafts` (surface key `owner_ask_explain.<id>:<ask>[:<item>].<conversation>`, exact prefix `db.AskExplainDraftKeyPrefix`) (`TestDeleteWorkbenchDropsAskExplainChats`, PROJ-02). A merge moves those drafts to the surviving bench's key in the merge transaction (`reKeyChats`). Queued drafts: written and cleared only by the Mac's `DatabaseDraftMirror` through the `chat.*` draft commands; an explain chat's key follows its conversation (`askExplainDraftKeyTx`): a save for a deleted one writes nothing, and a save or clear under a key a merge replaced lands on the current key (chat_writes.json `*ask_explain*` cases). The ask itself is never written by this feature; an ask answered or withdrawn while its chat is open leaves the chat as it is.

## Guards

The chat holds the ask's and the folder's text, so it is kept out of every reader `spec_review_thread` is kept out of: `internal/tools/chat_history.go`, `internal/kb/source_chat_artifact.go`, both `NOT IN` lists of `internal/db/chat_knowledge.go`, memory ingestion, and `EmbeddedChatWiring.savesKnowledge` (Swift). Pinned by `internal/tools/code_question_guard_test.go`, `internal/memory/code_question_guard_test.go`, the `chat_knowledge` tests and `EmbeddedChatWiringTests.testAskExplainSavesNoKnowledge`. The main chat's history lists only `context_type IS NULL` conversations.

- **Header and answer bar.** The real drawer header (icon, `#id` and the title in bold, "Question · just now", "k of N ›", expand, close) replaces the mock's kind chip; the answer bar is the drawer's own (status line, **Dismiss**, **Answer** / **Send**). The question view is the real question card (taller Other… fields, **Note for the agent**), so the three-question entry shot shows question 3's entry below the fold at 760 pt; `back-scrolled` shows it at the bottom, where the mockup does.
- **Recommended.** The card draws the ask question card's own mark (`DesignKitChatStyle(look: .ask).recommendedMark`), a little smaller than the mock's chip (2026-11-27 D5: "as the ask's question card draws it").
- **Feed and composer.** Owner bubbles are ChatUI's accent bubbles; replies carry ChatUI's copy button and time and sit at the feed's own margin; the composer is `EmbeddedChatComposer` (grey send button while empty, Stop while busy, a spinner in its queued line).
- **Loading / Error.** The feed's own live row instead of the mock's three dots, and the shared ChatUI error card ("Something went wrong while answering." with the reason, **Retry**) instead of the mock's red line (2026-11-24 D10, D11).
- **Failed open.** The line starts at the card's edge (the strip's and card's margin), 4 pt left of the mock's.

## Limits (v1)

- **Mac only** (D8): the phone has no embedded chat engine.
- **No session transcript** in the context (D9); the ask's summary is the agent's statement of the question.
- A reply to a conversation deleted mid-turn fails as a save error and the idle sweep releases the engine.
- An explain chat already open when its session is deleted keeps the folder it read at open until the next open (the drawer closes with the session; the folder is still a live folder of the same workbench, read only).
- **Code question and spec review thread drafts** are not deleted or re-keyed with their workbench (`deleteWorkbenchCodeQuestions`, `deleteWorkbenchSpecReviewThreads`, `reKeyChats` move only the conversations); only the explain chats' drafts are handled here.
