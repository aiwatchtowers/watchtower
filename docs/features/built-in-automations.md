# Built-in automations — the engine and the Morning brief (C2, 2026-10-22)

Watchtower ships some of its own daemon work as automations: a recipe embedded in the binary, run by the automations executor at a fixed place ("slot") in the daemon's sync cycle, shown in Automations → **Built in**, editable through the panel and resettable to the shipped text. C2 ships the engine and its first built-in, **Morning brief** (`morning-brief`), which makes the daily briefing and then the day plan in one run. C3 moves tracks, ideas, reactions and custom tracks onto the same engine.

Spec `docs/superpowers/specs/2026-10-22-inbox-built-in-automations-design.md` §4, §5.1–§5.4, §8, §9 (owner approved, ask #500; AUTO-06 and FEAT-01..03 amendments). Plan `docs/superpowers/plans/2026-10-22-c2-built-in-engine-and-morning-brief.md` (ask #502). Board #801 (under Automations #405), C2 group #875. The owner-recipe side of automations is `docs/features/automations.md`; contracts AUTO-01..13 are in `docs/inventory/automations.md`.

## Registry and slots

- `internal/automations/builtin/registry.go`: one `Entry` per built-in, in card order (`All()`, `Lookup(id)`, `AtSlot(slot)`; each returns clones). An `Entry` holds `ID` (the `builtin_id` and the recipe's slug), `Name`, `Slot`, `Recipe` (the embedded bytes, `//go:embed recipes/*.md`), `FeatureIDs` (features-registry ids whose config keys are the on/off truth), `Primitives`, `Prompts` (`PromptRef{Name, PromptID}`), `Parameters` (`Parameter{Key, Kind, Label}`, `ParamKind` = `hour` | `clock` | `count`), `Pipelines` (`pipeline_runs` names counted in Costs), `Reads`/`Sends` (card copy), `When(cfg)` (the card's When sentence), `RunNow` and `NoRunNowNote`.
- `Entry.Enabled(cfg)` is true when any of its features is on (`features.ByID(id).Enabled(cfg)`); a nil cfg or an unknown id counts as off. There is no `enabled` of its own: the config keys stay the truth (spec §5.4).
- `Entry.DefaultPrompt(name, role)` is the shipped prompt for the owner's role (`prompts.DefaultForRole`); `DefaultPromptFunc(builtinID, name, role)` is the same over the registry and is what `Backends.DefaultPrompt` holds.
- Slots: `automations.SyncSlots = morning_brief, custom_tracks, tracks, reactions, ideas` (all five reserved in C2); `builtin.Slot` constants exist for the ones a built-in uses (`SlotMorningBrief` in C2).

## The row model

- One `automations` row per built-in (migration 00150): `origin = 'builtin'`, `builtin_id = <id>`, `path = 'builtin:<id>'` (synthetic; no file is written until the owner edits), scope Personal. `overridden = 1` while the row is indexed from the owner's copy; `builtin_base_hash` is the shipped content hash the copy was made from (set on the 0 → 1 transition, kept while overridden). Owner rows are `origin = 'owner'`; `idx_automations_scope_slug` is unique only over owner rows, so a Personal recipe with a built-in's slug is a separate row. `builtin_migrations` records the one-time upgrade step (below).
- The owner's copy is `<workspace>/automations/.builtin/<id>.md` (`builtin.OwnerCopyPath`). The Personal scanner skips the directory and never treats a built-in row as one of its files.
- `builtin.Sync` / `SyncOne` (`sync.go`) bring each row in line with its source: the copy when it is a regular file (lstat first, read through `automations.ReadRecipeFile`, links never followed), else the shipped bytes. A copy that is a symlink, directory or special file is never read (the shipped text runs, `OwnerCopyNote` says why); a copy that exists but cannot be read is an error and the row keeps what it holds. An unchanged built-in writes nothing (`sameRow`), so the Personal scope's generation stays put. `SetBuiltinEnabled` mirrors `Entry.Enabled(cfg)` into the row last.
- `db.Automation` gains `Origin`, `BuiltinID`, `Overridden`, `BuiltinBaseHash` and `Confirmed()`, `IsBuiltin()`, `RunsAtSlot()` (= `IsBuiltin()` in C2); `Runnable()` is `Confirmed() && Enabled`. `automations.ScopeOf(row)` rebuilds the built-in scope (`Scope{Personal, BuiltinID}`, `String()` = `builtin:<id>`); a DB lookup by scope uses the folder scope.
- The card's data is `builtin.Card` (`card.go`): `show --json`'s `builtin` block — `id`, `slot`, `overridden`, `shipped_hash`, `base_hash`, `update_available` (overridden and base ≠ shipped), `shipped_text`, `default_prompts`, `when`, `reads`, `sends`, `parameters[{key,kind,label,value}]`, `feature_ids`, `enabled` (the features are on and the daemon has not stopped it — no `disabled_reason`), `run_now`, `copy_error` (the row's parse error, or an lstat error other than not-exist), `costs{usd,days:7,reported,tokens}` (`db.BuiltinCost`: reported run costs, plus the entry's `pipeline_runs` rows before its first run; `tokens` is those runs' and rows' input + output tokens — the pipelines report tokens but no cost, and the automation meter cannot price tokens, so no USD is made up). Pinned by `internal/automations/builtin/testdata/show_morning_brief.json` (regenerate with `go test ./internal/automations/builtin -run Golden -update`; it embeds the default prompts, so a prompt change regenerates it).

## AUTO-06 as amended (ask #500)

- Shipped bytes run without the owner's confirmation: `Sync` calls `db.ConfirmShippedBuiltin(id, shippedHash, approvalHash, now)` only when the row is unconfirmed, has no parse error and its content hash equals the shipped hash. `ConfirmShippedBuiltin` refuses an owner row (`ErrNotBuiltin`), other bytes and a stale approval hash (`ErrHashMismatch`).
- Everything else holds: the owner's copy is indexed unconfirmed and runs only after the owner confirms it in the panel; a hand edit makes it unconfirmed again (the built-in then stops — it does not fall back to the shipped text); a copy byte-equal to the shipped text is confirmed like the shipped text.
- Only a built-in scope may declare `trigger: {sync: <slot>}` (`syncTriggerAllowed`) or a `builtin:` capability (`capabilitySpec.builtinOnly`); a Personal or workbench recipe doing either is a parse error. The approval hash covers the built-in scope and the slot. A built-in's own recipe must keep `sync: <its registry slot>`: the built-in indexer (`automations.IndexBuiltinRow`) makes any other trigger kind or slot in the owner's copy the row's parse error ("a built-in's trigger must stay \"sync: <slot>\""), so it never runs.
- A dry run of a built-in calls no primitive (AUTO-12): `brief.compose`/`plan.compose` close their steps `dry_run`.
- Guards: AUTO-06 "C2 built-ins" in `docs/inventory/automations.md`, including the upgrade step's `TestAuto06_UpgradeConfirmsOnlyCarriedPrompt` — the fourth `ConfirmAutomation` caller, confirming only the copy it rendered from a customised prompt-store row that was already running.

## The `sync` trigger and in-cycle runs

- `trigger_kind = 'sync'` and run trigger `'sync'` (`db.TriggerSync`). A built-in's runs execute **inline, at its slot, in the daemon's sync goroutine** on a dedicated slot executor (`automations.NewExecutor` over `slotBackends`, never `Run`): `automationBackends` (so a copy has the read tools) + `Primitives = d.BuiltinPrimitives()` + `DefaultPrompt = builtin.DefaultPromptFunc`. `wireBuiltins` (`cmd/builtins.go`) builds it in `runSyncDaemon` before, and outside, `if automationsOK`, syncs each built-in with `SyncOne`, runs the one-time upgrade step, and hands `d.SetBuiltins(runner, active)`. The daemon never reloads config in process; runner and daemon share one `cfg`.
- The main executor's poll never claims, cancels or resumes a `RunsAtSlot()` run (`poll.consider`/`poll.resume` skip them). `Executor.ExecuteBuiltinInline(ctx, runID)` requires `RunsAtSlot() && Confirmed()` (else it cancels the run `not_runnable`, `ErrNotRunnable`) and claims with the per-automation concurrency (`ErrRunNotClaimed`, run stays queued); `enabled` is not checked there (the runner checks on/off). Slot runs do not count against `MaxConcurrent`.
- `builtin.Runner.RunSlot(ctx, slot)` (`runner.go`), per built-in at the slot, in card order: off → its queued manual runs cancelled `not_runnable` (`db.CancelQueuedBuiltinRuns`), `Skipped = off`, nothing else read or written (FEAT-01); the stale-run guard (`db.MarkStaleBuiltinRuns`); stopped by the daemon after a run that would not end (`disabled_reason`, AUTO-08) → queued manual runs cancelled, `Skipped = disabled`; unconfirmed → its queued manual runs cancelled `not_runnable`, `Skipped = not_confirmed`; a queued manual run → executed without asking the gate; else the entry's `Gate.Due(ctx, e, now)` decides and only a due built-in gets one `sync` row, executed inline. A sync run that loses its claim is cancelled (the next cycle asks again); a manual one stays queued. A DB failure is `Status = error`, logged.
- **Run Now at the next sync.** `automations run <id>` on a built-in (and the card's **Run Now**) only queues a `manual` row and sends `signalSyncNow`; the slot runs it (`"at_next_sync": true` in `--json`). Refused when `RunNow` is false (`NoRunNowNote`), before the built-in's one-time move is `done` (no `builtin_migrations` row yet: "Morning brief moves to Automations at the next daemon start — try again after it"; a failed move: "Morning brief hasn't moved to Automations yet — use Retry in the Inbox"), when the built-in is off, when the daemon stopped it ("Morning brief was stopped after a run that would not end — turn it on again in Automations → Built in"), when unconfirmed, and with `--rerun-of`. While the built-in is not active (its move failed) `phaseMorningBrief` cancels its queued manual runs before the legacy phases.
- **Run Now inline (CLI generate).** `Runner.RunNow(ctx, id, in)` queues a `manual` run with `event_json = {"builtin": in}` and executes it inline whether or not the built-in is on; a built-in the daemon stopped is refused first (`ErrBuiltinStopped`). A coalesced queued run with other input is refused (`ErrRunNowQueued`, wraps `ErrRunNotClaimed`); a run this call queued that cannot be claimed is cancelled while it is still queued (`db.CancelQueuedAutomationRun`) so it never runs later with that input — one the slot claimed meanwhile is left running and the CLI says it is running now.
- **Runaway stop (AUTO-08).** An abandoned run's `DisableRunawayAutomation` sets `enabled = 0` and `disabled_reason` on the built-in's row; `db.SetBuiltinEnabled` (the sync's mirror of the features) never turns such a row on, the card shows it off (`enabled` false), and only the owner's turn-on clears it: `features enable <feature>` of one of its features — also when the feature is already on (no fast-forward then) — calls `db.ResumeBuiltin` and prints "Turned Morning brief on again."; under AI-agent markers it is not cleared ("Morning brief stays stopped: …"). The card's **Turn On** with every feature on already runs `features enable <first feature>` (`FeatureManagerService.resumeStoppedBuiltin`, no daemon restart). The daemon's "turned off" notice (#584, `AutomationFailureWatch`) of a built-in opens its card (`openAutomationRun` → `.card(id)` → `BuiltinAutomationCard`), so its Turn On is that path, never `automations enable`.
- Run ends: `MarkInterruptedAutomationRuns` (the main executor's start sweep) skips built-in runs; `db.MarkInterruptedBuiltinRuns` is the daemon's own sweep (`sweepBuiltinRuns`, at start before `startAutomations`, retried before each slot until it succeeds); it ends a `running` `manual` run (a CLI's inline run) and a dry run only past their deadline (started_at + budget + 1 min), sync and waiting runs at once. `db.MarkStaleBuiltinRuns(now)` (before each slot entry and `RunNow`) ends a `running` built-in run past `started_at` + budget minutes + 1 min that never waited (no `resume_pending`, no pending replay, no ask/session/waiting step, no `{wait}` write) — a SIGKILLed CLI's run. A CLI run killed after a wait is not ended by it and holds the built-in until the daemon's start sweep. No column says who holds a `manual` run, so a queued Run Now the daemon itself was executing when it died is kept the same way: it blocks the built-in until `MarkStaleBuiltinRuns` ends it, about budget + 1 min after it started (v1 limit; a holder marker on the run would close it).

## The primitive contract

- `sdk_builtin.go`: `BuiltinInput{Only, Date, Feedback, Force}` (C3 adds `Since`), `PrimitiveCall{Name, BuiltinID, Prompt, Args, Trigger, Input, Role}`, `PrimitiveUsage{InputTokens, OutputTokens, CostUSD, Reported}`, `PrimitiveResult{Status "done"|"skipped", Fields, Note, Usage}`, `PrimitiveFunc`. `Backends.Primitives` maps primitive names to funcs.
- `BuiltinModule` defines a primitive path (`brief.compose`, `plan.compose`) only when the manifest holds `CapabilityForPrimitive(name)` (default `builtin:<name>`, overridden by `PrimitiveCapability`), and `builtin.defaultPrompt(name)` / `builtin.input` when any `builtin:` entry is present. Outside a built-in scope nothing is defined.
- Each call `x.compose({prompt})` is one `llm` step named after the primitive (step permission `builtin:<name>`): `AllowPrimitive`, argument checks (`ValidationError`), dry run → `dry_run`, else the func under `MeteredModelCall`. The reported usage is debited from the run's meter and recorded on the step and the run (a primitive must report real usage; the pipelines reset theirs at the start of each run). An error → `SDKError{PrimitiveFailed}`; uncaught it ends the run `failed`/`backend`. A status other than done/skipped is `PrimitiveFailed`. `Note` (e.g. the placeholder fallback) is journalled on the step, not shown to the script.
- The owner's role is read once per run (`OwnerRole`). `builtin.defaultPrompt` is a pure read, not journalled. A malformed `{"builtin": …}` input (bad JSON, date not `YYYY-MM-DD`, unknown `only` name) fails the run `backend` before any script code.

## Morning brief

- Recipe `internal/automations/builtin/recipes/morning-brief.md`: `trigger: {sync: morning_brief}`, permissions `builtin:brief.compose`, `builtin:plan.compose`, budget 400 000 tokens / 15 minutes. The script calls `brief.compose` then `plan.compose`, each with `builtin.defaultPrompt(name)`; a failed brief does not stop the plan; the first failure fails the run.
- Entry: features `briefing`, `day-plan` (on while either is on); prompts `brief` → `briefing.daily`, `plan` → `day_plan.generate`; parameters `briefing.hour` (Time), `day_plan.working_hours_start`/`_end`, `day_plan.max_timeblocks`, `day_plan.min_backlog`, `day_plan.max_backlog` (the three counts are card fields; the plan pipeline still does not read them); pipelines `briefing`, `day_plan`; `RunNow: true`.
- `phaseMorningBrief(ctx, now)` (`internal/daemon/morning_brief.go`) replaces `phaseBriefing` + `runDayPlanPhases` in `runSync`. With no runner or the built-in not `active`, it runs those legacy phases unchanged. Otherwise it resolves the cycle owner once (`dayPlanOwner`), runs `RunSlot(SlotMorningBrief)`, then `runDayPlanConflictPhase` — the conflict phase stays Go and runs every cycle.
- Gate `MorningBriefGate`: due when `briefDue(now) || planDue(now)`. `briefDue` = `briefing.enabled` + pipeline + `shouldRunBriefingAt` (one per calendar day after `briefing.hour`, fresh-install bypass `briefingFresh`, 3 attempts a day) + `briefingHasOwner`, and false for an hour after a sync brief that found no data (`briefingNoDataBackoff`). While no briefing was ever made (`briefingFresh`) the backoff is replaced by `briefing.Pipeline.HasMaterial(date)` — the run's no-data rule as a read, no model call: nothing to summarize is not due (no run row), data is due at once, so a fresh install's first brief comes in the first cycle after its first digests. `planDue` = `day_plan.enabled` + `shouldRunDayPlan(now, owner)`, which now uses **`briefing.hour`** (fresh-install bypass `dayPlanFresh`). `day_plan.hour`, `DayPlanConfig.Hour` and `DefaultDayPlanHour` are retired; a leftover key in `config.yaml` is ignored.
- Primitives `builtin.MorningBriefPrimitives(brief, plan, hooks)` (`morningbrief.go`): a call returns `skipped` when `Input.Only` leaves it out or, in a sync run, when its gate says not now. `brief.compose` → `briefing.RunForDateWith(date, {Prompt})` → `briefing_id`; `plan.compose` → `dayplan.Run` with the owner, `Feedback`, `Force` (feedback implies force) → `plan_id`, `items`. Both report usage and `LastPromptNote` (a prompt with the wrong `%s` count falls back to the default, and the note says so).
- Tracking (daemon hooks `trackBrief`/`trackPlan`): the legacy closures — `pipeline_runs` rows named `briefing` and `day_plan`, `last_briefing.txt` (today only), `lastDayPlanDate`, attempt files `briefing_attempts.txt` / `day_plan_attempts.txt`. Only a `sync` run charges an attempt; a sync no-owner brief is the benign once-a-day skip; a manual run surfaces `db.ErrNoOwner` (OWNER-02).
- Prompts: an active built-in uses the recipe's prompt, never the prompt store. `prompts.MovedToBuiltin` lists `briefing.daily` and `day_plan.generate`: `prompts show` prints "Used by the Morning brief built-in — change it in Automations → Built in.", and the tuner skips them.

## CLI paths

- `briefing generate` / `day-plan generate [--date --force --feedback]`: `RequireOwner`, then `runMorningBriefNow`. Until the Morning brief's `builtin_migrations` row is `done` (the daemon's one-time move), it runs `runMorningBriefLegacy` — the briefing / day-plan pipelines straight, with the prompt store and no override, both features forced on, no automation run — as the commands ran before C2. After the move: `SyncOne` with the loaded cfg, both features forced on in a copy of cfg for the pipelines (so the commands work with the features off), `newCLIBuiltinRunner` (own executor over `automationBackends`, no gates, no attempt budget, no `pipeline_runs`), `RunNow` with `Only:[brief.compose]` or `Only:[plan.compose]`. SIGINT/SIGTERM end the run. Pinned refusals: "Morning brief was stopped after a run that would not end — turn it on again in Automations → Built in", "Morning brief: your edited copy is not confirmed yet — confirm it in Automations → Built in", "Morning brief: your edited copy has an error — fix it in Automations → Built in", "Morning brief is running now — try again in a minute", "Morning brief is already queued for the next sync".
- `automations reset <id> [--json]` (owner only): removes the copy if it is a regular file, `SyncOne`; JSON `{"automation_id","overridden","approval_hash"}`. Refused for an owner automation and when `.builtin` is not a real folder.
- `automations save --path builtin:<id>`: writes the copy atomically (0600, `.builtin/` 0700), `SyncOne`, then `--confirm-hash`; `--expect-content-hash` compares against the copy, else the shipped hash; refused under agent markers before anything is read.
- Refusals with pointers: `enable`/`disable` ("A built-in turns on and off with its features: watchtower features enable|disable briefing day-plan"), `delete` ("built-ins cannot be deleted; turn it off instead"), `auto` ("built-ins get no auto grants (AUTO-03)").
- `show <id|morning-brief> --json` adds `builtin` (`null` for owner rows); `list --json` rows add `origin`, `builtin_id`, `overridden`. `validate --against <builtin id>` parses in the built-in scope.
- Authoring: `draft_automation` takes `builtin_id` (the draft parses in that scope, slug forced, widening against the confirmed text); `save_automation` refuses any `builtin_id` ("a built-in is saved from its panel").
- `automations upgrade-builtins [--json]` (owner only, refused under agent markers) re-runs the upgrade step for `failed` entries; JSON `{"results":[{"builtin_id","status","error"}]}`.

## The one-time upgrade step

`upgradeBuiltins(cfg, db, now, logger)` (`cmd/builtin_upgrade.go`) runs in `wireBuiltins` after the sync and before `SetBuiltins`; a built-in is active only when its sync succeeded **and** its move is `done` (`active[id] && moved[id]`). Per built-in (a `done` row in `builtin_migrations` skips it; idempotent; it runs under agent markers too, as it only carries content already running):

1. On/off needs nothing: the config keys are the truth.
2. For each `PromptRef`, `customisedLegacyPrompt` finds the template the legacy pipeline really ran: the briefing's role-resolved row (the role variant row when it exists; a shipped role variant with no row wins over the base row, as in `Store.GetForRole`), the day plan's base row only (`rolelessLegacyPrompts`: its legacy pipeline never asked for a role). It is collected only when that row is `customized`, not blank, and has the default's `%s` count (the legacy pipeline ran the default in its place otherwise); a template that changed while it was read is an error.
3. If any were collected, `RenderOwnerCopy(e, collected)` is written atomically to `.builtin/<id>.md` (folder created 0700; a `.builtin` that is a symlink or a file is refused), `SyncOne` indexes it (`overridden = 1`, `builtin_base_hash` = the current shipped hash) and `ConfirmAutomation` confirms exactly those bytes. An existing copy is never overwritten: one with exactly the rendered bytes (a move interrupted after its write) is indexed and confirmed, any other is the owner's and is kept (logged, the prompt store not carried); a copy path that is not a regular file is an error. `RenderOwnerCopy` inserts `const __builtinPrompts = {…}` (each prompt one JSON string literal) at the top of the script and redirects every `builtin.defaultPrompt(` to it; a prompt not given keeps the shipped default, and the result is re-parsed in the built-in scope.
4. `RecordBuiltinMigration(id, "done")`. Any error records `failed` with the error text and logs it; the built-in is not active, so its **legacy phases keep running** this daemon life.

A `failed` row is an Inbox notice "Couldn't move Morning brief to Automations" with the error and **Retry**: `automations upgrade-builtins [--json]` re-runs the move for `failed` entries only (JSON `{"results":[{"builtin_id","status","error"}]}`; text "<id>: moved; restart the daemon so it runs as a built-in." or "failed again: …"). It is owner-only — refused under agent markers, like every CLI path to `ConfirmAutomation` (`TestBuiltinUpgrade_RetryRefusedUnderAgentMarkers`). The Desktop restarts the daemon when a result is `done`, since the daemon picks its path at start.

## v1 limits

- The legacy `phaseBriefing` / `runDayPlanPhases` code stays until the release after C3, as the fallback for a failed upgrade step or a failed sync of the row.
- Deleting the copy by hand equals **Reset**: the next sync indexes the shipped text, confirmed.
- A description-only edit of the copy keeps its confirmation (name and description are not hashed, as for owner recipes).
- The daemon's start sweep (`MarkInterruptedBuiltinRuns`) also ends a live CLI generate run if the daemon starts while it runs; the CLI then reports the run as failed.
- A `sync` brief that found no data backs off one hour; before the first digests that still writes a succeeded run every hour.
- The three plan counts are card parameters, but the plan pipeline does not read them yet (known issue in the guide).
- The Desktop prompt editors are not changed; a prompt-store edit of `briefing.daily` or `day_plan.generate` has no effect while the built-in is active.

## How C3 plugs in

In this order (C3 appends its own section below and does not rewrite this one):

1. A `builtin.Entry` in the registry (`All()`), with `RunNow` and, when false, `NoRunNowNote`, and its recipe under `recipes/`.
2. Its `Slot` constant (the slot is already reserved in `automations.SyncSlots`).
3. Its primitive names appended to `automations.BuiltinPrimitiveNames`.
4. A `PrimitiveCapability` entry only when its capability is not `builtin:<name>` (`CapabilityForPrimitive`), and a `syncTriggerAllowed` case only when a non-built-in scope may use the slot (C3: `custom_tracks` for a Personal recipe holding `track:scan`).
5. Its `Gate` (in `wireBuiltins`' gate map).
6. Its `PrimitiveFunc`s added to `Daemon.BuiltinPrimitives()`.
7. Its `PromptRef`s and `Parameter`s (new `ParamKind`s in lockstep with Swift's `Parameter.Kind`).

## C3 — Track my threads, Idea finder, Reactions and watched tracks (2026-10-23, board #801)

Tracks, ideas, reactions and custom tracks run on C2's engine, following the eight steps above in order. Spec: `docs/superpowers/specs/2026-10-22-inbox-built-in-automations-design.md` §5.1–§5.4, §6.3, §8.

### The three entries and their slots

| Entry (`id`) | Slot (`trigger: {sync: …}`) | Primitive (capability) | Feature | Prompt | Parameters |
|---|---|---|---|---|---|
| Track my threads (`track-my-threads`) | `tracks` | `tracks.extract` (`builtin:tracks.extract`) | `tracks` | `tracks.extract_batch` | none |
| Idea finder (`idea-finder`) | `ideas` | `ideas.consolidate` | `ideas` | `ideas.consolidate` | `ideas.mine_interval_hours` (`interval`, label **Every**, 1–24 h) |
| Reactions (`reactions`) | `reactions` | `reaction.compose` | `reaction-commands` | `reactioncmd.command` | `reaction_command_map` (`dictionary`, label **Reactions**) |

Watched tracks are not built-ins: they are Personal recipes at the `custom_tracks` slot (below). `ParamKind` gained `interval` and `dictionary`, in lockstep with Swift's `BuiltinAutomationDetail.Parameter.Kind`. Run Now: Track my threads and Idea finder yes; Reactions no (`NoRunNowNote` "Reactions run for each reaction you place").

### Primitive contracts and seams

- `tracks.extract` → `tracks.Pipeline.RunWith(RunOptions{Prompt})` through `ThreadsHooks.Track` (the `pipeline_runs` "tracks" row). Usage is read after the call (the pipeline resets its counters per run). `tracks.RunOptions` / `LastPromptNote`: an override that does not keep the default's verb count falls back to the default with a note.
- `ideas.consolidate` → `ideas.Pipeline.RunWith`, `IdeaHooks.Lock` first (`ideas.AcquireBackfillLock`); `ErrBackfillLockHeld` is `skipped`, any other lock error fails the call. Usage is the delta of `AccumulatedUsage`.
- `reaction.compose` → the seam in `internal/reactioncmd` (`Dispatch`, `Outcome`, `Step`, `Dispatcher`, `SetDispatcher`, `SetDispatchPaused`, `DispatchWith(ctx, d, prompt)`). The pass keeps the tool routing, the budget, the claim and the 25-per-run cap; the dispatcher composes. The primitive returns `{status: done, outcome: dispatched, action_id}`; any other outcome is stored in `builtin.ReactionSlot` and the call errors (the SDK admits only `done|skipped`), and the pass reads the Outcome from `ReactionSlot.End`, not from the run status. `Begin` refuses a second pending entry for one run (`ErrReactionRunBusy`); `End` of a run that ended mid-compose returns a strand outcome. The compose call's token usage rides on `Outcome.Usage` and is the primitive's usage, dispatched or not, so the run row, Costs and the recipe's 20000-token budget count it.
- `track.scan` (capability `track:scan`, Personal only) → `customtracks.Pipeline.ScanBound`. The instruction arrives as `PrimitiveCall.Prompt`, extra items as `Args["extra"]` (`[]automations.TrackScanItem`, ≤ 40, source_type slack/email/jira/linear, text ≤ 4096 bytes), `since` only from the run input (`BuiltinInput.Since`, RFC 3339, normalised to UTC), never from the script. The scan reports its tokens (`Pipeline.AccumulatedUsage` delta, error path included).
- Prompt capture: `builtin.CapturePrompts` (confirmed copy only, `DryRunInMemory` with `CapturePrompts` + `StopAtModelCalls`) gives `ideas mine --from` the recipe's prompt.

### Gates

- **Track my threads** (`TrackMyThreadsGate`): tracks on, digests on, a pipeline, a known owner and `tracks.HasMaterial()` (new digests since the last tracks run, or owed retry digests). A quiet cycle writes neither an `automation_runs` nor a `pipeline_runs` row. A failed `HasMaterial` read logs and counts as due. `TrackContext` injection and the rollups stay in `phaseTrackMyThreads` and run even when extraction is not due.
- **Idea finder** (`IdeaFinderGate`): ideas on, the throttle (`ideas.mine_interval_hours`, default 6; the stamp advances whenever the pipeline ran, errors included) and no fresh `BackfillLockFresh`. The primitive takes the lock itself; losing the race is `skipped`.
- **Reactions**: no gate. Each claimed ledger row gets its own `sync` run (`Runner.EnqueueSync`, `ExecuteRun`) from `Daemon.setReactionDispatch` / `builtin.ReactionDispatch` (shared by the daemon and the CLI poll). An unconfirmed copy, or a built-in stopped by AUTO-08, pauses claiming (`SetDispatchPaused`); polling, seeding and `slack.reaction_added` events continue, and those reactions fire once after confirmation (cap 25). A dispatch that refuses before the script ran releases the row (REACT-03 holds: nothing composed, nothing lost); a transient executor failure after the claim finalizes `failed`. A cancelled pass releases. The Reactions card has no Run Now.
- **Watch slot** (`phaseWatchSlot`, before Track my threads): `tracks.enabled && digest.enabled` (FEAT-01: Track my threads off also stops the watches). `NewWatchGate` = `Pipeline.Due` and `HasScanActivity` (digests, auto tracks, inbox; a failed probe reads as not due).

Run order in `runSync`: `phaseWatchSlot` → `phaseTrackMyThreads` → … → `phaseIdeaFinder` (pinned by a static parser test).

### The watch recipe

A watch is a Personal recipe, file `<workspace>/automations/watch-<track id>-<slug>.md`, rendered by `watch.Render` from `internal/automations/watch/template.md`: `trigger: {sync: custom_tracks}`, `permissions: [track:scan]`, no outputs, budget 200000 tokens / 10 minutes, a script of two lines (the `const instruction = "<JSON>";` line at column 0 and a `track.scan({instruction})` call).

- **Binding.** `tracks.automation_id` (migration 00151, unique partial index, no SQL foreign key so the down migration is a `DROP COLUMN`). `db.BindWatchTrack` also copies the recipe's `enabled` to the track; `EnsureWatchTrack` creates the track for a hand-written recipe; `UnbindRemovedWatchTracks` unbinds and pauses the tracks of soft-removed recipes. `GetCustomTracksDueForScan` skips bound tracks (the legacy scan covers only unbound ones).
- **Collecting/Paused is the recipe's `enabled`.** Two SQL triggers (00151): `trg_automations_enabled_watch_track` mirrors `automations.enabled` to `tracks.enabled`, `trg_automations_delete_watch_track` unbinds and pauses the track when the recipe row is deleted. Auto-disable after repeated failures pauses the track too.
- **Instruction is recipe text.** The track's `instruction` column mirrors the recipe line on every scan (only for a run of the current `approval_hash`). The card's inline **Save** rewrites only that line (`tracks instruction`); the owner's press is the confirmation. A watch edited into another shape is changed only in the chat.
- **Triggers and slot.** `syncTriggerAllowed`: a Personal recipe may use `trigger: {sync: custom_tracks}` only with `track:scan` in its manifest, and `track:scan` needs that trigger and is refused in workbench and built-in scopes (AUTO-06 amended). `RunsAtSlot()` = built-in or (Personal and `sync`); the executor poll never claims such runs, the slot sweeps (`slotRunSQL`) include them, `ExecuteBuiltinInline` refuses an unconfirmed or disabled watch.
- **Run Now** is the manual run with **Scan from** (`automations run <id> --since <RFC 3339>`); it queues a run with `{"builtin":{"since":…}}`, wakes the daemon and says "Runs at the next sync" (`at_next_sync: true` in `--json`). A queued run with another Scan from is refused. "All history" sends `1970-01-01T00:00:00Z`.
- **Forward dedup is kept** (a cap-hit window overlap would duplicate events); only the two-stage shortlist is backfill-only. Extra items are kept only inside the scan window `(watermark, until]`.
- **Owner copies of the built-ins** carry the customised prompts through C2's `carryCustomPrompts` (role variant first). Custom-track system prompts (`customtrack.run`, `.shortlist`, `.compose`) stay in Go; a watch's owner-editable text is its instruction.

### CLI paths and the capture rule

- `tracks generate`: after the move, `RunNow` inline of Track my threads (refused with Slack Digests off: "Track my threads needs Slack Digests on"); before it, the legacy pipeline.
- `tracks scan [<id>] [--since]`: a bound track runs only through `Runner.RunWatchNow` (never `RunForTrack`); an unbound custom track after the move is refused with "track #N is not watched — run `watchtower tracks start N`"; before the move it scans the legacy way.
- `tracks start <id> [--json]` (owner only; JSON `{"track_id","automation_id"}`) writes, binds and confirms the watch (`watch.Start`); `tracks instruction <id> --text|--text-file` (owner only) rescans the file, requires a confirmed recipe, rewrites the line, writes and confirms. `tracks enable|disable <id>` toggles the track's own recipe; `enable` is owner-only. `tracks create|watch` write a watch and confirm it, except under agent markers (JSON `"confirmed": false`); the owner's confirmation window (showing the text given) is asked before the compose call, so the Desktop's launch grant is still live, and a denial writes nothing.
- Every owner verb that confirms goes through `refuseUnderAgent` then `confirmWithOwner` (AGENT-07); the Desktop's launches are granted by `OwnerConfirmGrants`. `confirmBound` confirms a bound, unconfirmed recipe only while its text is the untouched template render.
- `automations run <watch id> [--since]`; `--since` on anything else is refused. `show --json` adds `watch` (`track_id`, `instruction`, `template_shaped`), `list --json` adds `track_id`.
- `ideas mine` (flagless): after the move, stage-1 as before, then `RunNow` of Idea finder with `AcquireBackfillLock(ws, "cli")`; a held lock prints the lock-held line and writes no run. `ideas mine --from`: `CapturePrompts` takes the prompt from the current recipe and the multi-cycle drain runs in Go under the "CLI backfill" lock; **it writes no `automation_runs` row**, so a long backfill is never cut by a per-run token budget. `reaction-commands poll` installs the dispatcher over a CLI runner (unconfirmed or stopped copy: polls paused, prints why).
- Before a built-in's move is `done`, each of these paths runs its legacy code unchanged.

### The upgrade (`custom-tracks`)

`upgradeBuiltins` also moves the three entries (as in C2) and ends with `upgradeCustomTracksOnce` (`cmd/builtin_upgrade.go`): for each live (non-dismissed, `ListUnboundCustomTracks`) custom track created at or before the move's first attempt, `watch.Start(Confirm: true)` writes one confirmed recipe, keeping Collecting/Paused, history and linked target. A recipe that was edited since it was rendered (`ErrEditedSinceRendered`) is logged and left unconfirmed, not a failure. A start error after the bind gets one more `Start` in the same attempt; a Retry (`automations upgrade-builtins`) also visits tracks bound earlier whose recipe is still unconfirmed and was written at or after the first attempt (an agent's `tracks create` is never visited). Dismissed tracks stay unbound; `tracks restore` of one prints the `tracks start` hint. `wireBuiltins` sets `active["custom-tracks"]` only when the move is `done` (`activeBuiltins`); until then `phaseWatchSlot` runs the legacy `phaseCustomTrackScan` for unbound tracks and recipes for bound ones, so nothing is scanned twice. The Inbox notice names it "your watched tracks".

### Dual paths

1. `tracks.automation_id` ↔ Swift `Track.automationID` (read-only in Swift; only Core's `WatchTrackControls` sets its copy, then re-reads the row).
2. `tracks.enabled` / `tracks.instruction` are never written from Swift for a bound track: Collecting goes through `automations enable|disable`, the instruction through `tracks instruction`.
3. `trg_automations_enabled_watch_track` and `trg_automations_delete_watch_track` (migration 00151) keep `tracks.enabled`/`automation_id` honest for every reader, including the briefing and MCP. A table recreation of `tracks` or `automations` must recreate both triggers.
4. Migration 00152: `builtin_migrations.first_attempted_at` (TEXT, backfilled from `updated_at`; `RecordBuiltinMigration` sets it on insert and keeps it) bounds which tracks a Retry may move. The Swift notice query names its columns, so it is unaffected.
5. `RunsAtSlot()` ↔ `slotAutomationSQL` (`a.origin = 'builtin' OR (a.scope = 'personal' AND a.trigger_kind = 'sync')`), pinned by `TestAutomation_RunsAtSlotMatchesSlotSQL`.
6. `builtin.ParamKind` `interval`/`dictionary` ↔ `Parameter.Kind`; goldens `show_track_my_threads.json`, `show_idea_finder.json`, `show_reactions.json` decoded through `#filePath`.
7. `AutomationTriggerText` (`tracks` → "After every sync", `ideas` → "Every few hours", `reactions` → "When you react in Slack", `custom_tracks` → "After every sync") and `AutomationCardPresentation` permission lines (`builtin:tracks.extract` "Update your tracks from Slack digests", `builtin:ideas.consolidate` "Find ideas and decisions in your messages", `builtin:reaction.compose` "Turn your reactions into proposals", `track:scan` "Add events to this watch's track") ↔ the manifest.
8. `BuiltinUpgradeNotice.names` (Track my threads, Idea finder, Reactions, "your watched tracks") ↔ `builtin.Entry.Name` and the `custom-tracks` migration id; `isMoveDone` reads `builtin_migrations`.
9. `ideas.mine_interval_hours` ↔ the Idea finder card's **Every** stepper (`ConfigService.saveBuiltinParameters`, one daemon restart), the `reaction_command_map` ↔ `ReactionDictionaryEditor` under **When**.
10. Daemon gates ↔ `FeatureReadiness` (`phaseTrackMyThreads`, `phaseWatchSlot`, `phasePeopleCards`: `Tracks.Enabled && Digest.Enabled`).

### v1 limits

- The legacy `phaseTracks`, `phaseIdeas` and `phaseCustomTrackScan` code stays until the release after C3 (fallback for a failed move or a failed sync of the row).
- Dismissed custom tracks are not migrated and stay unbound.
- `ideas mine --from` writes no `automation_runs` row.
- The `on-reaction` template shows the message text only for the channel's latest 200 messages; an older one gets a fallback card "Reacted with :<emoji>:" naming the channel id and ts (the event holds ids only, so there is no link).
- A watch's **All history** is a full backfill from the epoch, bounded only by what Watchtower holds and the scan's caps.
- A recipe an agent binds in the same second as the move's first attempt counts as the move's (it is confirmed only while still the untouched template).
- The gate probes only the pipeline's own activity: a hand-written watch that gathers `extra` through read tools does not run in a cycle without digests, auto tracks or inbox activity.
- A Retry while the daemon runs can double-scan one cycle (the daemon changes path at restart, as in C2).
- `tracks watch <target-id>` requires `--text` but has no such flag (pre-existing; follow-up).
- Turning off Track my threads also stops the watches (FEAT-01).
- A failed owner copy of Track my threads waits for a digest newer than the failed attempt; that mark lives in memory, so a daemon restart allows one more attempt.
