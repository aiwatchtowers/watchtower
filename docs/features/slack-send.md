# Slack send from the AI chat and the project terminal (2026-10-02)

- `send_slack_message` (`internal/tools/slack_send.go`, board #166; spec `docs/superpowers/specs/2026-10-02-slack-send-design.md`, plan `docs/superpowers/plans/2026-10-02-slack-send.md`): an External write tool on the `main` and `project` surfaces — not the target chat, not reaction, never a draft-only surface (AGENT-04). The model drafts in the owner's style from `get_writing_style` (a read tool over `workspace.style_profile`, registered in `buildToolRegistry` only, so dev-mode MCP is unchanged — DEV-01) and passes `channel` (`#name`, id, or a Slack link — a message link replies in its thread, a reply's link in the parent thread) or `user` (DM: id, handle, display/real name, email), plus `text` (≤ 4000 runes) and optional `thread_ts`/`account_id`.
- **Resolution is local and pinned at propose time** (Normalize): enabled, non-removed accounts; non-archived public/private channels or non-deleted, non-bot users. Zero matches or several inside one workspace → a `ValidationError` (no row). One match per workspace in several → stored `candidates`, no `target`; the card's **Send from** picker and `Ready` gate Approve. Execute never re-resolves (the PR #92 rule). A DM without a synced IM is opened at Execute (`conversations.open`).
- **Owner edits:** `Tool.Revise`/`Tool.Ready` + `Registry.Approve(ctx, id, patch)` — `watchtower actions approve <id> --patch '{"text":…,"candidate":N}'` saves the edit with the approval in one conditional update (`db.ApproveAgentActionWithArgs`: still pending AND args unchanged). Only `text` and `candidate` are editable.
- **Execute:** the pinned account must be enabled/not removed; namespaced mentions of that account (`<@2:U…>`) are rewritten raw, another account's fail the send; then `chat.postMessage` with the user token. Result `{channel_id, ts, url, label, workspace}`. A failure before `chat.postMessage` on every attempt so far (or Slack refusing the post outright: scope/auth/channel codes) carries `tools.SlackNotSentPrefix` ("nothing was sent: "); its Retry just sends. Otherwise a retry (row was `failed`) first reads the conversation since the proposal (thread replies, or up to 5 history pages; `has_more` past that counts as unknown) for the owner's message with the same text (compared after undoing Slack's storage form: `<url>`/`<url|label>` links, labelled mentions and special tokens `<#C…|name>`/`<@U…|name>`/`<!here|here>`, `&amp;`/`&lt;`/`&gt;`) and reuses it (`reused: true`); a failed or overflowing lookup fails the retry rather than re-posting.
- **Scope:** `auth.UserScopes` and `slack-app-manifest.json` gain `chat:write`; the token file records the granted scopes (`Token.Scope` from `authed_user.scope`). A recorded grant without `chat:write` fails at once; a legacy token (no recorded grant) is tried and Slack's `missing_scope`/`not_allowed_token_type` maps to the same error. Every such error carries `tools.SlackSendScopeHint` ("sign in again to grant send"), mirrored by Swift `SlackSendProposal.scopeHint`: the card then shows **Reconnect Slack** (`AppState.reconnectSlack` → `SlackAccountsViewModel.relogin`; its outcome is shown on the card). Slack's `invalid_auth`/`token_revoked`/`account_inactive` map to the same hint; `not_in_channel` and `channel_not_found`/`is_archived` say what to do. A sign-in whose grant still lacks `chat:write` prints a warning (the Slack app or the admin must allow it — signing in again will not). Settings → Slack's per-account button is now always shown (**Reconnect** for a healthy account). The live Slack app must list `chat:write` among its user scopes for the re-consent to grant it.
- **Project terminal (DEV-06 rule 3, amended):** `Tool.ProposeUnderDirectApply` lets this one External tool run in a direct-apply session as a **pending** proposal bound to the project (never inline; trust stays `ask`). The Desktop's Inbox strip shows its card — `AgentActionQueries.notProjectRow` hides a project's direct-apply audit rows but lets an External project row through (STRIP-01 changelog 2026-10-02); `ProjectNotificationPolicy` posts `actionAwaitsApproval` ("Send to Slack awaits your approval", watermark `Snapshot.lastActionID`, an older snapshot baselines silently) whose click (`type: agent_action`) opens the Inbox.
- Desktop: `SlackSendProposal` (WatchtowerCore, pure: recipient line, `canApprove`, `patch`, `reconnectAccountID`), `AgentActionCardView+Slack.swift` (`SlackSendEditor`: text editor + picker; editable only where the host wires `onApproveEdited` — the main chat and the Inbox strip), `AgentActionFeed.approve(_:patch:)`. `ReactionToolCatalog` names it "Send to Slack". The actions contract (Go `chat.ActionsContract` + Swift `AgentToolsContract`, fixture `actions_contract_main.txt`) lists the tool and the style rule on main only.
- v1 limits: no target-chat surface; a failed row cannot be edited before Retry; only synced channels/people are addressable; `@name` inside the text is not turned into a mention; the retry lookup knows Slack's link and entity forms only, so a message Slack rewrote otherwise (e.g. an emoji shortcode it converted) is not recognised and a retry would post it again; no Settings badge for an account that cannot send yet (the card is where the owner meets it).
