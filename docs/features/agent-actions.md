# Agent Actions — tool registry + controlled writes (2026-09-04)

- `internal/tools/` is the core tool **registry** (`Propose`/`Apply`/`SetTrust`/`List`); `internal/mcp/actions.go`'s `WithRegistry` chat-mode option is one **adapter** over it — a Go-owned tool loop for HTTP providers ("runtime B", mandatory follow-up below) will be a second adapter, not a rewrite.
- Two MCP entry points: `watchtower mcp` (dev mode, DEV-01, stays read-only/`query_only=ON`, no write tool, no `get_action`) vs `watchtower mcp --chat` (chat mode, launched only by the Desktop's `ai query --tools chat`, mounts the registry's write tools plus `get_action`) — chat mode's connection is **writable**, but only so the registry can record proposals: no read tool writes on it (AGENT-06).
- A write tool never touches its target on propose: `Registry.Propose` records one `agent_actions` row (`pending`); `Registry.Apply` executes exactly once, only from `approved`/`failed` (`applied`/`rejected` are terminal). "Exactly once" is a **claim**, not a post-hoc check: `Apply` CASes the row `approved|failed → executing` BEFORE running the tool, so of two overlapping applies the loser is refused before its side effect; a row stranded in `executing` by a killed process is reclaimed with `watchtower actions apply <id> --force`. Trust is per-tool, never global — `ask` by default, `execute` opt-in via `watchtower actions trust`; an `External: true` tool can never be set to `execute` (`SetTrust` refuses it and `Propose` re-checks, so a stale `tool_trust` row cannot grant it either).
- The write tools (`buildToolRegistry`, `cmd/actions_registry.go` — the ONE assembly point, pinned by `TestBuildToolRegistry_PinsWriteToolsReadToolsAndSurfaces`): `create_target` (main AI Chat only — the target chat's mandate forbids creating work outside its vertical line, TGT-BRIEF-01 axis 3), `create_jira_issue` (main chat + target chat, `External`, always behind Approve even with `execute` trust elsewhere), `connect_jira_board` (2026-09-09; main chat only, `External` — starts watching a board; profile bootstrap is best-effort and reports through `result_json.warning`), and the four Reaction Commands Wave 2 tools `create_track`/`create_idea`/`remind_me`/`brief_context` (`Surfaces: ["reaction"]` — reaction path only: they bind to the reacted message via REACT-02 and were never designed for chat, where they would create work outside a chat's mandate with no message to bind to; `remind_me` normalizes `remind_at` to UTC because both due readers compare the column as TEXT).
- CLI: `watchtower actions list|show|approve|reject|apply [--force]|trust|tools`; `watchtower jira create --project --type --summary [--description-file] [--label]… [--priority] [--json]` is the CLI face of `create_jira_issue`.
- Desktop: a shared `AgentActionFeed` drives per-conversation proposal cards (`AgentActionCardView`, Approve/Reject/Retry, no buttons while a row is `executing`); the main and target chat VMs generate a `turn_id` per send and pass `--tools chat --surface … --conversation --turn`, while draft-only VMs (situation/meeting/idea/track/setup) stay on `toolMode: nil` (AGENT-04).
- Contracts: `docs/inventory/agent-actions.md` (AGENT-01..06 — the model never writes, dev surface untouched, external tools never auto-execute, draft-only surfaces see no tools, apply exactly once, chat mode is writable only for proposals).
- **Mandatory follow-up (runtime B):** a Go-owned tool loop for OpenAI-compatible HTTP providers dispatching registry tools in-process; the existing `internal/mcp` read tools migrate into the registry once it lands.
