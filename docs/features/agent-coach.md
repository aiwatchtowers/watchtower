# Agent coach — weekly proposals to improve the owner's agent setup (2026-10-26, board #1120, Plan 1: the loop)

Spec: `docs/superpowers/specs/2026-10-26-agent-coach-design.md`. Plan 1 shipped the loop and the CLI; Plan 2 (2026-10-29, `docs/superpowers/specs/2026-10-28-agent-coach-screen-design.md`) shipped the Analytics screen, Home's row and the miner fold. The tuning chat (board #1517, `docs/superpowers/specs/2026-11-03-tuning-chat-design.md`, `docs/features/tuning-chat.md`) files **chat proposals** into the same table, adds ten destinations (five in the owner's home, five in a workbench's own repository) and measures each proposal on the agent its destination serves; see "Chat proposals (tuning chat)" below. COACH-01 in `docs/inventory/coach.md`.

Once a week the daemon reads what already exists (the owner's marks on spec review findings, first-round code review comments, the owner's lines to agents and chats, Analytics hints), asks the strong-tier model for concrete edits to the owner's own setup, validates them in Go and stores them as proposals. **Nothing is applied without the owner's Accept.** An accepted edit is measured for 14 days and gets a verdict.

## Tables (migration 00162)

- `coach_proposals` — one proposed edit: `fingerprint` (UNIQUE, from the destination and the change, so a declined or superseded edit never returns), `kind` (`add`/`cut`/`replace`), `destination`, `workbench_id` (NULL = global), `prompt_id`, `title`, `why`, `metric`, the whole `before_text`/`after_text`, `evidence` (JSON `[{kind,ref}]`, at most 12), `sources` (distinct sources, recomputed in Go), `status` (`open`/`accepted`/`declined`/`superseded`/`rolled_back`), `reverts_id` (a cut of an earlier no-effect edit), `baseline`/`baseline_n`, `verdict` (`works`/`no_effect`/`too_little_data`), `verdict_value`, timestamps.
- `prompt_additions` — owner-approved lines added to a Watchtower prompt (`prompt_id`, `text`, `proposal_id`).
- `spec_reviews.findings` — findings counted in the stored result when the review finished (`-1` = rows from before the migration, not counted); a re-run replaces `result`, so the first round's number is kept here.
- `spec_review_marks.state` gains `not_useful` (see the amended `docs/features/spec-review.md`).
- Migration 00187 (`00187_tuning_chat.sql`, one-transaction rebuild of `coach_proposals`): `origin` (`weekly`/`chat`, default `weekly`), `skill` (the skill a skill or overlay destination names, `''` otherwise), `conversation_id` (the tuning chat a `chat` proposal came from, `REFERENCES chat_conversations ON DELETE SET NULL`: deleting the chat keeps the proposal, listed and declinable), `written_branch` (`repo_*`: the branch Accept wrote on), `measure_from` (`repo_*`: when the daemon first saw the edit committed), and the `destination` CHECK widened by the ten new names. New table `skill_pack_overlays` — one owner-accepted line rendered into a shipped pack skill (`skill`, `text`, `proposal_id` `ON DELETE SET NULL`, `created_at`; index `(skill, id)`), shaped like `prompt_additions`.

## Metrics (`internal/coach.Measure`)

Over `[since, until)`, per workbench or (id 0) over every workbench with analytics on; numerators and denominators are summed, then divided once. A value with a zero denominator is `known: false`.

| Key | Definition | Per |
|---|---|---|
| `corrections` | interrupts + rejected calls | task (a leaf target, `agentreport` tasks attribution) |
| `task_hours` | agent hours | task |
| `task_cost_usd` | agent cost | task |
| `owner_loop` | owner time / active time | sessions |
| `spec_findings` | findings of the first review round of a spec | first-round spec review |
| `review_comments` | non-carried comments of a diff review's first round | first-round review |

Sessions starting at or after `until` are left out. With workbench 0 the agent metrics cover the analytics-on workbenches only, the two review counts every workbench.

**Per agent (board #1517, spec §4.7, ask #1132).** `Measure(main, al, workbenchID, since, until, agent)` takes the report's agent filter (`agentreport.AgentAll`, `claude`, `codex`; `BuildOverview` with that filter, `docs/features/agent-analytics.md`). A proposal's baseline (`Applier`) and verdict (`verdictOf`) are measured on `AgentFor(destination)`: Codex texts (`codex_skill_user`, `codex_agents_md_user`, `codex_rules_allow`, `repo_agents_md`, `repo_codex_skill`) on Codex sessions; the texts both agents read — `session`, `procedure` (both agents' briefs and `update_target`, owner ask #1196), `pack_overlay` and `repo_workflow` — on every session; every other destination (`chat` included: it reaches the AI chats, not an agent session) on Claude sessions. The weekly proposer's evidence (`hintSignals`) covers every agent (`agentreport.AgentAll`); only `coach status` filters (`--agent all|claude|codex`, default `all`; the Analytics pane passes its agent filter). `RemeasureMixedBaselines` re-takes, once per install, the baseline of every accepted proposal the judge may still judge on its destination's agent over the Accept's own window (before #1517 a Claude text's baseline could carry Codex rows, spec D58, ask #1152): a compare-and-set per row (`db.CASCoachBaseline`), so a verdict or rollback written meanwhile wins; done when the `db_maintenance` key `coach_baselines_per_agent` is written (at once with no `agentlog.db`; it waits for `agentlog.db`'s move out of `watchtower.db`). It runs at daemon start (`cmd/sync.go` `remeasureCoachBaselines`) and before each `Judge`, and no verdict is written until it is done (`errBaselinesPending`).

## Signals, gates, proposals

- Signals (28-day window, newest first, at most 400, each cut to 600 runes): `ask:<id>#<key>` (a comment mark = a real problem, a **Not useful** mark = noise; other marks and no mark are skipped), `round:<id>#c<id>` (first-round review comments), `s<id>`/`c<id>` (owner lines of a session or chat, the instruction miner's input), `hint:<id>@wb<id>` (an Analytics hint with an action). Owner asks and the time agents wait for the owner are not read directly: they reach the coach only through the Analytics hints (H4: "waiting for you" over 30 % of active time).
- Gates: at least 3 distinct sources per proposal (a hint counts as one source); at most 3 open proposals; no model call without a free slot or three sources; one open proposal per destination text (an Accept of one would supersede the other). Only weekly proposals count against the 3 slots (`weeklyOpen`): an open chat proposal takes no slot but still blocks a weekly proposal on the same text. A text is `keyOf(destination, workbench, prompt, skill)`: the skill is part of the key for the five skill destinations (`claude_skill_user`, `codex_skill_user`, `pack_overlay`, `repo_claude_skill`, `repo_codex_skill`), so two skills are two texts; `fingerprint` keeps its old format for every v1 destination.
- Validation (`coach.Validate`) in Go: evidence refs must exist, counts are recomputed, the destination must be allowed, `find` must match the current text once (whole lines), the result must fit the destination's budget (`instructions.MaxRunes` 1000 for owner texts; `prompts.MaxAdditionRunes` 600 and 300 per line for additions; `~/.claude/CLAUDE.md` current length + 400 runes, never past 4000). Owner text goes to the model on stdin only and never to a log (FILES-01).
- Prompt `coach.propose` v2 (strong tier, both providers); titles in `digest.language`. It sees the earlier proposals as OPEN, DECLINED, ACCEPTED, ROLLED BACK and NO EFFECT groups and is told never to repeat the first four in other words; its allow-rule list is the Go table word for word (`TestCoachPrompt_AllowTableMatchesGo`).

## Destinations

In v1: the global and per-workbench session instructions and target procedure, the chat text (`owner_instructions`, `projects.session_instructions`/`target_procedure`), prompt additions, `~/.claude/settings.json` `permissions.allow`, `~/.claude/CLAUDE.md`. The weekly pass (`Validate`, `textDestinations`) still names only these and **never** a repository file; `TestCOACH01_DestinationsAreNeverRepoFiles` holds it. The ten destinations below are proposed only from the tuning chat (`chatDestinations` and `repoDestinations`, checked by `ValidateChatProposal`).

| Destination | Text | Budget (`coach.BudgetOf`) |
|---|---|---|
| `claude_skill_user` | `~/.claude/skills/<skill>/SKILL.md` (`ClaudeSkillPath`) | `skillBudget`: current + 2000 runes, never past 20 000 (a skill already there may only keep its size or shrink) |
| `codex_skill_user` | the one copy Codex reads: `~/.agents/skills/<skill>/SKILL.md` or `<codexHome>/skills/<skill>/SKILL.md` (`CodexSkillPath`) | `skillBudget` |
| `codex_agents_md_user` | `<codexHome>/AGENTS.md` | as `~/.claude/CLAUDE.md`: + 400 runes, never past 4000 |
| `codex_rules_allow` | `<codexHome>/rules/default.rules` | none (append-only, the safe-rule table) |
| `pack_overlay` | the overlay lines of one Watchtower pack skill (`skill_pack_overlays`) | 1000 runes per skill, one line per row |
| `repo_claude_md`, `repo_agents_md`, `repo_claude_skill`, `repo_codex_skill`, `repo_workflow` | the workbench folder's `CLAUDE.md`, `AGENTS.md`, `.claude/skills/<skill>/SKILL.md`, `.agents/skills/<skill>/SKILL.md`, `.watchtower/workflow.md` (`RepoRelPath`, the only place the five paths are spelled) | `skillBudget` for all five |

`<codexHome>` is `Env.CodexHome` — an absolute `$CODEX_HOME` (`CodexHomeFromEnv`, set by `cmd`), else `~/.codex`.

**Prompt additions.** A coach edit never changes a template or sets `customized`: `prompts.Store` appends the prompt's additions as one `=== OWNER PREFERENCES (approved by the owner) ===` block at resolve time, so shipped prompt upgrades keep reaching the owner. An addition is one line, no `%` and no `{{`/`}}`. Prompts a built-in automation owns are skipped.

**Allow rules** use the coach's own exact-match table (`SafeAllowRule`): `Bash(<verb>:*)` for `cat`, `ls`, `grep`, `head`, `tail` and the exact toolchain commands `go test`/`build`/`vet`, `swift test`/`build`, `cargo test`, `npm test`, `pytest`; nothing else (no `sed`, `find`, `rg`, `make`, `npm run`, no arguments). The list may only grow through Accept, and a proposal must add at least one rule it does not have. Residual risk, accepted by the owner: a build/test rule runs project code by design, so `go test -exec`, `go build -toolexec` and `-vettool` reach any program without a prompt; every rule needs Accept, and unprompted rules apply anywhere on the machine.

**`~/.claude/CLAUDE.md`** is read only as a regular, UTF-8 file up to 256 KB (a symlink, special file, larger or non-text file is never targeted and gets no cut), edited as an exact-text replace through an atomic write that re-reads the file just before the rename.

**The owner's skill and Codex files** (`internal/coach/userfile.go`, the same `textFile` rules as CLAUDE.md, `claudemd.go` now one kind of it): a regular UTF-8 file up to 256 KB; no symlink at the file or at any folder below the home root (the roots `~/.claude`, `~/.agents` and the Codex home may themselves be links to a real folder, D71); atomic replace with a re-read before the rename (a changed file is `ErrStale`, the owner's text kept). A refusal names the destination's label, never a path or text (FILES-01). A skill file must exist (never created, `errSkillNotFound`), its name must match `validSkillName`, and a file carrying the devpack marker is a pack copy, refused ("propose a pack_overlay"). A Codex user skill present in both `~/.agents/skills` and `<codexHome>/skills` is refused — "Codex sees this skill in two folders (~/.agents/skills and ~/.codex/skills) — remove one copy first." (the real Codex home path; Codex loads both and merges neither, owner ask #1202). `AGENTS.md` may be missing (read as `""`) and is created by Accept (folder 0700, file 0600); undoing or rolling back a created one writes it back **empty**, never removes it.

**Codex rules** (`codexrules.go`): the safe-rule table's twin `codexSafeAllowPatterns` (`TestCodexSafeAllowTable_EqualsClaudeTable` keeps the two equal), each line exactly `CodexRuleLine` — the bytes Codex's own "always allow" appends, e.g. `prefix_rule(pattern=["go", "test"], decision="allow")` (`CodexSafeAllowRule` is exact equality). The file must exist (`errCodexRulesMissing`); the text may only grow (`find` must be empty), each appended line a table rule not yet present. Rollback removes one occurrence of each line its proposal added and nothing else.

**Pack overlays** (`pack_overlay`, `internal/devpack/overlay.go`): an owner line is rendered into a shipped pack skill (`devpack.PackSkillNames`: the pack's skills, the core workbench skill and the flow skill) under `## Owner additions (approved by the owner)` (`OverlayHeading`), right after the frontmatter (`devpack.Render`); the sidecar digest is the rendered one, so an overlay is not drift and a pack upgrade carries it. Accept and Rollback re-render every installed copy (`Applier.rerenderPack` over each workbench's `.claude/skills` and `.agents/skills` and `~/.claude/skills`; a copy edited by hand is left and counted drifted, a missing one is not created; a folder that fails is logged as a fingerprint and rendered at the next `integrate claude-code` or workbench open/resync, the other re-render points — there is no daemon drift pass). When the overlay rows cannot be read, workbench setup reports pack copies instead of writing them (`WorkbenchInstallOptions.OverlaysUnread`), so no copy loses its owner lines over a database error. `coach accept --json` counts the copies (`pack_copies_updated`, `pack_copies_drifted`).

**Workbench repository files** (`repo_*`, `internal/coach/repofile.go`, spec §4.3a, D66/D67, owner ask #1165): chat-only, per workbench (`workbench_id` required and live; `prompt_id` refused; `skill` required for the two skill kinds). The folder is the workbench's own `projects.folder_path`, never a session worktree; the `textFile` rules apply with that folder as the root below which nothing may be a symlink. `CLAUDE.md`/`AGENTS.md` may be missing and are created by Accept (0644, the folder must exist); the skills and `workflow.md` must exist; a pack copy is refused as above. **Watchtower never runs a git write**: `internal/coach` imports no `workbenchgit` and no `os/exec`; it reads git state through the `Applier.RepoState`/`Applier.RepoBranch` and `Env.RepoState` seams, which have no default (nil → refused, `repo_* accept: git state reader not wired`) and which `cmd` fills (`coachRepoState`/`coachRepoBranch` over the read-only `workbenchgit.PathStatus` and `workbenchgit.ReadStatus`). `ValidateChatProposal` refuses a folder that is not a git work tree (`RepoNotGitLine`: "This workbench folder is not a git repository: Watchtower changes files here only where you can review and commit the change."). Accept checks, in order: the workbench row ("workbench N not found"), the folder ("workbench folder not found"), the path's git state (not git → `ErrRepoNotGit`; any `git status` entry — modified, staged, untracked, conflicted → `ErrRepoDirty`, "`<path>` has uncommitted changes — commit or discard them, then press Accept again."; a failed read refuses, never counts as clean), then the read, the `before_text` compare, the atomic write and the status compare-and-set (a row gone meanwhile — the workbench deleted — undoes the write). It records the branch it wrote on (`written_branch`; `detached:<short sha>` on a detached HEAD; a failed branch read leaves `""` and never undoes the write). The owner reviews and commits the change. Rollback runs no git check (the file is expected to show Accept's change, committed or not); a `CLAUDE.md`/`AGENTS.md` Accept created is deleted again while it still holds Accept's text, else `ErrChangedSince` and kept (ask #1169). Errors name the relative path, never the folder (FILES-01). Guards: `TestCOACH01_RepoFilesOnlyInTheWorkbenchFolder`, `TestCOACH01_NoGitWrites` (no git import in coach; the coach and tuning callers in `cmd/coach*.go`, `cmd/tuning*.go`, the daemon's commit check and `internal/tuning` call only `PathStatus`, `ReadStatus` and `FileAtHead`, each with the read-only verbs `status`, `rev-parse`, `show`), `TestCOACH01_NoGitWrites_ScansTheTuningPackage`; the home ones stay under `TestCOACH01_HomeDestinationsStayUnderHome`.

## Chat proposals (tuning chat)

The tuning chat's `propose_tuning_edit` (`internal/tuning/tools_propose.go`, `docs/features/tuning-chat.md`) sends a `coach.ChatEdit` (destination, workbench, prompt or skill, kind, `find`/`replace`, title, why, metric, the refs it cites with `c<conversation>`) to `coach.ValidateChatProposal(ctx, d, e, env)`, which reads the destination's current text (`ReadText`, also used by the tuning read tools), applies the edit in whole lines and returns the proposal ready to insert, or a refusal (`errors.Is(err, coach.ErrRefused)`, `Error()` the plain reason the chat shows as is). Against the weekly `Validate`: no 3-source floor and no 3-open cap; the destination must be in `chatDestinations` or `repoDestinations`; arguments must fit the destination; a prompt must take additions (`PromptAdditionRefusal`: unknown, owned by a built-in automation, or `!prompts.TakesAdditions`); `find` must match once and cover whole lines; the allow destinations only grow; the result must fit `BudgetOf` and `ValidateAfter`; a known fingerprint is refused ("already proposed as #N (status)"), and so is a text with any open proposal ("proposal #N is already open for this text — decide it first"). `db.InsertChatCoachProposal(p, convID, now)` writes it with `origin = 'chat'` in one short transaction that rechecks the one-open-per-text rule (`ErrCoachTextBusy`) and maps a deleted conversation to `ErrConversationRemoved` (nothing filed); a fingerprint conflict returns `0, nil`. Accept, Decline and Rollback are the same for both origins.

## Accept, decline, rollback, verdicts

- **Accept** (`coach.Applier`): the destination must still hold the proposal's `before_text` (else the proposal is `superseded`, `ErrStale`); an owner text is written by compare-and-set; the baseline of the proposal's metric over the previous 14 days is stored; if the status write fails the destination is put back. "Edit then accept" passes the owner's whole text, checked by the same rules.
- **Decline** is for good (the fingerprint stays).
- **Rollback** restores the before-state when the destination still holds the accepted edit; otherwise it returns a diff and `ErrChangedSince` until `--force`. A prompt loses only the additions this proposal made; the allow list loses only this proposal's rules (it is not a byte restore: Claude Code writes the file too).
- **Verdict** (`coach.Judge`, 14 days after Accept, retried to 42 days): under 5 sessions or no baseline/value is `too_little_data`; a value at least 10 % below the baseline is `works`; anything else is `no_effect`. A baseline `<= 0` is `too_little_data`. A `no_effect` edit gets one mechanical cut proposal (no model call) when a slot is free, except for allow rules and repository files (use Rollback; see the judge's cut below). The screen wording is "since this edit", never "because".
- **Repository edits are measured from the commit** (spec §4.3a, D68): a `repo_*` proposal's window starts at `measure_from`, which the daemon sets the first time the file at the workbench folder's HEAD equals the accepted text (`coachCommitCheck`, below). Not committed within 30 days of Accept (`repoCommitWait`; a commit seen later counts as never) gives a final `too_little_data`. Every other destination's window still starts at the Accept.
- **The judge's cut** (`writeCut`): only weekly proposals count against its slot (`weeklyOpen`), so open chat proposals never block it; it checks the same text by `keyOf` with the skill; no cut for `claude_settings_allow`, `codex_rules_allow` or any `repo_*` file (the verdict is still stored); an unreadable destination (unsafe file, missing skill, missing rules file, a Codex skill in two folders) files nothing. A cut of a chat edit is a weekly proposal (`origin` `weekly`, no conversation) carrying the original's destination and skill and today's text (D64).

## Daemon and CLI

`phaseCoach` runs after the history backfill. Once a day per daemon process it runs `coachCommitCheck`: for each accepted `repo_*` proposal with no `measure_from` (`db.ListRepoProposalsAwaitingCommit`), the read-only `workbenchgit.FileAtHead` (`git show HEAD:<rel>`, outside any write transaction) in the workbench folder; equal to the accepted text → `db.SetCoachMeasureFrom` (a compare-and-set on `measure_from IS NULL`, its own short write); a folder gone, not git or unreadable skips the row that day (logged with ids only). Then, once 7 days have passed since `<workspace>/last_coach.txt` (no catch-up of missed weeks), it takes the coach lock, folds the old instruction suggestions in (below), judges, then collects and proposes. There is no plan-limit gate (ask #655); no `agentlog.db` handle skips judging; the stamp is written only when proposing ran to completion (a model call skipped for want of slots or sources counts): a collect or model error writes `<workspace>/last_coach_failed.txt` instead and is retried a day later (not every cycle; a later success removes it), a cancelled cycle writes neither and the next cycle runs again, and a judging error alone does not hold the week. Logs carry counts only.

`watchtower coach status|proposals|accept|decline|rollback|run`, each with `--json` (a failure prints `{"ok":false,"error":…,"code":…}` and exits non-zero; `code` is `stale`, `changed_since`, `state_changed`, `busy`, `refused` (`coach.ErrRefused`), `dirty` (a repository file with uncommitted changes), `not_git` (a workbench folder that is not a git work tree) or `failed`; with `--json` the object is also written as one JSON line on stderr (Execute() prints the error as prose after it; a reader takes the last line that decodes as a JSON object), rollback adds `diff`). Pinned keys: `status [--days N] [--agent all|claude|codex]` (1..90, default 14; the previous period is the same length; `--agent` filters the agent metrics, default `all`) — `ok`, `period{since,until}`, `metrics{corrections,task_hours,task_cost_usd,owner_loop,spec_findings,review_comments}` each `{value,n,known,previous}`, `open`, `last_run`; `proposals --status open|accepted|declined|all` — `ok`, `proposals[]` with `id`, `title`, `why`, `destination`, `workbench_id`, `prompt_id`, `kind`, `metric`, `before`, `after`, `evidence[{kind,ref}]`, `sources`, `status`, `created_at`, `decided_at`, `baseline`, `verdict`, `verdict_value`, `verdict_at`, `reverts_id`, `budget` (rune budget of the destination, `0` = none; `coach.BudgetOf`, the number `Validate` uses), and since #1517 `origin`, `skill` (`""` for a destination without one), `conversation_id` (null for weekly proposals and deleted chats), `written_branch`, `measure_from` (null until set) and, on **open** `repo_*` rows only, `folder_branch` (the branch checked out in the workbench folder now, read once per workbench per call through `workbenchgit.ReadStatus`; `detached:<short sha>`; `""` when the folder is not a git work tree, is missing or the read failed); `accept|decline|rollback` — `ok`, `id`, `status`, and on `accept` also `pack_copies_updated`, `pack_copies_drifted`, `written_path` (relative, `repo_*` only) and `written_branch`; `run [--dry-run]` (holds `<workspace>/coach.lock` — `fsutil.TryLockFile` — while it judges and proposes; the daemon's weekly pass takes the same lock and logs `coach: busy, skipped`) — `ok`, `dry_run`, `judged`, `cuts`, `written`, `skipped`, `proposals`, `judge_error` (`""` unless judging failed; proposing goes on, as in the daemon). Keys are only added. A refusal under an agent prints the same failure object with `--json`. `accept --stdin` reads the owner's edited text and refuses an empty one (it never falls back to the proposed text). The human output of `proposals` and `run` shows each proposal's change: the removed lines with `-`, the added ones with `+`. `accept`, `decline`, `rollback` and `run` are refused under an AI agent's markers (AGENT-07's `refuseUnderAgent`, first) and otherwise run only after the owner confirms them in the running Desktop (`confirmWithOwner`, ask #659; the window shows the proposal, its change and an edited accept's text; `run` says what the pass does; `run --dry-run` writes nothing and needs no confirmation, only the marker refusal). The CLI does not meter its model usage.

## The instruction miner folds in (Plan 2, ask #722)

The daily `phaseInstructionSuggestions` and its stamp are gone; the coach already reads the same owner lines (`s<id>`/`c<id>` signals). `coach.ImportSuggestions(db, digest.language, now)` is a one-shot fold, run under the coach lock right before judging, in `phaseCoach` and in `coach run` (not `--dry-run`): in one short transaction (no model call) the open `instruction_suggestions` rows with `moved_to IS NULL`, newest `last_seen_at` first, fill the free slots (3 − open proposals) as open `add` proposals to the same text (`field` → destination, `workbench_id` → workbench, after = before + the line through the same `applyEdit`/`ValidateAfter` as the model's proposals, title = the text cut to 80 runes, `why` "You said this in N sessions" / "Ты говорил это в N сессиях", metric `owner_loop`, evidence `[{kind:"suggestion", ref:"sg:<id>"}]`, `sources` = `session_count`). A row whose destination already has an open proposal (accepting one would supersede the other), that fails validation, or whose fingerprint is known, is retired. Every open row gets `moved_to` (migration 00166): its proposal id, or `-1` (retired; its owner lines stay coach signals). Nothing writes new suggestions, so after its first run the fold is a no-op and old suggestions never crowd later weeks. A moved row is decided only through the coach: `instructions suggestion add|dismiss` refuse it (`db.ErrSuggestionMoved`, "moved to the coach (proposal #N)") and `instructions show` no longer lists it. Suggestions the owner added or dismissed keep blocking their texts: the Proposer drops a proposal one of whose added lines equals (trimmed, case-folded) such a text.

## v1 limits

- The verdict is judged on the whole metric over the scope, not a narrower measure of the edit (correlation, not causation).
- No cut for allow rules; the owner uses Rollback of the original.
- `settings.json` top-level and `permissions` keys are re-sorted when written; a rolled-back prompt addition returns without its `proposal_id`; two concurrent rollbacks can duplicate restored lines; a small race remains between the re-read and the rename.
- `~/.claude/CLAUDE.md` has a hard ceiling of 4000 runes (`claudeMDMaxRunes`, ask #659): an edit may grow the file by at most 400 runes and never past 4000; a file already at or over 4000 may only keep its size or shrink, so there the coach can only cut. The owner's own edits are not limited.
- `~/.claude/CLAUDE.md` is written by atomic rename: hard links, extended attributes and ACLs on it are not kept. Rolling back an edit that created the file leaves an empty file (a created and an existing empty file cannot be told apart).
- The ask level, personal methodology overrides and disabling skills are out of v1.
- There is no Settings → Prompts view of additions; the Accepted edits log is where they are undone.
- A declined carried suggestion can be proposed again after its destination text changes (its fingerprint then differs).
- The one-shot fold retires extra suggestions for a destination that already has an open proposal; their lines stay coach signals.
- Review-round and chat evidence on a card is plain text (no open-review link yet).
- A model proposal cites evidence only from the collected signals, so the `suggestion` evidence kind appears only on folded proposals.
- `coach run` does not meter usage and `coach` never moves agentlog rows: a CLI-only install before the daemon's move measures an empty agentlog.
- Allow-rule table contents and risk: above. A baseline needs analytics on for the workbench.
- Tuning chat (#1517): a repository edit's commit is seen only at the workbench folder's HEAD, by the daily check; a commit on another branch or in a session worktree that never reaches the folder's HEAD is not seen. The 30-day "not committed" verdict also covers a folder whose git read fails every day of the 30 (gone, not git, unreadable): such a row ends `too_little_data` without a measure.
- `workbenchgit.FileAtHead` reads the file at HEAD whole, with no size cap (the working-tree file is capped at 256 KB, the committed one is not).
- No judge's cut for a Codex rule or a repository file; the owner uses Rollback.
