# Slack Full — entry into Full and the retired shared app (2026-11-18, #1709, plan B)

Spec `docs/superpowers/specs/2026-11-14-slack-full-and-live-design.md` §5–§6 and the screens spec `2026-11-15-slack-full-live-screens-design.md`; plan `docs/superpowers/plans/2026-11-17-slack-full-plan-b.md` (decisions A1–A23, approved in asks #1414/#1438; owner rulings #1425, #1525, #1572, #1577). A company gets Watchtower's Slack app into its own workspace with one paste of a configuration token; every colleague connects from the app's About page, a pasted code or the MDM key `SlackApps`, with PKCE and no client secret; rotated tokens refresh on their own; accounts on the retired shared public app keep syncing under a banner and move to Full on the same row. Live (the owner's Claude/ChatGPT connector) is [slack-live.md](slack-live.md); accounts and sync are [slack-multi-account.md](slack-multi-account.md). Contracts: SLACKFULL-01, SLACKFULL-02 (new), SLACK-01 untouched, SLACKMODE-01 (`docs/inventory/slack-accounts.md`); POLICY-01/02 gain `SlackApps` (`docs/inventory/policy.md`). User guide: `docs/guide/features/slack-full.md`.

## Which account is on the shared app

- One rule, no build flavor in app code (ask #1425): `slackmode.SharedApp(a, retiredID)` = `retiredID != "" && a.ClientID == retiredID && a.CompanySlug == ""`, with `auth.RetiredSharedClientID` an ldflag only the public profile sets. Every other id — a setup app, an MDM or link id, the corp build's baked app — is a company app (Full). An empty `client_id` is never shared. An account tied to a company bundle is never shared either (ask #1644): the corp build's baked app *is* the retired public app (one client id), so after the company bridge the public build sees tied corp rows on the retired id and must list them as the company's app (no banner, `relogin: connect`) — `TestSlackAccountSharedApp_CompanyTiedIsCompanyApp`, `TestBridge_PublicSlackOnRetiredIDStaysCompanyApp`. Slack app setup's own lookup of the team's company app (`slackapp.Runner.companyAccount`, for `create`'s adopt offer and `adopt`) uses the same rule — `TestAdopt_CompanyTiedRetiredIDIsACompanyApp`.
- **Backfill (A17):** `slackmode.BackfillClientIDs` fills empty ids from `BackfillSource()` — the baked/env client id (no secret needed), else `RetiredSharedClientID`, else nothing — run by `slack accounts`, the sync start (not `--users-only`) and every connect (`connectSlackAccount`, `writeConnectedAccount`).
- **`slack accounts --json`** → `{"builtin_app": bool, "accounts": [{id, team_id, team_name, label, status, enabled, client_id, shared_app, relogin, home_team_id}]}`. `home_team_id` is the team a connect Re-login signs into: the home team of the account's stored data (`db.SlackAccountHomeTeam`, the legacy workspace row for a moved account #1), else `team_id`. `builtin_app` = `auth.BuiltinApp()` ok (a baked or env client id **and** secret, A8). `relogin` (`slackmode.Relogin`, first match wins): an untied row on the retired id → `builtin` while the build bakes it, else `move` (a company-tied row on it falls through to the rules below); the builtin id, or `''` while a built-in app exists → `builtin`; otherwise `connect`. Removed rows are listed with `shared_app: false`. Pinned by `TestSlackAccountsJSON_*`.
- **Release guard:** the `retired-slack-id-check` block of `scripts/build-app.sh` refuses a public release (flavor `""`/`dev`, not `--dev`, `NOTARIZE_PROFILE` set) without `RETIRED_SLACK_CLIENT_ID`, and any build whose id holds whitespace (`scripts/tests/test-build-app-retired-slack-id.sh`, run by `make test-scripts`).

## The connect flow (`internal/slackconnect`, `cmd/slack_connect*.go`)

- **Input:** the link `http://127.0.0.1:18551/slack/connect?team=<T>&client=<id>` or the code `<T>:<id>` (`ParseConnectInput`; team `^[TE][A-Z0-9]{2,}$`, client `^[0-9]+\.[0-9]+$`; Swift twin `SlackConnectTarget.parse`). `ConnectLink`/`ConnectCode` build them for the About text.
- **Port 18551 has one owner (A1, A3):** while the Desktop runs, its child `watchtower slack connect serve` holds `127.0.0.1:18551`; without the Desktop, `slack connect (--team T --client C | --code CODE) [--account N] [--no-open] [--app-return] [--json]` binds it one-shot (busy → exit 2, "port 18551 is busy (is Watchtower open? connect from Connections → Slack)"). `TestOAuthPortRanges_Disjoint` keeps 18551 outside every other listener's range.
- **The listener** answers only `GET /slack/connect` and `GET /callback`, `Host` exactly `127.0.0.1:18551` (421 otherwise; 404/405 for other paths/methods, no body), never serves files. `/slack/connect` answers at once with "Switch to Watchtower to confirm" (`oauthpage.SwitchToApp`, A2) and emits `link`; nothing reaches Slack before **Connect** (SLACKFULL-01). A callback with no live flow gets `oauthpage.Stale()`.
- **`Registry`:** one flow at a time (`ErrFlowRunning`, the running flow's id returned for the `busy` event); a link flow needs `Confirm`, a paste/MDM/Reconnect/setup start skips it; no deadline (A22): a confirmed flow waits until its callback, **Cancel** or quit, and the Desktop shows "Waiting for Slack since N min" past 5 minutes. A wrong `state` leaves the flow waiting; a replayed callback finds no flow; **Cancel** during the exchange wins (the grant is dropped, not revoked). The exchange (`oauth.v2.access`) sends `client_id`, `code`, `code_verifier`, `redirect_uri` — no secret (`TestExchange_NoSecretInForm`), redirects refused.
- **Serve wire (JSON lines):** stdout `listening`, `port_busy` (then exit 3), `link`, `browser`, `connected{account_id, team_id, team_name, rebound_from}`, `failed{reason: team_mismatch|other_user|denied|cancelled|exchange|policy|purge_running|other}`, `busy` (a `start` refused: another flow runs), `link_busy` (a link refused while a flow runs — never the answer to a start); stdin `start{team_id, client_id, account_id?}`, `confirm`, `cancel`; stdin EOF closes the listener and exits 0. A `failed` with `"flow":""` answers the latest start. The golden `internal/slackconnect/testdata/serve_events.jsonl` is written from the real serve loop (`TestSlackConnectServe_WireGolden -update`) and decoded by Swift `SlackConnectListenerHostTests.testDecodesEveryEvent`.
- **The write (`writeConnectedAccount`, A6, ask #1425):** target = `--account`/`account_id`, else the team's live row, else a new row (an explicit target while another live row holds the team is refused). Before any write: policy, the grant's team against the target (`team_mismatch`), the running purge, `auth.test` identity, the home-team check and A18 (another Slack user → `other_user`, "signed in as someone else; nothing was changed"). Then under the token lock: the atomic token save (new tokens, `client_id`, `app_id`), then the row (`SetSlackAccountApp`, refresh expiry, auth `ok`). Data, watermarks and the account id stay; nothing is soft-removed; the old token is dropped, not revoked (A21). A crash between file and row is repaired by `LoadFresh`. A new row is rolled back with its token on failure.
- **Re-login:** `slack login --account N` with `relogin: connect` runs the one-shot PKCE flow on the row's client id (no secret) into the account's home team (`home_team_id`). The Desktop never runs that while its child holds the port: `relogin` `connect` → `start` on the child with `home_team_id` (A7, A14), `move` or `connect` with no client id → the connect section. The legacy `auth login` (account #1 through the build's app) refuses an account #1 whose `relogin` is `connect` (pointer to `slack login --account 1`) or `move` (pointer to the connect link or code), so it never overwrites a company app's client id and rotating token; `connectSlackAccount` applies the same refusal to the account it actually writes, again under the token lock and before any of its writes (`slackBuiltinSignInRefusal`; the token file's non-empty `client_id` wins over the row's), whichever account a builtin sign-in resolved to.
- **Policy:** `slack connect` is wrapped by `applySourceGuards`; `slack connect serve` checks the policy itself at every link, start, confirm and write (`sourceGuardedInside`, proven by `TestSlackLinkConnect_PolicyBlocksSlack`).

## Token refresh (`internal/slackauth`)

- `LoadFresh(ctx, workspaceDir, db, accountID, refresh, now)` is the pre-use check of every token reader (`wireSlackSyncers`, the Slack sender factory, reaction commands, `slack backfill`, `repl /sync`) and runs for every enabled account at the start of each daemon cycle, also when the adaptive cadence skips its run (A12). A token without a refresh token is returned as is (the shared app, old rows).
- Due when the access token has < 1 h left or the refresh token < 7 days (`refreshAhead`, `refreshTokenAhead`). Under the lock it re-reads the file, repairs the row from the file's non-empty `client_id`/`app_id` (an empty value never blanks the row), checks again, refreshes (`grant_type=refresh_token`, `client_id`, `refresh_token`, no secret), saves atomically (one retry), then writes `refresh_token_expires_at`. Unstated lifetimes: a new access token gets 12 h, a new refresh token 30 days (`IssuedExpiries`, which the connect's grant uses too: a token without a refresh token gets no assumed expiry). The file records `refreshed_at`; an expiry a refresh inside its window left where it was (Slack kept the token or stated no lifetime) is not due again until that expiry passes (an expired token is always refreshed again), so no read calls Slack meanwhile. The caller's ctx bounds only the lock wait.
- `invalid_refresh_token`/`token_revoked` → row `error` "Sign in again: the Slack sign-in expired" (`ReloginMessage`) and `ErrReloginNeeded`; the daemon skips that account's run until a new sign-in.
- **Writers:** every Slack token-file write or delete runs under the per-account flock (`withSlackTokenLock`, one minute): `connectSlackAccount`, `removeSlackAccount` (refresh a due token with `LoadFreshHeld`, revoke and delete in one section; a failed refresh revokes what the file holds), `ensureLegacySlackAccount`, `writeNewSlackAccount`/`writeSlackGrant`, `LoadFresh`, the purge. `TestSlackTokenWriters_AllLocked` walks the AST of `cmd/` and `internal/` and fails on any other call site.

## v1 limits and follow-ups

- **Corp build:** keeps its baked app until plan B Task 18; its accounts are Full throughout. A build that bakes the corp app refuses to adopt it (`builtin_app_pkce_deferred`), so the corp admin adopts with PKCE only together with the Task 18 build: adopting earlier would turn PKCE on under colleagues whose build still signs in without it (review M1, Task 18 gate). Plan B and Task 18 ship in one release (ask #1632): the corp profile drops `WATCHTOWER_OAUTH_CLIENT_SECRET` and keeps `WATCHTOWER_OAUTH_CLIENT_ID`. The id alone is no built-in app (`auth.BuiltinApp` needs id and secret, so `builtin_app` is false and nothing answers `builtin_app_pkce_deferred`) but still feeds the A17 backfill (`slackmode.BackfillSource`), so old corp rows get the corp id and Re-login runs `connect` (PKCE) — `TestSlackAccountsJSON_CorpIDWithoutSecret`, `TestAppSetup_CorpIDWithoutSecretNotDeferredCLI`. A secret-less exchange on an app without `pkce_enabled` answers `bad_client_secret` (spike), so the admin runs adopt `--enable-pkce` as soon as the release ships: until then new sign-ins and Re-login on the new build fail; afterwards only new sign-ins on older builds fail (fix: update). Tokens already issued keep working (Verified live 1). The release guard (`retired-slack-id-check`, A15) refuses any release with `WATCHTOWER_OAUTH_CLIENT_SECRET` set and a public release that sets any `WATCHTOWER_OAUTH_CLIENT_ID` (a stale id would become the backfill source for shared rows); a corp release with the id and no secret passes.
- **Adopt turns on PKCE (Task 16):** adopt sets `oauth_config.pkce_enabled` with `--enable-pkce` — one-way on Slack's side (undo only through Slack support), required for the secret-less exchange; Slack may ask colleagues already connected to allow Watchtower again, and the adopt body says so (screens §3.2).
- **Port strictness (A9):** Slack matches the redirect port exactly, so with 18551 busy neither the link nor a paste can finish; the owner must free the port.
- **Approval:** Slack sends no callback for an install request, so the setup's approval row never appears (`SlackSetupConnector` never answers `approvalRequested`); a waiting flow stays on the browser step until **Cancel**.
- **`--app-id`/`--attach`** trust the ids the owner copies: Slack offers no API tying an App ID to a client id.
- **The banner names only the first shared-app account**; every flagged row has its own tag.
- **The legacy Workspace block** keeps the label **Reconnect Slack** where account rows say **Move to Full**; the press routes the same way.
- **A refresh that succeeds and then fails to save** loses the rotated refresh token on Slack's side; the next use shows Re-login.
- **Follow-up:** `slack accounts --json` runs on every Desktop accounts refresh and so runs the A17 backfill `UPDATE` each time; it should skip it when no row has an empty `client_id`.
- **Follow-up:** `notCreatedCodes` and the `not_allowed` code (`restricted_action`) are our list, not Slack's documented set.

## Verified live (2026-11-19, target #1915)

Run on a throwaway app in the test workspace (no PKCE, `token_rotation_enabled: false`, then PKCE turned on through `apps.manifest.update` as adopt does):

1. A user token issued with the secret before PKCE was turned on still answers `auth.test` after it.
2. With PKCE on, a sign-in without PKCE on a loopback redirect is refused on Slack's page: "Must use PKCE to redirect to a non-web URI" (review M1 confirmed).
3. Before PKCE is on, Slack's authorize page accepts PKCE parameters and returns a code, but the secret-less exchange answers `bad_client_secret`.
4. After PKCE is on, the secret-less PKCE exchange succeeds and returns a rotating grant (`expires_in` 43200 and a refresh token) although the app had token rotation off. A refresh returns a new access token and a new refresh token; the previous refresh token still worked once right after the rotation (Slack's grace period).

## Unverified live (post-merge E2E, ask #1594)

1. Whether a refresh token's 30 days are absolute from the first grant or slide with each refresh (the refresher assumes 30 days from each new refresh token). If Slack ever keeps the refresh token and states no lifetime, an access token it also kept is refreshed again on every read once it has expired (`expiryDue` retries past expiry; review ruling, verify round 2): harmless while Slack rotates as observed, a refresh per read if it does not.
2. End to end with the app: create → connect → a 12-hour refresh → Re-login.
3. The corp app's connect (PKCE) Re-login on the Task 18 build needs the loopback redirect `http://127.0.0.1:18551/callback` registered on the app and `pkce_enabled` on. Adopt adds the redirect only together with PKCE: without `--enable-pkce` it changes nothing on an app without PKCE (`needs_pkce_consent`). So the corp admin's adopt `--enable-pkce` right after the one release (ask #1632) is the single step that makes the new build's sign-in work; the gap between the release and that step blocks new sign-ins and Re-login on the new build only, and after it only new sign-ins on older builds fail (Verified live 2).
