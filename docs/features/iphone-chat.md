# AI chat on the iPhone, over the relay (2026-11-15, board #1791)

Spec: `docs/superpowers/specs/2026-11-15-iphone-chat-design.md` (approved; owner decisions in ask #1340, §13 lists what changed in the code). Plan: `docs/superpowers/plans/2026-11-15-iphone-chat.md`. Guide: `docs/guide/features/iphone-chat.md`. Contracts: CHAT-01/02/03/05 and LIVE-01 amended in `docs/inventory/chat.md`. Protocol: `docs/superpowers/specs/2026-10-31-hub-phone-protocol-design.md` §6.2, §7.2, §9.

The phone gets a **Chats** tab: the same conversations as the Mac's AI Chat (list, search, pin/rename/delete with Undo, the whole history by paging, branches, regenerate, edit, attachments, quote-reply, approvals, artifacts, sources), a turn started on the phone runs on the Mac through the Go hub, and a turn started on the Mac streams to the phone. Relay only: on iCloud the capability is off.


**Superseded in part by the unified chat (2026-11-16, board #1822, [unified-chat.md](unified-chat.md), spec §9.2).** D1 (the writer is the lease holder's store), D5 (the lease), D6 (the hub's separate pool of 2), D11 (the Mac's foreign-turn view and the polled 1 s re-read), D13 (the `chat_lease` heartbeat flag and `chat_reason=desktop_too_old`) and D18 (the Desktop's own pool beside the hub's) no longer hold: one Go engine in the daemon is the only writer, runs one pool of 3 for the Mac and the phone, and streams every turn live to both with the normal Stop; the phone draws its conversation with the shared `ChatUI` and sends through `RelayChatClient`. The bullets below that describe the lease, the hub runner and the Desktop path are kept as history and marked.
## Architecture

- (Superseded: the engine keeps claiming and releasing it as owner `hub`, id `chatengine`, for one release, then the table is dropped. The turn lock is in memory.) **One turn, one writer: the lease.** Migration `00189` `chat_turn_leases` (one row per conversation: `owner` desktop|hub, `owner_id`, `turn_id`, `heartbeat_at_ms`, `cancel_requested_at_ms`). Claim is a conditional upsert inside the owner-row transaction (`BEGIN IMMEDIATE`, first commit wins); a lease is stale after 60 s without a heartbeat (`ChatLeaseStaleMS`; heartbeat every 15 s); release and Stop are scoped by `turn_id`; a takeover clears a cancel. `internal/db/chat_lease.go` ↔ Swift `ChatLeaseQueries` run the same SQL over the shared `chat_lease_cases.json`. Conversation delete cascades the lease; the holder sees 0 rows changed or a foreign-key failure, rolls back, cancels, closes its session and writes nothing more (`ErrConversationGone` / `ChatConversationGoneError`).
- **Go turn store `internal/chatstore`.** The twin of the Swift `ChatTurnStore`/`ChatTurnDriver`: `Start` (one transaction in `persistTurnStart` order: lease, owner row, attachment links, prefix title, routing, empty `partial` assistant row), `Turn.Apply/Flush/Finalize` (text flushed on the first delta then at most every 1 s, steps written as they start, status mapping, artifacts with Swift's `saveVersion` last-wins semantics, `markIfSlackStep`/`markIfUsed` for LIVE-01), `SelectBranch`, `MarkRead`, conversations (`NewConversation`, `Pin`, `Rename`, `Delete`), attachments (`ValidateAttachment`/`SaveAttachment`, the Mac's limits; `RemoveConversationFiles` after a delete commits), `composer.go` (the port of `ChatTurnComposer`: edit recomposes the original's skill and REFERENCED lines, owner text that looks like them gets the U+200B escape), `outcomes.go`, `prefix.go` (`remember:`/knowledge prefixes in process) and `artifacts.go` (Go artifact parser twin). `db.CreateIdeaFromChat` is the Go twin of `IdeaQueries.createFromChat`. Shared fixtures with Swift: `chat_turn_cases.json`, `outcomes_block_cases.json`, `chat_idea_rows.json`, `artifact_parse_cases.json`, `attachment_limit_cases.json`, `chat_search_cases.json`, `chat_lease_cases.json`.
- (Superseded: it is now `internal/chatengine`, pool of 3, shared with the Mac.) **Hub runner `internal/hub/chatrun`.** A second bounded pool in the daemon: `MaxLive = 2`, `IdleTTL = 10m`, `ai session --conversation N --surface main …` children in their own process groups (group file `<hub dir>/chatrun/<conv>.pgid`), one goroutine per session owns every write, a lease watch every 1 s (remote cancel: `cancel`, 7 s grace, then SIGTERM, then SIGKILL 3 s later; a lost lease stops writing), a heartbeat every 15 s. `Sweep()` at hub start kills orphan groups (`ps` args must name `ai session --conversation N`), marks `session_lost` and releases owned leases. Close order at hub stop: runner first, then titles, then background applies (`wiring.spawn`, 30 s budget). The Desktop's pool stays 3; with both busy up to 5 provider processes run on one Mac (a v1 limit).
- (Changed: `desktop_too_old` is gone, the heartbeat's `chat_lease` is accepted and ignored for one release, and `hub desktop heartbeat --chat-lease` likewise.) **Capability.** Heartbeat `capabilities.chat` on|off + `chat_reason` (`not_relay`, `runner_down`, `desktop_too_old`, `policy`); `hubRuntime.chatAvailable()` checks, in order, `workbench_only` → `policy`, no sources or runner → `runner_down`, not on the relay → `not_relay`, an old Desktop → `desktop_too_old`. The Desktop sends `chat_lease: 1` on its control-socket `desktop_heartbeat` (CLI twin `hub desktop heartbeat --chat-lease 0|1`; the hub keeps `desktop_chat_lease` in the sidecar meta next to `desktop_at`). Every `chat_*` handler refuses `not_supported` when chat is off. Chat sources publish only under MobileSync `allowed`.
- **Grant.** `chat` on by default for linked and new phones (sidecar migration `00017_chat_grant`, `devices.chat_allowed DEFAULT 1`; `LinkDevice` keeps it across a re-link). `device_grant` carries `chat` on every row (an absent key reads as allowed in the Kit). Verb `watchtower hub allow <device> chat [--revoke]` (no `deny`), `hub phones --json` `chat_allowed`, Desktop Settings → Mobile **Chat** switch (calls the same verb). `chat_action_answer` also needs `permissions`.
- **Actions (ten kinds + the upload frame).** `chat_new`, `chat_turn` (`received` echo; 32 000 runes), `chat_cancel`, `chat_feed_request`, `chat_read`, `chat_branch_select`, `chat_page`, `chat_search`, `chat_manage`, `chat_action_answer` in `internal/hub/actions/handlers`, ordered/non-idempotent per `NonIdempotentKinds`; `chat_attachment` is a sealed upload frame (`IntakeChatAttachment`: download, decrypt in memory, the Mac's validator, 0600 file, `applied {attachment_id}`). Approve goes through `Registry.ApproveSeen` with the shown `args_sha256`, reject through `Registry.Reject` (new; the approval-writers guard allows only the registry). New reasons `conversation_busy`, `attachment_missing`, `changed`.
- **Slices.** `chat_list` (200 conversations, state in the Mac's precedence: waiting = any pending `agent_actions` row of the conversation, answering = a live lease), `chat_feed` (urgent; open watch 5 min repeated every 60 s, prefetch 2 min, never counts as looking), `chat_page`, `chat_search` (Go port of `ChatSearchQueries`, `internal/db/chat_search.go`). Every record ≤ 600 000 bytes encoded for any input (oldest messages, then artifact contents, then a text cut with `text_cut`, then steps and actions). `siblings` carries `ids`. Titles, names and error messages are clipped at 200 graphemes (`maxChatLabel`); an artifact whose key is longer is left out of the feed (keys stay exact, the phone shows the fence's draft). Live text of a hub turn comes from the runner (`OnChange` → `publishSoon`), of a Mac turn from the database on `data_version`. A 5 s chat timer republishes time-only changes (watch expiry, a stale lease, a grant toggle).
- **Push.** Event `chat_answer` (`conversation_id`, key `chat:<turn_id>:<answer|stopped|approval>`, fixed bodies; see `docs/features/go-hub.md` Phase 4 and `chat_turn_watch.go`). Phone router opens the chat (`wt_conversation`, thread `chat-<id>`).
- (Superseded: no Swift writer, no lease check, no `ChatForeignTurnModel`; a phone turn streams on the Mac live.) **Desktop.** `ChatViewModel.persistTurnStart` claims the lease first (refused → the draft comes back and the composer shows the holder's line), the driver polls its lease every 1 s (remote Stop, conversation gone) and heartbeats every 15 s, `finalizeTurn` releases it (a finalize that fails rolls the release back, so the driver then frees the lease in its own best-effort write), `releaseEarlierLaunchesChatLeases` at launch; `ChatForeignTurnModel` reloads the open chat every second while the phone answers ("Answering from your iPhone — you can watch here"), Stop sets `cancel_requested_at_ms`.
- **Shared text package `WatchtowerChatText/`.** `ArtifactParser`, `MarkdownRunBuilder`, `ChatQuoteReply`, `MarkdownDocument`, `CommentBatchComposer`, `ArtifactLinks` (mailto / Google Calendar / Slack builders; the Mac's `ArtifactActions` delegates) and `ChatErrorText` (the Mac's `ChatErrorPresentation` delegates). Kit-free (swift-markdown only) so that WatchtowerCore stays Kit-free (`PublicAPISurfaceTests`); `make chattext-test`.
- **Phone (`WatchtowerMobile/Sources/Features/Chats/`).** `ChatsGateModel` (needsUpdate, turnedOff, needsRelay, notAllowed, unavailable, loading, error, empty, offline/away, ready — the copy names the hub through `ChatText` in `TowerText.swift`), `ChatListModel`/`ChatSearchModel`/`ChatRowActions` (Undo bar 5 s, delete sent only when it ends, refused delete brings the row back), `ChatConversationModel` (open request + 60 s repeat, 30 s patience, pages stitched by `before`, `chat_read` only for the newest complete answer while visible, Stop, Regenerate, Edit, branch arrows — all of them never queue offline), `ChatFeedItems`/`ChatMarkdownView`, composer (`ChatComposerModel`, `ChatDraftStore`, 32 000-scalar cap, nothing queued offline), `ChatSendCoordinator` (`chat_new` → uploads one at a time → `chat_turn`; `chat_outgoing` keeps each send across a kill so CHAT-01 holds on the phone; echo patience 120 s), `ChatAttachmentPicker.swift` (`ChatAttachmentPrep`: HEIC → JPEG, downsizing over 5 MB; `ChatAttachmentLimits`: the Mac's validator over the shared fixture), `ChatApprovalCardModel` (the state line of ChatUI's shared `AgentActionCard`; no `permissions` grant → "Approve on the Mac"), `ChatArtifactSheet` + `SandboxedArtifactWebView` (CHAT-05), `ChatSourcesSheet`, `ChatOfflineCopy` (own GRDB file `chat-copy.sqlite` per hub, class C, 200 MB budget evicted by chat, deleted with the link; a file that does not open leaves the tab on an in-memory copy with the line "Saved chats are off on this phone — chats can't be read offline and an unsent message won't survive a restart." (`ChatText.copyUnavailableLine`); a kept send that no longer decodes is logged by error type and client key and deleted, a read that fails recovers and deletes nothing) and `ChatPrefetcher` (20 most recent, one at a time, once per chat per hour, foreground and reachable only). Since the unified chat everything inside a conversation and a list row comes from the shared `ChatUI` (`PhoneChatStyle`, `RelayChatClient`, `ChatWireKitConformances`); the pickers `@` and `/` go over `chat_entity_search` and `chat_skills_list`; project editing, artifact comments, Add to Knowledge, `continue`, move, archive, discard, warm and session retire answer `unsupported` locally (no relay kind). See [unified-chat.md](unified-chat.md).
- **Main chats only (spec §1).** The phone reaches a conversation only while `context_type IS NULL`: a Discuss chat is absent at every entry point — `chatstore` `ConversationExists`/`Pin`/`Rename`/`Delete`/`SelectBranch`/`SaveAttachment` (so `chat_feed_request`, `chat_page`, `chat_read`, `chat_branch_select`, `chat_manage` and the attachment intake answer `not_found`; `chat_turn` was already refused), the `chat_feed`/`chat_page` reads, the `chat_answer` push (title, desktop leases and pending actions of main chats only) and `chat_action_answer`, which answers `not_found` for an action whose conversation is not a main chat — phone approvals cover main-chat actions only.
- **Publish folder per process.** The claude.ai publish folder is `<NeutralWorkDir>/publish/<conversation>-<pid>` (`chat.PublishDirName`): the Desktop's and the hub's `ai session` of one conversation share the work dir, and each removes only its own folder on close.
- **Ask about this.** A long-press on a finished answer opens a passage picker sheet (selectable text), not an in-place selection with a floating chip; the quote batch goes out with the next message through `ChatQuoteReply.compose`.

## v1 limits

- Phase 2 items of the spec (§1) are not in v1. A chat's project is fixed after the first message; its model pill follows the Mac's rules (ask #1418) and stays editable between turns. An edited message keeps its attachments on the original.
- Every turn, started on the Mac or the phone, streams to the phone from the engine's record at relay spacing (the unified chat removed the Mac turn's 1 s database re-read); a hub-run turn is unchanged. The record is capped at 600 000 bytes, and the Mac's feed cuts a message's text at 40 KB.
- Offline, only chats opened or prefetched can be read, as far as their pages were loaded; search over message text needs the Mac; sending, Stop, Regenerate, branches and row actions are off offline.
- One pool of 3 `ai session` processes serves the Mac and the phone together (it was the hub's 2 plus the Desktop's 3); a 4th waiting conversation shows "Waiting for a free slot".
- The phone's steps line shows the hub's step summary or source kinds, not the Mac's tool catalog names.
- html artifact WebRTC is removed in the page and script-made iframes (simulator test `PhoneArtifactWebRTCTests`); the phone sets no private `WKPreferences` selector.
- The chat attachment intake is not claimed `begun`: a hub crash between the file commit and the echo can leave one extra pending attachment row (the file is deduplicated by hash). The per-message 30 MB encoded cap is enforced by `ai session` at send, not by the hub's `chat_turn`. Approved non-session actions apply in a hub goroutine; a stopping hub refuses to start one and the row stays `approved` for `actions apply`.
- **A send that gives up (T11 fix round 2).** After the 120 s echo patience the coordinator first calls `ActionOutbox.withdraw(actionID:)` (`.withdrawn` / `.onItsWay` / `.notWaiting`; a throw counts as `.onItsWay`). It takes back a queued `chat_turn` only while the hub cannot have it (a never-written row, or a written one whose record can still be deleted under the version the phone wrote — the gap closed by `resend_from` → `skip_to`; an action the hub's `received` or final echo moved stays). Only `.withdrawn` gives the text back with "Couldn't send that"; otherwise the bubble shows "Waiting for your Mac…" (`isStalled`), the text stays out of the composer, and a late applied echo marks the message sent while a late refusal returns the text with its reason. Recovery after a relaunch adopts a queued `chat_turn` the kept send never recorded, matching conversation, text and mode in the snapshot's queued chat actions (`QueuedChatAction`). Residual: a kill between the outbox write and the recording of the turn id, plus the hub applying the turn while the app is dead, leaves nothing to match, so the phone shows "Couldn't send" for a message that was sent (a resend may duplicate it).
- **Since the unified chat's addendum (#1822 T13–T17, asks #1409, #1411, #1418, #1420)** the composer, the approval card and the routing pill are `ChatUI`'s, one implementation with the Mac. The phone's approval card has no editing (Slack text, workspace pick, connector input) and no Approve all, Dismiss or Retry; a clipped Confluence edit shows no diff but may be approved, pinned to the args digest. The model menu lists the registry's models only (no live Ollama list), and provider availability refreshes only when `chat_list` is rebuilt (no "check again", no refresh on app activation). Details in [unified-chat.md](unified-chat.md) v1 limits.
- Every turn's end pushes (`chat_answer`, the engine's turn-end hook); the old Mac-turn lease watch and its cadence limit are gone.
- Dark list screenshots show the iOS 26 glass tab-bar lens (a capture artifact).
- Deferred minors from review: a restored send may keep a deleted plaintext URL; the phone's sign-in hint uses the conversation's actual provider; sealed upload files remain until unlink; a grant record without a `chat` value ignores a real `device_not_allowed` refusal (only an older hub).
