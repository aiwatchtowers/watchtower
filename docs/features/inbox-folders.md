## Folders

- Migration **00183** (`internal/db/migrations/00183_inbox_folders.sql`; renumbered from 00181 after main took 00179–00180, with Inbox builder A's 00179 → 00181 and 00180 → 00182): `inbox_folders` (`kind` `root|approvals|owner`, `parent_id`, unique `slug`, `title`, `icon`, `position`, `hidden`; one root and one Needs approval by a partial unique index), `inbox_folder_state` (one row, `revision`), `inbox_folder_routes(automation_id → folder_id, ON DELETE CASCADE on the automation)`, `automation_outputs.folder_id` (`ON DELETE SET NULL`) and the view `inbox_artifact_folders(output_id, folder_id)` = explicit folder ?? route ?? root. Seeds: root `inbox` "Inbox", Needs approval `needs-approval` under it at position 0, revision 1. No rebuild; folders hold no source data, so purge and source deletions are untouched.
- Rules (`internal/inboxfolders`): root first, never renamed, moved, hidden or deleted; Needs approval pinned at position 0, fixed, no child folders. Owner folders: title 1–60 characters on one line (`MaxTitleRunes`), unique among siblings ignoring case; icon from the allowlist `icons.json` (24 SF Symbols, `""` = `folder`; Swift twin `InboxFolderIcons`, pinned by `InboxFolderIconsTests`); depth ≤ 3 below the root (`MaxDepth`), ≤ 100 owner folders (`MaxOwnerFolders`). The slug is made once from the title (lowercase ASCII, `-`, `-2` on a clash) and never changes, so a rename never breaks a recipe. Positions are rewritten densely by every move.
- **Writes are CLI-only with compare-and-set on `revision`** (`db.WithInboxFolderRevision`, one `BEGIN IMMEDIATE` transaction): a stale `--expect-revision` writes nothing and exits 1 with `the Inbox menu changed — reload it and try again (revision N, you had M)`. Writes are owner verbs, refused under every agent marker (`refuseUnderAgent`). The Desktop writes none of the folder tables nor `automation_outputs.folder_id`; on the conflict phrase it re-reads and shows "The menu changed — reloaded. Drag again if needed." and never retries by itself.
- **Delete** (FOLDER-01): children, routes and explicit artifacts move to the parent, a moved child whose title clashes is renamed " (2)"…, counts and renames reported; nothing else is deleted. Root and Needs approval are refused.
- **CLI** `cmd/inbox_folders.go`: `watchtower inbox folders list [--json]`, `create --title [--icon] [--parent] [--position]`, `update <id> [--title] [--icon] [--hidden]`, `move <id> --parent --position`, `delete <id>`, `route <automation-id> (--folder ID | --new-title T [--new-icon] [--parent])`; every write takes `--expect-revision` (refused without it) and `--json` (one object, last stdout line). Pinned keys: folder `id`, `kind`, `slug`, `title`, `icon`, `parent_id`, `position`, `hidden`, `automation_ids`; `list` `revision`, `folders` (pre-order); `create`/`update`/`move` `revision`, `folder`; `delete` `revision`, `moved{folders, automations, artifacts, renamed[{id, from, to}]}`; `route` `revision`, `automation_id`, `folder`, `created`. The `needs-approval` built-in can't be routed elsewhere. Hidden `watchtower inbox approvals changed --ref <kind>:<id>` is the Desktop's reminder hook (below).
- Desktop: `InboxFolderQueries` (one read with the strip: tree, routes, cards per folder, ref state, Needs approval and Waiting for me state; an older database reads a root-only tree), `InboxFoldersCLI`, `InboxFolderMenuModel` (selection in `UserDefaults` `inbox.folder`, drag rules, inline edits, delete confirmation, CLI-missing line), `InboxFolderCounts` (each folder's own count; badge = sum over visible folders), views in `Views/Inbox/Folders/`.

## Routes and `folder` on `output.inbox`

- An automation's folder is its route, configuration outside the recipe: **Move to Folder ▸** rewrites it (`route --folder`), never touches `approval_hash` and asks for no confirmation. Every artifact that follows the route moves with it.
- `output.inbox({…, folder: "<slug>"})` registers through A's `RegisterInboxField` (`internal/automations/inbox_folder_field.go`): the call checks the shape (≤ 80 bytes, no control characters) and buffers the slug; `commitRunTx` resolves it in the run's own transaction (`resolveOutputFolderTx`). A missing folder puts the artifact on the route with the journal line `folder "<slug>" not found — shown in <route title>`; it never fails the run. A dry run resolves for its preview only. A script never creates a folder.
- Built-ins: `builtin.Entry.DefaultFolder` (`inbox` or `needs-approval`; `show --json` `builtin.default_folder`); `builtin.Sync` seeds a route only when the built-in has none (`SeedInboxFolderRoute`), so the owner's move is kept. The card's **Show in Inbox** opens the built-in's folder (the old `result_filter` is gone).
- **From the editor.** Read tool `list_inbox_folders` on `automation_editor` only (title, slug, `parent_slug`, `hidden`; Needs approval left out; AGENT-04 note). `draft_automation` takes `folder: {title, parent_slug}`, cached with the draft (`authoring.FolderSuggestion`; an undecodable cached suggestion is dropped, the draft kept), never in the evaluation or the hash. The Changed row's last line is "Folder: <title>" (an existing sibling of that title, ignoring case) or "New folder: <title>, in <parent>", shown only when the press saves; an unknown `parent_slug` puts the new folder at the root, and there is no line when the automation already sits in that folder or for the `needs-approval` built-in (Go refuses that move). A save that lands spends the chat entry its suggestion came from (per workspace and automation in the app's defaults, `automations.spentFolderSuggestions`, kept across restarts), so a later save never moves the automation back after a **Move to Folder**. After a successful save the Desktop runs one `route --new-title` (or `--folder`); a refused save sends none; a route failure keeps the recipe and shows "Saved. The folder was not created: <reason>" with **Try Again** (re-reads the revision first). **New Artifact…** opens the new-automation flow with the selected folder as its route.

## Needs approval

- Built-in `needs-approval` (`recipes/needs-approval.md`): `trigger: {event: approval}` (built-in only, `approvalTriggerAllowed`), `artifacts: living`, `concurrency: 1`, capability `builtin:approvals.list`, no `llm()` (pinned). One living card per open approval (keys `action:<id>` / `reminder:<id>`), `output.remove` for closed ones, the 50 oldest per run. Feature `approval-cards` (config `approval_cards.enabled`, default on, no fast-forward hook).
- **The hook.** `db.SetApprovalHook` once per process; the seven writers in `internal/db/agent_actions.go` and `reminders.go` (and `InsertInboxButtonProposal` / `InsertInboxReplyProposal` after commit) call it with the ref when a row that is or was an approval changes. `MarkReminderDone` / `SnoozeReminder` return `(changed bool, err)`. `builtin.Fire` skips rows that can never be approvals (`db.ActionCanBeApproval`), then only queues (`EnqueueAutomationRun`, or merges into the queued run, ≤ 100 events) and wakes (AUTO-09). A failure is logged with ids only and never fails the state change.
- **Desktop reminder writes** stay GRDB (STRIP-03) and then run `inbox approvals changed`; a failure there is not shown.
- **Sweep.** `phaseApprovalSweep` (`internal/daemon/approval_sweep.go`, after `phaseUnsnooze`) compares the open approvals with the cards (`db.ApprovalDriftOf`) and fires `sweep`; read-only.
- **Who runs it.** `Automation.RunsAtSlot` narrowed to sync-triggered automations, so the event-triggered built-in runs on the executor poll right after its wake (`TestAutomation_RunsAtSlotMatchesSlotSQL`).
- **What the Desktop shows** (APPROVAL-01, `NeedsApprovalSelection`): every open approval, by the recipe's card only while the feature is on and not stopped, the last finished run succeeded, the card exists and its `written_at` ≥ the approval's change; otherwise the native card (`AgentActionCardView`, `SaveAutomationProposalPane`, the reminder card). Built-in upgrade notices first, then native, then recipe cards. Closed approvals are never drawn. Notes: off, stopped (AUTO-08) and last run failed, each with **Turn On** or **Run History** through `AppState.setBuiltinEnabled` (its own error under the note; a failed daemon restart sets the app-wide banner, ask #503).
- **Approved and executing rows** (final review, 2026-11-09): Needs approval also draws them on their native card after the open ones, so a stuck target proposal shows "Didn't finish" with **Try again** (spec A). They are not approvals: never counted in the folder or the badge (`awaitingOwnerCount`); the pane header counts the cards drawn. Closed rows and the old 24-hour tail are never drawn here (a thread brief is a root entry, ask #609). A waiting target button opens Needs approval scrolled to its card. Waiting for me draws and counts nothing while the owner has it turned off (`enabled` = 0); a daemon stop (`disabled_reason`) counts as a failed run, so Messages stands in.

## Waiting for me

- Built-in `waiting-for-me` (`recipes/waiting-for-me.md`): `trigger: {sync: waiting_for_me}`, run by `phaseWaitingForMe` right after `phaseInbox`; `FeatureIDs: [secretary-inbox]`; capability `builtin:attention.waiting` over `db.OpenInboxItems` (the Go twin of `HomeFeedQueries.openMessageClause`, newest first, 200); one living artifact `waiting` with a row per item (`ref {kind: inbox_item}`, age badge, `warning` tone past 24 h); no `llm()` (pinned).
- Pinned first in the root while a row waits. A native row action queues no run: the render-time check hides the closed row at once.
- **Stand-in:** until its first successful run and after a failed one (`WaitingForMeState.messagesStandIn`), the root shows the **Messages** legacy entry and leaves the built-in's artifact out.

## The root and the legacy entries

The root lists Waiting for me, the artifacts routed there, and Desktop-only legacy entries over today's queries and panes (`InboxFeedQueries.read`, `InboxLegacyList` `tracks|ideas|messages`): **Morning brief** per date (`InboxListBuilder.rootDays`: today's — a placeholder before it exists while the owner is known — and every unread one), **Track my threads** (Stopped fold, **Restore**), **Idea finder** (its ⋯ has **Find Ideas in Past Messages…**), **Messages** (stand-in only), and one **Thread brief** per `brief_context` row applied in the last 24 hours (ask #609: `AgentActionQueries.fetchExecutedBriefs` by `applied_at`, `notWorkbenchRow` as on the strip, read as `InboxFeedSnapshot.briefs`; `InboxFolderEntry.brief`, row kind `result`, placed by `applied_at` among the root's timed entries). A brief is a result, not something waiting: never unread, never in a folder's count or the badge, never in Needs approval. Selecting it draws its `AgentActionCardView` (the summary from `result_json`) in the reading pane; a `.proposal` route to a listed brief opens its root entry. The list re-reads on the 30 s poll, on appear and after a press (the daemon writes the row from another process, which no observation sees). This replaces the old Automations filter's 24-hour executed tail, which nothing drew after the filters went. The filters are gone: no `InboxFilter`, no `inbox.filter` key, no `inbox.dayCardDone`, no Done on the day card (ask #607). `InboxRoute` is `{folderID, entry}`; the old nav hosts `briefings`, `dayPlan`, `day-plan` open today's Morning brief, `tracks` / `ideas` their entry; a deleted folder opens the root. Empty-state keys: `inbox`, `inboxFolder`, `inboxApprovals`, and `InboxLegacyList.emptyCopyKey` (`tracks`, `ideas`, `inboxMessages`).

## Native row actions and Reply

- `InboxRefState` reads every `ref` at render time in the same read as the folder ("shown" and "waits on the owner" per kind); Go twins in the primitives; shared fixtures `internal/inbox/testdata/open_items.json` and `internal/automations/builtin/testdata/open_approvals.json` (`InboxRefStateParityTests`).
- `InboxRefHooks` draws today's buttons per kind through `ArtifactRefHooks` and suppresses the recipe's same-kind actions (`nativeKinds`). Every press calls today's function (STRIP-03); a failed press stays on its row (`ActionStripViewModel.rowErrors`, **Retry**); `lastError` is for read failures only.
- **Reply…** (`InboxReplyPolicy`): Slack → `send_slack_message`, Jira → `add_jira_comment`, Linear → `add_linear_comment`; none for mail, a Slack item without a permalink or an issue without a key. **Propose Reply** runs `actions propose --tool … --surface inbox --context inbox_item:<id>` without `--approve` (refused for `tools.InboxReplyTools`); the reason is "Reply from <host title>". One open reply per item (`db.ErrReplyAlreadyWaiting`); the row shows **Reply waiting for approval**. The strip and badge leave out only `surface='inbox' AND tool='apply_track_action'` (STRIP-01 narrowing), so the reply shows in Needs approval.

## Menus

Artifact ⋯ (header and row context menu): **Run Now**, **Edit What It Collects…**, **Edit the Look…**, **Schedule…**, **Move to Folder ▸**, **Turn Off**/**Turn On**, **Run History**, **Delete…** — each the Automations tab's own verb (`InboxArtifactMenuModel`, shared busy guard; a result `done`/`busy`/`failed` shown on the header). No **Delete…** on a built-in, no **Move to Folder** on Needs approval, no **Run Now** where `Entry.RunNow` is false. Folder ⋯: **Rename…**, **Icon ▸**, **New Folder Inside**, **Hide**/**Show**, **Delete…**. Root ⋯: **Learned Rules**, **Assistant Profile** (INBOX-05), **Show Hidden Folders**, **New Folder**. Needs approval ⋯: **Edit the Look…**, **Turn Off**/**Turn On**, **Run History**. The header with **?** spans all three columns.

## v1 limits

- **New Artifact…**'s folder lives in memory only: an app restart before the save loses it (the automation then lands in the root).
- A failed reply does not block a new one: **Retry** on the failed proposal plus a new reply can post twice (Go's rule: only pending, approved or executing replies block).
- The editor's folder suggestion must be passed on every `draft_automation` call; the newest draft's is the one shown.
- No artifact drag: **Move to Folder** moves the automation. A folder has no look of its own. The phone keeps its current Inbox slice.
- A read past brief has no list entry until sub-project C (Home's **Briefing** link or a notification opens it).
