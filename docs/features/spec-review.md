# Spec review — an independent reviewer for specs and plans (2026-10-25; author loop 2026-10-26; open-ended loop, Discuss and the summary 2026-11-08)

Spec: `docs/superpowers/specs/2026-10-25-spec-review-design.md`; plan 1: `docs/superpowers/plans/2026-10-25-spec-review-p1-core.md`; plan 2 (Desktop): `docs/superpowers/plans/2026-10-25-spec-review-p2-desktop.md`; plan 3 (pack, guide, phone): `docs/superpowers/plans/2026-10-25-spec-review-p3-pack-guide-phone.md`. Author loop: `docs/superpowers/specs/2026-10-26-spec-review-author-loop-design.md`, plan `docs/superpowers/plans/2026-10-26-spec-review-author-loop.md` (board #1121). Contracts: SPECREVIEW-01..05 in `docs/inventory/spec-review.md`.

## Summary

When the agent files a `review` ask for a spec or a plan, a second, independent reviewer agent reads the document against the conversation that produced it and the workbench folder, and stores a structured, quote-checked result next to the ask. The owner opens the ask with the findings ready. The reviewer never replaces the ask: it is filed whatever the reviewer does (SPECREVIEW-02).

## Storage

Migration `00158_spec_reviews.sql` (mirrored in `schema.sql`); access in `internal/db/spec_reviews.go`.

- `owner_asks.doc_type` — `''` (not a review), `spec`, `plan`, `other`.
- `spec_reviews(ask_id PK, status queued|running|done|failed|skipped, reason, result, provider, model, doc_sha, dropped, pid, attempt, queued_at, started_at, finished_at)` — one reviewer run per review ask. `QueueSpecReview` upserts to `queued`, clears the result and adds one to `attempt`; `RelaunchQueuedSpecReview` is the sweep's conditional re-queue (only `WHERE status='queued' AND attempt < 3`); `RequeueSpecReview` (the owner's `start`) resets `attempt` to 1; `ClaimSpecReview` moves queued to running under the reviewer's pid; `FinishSpecReview` / `FailSpecReview` act only on a running row of that pid; `SkipSpecReview` records why no review runs.
- `spec_review_marks(ask_id, item_key, state, body, about, updated_at)` — the owner's per-item marks; the Desktop writes them, Go only reads them for `show` (`about` key). A comment's `about` is the finding text, so a comment whose finding a re-run drops still says what it was about; `''` when there is none.

## Starting a review

- `ask_owner` (`internal/tools/workbench_asks.go`) takes `doc_type` (`spec`, `plan`, `other`; default from the path by `specreview.ClassifyDoc`). A spec or plan queues a review row right after the ask's transaction has committed, then calls the surface's launcher.
- Neither a failed queue write nor a launcher failure fails the ask: a refusal or failure records `skipped` with the reason (`could not queue: …`, `launch failed: …`, or `no reviewer on this surface` when the surface has no launcher); the reason is always in the `spec_review` result key, also when the skip itself cannot be written. The cmd launcher (`specReviewLauncher`) does not look at the Claude plan's limits (owner, 2026-10-26: the automatic start used to skip on `planusage.NearLimit`, whose weekly projection fired right after a reset; rows stored before keep the reason `plan near limit`).
- Skill pack v17, v18 since the author loop (`internal/devpack`): the core skill tells the agent to pass `doc_type` on a review ask; the `watchtower-flow` preset makes every spec carry a `## Decisions` section (one line per owner decision with its source, `ask #N` or `conversation`) and commits mockups agreed in a brainstorm under `docs/design/mockups/<feature>/`, linked from the spec.
- `LaunchSpecReview` (`cmd/workbench_spec_review_launch.go`) starts `workbench spec-review run --ask N` detached in its own session, output appended to `<workspace>/logs/spec-review.log`, agent-session env markers dropped, the child reaped in the background. The binary comes from the package var `specReviewExe` (`/usr/bin/false` in cmd tests).

## The run — `internal/specreview`

The review header (`reviewHeader`) names the document's type, path, chapters and design lens; a spec's also says `decisions_section: present|absent`. A plan is never asked for a Decisions section: its agreements come from its spec, whose Decisions section is part of the spec block. A spec's Decisions section is a `## ` heading whose text starts with the word "Decisions", any case (`## Decisions (owner-approved)`): `isDecisionsHeading`, the same rule as the Desktop's `SpecReviewDecisions`.

`Run` claims the row (a row no longer queued is left alone) and fails it at once with "ask withdrawn" when the ask was withdrawn or superseded before the claim (an ask withdrawn while the agent works still gets its result), then: `BuildInputs` (the document snapshot, the conversation from the session feed trimmed to `MaxConversationRunes`, answered asks, the linked spec of a plan, mockups and the style guide when the document talks about screens, the previous round's findings), one `Agent.Review` call under `RunTimeout` (10 min, `MaxTurns` 40 model turns on claude and codex — codex counts its run's rollout in a private `CODEX_HOME` removed after the run, SPECREVIEW-01 note), `Parse` (validation: caps in `limits.go`, every quote must be a whitespace-normalised substring of its source, SPECREVIEW-03), then `FinishSpecReview`. Any failure after the claim stores `failed` with a one-line reason. Every quote's source records its `speaker` (`owner` | `agent`, set by `Parse` from `Sources.OwnerWords`, never by the model): the owner's words are an owner line, the owner's answer texts, check notes, comment bodies and note of an ask (chosen option labels count as the owner's answer; questions, check items and quoted document text do not), and owner comments; agent text, agent comments, the target, the Decisions section and the spec are `agent`. `idea.owner_source` must be the owner's; an agreement from the conversation, an ask or a comment must quote the owner, while `decisions`, `spec` and `target` sources stay allowed. The result carries `summary`, `idea`, `agreements`, `decided_alone`, `blind_spots`, `checks`, `resolved`, `notes`, `dropped`, `code_read`; items have stable keys (`ag:` + 12 hex digits) and chapters (`Chapters`). An idea with no real quotes, or none, is left out (`idea` is a pointer with `omitempty`; the Desktop also reads an idea with blank quotes as absent, for rows stored before). An anchored item's chapter is its where-quote's; a missing agreement or a blind spot without `where` keeps the `chapter` the reviewer named (key or heading) when the document has it, else `""` (the Desktop's Other).

The agent (`specReviewCLIAgent`, cmd) runs the configured provider in read-folder mode with **no MCP server at all**: claude with Read/Grep/Glob/LS only and no folder settings, codex in its read-only sandbox with the same feature flags off as every Watchtower-launched codex run (no owner hooks, skills or subagents; see `chat-redesign.md`), both in their own process group. Ollama has no file tools: the same prompt answered from the data alone (`code_read` false). The model tier is strong (`workbench.spec_review`).

## Daemon sweep — `internal/daemon/spec_review_sweep.go`

`phaseSpecReviewSweep`, the last step of a cycle (after `phaseCoach`), runs only when cmd wired `SetSpecReviewLaunch` (`cmd/sync.go`):

- a `queued` row older than 60 s is re-queued by `RelaunchQueuedSpecReview` (attempt + 1, the minute restarts, only while still queued with `attempt < 3`) and launched only when that update changed the row, at most 3 per cycle — a slow reviewer that claimed the row meanwhile keeps it, no second reviewer starts; a row still queued with `attempt >= 3` is claimed under pid 0 and failed with "could not start";
- a `running` row whose pid is gone (`syscall.Kill(pid, 0)` gives ESRCH) or that started more than `RunTimeout` + 2 min ago is failed with "reviewer process ended without a result"; an overdue reviewer still alive is first sent SIGTERM to its process group (`-pid`; it leads its own session), only when the pid still leads its group and the process started no later than `started_at` (+1 s), so a reused pid is never signalled.

## CLI — `watchtower workbench spec-review`

- `run --ask N` (hidden) — the detached child; the exit status is the run's.
- `start --ask N [--force]` — `RequeueSpecReview` (attempt back to 1: the sweep's 3-launch cap counts automatic relaunches only) and launch. A queued review is launched again; a running one is refused (exit 3); a done, failed or skipped one needs `--force` (exit 3 without). A failed launch leaves the row queued for the sweep.
- `show --ask N [--json]` — pinned `--json` keys: `ask_id`, `status`, `reason`, `provider`, `model`, `dropped`, `attempt`, `queued_at`, `started_at`, `finished_at`, `result` (the validated result or `null`), `marks` (item key to `{state, body, about, updated_at}`; `state` is `ok`, `comment`, `viewed` or, since 2026-10-26, `not_useful`; `about`, a comment's finding text, is left out when not known). The database is opened read-only.

## Desktop — the findings screen

- `SpecReviewModel` (`WatchtowerDesktop/Sources/ViewModels/`) drives one open review ask of a spec or a plan: its `spec_reviews` row and `spec_review_marks` (read through `SpecReviewQueries`, the marks written there), the 3 s poll while the reviewer is queued or running, Run / Re-run reviewer (`workbench spec-review start --force`; exit 3 = already running), and the derived Meaning / Chapters / Wrap-up state (findings by chapter, a trailing Other, unmarked counts, orphans of a re-run, the Decisions list of a spec — a plan shows none). It is built on the app's pool by `OwnerAskDrawer`; `followReviewer` looks for a row not written yet (10 × the poll interval) and then starts the poll.
- Drawer modes (`SpecReviewPresentation.drawerMode`): `loading` until the first read returns (nothing shown, so the classic view never flashes), `review` (the screen) for a done result or a reviewer still working, `classic` with a status strip (failed, skipped, or working after **Read the spec**) or a banner (a result that arrived while the classic view was open). Under the screen the footer's verdict buttons and the draft keys stand aside.
- One answer builder. Every answer to a review ask ends in `OwnerAsksViewModel.answer(_:with:)` — the classic footer's Request changes / Approve, the screen's Send / Approve, a Quick answer and the phone's relay (`AskAnswerHandler`). For a review ask (not a dismissal) it reads the row and the marks from the database at answer time and appends `SpecReviewAnswer`'s comments: comment marks only, in findings order, placed in the rendered snapshot (off the main actor); with no result (queued, running, failed) every comment mark goes out as "From the previous run: <about> — <body>". The screen itself hands over only the draft (margin comments, question answers, note) and the verdict, so nothing is sent twice and nothing depends on the screen having been opened.
- **Fix** (2026-10-27, ask #678): the first button on a finding — the reviewer is right, send it as it is. It writes a `comment` mark with an empty body (no schema change); `SpecReviewAnswer` then sends the finding's text alone (an orphan: "From the previous run: <about>"). The card shows **Fix** with **Add Comment** and **Undo**, the wrap-up a wrench glyph; the four buttons wrap to two rows in a narrow drawer (`ViewThatFits`).
- **Not useful** (2026-10-26, agent coach #1120): a third button on a finding beside **Fine as is** and **Comment**; the mark reads "Not useful" with **Undo** (`SpecReviewMarkState.notUseful`, `SpecReviewFindingCard`, `SpecReviewWrapUpView.markGlyph`). It is the coach's noise signal (`docs/features/agent-coach.md`) and `SpecReviewAnswer` never sends it to the author. An older app reading a newer row skips the unknown state.
- The phone's `owner_ask` slice carries one `spec_review` line per review ask: one query for all the slice's review rows, a done review's counts decoded once per `finished_at` (`SpecReviewLines`).

## The author loop (2026-10-26, board #1121)

For a spec or plan ask bound to a terminal session on a surface with a launcher, the ask starts **hidden** while the reviewer and the author go back and forth, and reaches the owner once, with only what is disputed. Spec: `docs/superpowers/specs/2026-10-26-spec-review-author-loop-design.md` (owner asks #647, #649, #650, #653, #658). Contracts SPECREVIEW-04 and -05.

- **Storage (migration 00160).** `spec_reviews` gains `loop` (`''` | `author` | `owner`), `round`, `replies` (the author's replies of the round that produced this row), `open_items` (what the author still has to answer), `ledger` (every finding the author answered `fixed` and the reviewer settled, with its round and note) and `loop_end` (`settled` | `cap` | `reviewer_failed` | `session_gone` | `timeout`). `QueueSpecReview` takes a `*SpecLoopStart`; `FinishSpecReview` keeps `loop = author` unless the round ends (`owner`); `RevealSpecLoop` is the one conditional flip to `owner`.
- **Filing.** `ask_owner` returns `spec_review: "author_loop"` when the row was queued as a loop. The author files the next round with `previous_ask_id`, `changes` and `review_replies` `[{key, reply: fixed|disagree, note}]`: `disagree` needs a note (at most 500 runes), an unknown key is refused, a missing reply counts as `fixed`. Replies are refused when the previous ask is not looping: "the owner has this review now — wait for their answer". Replies are also refused when the new ask will not loop (not a spec or plan, no Watchtower session, or no reviewer on the surface) instead of being dropped. A re-round whose previous review the owner already has (`loop = 'owner'`) starts no hidden loop: it is a classic visible review; so is a round past `MaxLoopRounds`. A hidden ask is open for the author: `get_ask` and `list_asks` return it with `spec_loop`, the Stop ask guard counts it.
- **`get_spec_review`** (read tool, the nineteenth workbench tool of DEV-06, not company data: the owner's own review loop in `company_data.go`): keys `ask_id`, `round`, `max_rounds`, `loop`, `status`, `reason`, `items`, `hint`; the open findings of the round with key, kind, text, quotes and where.
- **The loop (`internal/specreview/loop.go`).** `MaxLoopRounds` 3, `AuthorTimeout` 30 min from `finished_at`. `NextRound` folds the reviewer's verdicts (`resolved`, `disputed`, `still_open`) and the author's replies into the next `open_items` and `ledger`; a missing verdict leaves an item open; at the cap the open items move to unsettled. `Reveal` ends a loop for an early exit: a done row uses its own `open_items`, a failed row the previous round's, and an item the author answered `fixed` on a not-done row says "The fix was not checked…" (per end reason) instead of "The author did not answer". An item still open after an earlier `disagree` keeps that reason. The prompt `review.spec` v2 carries the verdict list and the round-2+ rule: a new finding only on text changed since the previous round or on a blocker.
- **Exits.** `Run` ends a round by `NextRound`; a reviewer failure reveals (`reviewer_failed`). `ask_owner` reveals at once when the queue write or the launch is skipped for a loop row. The daemon's `sweepSpecLoops` (not gated on the launcher, in `phaseSpecReviewSweep`) reveals `session_gone` when the ask lost its session and `timeout` 30 minutes after the findings were written; a dead or could-not-start reviewer reveals as `reviewer_failed`, and so does a loop row left `failed` or `skipped` when the immediate reveal after it did not land (a done row with an unreadable `finished_at` is logged). `watchtower workbench spec-review reveal --ask N --reason session_gone` (hidden) is the Desktop's call when a delivery cannot be made; `show --json` gains `loop`, `round`, `loop_end`, `open_items`, `ledger`.
- **Show Now and plan order (2026-10-27).** `specreview.EndOwner` (`reveal --reason owner`): a done round's open items go unsettled with "You opened the review before the author answered", a running round's fixes "The fix was not checked: you opened the review before it was"; a first round with no finished result leaves the loop (`db.LeaveSpecLoop`: `loop = ''`, `loop_end = 'owner'`) and becomes a plain review. Desktop: `SpecReviewLoopQueries.hidden`, `SpecReviewLoopCenter.hidden`/`showNow` (no findings line after it), the stack's **Reviewer and author** rows with **Show Now**. `ask_owner` refuses a plan (`planAfterSpec`, at the scope step) while the session has an open spec ask (`db.OpenSpecAskOfSession`, hidden or not). The loop screen splits **Disputed** (`SpecReviewLoop.disputed`: `disputed`, or `unsettled` after a `disagree`) from **Not answered by the author** (`unanswered`: `unsettled` with no reply or an unchecked fix; **Fix** / **Skip**, same marks); a card shows the reviewer's own note, never a loop-end line (`loopStatus` shows that separately), and `SpecReviewAnswer.loopBody` sends the finding's note for an unanswered item. Phone line: "Reviewer and author disagree on N · K not answered · M fixed by the author".
- **Desktop.** Hidden asks leave every owner surface (`OwnerAskQueries.notInSpecLoop` in the stack, drawer, notifications, Home feed, phone slice; `OwnerAskQueries.visibleAsk` for the terminal's `ask #N` link and look-ups — the findings line names the hidden ask; Go's morning brief lists open asks with `ExcludeSpecLoop`); the guarded `open → answered` update refuses them (PROJ-12 amendment, no guard weakened). `SpecReviewLoopCenter` types the findings line when a loop row turns `done` (`Spec review of ask #N, round R: K findings to address — read them with get_spec_review N using the watchtower-workbench skill.`, Go twin `asks.SpecReviewLine` with shared fixtures `spec_review_lines`), holds a delivery until the hosted sessions have reattached, reveals `session_gone` when the session is gone, and shows `Spec review: round R of 3` on the session (`round R` since 2026-11-08). The loop screen: **Disputed** cards (**Reviewer is right** / **Author is right**, optional comment), **Fixed by the author** folded with **Reopen** (findings resolved after a `fixed` reply; one resolved after the author's `disagree` fixed nothing and is in neither list), one-press **Approve** (an unsettled dispute counts as Author is right; after an early exit Approve asks once). The loop screen's Approve sends `approved`; any other answer to a finished loop (the classic footer, Quick, the phone) keeps the owner's verdict and still carries the loop's comments. The phone line reads `Reviewer and author disagree on <n> · <m> fixed by the author` (since Show Now also `· <k> not answered`, below).
- **v1 limits.** Rounds are capped at 3 (since 2026-11-08 a fuse of 8 for new loops, below) and the timer is per round; no backfill: asks and rows that exist at the upgrade keep the old flow; the findings line is typed by a running Desktop (the sweep covers a gone session and the timeout without it); the phone has the line only.

## Severity and the footer verdicts (2026-10-28, board #1184)

Spec: `docs/superpowers/specs/2026-10-28-spec-review-severity-design.md`.

- Prompt `review.spec` v3: `severity` (`blocker`/`major`/`minor`) on `differs`/`missing` agreements, decided alone, blind spots and `concern` checks. Go `Parse` keeps only the three values and empties it on `as_agreed` and non-concern checks; `Findings` copies it into `AuthorItem`, so the ledger and `get_spec_review` carry it. Keys ignore it; a carried loop item keeps the severity it was raised with. Swift `SpecReviewSeverity` decodes it as optional (an old review has none).
- Desktop: only the severity chip is coloured (red/orange/grey); kind and loop status are one grey chip (`SpecReviewPresentation.loopBadge`); lists sort by severity (`sortedBySeverity`); Meaning's counts lead with the severity counts. Quotes are upright inline Markdown with a left bar; long `; `-joined `changes` render as a list (`OwnerAskPresentation.changesMarkdown`).
- Comments in a loop: chapter findings and concerns take **Fix** / **Comment** (`SpecReviewMarkControls(commentOnly:)`), a picked Fix / Reviewer is right takes **Add Comment** (`SpecReviewMarkComment`) — all the one `comment` mark.
- Verdicts live in the drawer's footer on every step (`SpecReviewVerdictButtons` in `OwnerAskAnswerBar`; ⌘↩ / ⌘⇧↩ through `SpecReviewModel.pressKey` while no field has focus). **Approve** is never off (D7, ask #690): with comment marks it is `approved` with fixes to make (author-loop spec §7); **Request changes** (on with a comment mark, a margin comment or the note) is `changes`, a new round — after a loop a classic visible review (`specLoopStart`). Approve on the reviewer's status page asks once.

## Open-ended loop, Discuss and the summary (2026-11-08)

Spec: `docs/superpowers/specs/2026-11-08-spec-review-discuss-design.md`; plan `docs/superpowers/plans/2026-11-08-spec-review-discuss.md` (board #1036; owner decisions in asks #566, #568, #571, #579, #582, #586; inventory amendments in ask #593; screens approved in ask #602, fixtures in `docs/design/mockups/spec-review-discuss/`). SPECREVIEW-04 and -05 are amended, DEV-06 has twenty-one tools.

- **Storage.** Migration 00177: `spec_reviews.loop_rules` (`0` = the rules of 2026-10-26, a cap of 3 rounds; `2` = `specreview.LoopRulesOpen`). A loop keeps the rules it started with: `specLoopStart` starts round 1 under `LoopRulesOpen` and an advanced round copies the previous row's value, so a loop running at the upgrade finishes under the cap of 3 (no backfill). Migration 00178: `spec_review_questions(id, ask_id, thread, item_key, question, answer, state open|answered|expired|gone, created_at, closed_at)` with a partial unique index (one open question per `thread`), and `spec_review_thread_findings(ask_id, item_key, thread, finding, created_at)`, primary key `(ask_id, item_key)`. Both cascade with the ask; **Go is the only writer** of both (`internal/db/spec_review_threads.go`), the Desktop only reads them. Every question state change is `UPDATE … WHERE state = 'open'`; the loser gets `db.ErrQuestionClosed`, "the question is closed".
- **The loop runs while the author's fixes hold.** `NextRound(round, rules, …)`: under `LoopRulesOpen`, from round 2, the next round runs only when this round's verdicts resolved at least one item the author answered with an **explicit** `fixed` reply and something is still open. A missing reply still counts as `fixed` for the ledger (SPECREVIEW-05) but does not keep the loop going. No such progress ends the loop as `stalled`: the open items move to the ledger as unsettled with "The reviewer and the author stopped making progress" (a `disagree` keeps its reason). Round 1 never stalls. `MaxLoopRounds` is now a fuse of 8 (`MaxRoundsFor(rules)`; `LegacyMaxLoopRounds` 3 for `loop_rules = 0`); reaching it ends with `cap` and "Not settled in N rounds". `AuthorTimeout` and the other exits are unchanged.
- **Drift guards in `Parse`** (`internal/specreview/drift.go`; only for a loop round with `loop_rules ≥ 2` (`LoopRulesOpen`), a legacy loop keeps the old `Parse`). From loop round 2 a non-blocker new finding whose where-quote lies wholly in paragraphs unchanged since the previous ask's snapshot is dropped ("on unchanged text"; a quote spanning paragraphs counts as changed). A new finding with no where-quote passes only as a blocker or when it quotes a source newer than the previous ask (`Sources.NewRefs`: conversation entries, answered asks and comments by time). From loop round 3 a new finding below `major`, an empty severity included, is dropped ("minor finding after round 2"). A new finding whose key is on the closed list, or whose kind and where-quote match a closed item (a reworded repeat), is dropped ("already decided"); an agreement's status is part of its kind there, so dismissing an **As agreed** card never drops a later differs/missing finding on the same passage (owner ruling on the branch review). The changed-text baseline is the previous ask's whole snapshot: only the prompt's copy is trimmed to 300 000 characters. A previous ask with no readable filing time is a note and no source counts as new. Drops are counted in `dropped` and by reason in the result's `dropped_by`. The floor and the fuse count the rounds of one loop; a new loop starts again at round 1.
- **The closed list** (`internal/specreview/chain.go`). `ClosedList` reads the review chain (`db.SpecReviewChain`: the asks linked by `previous_ask_id`, root first, depth capped at 100): ledger entries resolved after a `fixed` reply (or no reply), and every key the owner marked `ok` (Skip, Checked, Author is right) or `not_useful` along the chain; a later `comment` mark (Fix) on a closed key reopens it until something closes it again. Kinds and where-quotes come from the ledgers, open items, results and the owner's thread findings (`spec_review_thread_findings`); a row that does not decode is a note. `BuildInputs` hands it to the reviewer as the `closed_items` block; the previous ask's snapshot is the changed-text baseline.
- **Prompt `review.spec` v4.** The review block carries `loop_round: N` on a loop round under the open-ended rules (none on any other review); the prompt states the closed list, the rising floor, the owner's items of a seeded round, and asks for `brief` and `theses`.
- **A new hidden loop after Request changes (D8).** When the previous review is the owner's (`specreview.OwnerHas`) and the owner answered it `changes` (`AnsweredChanges`), the author's re-round starts a new hidden loop at round 1 under the same conditions as any loop (spec or plan, a Watchtower session, a launcher); otherwise it stays a classic visible review. Approve with fixes keeps today's behaviour. `SeedOf` opens round 1 with the owner's items (each with `owner: true` on the `AuthorItem`, kept through the loop, so the loop screen says "Your item" whatever the kind; stored rows that do not decode, and an answer that does not decode, become notes of the round instead of disappearing): one per comment of the answer (keyed by the comment's `item_key` — `asks.Comment.ItemKey`, written by `SpecReviewAnswer` for a findings comment — else an `oc:` key of its body and quote; kind, text and severity from the finding behind the key, else kind `owner_comment` with the comment as text; the owner's comment is the note; a comment with no body and no finding is left out), then every thread finding of the previous ask not already seeded and not closed; a key marked `ok` or Not useful is never seeded. Answers stored before 2026-11-08 carry no `item_key`, so their finding comments seed as `oc:` owner comments with the owner's words. `NextRound` and `Reveal` settle the seed like any earlier round's open items (`Reveal` on a seeded round that failed shows the owner's items).
- **`get_spec_review`.** `max_rounds` = `MaxRoundsFor(loop_rules)`; the hint no longer says "last round".
- **Summary.** The result gains `brief` (≤ 1200 runes) and `theses` (≤ 10: `key` `th:` + hash of kind and normalised text, so a thread survives a re-run that keeps the thesis; `kind` `goal`|`decision`|`owner_change`|`non_goal`|`risk`; `text`; `where`, validated like any quote; `chapter` from it). A thesis whose quote is not found is dropped and counted. `summary` and `idea` stay.
- **Threads.** A thread is a `chat_conversations` row of context type `spec_review_thread` and context id `<workbench>:<root ask>:<item key>` (`specreview.ThreadContextID`, Swift `SpecReviewThreadKey`, shared fixture `internal/specreview/testdata/thread_keys.json`), so a re-round's card with the same key continues the thread. `watchtower workbench spec-review thread-context --ask N --item K` (read-only) prints the agent's first-turn context as fenced blocks: the snapshot, the item, the whole result, the ledger and replies, and the conversation and asks blocks `BuildInputs` builds (exit 3 "no such item", or "ask N has no spec review"). The Desktop's surface (`SpecReviewThreadSurface`, an `EmbeddedChatEngine` spec) runs the configured provider at the strong tier with `ai query --read-folder-ask <askID>`: the CLI loads the spec or plan review ask and runs in the folder its reviewer read (`specreview.ReadFolder`: the session's recorded working directory when it is still a directory, else the workbench folder; symlink-resolved, exit 2 for any other ask or together with `--read-folder`/`--tools`), so the Desktop computes no folder; whether a turn passes it is the provider's capability row (`read_folder`, LLMTRANSPORT-01): a row that reads none runs on the data alone with "This model cannot read files…" once, and a turn started after a failed catalog read says that instead; `toolAccess: .draftOnly` (AGENT-04: no write tools), the 3-turn embedded gate and `ai query --purpose spec_review.discuss` (the usage ledger's purpose, `LLMPurposeNames` "Spec review — Discuss"). The agent ends a reply with at most one ```` ```watchtower-ask-author ```` block (`{"question": "…"}`) and one ```` ```watchtower-finding ```` block (`specreview.ThreadFindingInput`); the last valid block wins (`SpecReviewThreadBlocks`, shared fixtures `internal/specreview/testdata/thread_blocks/`). A closed block that is not valid becomes a notice row saying why ("The assistant's question to the author could not be sent: longer than 1000 characters."), never nothing. The blocks stay in the stored reply text and are stripped at render (`SpecReviewModel.threadEntries`), so a proposal survives a closed drawer or app; `postTurn` hands the question and the finding over. It never writes and never sets a mark. - **Questions to the author.** `watchtower workbench spec-review question --ask N --item K` files the question on stdin (≤ 1000 characters) and prints its id; exit 3 when the thread already has an open question or the ask has no session. `--close ID --reason gone` closes an open question the Desktop could not deliver. Both are refused under an AI agent's marker (AGENT-07, ask #593). The author answers with the workbench tool `answer_review_question` (`question_id`, `answer` ≤ 2000 runes, required `reason` ≤ 300 runes; workbench surface only, applied directly and audited): refused for an unknown or foreign id ("question N not found"), another session's question ("this question is not for your session") or a closed one. The daemon's `sweepSpecReviewQuestions` (in `phaseSpecReviewSweep`, no launcher needed) closes a question `gone` when its ask has no session row and `expired` after `QuestionTimeout` (= `AuthorTimeout`, 30 min); a stopped session's question waits for the expiry. On an answer the Desktop starts the agent's next turn once with the notice "The author answered (question #<id>): <answer>"; on an expiry or `gone` the notice is "The author did not answer" — or "The question may not have reached the author" when this app run never saw it typed — and the agent is told to continue without it. A line typed without Return or only copied tells the owner what to press in the author's session; a failed read of the questions, and Go's refusal for a thread whose chat is not loaded, show in the thread (the latter when it next opens). The notice row in the thread keeps it from being sent twice, so a thread opened later picks up an answer that landed while the app was closed. The center polls every 3 s only while a thread has an open or undelivered question. Skill pack v20 teaches the line and the tool.
- **Add to review.** `watchtower workbench spec-review add-finding --ask N --thread CONTEXT_ID` reads the proposed block on stdin (≤ 64 KiB) and validates it with `ValidateThreadFinding` — kind `differs`|`missing`|`decided_alone`|`blind_spot`, the quote a real substring of the document snapshot (speaker `agent`) or of the owner's own rows of that thread (`db.OwnerThreadLines`, speaker `owner`), a where-quote anchored in a chapter — then stores it under a `tf:` key and prints `{"key": "tf:…"}` (adding the same finding again prints the same key; a different finding with the same text and where-quote, hence the same key, is refused). Refused under an AI agent's marker (AGENT-07, ask #593): a new finding exists only after the owner presses for it. `show --json` gains `thread_findings` (`[]` when none). ## Rulings that changed behaviour against the spec

- An invalid `doc_type` is refused by `ask_owner` instead of being guessed.
- A surface without a launcher (not the workbench MCP server) records `skipped: no reviewer on this surface`.
- The reviewer gets no MCP servers, not even the watchtower ones, and reads one folder (the session's worktree when recorded, else the workbench folder).
- Neither start has a plan-limit gate (the automatic one lost it on 2026-10-26).
- (2026-11-08) "Dismissed in a thread" is the owner's Skip (`ok`) or Not useful mark on that key: there is no separate thread state, and both put the key on the closed list, so a Not useful finding cannot be raised again.
- (2026-11-08) The drift guards apply only to loops with `loop_rules ≥ 2` (`LoopRulesOpen`); a legacy loop keeps the old `Parse` for its remaining rounds.
- (2026-11-08) An anchored new finding whose source quote is new since the previous ask (`NewRefs`) passes the changed-text guard (the floor and the closed list still apply): a document that contradicts what the owner just said is news.
- (2026-11-08) `Parse` reads no current-row ledger: each loop round is its own ask, and the chain covers earlier rounds (`TestBuildInputs_KeyClosedEarlierInTheLoopDropped`).
- (2026-11-08) A question's "session gone" is the ask's session row deleted (`session_id` NULL), as for the loop's `session_gone`; a stopped session can be resumed, so its question waits for the 30-minute expiry.
- (2026-11-08) `answer_review_question` takes a required `reason` beside `question_id` and `answer`: the registry refuses a write proposal without one, as for `reply_review_comment`.
- (2026-11-08) A plain Fix (no comment) seeds the finding as it stands, with its own anchor when the comment has no quote; an empty-body comment with no finding behind it is left out.
- (2026-11-08) The reviewer's review block names the loop round (`loop_round: N`) so the model sees the round its rules depend on.
- (2026-11-08) The thread reads the reviewer's folder through `ai query --read-folder-ask N`, not a widened `--read-folder`. A first fix let `--read-folder` accept any terminal session's recorded working directory or worktree; it was rejected because it widened the security boundary for every caller (code questions included) to every folder any session ever recorded, with no tie to the review the thread is for. `--read-folder` takes workbench folders only; `--read-folder-ask` takes exactly the one folder of one spec or plan review ask, chosen by the reviewer's own `specreview.ReadFolder`.
- (2026-11-08) A thread reply's blocks stay in the stored text and are stripped at render (the plan said strip in `postTurn`): the Desktop cannot write Go's tables, so stripping in storage would lose an un-added proposal when the drawer or the app closes.
- (2026-11-08) Screens as approved in ask #602: an `n/a` check has no buttons, theses are grouped under titles, **Read the spec** on a thesis opens the document without jumping, the Fixed list opens when it holds an owner item, and the thread agent is labelled "Assistant".

## v1 limits

- Phone: a one-line status only; no findings screen, and it writes no marks (a Not useful mark is not counted in its line).
- `spec_reviews.findings` (migration 00162) is the number of findings in the stored result when the review first finished (a re-run, a `--force` start or a sweep relaunch never rewrites it) (`-1` before the migration); the coach reads it for the first round's count because a re-run replaces `result`.
- Ollama has no file tools, so its reviews are from the data alone and are marked `code_read: false`.
- Marks are the Desktop's alone: the phone answers a review ask without seeing them (they still go with its answer).
- The sweep is the last step of `runSync`: a lost start can wait one whole cycle, and a cycle cancelled before the end skips it.
- `<workspace>/logs/spec-review.log` is appended to and never rotated.
- The reviewer's model usage is not in the usage meter yet (the read-folder `QuerySync` path does not tag its source).
- Without a running daemon, a queued row whose child died before claiming stays queued until the owner runs `start`.
- (2026-11-08) No thread and no summary screen on the phone; its line has counts only.
- (2026-11-08) A thread's follow-up turn on the author's answer needs the Desktop: a running app starts it when the answer lands, otherwise it starts when the thread is next opened. The sweep expires questions without the app.
- (2026-11-08) Questions and thread findings are written by Go only; the Desktop files and closes through the CLI.
- (2026-11-08) An open question is not typed again after an app restart or **Keep Sessions and Quit** (the app cannot tell whether it was delivered; delivered once is preferred to a double paste): it expires after 30 minutes and the thread says "The question may not have reached the author" (this run never saw it typed). A persisted delivery time is a follow-up.
- (2026-11-08) An unsaved Fix draft lives for the app run (the thread center); after a quit only the plain Fix mark stays.

- (2026-11-08) The coach's chat reader (`ListOwnerChatTurnsSince`) still reads the owner's lines of a thread, as it reads code questions; only the ideas miner, chat-artifact knowledge and the Chats list filter them out.

### Reviewer model follows the asking session (2026-11-01)

The reviewer uses the provider of the session that created the ask and the exact latest main-conversation model from that session's transcript. It does not normalize a concrete model to a family alias or upgrade it to a newer model. Missing model metadata uses that provider's configured/default strong model; a missing session uses the existing global default. Transcript read failures are reported, not mistaken for missing metadata. The recorded provider/model match the actual client; global configuration is unchanged.

A successful forced retry after an empty first-round `reviewer_failed` loop becomes a plain review and clears that stale failure banner; existing findings, owner disputes and later rounds retain their loop state.
