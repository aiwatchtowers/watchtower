# Model & Provider Registry (2026-08-18)

- `internal/providers` is the single source of truth for AI backends: `{id, kind cli|http, default light/strong models, live-listing capability}` for `claude` (defaults are the CLI **aliases** `haiku`/`opus` — strong tier moved from `sonnet` to `opus` 2026-10-03 — which track new model releases without a Watchtower release), `codex` (`gpt-5.6-luna`/`gpt-5.6-sol` since 2026-10-18; 2026-10-03 moved off the retired gpt-5.4/5.5, and the `gpt-6-luna`/`gpt-6-astra` defaults of that change were refused by codex-cli 0.145 on ChatGPT sign-in), and `ollama` (OpenAI-compatible HTTP — Ollama/LM Studio/vLLM; `internal/ollama` client+generator, model list via standard `GET /v1/models`). `providers.ResolveModelsFor(cfg, providerID)` resolves per-tier models: `ai.models.light`/`ai.models.strong` → legacy `ai.model` (strong only; a value equal to the retired seeded default `claude-sonnet-4-6` means "never chose" and is ignored — setup no longer seeds it, Desktop onboarding included) → registry default. For `claude`, a pinned **full** model id (`claude-opus-4-6`, `claude-haiku-4-5-20251001`) resolves to its family alias (`opus`/`haiku`/`sonnet`) on either tier, so a pin written once never strands the install on an old release; for `codex`, a pinned retired gpt-5 model (`gpt-5`, `gpt-5.0`–`gpt-5.5` and their `-mini`/`-codex` variants) resolves to the tier default (`normalizePinnedModel`); the still-offered `gpt-5.6-*` pins stay. **Config overrides are scoped to the provider configured in the file** (`AIConfig.ConfiguredProvider`, snapshotted at Load and never mutated by the `--provider` flag): resolving any other provider (per-command `--provider`, the chat provider switch, the `ai models` listing) yields that provider's registry defaults, never the configured provider's models. Ollama ships **no default model** — unconfigured resolves to empty strings and the surfaces prompt the user to pick from the live list; an unset light follows strong (one model configures both tiers).
- The old duplicated 17-source `ModelForSource` switches are gone: one `digest.TierForSource(source) → TierLight|TierStrong` table; generators carry `modelLight`/`modelStrong` resolved at construction, untagged calls use strong. Generator implementations MUST read the source tag via `digest.SourceFromContext` — a locally-declared context-key type never matches (`context` keys compare by concrete type; this exact bug kept codex tier routing dead until 2026-08-18, pinned by `TestGenerate_TierRoutingHearsDigestSource`).
- **Tier-hole closure + property scan (2026-09-13):** two previously-untagged sources that only ever produce a bounded, fixed-shape rule/downgrade output (`catchup.learn`, and `inbox.situation_learn` — the latter removed outright on 2026-09-14 with the situations pipeline, so only `catchup.learn` remains in the tier table) moved to light; eight other untagged `Generate` call sites across `meeting`/`targets`/`prompts` got a source tag with no tier change (stay strong). `internal/digest/tier_scan_test.go`'s `TestTierForSource_EveryGenerateCallIsTagged` is a property scan (via `go/parser`, no compile step) over every `.go` file under `internal/` and `cmd/`: every `Generate(ctx, ...)` call site must carry a `digest.WithSource` tag resolvable to a literal, and every tag routed to strong must appear in an `allowedStrongSources` allowlist with a stated reason — an untagged call or an unacknowledged strong tag fails the build. The scan asserts a floor on how many files/call sites it actually walked (300 files / 30 calls), so pointing it at an empty or wrong root fails loudly instead of passing on nothing. `digest.channel` (strong) vs `digest.channel_batch` (light) is a known inconsistency left untouched pending an owner call — see `docs/audit/2026-09-13-feature-audit/README.md`.
- `watchtower ai models [--json]` prints the registry + resolved models + live Ollama list (best-effort: unreachable server → `error` string, exit 0). Desktop consumes it via `AIModelCatalog` (WatchtowerCore, cached on AppState): Settings → System → AI has per-tier Light/Strong free-text fields with suggestion menus, an Ollama server-URL row, and an Ollama branch in Test Connection; the main AI Chat model picker is dynamic with an **Auto** ("" = resolved strong) default; Discuss chat VMs pass `model: nil` and let the CLI resolve. **No model names are hardcoded in Swift** — keep it that way.
- **Refused codex models (2026-10-18, board #666).** codex-cli 0.145 with a ChatGPT sign-in refuses `gpt-6-astra` ("requires a newer version of Codex") and `gpt-6-luna`/`gpt-5.4` ("not supported when using Codex with a ChatGPT account"); `codex debug models` lists `gpt-5.6-sol`/`-terra`/`-luna`, hence the defaults. codex exec reports a failed turn only in its JSONL stdout (`turn.failed`, after a top-level `error` event with the same text) and exits 1 with an empty stderr, so the error used to be "codex CLI failed with exit code 1". `internal/codex` (`runError`/`failedTurn`/`turnError`, `model_errors.go`) now reads the reason from stdout: turn.failed first, a top-level `error` line only when there is none (alone it may be a retry notice, so it counts only once the run failed). The server's JSON envelope is unwrapped to its message with its type and status kept ("codex error (rate_limit_error, status code 429): …", so `digest`'s `aiUnavailable` still classifies rate limits and outages as transport failures); the exit error stays a cause (`digest.WithCause`) and a non-empty stderr stays in the text — except on a refusal, which never picks up stderr (its transport words would make it an `ErrAICall`). Three exact phrasings become `*ModelUnavailableError`: "requires a newer version of Codex" → "Codex needs an update to use <model>: run `codex update`, or pick another model in Settings → System → AI"; "not supported when using Codex with a ChatGPT account" and "does not exist or you do not have access to it" → "<model> isn't available on your Codex account: pick another model in Settings → System → AI". There is no automatic fallback. **Dual path:** Settings → Test Connection runs `codex exec --json` and reads the same stdout through `ConnectionTest.codexTurnError` (WatchtowerCore) with the same wording; both sides are pinned by `internal/codex/testdata/turn_failures.json` (`TestFailedTurn_SharedFixture`, `ConnectionTestTests`).
