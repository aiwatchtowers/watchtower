# Model & Provider Registry (2026-08-18)

- `internal/providers` is the single source of truth for AI backends: `{id, kind cli|http, default light/strong models, live-listing capability}` for `claude` (defaults are the CLI **aliases** `haiku`/`opus` — strong tier moved from `sonnet` to `opus` 2026-10-03 — which track new model releases without a Watchtower release), `codex` (light `gpt-5.6-luna`, strong `gpt-6-astra`; 2026-10-03 moved off the retired gpt-5.4/5.5 models, 2026-10-18 the light tier left `gpt-6-luna`, which the server refuses on ChatGPT sign-in), and `ollama` (OpenAI-compatible HTTP — Ollama/LM Studio/vLLM; `internal/ollama` client+generator, model list via standard `GET /v1/models`). `providers.ResolveModelsFor(cfg, providerID)` resolves per-tier models: `ai.models.light`/`ai.models.strong` → legacy `ai.model` (strong only; a value equal to the retired seeded default `claude-sonnet-4-6` means "never chose" and is ignored — setup no longer seeds it, Desktop onboarding included) → registry default. For `claude`, a pinned **full** model id (`claude-opus-4-6`, `claude-haiku-4-5-20251001`) resolves to its family alias (`opus`/`haiku`/`sonnet`) on either tier, so a pin written once never strands the install on an old release; for `codex`, a pinned retired gpt-5 model (`gpt-5`, `gpt-5.0`–`gpt-5.5` and their `-mini`/`-codex` variants) resolves to the tier default (`normalizePinnedModel`); the still-offered `gpt-5.6-*` pins stay. **Config overrides are scoped to the provider configured in the file** (`AIConfig.ConfiguredProvider`, snapshotted at Load and never mutated by the `--provider` flag): resolving any other provider (per-command `--provider`, the chat provider switch, the `ai models` listing) yields that provider's registry defaults, never the configured provider's models. Ollama ships **no default model** — unconfigured resolves to empty strings and the surfaces prompt the user to pick from the live list; an unset light follows strong (one model configures both tiers).
- The old duplicated 17-source `ModelForSource` switches are gone: one `digest.TierForSource(source) → TierLight|TierStrong` table; generators carry `modelLight`/`modelStrong` resolved at construction, untagged calls use strong. Generator implementations MUST read the source tag via `digest.SourceFromContext` — a locally-declared context-key type never matches (`context` keys compare by concrete type; this exact bug kept codex tier routing dead until 2026-08-18, pinned by `TestGenerate_TierRoutingHearsDigestSource`).
- **Tier-hole closure + property scan (2026-09-13):** two previously-untagged sources that only ever produce a bounded, fixed-shape rule/downgrade output (`catchup.learn`, and `inbox.situation_learn` — the latter removed outright on 2026-09-14 with the situations pipeline, so only `catchup.learn` remains in the tier table) moved to light; eight other untagged `Generate` call sites across `meeting`/`targets`/`prompts` got a source tag with no tier change (stay strong). `internal/digest/tier_scan_test.go`'s `TestTierForSource_EveryGenerateCallIsTagged` is a property scan (via `go/parser`, no compile step) over every `.go` file under `internal/` and `cmd/`: every `Generate(ctx, ...)` call site must carry a `digest.WithSource` tag resolvable to a literal, and every tag routed to strong must appear in an `allowedStrongSources` allowlist with a stated reason — an untagged call or an unacknowledged strong tag fails the build. The scan asserts a floor on how many files/call sites it actually walked (300 files / 30 calls), so pointing it at an empty or wrong root fails loudly instead of passing on nothing. `digest.channel` (strong) vs `digest.channel_batch` (light) is a known inconsistency left untouched pending an owner call — see `docs/audit/2026-09-13-feature-audit/README.md`.
- `watchtower ai models [--json]` prints the registry + resolved models + live Ollama list (best-effort: unreachable server → `error` string, exit 0). Desktop consumes it via `AIModelCatalog` (WatchtowerCore, cached on AppState): Settings → System → AI has per-tier Light/Strong free-text fields with suggestion menus, an Ollama server-URL row, and an Ollama branch in Test Connection; the main AI Chat model picker is dynamic with an **Auto** ("" = resolved strong) default; Discuss chat VMs pass `model: nil` and let the CLI resolve. **No model names are hardcoded in Swift** — keep it that way.
- **Refused codex models (2026-10-18, board #666).** codex-cli 0.145 with a ChatGPT sign-in refuses `gpt-6-astra` ("requires a newer version of Codex") and `gpt-6-luna`/`gpt-5.4` ("not supported when using Codex with a ChatGPT account"); its catalog (`codex debug models`) lists `gpt-5.6-sol`/`-terra`/`-luna`. codex exec reports the refusal only in the JSONL `turn.failed` event and exits 1 with an empty stderr, so the old error was "codex CLI failed with exit code 1". Now `internal/codex` reads the failed turn from the output (`failedTurn`/`turnError`, the server's JSON envelope unwrapped to its message) and turns a refusal into `*ModelUnavailableError`: "Codex needs an update to use <model>: run `codex update`, …" or "<model> isn't available on your Codex account: …". On that error `Generate`, `QuerySync` and `Query` (only before any chunk went out) retry once with `providers.FallbackModel` (`FallbackLight` `gpt-5.6-luna`, `FallbackStrong` `gpt-5.6-sol`; a `Client` counts as strong), log the swap, and remember it for the life of the process (`refusedModels`), so the daemon pays the refused attempt once. If the fallback fails too, the error keeps the configured model's refusal first. The strong default stays `gpt-6-astra` for an up-to-date Codex.
