# Revoked access wipes the account's data (2026-10-21, board #601)

When a company revokes the owner's Slack, Google, Jira or Linear access, or an install has not reached a source for 30 days, and the purge is on, the account's synced data is deleted after a notice (72 h, or the organization's `PurgeGraceHours`) unless the owner reconnects first. **Off by default** (owner decision 2026-11-23): it is on only when the owner turns it on, the organization's policy forces it, or the corporate build sets it. Part of board group #595 (corporate data on the Mac). Spec: `docs/superpowers/specs/2026-10-21-revoke-purge-design.md` (approved 2026-10-21, ask #474: Q1 on in the corp build and under a future MDM policy, opt-in elsewhere — overturned 2026-11-17 (#1769, ask #1412): on by default everywhere, with origin `default` covering revoked and removed accounts only — itself overturned 2026-11-23 by the owner: off by default again, because unlinking an old company Slack app while swapping it for a new one scheduled the whole workspace's history for deletion; Q2 (a); Q3 72 h; Q4 30-day lease; the LINEAR-03 amendment). Plan: `docs/superpowers/plans/2026-10-21-revoke-purge.md` (ask #477: the lease counts disabled accounts, and removed accounts get a lease of their own). Contracts: PURGE-01..02 in `docs/inventory/account-purge.md`, LINEAR-03 amended in `docs/inventory/linear.md`; SLACK-01 unchanged in what it keeps (amended in #1769: `slack remove` revokes the token). User guide: `docs/guide/concepts/revoked-access.md`.

## Schema (migration 00148)

- `access_ok_at`, `revoked_at` (TEXT, `''` = unset, RFC 3339 UTC) on `slack_accounts`, `google_accounts`, `jira_accounts`, `linear_accounts`. The migration stamps `access_ok_at` = now on every row (removed ones too) and `revoked_at` = now on revoked rows, so an upgrade never starts a clock in the past.
- `account_purges(id, source, account_id, reason revoked|lease, scheduled_at, due_at, state scheduled|running|done|cancelled|failed, started_at, finished_at, rows_deleted, error, failures)`, one open (scheduled or running) row per account (`idx_account_purges_open`). `failures` counts chunk failures since the last chunk that deleted rows; `failed` is terminal. No foreign key: four parent tables, and the account row is never deleted.
- New `status` value `purged` (no CHECK on any of the four columns).

## Access facts

- `revoked_at` is kept by the `Set*AccountAuthState` writers themselves (`internal/db/account_access.go`): `revoked` sets it when empty (kept on a repeat, restamped when `access_ok_at` is newer: a new revocation after confirmed access), `ok` clears it, `error` keeps it. Every existing writer (sync phases, the `login` paths) is covered with no new call. Both columns are fixed-width RFC 3339 UTC, so SQL compares them as text.
- `access_ok_at` is set by the same writers on `ok` (Slack and Google write `ok` after a clean sync). Jira and Linear passes never write `ok` (LINEAR-03), so the daemon calls `db.MarkAccountAccessOK(source, id)`; it touches `access_ok_at` only. Linear: after a nil `Sync` error (every pass starts with a viewer query). Jira: whenever `ReachedSource()` is true (a project's issue search came back), whatever the pass returned after, except `ErrAuthRevoked`. A clean Confluence sync stamps its Jira account's access too (not while the account is held): one Atlassian grant covers both, and an account used only for Confluence makes no Jira request.
- A local change that makes no authenticated call proves no access: `google disconnect <service>` (`gmail logout`, `calendar logout`) clears a plain `error` with `ClearGoogleAccountError` (status `error` and no `revoked_at` only) and never writes `ok`.
- A `purged` row refuses every auth-state write except `ok` (`authStateWhereSQL`); that `ok` (a Re-login) re-enables Slack/Jira/Linear rows and starts the account over as a first sync. `MarkAccountAccessOK` leaves a purged row alone. In the owner ladder (OWNER-01) and the sidebar a purged account counts as removed (ask #491, #858): no rung takes it, and a source whose only accounts are purged hides its tab.

## The switch

`purge.Enabled(cfg)` returns the effective value and its origin, strongest first: the organization's forced `PurgeRevokedData` managed preference (#608, `policySwitch`) > the config key `privacy.purge_revoked_data` (tri-state `*bool`, absent = build default) > the build default `purge.BuildDefault` (ldflags from `WATCHTOWER_PURGE_DEFAULT`, which `Makefile` and `scripts/build-app.sh` pass next to the OAuth client ids; the corporate build profile sets `WATCHTOWER_PURGE_DEFAULT=on`, origin `build`) > **off, origin `default`** (owner decision 2026-11-23, every build, every source; it replaced #1769 A1's on). The switch is therefore on only by a setting, a policy or the build, and every such origin gives the same rules: `purge.Rules(on, policy.SourceAllowed)` turns the switch into a per-account rule (A21; the origin-default rule `RuleRevokedAndRemoved` for every account is gone with the default on):

| Switch, origin | Live account | Removed account | Revoked account |
|---|---|---|---|
| off | `RuleNone`: nothing scheduled, scheduled rows cancelled | none | none |
| off, origin `default` (nothing set) | `RuleNone` | none | none |
| on, origin `setting`, `policy` or `build` | `RuleFull`: the 30-day lease | Slack: zero lease (due the grace after the first pass after the remove); others: the 30-day removed lease | the grace |
| on, source forbidden by policy (POLICY-03) | `RuleRevokedAndRemoved` (lease held) | `RuleNone` (lease held) | the grace |

**The grace.** `purge.Grace` (72 h) is the standard notice. The organization's `PurgeGraceHours` managed preference (an integer 0…720, `policy.PurgeGraceHours`) replaces it whatever turned the purge on (`purge.EffectiveGrace`, read by `Plan` on each pass); there is no config key or CLI flag for it. `0` makes a row due at the pass that schedules it, so the next run (the next cycle's first pass) executes it. A non-integer value is a `wrong_type`, a value out of range an `unknown_value`; both leave the 72 h notice (POLICY-02 fixture). A changed grace applies to rows scheduled after the change; a scheduled row keeps its `due_at`, shortened or lengthened alike (`TestPurge01_GraceChangeKeepsScheduledRows`).

Go and the Desktop read one fixture of the default, `internal/purge/testdata/default_cases.json` (policy, setting, build default, CLI status → shown value and origin): `TestPurge01_DefaultSharedFixture` runs its cases without a CLI status against `Enabled`; the cases with `status_enabled` set are the Desktop's alone (and `build` is Go's alone: the Desktop learns the build default from the CLI status). The Desktop never re-implements it: it reads `enabled`/`enabled_by` from `watchtower accounts purges --json`, writes only the config key (Settings → System → Privacy, absent stays absent until the owner toggles), and restarts the daemon after a Save that changed it, since the daemon reads config only at startup.

## Scheduling (`phaseAccountPurge` first in every cycle, `phaseAccountPurgeLeases` after the syncs)

`purge.Plan(accounts, open, rules, now)` reads the account rows and the open ledger rows only; `purge.Apply(d, rules, leases, now)` writes its decision, joining write errors and continuing past a bad row. Both daemon passes build the rules the same way (`Daemon.purgeRules`: `purge.Enabled` + the live `policy.SourceAllowed`) and hand them to `purge.Run` too. Two passes a cycle: `phaseAccountPurge` runs first (cancels, revoked schedules, then the due purges) and schedules no lease row; `phaseAccountPurgeLeases` runs after `phaseExternalSync` with leases on, so a Mac back from a long absence first lets the cycle's syncs prove access instead of getting a false notice. Its due rows run next cycle.

- **`RuleNone` (off, or a removed account of a forbidden source):** every scheduled row of the account is cancelled; nothing is scheduled; a running row finishes.
- **Revoked:** a revoked account is scheduled due the grace after the first pass that sees it (`now + grace`; `revoked_at` is never in the future, so it cannot set a later date). Cancelled when the account is no longer revoked or in error, or when its `access_ok_at` is newer than its `revoked_at` (a clean Jira/Linear pass); no new row is scheduled for such an account. An empty or unreadable `access_ok_at` is no proof: still revoked. A due row runs only while the account is still `revoked`; `error` waits (the Desktop line says it is on hold).
- **Lease (live accounts under `RuleFull`, status not removed/purged, disabled included):** when every live account of a source has an `access_ok_at` and the newest is older than 30 d − the grace, each is scheduled due now + the grace (on a daemon that runs every cycle, the 30-day mark). An empty `access_ok_at` is no evidence: that source is never lease-scheduled. Under `RuleRevokedAndRemoved` (a forbidden source) a live account has no lease, and an open live lease row is cancelled.
- **Lease (removed accounts):** a removed account whose own `access_ok_at` is older than 30 d is scheduled due now + the grace. A removed **Slack** account has a zero lease (A2): its deadline is its `access_ok_at` (the zero time when empty — the remove itself is the evidence), so the first pass after the remove schedules it, due the grace later (`TestPurgePolicy_RemovedSlackZeroLease`). A zero-lease row scheduled before the account's latest `access_ok_at` (added back and removed again before the next pass) is cancelled, and the next pass gives a fresh notice; `StartAccountPurge` refuses it too (`TestPlan_ReaddAndRemoveAgainReschedules`). `removeSlackAccount` cancels the account's scheduled rows before it marks the row removed (`CancelScheduledAccountPurges`), so a lease row scheduled while the workspace was live never runs at its old due date; the next pass schedules a fresh one (`TestApply_RemoveAfterLiveLeaseGivesFullNotice`). Removed accounts are not part of their source's live set.
- A lease row is cancelled when its account's deadline moves past the row's `due_at` (fresh access, the account added back, or a rule that gives it no lease) and runs only once the deadline has passed.
- **Deviation from the plan text:** every due date is at least the grace (72 h unless `PurgeGraceHours` sets another) after the pass that schedules it, so the notice always shows for the full grace period (also when the purge is turned on for an account revoked long ago, or the daemon was off longer than the lease).

The daemon then keeps `purgeHold`: the sync phases, the reaction poll (`reactioncmd.Pipeline.SetAccountSkip`), the history backfill and the Confluence access stamp skip accounts being or already purged, so a syncer wired at startup never refills one. `Run` refreshes it before the startup calendar sync too. A row failed by its chunks releases its account; one failed by the verify count holds it (below).

## Running a purge (`purge.Run`)

The plan is a snapshot, so a scheduled row is started only after `Run` re-plans that one account against the current rows with the scheduler's rules (a zero-lease row stays due there, `TestRun_ZeroLeaseRowStartsAfterReplan`); `StartAccountPurge(id, cutoff, requireRemoved)` — the row's own cutoff from `purge.Cutoff`: `now − Lease`, or `now` with the account required to be still `removed` for a removed Slack account's zero lease — is one conditional `UPDATE … WHERE state = 'scheduled'` that also re-checks the account, so an access proof written between the re-plan and the start cannot start the purge: a revoked row needs the account still `revoked` with no `access_ok_at` newer than its `revoked_at` (an empty time on either side is no proof); a lease row needs a non-purged account with no `access_ok_at` newer than the cutoff in its lease scope (its own for a removed account, every live account of its source otherwise, as in `Plan`), and with `requireRemoved` the account still `removed`, so an "add again" after the re-plan wins (`TestStartAccountPurge_ZeroLeaseNeedsRemovedStill`). It reports whether it changed the row. A row that is cancelled, no longer due, or whose account no longer qualifies returns `purge.ErrNoLongerDue` and nothing is deleted (`TestRun_AccessBetweenReplanAndStart`, `TestStartAccountPurge_AccountMustStillQualify`).

`(*db.DB).PurgeSteps(source, id)` is an ordered list of idempotent statements (dependents before the rows their predicates read). It reads the ids the knowledge steps need (the account's stream digests and Confluence spaces) first, read only, outside any write transaction; every `kb_documents`, `kb_dirty` (by `source`) and `doc_links` (by `from_kind`) delete is a primary-key range, never a scan inside `BEGIN IMMEDIATE` (`TestPurge02_KnowledgeStepsUseKeyRanges`, EXPLAIN QUERY PLAN). `RunPurgeStep` deletes at most 500 rows of the step's driving table per transaction and is repeated until it affects nothing; `AddPurgeRows` counts them on the ledger and resets `failures`. A cycle spends at most 5 minutes (`purgeCycleBudget`); an unfinished purge stays `running` and resumes from the top of its (re-read) list next cycle. A failed chunk is recorded in `error` and retried next cycle; the third failure in a row (`purge.MaxChunkFailures`) ends the row in `failed` (`finished_at` set, account untouched, hold released; the Desktop shows the error and notifies once). A revoked or still-stale account is then scheduled again, with a new notice. After the last step `Run` verifies (#1769, A4): `(*db.DB).PurgeLeft(ctx, steps)` runs the count form of each step of the list the run executed (`PurgeStep.Count`: the same predicate as `SELECT count(*)`; the ids were read before the deletes) in one read-only transaction under the run's context and remaining budget, and returns the tables with rows left. None → on to the tokens; a shutdown or spent budget → a pause (row running, no failure counted); rows left end the row `failed` at once with `error = "left: <table>=<n>, …"` (tables sorted, `TestPurgeRun_VerifyLeftRowsFails`); a failed count is a failed chunk (`TestPurgeRun_VerifyErrorRetries`). A verify failure holds a **revoked or removed** account (spec §9, `purge.VerifyHeld`): while its newest ledger row is such a failure and no access was confirmed at or after it, `Apply` gives it `RuleNone` (never rescheduled — no new notice every 72 h for a leftover the steps cannot delete) and, with the purge on, `refreshPurgeHold` keeps the syncs off it; only a Re-login or adding a removed account back releases it (the syncs skip it, so no clean pass can). A live account is never held: it keeps syncing and its lease schedules it again with a new notice. The stream digest and Confluence space steps delete a parent only while none of its knowledge rows is left, in the same statement (`delParent`; their count form counts every such parent), so a purge resumed after those steps never loses the ids its verify count needs (`TestPurgeRun_ParentKeptWhileKnowledgeLeftAcrossCycles`). Same-second clocks resolve toward keeping data: access stamped in the second a zero-lease row was scheduled cancels it, and in the second a verify failed releases the hold. Token files are deleted after the verify, outside any transaction (Jira/Linear under their token lock); no remote revoke call is made. `FinishAccountPurge` then, in one transaction, requires the row to be `running` (else `db.ErrPurgeNotRunning`), marks it `done`, resets the account's sync clocks and marks it `purged`.

A Re-login during the run: the Desktop disables **Re-login** while the account's purge runs, and every CLI login path refuses before its first write — `slack login`/`add` and the onboarding auth (`connectSlackAccount`), `google login`/`add`, `gmail login`, `calendar login` (`loginAndSaveGoogleToken`, after the consent, before the token save), `jira login`/`add` (`connectJiraAccount`), `linear login` (`relinkLinearAccount`) and `linear add` reviving a removed workspace (`reviveLinearAccount`): `refuseLoginDuringPurge` over `db.AccountPurgeRunning(source, id)` returns "<source> account <id>: watchtower is deleting this account's data; log in again once it finishes (see 'watchtower accounts purges')" and no token file or account column is written. If access is confirmed anyway at or after `started_at` (`PurgeAccessReturned`: a login whose check ran just before the row started), the token files are kept and `FinishAccountPurge` keeps the account (status and enabled untouched, sync clocks reset so it starts over) and closes the row `done` with a note in `error`. Left: a login that passed its check before the start and writes between the `PurgeAccessReturned` read and the token delete; with the purge spanning cycles that window is a few milliseconds. The start side has no such gap: an access proof that lands before `StartAccountPurge` keeps the row scheduled (above).

### What each source deletes

- **Slack** (namespace `<id>:`): messages, reactions, files; inbox items of Slack trigger types and the situations whose every signal is such an item; learned rules scoped to its channels and senders; the account's channel digests (cross-channel digests have `channel_id ''` and stay) with their KB documents and feedback; tracks whose every channel is the account's; user analyses, people cards, `user_interactions`; `issue_slack_links`, reaction commands and events, reminders; `sync_state`, watch list, channel settings, user checkpoints, users, channels; KB documents under `slack:thread:<id>:` and `slack:day:<id>:` with their `kb_dirty` marks and `doc_links`; `history_backfill`.
- **Google:** `gmail_messages`; inbox items of its Gmail threads and of the calendar events it deletes; learned rules; `meeting_prep_cache` and KB documents of those events; calendar events and emptied calendars (`purgeGoogleAccountCalendarsTx` rules: events a transcript or recap references are kept, and their calendars are detached); Gmail stream digests and their KB documents; KB documents under the Gmail prefix; `history_backfill`.
- **Jira:** inbox items whose key is the account's issue and no other account's; every `jira_*` table with `account_id`; the account's Confluence `ext_comments`, `ext_documents`, their KB documents, marks and `doc_links`, and its `ext_sources` rows; Jira stream digests; KB documents under `jira:<id>:`; `history_backfill`.
- **Linear:** inbox items as for Jira; every `linear_*` table with `account_id`; Linear stream digests; KB documents under `linear:<id>:`.
- The account row is kept with `status = 'purged'`, `error` cleared, `enabled = 0` (Google: `gmail_enabled = calendar_enabled = 0`), and its sync watermarks reset (`purgedAccountSQL`), so a Re-login is a first sync.

Scope additions beyond the spec's list: stream digests and their KB documents, `doc_links`, `meeting_prep_cache` of deleted events, `user_interactions`, the Jira account's Confluence `ext_*` rows, and the watermark reset. Kept on purpose (`purgeKeptTables` in `internal/db/account_purge_steps_test.go`, enforced by `TestPurge02_EveryAccountTableCovered`): `imap_messages` (IMAP is not a purge source), `account_purges`, `jira_user_map`, `linear_user_map` (identity maps keyed by the provider's user id). AI text that mixes sources is kept: briefings, Catch-Up recaps, ideas and decisions, memory, chats, automation outputs, transcripts; so are digests and tracks spanning several accounts.

## CLI

`watchtower accounts purges [--json]` lists the ledger, newest first, every state (`scheduled`, `running`, `done`, `cancelled`, `failed`); a done, cancelled or failed row's text line shows its finish time. Text: a header `Purge on revoked access: on (build default)` (`off (default)` when nothing set it) and one line per row. `--json` (pinned by `TestAccountsPurgesJSONKeys`):

```json
{"enabled": true, "enabled_by": "policy|setting|build|default", "grace_hours": 72, "lease_days": 30,
 "purges": [{"id", "source", "account_id", "account_label", "reason", "state", "scheduled_at", "due_at",
             "started_at", "finished_at", "rows_deleted", "error"}]}
```

`grace_hours` is the effective notice (`purge.EffectiveGrace`: the organization's `PurgeGraceHours`, else 72). Times are RFC 3339 UTC, `""` when unset; `purges` is `[]`, never `null`; `account_label` is `""` when the account row is gone. There is no command to purge sooner or to export first.

## Slack remove and verified deletion (2026-11-17, #1769)

- `slack remove` and `auth logout` revoke the account's token at Slack (`auth.revoke`, best effort, 10 s) before the token file is deleted; that ends the user's authorization of the app everywhere, so another Mac using the same sign-in sees a revoked token and deletes its copy after its own notice, if its purge is on. A failed revoke never blocks the remove and prints "Slack did not confirm the token was revoked; it may stay valid until a workspace admin removes the app".
- With the purge on, a removed Slack account is due the grace after Watchtower's next pass after the remove (zero lease); adding it back cancels it (`StartAccountPurge(requireRemoved)` re-checks in the same `UPDATE`).
- After the last step `purge.Run` counts what each step's predicate still matches (`db.PurgeLeft`). A non-zero count ends the row `failed` with `left: <table>=<n>, ...`. A revoked or removed account whose row failed that way stays held (no retry, no new notice) until a Re-login or adding it back; a live account keeps syncing and retries under its lease.
- Kept after a purge, and said so in the guide and the privacy policy: AI text that mixes sources (PURGE-02).
- The policy text for the site is `docs/legal/2026-11-17-privacy-policy-slack-changes.md`; nothing there is applied in this repository.
