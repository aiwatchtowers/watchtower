# Developer Surface — MCP tools + skill pack (2026-08-09)

- Watchtower as a knowledge base a developer's coding agent can query directly. Two mechanical (no AI call) read tools, today registry entries in `internal/tools/` mounted by `internal/mcp/`: `get_task_context` (`taskcontext.go`, one Jira key → the ticket + comments, its linked Slack threads resolved to full conversations via `jira_slack_links` → thread, meeting mentions, registry decisions via the exact `idea_mentions(source='jira', ref=<KEY>)` lookup, and the people involved — every section capped and omitted rather than emitted empty when there's nothing to show), `find_experts` (`experts.go`, "who to go to" for a `topic`/`issue_key`/`emails` list — ranked candidates carrying countable evidence with refs, never a bare verdict, plus the ranking weights and `people_cards` enrichments for decision role and communication style). A third pair, `list_situations`/`get_situation` (`situations.go`), shipped with this feature and was **removed on 2026-09-14** with the situations pipeline — see Attention detection. `db.GetSituation`/`db.ListSituations` backed only that pair and, having no other production caller, were deleted alongside it; `internal/db/situations.go` now keeps just `ListSituationSignals` (memory's chat ingest) plus `ConvertedSituationIDs` in `internal/db/memory.go` (memory's operational mirrors). Backing query gaps closed to support the set also included `db.GetJiraCommentsByIssueKey`, and `db.SearchTranscripts` over a new `transcripts_fts` FTS5 index (migration 00052) — the only keyword search Watchtower had over meeting transcripts before this branch was none; the same function also backs a new optional `query` argument on the pre-existing `list_transcripts` tool.
- The know-how layer ships as three skills embedded in the binary (`internal/devpack/skills/watchtower-{task-context,who-to-ask,why-decision}/SKILL.md`, `//go:embed` per the migrations precedent; a fourth, `watchtower-whats-changed`, was removed on 2026-09-14 with the two situations tools it was built on) — each a trigger + tool-call sequence + presentation rule teaching the dev's agent when and how to use the tools above, not new facts. `watchtower integrate claude-code [--scope user|project] [--path DIR] [--skills-only]` installs the pack into the client's skills directory and registers the MCP server (`claude mcp add watchtower -- <bin> mcp`, printed as a manual step if the `claude` CLI is absent); `integrate status` reports each skill's installed/drifted/missing state plus the resolved binary; `integrate remove` deletes only marker-carrying files and unregisters the server. The installer (`internal/devpack/install.go`) never overwrites a user-edited skill — a `.watchtower-shipped` digest sidecar tells "we upgraded the pack" apart from "the user edited their copy," and a file without the `x-watchtower-pack` frontmatter marker is never touched at all.
- See `docs/inventory/dev-surface.md` for the DEV-01..05 contracts (read-only forever, no AI in the data layer, evidence not verdicts, the installer never clobbers, pull only).
