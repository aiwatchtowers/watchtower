# Workbench — Claude Code works a folder-bound board (2026-09-29, POC; renamed 2026-10-02)

- A **workbench** is a folder (table `projects`, migration `00081`; `folder_path` symlink-resolved and UNIQUE) with sources (`project_sources`), attached markdown documents (`project_documents`, `rel_path` inside the folder), owner↔agent comments (`project_comments`: on a target, on a document with a text anchor `anchor_quote/prefix/suffix/heading`, or a reply; roots `open|resolved|outdated`) and a board of ordinary `targets` rows carrying `project_id` (`level='custom'`, `custom_label='project'`, `source_type='chat'`). Separate from the AI Chat's projects (`chat_projects`), which keep the name Projects. Until 2026-10-02 this feature was itself called Projects; see **Rename** below for what still says `project`.
- **PROJ-01:** a workbench target never reaches a non-board reader — `TargetFilter.WorkbenchID` 0 = exclude (the default for every existing caller), plus `project_id IS NULL` in next-step, briefing targets, counts, due-notify, catch-up, memory mirrors, day plan, channel stats and the extract/dedup snapshots; Swift `TargetQueries.fetchAll/fetchCounts/fetchDistinctTags` (so the Targets badge), the chat `@` picker, and "Wipe LLM data" (which would otherwise delete them as `source_type='chat'`).
- Work is done by Claude Code in the folder — the owner's own terminal or the Desktop's embedded SwiftTerm terminal (`TerminalCenter` on AppState, one process per `terminal_sessions` row — migration `00084`, a named claude/shell session that `watchtower terminal title` AI-names from its first owner messages — launched as `claude --session-id <uuid>` and relaunched with `--resume` only when `~/.claude` holds its transcript (never `CLAUDE_CONFIG_DIR`, a dual path with Go `defaultTerminalClaudeDir`); SIGHUP → SIGKILL after 3 s, closed by `QuitCoordinator`; a session is only running or not — there is no Close action (removed 2026-10-01; Delete… removes the row, and `terminal_sessions.closed_at` is a legacy column nothing reads or writes). Both see the board through `watchtower mcp --workbench N` (**DEV-06**: writes only workbench N's rows, applied directly under `tools.Binding.DirectApply` with an `agent_actions` audit row, never an `External` tool; plain `watchtower mcp` stays read-only, DEV-01) and a `SessionStart` hook running `watchtower workbench brief --workbench N` (≤ 4000 chars, always exit 0).
- `watchtower integrate claude-code --workbench N` installs, locally and never committed: the `watchtower-workbench` skill (setup, plan = board, comment discipline; DEV-04 marker + digest), the hook merged into `.claude/settings.local.json` (a malformed file is left byte-identical and reported; a well-formed one has its keys re-sorted alphabetically by the merge — values byte-exact, so a diff of the file shows only that reordering), `claude mcp add --scope local watchtower-workbench`, and `.git/info/exclude` lines; `integrate remove --workbench N` undoes exactly those (**PROJ-04** never overwrites the owner's own content). `watchtower workbench create|list|show|board|import-docs|attach-doc|delete|brief|check|resync`; `create` (and `import-docs <id>`, additive, idempotent, `--dry-run`) mechanically attaches the folder's root `README.md` plus `.md`/`.txt` files directly inside a `specs`/`plans` directory under `docs/` (`internal/workbenchdocs`, no AI, symlinks never followed, ≤ 50 new per run, README first then newest) as `project_documents.origin='import'` (migration `00083`; `agent` for `attach_document`, which also flips an imported or owner row to `agent` on re-attach — the path compared ignoring case, the stored spelling kept; `owner` for the Desktop Documents pane's **Add Document…**, which runs `watchtower workbench attach-doc <id> <path>` — `attach_document`'s checks via `tools.ResolveWorkbenchDocumentPath`, absolute paths allowed, an already attached path left untouched) — only an `agent` row is ever "revised": the Desktop badge, the document list's revised dot and the "ready for review" notification skip `import` and `owner` rows until an agent re-attach turns them `agent`; a path below `docs/` it cannot read is skipped and reported (`unreadable`, `<rel_path>: <reason>`), only an unreadable folder or `docs/` fails the import, and `create --json` reports a failed import in `docs_import_ok`/`docs_import_error` (the Desktop's workbench page shows a failed import, unreadable paths and files past the cap, each with the retry command); board targets carry `priority` (`create_targets`/`update_target`), and board siblings sort by priority, then status (the brief lists subtrees holding in-progress, then blocked work first, keeping priority order within a rank, so the 4000-char cut never drops active work); `delete` runs the removal first and deletes rows in one transaction (**PROJ-02** nothing left behind).
- Desktop: sidebar **Workbench** tab (list + badge = unread agent comments + revised documents) with a collapsible, resizable (`projects.panelWidth`) two-level panel (**Workbenches** + standalone **Terminals** → one workbench's sessions, in a stable drag-reorderable order, `TerminalSessionOrder`; the page header's **Terminal | Board | Documents** toggles — `WorkbenchesViewModel.showView`/`hideView` over `WorkspaceLayout.isShowing`/`showWorkbenchView`/`hide` — put a view on screen without hiding the terminal (Terminal: a session already in a slot, else the live one, else `openMostRecentSession` with `keeping`), and turning one off closes that pane of a split; in a split each pane's slim header also picks what it shows; a single pane has no header, so the terminal gets the height). The workbench page renders a per-workbench `WorkspaceLayout` (WatchtowerCore, UserDefaults `projects.layout.<id>`; single pane, side-by-side split with a draggable divider, any pane expandable; both slots stay in the view tree while one is expanded so pane state survives) — the layout is the only record of what is on screen, and every session placement goes through `WorkbenchesViewModel.Placement` (`show` = panel click, `keeping` = Send comments/Open terminal/Work on it keep the pane they came from in a split (a single pane switches to the session), `replacing` = a pane's own picker, `inPlace` = buttons inside the pane). **Work on it** on a board card/detail (`WorkOnTargetButton` → `WorkbenchesViewModel.workOn`) opens the target's most recent session (`TerminalSessionPolicy.sessionForTarget`, resumed) or creates one titled after the target and launched with the fixed argv prompt `Work on target #<id> using the watchtower-workbench skill.` — the title never reaches argv. A standalone terminal (`terminal_sessions.project_id IS NULL`, Claude Code or a shell in Home or a chosen folder) gets no workbench MCP/hook and writes nothing to the workbench tables; several may run, all closed on quit. Documents render in a selectable `NSTextView`; a comment anchors on the rendered plain text and is re-located on every file change by the pure `CommentAnchor` (exact quote → best prefix/suffix among duplicates → else `outdated`, never re-attached elsewhere); the Desktop never writes a workbench document (**PROJ-03**). The board edits status/priority/title with the `TargetQueries` mutators and orders siblings with `WorkbenchBoardOrder` (priority → status → id, a dual path with Go's `boardSiblingOrder`) and polls a fingerprint because agent writes come from another process. The Board pane also has a **List | Kanban** mode (`WorkbenchBoardKanban`, pure, WatchtowerCore): leaf targets only, one column per status (Done capped at the 10 most recently updated unless Show done; unknown statuses in an Other column), dragging a card sets its status through the same `WorkbenchBoardViewModel.setStatus(_:for:)` writer as the status menu, and the mode + parent filter are remembered per workbench in UserDefaults (`projects.boardMode.<id>`/`projects.boardKanbanFilter.<id>`). `WorkbenchesViewModel.deleteWorkbench` closes the terminal, runs `workbench delete`, reloads; a workbench deleted from the CLI closes its terminal on the next reload. `WorkbenchNotificationCenter` (pure `WorkbenchNotificationPolicy`, 30 s poll, per-workbench watermark, bursts ≥ 3 coalesced, never the owner's own writes; `projects.notifications` default on) notifies on an agent question, a document ready for review, all comments answered, a target done.
- Briefing: `gatherWorkbenches` adds a `=== WORKBENCHES ===` block (`briefing.daily` v9 — v8 called it `=== PROJECTS ===`; before MEMORY REVISIONS, which stays last; workbench activity alone is enough for a briefing); a stored template whose `%s` count differs from the default falls back to the default.
- **Selection comments reach the agent as one owner turn (Phase 6, 2026-09-29):** the AI Chat's own artifact side panel gains the same idea — the owner selects a passage of a rendered artifact and drafts a comment (`chat_artifact_comments`, migration `00082`, Swift-written and Swift-read only; Go neither writes nor reads it and the assistant never sees a row directly), collects several, and **Send N comments** sends them as one ordinary owner chat message (`ArtifactCommentMessage`/`CommentBatchComposer`) — never one by one. Every open/sent comment re-anchors onto the artifact's next version at each panel reload: found → it moves onto that version, gone → `outdated`; a resolved comment only loses its highlight, and an `outdated` one is never silently re-attached even if its exact text reappears later. `ArtifactsContract` gains one line telling the assistant to answer with a new version of the same key, and CHAT-05's source scan is extended to the comment files (no process/CLI/network/session reference; adding a comment sends nothing). A finished assistant answer's **Quote in reply** opens it in a sheet built on the same `DocumentTextView`, and each selected passage joins a **pending quote batch** shown above the composer — nothing is sent per quote; the owner's own send carries the whole batch plus the typed text as one turn (`ChatQuoteReply`, the same `CommentBatchComposer` rule). Specs, plans and designs are review documents (#105): the skill attaches each and sets its review target `in_review` until the owner approves (a `Review: <title>` leaf for a plan or a sub-targeted feature, so the PROJ-05 rollup never overwrites it); the Documents list labels an agent document on an `in_review` target **In review** (`WorkbenchDocumentListItem.awaitingReview`) and `WorkbenchNotificationPolicy.readyDocuments` also announces a target the agent put in review ("awaits your review", same revision key; an owner's own move — the latest `target_status_history` actor — is not announced back; a pre-#105 persisted snapshot reads as review unknown, `reviewKnown`). The Documents list is grouped by kind (Specs / Plans / Docs / Imported, pure `WorkbenchDocumentGrouping`; collapsed groups and the title search live on `WorkbenchesViewModel`), and an open document offers a Contents menu from its rendered headings (`DocumentScrollTarget` on `DocumentTextView`). On a workbench document, selecting text shows a floating **Comment** button at the selection (plus "Comment…" in the context menu — the shared `CommentableDocumentText` over `DocumentTextView`, also used by the artifact panel, replacing both header Comment buttons; a composer opened on an older render refuses to save and keeps the typed text); a comment becomes an in-memory draft (`WorkbenchCommentDrafts`, owned by `WorkbenchesViewModel`: survives document/pane/tab switches, and a quit with drafts left asks first — no `project_comments` draft state, so no Go reader can leak one to the agent), highlighted and listed under Drafts, and **Send N comments to Claude** first writes every draft still on the text in one transaction (all or none, guarded against a double click; a lost-passage or emptied draft stays unsent and is named) and then types exactly one line — `Address the N open comments on <rel_path> (watchtower document <id>) using the watchtower-workbench skill.` — into the workbench's *running* embedded terminal, switches the page to the Terminal pane so the owner sees it land, and leaves it unsubmitted (`WorkbenchCommentPrompt`/`TerminalCenter.sendPrompt`): the owner presses Return themselves, because an auto-submitted Enter could confirm whatever the TUI happens to be showing (a permission dialog's highlighted default, a half-typed prompt) without the owner ever seeing it. It writes nothing to the DB and never starts a session, and a crafted `rel_path` can neither inject a newline nor any other control sequence (every control/newline scalar becomes a space, and none of the remaining bytes include a carriage return). With no running session the bar instead points at the next session's brief and offers **Open terminal**.
- **Status rollup (2026-09-30, PROJ-05):** a workbench parent's status follows its children — migration `00085`'s triggers (`targets_project_status_rollup_{ai,au,ad}`) re-derive it on every child insert/delete/status/parent change (all closed with a done → done, all dismissed → dismissed, every open child blocked → blocked, any in_progress|in_review|done → in_progress — in_review since 00086 — else todo; no children untouched) and walk up while a status changes, never re-deriving a dismissed ancestor, one recursive CTE per trigger so it needs no `recursive_triggers`; a parent's own update stands until a child changes, and the skill tells the agent never to set a parent's status.
- **Workbench sources scope search and the brief (2026-10-01, board #90):** in a workbench session `search_knowledge` resolves the workbench's `slack_channel`/`jira_project`/`confluence_space` sources (`tools.WorkbenchKnowledgeScope`: a channel id, `#name` or archive URL against `channels`; a project/issue key or browse URL; a space key or `/spaces/KEY`|`/display/KEY` URL — an unresolvable ref is skipped and named in the result's `scope_note`) into a `kb.Scope` and, by default, **boosts** it: `kb.Search` runs each query a second time restricted to the scope and fuses that list in too (an in-scope chunk outside the global top 50 is still retrieved, nothing outside is dropped), hits carry `in_scope`. `workbench_scope: only` (deprecated alias `project_scope`, accepted; both together are refused) hard-filters, `off` ignores the sources, an explicit `sources` filter applies on top of either; `workbench_scope` outside a workbench session, and `only` with a `sources` filter naming none of slack/jira/confluence, are refused. `workbench brief` gains a "Recent in workbench sources (last 14 days)" section (`kb.Recent`, ≤ 8 documents, ≤ 1200 runes) after the comments, only when neither the targets nor the comments were cut and at least one document fits, so it never takes their room ("nothing indexed yet" instead of "none." when the index holds nothing from those sources; queries bounded at 2 s, a failure is the section's one line plus stderr); the same change fixed a pre-existing ≤ 10-rune overflow of the 4000 cap when the board filled the budget exactly with no comments.
- **Workbench documents in search (2026-10-01, board #89, PROJ-08):** attached documents are indexed into kb as source `project_doc` (`internal/kb/source_workbench.go`: the file read from the folder — a regular file resolving inside it, symlinks followed, ≤ 2 MiB (anchor `truncated` past it), split at `#`–`###` headings; anchor `project_id`/`document_id`/`rel_path`, link `file://…`; a gone/irregular/escaping file is title-only with anchor `unreadable`). Visible **only** in that workbench's own sessions: `kb.Request.WorkbenchID`/`kb.DocOptions.WorkbenchID`, filled from `tools.Binding.WorkbenchID` by `search_knowledge`/`get_knowledge_document`; every other caller passes 0 and sees none, and `sources: ["project_doc"]` outside a session is refused. Not boosted by `workbench_scope`. The daemon re-renders a document whose file mtime differs from the indexed one (no cursor — an older mtime counts too) and never reads a folder macOS guards (`privacyProtected`: `~/Documents`, `~/Desktop`, `~/Downloads`, `~/Library/CloudStorage`, `~/Library/Mobile Documents`, `/Volumes`, case-insensitive) nor follows a symlink out of a workbench folder (`resolveInside`); `kb.IndexWorkbenchDocs(workbenchID)` — run by `workbench resync`, by `kb reindex` for every workbench, by `attach_document` (`tools.WorkbenchTools(files, cfg.Knowledge.Enabled)`, best-effort: a failure is `index_warning` in the result), and by the owner's `workbench create`, `import-docs` (not `--dry-run`) and `attach-doc` (best-effort when knowledge is on: a failure is a stderr warning) — indexes one workbench now, protected or not. `db.DeleteWorkbench` drops the workbench's entries in its transaction (PROJ-02). v1 limit: in a protected folder, a document edited on disk after its attach becomes searchable at the next attach, import or Re-run Setup.
- **Re-run setup (2026-10-01, board #91):** `watchtower workbench resync <id> [--json]` (`cmd/workbench_resync.go`) brings an existing workbench up to the current setup, **additively**: `workbenchdocs.Import` (the `import-docs` rules) plus `devpack.InstallWorkbench` (the `integrate claude-code --workbench` rules — PROJ-04: an edited skill stays `drifted`, settings merge; the MCP registration is removed and re-added, the Repair behaviour, so a moved binary is picked up), each step running even when the other failed; since the rename it also migrates a pre-rename folder (see **Rename**). It never touches targets, statuses, comments, attached documents, sources or the description and never creates targets — it prints suggestions instead (setup when the description is empty, sources when there are none, a first board when it is empty, a look at newly attached documents). `--json` (`docs_ok`/`integration_ok` + errors, `suggestions_error`, `skill`, `hooks_added`, `excluded`, `mcp_registered`/`mcp_command`, `suggestions`) always exits 0 once the workbench is found, the `create --json` precedent; the text form exits non-zero on a failed step. Desktop: **Re-run Setup** in the workbench header (`WorkbenchesViewModel.resync`, result kept per workbench on the AppState-owned VM until dismissed, `WorkbenchResynced.summaryLines`; it and Repair share one per-workbench busy guard, since both run the folder install). The skill keeps pointing the agent at `import-docs` and has it suggest Re-run Setup to the owner rather than re-install the folder from inside its own session.
- **Review status + status history (2026-09-30, PROJ-06):** migration `00086` rebuilds `targets` (re-creating 00085's triggers) so a workbench target may be `in_review` (CHECK: workbench targets only; the rollup counts it as started) and adds `target_status_history`, written only by triggers on every workbench-target creation/status change with `actor` copied from a per-write `targets.status_actor` claim (`agent` = workbench MCP tools, `owner` = Desktop writers and anything unclaimed, `system` = the rollup, unsnooze and the Jira status sync), cleared again by the trigger; `get_target` (workbench session) returns `status_history`, and the CLI `workbench board`, the `workbench_board` tool and `workbench brief` show time in the current status (the Desktop only decodes the history — its UI is a later PR); a target that joins a workbench later starts its history at its next status change.
- **Board language (2026-10-01, board items #122 → #153):** the board always follows the session language — the language the owner uses with the agent, not the repo's. The brief and `workbench_info` carry one constant `Board language:` line (`tools.BoardLanguageLine`) and the skill's Board language section makes every session write targets/intents/comments in it (identifiers, paths, plan refs unchanged). The #122 per-project override was retired by #153: the then `watchtower project update`, MCP `update_project`'s `board_language`, the Desktop menu and the `terminal title` override are gone; the `projects.board_language` column (migration `00087`) stays but is never read (no migration to drop it). Advisory only — no write is refused for its language, nothing on the board is translated.
- **Target images (2026-10-01, board target #117):** `create_targets` items take `images` and `update_target` takes `add_images`/`remove_image_ids` — absolute paths the workbench MCP checks read-only before any row (`workbenchfiles.Check`: regular file, no symlink, PNG/JPEG/GIF/WebP by content sniff, ≤ 5 MB = the chat image cap), then copies into `<workspace>/project_files/<project_id>/<sha256>.<ext>` (0700/0600, `internal/workbenchfiles`, outside the folder so nothing is ever committed; one copy per content per workbench) and records in `project_target_images` (migration `00088`, UNIQUE(target_id, sha256), ≤ 20 per target) inside the same transaction as the target writes; a failed write discards the copies no row names. `get_target` lists them with the stored `path` (the agent can read it). PROJ-02: `workbench delete` removes the directory after the rows, `targets delete`/a detach discard copies nothing else names (`Store.Discard`, never a path outside the store). Desktop: read-only thumbnails in the board's target detail card (opened over the board, `WorkbenchTargetDetailCard`) (`WorkbenchTargetImagesSection`, ImageIO decode off the main actor via `WorkbenchImageLoader`), a click opens the full image in a sheet; the fingerprint poll covers attaches. The skill tells the agent to attach an image the owner shared in the message a target comes from. A failed write discards only the copies it created (`Image.Created`) and folds a cleanup failure into its error; `workbench delete --json`/`targets delete --json` report `files_ok`/`files_error`, which the Desktop surfaces. v1: no Desktop attach/detach; a pasted image with no file path cannot be attached (the skill asks the owner for the file); TCC attribution of an image read under `~/Desktop` from the embedded terminal, and a detach or failed write racing another session's reuse of the same copy, are listed in `docs/inventory/workbench.md`'s v1 limits.
- **New Workbench… vs Add Existing Folder… (2026-10-01, board #158):** the panel header's + is a menu. **Add Existing Folder…** is the original NSOpenPanel flow (`name: nil`, the CLI names the workbench after the folder). **New Workbench…** is an NSSavePanel ("Workbench name:", starts in `~/Projects` when it exists, else home) whose entered name is both the folder and the workbench name; `NewWorkbenchFolder` (WatchtowerCore) `check`s it read-only (absent → create, empty but for `.DS_Store` → reuse, a file or non-empty folder → refused with the error line under the list), the `WorkbenchFolderPolicy` TCC warning runs next, and only then `prepare` creates the folder (non-intermediate, re-checked) and `createWorkbench(folder:name:)` runs — so "Choose another folder" leaves nothing on disk. A `workbench create` failure after the folder was made leaves it empty, and a retry with the same name reuses it.
- **Board drift (2026-10-01, PROJ-07):** workbench targets carry optional `branch`/`pr` (migration `00089`, set by `create_targets`/`update_target`; a branch is the plain local name). `watchtower workbench check --workbench N [--json] [--stale-days 3] [--no-network]` (`internal/workbenchcheck`, mechanical, read-only git subcommands only, no git process outside a repository, never fetches) flags `merged_but_open` (merge commit; fast-forward of a local branch whose tip its reflog shows committed on it; `git cherry` rebase merge; squash by patch id; gh PR merged — a parent's fix points at its sub-targets), `done_but_unmerged` (done in the last 14 days, unless open work still carries the branch/PR), `branch_missing`, `pr_closed_unmerged` and `stale`; a failed git call or a deadline never becomes a finding (`incomplete`). `integrate claude-code --workbench N` also installs a `Stop` hook (`workbench check --workbench N --stop-hook`, offline, 8 s git budget — the DB open/migration is never cut off by it — always exit 0, panic recovered) that returns only the certain kinds (never `stale`/`done_but_unmerged`) as `{"decision":"block"}`, once per stop (`stop_hook_active` → silent); a deleted workbench's leftover hook is silent; delete/`integrate remove` take it away with the SessionStart hook. `workbench brief` shows every finding (4 s offline budget), and so does the Desktop board (`WorkbenchDriftBanner` over `WorkbenchesViewModel.refreshDrift` → `workbench check --json --no-network`, on appear/Refresh and every 30 s while the Board pane polls; a failed or partial check is shown as such); `integrate status --json` reports `stop_hook` and the Desktop offers Repair without it.
- **Terminal session follows `/clear` (2026-10-01, board #160):** `/clear` (and a resume that lands on another conversation) moves Claude Code to a new session id, while the Desktop relaunched the id the row was created with — after `/clear` + an app restart the owner was back in the pre-clear conversation. `TerminalCenter` now starts every `claude` row's process with `WATCHTOWER_TERMINAL_SESSION_ID=<row id>` (`TerminalLaunch.sessionRowEnv`, a dual path with Go `terminalSessionEnv`), and the workbench's existing `SessionStart` hook (`workbench brief --workbench N`, or `project brief --project N` in a folder not resynced since the rename; command line unchanged by this change — no reinstall) reads Claude Code's stdin payload when that variable is set: for `source` `clear`, `compact`, `resume` or `fork` with a canonical lowercase UUID it stores `session_id` on the row (`db.SetTerminalClaudeSessionID`: that workbench's `claude` row only, the same column write as the Desktop's `replaceClaudeSessionID`; read first, so the common resume of the stored id never takes the write lock, and a 1 s lock wait). `startup` is ignored — the launch id is already stored, and a nested headless `claude -p` the agent runs inherits the variable. The payload read never blocks (1 s wait, shared `readHookInput` with the Stop hook); a failure is one stderr line in Claude Code's hook log (the Stop hook's convention) and the brief prints as before, exit 0. Every relaunch (`open`, Restart) re-reads the row, so it resumes the stored id.
- **Rename (2026-10-02, spec `docs/superpowers/specs/2026-10-02-workbench-rename-design.md`):** the feature was called Projects until 2026-10-02 and is now **Workbench** everywhere the owner and the agent look — the sidebar tab, the CLI (`watchtower workbench …`, `--workbench N`), the MCP server (`watchtower-workbench`, `devpack.WorkbenchMCPServerName`), the skill (`watchtower-workbench`, `internal/devpack/workbenchskill/watchtower-workbench/SKILL.md`, same DEV-04 marker; `devpack.WorkbenchSkillName`), five tools (`workbench_info`, `workbench_board`, `update_workbench`, `add_workbench_source`, `remove_workbench_source`), `search_knowledge`'s `workbench_scope`, the brief, the briefing block and the Go/Swift code names. A naming change only — PROJ-01..08 and DEV-06 hold with the same meaning. **Legacy aliases** keep a folder set up before the rename working until the owner resyncs it: `watchtower project …` is a cobra alias of `workbench` (not in the root command list), `--project N` is a hidden spelling of `--workbench N` on every command that takes it (both together are refused: "--project is the old name of --workbench; pass one"), and that spelling is the legacy signal — `mcp --project N` serves the five renamed tools under their old names (`project_info`, `project_board`, `update_project`, `add_project_source`, `remove_project_source`; `tools.LegacyWorkbenchToolNames`, `Binding.LegacyNames`; `Registry.Get` resolves both spellings and the audit row records the new name), and `project brief --project N`/`project check --project N --stop-hook` name the old skill and tools, the brief adding one line, dropped first at the 4000-char cap: "This folder's Watchtower setup predates the Workbench rename — suggest Re-run Setup to the owner." `project_scope` stays accepted as a deprecated alias of `workbench_scope`. **Migration is manual only** — nothing resyncs on an app or daemon update: `watchtower workbench resync <id>`, the Desktop's **Re-run Setup**, or `integrate claude-code --workbench N` first registers `watchtower-workbench` → `mcp --workbench N` and runs `claude mcp remove --scope local watchtower-project` only once that succeeded; when the registration does not go in (a failed `mcp add`, no claude CLI) a legacy folder is left entirely on its old skill, hooks and registration — one vocabulary, still working through the aliases — and the error says so (`resync --json` then reports `legacy_skill: "unchanged"` and suggests only the old tool names). Otherwise it installs the new skill and removes the legacy `watchtower-project` one through the DEV-04 marker/digest rule (an edited or foreign copy is kept and reported, and keeps its exclude line), replaces the legacy hook entries in place (`looksLikeOurHook` accepts both suffixes; never a second brief), and only counts the `permissions.allow` rules in the folder's `.claude/settings.local.json` naming `mcp__watchtower-project__…` for a suggestion (never rewritten, PROJ-04; an unreadable file is reported). `resync --json` adds `legacy_skill`, `legacy_mcp_removed`, `legacy_hooks_replaced`, `legacy_permission_rules`; `integrate status --json` adds `legacy`/`legacy_skill` (a legacy hook still counts as `hook: true`) and `current_mcp` (the `watchtower-workbench` registration itself, while `mcp` also counts the legacy one). `integrate remove` and `workbench delete` take away both vocabularies (PROJ-02). A save is atomic, through a symlink to the real file, keeping its POSIX permissions, and **never over a version it has not seen** (PROJ-03 as amended): a changed disk version (`conflict`), a deletion under edits (`deletedWhileEditing` — the autosave never recreates the file, Write it back / Cmd+S does) and a version that no longer reads as text (`unreadable`) block it until the owner picks Reload from disk (the page replaces its text, `force`) or Keep mine (`rebase`; Write mine over it for a binary or oversized version, Try again for a read that failed for a passing reason); an edit typed on a stale revision (before a reload reached the page) is a conflict, and a reload never replaces an unsent edit. Limits: the atomic write replaces the file, so extended attributes/ACLs are not carried over and a hard link stops sharing the file (accepted for never leaving a half-written file); a commit made from another git worktree shows on the next file change or app activation; edits typed in the last 300 ms before Cmd+Q are lost if the app quits without resigning active first; no middle-click close, drag-and-drop between folders, copy/paste or multi-select in the tree; files over 5 MB or not UTF-8 are not opened.
