# Voice Dictation (2026-08-11)

- Dictation is a **consumer** of the transcription stack, not a fork of it — it never modifies `StreamingTranscriber`/`WindowedTranscriber`/`WindowPlanner` or the live↔batch equivalence pins; it rides the existing Settings engine/model choice with a dictation-tuned `TranscriptionConfig` override (`windowSec = 3`, `boundarySnapSec = 0`, `diarization = false` — latency-first, 2026-08-16) and ignores the `transcription.liveTranscription` meeting toggle — live-ness is decided by whether the active provider supports it.
- `DictationCenter` (`WatchtowerDesktop/Sources/Services/DictationCenter.swift`) — an `@Observable` app-wide single-slot center on `AppState` (the `MeetingRecorderCenter`/`TranscriptNotesCenter` surviving-state precedent, minus the FIFO queue: only one dictation at a time). State machine `idle → loadingEngine → recording → cleaning → idle`, plus `failed(message)` with retry. Owns the target text span (base text captured once, cleaned/live text re-derived from it — never incremental field mutation, see `DictationSpan` in `DictationButton.swift`), the raw transcript (kept for the "Raw" revert), and the in-memory 16 kHz sample buffer.
- **Sticky engine, 15-minute idle TTL** (`engineIdleTTL`, constant in v1): the loaded `Transcriber` stays resident after a dictation finishes so a burst of quick dictations reuses one warm engine; unloads after 15 min of no dictation.
- **`captureWillStart` seam (single-engine invariant, both directions):** `MeetingRecorderCenter` and `DictationCenter` share one physical engine slot. `DictationCenter.meetingCaptureWillStart()` is dictation's side of the handshake — recording → deliver what was said (same as `stop()`) then drop the resident engine as soon as transcription completes (before the cleanup CLI call); idle-with-warm-engine → drop immediately; loading → cancel the dictation outright (the stop-during-load rule — almost nothing decoded yet); cleaning → drop the engine immediately (it plays no part in the CLI cleanup) while the cleanup runs to completion and still delivers its result. While the dictation engine is still resident at meeting-record start, the meeting's live pass parks (`dictationEngineResident` → the busy-queue `.waiting` path) and catches up when `DictationCenter.engineReleased` fires (`dictationEngineDidRelease()`), so two engines are never resident at once. The dictation mic button is disabled whenever `MeetingRecorderCenter.isBusy` (active capture OR any non-failed processing job) — meeting capture always wins the shared slot.
- `MicRecorder` (`Sources/Services/Transcription/MicRecorder.swift`) — mic-only `AVAudioEngine` capture, downsampled 16 kHz mono `Float`, `AsyncStream<[Float]>`. Deliberately none of the meeting recorder's machinery: no system audio, no aggregate device, no `MicAGC`, no `rec_X.activity` sidecars, nothing written to disk.
- **Go: `dictation.clean` prompt + `dictate clean` CLI** — new prompt `dictation.clean` (light/cheap tier, both providers, `internal/prompts`). `watchtower dictate clean --mode idea|note --transcript-file <path>` (`cmd/dictate.go`) is a pure transform: no DB writes (DB opened only to read the tunable `dictation.clean` prompt), transcript travels by file (never argv), JSON envelope on stdout (`{"mode":...}` plus `idea` → `title`+`body`, `note` → `markdown`; failure → non-zero exit with the error on stderr, no JSON). `DictationCleanService` (Swift) is the CLI wrapper consumed by `DictationCenter`.
- **Chat destinations skip the AI pass entirely (owner call 2026-08-18):** `DictationMode.cleanupMode` is nil for `.chat`, so a dictation into any `ChatInput` (target/situation/idea/meeting Discuss, the setup assistants) delivers the raw transcript — no `dictate clean` call, no `.cleaning` phase, no "Cleaned/Raw" revert chip. The assistant on the other side reads speech-shaped text fine; the round trip only added latency and rewrote the user's wording. `--mode chat` is retired from the CLI, which now rejects it. Idea and note keep the pass — they need a title/markdown shape the transcript hasn't got.
- **Carbon `RegisterEventHotKey`, not an `NSEvent` global monitor** (`GlobalHotKey.swift`) — the quick-capture hotkey (⌃⌥D, "dictate") is registered via Carbon specifically because it needs **no Accessibility permission** (no TCC prompt); an `NSEvent` global monitor would trigger one, which is a P0 for this project (see `[No TCC prompts from Watchtower]` project convention). Failure to register (combo already taken) is logged and left unregistered — never crashes, never blocks the tray item.
- **Quick Capture** (`Sources/Views/QuickCapture/QuickCaptureView.swift`) — a floating window opened from the tray's "New Voice Idea" item or the hotkey; starts dictating on `onAppear` into a fixed `targetID` (`"quick-capture"`), tracks its own `ownsCapture` (whether it actually won the shared `DictationCenter` slot vs. another surface already owning it — closing the window must never cancel a capture it doesn't own) and saves the cleaned result via the existing manual-create path (`IdeaQueries.createManual`, `status='active'`, `source='owner'`).
- Integrations: `IdeaCreateSheet` (mode `idea`, fills `essence` always + `title` only when empty), Recording Notes tab in `RecordingDetailTabs.swift` (mode `note`), the shared `ChatInput` component (mode `chat`, minimal cleanup preserving intent — covers all 8+ Discuss chat surfaces via one integration point).
