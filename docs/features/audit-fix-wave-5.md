# Audit fix wave 5 (2026-09-14)

- **Reaction Commands enable (decision 6):** `features enable`'s `FastForward` gained a sixth hook for `reaction-commands` — since the feature has no watermark, it instead seeds every reaction the owner has already placed (dictionary or not) into the `reaction_commands` ledger as `skipped` (`internal/reactioncmd.SeedLedger`), so flipping the feature on never replays the owner's whole Slack reaction history as commands. The hook is fail-closed per FEAT-03: an unreachable Slack account aborts the enable and the config key is never written. `Run` also gained a per-run dispatch budget (`maxDispatchPerRun = 25` AI compose calls, shared across accounts; an over-budget candidate is left unrecorded and picked up next poll). `watchtower features enable reaction-commands` now prints "Seeded N pre-existing reaction(s)…" instead of the generic watermark sentence.
- **Reaction Commands on by default, polled every cycle (2026-09-26, owner call):** `DefaultReactionCommandsEnabled = true`, `DefaultReactionCommandsIntervalHours = 0` — `interval_hours <= 0` now means "no throttle" (was "fall back to 6 h"; an explicit value > 0 still throttles), and `phaseReactionCommands` moved in `runSync` from behind ideas/memory to right after `phaseSlackSync` (before the other source syncs — Jira alone can take minutes; skipped on a cancelled ctx like every pipeline), so a tray Sync Now (which runs the full `runSync`) delivers a reaction's proposal as soon as the Slack sync lands instead of after the AI phases. The phase also skips its tracked run when no Slack account is enabled (a Google/Jira-only install, now default-on, writes no 0-item `pipeline_runs` row per cycle). The 6 h throttle had been copied from the batch pipelines by analogy; a reaction is a command the owner is waiting on, and the poll is one cheap `reactions.list` call (≤20 Tier-3 pages) — only a NEW reaction costs an AI call, the ledger makes re-polling free. What makes default-on safe under FEAT-03 is a **second seed site**: `Pipeline.processAccount` checks `slack_accounts.reaction_commands_seeded_at` (migration 00073) and, when empty, seeds that account's history (`seedAccount`, the same `skipped` rows the enable hook writes) and stamps it instead of dispatching — dispatch starts on the next poll. **Migration 00073 backfills the stamp for every account that already holds a ledger row** (a row proves the feature has polled it), so an install that was already running the feature does not have its first post-upgrade poll swallow the reactions placed since its last poll — the residual (feature on, zero ledger rows ever) is at most one poll interval. `features enable` on an already-enabled feature is now a no-op in the CLI too (the Desktop's `enableNow` already guarded it): its hook would otherwise re-seed against an actively polled account. The stamp is written last, so a part-way failure re-seeds rather than replays (pinned by a SQLite-trigger failure injection, mutation-checked); it is a stamp rather than "ledger empty" because an owner who never reacted has an empty ledger too and their first real reaction must dispatch. This also closes a pre-existing hole: a Slack account added *after* the enable was never seeded and replayed its history on the next poll. Known and unchanged: a reaction removed and re-placed on the same message is the same ledger key and never re-fires (REACT-05, no undo), so a reaction placed before the seed cannot be re-armed by re-placing it — react on a different message. The Desktop cheat sheet's "Runs immediately" copy (PR #167's open owner call) is now accurate to within one daemon cycle. Guards: `internal/daemon/daemon_reactioncmd_test.go`, `internal/reactioncmd/seed_test.go`'s four first-poll tests.
- **Prompt-store wiring (M-2 census follow-up):** `SetPromptStore` existed on briefing/digest/tracks/guide but no `cmd/` caller had ever invoked it, so `briefing.daily`, every `digest.*` prompt, `tracks.extract_batch`, and `people.*` always rendered compiled-in defaults — Settings → Prompts edits to those rows were silently inert. Wired at every construction site; a `go/parser` property scan (`cmd/prompt_store_scan_test.go`'s `TestPromptStoreWiring_EveryPipelineConstructionIsWired`) also caught seven further holes of the same class (`meeting.prep`/`meeting.extract_topics`/`day_plan.generate` wired on the daemon path but not the CLI path). **Consequence, not cosmetic:** `internal/digest`'s compiled prompt consts had drifted from the DB registry defaults, so this also changes every install's digest prompts on the next cycle and revives Slack-sourced idea mining (the `ideas` array inside `digest.channel`/`digest.channel_batch`), which the drifted consts never carried at all — see `docs/inventory/ideas.md`'s 2026-09-14 entry. `targets.extract`/`targets.link` were wired on 2026-09-23 per owner decision: `internal/targets.Pipeline` gained the same `SetPromptStore`/`getPrompt` seam (`store.Get`, not `GetForRole` — targets has no role profile) and all four `targets.New` construction sites in `cmd/` (`targets_ai.go` ×3, `sync.go`'s next-step wiring) now call it. **Drift reconciled the same day:** `internal/targets/prompts.go`'s compiled `ExtractPromptTemplate` had carried a `sub_items`/GROUPING/LANGUAGE-preservation block that `internal/prompts/defaults.go`'s registered `defaultTargetsExtract` lacked entirely (`LinkPromptTemplate`/`defaultTargetsLink` were already byte-identical) — an install whose `targets.extract` DB row was still the seeded default would have lost those instructions once the wiring above landed, the same "consequence, not cosmetic" shape the digest wiring above hit. `defaultTargetsExtract` was made byte-identical to `ExtractPromptTemplate` and `TargetsExtract` bumped v1→v2 in `DefaultVersions` (`prompts.Store.Seed` auto-upgrades a non-customized DB row to a higher-versioned default; a customized row is left alone until an explicit Reset) so an existing install's seeded-and-never-edited `targets.extract` row picks up the fix the next time something calls `Seed()` — that's `watchtower db migrate`, which the Desktop app runs on every launch (`DatabaseManager.swift`); the daemon and the `targets` CLI commands never call it, so a CLI-only install keeps the seeded v1 row until it runs `db migrate` by hand. `internal/targets/prompt_store_test.go` now pins `ExtractPromptTemplate == prompts.Defaults[prompts.TargetsExtract]` and the same for `LinkPromptTemplate`/`targets.link`, so a future edit to one copy without the other fails the build immediately. (Superseded 2026-10-02: the compiled consts are gone and every pipeline falls back to `prompts.Defaults` through `prompts.Resolve`, so there is no second copy left to drift.)
- **One daemon log stream, rotated while running:** the detached daemon's stdout/stderr (`daemon.log`) and its own logger's output (`watchtower.log`) used to duplicate byte-for-byte because `runSync` also mirrored the logger onto `os.Stderr` when detached. `logWriterFor` (`cmd/logfile.go`) now adds stderr only under `--verbose`; `daemon.log` keeps its narrower role as the crash channel (Go runtime panics, the parent's rotation note, and `internal/daemon/pidfile.go`'s direct-stderr cleanup warnings — shared with CLI commands, error-only; the daemon itself reaches only `RemovePID`, once at shutdown). Everything else a daemon phase logs reaches `watchtower.log`: `routeStdLog` points the stdlib default logger (`log.Printf` in `internal/db`, `internal/ai`, `internal/jira`'s dashboards…) at the daemon's stream for the daemon's lifetime (`sync --daemon` only — CLI commands keep stderr), and every `internal/jira` component with a `SetLogger` seam gets a prefix-preserving `subLogger` in `cmd/sync.go` (`[jira]`/`[jira-users]`/`[jira-sync]`/`[jira-analyzer]`/`[jira-keys]`, the detector via `newJiraKeyDetector`), pinned by the `TestSyncWiring_EveryJiraComponentGetsTheDaemonLogger` property scan. `watchtower.log` is wrapped in `rotatingFile` (`newSyncLogWriter`) so it now rotates past 20 MiB while the daemon runs, not just at open time; `daemon.log` itself still cannot be rotated in-process (the child holds it as an inherited descriptor from an already-exited parent), so it keeps its open-time-only rotation.
- **Daily rollup attempt budget (decision 9 follow-up, third copy of the day-plan/briefing shape):** `phaseTracksAndRollups`'s rollup sub-block persists a 3/day failure budget to `rollup_attempts.txt`, keyed on the **UTC** calendar date via the pure `rollupBudgetDate(now)` (the phase takes `now time.Time` from the daemon loop, the `runDayPlanPhase` shape) — deliberately UTC, not local, because `RunDailyRollup` itself computes its window in UTC. The CLI `digest generate` path is unbudgeted by design (it lives in `internal/daemon`, not `internal/digest`), so a manual run always gets a real attempt.
- **Meeting recap/notes speaker attribution (decision 13):** `meeting.recap` (v2→v3) and `meeting.notes` (v1→v2) now describe both the labeled case (a `[label]` line prefix — `[Я]` rendered as the recording owner in the output language's natural third-person terms, `[Speaker N]` unidentified, anything else a real name) and the unlabeled case, instead of unconditionally claiming transcripts are never speaker-labeled — a claim diarized transcripts (D1) already contradicted.
- **Calendar stale-cleanup guard (decision 14):** `DeleteStaleCalendarEvents` now spares an event still referenced by a `meeting_transcripts` or `meeting_recaps` row even when it's stale, via index-backed `NOT EXISTS` clauses (not `NOT IN`, which a NULL `event_id` — an ad-hoc recording, or a recap already detached by migration 00056 — would silently poison into matching nothing). There is only one delete branch, so a recorded-then-cancelled meeting now persists locally by the same rule that spares a still-upcoming one.
- **Chat-client argv (item B, layers 2/3 of 3):** `internal/ai/client.go` and `internal/codex/client.go`'s chat clients (`Query`/`QuerySync`, both providers) now route a user message through stdin whenever it starts with `-` or exceeds `digest.StdinThreshold` (32 KiB) — the same protection their batch-generator siblings already had, which the chat path lacked entirely. Layer 1 (Swift `WatchtowerAIService.buildArgs` emitting flags, then `--`, then the prompt, unconditionally) is Desktop task 12's side of the same dual path; a `cmd/ai_test.go` guard pins the cobra-side contract the Swift ordering must match.
