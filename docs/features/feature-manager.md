# Feature Manager (2026-08-16)

- `internal/features/` — a static feature registry (`All()`, `ByID()`, `Dependents()` with transitive closure over FeedsInto edges) pairing each feature with a config key, cost annotation (heavy/medium/light/none), and UI title/description. Daemon startup calls `config.MigrateFeatureGates(configPath)` to detect legacy `digest.enabled=false` installs and convert them to feature-wide disables (one-time only, marked by `features.migrated`). Pipelines are always constructed; per-feature gates are early returns at the top of each daemon phase (before nil-checks, throttles, locks, or trackedPipelineRun): `if !d.config.Tracks.Enabled { return }`, etc. (FEAT-01: off = zero AI calls, no locks/pipeline_runs). `digest.enabled` demoted from de-facto master switch to just the Slack-digests feature key. Fast-forward hooks on enable reset watermarks to the present moment (FEAT-03: re-enable resumes from now, never auto-backfill).
- CLI: `watchtower features list [--json]` (renders registry + config state); `enable <id>` (runs fast-forward hook first, then writes config true on success); `disable <id> [--dry-run] [--with-dependents]` (plain disable writes only that key and succeeds; enabled dependents stay on but degraded; --dry-run prints the cascade; --with-dependents also disables each enabled dependent — FEAT-04: no silent cascade; FEAT-02: off is non-destructive). Desktop: Settings → Features panel lists all features with title, description, cost badge, and on/off toggle; Core rows show badge only; Memory feature expands to show sub-toggles (semantic.enabled + six sources + six surfaces); disable flow shows cascade confirmation dialog fed by `disable --dry-run --json`, then applies via CLI calls + one `DaemonManager.restart()`.
- See `docs/inventory/features.md` for the FEAT-01..04 behavioral contracts (off = zero new data and locks, non-destructive, fast-forward on enable, no silent cascade).
- **Onboarding feature splash (2026-08-16):** a new final `OnboardingStep` `.features` — `FeatureSplashView` renders the registry's selling attributes (tagline/benefits/icon, `internal/features/registry.go`) as a pick-what-it-does screen and exits through `OnboardingCompletion.finish`, making the splash the **second Desktop write surface** for feature state, routing through the same `FeatureManagerService`/CLI as Settings → Features (so a fix at the service, e.g. dropping staged no-op toggles, lands on both). Re-running onboarding from Settings replays the splash by design.
- **Onboarding v2 feature preset (2026-10-02):** `OnboardingFeaturePlan` (WatchtowerCore) maps the Goals step's `OnboardingGoal`s to a feature set over a fixed managed id list (Knowledge search always on, Memory always off; core entries and `unmanagedFeatureIDs` — Confluence in search — left alone; `OnboardingFeaturePlanTests` parses `internal/features/registry.go` and fails on a toggleable feature in neither set); `OnboardingFeatureSelection` follows the goals until the owner flips a switch on the Customize screen (`FeatureSplashView` in `.customize` mode), then freezes until `resetToGoals()`. The selection is written by `FeatureManagerService.applySelection(enabled:managed:)` — the same `features enable`/`disable` calls; it never restarts the daemon. Onboarding completion is the only point that starts or restarts it. It returns false (reason in `loadError`) when the live list could not be read, a write failed, or another call was in flight. A feature left off here and enabled later resumes from now (FEAT-03), by design.
