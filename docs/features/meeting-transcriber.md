# Meeting Transcriber (v74+)

- **Pluggable transcription providers:** The transcription engine is pluggable via `TranscriptionProviderRegistry` (single list in `WatchtowerDesktop/Sources/Services/Transcription/`). One active provider is chosen in Settings via two pickers: **Engine** (`@AppStorage("transcription.provider")`, default `"whisperkit"`) and **Model**. New installations default to WhisperKit; absence of the provider key preserves existing behavior. Adding a provider = one line in `TranscriptionProviderRegistry.all` + one file in `Providers/*.swift` conforming to `TranscriptionProvider`. Diarization strictness is an engine-independent Settings key alongside the model ones: `transcription.diarizationThreshold` (default 0.6, accepted only within 0.3–0.9 by `TranscriptionConfig.fromDefaults`, passed to `FluidAudioDiarizer.load(clusteringThreshold:)`; lower = more distinct clusters). Cross-window prompt conditioning is a Settings → Transcription toggle ("Cross-window context (experimental)"), **default OFF** — a 2026-08-07 full-recording validation measured quality parity at ~1.4x decode cost, so it ships dark: `transcription.contextPrompt` (on) feeds each window's decode the previous speech window's text tail via `contextPromptTail`, expiring after `ContextPromptState.silenceLimit` (3) consecutive silent windows; off = blind-window decoding, byte-identical to pre-feature behavior. **WhisperKit path only** — Qwen3/Parakeet/Apple run their own windowing and ignore it. Because a prompted decode can collapse to an immediate end-of-text (or throw) on audio that decodes fine clean, `decodeWithPromptFallback` retries such a window ONCE without the prompt — but an empty clean retry after a prompted THROW rethrows the original error, so an engine failure can never masquerade as silence; a poisoned prompt can never cascade, and an error reaching the transcriber always means the window yielded no usable speech even without the prompt.
- **Built-in providers:** `WhisperKitProvider` (on-device, default, `large-v3-v20240930` turbo default, supportsLive=true — its `WindowedTranscriber`/`StreamingTranscriber`/`resolveWindowLanguage` and the live↔batch pin test `StreamingTranscriberTests.testMatchesBatchOnSameSamples` are Whisper-internal); `ParakeetProvider` (FluidAudio, batch-only, Apple-Silicon-gated); `Qwen3Provider` (soniqo/speech-swift, Apple-Silicon-gated; batch AND live both decode through `Qwen3Windower` — WindowPlanner windows over one shared loop, bounded memory, no sticky language: forced hint or per-window auto-detect, segments labeled "auto"); `AppleProvider` (SpeechTranscriber, macOS 26+, batch-only, no Ukrainian).
- Record a meeting from the Calendar tab (event-linked or ad-hoc): Swift captures mic + system audio natively (CoreAudio process tap + private aggregate device, macOS 14.4+, no BlackHole/ffmpeg — `SystemAudioRecorder`), transcribes on-device via the active provider with windowed ru/uk/en sticky language detection (WhisperKit only; Qwen3 live/batch uses its own per-window auto-detect via Qwen3Windower; Apple and Parakeet are batch-only), orchestrated by `MeetingRecorderCenter` on AppState (survives navigation; the audio file survives every failure). The mic channel passes through `MicAGC` (slow, hard-clamped 1–6x, mic-term only — deliberately NOT the mix-wide auto-leveling snoop burned on, which drove the signal into clipping) before the 0.9-weighted `tanhf` mix, with the per-cycle gain ramped linearly across the cycle's frames rather than stepped at the boundary (bounded, not exact: the ramp starts where the previous cycle ended, so a gain change is spread over ~10 ms and the last frame sits one step short of the target). **The gate is the mic/system RATIO, not the mic level**: only a cycle where mic RMS exceeds `dominanceFactor` (2, the same per-bin test as `RoleAssigner.micDominanceFactor`) × system RMS *and* clears an absolute floor adapts the level EMA. **Adapt-gate and apply-gate are separate** — deciding per ~10 ms cycle but also *applying* per cycle amplitude-modulated the owner's own speech at syllable rate (measured 1.68 unity↔boost flips/sec), so an admitted cycle arms a 1 s hold (`holdSec`), an unambiguously system-dominant cycle cancels it immediately (bleed never coasts on boost), and ambiguous cycles — sub-floor room tone, consonants, near-threshold double-talk — coast on the held gain until it expires. Where `RoleAssigner` aggregates the same predicate by majority share over a segment, the AGC aggregates it temporally through the hold. Remote audio bleeding into the mic is therefore never amplified (measured on a real sidecar: own-speech mic RMS median 0.0074 sits *below* the bleed's 0.0128, so absolute level cannot separate them — the dominance ratio does, 253 vs a bleed p90 of 0.36). Time constants are wall-clock (EMA/ramp-up tau 2 s, back-off tau 0.2 s), converted per cycle, so the law is independent of IO buffer size. Settings toggle `transcription.micAGC`, **default OFF** (dark until validated end-to-end on a real recording — the `transcription.contextPrompt` precedent, PR #79), read via `MicAGC.isEnabled` by the recorder (which consumes no `TranscriptionConfig`). The `rec_X.activity` sidecar keeps the RAW pre-gain mic RMS, so `RoleAssigner.detectSelfCluster`'s mic-vs-system comparison is unchanged by the AGC — but note the diarizer itself clusters the gain-modified mix, so the AGC does change what the embeddings see.
- Tap re-attach (2026-10-02): a process tap and its aggregate device are bound to the devices present at creation, so a default output/input change mid-recording (headphones, a Bluetooth headset) used to leave the call channel silent for the rest of the meeting (`CallAudioWatch` only warns). `SystemAudioRecorder` now listens for `kAudioHardwarePropertyDefaultOutputDevice`/`DefaultInputDevice` changes and rebuilds tap + aggregate + IO proc on the current defaults, **make-before-break**: the new chain is built first and any failure before the switch leaves the running capture untouched; only the window between stopping the old IO proc and starting the new one is lost. The `.caf` file, live streams and `rec_X.activity` sidecar keep going; each rebuild installs a fresh device-rate converter (the sidecar accumulator is re-binned when the rate changes; the rate is read strictly — a device that cannot report one fails the rebuild instead of falling back to 48 kHz — and re-read once after IO starts, for a Bluetooth headset switching to its call profile). If the new device fails to start, the old proc is restarted (logged when that fails too). The state machine is `TapReattachController` (WatchtowerCore, pure; listener and timer are seams): 1 s debounce collapses a burst of changes into one rebuild, a failure is retried twice 2 s apart, then it waits for the next change; `stop()` cancels a pending rebuild and waits out one in flight. No TCC path: the rebuild never requests permissions (granted in `start`, per app). Gate `transcription.reattachSystemAudio`, default **on** (a kill switch, not a dark launch: without it the call channel is lost anyway), snapshotted at start; Settings label "Follow audio device changes". Logged as `[Recorder] …` lines on stdout. Validated by unit tests only until the owner's real-hardware check.
- Go owns persistence + AI: `meeting_transcripts` table (migration 00020; `event_id` `ON DELETE SET NULL` — transcripts outlive events), CLI `watchtower meeting-prep transcript save|recap|list|show` (transcript passed via `--transcript-file`, never argv), recap via `Pipeline.GenerateTranscriptRecap` reusing the `meeting.recap` prompt — event-linked recaps land in `meeting_recaps` (existing UI renders them) *unless the event already has a recap* (collision guard mirroring Swift `linkToEvent`: the existing row is never overwritten; the generated recap goes to `summary_json` instead — except the recording's OWN row, `meeting_recaps.transcript_id = id`, written by its save or copied by `linkToEvent`, which `transcript recap <id>` refreshes in place together with the `summary_json` copy when one exists, so the voice-registry recap-refresh hint's Regenerate replaces what the Recap tab shows; `storeTranscriptRecap` ↔ `MeetingRecapQueries.fetchForRecording`), ad-hoc in `meeting_transcripts.summary_json`. `save` exits 0 if the transcript persisted even when the recap failed (envelope `recap_ok`/`recap_error`; retry via `transcript recap <id>`).
- Window boundaries are planned by the shared `WindowPlanner` (silence-snapping: the cut lands on the quietest 20 ms frame within ±`transcription.boundarySnapSec` (default 2.5 s) of the nominal end; 0 disables). Both transcribers consume it, so the live↔batch equivalence invariant covers boundaries too (`testMatchesBatchWithSnappingOnSameSamples`).
- Speaker roles (v75+): after Stop, a diarization post-pass (FluidAudio pyannote/VBx behind the `SpeakerDiarizing` seam, `FluidAudioDiarizer`) maps `TranscriptionOutput.segments` (timestamped, from `WhisperWindowEngine.transcribeWindow`'s `[TranscribedSegment]`) to speaker clusters and renders `[Я]`/`[Speaker N]`/person-name prefixes into the same transcript text (`RoleAssigner`, pure). The «Я» label comes from the `rec_X.activity` sidecar (per-100 ms mic/system RMS written by `SystemAudioRecorder`; swept by the Go orphan cleanup like any `rec_*` file). The voice registry (below) names recognized voices, and the owner's voice (identity = `google_accounts` emails) refines «Я» in meeting rooms — tie-break toward the owner-matched mic-dominant cluster, veto when the winner is confidently a colleague; identity unknown → legacy absolute mic priority. Semantics: `RoleAssigner.clusterLabels` doc + `docs/superpowers/specs/2026-07-31-transcript-stack-design.md`. Any diarization failure saves the plain transcript — never `.failed`; toggle `transcription.diarization` (default on). Go/DB unchanged: roles are line prefixes in `meeting_transcripts.text`.
- **Voice registry (2026-09-28):** replaces the single-centroid `voice_prints`/manual-rename loop with per-sample nearest-neighbor matching (`voice_samples`) and continuous self-training. Bands, thresholds and caps live in one place, `VoiceRegistryPolicy` (`WatchtowerCore`): confident (best ≥0.70, margin ≥0.10, attendee-invited-or-owner) auto-labels a cluster (`label_source: auto`); unsure/unknown/conflict enqueue a `voice_label_queue` task surfaced by the "Who spoke" Voices window (tray, the post-meeting notification, or "Listen to samples" on a Transcript speaker label — the old in-place rename and the `meeting.speaker_guess` LLM-suggestion prompt are removed). Five invariants hold everywhere, guarded by `VoiceMatcherTests`/`VoiceRetroRelabelerTests`: an `auto` sample mints only against an owner `anchor` sample of the same person; import never creates owner or reserved-label (`Я`/`Speaker N`) samples; every match/retro/self-training read is `status='active'` at the current `model_version`; export carries only active `owner`/`auto` samples, never `imported` ones; retro relabel (owner confirm, import activation, or app launch) touches only clusters with `label_source: none` — `[Я]`/already-named clusters never move. A `pending` imported sample only suggests (`import_confirm`) until one owner confirmation activates it. Export/import is an encrypted `.wtvoices` file (AES-GCM, PBKDF2-derived key, password travels separately) carrying embeddings only, never audio/text/meeting metadata. The model-version literal is a deliberate dual-path: migration `00080`'s seed value ↔ `VoiceRegistryPolicy.embeddingModelVersion`. Design: `docs/superpowers/specs/2026-09-28-voice-registry-design.md`.
- Live (in-progress) transcription (WhisperKit and Qwen3): while recording, `MeetingRecorderCenter` loads the provider at start and runs `StreamingTranscriber` over the recorder's live 16 kHz sample stream (`AudioRecording.liveSamples`, tapped from `SystemAudioRecorder`'s downsampled `outBuffer`), showing finished window chunks (default `windowSec` 30 s, raised from 20 after the 2026-08-07 quality A/B) in the `RecordingIndicatorView` expandable panel. The Qwen3 engine's live path runs its own `Qwen3Windower` loop over the same live sample stream (no sticky language; single-pass save on Stop and the batch-from-file fallback apply the same way). Single-pass: the live result is saved directly on Stop (no re-decode); the engine loaded at start is reused for the fallback. The `.caf` file stays the source of truth — engine-load/stream failure silently drops to the engine's batch path from the file (`WindowedTranscriber` for Whisper, `Qwen3Windower` for Qwen3), which also serves crash recovery/retry. `StreamingTranscriber` and `WindowedTranscriber` share `resolveWindowLanguage` and `contextPromptTail` (plus the silence-streak expiry) and MUST stay behaviorally equivalent — the pins now assert **prompt-sequence** equality alongside the output (`StreamingTranscriberTests.testMatchesBatchOnSameSamples`, plus `testMatchesBatchAcrossErrorAndSilenceStreak` for the error/silence prompt state machine), Whisper-internal. Same model as Settings (`transcription.model`). The whole live pass sits behind `transcription.liveTranscription` (Settings toggle, default **on**): off = capture only, no engine load during the call, batch transcription from the file after Stop; `MeetingRecorderCenter` snapshots the flag at start (`captureLiveEnabled`, readable — `RecordingIndicatorView` gates the live panel on the snapshot, never a live Settings read) and a live-disabled capture never owns, awaits, or cancels a previous recording's still-draining live tail (`consumeLivePassOwnership`).
- **Capture/processing decoupling:** `MeetingRecorderCenter` is split into a single capture slot (`captureState`/`isCapturing`) and a FIFO post-processing queue (`jobs: [ProcessingJob]`, per-job `phase` = queued/transcribing/diarizing/summarizing/failed, per-job `eventID`/`title`/`liveOutput`/`transcriber` so a recording always saves against the event it was started for) — a new recording may start while earlier ones are still transcribing, and a failed job stays in the queue as retriable (`RecordingIndicatorView` renders one pill per job; the legacy single-slot `phase`/`pendingAudioURL`/`prepareRetry` computed views still project the head for the older affordances). **Single-engine invariant:** the queue never starts a job while capture is active, and a recording started mid-job parks its live pass (`liveEngineState = .waiting`, `pendingLiveStart`) until the engine slot frees and then catches up on the recorder's buffered live stream (no lost audio, single-pass save on Stop unchanged). Crash recovery is per recording via `rec_X.meta` sidecars (the `rec_X.activity` naming family, written before capture starts, swept by the Go orphan cleanup) — N recovered recordings surface at once, oldest first, opt-in; the pre-queue `recorder.pending*` `UserDefaults` pointer is read+cleared once by `restorePendingOnLaunch`. A successful transcription persists text+metadata next to the audio (`.txt`/`.json`, same basename, deleted on successful save), so a failed `transcript save` retries the CLI call without re-transcribing.
- **Phone ingest (mobile POC C, 2026-10-08):** a recording made on the iPhone (AAC `.m4a`, mono, mic only) and relayed by the mobile hub enters through `MeetingRecorderCenter.ingestPhoneRecording(audioURL:eventID:title:config:)`. It reserves `rec_<ts>[-N].m4a` by creating its `rec_X.meta` sidecar exclusively (`reservePhoneRecording`, `.withoutOverwriting`; done on the main actor, so it is serialised with `startRecording`'s `.caf` pick — concurrent ingests and a Desktop capture of the same second get distinct stems and never overwrite a sidecar), copies the audio off the main actor (`copyPhoneRecording`; a failure removes only the files this ingest created and throws), then enqueues a `ProcessingJob` directly — never the opt-in `recoverable` list — so it queues behind any running job and never claims the engine while the Mac is capturing (single-engine invariant). `.m4a` sits next to `.caf` everywhere the `rec_*` family is handled: the recovery scan and its chronological sort key, `uniqueRecordingURL(in:date:fileExtension:)` (a name is taken while either extension or the `.meta` exists), and the shared batch decode (`AudioFileDecoder`). The upload's `event_id` links the transcript and scopes voice matching (`registryLoader(eventID)`); without one the transcript is ad-hoc. A mic-only recording has no `.activity` sidecar, so diarization runs but the «Я» role is skipped, and the job saves normally. `onJobPhase(audioURL:phase:)` (every phase change, progress and `.failed` included) and `onJobFinished(audioURL:transcriptID:)` report every job on the main actor, keyed by the ingested audio URL; the hub filters them for its `recording_job` slice. The hub (`PhoneRecordingJobs`, see `docs/features/mobile-companion.md`) passes `event_id` only while that calendar event still exists, so an upload for a deleted event is saved ad-hoc instead of failing on the transcript's foreign key; the callbacks are single-slot, and the hub chains onto them (the earlier closure still runs) and restores them when it stops.
- **Warm engine slot (2026-08-11):** the **fourth state of the single-engine invariant** — besides the capture's live pass, a draining live tail and a job, an engine may sit parked idle in `MeetingRecorderCenter.warmTranscriber`, so a second recording (and a recording started just before a meeting) skips the "Loading model…" wait. Both load sites (`startLivePass`, the batch fallback in `transcribeAndSave`) go through `takeWarmOrLoad`, which awaits an in-flight prewarm FIRST, then takes the parked engine only if `warmKey` still equals `engineKey()` (provider+model, the same two Settings keys `defaultEngineFactory` reads) — so a Settings switch invalidates the slot instead of serving a stale engine, and a recording started mid-prewarm still produces exactly ONE load. A job parks its engine on success (never after a transcription failure; the live path parks `job.engine` and clears it). Unloading is decided in exactly one place: a 30-second poll (`startWarmPolicy`, the `MeetingReminderCenter.start` shape) feeding pure logic in `WarmEnginePolicy.decide` (`WarmEnginePolicy.swift`, the `MeetingReminderLogic` precedent — no clock reads, no I/O) — prewarm when the engine is free and a non-all-day meeting is ongoing or starts within `prewarmLead` (5 min); unload when nothing holds the parked engine (or the toggle is off, or the key drifted); never touch a busy engine. The calendar read is an injected `meetingsProvider` closure wired by AppState once the dbPool exists (`CalendarQueries.fetchEvents`; a read error is logged and treated as "no meetings"), and a prewarm failure is silent by contract — only the record-time load path surfaces engine errors. Settings toggle `transcription.preloadBeforeMeetings`, **absent = ON** (read fresh each tick and each park; off = the pre-2026-08-11 lifecycle, load per recording and drop after). Note for tests: the shared `MeetingRecorderTestCase.isolatedDefaults()` turns the toggle OFF so the legacy recorder suites keep pinning that older lifecycle; `MeetingRecorderWarmEngineTests` re-enables it via its own `warmDefaults()`.
- Both AI generators pass user messages > 32 KB via stdin (`digest.StdinThreshold`) to stay clear of ARG_MAX — claude gets bare `-p` + stdin, codex gets `exec -`.
- Daemon phase `phaseTranscriptAudioCleanup` deletes audio past `transcripts.audio_retention_days` (default 30) and NULLs `audio_path`; transcript text is permanent. It also sweeps `transcripts.recordings_dir` (default `~/Library/Application Support/Watchtower/recordings`) for orphaned `rec_*` files older than the window that no `audio_path` references. MCP tools `list_transcripts`/`get_transcript` expose transcripts to the assistant chat.
- **Recordings tab & single-view (v75+):** The Calendar screen has an Events | Recordings segmented control (`CalendarMode` in `CalendarEventsView`). Recordings (ad-hoc + event-linked) live in a master-detail list (`RecordingsView`/`RecordingsListView`/`RecordingDetailView` + tab views in `RecordingDetailTabs.swift`): the master uses the lightweight `RecordingListItem` projection (`fetchRecordingList` — never selects `transcript_text`/`summary_json`, only a 200-char snippet + booleans — perf guard), the detail fetches the full row async on selection and has four tabs (Recap / Notes / Transcript / Chat), chat VM created lazily. Recap resolution: the event's `meeting_recaps` row wins, falls back to the transcript's `summary_json`; decoded once in `load()`, never in row builders.
- **Persistent segments & utterance view (D1):** `meeting_transcripts.segments_json` (migration 00045) — JSON array of per-utterance segments (`RoleAssigner.assign`'s merge units: idx/start_sec/end_sec/speaker/text/deleted; NULL for legacy rows). Load-bearing invariant: when non-NULL, `transcript_text = render(segments where !deleted)` — **one canonical renderer per side, a deliberate dual-path like `saveNotes`**: Go `internal/meeting.RenderTranscriptSegments` (CLI `transcript save` validates the invariant — including idx == array position — and NULLs the column on any missing/malformed/mismatched `--segments-file`, exit-0 envelope semantics preserved, the drop reported via `segments_ok`/`segments_error` envelope fields per the `recap_ok` precedent) and Swift `TranscriptSegments.render` (UI edits via `MeetingTranscriptQueries.setUtteranceDeleted`, the transactional `segments_json` + `transcript_text` rewrite behind the Transcript tab's soft delete + undo toast; no hard deletion). The Swift save path writes a `--segments-file` temp file next to `--transcript-file` (live, batch fallback, and sidecar-retry paths alike); equivalence pinned by matching fixtures in `internal/meeting/segments_test.go` ↔ `TranscriptUtteranceTests.swift`. `RecordingTranscriptTab` renders the utterance list (speaker + timecode headers) when segments exist, the legacy flat text otherwise; `fetchRecordingList` never selects `segments_json` (perf guard). Spec: `docs/superpowers/specs/2026-07-31-transcript-stack-design.md`.
- **Meeting notes:** `meeting_transcripts.notes_md` (migration 00021) — publishable markdown. Generated by `watchtower meeting-prep transcript notes <id>` (`meeting.notes` prompt, strong tier, transcript in the user message / stdin path like the recap; exit 1 on failure, nothing persisted — unlike `save`). Edited in the Notes tab (debounced direct GRDB write via `MeetingTranscriptQueries.saveNotes` — a dual-path with the CLI writer; the editor is `.disabled` while generation runs so a finishing run can't clobber mid-run edits). Generation state lives in `TranscriptNotesCenter` on AppState so it survives navigation.
- **Meeting chat:** per-recording assistant chat, `chat_conversations.context_type='meeting'`, `context_id=transcript id` (`MeetingChatSurface` on the shared embedded chat component — `EmbeddedChatEngine` in `AppState.embeddedChatCenter`, see `docs/features/embedded-chat.md`; a reply survives switching recordings). System prompt inlines a capped transcript excerpt (12k chars) and points the model at the `get_transcript` MCP tool for the full text.
- **Delete:** Swift-only transactional delete (`MeetingTranscriptQueries.delete`): transcript row + meeting chat (+messages) in one write; returns `audio_path` for post-commit best-effort file removal (missing file = success — retention may have swept it). The event's `meeting_recaps` row is NEVER deleted with the recording.
