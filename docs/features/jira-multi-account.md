# Jira Multi-Account (sub-project 3 of 3 of the multi-account initiative, 2026-08-02)

- `jira_accounts` table (migration 00049) replaces the config-singleton site model (`jira.cloud_id`/`site_url`/`user_display_name` in config.yaml, now frozen — nothing reads them): one row per connected Atlassian site (`cloud_id`, `site_url`, `site_name`, `label`, `status`/`error`, `enabled` soft on/off, its own `memory_jira_last_extracted_ts` memory-extraction watermark, moved off `workspace`). Migration 00071 (2026-09-25) adds `owner_account_id`/`owner_email`/`owner_display_name` (`TEXT NOT NULL DEFAULT ''`), filled from `GET /rest/api/3/myself` (`jira.Client.GetMyself`) — best-effort at connect (`recordJiraOwner` in `cmd/jira_owner.go`, never fails the connect) and lazily once per daemon start for an enabled account still missing them (`maybeRecordJiraOwner` in `wireJiraSyncers`); a revoked account simply stays empty until re-login. These are the Jira rung of the owner-identity ladder — see "Owner identity" below. **Composite PKs, not namespaced strings** (the google_accounts route, deliberately unlike Slack): issue keys ("PROJ-123") are user-visible and live in regexes (key detector ×3 copies), prompts (`"jira:PROJ-123"`), `targets.source_id`, memory `jira:` refs, and MCP args — prefixing them would break all of that. Every site-scoped table gains `account_id NOT NULL REFERENCES jira_accounts(id) ON DELETE CASCADE`: `jira_boards`/`jira_sprints`/`jira_custom_fields`/`jira_issue_links` `(account_id, id)`, `jira_issues (account_id, key)`, `jira_board_field_map (account_id, board_id, field_id)`, `jira_sync_state (account_id, project_key)` (shared project keys no longer clobber watermarks), `jira_releases (account_id, id)` + `UNIQUE(account_id, project_key, name)`. `jira_user_map` (Atlassian ids globally unique) and `jira_slack_links` (text-detected keys are site-ambiguous by nature) are deliberately NOT scoped. **Bare-key readers keep their signatures** — a key shared by two sites resolves to an arbitrary site's row (documented v1 ambiguity, the `mail:`/`gmailthread:` precedent); only writers and board/sprint-scoped readers gained an `accountID` param (models carry `AccountID`, upserts read it from the struct).
- A pre-multi-account install migrates in place: the goose migration seeds account #1 when synced Jira data exists (empty `cloud_id` — SQL can't see config); `ensureLegacyJiraAccount` (`cmd/jira_legacy.go`) finishes in Go (guard = legacy `jira_token.json` **file** existence, the Google C1 lesson; fills identity from config, renames token → `jira_token_1.json`) and is idempotent — called from daemon wiring, `jira add` (seed-then-create), and the `jira login`/`logout`/`status`/`sync` legacy paths.
- Per-account token store `jira_token_<id>.json` (`jira.NewTokenStore(dir, accountID)`; `Load` keeps its error-on-missing contract, wiring gates on `Exists()`). `wireJiraSyncers` (`cmd/sync.go`) iterates `ListEnabledJiraAccounts` → one `jira.Syncer` per account (`NewSyncer(..., accountID)`) with its own per-account `BoardAnalyzer`/`FieldDiscovery`; a broken account records only *its* `status`/`error` (only flipping a currently-`ok` account) and never blocks the others. Daemon: `SetJiraSyncers([]*jira.Syncer)` (was singleton), `phaseJiraSync` loops accounts, aggregates board-analyzer usage into one `jira-boards` run, `SyncJiraTargetStatuses` once per phase as long as at least one account's pass returned nil; `cfg.Jira.Enabled` stays the global phase switch. **`jira.ErrAuthRevoked`** (`auth_revoked.go`, the `gmail`/`calendar.ErrAuthRevoked` shape: `invalid_grant` on the token endpoint, a 403 `unauthorized_client` naming the refresh token as invalid, or a 401 surviving a successful refresh) is what makes that status surface real — `Syncer.Sync` swallows ordinary per-project failures and returns nil, so before the sentinel a revoked grant stayed green while syncing nothing; it now aborts the account's pass and lands on the row. **Status writers are split three ways and each may write exactly one value:** the OAuth connect alone writes `"ok"` (it just proved access); `wireJiraSyncers` writes `"error"` for a missing token/cloud_id; `phaseJiraSync` writes `"revoked"` and only on `errors.Is(err, jira.ErrAuthRevoked)` — any other `Sync` error is log-only, since a phase that cannot write `"ok"` back would turn a transient blip into a sticky error clearable only by re-login. A cancelled `ctx` is never recorded (shutdown ≠ auth failure). Deliberately unlike Google, whose `gmail`/`calendar` syncers *do* write `"ok"` back on a clean pass (`recordAuthResult`) because their `Sync` fails outright on an auth problem; Slack's sync wiring writes no auth state at all.
- CLI: `watchtower jira add [--label L] [--site URL] [--no-open]`, `jira login [--account N]` (re-consent, prefers the account's current site; account #1 created on first use), `jira accounts`, `jira enable <id>`/`jira disable <id>`, `jira remove <id>` — **non-destructive** (Slack precedent: token deleted, row `status='removed'`, synced data kept). `jira logout` = remove account #1 — deliberate behavior change: the old logout wiped all `jira_*` tables via `ClearJiraData`, which is deleted. Per-account commands (`boards`/`sync`/`fields`/`boards analyze`/`override`) take a persistent `--account` flag defaulting to the single enabled account; the four cross-site dashboards (`workload`/`blockers`/`project-map`/`releases`) **reject** `--account` with an error rather than ignore it — they aggregate every connected site (`releases` scopes its per-release issue lookup by the release's own `account_id`). `jira enable`/`disable` and an explicit `--account <id>` refuse a `status='removed'` row; on re-login (`jira login --account N`) `selectJiraSite` errors out when the account's stored `cloud_id` is absent from the granted resources instead of silently re-pointing the row at another site.
- Memory: `runJiraIngest` loops enabled accounts (the `runGmailExtract` precedent), each against its own `jira_accounts.memory_jira_last_extracted_ts`; `jira:<KEY>` provenance and `jiraissue:<KEY>` aliases stay account-unscoped (documented v1 limitation mirroring `mail:`): two sites sharing an issue key address the same vault node, so each run rewrites it with the other site's issue (a per-run flip-flop, not first-writer-wins); alias scoping is an open follow-up — see `docs/inventory/memory.md`.
- Desktop: Settings → Jira is an account list (`JiraAccount`/`JiraAccountQueries`/`JiraAccountsViewModel`/`AddJiraAccountView`/`jiraSettingsSection` — structural copies of the Slack four); browse-URL resolution moved off the frozen config keys: `JiraConfigHelper.readSiteURL()` reads the first enabled account's `site_url` from the DB (pool wired in `AppState.initJiraAccounts`), yaml as pre-migration fallback — per-issue site resolution is a documented v1 non-goal. `JiraQueries.isConnected()` accepts any `jira_token*.json`; the old single-connection `JiraAuthService` is deleted. Removed accounts are filtered out of `JiraAccountQueries.fetchAll`, so a removed site leaves no ghost row. Per-board actions are account-scoped end to end: `JiraQueries.fetchBoard(_:accountID:id:)` addresses the composite PK, both boards screens pass `--account` on every CLI action, and the boards refresh runs `jira boards --account <id>` once per enabled account.
- Design: `docs/superpowers/specs/2026-08-02-jira-multi-account-design.md`. Non-goals (v1): cross-site issue-key dedup/disambiguation, per-issue Desktop browse links, concurrent OAuth flows, per-account sync schedules, per-account custom OAuth clients, cascading deletion on removal.
