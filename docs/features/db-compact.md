# Database compaction at launch (2026-10-18, board #850)

- **Why.** SQLite never gives space back to the disk on its own: `auto_vacuum` is NONE, and nothing ran `VACUUM`. A migration that shrinks rows in place (00134 rewrote every `messages.raw_json` to `'{}'`) leaves the file as large as before, and the waste is not even visible in `PRAGMA freelist_count` — the rows stay one per page. Only `VACUUM` reclaims it. It cannot run inside a migration (cost; the Desktop kills `db migrate` after 30 s), so compaction is its own launch step, between the migration and opening the Desktop's pool.
- **Go owns every rule** (when, whether, how) in `internal/db/compact.go` and `cmd/db_compact.go`; the Desktop runs the CLI and shows its state (`DatabaseCompactionStep` in WatchtowerCore, `AppState+DatabaseLaunch.swift`). Design: `docs/superpowers/specs/2026-10-18-db-compact-design.md`.
- **Out of scope:** compaction while the app runs, on a schedule or in the daemon; `auto_vacuum`/`incremental_vacuum`; `agentlog.db`.

## D1. When compaction is due (`db compact --check`)

`db.CheckCompaction` decides, by reads only: it opens with `db.OpenExisting` (read-only, 5 s busy timeout), so it never creates the file, migrates or writes. In order:

1. No `watchtower.db` → not due, `disk_ok: true`.
2. Embedded migrations not all applied → not due, `reason: "schema_pending"` (compaction waits for a launch whose `db migrate` finished).
3. **Search index fill pending** (`fts_rebuild_pending` set or `messages_fts_legacy` present, see [Search index rebuild](#search-index-rebuild-872)) → due, `reason: "fts_rebuild"`, `fts_rebuild_pending: true`; the disk fields carry the fill's rule instead of D3's (the same `statfs` reading, one call). It comes before `gave_up`: the compaction's failure cap counts compactions, not fills, so three failed compactions never hold the fill back. The fill has its own cap: after 3 failed launch fills under this CLI version it is no longer due here (see the fill's failure cap under [Through `db compact`](#through-db-compact)); the rules below then apply with `fts_rebuild_pending: true`, without rule 5 (its record waits for the fill, so a `VACUUM` now would repeat at every launch), and when none is due the reason is `fts_rebuild_gave_up`.
4. `compactMaxFailures` (3) consecutive failures under this CLI version → not due, `reason: "gave_up"` (see the failure cap below).
5. **Known space-freeing migration:** a version in `compactAfterMigrations` (`[]int64{134}`) is applied (`goose_db_version.is_applied = 1`) and greater than `last_compacted_version` → due, `reason: "migration:<v>"` (the highest such version). A missing `db_maintenance` table or key reads as never compacted (0).
6. **Free pages:** `freelist_count * page_size > compactFreelistMinBytes` (256 MiB) **and** `freelist_count > compactFreelistMinRatio * page_count` (0.25) → due, `reason: "freelist"`.

A fresh database is due after 00134 like any other; compacting a near-empty file takes milliseconds.

**A migration that frees a lot of space** (rewrites or deletes most of a big table) adds its version to `compactAfterMigrations`, so the next launch compacts once. The rule is in `.claude/skills/add-migration` and the doc comment above the list.

## D2. Running it (`db compact`)

```
watchtower db compact [--check | --if-due] [--force] [--json]
```

- `--check` reports and writes nothing; it takes neither `--if-due` nor `--force` (that misuse is exit 1). `--if-due` runs the D1 check first and does nothing when not due (`schema_pending` and `gave_up` included): exit 0, `"skipped": "not_due"`. Without either flag the command compacts without the due check (`reason: "manual"`; the daemon and disk rules still apply): it reads only whether the search index fill is pending (`db.MessagesSearchPendingAt`), so a due check that would fail does not stop it, and a failed read is logged to stderr and the run compacts. The Desktop always runs `--check`, then `--if-due`.
- **Daemon rule:** refuses with exit 3 when the daemon runs — `daemon.FindConfirmedProcess` on `daemon.pid`, the check `sync stop` uses. Only a confirmed live daemon process, or a live pid whose identity cannot be confirmed (`daemon.ErrIdentityUnconfirmed`), counts as running; a missing, stale (dead or reused pid), unreadable or malformed pid file does not, so a broken pid file never blocks compaction at every launch. `--force` overrides.
- **Disk rule (D3):** `free_disk_bytes >= 2 * db_bytes` on the volume holding `watchtower.db` (`statfs`, `Bavail * Bsize`; `VACUUM` writes a compacted copy, then the pages through the WAL). Short → exit 2 `disk`, before the database is opened. `--force` overrides. `SQLITE_TMPDIR`/`temp_store` are not changed: a system temp on another volume is not counted, and a `VACUUM` that then fails with `SQLITE_FULL` is an ordinary failure (exit 1, nothing lost).
- **Open:** `db.OpenExistingRW` with a 30 s busy timeout (`compactBusy`) — never `db.Open`, never `openDBFromConfig`. A schema that is not current → exit 5 `schema_pending`: compaction never finishes migrations the Desktop's 30 s `db migrate` did not get through.
- **Run:** `PRAGMA wal_checkpoint(TRUNCATE)`, `VACUUM`, `PRAGMA wal_checkpoint(TRUNCATE)`. `VACUUM` runs outside any transaction and is atomic: a SIGTERM, crash or power loss leaves the old content. A checkpoint that reports busy (a reader still on an older snapshot) is not an error; the final one waits up to the busy timeout, and when it still reports busy the result carries `checkpoint_busy: true` — the file shrinks at a later checkpoint (the Desktop logs it).
- **Busy is not a failure:** a `VACUUM` or checkpoint that gives up on another process's lock (`SQLITE_BUSY`/`SQLITE_LOCKED`, `db.IsBusy`) is exit 1 with `error` saying busy, and is **not** counted against the failure cap — the file is fine and the next launch tries again.
- **Record:** on success, in one transaction, `last_compacted_version` = the highest applied goose version, `compacted_at` (RFC 3339 UTC), and the failure counter removed.
- **SIGTERM:** the command installs the shutdown context (`notifyShutdownContext`) before the `--if-due` check, and `VACUUM` runs with `ExecContext`, so a SIGTERM fires `sqlite3_interrupt` → `"skipped": "interrupted"`, exit 4, nothing recorded, due again next launch. The interrupt is honoured while the compacted copy is built, not during VACUUM's final copy-back into the main file (seconds on a large file), so a skip may take a few seconds. An interrupt racing VACUUM's commit can report `interrupted` for a file that was compacted; nothing is recorded, and the next launch re-runs it cheaply.

### Exit codes and JSON

| Exit | `skipped` | Meaning |
|---|---|---|
| 0 | — / `not_due` | Compacted, or nothing due |
| 1 | — | Any other error (`error` filled; flag misuse, config, workspace, the `--check` read, `VACUUM` failure, busy) |
| 2 | `disk` | Not enough free disk (D3) |
| 3 | `daemon_running` | The daemon runs |
| 4 | `interrupted` | SIGTERM; the database is unchanged |
| 5 | `schema_pending` | Migrations pending; run `watchtower db migrate` |

With `--json` the result is the **last** stdout line on every outcome, errors included; the Desktop decodes the last non-empty line, so a line printed before it is not part of the contract. `db compact` sets its own no-op `PersistentPreRunE`, so the root's `ensureSchemaFormat` (a schema-format upgrade and a config write) does not run for it: `--check` writes nothing, the config included. Keys (snake_case, `internal/db/compact.go`; `TestDBCompact_WireKeys` pins them):

- `--check`: `due`, `reason` (`fts_rebuild`, `migration:<v>`, `freelist`, `schema_pending`, `gave_up`, `fts_rebuild_gave_up` or `""`), `db_bytes`, `wal_bytes`, `free_disk_bytes`, `needs_disk_bytes` (= 2 × `db_bytes`, `needsDiskBytes`; while the fill is due, the fill's 64 MiB floor), `disk_ok`, `fts_rebuild_pending` (always present once the schema is current). A `--check` that fails (flag misuse, config, workspace, the read) prints the run shape instead: `{"compacted":false,"error":"…"}`, exit 1.
- run: `compacted`, then as they apply `skipped`, `reason`, `bytes_before`, `bytes_after`, `duration_ms`, `error`, `failures`, `gave_up`, `checkpoint_busy`, `fts_rebuilt`. `fts_rebuilt: true` means **the fill is complete** — also when another process (the daemon, a second CLI) completed it — not that this run did the work. A fill that is skipped or fails ends the run with `skipped` as in the table and `reason: "fts_rebuild"`; there is no separate `fts_skipped` key.
- phase lines (only with `--json`, before the result line): `{"phase":"fts_rebuild"}` before the fill, `{"phase":"compact"}` before the `VACUUM`. Only the key `phase`; the Desktop's `CompactionPhaseScanner` reads them as they arrive and skips any other line.

## D4. State — `db_maintenance` (migration 00145)

`db_maintenance(key TEXT PRIMARY KEY, value TEXT NOT NULL)`, values as text: `last_compacted_version`, `compacted_at`, `compact_failures`, `compact_failures_version`, the search index fill's `fts_rebuild_pending` / `fts_rebuild_cursor_messages` (migration 00147), and the launch fill's failure counter `fts_rebuild_failures` / `fts_rebuild_failures_version` (no migration: `db_maintenance` is key/value). Absent key = never compacted / no failures. A value that is not an integer where one is expected is an error, not a zero.

**Failure cap.** A failed compaction (`VACUUM` error, an I/O error after the `VACUUM`, a failed record) increments `compact_failures` under `compact_failures_version` = the CLI build version (`cmd.Version`; the bundled CLI ships with the app, so this is the app release); a new version restarts the count at 1, and a success removes both keys. At 3 the result carries `gave_up: true` and `--check` reports `gave_up` (not due) until the version changes, so a persistent failure cannot cost every launch.

## D5. The Desktop launch step

Launch order: `db migrate` → **compaction step** → `DatabaseManager(path:)` (the pool) → `ensureDaemonRunning` (`AppState.migrateCompactOpen`). The step never fails the launch:

0. `DatabaseManager.resolveDBPath()` fails → no CLI call at all; `databaseNotFound` (a fresh install) is silent, any other error is logged.
1. `db compact --check --json`, 30 s timeout; a spawn failure, timeout, non-zero exit or undecodable line is logged and the launch continues (a quit during it logs "cancelled by quit").
2. Not due → continue. Due but `disk_ok` false → continue with a notice: **Watchtower could not optimize its database: it needs <N> free, <M> available.** (sizes via `ByteCountFormatter`, `.file` style).
3. Due and disk OK → `DaemonManager.stopDaemonBounded()` — on the daemon-start queue (`serializeDaemonStop`), so a start already running finishes first; the step records `stoppedDaemon` — then `db compact --if-due --json` with **no** timeout. The splash (`SplashView`, the existing `isLoading` screen) shows **Optimizing database — <size>, <m:ss>** with **This happens rarely, usually after an update.** under it; the time ticks every second. From 15 s a **Skip for now** button sends SIGTERM; if the child is still alive more than 10 s later, SIGKILL (safe: `VACUUM` is atomic). The launch continues once the child has exited.
4. The exit is read with its termination reason (`CompactionExit.reason`): a child ended by a signal is logged as "killed by signal N" with stderr. Exit 2 shows the disk notice and exits 3, 4 and 5 are logged as their skip only when the result line's `skipped` agrees (`disk`, `daemon_running`, `interrupted`, `schema_pending`); any other combination is logged with the exit status and stderr. Exit 1 with `gave_up` shows **Watchtower could not optimize its database after 3 attempts. It will try again after the next update.**; exit 0 without a result line logs stderr; `checkpoint_busy` is logged ("the space is reclaimed at the next checkpoint"). Any result → open the pool, then the rest of the launch as before.
5. The database then fails to open after the step stopped the daemon, or after a restart was refused during the launch's database steps → on a finished install (onboarding complete) the daemon is brought back (`restoreDaemonStoppedForCompaction`): a refused restart (`deferredRestartDuringLaunch`) restarts it (`bringUpDaemonInBackground(startOnly: false)`) so it reads the new config, a stop alone only starts it. A launch that lands in onboarding with a database never had onboarding complete (`reconcileOnboarding` keeps a complete step), so it needs no restore.

The notice is non-blocking and shown once per launch, in the main window's detail header; it is hidden while a daemon banner shows (the banner takes the slot). It is not shown in the tray.

**Daemon starts are gated** from before `db migrate` until the open (`launchDatabaseStepsRunning`), and while the step runs (`databaseCompactionInProgress`) — `AppState.daemonStartBlocked`: `ensureDaemonRunning`, `bringUpDaemonInBackground`, `startDaemonFromBanner`, `restartOnChain` (Features turn-on and other config changes) and the Slack disconnect restart do nothing, and the tray's **Sync Now** is disabled. Starts queued on the daemon-start queue re-check the gate when they run, not only when enqueued. A restart refused this way (`restartOnChain`, `bringUpDaemonInBackground`) sets `deferredRestartDuringLaunch`: after a successful open the launch's own `ensureDaemonRunning` starts the daemon with the current config; after a failed open the D5.5 restore replays it as a restart. The account view models' `restartLoggingQueued` is not gated: they are built after the database opens.

**Quit during the step** (⌘Q, tray Quit): the quit path calls `terminateDatabaseCompactionForQuit` before it stops the daemon — a running `--check` is cancelled and a running `db compact` child gets SIGTERM, then SIGKILL if it has not exited within `DatabaseCompactionStep.quitGrace` (3 s), so neither outlives the app under launchd; the launch then neither runs the step nor starts the daemon.

## D6. Other processes during the step (accepted effects)

- **Daemon:** stopped for the step.
- **`watchtower mcp` servers and terminal-session hooks** that survived the update keep idle connections; an idle connection does not block `VACUUM`. Their writes during the step wait up to their busy timeouts (MCP owner writes 30 s, hooks 1 s, ask guard 0.5 s) and may fail. Accepted: an agent left running across the update may lose a status update; the state hooks rewrite the current state on their next event.
- **A CLI command started by the owner** during the step waits up to 5 s and may fail with busy. Accepted.

## Search index rebuild (#872)

- **Why.** Until migration 00147, `messages_fts` and `transcripts_fts` found their row for a message or transcript through an UNINDEXED column (`channel_id` + `ts`, `transcript_id`), so every trigger's `DELETE` scanned the whole index: each message write cost O(index), a sync batch O(n²). 00147 keys both indexes by the source row's rowid (`messages.rowid`, `meeting_transcripts.id`); the triggers delete by `rowid` first, then insert under the same rowid. The contract is SEARCHIDX-01 (`docs/inventory/search-indexes.md`). Design: `docs/superpowers/specs/2026-10-20-fts-rowid-design.md`. `memory_fts` is out of scope (owner decision, ask #364): its text lives only in the index and the vault, and it is small.
- **The migration.** `transcripts_fts` is rebuilt inside 00147 (small). `messages_fts` is not: refilling it would not fit the Desktop's 30 s `db migrate`. 00147 renames the old index to `messages_fts_legacy` (triggers dropped first), creates the new rowid-keyed index empty and sets `fts_rebuild_pending = '1'`. After goose returns, `migrate()` drops the legacy table and both keys when no message is indexable (`dropEmptyMessagesSearchLegacy`, best effort — a fresh install never sees a fill). Readers are unchanged and read only `messages_fts`, so until the fill finishes search misses older messages; new and edited messages are indexed by the triggers from the start.
- **Pending** = `fts_rebuild_pending` set **or** `messages_fts_legacy` exists (a legacy table without its key is still filled and dropped).
- **Desktop Search line (#892).** While the fill is pending, the Search screen shows **Search index is still being updated — older Slack messages may be missing.** above the results (`SearchIndexRebuildNotice`). `SearchViewModel` reads the state with `SearchQueries.messagesIndexRebuildPending` — the Swift twin of Go's `messagesSearchPending`, the same rule (the key with any value, or the legacy table; a missing `db_maintenance` reads as no key) — when the screen appears and on each search, one small read beside the search reads; no polling. A failed read is logged and hides the line; it never blocks the search. Twin tests: `TestMessagesSearchPending_States` (Go) and `SearchIndexRebuildPendingTests` (Swift) over the same states. The chat's `list_messages` result is a bare JSON array (also read by automation recipes through `tool()`), so it carries no note.

### The fill (`db.RebuildMessagesSearch`, `internal/db/fts_rebuild.go`)

- **Order: the legacy index goes first.** While `messages_fts_legacy` exists, each chunk frees it: the launch step (daemon stopped) drops it in its first chunk; the daemon drains it in short chunks and then drops it (see the bounded legacy drain below). The drop sets `fts_rebuild_pending` in the same transaction, so a legacy table that was the only pending mark still leads to the fill. Only then do fill chunks run, and the new index, about the legacy one's size, reuses the freed pages: the file does not grow (`TestRebuildMessagesSearch_FileDoesNotGrow` samples `page_count` after every chunk). Readers never read the legacy index, so freeing it first loses no search result that the fill would not restore.
- **Chunk:** one short write transaction over the next 5000 `messages` rows past the cursor (`fts_rebuild_cursor_messages`), indexable or not, cut short once their indexable text reaches 4 MiB (`ftsRebuildChunkTextBytes`): a Slack message holds up to ~40k characters, and a chunk writes a small multiple of its text to the WAL, so this keeps a chunk well under the disk floor. The chunk takes rows while the text before them is under the budget, so a single message larger than it still gets a chunk of its own. `hi` = their highest rowid; every indexable row in (cursor, hi] that is not already indexed is inserted under its rowid (`NOT EXISTS` skips rows the triggers indexed), and the cursor moves to `hi` in the same transaction. Each chunk re-reads the pending state and the cursor first, so a process that finds the fill finished by another one completes without writing a cursor.
- **Gap:** 100 ms after each committed chunk (`ftsRebuildChunkGap`), so a writer waiting on the lock gets in: SQLite's busy handler sleeps in steps that grow to 100 ms. A cancel during the gap ends the call. On synthetic data (200k messages) one chunk held the write lock for about 50 ms, and the fill runs at roughly 30 s per million messages.
- **Resumable:** a budget stops the call between chunks; a cancelled context rolls back the chunk in flight; committed chunks keep their cursor and the next call resumes.
- **Completion:** when the legacy table is gone and no row is left past the cursor, one transaction deletes both keys and the launch fill's failure counter. It does not touch the compaction record: the freed legacy pages make a compaction due on their own (D1's free-pages rule).
- **Disk rule:** free space on the volume ≥ 64 MiB (`ftsRebuildMinFreeBytes`), a fixed floor: since the legacy index is freed first, only WAL frames need room (a chunk writes a few MB, bounded by its text budget). No sizes are read. `--force` overrides. (Until the 2026-10-20 review it was 1.5 × the legacy index's size, kept to the end of the fill: a volume with less free space than that skipped forever — the daemon too, since each Slack sync moved `MAX(rowid)` past the cursor before its fill phase.)
- **A chunk error during a cancel** (a real failure in the same moment as a SIGTERM or Skip) is logged (`slog.Warn`) and the run still ends as interrupted.

### Through `db compact`

- **Check order** (D1): `schema_pending` → `fts_rebuild` → `gave_up` → migration → freelist. A pending fill is due and is not held back by the compaction failure cap.
- **One child, fill then `VACUUM`:** after the check and the daemon rule, `compactDatabase` prints `{"phase":"fts_rebuild"}` (with `--json`; a human run prints `Updating the search index of <file>…`) and runs `RebuildMessagesSearchAt` to completion (no budget). That call reads first on a read-only handle and applies the disk rule before any read-write open. A fill that is skipped (`disk`, `interrupted`, `schema_pending`) or fails ends the run with that `skipped`/error, the exit code from the table and `reason: "fts_rebuild"`; a fill error is never counted in `compact_failures`.
- **The fill's failure cap:** a launch fill error (not busy, not interrupted) is counted in `fts_rebuild_failures` under `fts_rebuild_failures_version` = the CLI version, as the compaction's counter is (a new version restarts at 1; the fill's completion, by any process, deletes both keys). The run result carries no `failures`/`gave_up` for it: those stay the compaction's. At 3 the check reports `{"due":false,"reason":"fts_rebuild_gave_up","fts_rebuild_pending":true,…}` (or `freelist` when that rule is due), so `--if-due` runs no fill and the launch is not held by a fill that keeps failing; a manual `db compact` still fills, and the daemon keeps filling regardless. A human `--check` prints `<file> is not due for compacting; its search index rebuild failed repeatedly at launch and is left to the background sync (fts_rebuild_gave_up).` After the fill, `--if-due` checks again: not due → `{"compacted":false,"fts_rebuilt":true,"skipped":"not_due"}` (a human run prints `Updated the search index of <file>; it does not need compacting.`). Otherwise `{"phase":"compact"}`, then the `VACUUM` as in D2, with `fts_rebuilt: true` on the result. A manual run (no flag) fills first too.
- **No record while pending:** `Compact` never writes `last_compacted_version`/`compacted_at` while the fill is pending, so a compaction can never be recorded over a half-built index.
- A launch-step `DROP` of a large legacy index holds the write lock in one transaction: about 0.5 s on 2M synthetic messages. The daemon is stopped then, so only a surviving hook or MCP write may wait on it (D6).
- An interrupted fill (SIGTERM, Skip) prints `… was interrupted; it continues where it stopped on the next run` and exits 4; the committed chunks stay.

### The launch splash

The Desktop picks its first running phase from the check's `fts_rebuild_pending`: the splash shows **Updating search index — m:ss** with the same subtitle (**This happens rarely, usually after an update.**) and the same **Skip for now** from 15 s. A `{"phase":"compact"}` line moves it to **Optimizing database — <size>, <m:ss>** with the clock reset; the skip and kill thresholds still count from the child's start. When the check has `fts_rebuild_pending` and the disk is short (`disk_ok: false`, or exit 2 before the fill finished), the notice reads **Watchtower could not update its search index: it needs <N> free, <M> available.**; an exit 2 after the fill finished (`fts_rebuilt`, or a `compact` phase line seen) shows the compaction notice. A result with `fts_rebuilt` logs `DB search index rebuilt`. Skip leaves a partial fill, which the next launch or the daemon finishes.

### The daemon fallback (`internal/daemon/search_rebuild.go`)

`phaseMessagesSearchRebuild` runs in every sync cycle, right after `phaseKnowledgeIndex` (and so after `phaseSlackSync`; `TestDaemon_RunSync_RebuildsSearchIndex` pins it), for installs whose launch step did not run, did not finish or gave up. It is inert when nothing is pending; mechanical, no AI, no `pipeline_runs` row, independent of both failure caps. Each cycle fills for at most 30 s (`searchRebuildBudget`); a volume below the 64 MiB floor is skipped and logged once, and logged again only after a cycle found room. Log lines: `search index: rebuilt`, `search index: clearing the old index, continuing next cycle`, `search index: N messages indexed, continuing next cycle`, `search index: old index cleared, N messages indexed, continuing next cycle` (the cycle that dropped the legacy table and began filling), `search index: stopped by shutdown`, `search index: <error> (this cycle: N messages indexed in M chunks)`, and on a short disk `search index: rebuild needs N MB free, M MB available; skipped until there is room`.

**Bounded legacy drain.** Hooks, MCP and the Desktop write beside the daemon, and one `DROP` of a large legacy index holds the write lock for the whole table (about 0.5 s on 2M synthetic messages, past a hook's lock budget). So the daemon passes `DrainLegacy`: before any fill chunk, each chunk deletes up to 150 `_data`, 1500 `_content` and 1500 `_docsize` rows of the legacy shadow tables (`ftsLegacyDrain`), with the same gap and budget; the chunk that finds them all below their limits drops the near-empty table, and the fill chunks follow. On the same synthetic data a drain chunk held the lock for about 3 ms (p99 about 10 ms). The launch step runs with the daemon stopped and drops the legacy table directly, also after a partial drain.

**`PRAGMA integrity_check` during a drain** reports `malformed inverted index for FTS5 table main.messages_fts_legacy`. This is expected and harmless: nothing in the app runs `integrity_check` or reads the legacy index, and the table is dropped right after the drain. A support or debug run in that window should not treat it as corruption.

## Rowid guard

`messages` (and several other tables) have no `INTEGER PRIMARY KEY`, and SQLite documents that `VACUUM` may renumber such rowids — but saved cursors depend on them (`internal/doclinks/linkscan` `synced_at|rowid` cursors, memory's rowid identities, the knowledge-index cursors). The SQLite inside `modernc.org/sqlite` keeps rowids through `VACUUM`, and `TestCompact_PreservesRowids` (`internal/db/compact_rowid_test.go`) pins it: it seeds every table in `rowidTables` with gaps from deletes, compacts, and asserts every `(rowid, primary key)` pair is unchanged. A new table with a rowid-based cursor must be added to `rowidTables`.

**If the guard fails** (typically after a driver upgrade): do not ship that driver with compaction as is. Either keep the old driver, or make `Compact` reset the affected cursors after a successful `VACUUM` (they then rescan once) before upgrading.
