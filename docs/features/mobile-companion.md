# Mobile companion (POC)

Specs: [business](../superpowers/specs/2026-10-07-mobile-poc-business.md) and [technical design](../superpowers/specs/2026-10-07-mobile-poc-design.md).

Section labels name the plan task that built them: A<n>, B<n> and C<n> are Task n of `docs/superpowers/plans/2026-10-08-mobile-poc-a-skeleton.md`, `…-b-workbench-remote.md` and `…-c-calendar-recording.md`. Sections are grouped hub (the Mac) → Kit (shared Swift package) → phone; each half of a phone feature links its other half.

## Architecture

- **The hub lives in the Desktop process** (`WatchtowerDesktop/Sources/Services/MobileHub/`). The Go daemon never touches CloudKit. Only the Desktop executable target (and its test target) links the Kit's `WatchtowerSync`; `WatchtowerCore` stays Kit-free (`PublicAPISurfaceTests`).
- **Zones and scopes.** The hub writes `DataZone` (it is the zone's only writer) and reads phone requests from `RelayZone`, both custom zones in the Mac user's private database, through `CKSyncEngine` (`CloudKitTransport`, `private` scope). A same-Apple-ID phone syncs that private database; a different-Apple-ID phone reaches both zones through zone-wide shares in its `shared` scope (DataZone read-only, RelayZone read-write).
- **Kinds.** DataZone records are `SliceKind`s (`heartbeat`, `device_grant`, `recording_job` and the workbench kinds); RelayZone records are `RelayRecordKind`s (`action`, `recording_upload`, `device`). Record names are `<kind>-<id>`.

## Building and testing

- **Three Swift trees.** `WatchtowerKit/` is a Swift package with two products: `WatchtowerSync` (transport, replica, relay, link codec; the Mac hub links it) and `WatchtowerKit` (the slice mirrors and the review text helpers, phone only). `WatchtowerDesktop/` holds the hub (`Sources/Services/MobileHub/`). `WatchtowerMobile/` is the iPhone app, an xcodegen project: `project.yml` is the source, `WatchtowerMobile.xcodeproj` is committed and regenerated with `make mobile-gen` (never hand-edited).
- **Kit.** `make kit-test FILTER=<Class>` (a regex alternation works); without `FILTER` the whole Kit suite runs (small, no ML stack). An unfiltered `make test-swift` runs the Desktop suite and then `kit-test`.
- **Phone.** `make mobile-build`, `make mobile-test MOBILE_FILTER=<Class>` (an alternation becomes one `-only-testing` per class), `make mobile-run` (build, boot, install, launch) on the simulator named by `SIM` (default `iPhone 18 Pro`; override with one your Xcode has). `mobile-test` boots the simulator and uninstalls the app first, because the test host shares the installed app's on-disk replica. Every simulator target passes `CODE_SIGNING_ALLOWED=NO`.
- **Signing.** `WatchtowerMobile/Base.xcconfig` is unsigned by default and includes the gitignored `Signing.xcconfig` (copy `Signing.xcconfig.template`, set `DEVELOPMENT_TEAM`; never commit a team id). A signed build carries the iCloud entitlement and goes live over CloudKit; an unsigned one runs the in-memory demo (see App shell). `make mobile-archive` makes a TestFlight archive and `.ipa` through `ExportOptions.plist` and needs `Signing.xcconfig`; the upload is manual.
- **Lint.** `make lint-swift` lints the Desktop (with its baseline), the Kit and the phone app (`swiftlint lint --strict` in each); the phone's config holds the `orange_outside_phone_tone` rule.
- **CI.** Swift Test runs the Desktop and Kit suites; Swift Lint lints all three trees; Mobile App runs `make mobile-build` and `make mobile-test` on macos-26 with `SIM="iPhone 17 Pro"`, a device the image's iOS 26.4 runtime lists (Xcode 26.4.1).
- **Shell tests.** `scripts/tests/test-build-app-cloud.sh` (`make test-scripts`) covers the hub's signing.

## Building a hub-capable Mac app (A10)

The mobile hub syncs through CloudKit, so it needs a Developer ID build that carries the iCloud entitlements and an embedded provisioning profile (design §10).

- **The profile.** A Developer ID provisioning profile (developer.apple.com → Profiles → Developer ID) for App ID `com.watchtower.desktop` — the app's `CFBundleIdentifier` (`BUNDLE_ID` in `scripts/build-app.sh`), not `com.aiwatchtowers.watchtower` — on the signing identity's team, with the iCloud capability and the container `iCloud.com.aiwatchtowers.watchtower`. Point `WATCHTOWER_PROVISION_PROFILE` at the downloaded `.provisionprofile`; a relative path resolves against the project root, so the variable can live in the build profile (`.env`, or the `ENV_FILE` of a flavor).
- **Early check** (`provision-profile-check`, before the Swift build): the profile is decoded with `security cms -D`; the build fails if the file is missing or undecodable, if its `com.apple.application-identifier` is not `<its team-identifier>.com.watchtower.desktop`, or if it does not grant the container.
- **Signing** (`app-codesign`): with a real identity and a checked profile, the profile is copied to `Contents/embedded.provisionprofile` and the bundle is signed with a temporary copy of `scripts/Watchtower-cloud.entitlements` into which the profile's `com.apple.application-identifier` and `com.apple.developer.team-identifier` are merged. A hand-signed app with restricted entitlements needs both (Xcode adds them; `codesign` does not). The team id is never written in the repo.
- The cloud entitlements are the base `scripts/Watchtower.entitlements` plus `com.apple.developer.icloud-container-identifiers` = `iCloud.com.aiwatchtowers.watchtower`, `com.apple.developer.icloud-services` = `CloudKit`, `com.apple.developer.icloud-container-environment` = `Production` and `com.apple.developer.aps-environment` = `production`. Keep the base keys in sync; the test checks it.
- Every build flavor (`BUILD_FLAVOR`, e.g. `ENV_FILE=.env.corp`) uses the same bundle id and container: both are signed by the same Developer team. The signing blocks have no flavor logic.
- A real identity without a profile signs with the base entitlements and prints `WARNING: mobile hub disabled: no provisioning profile`; the app then shows "Needs a signed build" in Settings → Mobile.
- Ad-hoc signing (`make app-dev`, or no identity) always keeps the base entitlements and never embeds a profile: amfid kills an ad-hoc app that carries restricted entitlements. A set `WATCHTOWER_PROVISION_PROFILE` is still checked early, then ignored with the note `provisioning profile ignored: ad-hoc signing`. Hub logic is tested on `InMemoryCloudTransport` and needs no signing.
- Whether amfid accepts the signed bundle and CloudKit reaches Production can only be shown on a real device (the A14 device smoke).
- Covered by `scripts/tests/test-build-app-cloud.sh` (`make test-scripts`), which runs both blocks against stubbed `security` and `codesign`.

### CloudKit environments

CloudKit keeps two environments per container, Development and Production, and a record saved in one is never seen from the other. The Mac and the phone must talk to the same one, or the phone sees no hub and the hub sees no phone actions — with no error on either side.

- **Which build lands where.** The Mac's Developer ID build is Production (`com.apple.developer.icloud-container-environment` = `Production`, `aps-environment` = `production`, from `scripts/Watchtower-cloud.entitlements`). The phone run from Xcode (the Debug configuration, `WatchtowerMobile/WatchtowerMobile.entitlements`) is Development; a TestFlight or App Store phone build is Production.
- **Pairs that work.** A Developer ID Mac ↔ a TestFlight/App Store phone (Production). A Development-signed Mac ↔ a phone run from Xcode (Development). A Developer ID Mac with an Xcode-run phone never meets.
- **A Development Mac.** Build with an Apple Development identity, a macOS development provisioning profile for `com.watchtower.desktop` with the container, CloudKit and Push Notifications, and `WATCHTOWER_CLOUDKIT_ENV=Development` (environment or build profile). `build-app.sh` then rewrites `icloud-container-environment` to `Development` and `aps-environment` to `development` in the temporary signing copy; the repo's entitlements file stays Production. Any other value than `Production` or `Development` fails the build.
- **Early profile check.** Besides the App ID and the container, the profile must grant CloudKit (`com.apple.developer.icloud-services` lists `CloudKit`, or is `*`), the chosen environment (`com.apple.developer.icloud-container-environment` lists it; a Developer ID profile lists Production only), and an `aps-environment` equal to the chosen one (`production` / `development`). Otherwise the build fails before the Swift build, naming the missing grant.
- **Before the first Production run**, deploy the schema from Development to Production in the CloudKit Console (Deploy Schema Changes): Production refuses record types it has not been given, and records are created in Development first by any Development run.

## Mac hub

### Hub skeleton, heartbeat and the single-hub rule (A6, A7)

- **Opt-in.** `Constants.mobileSyncEnabledKey` (`mobileSyncEnabled`, off by default in every flavor). `AppState.initMobileHub(dbPool:)` runs at the end of `initWorkbenches`: it stops and drops the previous hub, and builds a new one only while the toggle is on, because the hub holds the centers `initWorkbenches` replaces. With the toggle off nothing is opened or written. `AppState.setMobileSyncEnabled(_:)` starts or stops the same hub object. A replaced hub is `dispose()`d (it never starts again, even from a queued start), and the new one starts only after the old one's teardown has drained.
- **Storage.** `MobileHubStorage` opens `~/Library/Application Support/Watchtower/MobileHub/` (`transport.db` behind the CloudKit transport, `hubstate.db` = `HubSyncState`) once per app run; hub rebuilds and toggles reuse it, so two sync engines never drive one store. A failure to open it is kept in `AppState.mobileHubInitError` and no hub is built.
- **`MobileHubService`** (`@MainActor`): starts the transport, gates on iCloud availability (`.unavailable` runs no loop and re-probes every 600 s), then runs the publisher loop and the relay loop. Relay cadence: 3 s while a QR code is open (`linkCenter.openCode`, so a scanning phone's `device` record is read well inside its 60 s grant wait) or a phone action or `device` record was handled in the last 300 s, otherwise 30 s, plus the engine's own pushes. `stop()` stops the transport first (so a hung fetch is cancelled), then lets the cancelled relay loop end: each record's work runs in an unstructured task that does not inherit the loop's cancellation, so a stop takes effect only between two records and never turns an apply into a false `write_failed`. The transport stop (`HubTransport.stop()`; `CloudKitTransport.stop()` cancels and drops the engine, so a turned-off hub neither fetches nor sends); the next `start()` awaits that teardown. An account-change reset wipes the slice hashes and the relay change token but keeps the exactly-once ledger: relay record names are phone UUIDs, and on a same-Apple-ID sign-out/sign-in the re-fetched zone still holds actions whose echo never landed. A record CloudKit rejects even alone (`.limitExceeded`) has its `slice_state` hash cleared.
- **`SlicePublisher`.** One loop serves both cadences, so two sends never interleave: a full hash diff every 10 s over every kind, and the fast lane — `nudge(kinds:)` coalesces for 1 s, then diffs only the nudged kinds, with at least 2 s between two fast sends. `sliceSQL` is empty: every published kind is a capped projection behind a `SliceSource` (`kind`, `records(_ db: Database) -> [SliceRecord]`, the kind's whole window — a record missing from it is deleted from the zone). Payload guard: a record over `maxPayloadBytes = 900_000` is skipped and not hashed, with a warning throttled per (record name, payload hash); exactly 900_000 bytes publishes. A mid-cycle account reset (generation bump) aborts the cycle before stale hashes are recorded.
- **`RelayProcessor`** (background): decode, exactly-once, age, echoes. `relay_processed(record_name, phase, outcome, updated_at)` is the ledger: a `done` record is skipped; a non-idempotent kind (`board_comment_add`, `board_comment_reply`, `board_target_create`, `session_start`, `session_input`, `session_finish_request`) is claimed `begun` atomically (`INSERT … ON CONFLICT DO NOTHING`) before its handler and marked `done` after its echo; a record a later pass finds still `begun` is echoed `failed` / `outcome_unknown` and never re-applied. Age: older than 7 days after `created_at` → `expired` (24 h for `session_input`, `session_finish_request`, `session_start`). `session_start`, `session_input` and `board_target_create` are echoed `received` before any work. `probe` is answered by the hub itself (`applied`, `{nonce, hub_id}`; no nonce → `invalid_params`). `target_done`, `target_snooze`, `task_create` and every kind without a registered handler fail `unsupported_in_poc`; a throwing handler fails `write_failed`. Passes are single-flight across every processor sharing the sidecar (`RelayPassGate`, also covering hygiene), and cancellation is checked between records. A pass handles at most 200 records and reports the rest; the service re-runs at once until the backlog is empty (a long Mac sleep drains in one cycle), `relayBacklog` counts down, and the change token is persisted only when a pass leaves nothing behind. Daily hygiene deletes action and recording-upload records older than 7 days (an unhandled pending one waits for its `expired` echo), then sweeps the local buffer and prunes the ledger one day past that window.
- **`MobileHubCommandDispatcher`** (`@MainActor`): `register(_ kind:handler:)` with `@MainActor (ActionRequestPayload) async throws -> ActionOutcome`. Empty in A; B registers its workbench handlers in `AppState.buildMobileHub`. Rules for handlers: a handler must never call back into the relay processor (`processOnce`, `runHygieneIfDue`) — the pass gate is not re-entrant, so the pass would wait on itself forever; and each handler owns its timeout — a hub stop (and a rebuilt hub's start) waits for the record being applied, so a hung PTY write or DB call would hang them.
- **Hub id.** `HubSyncState.ensureHubID()` creates one UUID per install in `hub_meta` (`hub_id`), kept across account resets.
- **Heartbeat and the single-hub rule** (spec §4.1, §8 I-1). `HubIdentity` keeps `hub_id` and `enabled_at` (set by the first enable, kept across relaunches, off/on and account resets) in `hub_meta`, plus the heartbeat read state (`heartbeat_cursor` over the DataZone buffer and `heartbeat_seen`, both wiped on an account reset). `enable()` (= `start()`) pulls (bounded by `cloudTimeout`, 30 s), reads `heartbeat`, and refuses with `.otherHub(mac_name)` when the newest heartbeat known is another `hub_id`'s, written under 720 s ago — the transport is stopped and nothing is written; exactly 720 s old is stale and allowed. A pull that failed or timed out before this hub ever completed a heartbeat read (no `heartbeat_cursor`) is not a claim: the hub goes `.unavailable` and re-probes, since an empty buffer proves nothing; once a read completed, the buffered heartbeat decides. Otherwise it writes this hub's heartbeat (DataZone, record `heartbeat`, every field of `HeartbeatPayload`) and remembers it as `heartbeat_seen` — CloudKit never fetches a device's own saves back, so without that a restart right after a take over would refuse itself. A fetched heartbeat replaces `heartbeat_seen` only when its `updated_at` is later. The heartbeat loop runs every 300 s: it reads first, and when the newest heartbeat is another hub's, live and later than this hub's own last write, this hub stops with `.tookOver(mac_name)`; otherwise it rewrites the heartbeat. Three failed ticks in a row (`maxTickFailures`) stop the hub as `.unavailable` and the reprobe loop restarts it through the full check. `takeOver()` skips the refusal, writes this hub's heartbeat, then calls the `onTakeOver` seam (share teardown, wired with the zone shares). `accounts[]` is `HubAccountRows` — kind, label (falls back to team/email/site name, ≤ 80) and status of Slack, Google and Jira rows, removed ones left out, ≤ 20; no other column is read. `mac_name` is `Host.current().localizedName`, cut to 60 grapheme clusters; `flavor` is `default` for a build with no `WTBuildFlavor` or `dev`, `corp` for any other; `owner_user` is looked up once (bounded) through `MobileHubStorage.ownerUser`; `sharing` is set by the link center (`none` until then). Races (spec risk 6): a late-arriving older heartbeat never stops a hub, so of two writes the later `updated_at` wins and only the other hub stops. This compares two Macs' clocks; a skew larger than the gap between the two writes can pick the wrong one.
- Tests: `MobileHubServiceTests`, `RelayProcessorTests`, `SlicePublisherTests`, `HubSingleHubTests` (on a stub transport over `InMemoryCloudTransport`; two stubs over one cloud are two Macs).

### Linking, hub half (A8)

- **`MobileLinkCenter`** (`@MainActor`, `@Observable`; `MobileHubService.linkCenter`, built by `AppState.assembleMobileHub` only when `MobileHubStorage.shares` is set — the live storage has `CloudKitShareService`, a stub storage none). Observable state: `openCode` (the QR on screen) and `devices` (the linked phones, oldest link first). Settings → Mobile (A9) uses `accountAvailability()`, `issueCode()`, `closeLink(reason: .sheetClosed)`, `remove(deviceID:)`, `setTypingAllowed(_:deviceID:)` and `setStartSessionsAllowed(_:deviceID:)`.
- **`ShareService`** is the CloudKit seam: account status, `ensureShares()` (the two zone-wide `CKShare(recordZoneID:)`, created on first use and reused), `setPublicLink(open:)` (DataZone `.readOnly`, RelayZone `.readWrite`, or `.none`), `participants(in:)`, `removeParticipants(in:where:)`, `deleteShares()`. `CloudKitShareService` runs on the Mac user's private database; tests use `FakeShareService`.
- **`issueCode()`** refuses without iCloud (`MobileLinkError.account(.noAccount / .restricted / .unavailable)`, sentences per spec §2.3) or without the Mac's user record name, and then creates nothing. Otherwise it creates or reuses the shares, marks `share_sweep_pending` in `hub_meta`, opens the public link and stores the code in `link_codes(nonce, issued_at, exp, used_by_device, used_at)` (`exp = iat + 600`, the newest 50 kept). A new code retires every unused code still open (its `exp` set to just before the new one's issue), so only the newest code links; a phone scanning the old QR reads `expired_code`. A share failure leaves `data_share` / `relay_share` out of the QR (only a same-Apple-ID phone can link then) and sets the heartbeat's `sharing` to `unavailable`; a success sets `available`.
- **`closeLink(reason:)`** runs on use, at expiry (a timer at `exp`; `closeLinkIfExpired()`) and on `.sheetClosed`: it sets `publicPermission = .none`, then removes every participant whose iCloud user is not a linked `shared` phone (spec primary path; the F2 fallback is not built). The sweep runs only while `share_sweep_pending` is set (the link was opened, or a Remove failed to drop its participant), so no share call is made otherwise; a failed sweep keeps the mark and is retried by the next close, including `.restart` at each hub build (a crash with the QR shown). The expiry timer detaches itself before it closes, so the close is never cancelled by its own timer.
- **Bounds.** Every share call runs under `shareTimeout` (`MobileHubService.defaultCloudTimeout`, 30 s; a call still running is cancelled and left to end): offline CloudKit waits for connectivity, and `handleDevice` runs inside the relay pass, which a hub stop waits for. The close after a link runs outside the pass (`closeAfterLink`). `CloudKitShareService` checks the iCloud entitlement first: without it (an unsigned dev build) the account reads `.unavailable` and no `CKContainer` is touched.
- **`handleDevice(_:)`**: the relay hands it every `device` record (`RelayProcessor.DeviceRecords`, unbudgeted). A record without a `link_nonce`, or marked `unlinked`, is a rewrite: ignored unless the device is linked, its scope is the linked one and its creator passes both the creator check below and the device gate's `LinkedDevice.accepts(creator:)`; then `unlinked: true` removes the phone exactly as Remove does (in `shared` scope it has already left the shares, so a missing participant is no error; a share failure is logged and swept by the next close, never failing the relay pass), and otherwise its `start_sessions` is mirrored into `start_sessions_allowed` (`setStartSessionsAllowed`, only when it differs, so `decided_at` moves only on a change). `typing_requested` is not stored. The creator must be the phone's own user: in `shared` scope `creatorUserRecordName == user_record_name` and that user has accepted both shares; in `private` scope the Mac's own user (`CKCurrentUserDefaultName` or the owner's name; unknown passes). A wrong creator gets no grant at all. Then the nonce decides (`HubSyncState.LinkDecision`): known, unused and `exp ≥ now` links (`linkDevice` marks the code used and upserts `devices` in one transaction, keeping the grants of a re-linking phone) and closes the link; the same nonce from the same device is a no-op; a nonce used by another device, expired or unknown is stored in `link_refusals` and published as `link_refused` (`used_code`, `expired_code`, `unknown_code`). A linked phone keeps its link whatever nonce it sends later, and a removed one is never re-linked by its old nonce. Names are clipped to 60 grapheme clusters.
- **`devices(device_id, name, scope, user_record_name, linked_at, typing_allowed, start_sessions_allowed, decided_at)`** in `hubstate.db` is the device gate's table. `remove(deviceID:)` deletes the row first (the gate refuses the phone at once; its grant leaves the zone at the next publish) and, in `shared` scope, removes that iCloud user from both shares unless another linked phone is on it; if that removal fails it sets `share_sweep_pending` (the next close sweeps the participant) and rethrows. The grant setters stamp `decided_at`. `SessionStartStopHandlers` reads the phone's grants through `MobileLinkCenter.sessionGrant` (`denied` when the row is missing or unreadable).
- **`DeviceGrantSlice`** publishes `device_grant-<device_id>` from the sidecar: linked phones (`linked: true`, their grants), then refusals for an hour (`decided_at` = the refusal's time, so a second identical refusal still changes the payload and the phone reads it as an answer); at most 20, latest first.
- **Device gate** (spec §5.2 rule 4) in `RelayProcessor`: an action (the `probe` included) or a recording upload is applied only when its `device_id` is in `devices` and `LinkedDevice.accepts(creator:)` holds (`shared`: the record's creator equals the phone's `user_record_name`; `private`: unknown, `CKCurrentUserDefaultName` or that name). Anything else is echoed `failed` / `device_not_linked` and never dispatched. The creator rides on `CloudRecord.creatorUserRecordName` (see Transport).
- **Take over**: `MobileHubService.onTakeOver` calls `takeOverReset()`, which deletes both shares, clears `link_codes`, `devices` and `link_refusals`, and sets `sharing` to `none`; the next QR creates new shares.
- Tests: `MobileLinkCenterTests` (fake share service, fake clock); the gate also in `RelayProcessorRecordingUploadTests`. Suites that drive actions through the relay link a test phone first (`HubSyncState.linkTestDevice`).

### Settings → Mobile on the Mac (A9)

- **Tab.** `SettingsTab.mobile` ("Mobile", between System and Profile). `MobileSettingsTab` builds `MobileSettingsViewModel` over `AppState` once; `MobileSettingsView` and `MobileLinkSheet` take their models directly, so ViewInspector drives them without an environment. `AppState` conforms to `MobileSettingsHost` (`isMobileSyncEnabled`, `mobileHub`, `mobileHubInitError`, `setMobileSyncEnabled(_:)`), in `AppState+MobileHub.swift`; tests use a fake host over a real hub and link center on fakes (`MobileSettingsFixture`).
- **Toggle.** "Sync with iPhone", off by default, drives the existing `AppState.setMobileSyncEnabled(_:)` (the hub is built on first use and kept); it applies at once, outside the Settings Save bar. Turning it off closes an open QR sheet and its link first (`closeLink(.sheetClosed)`). Without the iCloud entitlement (`CloudKitTransport.entitlementPresent()` false, an ad-hoc build) the tab shows "Needs a signed build" and the toggle cannot be turned on (`toggleDisabled = !entitlementPresent && !isOn`); an inherited on can still be turned off. The corp flavor (`HubIdentity.bundleFlavor()`, from `WTBuildFlavor`) shows "Work data from this Mac will be stored in your personal iCloud account." under it, whatever the toggle.
- **Hub status** (while on): `MobileSettingsViewModel.statusLine` maps `HubStatus` (Off, Starting…, On, "Unavailable: <reason>", "<mac_name> is your hub. Turn it off there, or Take over" with **Take over** → `MobileHubService.takeOver()`, "Another Mac took over" also with Take over). While running: last publish (`MobileHubService.lastPublishAt`) and the relay backlog. "iCloud is slowing sync down" shows once the transport has been throttled for 60 s (`HubTransport.throttledSince`, `CloudKitTransport.throttledSince`; read through `MobileHubService.throttledSince()`). The polled parts (account, last publish, backlog, throttling) refresh every 5 s while the tab is on screen.
- **iCloud account.** `MobileLinkCenter.accountAvailability()`: `.noAccount` shows "Mobile isn't available on this Mac: iCloud is off.", `.restricted` "Mobile isn't available on this Mac: iCloud is restricted by your organization." (the `MobileLinkError` sentences), and no QR button. **Use Watchtower on iPhone** shows only with a signed build, the toggle on, the hub `.running` and iCloud `.available`.
- **QR sheet** (`MobileLinkSheetViewModel`): `issueCode()` on appear, the QR (`LinkQRCode`, CoreImage, error correction M, rendered once per code) of `LinkPayload.url()`, "Expires in m:ss" and **New code**. At 0 the sheet closes the link (`closeLink(.expired)`; the center's own timer may have already) and offers **Show a new code**; a New code waits for that close, so it never lands on the new code's link. A phone that used the code shows "Linked <name>". Any dismissal (Done, Esc, leaving the tab) runs `closeLink(.sheetClosed)`; a code still being made when the sheet closes is closed as soon as it exists. An `issueCode()` refusal shows its sentence with **Try again**.
- **Phone list** (`MobileLinkCenter.devices`): name, "Same Apple ID" / "Shared", link date, "Typing allowed" / "Typing off". Every phone gets **Allow…** (a confirmation, then `setTypingAllowed(true)`) or **Revoke** (`setTypingAllowed(false)`), and **Remove**. There is no "the phone asked to type" prompt: the hub does not store the phone's `typing_requested`. Removing a same-Apple-ID phone says "Removed. It is signed into your Apple ID, so it can still read synced data until you sign it out of iCloud"; a shared phone "Removed <name>."; a Remove whose share removal failed says the phone is removed and the sharing is cleaned up at the next code.

### Workbench projections (B2)

- **Sources.** `AppState.buildMobileHub` registers `WorkbenchSlice`, `WorkbenchTargetSlice` and `WorkbenchCommentSlice` (`MobileHub/Slices/`). Each encodes a small `Payload` struct with `RelayCoder`, never a row; the tests pin every payload against the Kit fixture and scan its keys for the never-published columns (`folder_path`, `claude_session_id`, `agent_turn_end`, `agent_tool_run`).
- **Clipping.** `SliceClip.text(_:limit:)` cuts at a grapheme boundary, ends in `…` (counted toward the cap) and returns the flag as `true` or nil, so an unclipped field has no `<field>_clipped` key; `SliceClip.list(_:limit:)` returns the head and `more` (nil when nothing was cut). Caps count `Character`s. Every later slice reuses it.
- **`workbench`.** The ≤ 100 workbenches with the latest session activity (`WorkbenchSlice.publishedWorkbenches`, over `WorkbenchQueries.switcherSummaries`); the target and comment slices publish only these boards. `folder_display` is `WorkbenchBranchPresentation.displayPath` (the Mac's own: the home prefix becomes `~`, a path that merely starts with the same letters is not under home, anything else as-is), cut at 300. Workbenches order by parsed `last_session_activity`. `done_targets` counts done targets the archive view leaves unarchived. `targets_more` counts board targets outside the target window. `session_counts` counts the published `terminal_session` records per state (`TerminalSessionSlice.sessionCounts`; `working` counts working and running, `not_running` counts not started).
- **Git status.** `WorkbenchGitRefresher` runs `watchtower workbench git status --workbench N --json` (`WorkbenchCLI.gitStatus`, PROJ-10's git; the hub never runs git) for every published workbench, once every 120 s, and on `sessionStateChanged(workbenchID:)` at most once per 30 s. Each run is bounded (20 s). A failed, timed-out or `status_ok: false` run keeps the last value. A detached HEAD publishes `detached: true` and an empty branch. A changed value nudges the `workbench` kind. The refresher is a `HubCompanion`: `MobileHubService` starts it with the publisher and stops it with the hub, off the main actor. A stop ends the pass in flight: no workbench gets a CLI run after it, and the run in flight stores nothing and nudges nothing. Without a workbench CLI no refresher is built, and the branch stays "". The fast lane calls `sessionStateChanged` for the workbench of every session whose state changed. A stop mid-pass puts back the cadence state of every workbench the pass did not finish (the one in flight included), so a restart runs them at once and keeps their session-change requests.
- **Target window** (`WorkbenchTargetWindow`, one SQL read of `workbench_target_archive` for all boards; target, comment and workbench slices share it). Board targets only (`project_id IS NOT NULL`, PROJ-01). Per workbench it holds every non-archived target, ≤ 2000, newest `updated_at` first, plus archived targets whose last close is within 90 days, ≤ 500, newest close first. An archived target's last close is its subtree's newest close (a node's close is its newest status move, else `updated_at`), as the view decides the archive. A group is thus never older than its children, and on equal close times the larger subtree ranks first, so an archived child's `parent_id` names a published group. The archive verdict is the view's (PROJ-15, read only).
- **`workbench_target`.** Fields come from `WorkbenchQueries.board`: the tree (`parent_id`, nil for a root or an orphan, and `children_count`), `open_comments`, `unread_for_owner`. `open_asks` counts open asks on the target. `session_ids` holds `claude` sessions with this `target_id` or linked through `terminal_session_targets`, the most recently active first, ≤ 20 with `session_ids_more`. `last_status_at`/`_actor` come from the newest `target_status_history` row. `work_on_prompt` is `TerminalLaunch.workOnTargetPrompt` with the current skill name: the folder's install status lives on the main actor, so a folder still on the legacy skill name gets a prefill naming the current one.
- **`workbench_comment`.** Comments whose target (a reply naming only its parent counts toward its root's target) is published, the newest 200 per target. `read` means `read_at != ''`.
- **Cost.** Each tick evaluates the archive view once per slice, plus once per published workbench through `board()`. The view itself is computed over every board's targets (PROJ-15 v1 note), so the cost grows with workbenches × targets.
- **A deleted workbench** drops out of every source, so the next diff deletes its workbench, target and comment records (review focus 1).
- Tests: `WorkbenchSliceTests`, `WorkbenchTargetSliceTests`, `SliceClipTests`, plus `MobileHubServiceTests.testCompanionsRunOnlyWhileTheHubPublishes`.

### Sessions and the fast lane (B3)

- **`terminal_session`** (`TerminalSessionSlice`): the `claude` sessions of the published workbenches, every live one plus the newest 50 by `last_active_at` per workbench. Shell sessions and sessions of a workbench outside the 100 are not published.
- **States are the Mac's.** The slice reads `fetchAgentStates` and resolves it with `SessionAgentStatus.resolve` and `SessionSwitcherPresentation.state(of:)`, the center's and the switcher's own functions, against a copy of `TerminalCenter.liveIDs` and `startedAt` (`SessionLivenessBox`, written by the fast lane on the main actor). `SessionStatePresentation` renders the tone, glyph (`""` for none), ring and caption. The caption carries no age (the Mac's "Not running · 5m"), so a record does not change every minute. `open_asks`/`oldest_ask_id` come from the resolved state; `closed_asks` is `OwnerAskQueries.closedCounts`, the count behind the Mac's "▸ N closed". `state_at` is the trusted hook stamp, else a finished session's `finished_at`. `agent_error` is set only on a failed state.
- **Report fields.** `SessionReportSummaryRunner` runs `watchtower workbench session-report --workbench N --summary --json` every 60 s for each workbench with a live session, and on a session state change of a workbench at most once per 5 s. Each run is bounded at 20 s, runs off the main actor and never touches the relay processor. A failed, undecodable or hung run keeps the last values; the `report_*` keys are absent before the first good run. A changed summary nudges `terminal_session`. A workbench that leaves the published list is forgotten with its summaries and any pending request. It is a `HubCompanion`, and a stop mid-pass keeps the unfinished workbenches due, as with the git refresher.
- **Fast lane** (`FastLane`, main actor, a `HubCompanion`). It chains onto `SessionAgentStateCenter.onChange` and `onRead`: the closures `WorkbenchesViewModel` set (the PROJ-12 held-answer delivery) still run first, and a stop puts them back. A change nudges `terminal_session` and `workbench`, asks the git refresher and the summary runner to refresh the changed sessions' workbenches, and tells the session report runner (B6). GRDB `ValueObservation` over `owner_asks`, `terminal_sessions`, `project_comments` and `targets` nudges the kinds each table feeds. It sees only the Desktop's own writes; Go's writes arrive through the center's 1 s poll or the 10 s tick. The publisher's one loop does the coalescing (1 s window, ≥ 2 s between fast sends); there is no second send loop. A fast cycle that saved or deleted something then calls `HubTransport.sendNow()` (`CloudKitTransport.sendNow()`, the `resend()` path: `CKSyncEngine.sendChanges()` at once; a no-op while stopped, unlinked, paused for quota or inside a server-requested wait). The ≥ 2 s spacing bounds the call rate; the 10 s tick and an empty fast diff leave the timing to CKSyncEngine.
- Tests: `TerminalSessionSliceTests`, `FastLaneTests` (Needs approval within one window plus one send; a 30-session storm sends at most 30 times, ≥ 2 s apart, ending on the last DB state, review focus 5), `WorkbenchSliceTests.testAStopMidPassKeepsTheUnfinishedWorkbenchesDue`.

### Owner asks and ask alerts (B4)

- **`owner_ask`** (`OwnerAskSlice`): every open ask of a published workbench, plus its answered, delivered and withdrawn asks with `created_at` in the last 7 days, the newest 50 per workbench. Rows are read raw, not through Core's `OwnerAsk(row:)`, so an ask the Mac's card decoder refuses (a question with 1 or 5 options) is still published. `withdrawn_reason` is absent unless set. Caps: `title` 200, `summary`/`changes` 4000, `doc_path` 300 (`SliceClip`). `payload` is the stored JSON as an object (`JSONValue`); over 64 KiB serialized it is dropped with `payload_clipped: true`. `answer` (closed asks only) is the stored `OwnerAskAnswer` object, dropped over 64 KiB.
- **Snapshot.** `doc_snapshot` is sent on open review asks only. Up to 256 KiB of UTF-8 it is sent whole. Over that it is cut after the last newline before the cap, or at the cap's grapheme boundary when there is no newline. It then carries `doc_clipped: true` and `doc_bytes` (the full size). No `…` is added, because the phone anchors review comments on the text as shown.
- **`quick`** `{question_id, options: [{label, recommended}]}` is set only on a `question` ask whose payload was published and has exactly one question, `multi` false, 2–4 options and at least one recommended. Labels are trimmed the way the Mac's card decoder reads them.
- **`ask_alert`** (`AskAlertSlice`, `SliceKind.askAlert`, record `ask_alert-<ask id>`): the push trigger (design §7). Payload `{ask_id, workbench_id, workbench_name ≤ 60, session_id?, kind, title ≤ 120, quick}`, cut with `…` and no `_clipped` flags. An open ask with `created_at ≥ enabled_at` (`HubIdentity.ensureEnabledAt`) is remembered once in the sidecar's `alerted_asks(ask_id, at, generation)`. Its record is published while the ask is open, in the sync generation that wrote it, for up to 7 days after `at`. So a rebuilt hub or a full republish finds nothing new, and after an account reset (`wipeSyncState` keeps `alerted_asks` and bumps the generation) the new zone gets no alert for an old ask. A remembered row older than 7 days is forgotten once its ask is no longer open. While the ask stays open its row is kept, so it never alerts twice.
- **Fast lane.** A write to `owner_asks` also nudges `ask_alert`.
- Tests: `OwnerAskSliceTests`, `AskAlertSliceTests`, `FastLaneTests.testTheDesktopsOwnTableWritesNudgeTheirKinds`.

### Session reports and timelines (B6)

- **Window.** Both slices cover the `terminal_session` window's sessions that are live or had `last_active_at` in the last 7 days (`SessionReportSlice.window`). A session that leaves it loses both records.
- **`session_report`** (`SessionReportSlice`, record `session_report-<session id>`). `SessionReportRunner` (a `HubCompanion`, off the main actor like the summary runner) runs `watchtower workbench session-report --workbench N --session S --json` — `SessionReportCenter`'s argv — so PROJ-14 holds through the CLI's own scoping. Runs with `--no-network` (appended): every 120 s while the session is live, once when it has no stored report, and on a resolved state change no sooner than 5 s after its last run. Without `--no-network`: on the phone's `session_report_request`, at most once per 60 s per session (requests run first in a pass). Each run is bounded at 30 s (the CLI process is terminated on the cancel); a failed, undecodable or hung run keeps the stored report.
- **Caps.** `on_you` 30, `now` 20, `next` 20, `phases` 30 with ≤ 50 items, `prs` 10, each with `<list>_more` (`items_more` per phase); free texts 500 (no per-text `_clipped`, as the Kit mirror). Over 128 KiB the hub drops phase items oldest phase first (by `started_at`, a not-yet-started phase counting as the newest; a phase's last items first), then whole phases (`phases_more`), and sets `phases_clipped`.
- **Stored payloads.** The capped payload is kept in the sidecar's `session_reports` (`hubstate.db`), so a restart republishes the last good report instead of deleting the record until the next run. The record changes only when the payload bytes change; a stored change nudges `session_report` and `session_timeline`.
- **`session_timeline`** (`SessionTimelineSlice`, record `session_timeline-<session id>`). Newest first, ≤ 100 (`milestones_more`), `text` ≤ 200 with `text_clipped`. Sources: `state` — the hub-observed transitions in the sidecar's `session_milestones` (only `state` rows, a CHECK; ≤ 100 per session, pruned after 14 days); `ask_opened`/`ask_answered`/`ask_withdrawn` from the session's `owner_asks` (a withdrawal has no stamp of its own: the superseding ask's `created_at`, else the ask's); `target_linked` from `terminal_session_targets.first_at`; `target_status` from `target_status_history` of the linked targets and the session's own target, from the session's `created_at` on; `phase` (`started_at`, `finished_at`) and `pr` (`merged_at`, else `checked_at`; branch entries skipped) from the stored report; `finished` from `finished_at` and `finish_summary`. A session with none of them has an empty list. No subagent events (OD-3), never transcript or terminal text (I-4).
- **State milestones.** The fast lane tells the runner of every state change and of a liveness change seen on an unchanged read (`sessionStatesChanged`, the same chain on `SessionAgentStateCenter`; no second observation loop). The next pass resolves the window's states as `terminal_session` does and stores a milestone when the text differs from the session's last one: "Started", "Working", "Waiting for you", "Needs approval", "Stopped", "Finished", "Error: …" (never-started sessions have none). A transition is stamped with the time the lane reported it, a first sighting (or a hub start) with the state's own time. A hub start resolves once. The pending-change stamp is taken before the window read, so a change reported while the read is out is resolved by the next pass. The Desktop's own `owner_asks` and `targets` writes also nudge `session_timeline` through the fast lane's table observation.
- **`session_report_request`** (`SessionReportRequestHandler`, `MobileHub/Handlers/`, registered only when the CLI exists). Entity: the session id, `{}`. A session outside the report window (not a `claude` session of a published workbench, or neither live nor active in 7 days) → `not_found`, since no report would reach the phone; else `applied` `{}` at once — idempotent, a second request inside 60 s runs nothing more. The new report reaches the phone through the slice. Bounded at 10 s (one read).
- Tests: `SessionReportSliceTests`, `SessionTimelineSliceTests`; `FastLaneTests`, `TerminalSessionSliceTests` and the PROJ-14 guards stay unchanged.

### Ask answers from the phone, hub half (B8, B9)

- **Handler.** `AskAnswerHandler` (`MobileHub/Handlers/`, main actor) is registered on the dispatcher for `ask_answer` in `AppState.buildMobileHub`. Entity: the ask id. Params: `{workbench_id, answer: {verdict, answers, checklist, comments, note}}`, decoded into Core's `OwnerAskAnswer`. It loads the ask with `OwnerAskQueries.ask(id:projectID:)`. An ask that is missing or belongs to another workbench fails `not_found`, checked before the answer is decoded. A read error throws and is echoed `write_failed`, never treated as "not found". An ask that is no longer open fails `ask_not_open` before anything runs. Otherwise the handler calls `OwnerAsksViewModel.answer(_:with:)`, the Desktop's structured entry. That entry validates, does the guarded write, then delivers, holds and shows notices as a Desktop answer does (PROJ-12 unchanged), and discards a Desktop draft on success.
- **Echoes.** `.stored(d)` → `applied` with `result.delivery` ∈ `submitted|typed|held|queued|copied|no_session`. `.notOpen` → `ask_not_open` (an ask superseded or answered meanwhile). `.invalid` → `invalid_answer`, with Go's message: an unknown label, a review without a verdict, a blank comment, or an answer the decoder refuses (an unknown verdict or check state). `.failed` → `write_failed`. `.busy` (the owner's own Desktop answer is being saved at that moment) → `conflict`. Missing or mistyped params → `invalid_params`.
- **Exactly once.** `ask_answer` is idempotent, so the relay ledger does not claim it. A record is re-run when its echo never landed: the echo's save failed (a transient CloudKit or network error, so the record stays pending and is not `done`), or the hub stopped between the store and the echo. Right after a store, before the echo, the handler keeps the wire `delivery` in the sidecar's `ask_answer_deliveries(record_name, delivery, at)` (pruned with the ledger). A re-run finds the ask `answered` (or `delivered`) holding this very answer (`OwnerAskAnswer.normalized(for:)` equals the stored one). It is then `applied` again with the kept delivery, with no second write and no second line. If the hub stopped before the delivery was kept, the echo is `applied` with `result` empty. Any other ask that is not open fails `ask_not_open`.
- **Timeout.** The handler races its work against `defaultTimeout` (30 s). The work runs in its own task. If the timer wins, the echo is `outcome_unknown` and the answer keeps running to its end, never cut mid-write or mid-delivery. The handler never calls back into the relay processor.
- **Anchor fixture.** `WatchtowerKit/Tests/Fixtures/asks/anchor-fixtures.json` is shared with the phone's `CommentAnchorBuilder`. Each case has a snapshot's markdown, the text Core renders it to (headings with UTF-16 offsets), a UTF-16 selection, and the anchor `CommentAnchor` makes of it (`quote`, `prefix`, `suffix`, `heading`). The cases are a selection at the document start, one at the end, one spanning a heading (with a non-BMP emoji earlier, so UTF-16 offsets differ from characters), and one in a clipped snapshot's last shown line. The end case has a ZWJ family emoji and a combining accent inside its 64-character prefix, so a port that counts scalars or UTF-16 units instead of characters fails it. `CommentAnchorFixtures` in `Tests/Support` loads the file. `OwnerAskSliceTests` checks that the clipped case is what `OwnerAskSlice.clipSnapshot` leaves at the end of a snapshot over 256 KiB, and that the same anchor results.
- `AskAnswerHandlerTests` also sends Go's `internal/asks/testdata/answers` files (`valid_question`, `valid_review_changes`, `invalid_review_no_verdict`) through the handler, so Go, the Kit and the hub share one wire shape.

### Board writes from the phone, hub half (B12)

- **Shared writer.** Core's `WorkbenchOwnerWrites` holds the board's owner writes: `setStatus` (claims the owner, PROJ-06, and returns the parents the PROJ-05 rollup moved), `setPriority`, `addComment` and `reply` (a reply to a resolved or outdated root reopens it). Each runs inside the caller's write transaction and returns a `WorkbenchOwnerWrite` (`target`, `rolledUp`, `touched`); the comment writes also return the new comment id. `WorkbenchBoardViewModel` calls it for the same four edits, keeping its own guards and its `write` hook.
- **Handlers.** `BoardHandlers` (`MobileHub/Handlers/`, main actor) registers `board_target_status`, `board_target_priority`, `board_comment_add`, `board_comment_reply` and `board_target_create` in `AppState.buildMobileHub`. - **Status and priority.** The value must be one of `WorkbenchBoardCard.editableStatuses` / `editablePriorities`, else `invalid_params`. Otherwise a `from_*` that differs from the current value → `failed` / `conflict` with `result.current`. `result` on `applied`: `{status}` / `{priority}`.

A CLI failure → `write_failed`; an unreadable success output → `outcome_unknown`; no CLI on the Mac → `write_failed`. Parents whose status the new child re-rolled are reported with it. `result`: `{target_id}`.
- **Exactly once and timeout.** The relay claims the comment and create kinds `begun` before they run, so a crash between `begun` and the insert is echoed `outcome_unknown` and never applied again. Status and priority are idempotent and simply re-run. Each handler races its work against 30 s (`withHandlerTimeout`, shared with `AskAnswerHandler`); a timeout is `outcome_unknown`, the work keeps running to its end.

### Session start and stop from the phone, hub half (B14, B15)

- **Handlers.** `SessionStartStopHandlers` (`MobileHub/Handlers/`, main actor) registers `session_start` and `session_stop` in `AppState.buildMobileHub`. It holds `WorkbenchesViewModel` weakly (none → `write_failed` "The workbench is reloading on the Mac") and the app's `TerminalCenter`.
- **Start.** Entity: the target id. Params `{workbench_id, mode: new|open_existing, plan_first, bring_forward, brief?}`; a missing flag or an unknown mode is `invalid_params`. Order: the device grant (`start_sessions_allowed` false → `device_not_allowed`), then the board scope (workbench or target gone → `not_found`; a target of another workbench or of no board → `not_on_board`), then `WorkbenchesViewModel.startForTarget` — Work on it's read, reuse rule (`open_existing`) and launch path. The brief is `TerminalLaunch.workOnTargetPrompt`, or the phone's `brief` only when the device has `typing_allowed` (otherwise ignored); `plan_first` appends `TerminalLaunch.planFirstSuffix`. The brief rides `$WATCHTOWER_FIRST_PROMPT` as on the Desktop, so one starting with "-" is never read as a flag. Both apply to a new session only: an `open_existing` that finds the target's session resumes it and echoes its id — the Kit has no result key saying it was reused.
- **Placement.** `bring_forward` false → `.background` (nothing on the owner's screen moves). True → `AppState.bringWorkbenchForward` first (Workbench destination, the workbench drilled into, the app activated, the main window brought front or opened), then `.keeping(.board)`, as Work on it.
- **Outcome.** `applied` with `{session_id, stage: "starting"}` once the process runs. A new launch is watched for 3 s (100 ms steps): an exit 127 (`exec claude` found no Claude Code on the login shell's PATH) → `claude_not_found` with `TerminalLaunch.exitMessage(127)`; any other early exit is the session's own end and stays `applied`. A session already live before the start is not watched. `TargetStartError.notOnBoard` → `not_on_board`; `.inProgress` (a start for the target already running, here or a Work on it) → `conflict`; `.failed` (a db error, no terminal, a refused launch) → `write_failed`, never a success.
- **Exactly once.** The relay echoes `received` on dequeue, claims the record `begun` before the handler, and expires it 24 h after `created_at`; a record found `begun` after a restart is `outcome_unknown` and never starts a second session. There is no retry of a `new` start.
- **Stop.** Entity: the session id, `{}`. Idempotent. A session that is not a `claude` session of a workbench (unknown, standalone, shell) → `not_found`. A live one gets `TerminalCenter.close(sessionID:)` (SIGHUP, SIGKILL after the grace); one that is not live is `applied` with no signal. The row and its transcript stay.
- **Device grants (until A8).** The grants come from an injected `deviceGrant(device_id)` seam (`SessionStartStopHandlers.DeviceGrant`); AppState answers the spec defaults for every device (`typing_allowed` false, `start_sessions_allowed` true) until A8 reads the per-device grants.

### Calendar events (C2)

- **`calendar_event`** (`CalendarEventSlice`, record `calendar_event-<calendar_events.id>`), registered in `AppState.buildMobileHub`. Rows are read by an explicit column list; `raw_json` is never selected, and attendees keep `email`, `display_name` and `response_status` only.
- **Window.** Events overlapping local today 00:00 − 1 day … now + 14 days, as `CalendarQueries.fetchEvents` overlaps (start ≤ end of window, end ≥ start of window), so an event from 23:30 the evening before runs into the first day and is published. Both bounds are calendar steps in the Mac's injected `Calendar`: the start stays on local midnight across a DST change, and the end is 14 calendar days after now (not 14 × 86 400 s, so it moves by an hour when a DST change falls inside the window). An all-day event is stored as UTC midnight; the hub places it by that calendar day read as local midnight (end exclusive, the Kit mirror's `localStart(in:)` rule), so it neither leaks into the window nor drops out of it a day early west or east of UTC. `cancelled` events are left out. At most 500, earliest first.
- **Dedup.** Same non-empty `ical_uid` and same `start_time` → one record: the copy with a `conference_url`, else the lowest id. A cancelled copy never takes part. Prep and linked targets are read across every copy, so a transcript recorded against the dropped copy still links.
- **Fields.** Times travel as the stored ISO8601 strings. `title`/`location` 300, `description` plain text (Core's `CalendarEvent.stripHTML`) 2000, `attendees` ≤ 100, all with `SliceClip` (`_clipped`, `_more`). `prep_bullets`: `meeting_prep_cache.result_json` `talking_points[].text`, then `suggested_prep[]`, blanks dropped, first 8, each ≤ 300; `prep_generated_at` only when a readable prep exists (an empty `result_json` is no prep; an unreadable one is left out). A readable prep with no usable bullets still sets `prep_generated_at`, so "No prep yet" keys on empty bullets. `linked_targets` `{id, text ≤ 200, status}` ≤ 20: the `converted_target_id`s of the event's transcripts' chapter action items, oldest transcript first, joined to `targets` with `project_id IS NULL` (PROJ-01), so a board target or a deleted one drops out.
- **Unreadable sources.** Attendees `null` (Go's nil slice, an event without guests) or `""` are an empty list. A prep, attendee list or `chapters_json` that fails to decode is left out and logged once per row and content (with the decoding error), not on every tick; a changed value warns again.
- **Wire shape.** The Kit pins its `calendar_event` literal inline in `CalendarMirrorFixtureTests`; `CalendarEventSliceTests` reads that literal from the Kit test file and checks the hub payload's keys and literal types against it.
- Tests: `CalendarEventSliceTests` (window edges, Europe/Kyiv DST day, all-day west and east of UTC, over midnight, dedup, caps, prep, PROJ-01, HTML description, no `raw_json`).

### Phone recordings, hub half (C3, C4)

- **Ingest** (`RelayProcessor`, spec §5.3, §6.4). A `recording_upload` still `pending` goes through the device gate first: no `device_id`, or one `RecordingUploads.isDeviceLinked` refuses, is `failed` (`device_not_linked`) with nothing written. Until A8 reads the linked devices, `AppState` keeps the default gate (any non-empty `device_id`). Then the record is claimed `begun` (`HubSyncState.claimRelayRetryingFailure`) and its asset checked (missing or empty → `failed`, ledger `not_found`). `PhoneRecordingJobs.ingest` drops an `event_id` whose `calendar_events` row is gone (review focus 4: the transcript is saved ad-hoc, never failed) and calls `MeetingRecorderCenter.ingestPhoneRecording`, which writes `rec_<ts>.m4a` + `.meta` into the recordings directory and enqueues the job. A throw (an unwritable directory, a full disk) is `failed` / `write_failed`, and the transcriber's ingest leaves no partial `.m4a` or `.meta` (review focus 3). The ingest runs under `withHandlerTimeout` (300 s, `recordingIngestTimeout`); a timeout is `failed` / `outcome_unknown`.
- **Echo.** The hub rewrites the same record `received` (or `failed` with a phone-facing `error_message`) with **no asset**, which frees the iCloud storage; the phone deletes its file only on `received`. The wire payload has no reason field, so the reason code lives in the ledger outcome (`received`, `failed:<reason>`). After `received` the transport's copy of the asset is removed (best-effort, logged).
- **Exactly once.** A `received` record is `done` for good: a duplicate delivery ingests nothing. A failed attempt wrote nothing, so the phone's Retry (same record name, `pending` again) is claimed again and ingested; `claimRelayRetryingFailure` takes over only a `done` row whose outcome starts with `failed`. An upload found `begun` at the next pass (the hub stopped mid-ingest) is echoed `failed` / `outcome_unknown` and not re-ingested by the hub; the owner's Retry ingests it, and if the first copy had landed that is the accepted duplicate (spec §9).
- **`recording_job`** (`RecordingJobSlice`, record `recording_job-<upload id>`, a fast-lane kind). `PhoneRecordingJobs` (main actor, a hub companion) remembers each ingested upload in the sidecar's `phone_recordings(upload_id, audio_path, transcript_id, status, percent, error, updated_at)`: `queued` once the ingest returns (in the same main-actor turn, so the job's first callback finds it), then from the transcriber's `onJobPhase`/`onJobFinished` (chained on `start()`, restored on `stop()`): `transcribing` with `percent` = done × 100 / total (0 for the first 0-of-0 report), `diarizing`, `summarizing`, `failed` with `error`, `queued` again when the owner retries a failed job on the Mac, and `done` with `transcript_id`. A phase after `done`, and the Mac's own recordings, are ignored; an unchanged state writes nothing. Each change nudges the publisher (`recording_job`, plus `meeting_transcript` once a transcript is linked). A rebuilt hub reloads the remembered jobs, so it keeps following them.
- **Window.** A job is published until 7 days after it ended (`done`/`failed`; exactly 7 days is kept); an unfinished one stays. At most 100, latest `updated_at` first. Payload `{id, status, percent?, transcript_id?, error?, updated_at}`; `error` is cut at 300 with `…` (the Kit mirror has no `_clipped` flag). Sidecar rows are forgotten 31 days after their last update, past the `meeting_transcript` window, because they carry its `phone_recording_id`.
- **Known gaps (ledgered).** A job that was queued or running when the app quit is not re-enqueued (the transcriber offers it in its recovered list) and its record stays at its last state until the owner transcribes it on the Mac; phases that happen while the hub is off are not seen. `received` is never published by this hub (the job is `queued` once the ingest returns).

### Meeting transcripts (C5)

- **`meeting_transcript`** (`MeetingTranscriptSlice`, record `meeting_transcript-<meeting_transcripts.id>`), registered in `AppState.buildMobileHub`. An explicit column list: `audio_path`, `speakers_json` (voice embeddings) and `notes_md` are never selected, and of `chapters_json` only `overall_summary` is read (published as `overview`, 2000).
- **Window.** Created in the last 30 days, or its event is in the calendar window (`CalendarEventSlice.windowEventIDs`, every copy of a de-duplicated event); at most 200, newest first. `title` 300.
- **Recap.** `meeting_recaps` by `transcript_id` first, then by the transcript's `event_id` (the Recap tab's precedence, `MeetingRecapQueries.fetchForRecording`), so a recap whose event aged out or was deleted is still found; otherwise the transcript's own `summary_json` (ad-hoc recordings). An unreadable recap is logged and the next source is tried. `summary`, `key_decisions[]`, `action_items[]`, `open_questions[]`, each list ≤ 50 entries of ≤ 500 (`_more`). `speakers[]`: the labels of the non-deleted segments in order of first appearance, `""` (not diarized) left out, ≤ 20.
- **`phone_recording_id`** comes from the closure `MeetingTranscriptSlice(phoneRecordingID:)`, wired in `AppState.buildMobileHub` to `PhoneRecordingJobs.uploadID(forTranscript:)` (the sidecar's `phone_recordings.transcript_id`, see C4). A Mac recording has no entry (key absent); a job that finishes nudges `meeting_transcript` on the fast lane.
- **Segments asset.** The body rides as the record's CKAsset `segments.json`, `[{start_sec, end_sec, speaker, text}]` of the non-deleted segments (RelayCoder JSON). A legacy row (no or unreadable `segments_json`) is one segment `0 … duration_sec` holding `transcript_text`, speaker `""`; an empty text is `[]`. Over 20 MB (20 × 1024 × 1024 bytes) the array is cut after the last whole segment that fits and the payload carries `segments_clipped: true`.
- **Asset-backed records in the publisher.** A source conforming to `AssetSliceSource` returns, from inside the read, a build that yields `AssetSliceRecord`s (record + `SliceAsset`: file name, SHA-256 digest, and the data unless the staged file already holds that digest). The publisher stages each changed record's file in `SliceAssetStore` (`MobileHub/SliceAssets/<recordName>/segments.json`, `MobileHubStorage.sliceAssets`), written atomically in place, and saves the record with `assetFileURL` pointing at it — the transport's pending save reads that file until it is sent. The hash is `SliceDiff.recordHash`: SHA-256 of the payload plus the asset's SHA-256, so a speaker rename or a deleted segment republishes even when the payload is the same. A record whose staged file is missing or holds another digest is sent again whatever its hash; the store remembers each staged file's digest (a file left by an earlier run is hashed once). The store's lock is an `NSLock` (its critical sections span disk I/O); a sweep logs a listing error other than a missing directory. Files are removed when the record leaves the zone (and swept each cycle), on an account reset (`removeStagedAssets`), and when the Settings toggle turns the hub off (`MobileHubService.disable` → `closeStagedAssets`: the store refuses new files until the publisher's next `start()`); a record that cannot be staged is skipped unhashed and retried. Without a store (stub storage) asset-backed records are skipped, never published without their asset.
- **Cost.** Two phases. Inside the publisher's read the slice reads the window, the chosen recaps and each row's raw columns (`transcript_text` only when `segments_json` is NULL or not valid JSON) and fingerprints them: SHA-256 over the raw columns, the chosen recap's `id`/`updated_at` and the phone recording id. A row whose fingerprint is cached and whose staged file still holds its asset reuses the cached payload and digest. Every other row is decoded, encoded and hashed in the build the publisher runs after the read ended. An unchanged tick builds no asset (`assetBuilds`, pinned by a test); a fresh launch builds each once.
- **Wire shape.** The Kit pins `meeting_transcript` and `segments.json` inline in `CalendarMirrorFixtureTests`; `MeetingTranscriptSliceTests` reads both literals (`SliceJSON.kitInlineFixture`) and checks keys and literal types.
- Tests: `MeetingTranscriptSliceTests` (fixture shapes, recap join and precedence, ad-hoc `summary_json`, legacy and unreadable segments, deleted segments, the 20 MB clip and its boundary, hidden columns, the 200 cap and the 30-day/event window, speaker rename through the publisher); `SlicePublisherTests` (staging, asset-only change, file removal, missing file, closed store, no store); `MobileHubServiceTests` (account reset and disable remove the files).

## Kit (WatchtowerSync + WatchtowerKit)

### Kit package and wire rules (A3)

- **Port.** The sync core of the old `mobile-app` branch, re-homed as `WatchtowerSync`, with the chat seam removed. `SliceKind` keeps the branch's kinds and adds `heartbeat` and `device_grant` (later tasks add the workbench, calendar and recording kinds); `RelayRecordKind` is `action`, `heartbeat` (wire compatibility only), `recording_upload` and `device`; an unknown kind is logged once and ignored.
- **Tolerant decoding.** An unknown `ActionStatus` decodes as `pending`, an unknown `ActionReason` as nil, an unknown `RecordingUploadStatus` as `pending`, and enum-like slice fields are `OpenWireValue`s, so a record from a newer Mac never fails as a whole. `RelayCoder` is the one wire coder: snake_case keys, Unix-second dates, sorted keys, a nil optional is an absent key.
- **Payloads.** `ActionRequestPayload` gains `device_id`, `reason` and `result`; `HeartbeatPayload` (DataZone, §4.1) and `DevicePayload` (RelayZone, `device-<device_id>`) carry the hub's and the phone's identity. `CloudRecordFactory` writes the heartbeat to DataZone, so a RelayZone copy (writable by a share participant) is never trusted.
- Tests: `RelayPayloadTests`, `ActionStatusTests`, `SliceKindTests`, `CloudRecordFactoryTests`, `KitFixtureTests`.

### Transport: scopes, errors and the local buffer (A4, C8)

- **`CloudKitTransport`** is the `CKSyncEngine` adapter behind `CloudSyncTransport`. Engine events land in `TransportStore` (GRDB: an incoming event buffer whose local seqs are the consumers' change tokens, a pending-send queue, archived system fields, the engine state). `InMemoryCloudTransport` is the test and demo fake.
- **Scopes** (`CloudDatabaseScope`, spec §2.3). `private` — the hub, and a phone on the Mac's Apple ID — creates and deletes zones. `shared(ownerName:)` — a phone on another Apple ID — reaches the Mac's zones through accepted shares and never writes zones; another owner's zone is never ours. A store records its scope, and opening it under a different scope wipes it first.
- **Errors** (spec §9). `.limitExceeded` halves the batch (once per failure, even when it arrives both thrown and per record); a record rejected alone, or whose asset file is gone, is dropped from the queue and reported to the owner. `.requestRateLimited` / `.zoneBusy` wait out `Retry-After` (the transport keeps the start of a throttling stretch, for a "slowing down" notice after 60 s). `.quotaExceeded` pauses sends until `resume()` (`TransportEvent.quotaExceeded`). An expired change token re-fetches once. In `shared` scope a vanished zone (`.zoneNotFound`, `.userDeletedZone`, a zone-deleted event) emits `TransportEvent.unlinked`, terminal for that transport. An account sign-out or switch wipes the store and relaunches the engine (`setAccountResetHandler`); in `private` scope a server-deleted DataZone also fires the reset handler once.
- **Pulls** are single-flight: a `pull()` arriving meanwhile joins the running one, and fetch errors delivered while it awaits the engine are parked and handled once. `stop()` cancels and drops the engine; saves made meanwhile wait in the store.
- **Creator.** `CloudRecord.creatorUserRecordName` is a fetched record's `creatorUserRecordID.recordName` (the owner's own records read `CKCurrentUserDefaultName`), kept in the buffer's `events.creator` column. It is never sent on a save; nil for a record this device built, in `InMemoryCloudTransport` unless a test sets it, and for an event buffered before the column existed. The hub's device gate reads it.
- **Assets.** `CloudRecord.assetFileURL` rides as a `CKAsset`: a phone `recording_upload` in RelayZone, or an asset-backed slice record (a meeting transcript's `segments.json`) in DataZone. A rewrite with nil removes the asset. Fetched asset files are copied into the store's stash (named after the record, so a re-fetch overwrites), because CloudKit's own files are temporary.
- **Buffer retention.** `CompactingTransport.compactEvents(in:keepSince:)` drops events at or below a consumer's token: the phone's `ReplicaHydrator` compacts `.data` and its `RelayFeed` compacts `.relay` after each persisted token (best-effort, logged). Data-zone compaction also deletes the stash files of the compacted events, except a path a newer event still references, so a consumer copies an asset before it compacts past it. The hub never compacts `.relay`: its daily hygiene needs the full-zone scan, so it sweeps by age (`SweepingTransport.sweepEvents`, older than the cutoff **and** at or below the consumer token). Stash files no buffered event and no pending row references are swept at open, after a zone eviction and after a wipe.
- Tests: `CloudKitTransportErrorTests`, `CloudKitTransportScopeTests`, `CloudKitTransportResetTests`, `CloudKitTransportStopTests`, `CloudKitTransportMappingTests`, `TransportStoreTests`, `TransportAssetTests`, `InMemoryCloudTransportTests`.

### Replica, outbox and relay feed (A3, A11)

- **`ReplicaStore`** is the phone's mirror of DataZone: `slice_records` (opaque payloads, decoded on read, so a corrupt one is skipped and counted, never fails a batch), `replica_meta` (the data and relay tokens, the alert watermark), the `pending_actions` overlay, the `phone_recordings` ledger with `phone_recording_marks`, and `slice_assets` (a record's asset bytes, or the reason it was unreadable; files over 20 MB are refused unread). `apply` takes one data-zone batch in one transaction and refuses a token older than the stored one; asset files are read before the write transaction. `resetSyncTokens()` is SPI (`@_spi(DemoTransport)`) for the demo transport only. The UI reads it through GRDB `ValueObservation` (`*(from: db)` variants for tracking closures).
- **`ReplicaHydrator`** pulls DataZone into the replica: one cycle at a time (a caller arriving mid-cycle awaits it), `onRecordsApplied` for the records of known kinds a batch persisted.
- **`ActionOutbox`** is the phone's action producer: transport save first, then a `pending` overlay row (no phantom chip on a failed save). It refuses while no device id is set (`ActionOutboxError.notLinked`; a blank id counts as none). `applyEcho`: `received`/`held` mark the row (`echo_status`), `failed`/`expired`/`cancelled` flip it to failed with the echo's `reason` and `result`, `applied` removes it and tells the applied observer (once per removed row). `sweepSilentPending` fails rows the Mac never echoed within 24 h.
- **`RelayFeed`** is the phone's single relay consumer: it owns the relay token and routes `action` echoes to the outbox and `recording_upload` echoes to the uploader; a RelayZone `heartbeat` and `device` record are ignored. The token is persisted at batch end, so a throw replays the batch (routing is idempotent), and an undecodable payload is logged and left behind. The Mac reads as online while the DataZone heartbeat is under 720 s old (`heartbeatStaleAfter`).
- Tests: `ReplicaTests`, `ReplicaResetTests`, `ReplicaSliceAssetTests`, `ActionOutboxTests`, `RelayFeedTests`, `RelayFeedRecordingUploadTests`.

### Link code and device grant (A5)

- **`LinkPayload`** is the QR code (spec §2.3): `watchtower://link?d=<base64url(JSON)>`, unpadded canonical base64url, sorted keys; fields `v`, `container`, `hub_id`, `mac_name` (≤ 60), `owner_user`, a single-use 32-byte `nonce`, `iat`, `exp = iat + 600`, and the two share URLs (absent when none). `v` is checked first, so a newer code reads as "Update Watchtower on this iPhone"; a code for another container is refused. The codec only encodes and decodes: the expiry and nonce checks belong to the hub (A8, see Linking, hub half) and the phone's link flow (A12, [phone half](#onboarding-and-linking-phone-half-a12)).
- **`DeviceGrant`** is the hub's `device_grant-<device_id>` slice: the phone's name, `link_refused` (`used_code`, `expired_code`, `unknown_code`, or an unknown value, still a refusal), `typing_allowed` (default false) and `start_sessions_allowed` (default true).
- Tests: `LinkPayloadTests`.

### Workbench slice mirrors and action params (B1)

- **Kinds.** `SliceKind` gains `workbench`, `workbench_target`, `workbench_comment`, `terminal_session`, `owner_ask`, `session_report` and `session_timeline` (design §4.2–§4.9), and `ask_alert` (§4.7; the hub's B4 publishes it, its Kit mirror comes with A13). The phone decodes each record's payload with its `SliceMirror` in `WatchtowerKit/Models` (`Workbench`, `WorkbenchTarget`, `WorkbenchComment`, `TerminalSessionState`, `OwnerAsk`, `SessionReport`, `SessionTimeline`) through `RelayCoder` — snake_case keys, Unix-second dates, a nil optional is an absent key, unknown keys are ignored.
- **Enum-like fields** (state kind and tone, target status and priority, ask kind/status/withdrawn reason, verdict, check state, milestone kind, start mode) are `OpenWireValue`s: a value from a newer Mac decodes, keeps its raw string and reads `isKnown == false`.
- **Clipping on the wire.** `<field>_clipped` and `<list>_more` are absent unless the hub cut something, so the mirrors keep them optional (`Bool?`, `Int?`).
- **`session_report`** is the CLI's report as Go writes it (`internal/sessionreport.Report`): datetimes stay Go's UTC strings and every key may be absent, as in Core's `SessionReport`; the hub adds only `<list>_more`, `items_more` and `phases_clipped`. The other kinds carry dates as `Date`.
- **`session_timeline`** payload is `{session_id?, milestones, milestones_more?}`: `session_id` repeats the record id and may be absent. An ask's `withdrawn_reason` is absent (or `""`, read as nil) unless the ask is withdrawn.
- **`OwnerAskAnswer`** (Kit) encodes byte for byte like Core's and Go's (`internal/asks/testdata/answers`); an ask's `payload` resolves missing question and check item ids to their 1-based position, as Core and Go do.
- **Action params.** `ActionKind` gains the twelve §5.2 kinds. Each has a typed `ActionParams` struct whose `wireParams()` is the request's `params` object. Because `ask_answer` carries an object and `session_start` carries bools, `JSONValue` (WatchtowerSync) gains `.bool`, `.array` and `.object`; a row never produces them, and `databaseValue` stores them as 0/1 and JSON text.
- **Fixtures.** `WatchtowerKit/Tests/Fixtures/workbench/*.json` are the frozen payloads (`WorkbenchMirrorFixtureTests`); the hub's projection tests pin their encoder against the same files.

### Calendar and recording mirrors (C1)

- **`calendar_event`**, **`meeting_transcript`** and **`recording_job`** mirrors (`WatchtowerKit/Models`), RelayCoder JSON. Times stay the stored ISO8601 strings for the calendar and transcript kinds; `CalendarEvent.localStart(in:)` places an all-day event (stored as UTC midnight) on its local day. The transcript body is not in the payload: it is the record's `segments.json` asset (`TranscriptSegment`). An unknown `RecordingJob` status decodes as `queued`.
- **`RecordingUploadPayload`** gains `event_id` (absent for a voice note) and `device_id` (spec §5.3).
- **Wire shape.** `CalendarMirrorFixtureTests` pins the literals inline; the hub's slice tests read the same literals from that file.

## Phone app

### App shell (A11)

- **Boot.** `WatchtowerMobileApp` builds one `AppRoot` for the app's lifetime, which owns the current `AppEnvironment` and the link flow (A12) (or shows `BootFailureView` when the replica cannot open; a signed build without its app group container refuses to boot rather than keep the replica elsewhere). The replica lives in the app group `group.com.aiwatchtowers.watchtower.mobile`, so the notification extensions can read it.
- **Transport switch.** A build that carries the iCloud entitlement (signed device or TestFlight) runs `CloudKitTransport` and starts empty; anything else (unsigned simulator and CI builds) runs `InMemoryCloudTransport` with `DemoSeed`, DEBUG only. The demo pushes records through the transport as the hub would publish them, so hydration and every decode path run end to end; record names are fixed, so a re-seed upserts.
- **Fetch loop.** One loop: each cycle hydrates DataZone, then polls RelayZone. 5 s while Now or Workbench is on screen, 30 s otherwise; paused in the background (the recorder's audio background mode does not keep it running) and resumed with an immediate fetch. A silent push (`content-available`) triggers a fetch. At boot, after the first fetch: the 24 h silent-pending sweep, launch recovery of cut-short captures, then the upload relaunch retry.
- **Tabs.** Now, Workbench, Calendar and More (Settings and the voice-note entry). The Workbench badge is the open-ask count (orange, the only tab badge). A minimized capture shows a red bar above the tabs.
- **Settings.** Your Mac: online while the heartbeat is under 720 s old (one stamped ahead of the phone's clock reads online), Last sync, the hub's accounts read-only. Workbench: "Type into sessions from this phone" (`typing_requested`, off) and "Start sessions from this phone" (`start_sessions`, on) are requests to the Mac — while linked each change rewrites the phone's `device` record, writes run one at a time and the newest wins, a failed write reverts only its own change and shows the error; the grant shows "Waiting for your Mac to confirm" or "Allowed". Notifications: "New asks" (on). Choices persist in `UserDefaults`.
- **Not built yet.** The notification content (A13): the two extensions deliver notifications as they arrive.
- Tests: `ReplicaWiringTests`, `RootTabTests`, `SettingsWiringTests`.

### Onboarding and linking, phone half (A12)

- **Root.** `AppRoot` (main actor, the app's lifetime) owns the current `AppEnvironment` and `LinkingViewModel`, and is the flow's `LinkHost`. A transport serves one database for its lifetime and the replica has no wipe of its own, so a scope change or a wipe *restarts* the environment: the old one shuts down (loop and CloudKit engine stopped, after its boot ends); when wiping, the replica files are removed and the transport store is emptied (`TransportStore.wipe()`: buffered events, send queue, system fields, engine state — a transport reopened on the same scope would otherwise resume from its saved change token past the prefix the hydrator already compacted, so the new replica would never re-hydrate, and it would still send the old queue); then a new environment opens on the same paths (`AppRoot.Restarter`). Restarts queue behind each other, so two teardowns (an unlink and a removal) never share or leak an environment. The recorder's launch recovery then deletes audio files without a ledger row. `AppDelegate.root` (weak) reaches the current environment for silent pushes. The demo root keeps its environment, is linked as `DemoSeed.device`, never onboards and ignores link URLs. `AppRootView` shows `OnboardingView` while there is no link, else the tabs with the flow in a full-screen cover while a phase runs and the link notice in a bar above them.
- **`LinkStore`** (`UserDefaults`, plain JSON): the link (`LinkRecord`: `hub_id`, Mac name, `DeviceScope`, owner name, this phone's `user_record_name`, the nonce, the two share URLs in `shared` scope) and a `PendingLink` (the link, the wait's deadline, the grant the replica held before the write). The boot runs the link's database, else the pending link's, else private. `DeviceIdentity`: the device id is a UUID in the Keychain (`DeviceIDKeychain`, this device only; defaults if the Keychain refuses), name ≤ 60 from `UIDevice`, model, marketing version.
- **The scan** (`LinkingViewModel.open`, spec §2.3; `ScanView`'s AVFoundation QR reader and the `watchtower://link` URL from the Camera app run the same call). Step 1: `LinkPayload.parse` (`v` above 1 → "Update Watchtower on this iPhone"; any other parse failure → "This code can't be used…"); expired only when `exp < now − 120 s` (`expiryGrace`, so a phone clock ahead of the Mac's does not refuse — the Mac's own check decides). Already linked to this hub with a linked grant in the replica → "Linked to <Mac>" with nothing written. Step 2: `accountStatus` not `.available` → "Sign in to iCloud on this iPhone to use Watchtower". Step 3 (R2): `owner_user` equal to the phone's `userRecordID().recordName` → `private`, share URLs ignored and never accepted; different → both URLs fetched and accepted (`CloudKitLinkContainer`: `CKFetchShareMetadataOperation`, then one `CKAcceptSharesOperation`), a missing URL or any failure → "This Mac can't share with another Apple ID right now…", then `shared(ownerName: owner_user)`. Linked to another hub → "Switch from <old Mac> to <new Mac>?" before anything is accepted or written; No keeps the old link untouched, Yes unlinks it (below) and links the new one. Step 4: `prepare(scope)` (a restart onto an empty replica when the scope differs), the baseline grant fetched, the `PendingLink` saved, then the `device` record (`link_nonce`, `scope`, `user_record_name`, the Settings choices) saved in that database. Step 5: every 2 s up to 60 s (`grantWait`), one fetch and a read of `device_grant-<device_id>`; a grant of the code's hub that differs from the baseline answers — any `link_refused` → "This code can't be used — Show a new code on the Mac", `linked` → the link is saved, `setLinkedDevice`, "Linked to <Mac>"; none → "Your Mac didn't answer — keep Settings → Mobile open on the Mac and scan again". Step 6: **Continue** asks for notification permission and opens Now. A kill during the wait leaves the `PendingLink`: the relaunch (`resumePendingLink`) waits for what is left of the 60 s in the pending scope and never shows the phone as linked before a grant. A code arriving while a link runs is ignored.
- **Unlink** (Settings → **Unlink this Mac**, live builds only): the link is cleared before anything is awaited (a removal or account signal arriving meanwhile — leaving the shares is what makes the Mac's zones vanish — finds no link and is ignored). Then the wipe restarts on the link's own database (outbox items still pending plus recordings not yet delivered are counted first: "Not sent: N items were still waiting for your Mac"), so the emptied send queue holds only the `device` record with `unlinked: true` that is written next and flushed (`sendNow()` after the boot, best effort) — nothing reported "Not sent" goes out. In `shared` scope the zone-wide share records (`CKRecordNameZoneWideShare`) are then deleted from the shared database and the phone restarts on its private database (an `unlinked` record still unsent then is lost). Welcome.
- **The link's events** (spec §9). `TransportEvent.unlinked` (`AppEnvironment.onLinkSignal`, handlers set before the engine starts) → "This Mac removed this phone", the wipe, Welcome. The transport's account reset → the phone's `userRecordName` compared with the link's: another account wipes and shows Welcome; a sign-out (or a failed check) keeps the replica; the same check runs at launch. After each successful fetch (`onFetched`) the heartbeat is checked: another `hub_id` → "Watchtower moved to <mac_name> — scan the code on that Mac" and `setLinkedDevice(_, writesAllowed: false)` (the link stands, the outbox and uploader get no device id), given back when the linked hub's heartbeat returns; no heartbeat for 24 h → "Your Mac hasn't synced for a day — if it changed iCloud account, link again".
- **Unverified.** The `shared` scope (another Apple ID: share accept, leaving the shares, the account switch under it) runs only against fakes; nothing of it has run on a device yet. The same-Apple-ID path follows S0 (d).
- **Known limits.** The grant carries no nonce, so the phone takes a grant that differs from the one the replica held before the write as the answer; an identical answer to a second scan (the same grant, unchanged `decided_at`) reads as no answer; a refusal carries its own time as `decided_at`, so a repeated refusal is a new answer. A restart during a capture ends the capture (recovered as cut short). An unlinked live phone still runs the private-database engine with a fresh engine state, so a same-Apple-ID phone fetches the whole private database again behind Welcome (a re-link of the same Mac then has its data at once).
- Tests: `LinkingViewModelTests` (fake container, host, clock and Mac; the unlink's order and signals arriving during it), `AppRootWiringTests` (the real wipe, including a persistent transport store reused across the restart, queued concurrent restarts, writes stopped on a moved hub, the scope restart, the grant read, the demo).

### Workbench and Now tabs, read-only (B5)

- **One read for the app.** `AppEnvironment.workbenchReplica` observes the replica and decodes every Workbench slice (`ReplicaStore.payloads(of:from:)` + the Kit mirrors) plus the heartbeat (through Settings' logging decode) into one `WorkbenchReplicaSnapshot`. An undecodable record is skipped and counted in `skippedRecords`, logged only when the counts change. Now, Workbench and the tab badge (open-ask count) share it.
- **Pure screen models** (`WorkbenchCardModel`, `WorkbenchMenuModel`, `SessionRowModel`, `WaitingCardModel`, `BoardModel`, `BoardTargetDetailModel`, `NowModel`) carry every string and colour a screen draws; the views only lay them out.
- **Sessions are drawn as given.** Dot tone, ring (`is_ring`), glyph and caption come from the record (`PhoneTone(_:)` maps the five published tones to the system colours of spec §14; an unknown tone draws secondary). The phone adds only the age of a session that is not live. Report line: `#<report_target_id> · <done>/<total> · <report_pr_line>`, absent without `report_target_id`.
- **Counts.** Board progress is `done_targets / (open_targets + done_targets)`, no bar at 0 of 0. "todo" is `open − in progress − blocked`. Session-state counts are the hub's `session_counts`; "not running" is not shown. Now sums them over all workbenches.

A node has a disclosure only with visible children.
- **Sibling order** is the Mac's: priority high/medium/other, then status in_progress/in_review/blocked/todo/done/other, then id (`BoardModel.boardOrder`, a third twin of Core's `WorkbenchBoardOrder` and Go's `boardSiblingOrder`; change all three together).
- **Orange only for waiting and asks.** Views paint only tones the screen models hand them. Each model lists its `ToneUse`s with a `ToneRole` decided from the data; `OrangeToneTests` runs every DemoSeed screen and fails on orange outside a waiting or ask role, and checks that the data-driven tones (status, priority, Mac chip) are never orange. The project has no snapshot library.
- **DemoSeed** adds three workbenches (one without sessions and with an empty board), ten sessions covering every state kind, open REVIEW/ASK/CHECK asks plus closed ones, a board tree with archived targets and a comment thread.

### Session detail (B7)

- **Reached from** a session row on the Workbench tab or in a target's detail (`SessionRoute`). `SessionDetailModel` is the pure screen model: the header (title, target chip that opens the target, the target's branch or else the workbench's, "Claude Code · <age>", the Mac's state caption), the session's open asks newest first ("since <oldest age>"; the rows open nothing until the answer flow), "Needs approval on the Mac" for a `needs_approval` session (the phone never answers a permission prompt), the report card and the timeline. No report → header and timeline only.

### Ask answers, phone half (B9)

- **Kit anchors.** `PlainTextRendering` (WatchtowerKit `Review/`) renders a review's `doc_snapshot` to the plain text Core's `DocumentRendering` gives, with heading offsets in UTF-16, over a small CommonMark and GFM reader (`MarkdownBlockReader`, `MarkdownInlineText`). `CommentAnchorBuilder` ports `CommentAnchor.make`: 64 characters on either side, the nearest heading at or before the selection. `CommentAnchorBuilderTests` runs every case of the shared `anchor-fixtures.json`. Known limits: link reference definitions and reference links stay literal, and raw HTML stays as text. The Mac re-locates every anchor, and a whitespace run counts as one space.
- **Applied echoes.** An `applied` echo removes its overlay row. `ActionOutbox.setAppliedObserver` reports each row an applied echo removes, and never a redelivered echo or an unknown id. `removePendingAction` now returns whether a row went. This is how the phone reads `result.delivery`.
- **Drafts and sending.** `AppEnvironment.askDrafts` (`AskDraftStore`, in memory, keyed by ask id) holds each `AskDraft`, so a draft survives navigation. `AppEnvironment.askAnswerer` (`AskAnswerer`) enqueues `ask_answer` through the outbox, one answer per ask in flight. That guard is `SendGuard`, which `BoardWriter` now shares. Send is off until `AskDraft.isAnswerable` holds, using the Mac's rules: a review needs a verdict; every question needs a label from its options (one label unless multi) or an Other that is not just whitespace; a broken step needs a note; the note is at most 4000 runes. Empty comments are dropped, as Core drops them. An applied echo keeps its delivery in `AskAnswerer.applied` and clears the draft.
- **Form.** `AskFormModel` is pure. It shows a question page, the review snapshot, the check rows, the answer's state and a closed ask's stored answer (read-only). The answer's state is "Sending…" or "Waiting for your Mac" (`MacStatus`). A refusal shows the hub's message with Dismiss. `ask_not_open` shows the ask's status from the replica. After `applied`, a delivery line appears: `submitted` "Sent to the session", `typed` "Typed into the session — press Return on the Mac to send it", `held` "Held until the session is free", `queued` "Queued behind another answer to the session", `copied` "On the Mac's clipboard — paste it into the session", `no_session` "No session is running — the answer is saved on the Mac". With no delivery the line is "Answer saved on the Mac". With `payload_clipped`, the form is only "Open the ask on the Mac". A cut snapshot shows "Showing the first 256 KB of N" (N from `ByteCountFormatter`, `.file`).
- **Superseded (Review Focus 3).** On `ask_not_open`, `AskFormModel.successor` follows the `previous_ask_id` chain to its newest round. If that round is open, `AskViewModel.followSuccessor` moves the screen to it. The old draft's free text (Other answers, "“quote” — comment", step notes, the note) goes into the new draft's note. The old draft and the failed row are dropped. Labels, anchors and the verdict do not carry over.
- **Views.** `AskView` (with `QuestionAskView`, `ReviewAskView`, `CheckAskView`) is pushed by `AskRoute`. Routes come from Waiting-for-you cards on Now and Workbench, from the closed asks under "▸ N closed", from a session's asks and from a target's asks. Review comments go on a selection of a read-only `UITextView` showing the rendered text, and its UTF-16 selection becomes the anchor. Approve and Request changes set the verdict and send.

### Board writes, phone half (B13)

- **Sending.** `AppEnvironment.boardWriter` (`BoardWriter`) enqueues `board_target_status`, `board_target_priority`, `board_comment_add`, `board_comment_reply` (entity: the root comment) and `board_target_create` (no entity) through `ActionOutbox`. `from_status`/`from_priority` are always the replica's value the phone shows; picking that value sends nothing.

A failed row shows the hub's message (or "Your Mac could not make this change") with Dismiss.
- **Conflict.** A failed row with `reason = conflict` and a string `result.current` shows `ConflictPrompt`: "Changed on the Mac to <label> — apply anyway?" (the display label, "Blocked"/"Medium"). Yes enqueues a new action with the same request and `from_*` = current, then drops the failed row; No drops it. Without `current` it is an ordinary failure.

### Session start and stop, phone half (B15)

- **Overlay echo status (Kit).** `pending_actions` gains a nullable `echo_status` (added in place on an older replica), exposed as `PendingAction.echoStatus`: `ActionOutbox.applyEcho` records a `received` or `held` echo on a still-pending row (a failed row keeps its refusal). `applied` still removes the row and calls the applied observer with its `result`.
- **Starter.** `AppEnvironment.sessionStarts` (`SessionStarter`) enqueues `session_start` (entity: the target) and `session_stop` (entity: the session, `{}`) through the outbox, one start per target and one stop per session in flight (`SendGuard`). It keeps each start (`StartAttempt`: action id, params, applied, `session_id`) for the app's lifetime, so leaving the sheet or reopening the target shows the current stage. `AppEnvironment` shares the outbox's applied observer between `AskAnswerer` and `SessionStarter`; an applied start the starter did not send this run (before a relaunch) is followed too. Nothing retries on its own: after a refusal only Try again sends, as a new action with the refused one's params, and the refused row goes.
- **Stages.** `StartStage` follows the echoes: "Sent to your Mac" (the save succeeded) → "Mac picked it up" (`echo_status = received`) → "Starting Claude Code" (`applied`, `result.session_id`) → "Open session" (the `terminal_session` record is live and its `state_kind` is not `not_started`). Without this run's attempt the newest overlay row gives the stage. With a stale heartbeat no echo arrives, so the sheet stays on "Sent to your Mac" and adds "Waiting for your Mac". A refusal shows the hub's message (an `outcome_unknown` without one: "Your Mac restarted while applying this — check it on the Mac") with Try again and Dismiss.
- **Sheet.** `StartSessionSheet` ("New session on the Mac") opens from a target's "Work on it in a session" (target fixed) or the Workbench header's New session (a target picker over the workbench's non-archived targets). Rows: workbench, target, agent Claude Code (not selectable), the brief prefilled from `work_on_prompt`, "Bring the window forward on the Mac" (off) and "Plan first, then ask me" (on). The phone's grant comes from the `device_grant` records in `WorkbenchReplicaSnapshot.grants` (no record → typing off, starts on). The brief is editable only with `typing_allowed`, and `brief` goes on the wire only from such a phone and only when edited, so an unedited (possibly clipped) prompt never replaces the Mac's. With `start_sessions_allowed` false, Start is off with "This phone is not allowed to start sessions on the Mac".
- **Existing session.** A session with this target, or listed in its `session_ids` (a live one first, then the latest active), turns the buttons into Open it and Start a new one (`mode: new`). Open it on a live session opens its detail on the phone and sends nothing; on one that does not run it sends `mode: open_existing` and follows the stages.
- **Stop.** The session detail's actions menu (•••) shows Stop on a live session only; "Stop this session on the Mac?" confirms it. The stop shows in place ("Stopping…" or "Waiting for your Mac") until applied, and a refusal shows the hub's message with Dismiss. Finish stays hidden until session input.

### Phone recorder and uploader (C6)

- **Capture.** `PhoneRecorderController` (owned by `AppEnvironment`, so a capture survives navigation and Minimize) over the `AudioCaptureEngine` seam; on a device `AVAudioCaptureEngine` writes AAC 44.1 kHz mono 64 kbps `.m4a` (`aac-64k-mono`) as a fragmented MP4 (10 s fragments), so a capture cut short by a kill stays playable up to its last fragment. Files land in Application Support `phone-recordings/<uuid>.m4a` and stay until the Mac acknowledges them. An interruption (a call, Siri) pauses into the same file and the timer leaves the gap out; a route or configuration change (AirPods, CarPlay) ends the capture with a notice and saves what was written (POC choice). Auto-stop at 3 h with a notice 5 minutes before (a local notification when allowed). Under 1 s is discarded. "Record this meeting" ties the capture to its event; More's entry records a voice note (no event).
- **Screens.** `RecordingView`: REC mark, "<Meeting> | No meeting", timer, red waveform, Pause | Stop | Mark moment, Minimize; after Stop the Saved screen shows "Saved · mm:ss" and the recording's way to the Mac ("Waiting for the Mac to wake" while the heartbeat is stale, re-rendered every 30 s). Red is the recording colour.
- **Ledger** (`phone_recordings`, `RecordingUploader` is its only writer): `recording` (row from the first second; marks are stored as tapped) → `waiting` (finalized) → `uploading` (saved into RelayZone with the asset) → `delivered` (the hub's `received`: the local file is deleted, ack-then-delete) or `failed` (the hub's message; Retry re-sends the same record name). A local failure (file gone, over 90 MB, no readable audio) offers no Retry. File names are stored relative to the recordings folder, which iOS may move between launches.
- **Launch.** `recoverOnLaunch` finalizes a `recording` row from its file and deletes files no row points at. The first `uploadPending()` of a process re-saves `uploading` rows too (the relaunch retry; the hub's ledger absorbs duplicates); later passes send `waiting` rows only, and overlapping passes merge. Uploads wait while no device id is set.
- **Marks** stay on the phone (`phone_recording_marks`) and never travel in the upload payload (spec §5.3); the recap view shows them as jump points.

## Known limits (POC)

- **One hub, one version.** An unknown `recording_upload` status reads as `pending` on both sides. With one hub that is harmless; an older hub next to a newer one (multi-hub, or a downgrade mid-ingest) could ingest or re-echo an upload whose status the newer hub wrote. Multi-hub and mixed-version setups are out of scope; if they ever matter, decode an unknown status as a distinct inert case on both sides.
- **Take over on a failed pull** proceeds and can lose to a newer unread live heartbeat (clock skew); the take over is then lost, never split (spec §8 I-1).
- **Notifications** are not built (A13), and nothing here has run against real iCloud yet (A14, B16, C9 device checks).
- **Linking in `shared` scope is written to spec, verified only on fakes.** Spike S0(c) (does closing the public link keep the accepted phone?) was never run; only S0(d) (same Apple ID) passed on a device. The hub builds the spec's primary path (close the link, remove unbound participants) and not the F2 fallback. `CloudKitShareService` and the creator values CloudKit reports are untested until the device smoke.
- **No typing request on the Mac.** The phone's `typing_requested` is not stored, so Settings → Mobile offers Allow… for every phone instead of prompting when one asks. The phone's start-sessions toggle is mirrored into `start_sessions_allowed`; its typing request is not.
- **A phone's own unlink** (`unlinked: true` in its `device` record) removes it on the hub as Remove does, once the relay reads the record: until then (and if the record never reaches iCloud) the phone stays in `devices`, in the list and past the device gate.
- **Shared scope: one phone per code.** The link closes when the first phone uses the code, and its sweep removes every participant not bound to a linked phone. A second phone that accepted the public link but had not yet written its `device` record by then is swept and gets no grant; phones scan in turn, each with its own code.
- **A same-Apple-ID phone removed on the Mac is not told.** It reads the private database, so no zone vanishes: it keeps "Waiting for your Mac to confirm" and its actions fail `device_not_linked` until it unlinks itself.
- **CloudKit environments** must match between the Mac and the phone (see above); a mismatch fails silently.
