## Architecture

- **The hub is the Go hub, run by the daemon.** `watchtower sync --daemon` (`startGoHub` → `hub.Resolve`) runs `internal/hub` on every host: on a desktop host (a Mac with the app) in `<data root>/.hub` once the owner turned Mobile on, on a headless host (Linux, a Mac with only the CLI) after `hub enable`. See Hub below and [go-hub.md](go-hub.md). `WatchtowerCore` stays Kit-free (`PublicAPISurfaceTests`).
- **Two transports.** CloudKit, on a desktop host only, through the signed helper `WatchtowerCloudBridge.app` over `<hub dir>/bridge.sock`: it carries sealed envelopes and metadata, holds no hub key and opens no envelope. The hosted relay (`internal/hub/transport/relay`), on any host, for phones with a Relay subscription. `hub_meta.transport` names the active one; a desktop host links over CloudKit whichever is active, a headless host is relay only.
- **Zones and scopes (CloudKit).** The hub writes `DataZone-<hub_id>` (its only writer) and reads phone requests from `RelayZone-<hub_id>`, both custom zones in the Mac user's private database (`hub_id` from `hub_meta`, multi-hub spec §3.1), through the bridge. A same-Apple-ID phone syncs that private database; a different-Apple-ID phone reaches both zones through zone-wide shares in its `shared` scope (DataZone read-only, RelayZone read-write). **On the relay** the hub writes `data/<hub>`, reads one mailbox per phone (`relay/<hub>/<phone>`) and links new phones through `pair/<slot>`.
- **Kinds.** DataZone records are `SliceKind`s (`heartbeat`, `device_grant`, `recording_job` and the workbench kinds); RelayZone records are `RelayRecordKind`s (`action`, `recording_upload`, `device`, and the link request `hello`). Inside the app a record's plain name is `<kind>-<id>`. On the wire the kind and the name are opaque (see End-to-end encryption): every record is a `WatchtowerEnvelope` with `kind` = `"wt"`, and its name is an HMAC under `K_meta`. Only `heartbeat`, `keybox-<device_id>` and `hello-<device_id>` keep fixed names that contain no key.
- **Sealing sits above every transport.** The phone talks to its transport only through a `SecureTransport` (Kit, `WatchtowerSync/Secure/`) that wraps the `CloudSyncTransport` (`CloudKitTransport` live, `InMemoryCloudTransport` in tests and the demo); the neutral types above the seam (`RecordOrigin`, `HubRoute`, `LiveTransport`, `PushWake`, `LinkInvitation`) live in `WatchtowerSync`, and the CloudKit implementations (`CloudKitTransport`, `CloudKitPushWake`, `AskAlertSubscription`) only in `CloudKitTransport/`. The hub's twin is `internal/hub/secure`: `secure.Sealer` builds every record (`secure.Record`) and every push (`secure.Push`), and each transport refuses anything else. DataZone reads pass through still sealed, so the phone's replica verifies and opens them itself. Nothing ever falls back to plaintext.
- **Transport seam (relay client Phase 0a, #1237).** CloudKit-specific types sit below the seam, with no behaviour change on CloudKit. `RecordOrigin` (`CloudRecord.origin`: author, server date; `TransportStore` keeps `creator` and `server_modified_at`), `HubRoute` (`.cloudKit(scope)` or `.hostedRelay(macDeviceID:)`; a hub's `link_json` is unchanged), `LinkInvitation` and `LinkAccess` (the phone's CloudKit implementation is the only phone file importing CloudKit), `PushWake` (silent pushes and work alerts; `CloudKitPushWake`, also used by the NSE), `LiveTransport` and `TransportFactory` (the only phone file naming `CloudKitTransport`). Every 0a path that meets `.hostedRelay` throws `UnsupportedRouteError`; it never falls back to CloudKit. The Kit's `SeamBoundaryTests` keeps `import CloudKit` inside `CloudKitTransport/`. The hub side is the Go hub (ask #802); the phone's hosted relay transport is the relay client spec's (branch `feature/relay-client`).
- **Desktop over the hub.** Settings → Mobile, the pairing sheet, the phone recording queue and keep-awake read the hub only through `watchtower hub … --json` and the control socket (Hub → Desktop over the hub); Desktop never opens `hubstate.db`.

## End-to-end encryption (E2E1–E2E18)

Since 2026-10-12, every record the hub and a phone exchange through CloudKit (and, with the Go hub, the hosted relay) is sealed with keys that exist only on the Mac and on the paired phones. CloudKit's `encryptedValues` stays as the outer layer (spec §3, §7), so ADP is no longer what protects the content.

### Threat model in short (spec §1, §4)

- **Covered.** Apple and anyone who compels Apple see ciphertext only, whether or not ADP is on. So does an attacker holding the Apple ID or iCloud Keychain, because no key is synchronizable or backed up. A share participant and the storage layer see ciphertext too. None of them can forge a phone action or a hub record. A swapped, replayed or rolled-back record fails authentication or is ignored as stale. A photographed QR alone cannot link a phone: the owner must confirm on the Mac, comparing a code that hashes a nonce the Mac draws only after it accepted the phone's hello, so an attacker who also sees the owner's phone cannot pick keys that reproduce its code (SAS v2). A phone removed on the Mac reads nothing published after the removal. One edge: a save that `CKSyncEngine` had queued before the rotation committed can still land once under the old epoch; it carries only content from before the removal, and the next cycle reseals it.
- **Not covered.**
  - An unlocked phone that is stolen or runs malware, and any malware on the Mac (the Mac is the plaintext source of truth). This reaches past the data on the phone.
  - **No forward secrecy against a later device-key compromise.** The relay keys are static-static: X25519(`hub_kx`, `dev_kx`) with the link nonce as salt, and the epoch is only an HKDF label. The nonce is in the QR and in the phone's `UserDefaults`. Keyboxes are HPKE base mode to the long-lived `dev_kx`. Suppose someone kept the ciphertext: Apple retaining deleted records, a backup of the container, or a future relay's logs. If that person later reads a phone's `dev_kx` (an unlocked phone, malware, a forensic extraction of an unlocked device), they can derive every relay key of every epoch. They can then open:
    - every recording and action that phone ever sent, even after the phone deleted the plain audio on `received`;
    - every keybox it ever received, which gives each epoch's `K_data` and `K_alert`, so the DataZone content of all those epochs.
    
    A leaked `hub_kx` opens every phone's past relay traffic the same way. A ratchet (an ephemeral X25519 per hello and keybox exchange, so a relay key does not derive from static keys alone) is left for when a relay is built.
  - **`K_alert` is readable after the first unlock.** The shared alerts group keeps the current and previous `K_alert` and the hub's public signing key `AfterFirstUnlock` (the NotifyService extension must open alerts while the phone is locked). A forensic read of a phone that has been unlocked once since boot yields them. With the owner's CloudKit access, they reveal the title, workbench name and kind of every open ask alert.
  - The platform itself: the OS, CryptoKit and the Keychain are trusted.
  - Availability: records can be deleted, withheld or delayed. The phone detects staleness; it cannot prevent it.
  - Metadata (below).
  - Shared zones have no per-record ACL, so a RelayZone participant can trample other phones' records until swept (denial of service only).

### Primitives and keys (E2E1, E2E5, E2E10)

- **Primitives.** CryptoKit only. Suite 1 is X25519, Ed25519, HKDF-SHA256, ChaCha20-Poly1305, and HPKE RFC 9180 `DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20Poly1305` (`SealedBox.ciphersuite`). Suite byte `2` is reserved for a hybrid ML-KEM wrap and refused today, as is any unknown version or suite (`EnvelopeError.unsupportedVersion`/`.unsupportedSuite`, the phone's "Update Watchtower" path).
- **Hub keys.**
  - `hub_sig` (Ed25519) signs every DataZone envelope, keyboxes included.
  - `hub_kx` (X25519) receives hellos and derives the relay keys.
  - A 32-byte wrap key.
  - `K_meta` (32 bytes) makes record names.
  - Per epoch `e`: `K_data[e]` for DataZone content and `K_alert[e]` for lock-screen ask alerts. `K_alert` opens only ask alerts, but it is readable after the first unlock (see Not covered).
  - Per linked phone, epoch and direction: a relay key, `KeyDerivation.relayKey` = HKDF-SHA256 over X25519(`hub_kx`, `dev_kx`), with the link nonce as salt and info `"wt/relay/v1/" ‖ p2h|h2p ‖ 0 ‖ hub_id ‖ device_id ‖ epoch`. The epoch is part of the info (D10), so a rotation rotates the pairwise keys too.
- **Phone keys.** `dev_sig` (Ed25519) and `dev_kx` (X25519). The phone's `device_id` is the UUID form of `SHA-256("wt/device-id/v1" ‖ dev_sig_pub)[0..<16]` (`KeyDerivation.deviceID`, D7). It is written as the uppercase `uuidString` (F30); the hub compares ids case-insensitively. The hub's `sender_id` is its `hub_id`.
- **Where the hub keeps them (D2, D3).**
  - `hub_sig`, `hub_kx` and the wrap key are one 0600 file, `<hub dir>/identity.key` (`identity.FileStore`), on a desktop host as on a headless one: the Keychain check failed (go-hub.md, "The identity store on a desktop host"), so `hub_meta.identity_store` reads `file`. Never synchronizable; the data root is kept out of Time Machine.
  - `K_meta` (`hub_meta.k_meta_sealed`) and each epoch's `K_data ‖ K_alert` (`hub_epochs.sealed_keys`) live in `hubstate.db`, sealed with ChaChaPoly under the wrap key, with hub id and epoch in the AAD. A rotation is then one SQLite transaction.
  - `identity.Keyring` (`internal/hub/identity/keyring.go`) holds the epochs, rotates them and allocates seqs over `hub_meta.envelope_seq_ceiling`, so there is one keyring per sidecar (`hub.lock` keeps a second hub out).
  - The hub identity is deliberately not backed up: **a new Mac is a new pairing**.
- **Where the phone keeps them.**
  - `KeychainKeyStore` (the Kit's `PhoneKeyStore`), all `ThisDeviceOnly` and never synchronizable.
  - Secrets (the device identity, each hub's `HubLinkKeys`: hub public keys, link nonce, `K_meta` and at most two `EpochKeys`) are `WhenUnlocked`.
  - The non-secret `deviceid` item and an `AfterFirstUnlock` copy of the hub's public signing key are readable while locked (F14), so apply can verify signatures.
  - Every item goes to the app's private access group explicitly (`WTKeychainPrivateGroup` in Info.plist, F20).
  - Only the alert material (`AlertMaterial`: the `K_alert` epochs with the data keys emptied, plus the hub's public signing key, F21) goes to the shared alerts group (`WTKeychainAlertGroup`), `AfterFirstUnlock`, which the NotifyService extension reads.
  - The app reads every key through one `CachingPhoneKeyStore` (`PhoneKeychain.store()`). It caches only while the app is known to run unlocked: it drops everything on `protectedDataWillBecomeUnavailable`, `willResignActive` and `didEnterBackground`, never caches a failed read, and cannot put stale keys back after a drop (a generation counter).
- **Keychain writes.**
  - A write is update-or-add (`SecItemUpdate`, then `SecItemAdd` on `errSecItemNotFound`), never delete-then-add, so a failed write cannot destroy a key.
  - Creation is add-only. A creator that loses the race loads what the winner stored.
  - A locked keychain is its own error, `KeyStoreError.locked`, and is never read as "absent".
- **Sequence numbers.** `SeqAllocator` hands out u64 values from 1 (0 means "none" for the rollback guards). It persists the block ceiling before using a new block, so a crash skips ahead and never reuses a seq. The phone keeps its ceiling in each hub's replica (F29) and carries it to a rebuilt session of the same hub within the process (`AppRoot.seqFloors`, `HubSession.raiseSeqFloor`). The new replica stores the carried floor at once (`HubSession.persistSeqFloor`), so two removals with no seal between them keep it. Seqs that restart anyway (a reinstall, an unreadable ceiling) are absorbed by the hub at the re-link: the confirmed link (`link.Center.Confirm`) deletes the phone's `relay_seen` rows (final review Kit I2, Desktop I-1). Those marks protect nothing once the link nonce is replaced.

### Envelope, inner frame and record names (E2E3, E2E7)

- **Envelope.** `Envelope`/`EnvelopeHeader` (`Secure/Envelope.swift`). The 68-byte header is `"WTE" | ver u8 (1) | suite u8 (1) | flags u8 (bit0 signed, bit1 has-asset, bit2 padded) | hub_id 16 | sender_id 16 | epoch u32 | seq u64 | nonce 12 | class u16 | body_len u32`. Then the body (ciphertext ‖ 16-byte tag, or for HPKE `enc` 32 ‖ ciphertext ‖ tag), then a 64-byte Ed25519 signature when signed.
  - The AAD is the header plus the zone byte and the length-prefixed wire record name (`EnvelopeContext`). A record moved to another name or zone does not open.
  - The signature covers `"wt/sig/v1" ‖ AAD ‖ body`.
  - The u16 after the nonce is the **class** (`EnvelopeClass`), not the slice kind (D1): `data` (K_data, signed by `hub_sig`), `alert` (K_alert, signed), `keybox` (HPKE to `dev_kx`, signed by `hub_sig`), `hello` (HPKE to `hub_kx`, signed by `dev_sig`), `relayToHub` and `relayToPhone`.
  - `EnvelopeSealer.openSymmetric` refuses a `data` or `alert` envelope that is unsigned or opened without a verifier. Every DataZone envelope must carry a valid hub signature.
  - Nonces are 96 random bits. For the HPKE classes the header nonce is 12 zero bytes.
- **Inner frame** (`InnerFrame`, the encrypted plaintext). It carries the plain `kind`, the plain record id, the notify level, an optional 101-byte `AssetDescriptor` (key ‖ asset header ‖ SHA-256 of the plaintext) and the payload, then zero padding.
  - The frame is padded to the next of 256 B, 1 KiB, 4 KiB, 16 KiB or 64 KiB, then to 64 KiB multiples (`Padding.paddedLength`).
  - Padding is clipped so the envelope stays at or under `Envelope.maxBytes` = 900 000 (D12; the hub's twin is `secure.MaxEnvelopeBytes`, the publisher's 900 KB guard). A record that does not fit even unpadded is skipped as oversized, as before.
- **On CloudKit.** A sealed record is a `WatchtowerEnvelope` (`CloudKitTransport.recordType`).
  - `kind` is the constant `"wt"` (`WireKind.envelope`).
  - The envelope is `encryptedValues["payload"]`.
  - `modifiedAt` stays plaintext.
  - The asset file rides as the record's `CKAsset`, already sealed.
  - The notify level travels only inside the frame (F28).
- **Record names** (`KeyDerivation.recordName`, `SecureTransport.wireName`) are 26 lowercase base32 characters of `HMAC-SHA256(K_meta, "wt/name/v1" ‖ zone ‖ kind_len ‖ kind ‖ id)[0..<16]`, with the plain name split at its first `-`. Fixed names that contain no key: `heartbeat`, `keybox-<device_id>` (the plain `device_grant-<device_id>`), `hello-<device_id>` and the signal `sig-<wire name>`. The hub keeps each record's wire name beside its plain name in `slice_state.wire_name` (F19, `SecureTransport.plainName(forWire:)`).
- **Assets** (`ChunkedAssetCipher`, E2E2). Every asset gets a fresh random `K_asset` and is sealed in 1 MiB chunks. Chunk `c` uses nonce `u32 0 ‖ u64 c` and AAD = the 37-byte `AssetHeader` (`"WTA" | ver | suite | asset_id | chunk_size | total_len | chunk_count`) ‖ `c` ‖ last flag. The last chunk is zero-padded, so a sealed asset is a whole number of MiB.
  - **The sealed file has no plaintext header**, only the sealed chunks. A clear `total_len` or `asset_id` would cancel the padding. The header travels in the encrypted `AssetDescriptor` and is bound into every chunk's AAD.
  - Files are sealed and opened in a stream, one chunk in memory. Decryption writes through an owner-only (0600) temp file and an atomic move.
  - `ReplicaStore.maxAssetBytes` is the sealed length of 20 MiB (F33).
- **Signals** (`WireKind.signal`, the CloudKit type `WatchtowerSignal`, E2E11, E2E18) are the one plaintext record type. Each is a payload-free `sig-<wire name of an ask alert>` that `SecureTransport` passes through unsealed (F12). It names only the alert's opaque record. A `sig` record in any other shape is dropped as `malformedSignal`.
- **Pushes** (`alert-push`, hosted relay only, Go hub plan 4). An alert pushed through `send_alert` is the same `ask_alert` frame sealed as class `alert` under `K_alert[current]`, signed by `hub_sig`, with the fixed wire name `alert-push` in the AAD (`secure.AlertPushWireName`; zone byte `data`), so it opens with the Kit's `AlertOpener.open(wireName: "alert-push", envelope:)` and no network, and never under a record's wire name. The frame is padded to the 1 KiB bucket (a 1172-byte envelope); the envelope may not pass 3021 bytes (`secure.AlertPushMaxEnvelope`: the relay's 4096-byte APNs payload less its 67-byte body, base64), so `Sealer.AlertPush` clips body, then title, then workbench name one grapheme cluster at a time with "…" (`ErrAlertTooLarge` only when even empty texts do not fit); the data-zone record keeps the full text. `secure.Push` is built only there, and `transport.Alerts.SendAlert` takes no other type. Pinned by `go-sealed.json` case `alertPush` and the Kit's `GoSealedEnvelopeTests.testGoSealedAlertPushOpensWithAlertOpener`.

### Who seals and opens what (E2E7–E2E9, E2E11, E2E12)

- **The hub** (`slices.Publisher` through `secure.Sealer`, the one choke point: every transport refuses anything but a `secure.Record`) seals each DataZone record as `data` (or `alert` for `ask_alert`), signed, one record at a time. One record that cannot be sealed, such as a keybox without a recipient key, is skipped alone and never blocks its batch.
  - Slice hashes stay hashes of the plaintext (random nonces make every envelope differ).
  - Staged slice assets are sealed files under `<hub dir>/assets`; each one's descriptor (with `K_asset`) is a row of `hubstate.db`'s `slice_assets` (#604 S12), never a `.desc` file. The owner's off and an iCloud account change remove both (`internal/hub/staged_assets.go`). FileVault is the at-rest story on the Mac. A crash between the file and its row reads as "not staged" and is staged again.
- **The phone writes RelayZone only.** `device` records, actions and uploads are sealed `relayToHub` under the phone's p2h key. The hub's echoes come back sealed `relayToPhone` to the authenticated sender (F16).
  - The hub opens a p2h record only from a linked phone, in an accepted epoch: the current one, or the previous one for 7 days (D10).
  - On CloudKit's shared `RelayZone` the hub's own h2p records go to the phone whose key opens them (F2, `actions/shared.go`).
  - Anything that opens under no key is dropped and logged (ids and classes only), and is **never echoed**: the hub holds no key to answer it with. On CloudKit the daily hygiene (`actions.Processor.Hygiene`) deletes every mailbox record older than the action age window by server time, never by the sender's plaintext `modifiedAt` claim (target 168); the hosted relay ages them out itself (its 14-day TTL).
- **Rollback and replay (D4).** CloudKit gives no ordering, so there is no strict per-device sequence gate. Instead:
  - The AAD binds the opaque name, zone, hub, epoch and seq.
  - The exactly-once ledger keys on the wire name.
  - The authenticated `created_at` gives the 7-day / 24 h age window, and the ledger outlives it by a day. A `created_at` more than 5 minutes ahead of the Mac (`actions.MaxClockSkew`) is `expired` too, so a far-future date cannot stretch the window (target 168); that echo carries "Your iPhone's and Mac's clocks differ by more than 5 minutes — check Date & Time on both." (`clockAheadMessage`; either clock may be the wrong one), a plain expiry none.
  - A per-record `(epoch, seq)` guard, keyed by wire name and sender (F3, `relay_seen` on the hub and in the phone's replica), ignores an older version of the same record. An identical re-delivery is `.same` and idempotent.
  - `devices.last_seq` is only a high-water mark for diagnostics.
  - Uploads have no age window (a legitimate upload can be days late). Instead their ledger row and `relay_seen` row are kept while the record's epoch is still accepted, so a replayed upload can never open and also find an empty ledger.
- **Deliberate re-sends are not replays** (Review Focus 2). The outbox seals an action once at enqueue and keeps the envelope as its `pending_actions` row. The uploader seals a recording once. Every retry sends the stored envelope byte for byte (`SecureTransport.saveSealed`), and so does CloudKit's conflict re-save.
- **The device gate is key-based** (`internal/hub/actions`). An action or upload is applied only when:
  - the phone whose relay key opened it (`sealed.senderID`) is the payload's `device_id`;
  - that phone is in `devices`;
  - on CloudKit, the record's creator is the phone's iCloud user. The creator check stays as defense in depth (spec §5).
  
  Otherwise the record fails `device_not_linked`, echoed to the authenticated sender. A sealed `device` record acts only for the phone whose key opened it (`device_id` equal to the sender), so one phone can never unlink or regrant another. A mismatch is dropped and logged, never echoed. Likewise an action or upload whose payload id does not give the record name the envelope authenticated (`action.recordName`/`upload.recordName` ≠ the frame's name) is dropped and logged before any ledger read, claim or echo (target 148): the ledger and the echo key on that name.

### Pairing with the code (E2E4, E2E13, E2E16)

1. **The QR** (`LinkPayload` v3) adds the hub's public keys `hub_sig` and `hub_kx` (base64url, 32 bytes; an all-zero key is refused) to the multi-hub v2 fields. The Go hub makes its identity before its first code (`link.Center.Issue` on the relay, `IssueCloudKit` with the share URLs); the code is v4 on the Go hub (protocol §5.1).
2. **The phone** checks the code and creates its device identity on first use (only the link flow ever creates one). It stores the scan's `HubLinkKeys` (no `K_meta`, no epochs yet) and restarts on an empty replica (`prepare(fresh: true)`, so the old link's rollback marks, outbox and sealed recordings go). It then writes `hello-<device_id>`: a `DeviceHello` (its `DevicePayload` plus both public keys), HPKE-sealed to `hub_kx` with info `"wt/hello/v1" ‖ hub_id ‖ link_nonce`, and signed with `dev_sig`.
3. **The hub** (`link.Center.HandleHello`, `HandleCloudKitHello` on CloudKit; the transport hands hellos over still sealed, F4) tries each kept code's nonce, newest first. It checks:
   - the frame is the hello its record names;
   - the envelope is signed by the enclosed key;
   - the device id, the header's sender and the record name all hash to that key (D7);
   - the creator (and in `shared` scope, both shares accepted).

   The creator check reads `creatorUserRecordID`, not the last modifier: a shared zone has no per-record ACL, and a record keeps its first creator when another participant overwrites it (#69). That is enough here because the record name is bound to the hello's signing key (D7): another participant can only write its own key under its own record name, so content it writes into a phone's record fails D7, and a copy of that phone's own signed hello is that phone's (its nonce, the code decision and the `(epoch, seq)` guard make the replay harmless). Overwriting stays a denial of service (see Known limits → Availability).
   
   A hello that opens under no kept code, or fails a check, is logged and dropped. An unknown code is therefore unanswerable, and the phone ends on its wait timeout. A used or expired code gets a refusal keybox sealed to the hello's key (F5, `link_refusals.agreement_key`). A valid hello goes to `pending_devices` with its keys, a fresh `confirm_nonce` and its four-digit code, and the code stays unused.

   **Attempt cap.** One code hands out at most `link.MaxNoncesPerCode` (3) confirm nonces in total, across all devices (`link_codes.confirm_nonces_drawn`). A known device's key change counts too: `device_id` hashes only `dev_sig`, so re-rolling `dev_kx` would otherwise buy a fresh nonce and code per hello. Once the nonces are spent, every further hello for that code is refused with `too_many_requests` (sealed to its key) and never shown; the owner shows a new code. A waiting phone re-sending its hello unchanged (same code and keys) draws none and keeps its nonce and code; a changed name, typing request or start-sessions choice on such a re-send is ignored. The owner's Refuse gives no try back. So guessing the owner's code online costs at most three tries per code, each visible on the Mac. Refusals are bounded too (target 168): a new phone's refusal draws from the same per-code counter, up to `MaxNoncesPerCode + MaxRefusalsPerCode` (3 + 10) answers per code, and at most `MaxLinkRefusals` (50) phones hold a refusal at once; past either bound the hello is logged and left unanswered. A code pruned while its hello was being checked has no counter, so only the total cap applies and its phone still gets its refusal. A phone already refused is rewritten in place. Hellos also count toward the pass budget (`actions.BatchLimit`, 200), so a flood spreads over passes.

   **Names.** The link center (`displayName` in `internal/hub/link/hello.go`) cleans the hello's name before it is stored: control and format characters (newlines, bidi overrides, zero-width marks) go, except the emoji joiner; whitespace runs become one space; the result is clipped to 60 grapheme clusters, and an empty one reads "iPhone".
4. **The code (SAS v2, D6; final review I-1).** The hub draws `confirm_nonce` (32 random bytes) only after it accepted the hello, whose device keys are thereby committed, and keeps it with the request (`pending_devices.confirm_nonce`; a hello re-sent unchanged keeps the stored nonce and code, a hello under another code gets a new one). `KeyDerivation.sas` hashes the transcript `"wt/sas/v2" ‖ hub_id ‖ link_nonce ‖ hub_sig ‖ hub_kx ‖ dev_sig ‖ dev_kx ‖ confirm_nonce`, takes 4 bytes from HKDF (salt `link_nonce`, info `"wt/sas/v2"`), and reduces them mod 10 000 to four digits. The waiting keybox carries the nonce to the phone (`DeviceGrant.confirm_nonce`, sealed to its `dev_kx`, signed by `hub_sig`); the phone shows no code until it has a well-formed one. Every SAS input but the nonce is in the QR, so v1 let a QR photographer who could also read the owner's phone grind about 10 000 key pairs offline to match its code; now each try costs a hello and one of the code's three nonces. A request stored before v2 has no nonce and is never offered. Both screens show the code:
   - The Mac sheet (`MobilePairingModel`, over `hub pair --stream`'s `sas` event): "Link “<name>”?", the code and "Check that your iPhone shows the same code".
   - The phone: "Check that your Mac shows **7342**, then click Link on the Mac."
5. **The owner decides on the Mac.**
   - **Link** sends `{confirm: true}`, which runs `link.Center.Confirm(device, code, ok)`. It is bound to the code the sheet showed: if a new hello replaced the request meanwhile, nothing is linked and the request keeps waiting (`link.ErrCodeChanged`). Otherwise the code is re-checked (it may have expired or been used meanwhile), the phone is linked with its keys, and the post-link close refuses every other waiting request with `used_code` (F17).
   - **Refuse** (`{confirm: false}`), closing the sheet, or expiry give `not_confirmed` (or `expired_code`).
   - Keys are never wrapped for an unconfirmed device. Two hellos for one code (a photographed QR racing the owner's phone) show as two rows with different codes, and only the confirmed one gets keys (Review Focus 5).
6. **The keybox** (`Keybox`, published from `link.Center.Keyboxes` under `keybox-<device_id>`) is HPKE-sealed to the phone's `dev_kx` with info `"wt/keybox/v1" ‖ hub_id ‖ device_id`, and signed by `hub_sig`. It carries:
   - the `DeviceGrant` the readers already decode;
   - once linked, `KeyboxKeys`: the current epoch with `K_data` and `K_alert`, `K_meta`, and after a rotation the retired epoch's keys (`previous*`) while its grace runs.
   
   A pending request reads `awaiting_confirmation: true` with its `confirm_nonce` and without keys ("Your Mac sees this iPhone" and the code on the phone). A waiting keybox also carries `link_code_tag` = base64url(SHA-256(`"wt/link-code/v1"` ‖ link_nonce)[0..<16]) of the code the request was made with (`KeyDerivation.linkCodeTag`), inside the sealed, signed keybox. The phone shows "Your Mac sees this iPhone" and the code only from a waiting keybox whose tag is its own scan's: the same QR scanned again (an unchanged hello, so the keybox equals the scan's baseline) still shows the Mac's code, and one left from an earlier code never shows one. A refusal or a link still answers the scan only when it differs from the baseline. A refusal reads `link_refused` (`not_confirmed` and `too_many_requests` are new) without keys.
7. **The phone's wait** polls the keybox every 2 s (`grantPollInterval`) until the code's `exp` + 120 s (never longer than a full code lifetime plus the grace from now), because the owner needs time to compare and click.
   - A `linked` keybox with keys is this scan's answer only when its `linked_at` is at or after the code's `iat`, both on the Mac's clock. An older link's keybox is not this scan's confirmation (review M-3).
   - On success the keys join the stored `HubLinkKeys` and the link is saved.
   - A failed or timed-out scan removes its keys (unless they belong to the saved link). A re-scan of the Mac the phone is already linked to, which does not end linked, ends the old link (I-1). It never leaves a "linked but unusable" phone.

### Rotation and revocation (E2E14)

- **Triggers.**
  - **Remove** on the Mac, `hub unlink`, or the phone's own `unlinked` record (reason `unlink`).
  - The cap: 90 days or 2^28 seqs (`identity.RotationAge`, `RotationSeqCap`; `Keyring.RotateIfDue` in the hub's housekeeping, reasons `age`/`cap`).
  - Every accepted transport switch (`transport_switch`, see Hub → Switch and epochs).
  - `manual` (a suspected leak) exists in the keyring but no UI calls it yet.
- **One transaction** (`identity.Keyring.Rotate`/`RotateWith`, the only rotation path; Review Focus 4; the reason is stored in `hub_epochs.reason`, sidecar `00010`). It does all of this together or not at all:
  - creates the new epoch's `K_data`/`K_alert`;
  - retires the old epoch;
  - removes the device (for reason `unlink`);
  - blanks every `slice_state` hash. The hashes are blanked, not deleted, so records that left the window are still deleted next cycle.
  
  If another process rotated first, or the wipe fails, nothing is written: the old epoch stays current and the device stays linked. A killed rotation resumes on the same epoch. A cycle sealed under the old epoch checks the epoch again before saving, so a removed phone never gets post-removal data under the old key.
- **Then** the next cycle republishes the window under `e+1`. The remaining phones' keyboxes carry the new keys plus the previous epoch's. Open ask alerts are resealed under `K_alert[e+1]` without a new signal or push. Relay envelopes of the previous epoch are accepted for 7 days (D10).
- **The removed phone** loses its relay keys, so the hub can no longer echo to it. Instead, for 7 days (`link.RevokedLifetime`), its keybox reads `revoked: true` without keys, signed and sealed to its own key (`revoked_devices`, D9). The phone reads that as "This Mac removed this phone" and wipes, in either scope, including a same-Apple-ID phone that sees no zone vanish.
- **Settings → Mobile.** Removing a same-Apple-ID phone now says "Removed <name>. It can no longer read anything new from this Mac." (`MobileSettingsModel.removed(_:)`).
- **`K_meta` does not rotate** (D5): a removed phone could still map future opaque names of kinds and ids it already knows (metadata only).
- **Keys reach the phone's Keychain by a reconcile** (final review Phone I-1). The hydrator's keybox signal is one-shot, so the merge into the Keychain does not rely on it alone. `LinkingViewModel.reconcileKeyboxKeys(hubID:)` runs, per hub, after every fetch (from the grant check's keybox read), at unlock (`HubSession.onKeysAvailable`) and on a re-scan of the Mac the phone is already linked to. It merges the stored keybox's epochs that the Keychain lacks; it compares epoch numbers, never key material. It then has the host open the stored rows (`LinkHost.keysMerged(hubID:)` → that session's `indexStoredRows`). With nothing missing, it writes nothing.
- **Hygiene and `hello`/`device` records.** Relay hygiene deletes `hello` records older than 7 days. A linked phone's `device` record sealed under an epoch past its D10 grace no longer opens, so it is deleted after 7 days of plaintext age like other unopenable records. Before E2E, device records were kept. Nothing is lost: the link state lives in the sidecar, and the phone's next settings change writes a new record.

### The locked phone (E2E8, E2E9, E2E17)

- **Hydration while locked** (Review Focus 1). `ReplicaStore.apply` needs no secret key. It verifies each envelope's hub signature with the `AfterFirstUnlock` public key, checks the hub id and the class, and stores the ciphertext with its `(epoch, seq)` (`slice_records.epoch`/`seq`, `needs_index`).
  - A bad signature, another hub's record or an older version is refused and counted (`rejectedCount`), never stored.
  - The `data_seen` table remembers the newest version per wire name across deletions, so a deleted record cannot come back older. It is dropped only by the format wipe.
  - A newer envelope version or suite is stored unindexed and counted (`newerFormatCount`; Settings shows "Update Watchtower on this iPhone: your Mac uses a newer format.").
  - Signals and other phones' keyboxes are skipped silently (F12, F13).
  - A key that cannot be read at all (before the first unlock, no link yet) aborts the batch with its token kept (F15).
  - A record whose epoch keys are missing is still stored. It opens once its keybox lands, so a batch carrying new-epoch records plus their keybox never deadlocks.
- **Indexing.** `indexPending()` opens the stored rows with the epoch keys and fills their plain `kind` and `plain_name` (D11). Every read opens the payload again; only the kind and name are kept in the clear. It runs:
  - after each hydration;
  - on `protectedDataDidBecomeAvailable` (`HubSession.keysBecameAvailable`, which also seals waiting recordings and re-adopts held ones);
  - on foreground (`setActive(true)`).
  
  `ReplicaHydrator.onRecordsApplied` reports what indexing opened, with each frame's notify level (F11). A keybox indexed this way reaches the link flow.
- **Relay while locked.** `SecureTransport.changes` throws `SecureTransportError.keysUnavailable` on a locked keychain. `RelayFeed` keeps its token and replays the echoes after unlock. An enqueue while locked throws `KeyStoreError.locked` before anything is sent.
- **Decoded values.** `ReplicaDecodeCache` drops everything it decoded on `protectedDataWillBecomeUnavailable` and `didEnterBackground`, so decoded plaintext does not outlive the unlocked foreground (final review Protocol M-9). A decode that began before a drop returns its value but does not keep it.
- **On screen.** `ResilientObservation` does not count `locked`/`keysUnavailable` as failures. It keeps the last value and restarts every live observation on unlock, because list reads silently leave out locked rows. Settings shows "Unlock this iPhone to see the latest from your Mac.", the session detail "Unlock this iPhone to see the latest report.", and the recap "Unlock this iPhone to read the transcript."
- **Boot.** The device id is read from the non-secret `deviceid` item. Before the first unlock since a restart even that is unreadable, and the boot waits for the unlock (`Boot.waitingForUnlock`). A launch that is not the link flow never creates an identity.

### File protection on the phone (E2E17, D8)

`FileProtection` (`WatchtowerMobile/Sources/App/`):

- **Class C** (`completeUntilFirstUserAuthentication`, the spec's allowed fallback) for anything background work must reach after the first unlock, all of which is ciphertext or metadata: the app group directory and each hub's directory in it (the replica; `HubPaths.prepare`), each hub's transport store folder (`<appSupport>/hubs/<hub_id>/`; `AppEnvironment.liveTransportStore(path:)` sets the class before the store opens), the transport's incoming asset stash (`TransportStore.stashDirectory`), each hub's recordings folder (sealed `.enc` files), `.held` and its manifest. The hold manifest is class C so a locked background wipe can still hand audio over.
- **`completeUnlessOpen`** for plaintext audio, for its whole life on the phone: the capture in progress, then the finished recording. Plain audio stays on the phone until the Mac confirms receipt (owner ruling ask #89, option A): sealing writes the ciphertext `<id>.enc` beside it and only that ciphertext goes to iCloud; the hub's `received` echo deletes both, a `failed` echo keeps both, the owner's discard deletes both. This is what lets main's #63 hold carry an undelivered recording across a wipe.
- Apart from that plain audio, no plaintext content is left at rest after sealing. The simulator stores no protection class, so tests read back what was set; the real attributes need a signed device run.

### Migration: the hard cut (E2E15, D13)

- **The hub.** Record type `WatchtowerEnvelope` replaces `WatchtowerRecord`, which is ignored on fetch. The hard cut itself (zones deleted once, phones forgotten, fresh keys) was the Swift hub's (see History); the Go hub adopts an E2E state as it is (`hub adopt`, go-hub.md) and never runs it.
- **The phone.** A replica of format 1 (plaintext) is dropped and re-hydrated. Plaintext `pending_actions` rows are deleted with `secure_delete` and a WAL checkpoint. At launch, a saved or pending link without a hub signing key (a v2 link) is dropped, its hub removed (`dropUnencryptedLinks`, per registry row) with "Watchtower now encrypts your data. Scan the code on your Mac again." Main's #62 device id (a random UUID in the Keychain plus a `UserDefaults` copy) is deleted at every launch (`LegacyDeviceID.remove`), replaced by the key-derived id.
- **Every pre-E2E phone re-pairs once.** Restoring a phone to new hardware, or reinstalling it, also means re-pairing (keys are `ThisDeviceOnly`). A new Mac re-pairs every phone.

### Frozen vectors and the Go cross-check (E2E1–E2E3, E2E6)

- `WatchtowerKit/Tests/Fixtures/e2e/` holds `kdf.json` (relay keys, record names, device id, SAS v2 with the confirm nonce `0xE0…0xFF`), `envelope.json`, `asset.json` and `hpke-rfc9180-a21.json` (RFC 9180 A.2.1, checked by `HPKEVectorTests`). Every input is a fixed synthetic byte pattern.
- `E2EFixtures` regenerates a fixture only with `WT_E2E_REGENERATE=1`. The test then fails on purpose with "re-run without WT_E2E_REGENERATE". Only the task that introduces a fixture may regenerate it: any later change to one is a wire-format change and needs the owner's approval. The SAS value was regenerated once for SAS v2 (ask #97, 2026-10-13); every other value stayed byte-identical.
- Envelope vectors pin the header and body bytes. The signature is excluded from equality and checked by verification (F8).
- `internal/hub/secure` (Go, the Go hub's E2E primitives: `go test ./internal/hub/secure`) reproduces every deterministic vector byte for byte — KDF, record names, device id, SAS, link-code tag (`TestKitVectors_KDF`), padding (`TestKitVectors_Padding`), asset descriptors and sealed chunks (`TestKitVectors_Asset`), envelope headers and bodies under the fixture nonce (`TestKitVectors_Envelope`) — and verifies or opens the randomized ones (CryptoKit Ed25519 signatures). It replaced the test-only `internal/mobilee2e` reference checks (2026-10-31).

### Metadata that stays visible (spec §1 threat 8, §4)

- Total record count and churn per zone.
- Coarse sizes (the padding buckets; assets in whole MiB).
- `modifiedAt` and the timing of every change: a change publishes after a 150 ms debounce (at most 1 s; the nudge after an applied phone action publishes at once, `PublishNow`), at least 2 s apart on CloudKit and 150 ms on the relay, with a 60 s full diff as the backstop (`slices.Debounce`, `MaxDebounceWait`, `CloudKitSpacing`, `RelaySpacing`, `FullDiffEvery`), and the heartbeat comes every 15 min (`slices.HeartbeatInterval`).
- The hub id (zone names `DataZone-<hub_id>`/`RelayZone-<hub_id>`), the phones' device ids in `keybox-`/`hello-` names, and the fact that a hub exists.
- The Apple IDs of the owner and the share participants, and APNs tokens.
- On the hosted relay: that an alert was pushed to a phone and when (`send_alert`), never what — every push envelope is padded to the same 1 KiB bucket (1172 bytes).
- A `sig-` signal's appearance, which shows that an ask alert was raised (not its content).
- The epoch and seq in each envelope header, and its `sender_id`. Every RelayZone envelope carries the phone's `device_id` there, so without ADP Apple sees which phone acts and when.
- `device_id` = H(`dev_sig_pub`) is one identity for every hub, so one phone is linkable across hubs and containers.
- On the phone, the replica keeps each row's `kind` and `plain_name` in the clear (D11). An image of a locked phone (class C) therefore shows kinds and ids such as `owner_ask-42` or calendar event ids, though not their content.
- A shared-scope phone keeps the alert keys it posted (`hub.<hub_id>.sharedAlerts.seen` in the app's standard `UserDefaults`, not the app group: wire names and keys such as `ask-42` or `stop-7-<ms>`, i.e. ids and stamps, no text).
- The scanned code's `LinkRecord` is kept in the phone's `UserDefaults`: the link nonce (an HKDF salt, harmless without `dev_kx`), the share URLs (dead once the public link closes) and the owner and user record names.

### Trust model decisions (security review, board #153, ask #106)

- **Starting sessions is the Mac's grant (#565).** A phone could start an agent on a target whose text it wrote (a board write's `intent` is not gated by typing), so a start needs the owner's Allow on the Mac: `devices.start_sessions_granted` (Settings → Mobile, its own Allow… / Revoke, off by default), and only together with `typing_allowed` (the hub's start grant check, `handlers.startGrant`). `start_sessions_allowed` stays the phone's own opt-out: a linked phone's rewrite sets it either way, authenticated by that phone's key (`link.Center.ApplyDeviceRecord`), and never grants anything. A sidecar from before #565 gains `start_sessions_granted` in place, off: the link is kept and the owner allows starts once. Board writes (`board_target_create` and its `intent`) stay ungated by typing on purpose: the decision gates the start, which closes the free-text-to-agent chain, and gating target creation would take a capability away. Owner decision 2026-10-17, ask #305 q3 (replaces 2026-10-14 «Оставить телефону»).
- **`typing_allowed` gates typed session input, the start brief and (#565) starting sessions.** An ask answer from the phone (`actions/handlers`, `ask.go`) and a new target's `intent` from a board write are not gated by it. An answer is still delivered under PROJ-12's rules, which may type it into the asking session. Owner decision 2026-10-14: «Оставить как есть» — answering an ask is its own channel, separate from typing.
- **One zone-wide share per zone.** Every QR code reuses it, so an old QR's share URL can join while a later code's public link is open, and the close sweep then removes it. With E2E this grants ciphertext only. A failed close is retried with backoff while `share_sweep_pending` is set.

### Open items

- **The work-alert subscription is registered per hub** (mobile workbench remote, Task 7): `AlertSubscriptionRegistrar` (`HubSession.alertRegistrar`, built from the hub's `HubRoute` and a `PushWake`; `CloudKitPushWake` writes into the private `CKDatabase`) registers `AskAlertSubscription.subscription(for:hubID:)` after the engine starts and removes it when the phone-wide **When work stops** switch (`DeviceSettings.workAlerts`, key `notifications.workAlerts` in the app-group suite, the old `notifications.newAsks` value carried over once; `AppEnvironment.setWorkAlerts` follows it on every hub) is off, or the hub is unlinked or forgotten (`AppEnvironment.remove`); calls are serialized and the newest request wins; a shared-scope hub registers nothing (see the next item) and Settings says "Alerts may be late on this phone." (`WorkAlertsCopy.sharedFootnote`). The extension fills title, body, thread (`session-<id>` or `workbench-<id>`) and `userInfo` (`wt_hub`, `wt_event`, `wt_key`, `wt_session`, `wt_ask`) from the Kit's `WorkAlertContent` (`WorkAlertContent.Key`). After each successful fetch or engine apply while the app is active, the phone reads the replica that hydrate left (never the screens' lagging snapshot) and removes the settled alerts (`ResolvedAlerts`, `DeliveredAlertCleaner`; 120 s grace, absence rules only after a fetch later than the delivery, a Working session only when newer than the stop or fetched after it). The subscription (private scope only, D14) fires on record creation only, so a re-raised alert needs a new `sig-` record.
- **Shared-scope phones post their work alerts locally** (ask #622). The shared database has no query subscription (D14), so after every fetch of a shared-scope hub (`HubSession.performFetch`: a silent push through the sync engine, the foreground return, pull to refresh, the safety poll; and `applyBuffered`), in the background too, `SharedAlertPoster` reads the replica's stored alert-class envelopes (`ReplicaStore.alertEnvelopes`: the class is in the plaintext header, so rows a locked phone could not index yet are listed), opens each one not seen yet with the Kit's `AlertOpener` over the hub's `AlertMaterial` (`PhoneKeyStore.alertMaterial`, the extension's afterFirstUnlock copy) and posts a local `UNNotificationRequest` built from `WorkAlertContent` (same title, body, thread and `userInfo`, so taps route through `AlertDestination` and `DeliveredAlertCleaner` sweeps it), identifier `work-alert-<hub_id>-<key>`. The hub's first fetch (no stored list: a new link, an upgrade, a reinstall) posts nothing and takes every alert there as seen (the Mac keeps alerts up to 7 days; no burst). What was seen is kept per hub in the session's defaults (`hub.<hub_id>.sharedAlerts.seen`, wire name → alert key; read, updated and saved before the first post, so two fetches never post one alert twice; removed with the hub's other choices on unlink, `DeviceSettings.removeChoices`, so a link made again starts silent); entries whose record left the replica are dropped; a key already shown under another wire name is not posted again. With **When work stops** off nothing is posted and what arrives meanwhile counts as seen (as a private subscription, which fires on creation only). A record that does not open (an older payload, an epoch the phone lacks) is skipped, logged as a code and retried on the next fetch. A private-scope hub never posts locally (its subscription delivers, no duplicates). Best-effort: it runs only when iOS lets the app fetch (silent pushes are best-effort, D14), so an alert can be late or wait until the app opens.

## Hub

The hub is Go (`internal/hub`, `Run`), started by the daemon. [go-hub.md](go-hub.md) is its full note (packages, CLI tables, phases 1–4, Linux behaviour, deviations, tests); this section is the map from the phone's point of view.

### Go packages and the sidecar

- **Packages.** `secure` (the sealing choke point: `Sealer` builds every `secure.Record` and every `secure.Push`; the Kit vectors pin it), `state` (the sidecar `<hub dir>/hubstate.db`, the lock `hub.lock`), `identity` (keys and `Keyring`), `transport` (`relay`, `cloudkit` — the bridge client —, `memfake`), `link`, `actions` (+ `actions/handlers`), `slices` (+ `slices/sources`), `alerts` (pushes), `measure` (latency samples), `platform` (owner away, keep awake, peer uid), `adopt` (the one-time hand-over of a Swift hub's state), `hubtest` (the Go phone emulator, tests only).
- **Sidecar ownership.** `hubstate.db` belongs to the hub process holding `hub.lock`; the CLI writes it only while it holds the lock itself, else through the hub's control socket `<hub dir>/hub.sock` (peer uid checked). Desktop never opens it (`DesktopNeverOpensTheSidecarTests`).
- **Migrations** (`internal/hub/state/migrations`, the hub's own goose provider, applied on open): `00001_swift_baseline` (the Swift hub's schema, every statement `IF NOT EXISTS`, so an adopted sidecar opens) through `00009` (go-hub.md lists each), then `00010_switch_epochs` (`hub_epochs.reason`/`retire_after`, `devices.relay_lapsed_at`/`relay_skip_before`/`relay_skip_seq`), `00011_latency_samples`, `00012_alert_pushes` and `00013_alert_pushes_settled_index` (phase 4, below). New columns hold ids, counters, timestamps and classes only; envelopes stay sealed.

### Transports and hosts

- **Desktop host** (a Mac with the app): the hub runs in `<data root>/.hub` once the owner turned Mobile on and any Swift hub state was adopted (`hub_meta.adopted_at`). It links over CloudKit whichever transport is active and reaches CloudKit only through `WatchtowerCloudBridge.app` (`<hub dir>/bridge.sock`, sealed envelopes and metadata only, no key).
- **Headless host** (Linux, a Mac with only the CLI): relay only, live after `hub enable` (or `service install`), terminal pairing (`hub pair`). Guide: `docs/guide/features/headless-host.md`.
- **The iCloud account** (as the Swift hub, ask #969 Q3; go-hub.md "Phase 3 — the iCloud account"). With no usable account the CloudKit side is held (`icloud.go`): while CloudKit is the active transport `hub status` reads `paused`/`no_icloud` and Settings → Mobile shows "Paused until iCloud is available on this Mac. It goes on by itself."; on the relay the hub keeps running. An account change or a zone deleted on the server (`Event{zones_recreated}`) wipes the published state (`state.WipeSyncState`) and republishes in full; a failed wipe is retried at each housekeeping run.
- **The hosted relay** (`transport/relay`, the relay's Go client vendored by `make relay-go`, pinned in `transport/relay/VERSION`): the hub registers as `DEVICE_KIND_HUB`, is admitted once a paying phone vouched for it, writes `data/<hub>` and reads one mailbox per phone `relay/<hub>/<phone>`; with no paying phone it pauses (`needs_relay`).

### Linking

`link.Center`: codes (`Issue`, `IssueCloudKit`), hellos (`HandleHello`, `HandleCloudKitHello`), the owner's confirmation (`Confirm`), keyboxes and grants (`Keyboxes`, `Grants`), `Allow` (`typing`, `permissions`, `start_sessions`), `Unlink` (rotates). Over the relay a new phone links through a pairing slot `pair/<slot>`; on CloudKit through the zone shares. The rules are those of End-to-end encryption → Pairing with the code. An iCloud account change closes the old user's link (`link.Center.AccountChanged`).

### Slices and cadence

`slices.Publisher` hashes each record and saves only changes; a change marks its kinds dirty (nudges after applied actions and from the session-state lane, plus a `data_version` watch for other processes: every 250 ms while a phone was in touch within the last 10 minutes, else every 1 s — `slices.ActivePoll`, `ActiveWindow`, `IdlePoll`). Debounce 150 ms (at most 1 s; an applied action's nudge skips it — `PublishNow` — and only the spacing holds it), at least `CloudKitSpacing` (2 s) between sends on CloudKit and `RelaySpacing` (150 ms) on the relay, `FullDiffEvery` (60 s) as the backstop, the 900 KB guard, the heartbeat every 15 minutes. `MobileSync = workbench_only` keeps only `sources.WorkbenchOnlyKinds`.

### Actions and order

`actions.Processor`: ordered actions per phone by `action_seq` (hold ahead of a gap, one `resend_from` per gap, `skip_to`), the exactly-once ledger keyed on the wire name, `received`/final echoes, the legacy unordered path for older phones, controls; the handlers in `actions/handlers` (asks, board, session start/stop/input/Interrupt, permission answers, chat and report requests, recording uploads). The mailbox pass runs every 30 s on the relay (events wake it sooner) and, on CloudKit, every 3 s for 10 minutes after a phone's last write or while a link waits, else every 30 s; a bridge push runs one at once.

### Switch and epochs

`hub_meta.transport` is `cloudkit|relay`. Only a person switches: a paying phone's `transport_switch`, or `entitlement_expired`. Toward the relay waits at least 5 minutes after the previous switch; toward CloudKit is immediate. Every accepted switch rotates the keyring (reason `transport_switch`), leaves a notice in the transport being left, and keeps the old epoch's relay keys for 7 days (`hub_epochs.retire_after`).

### Recordings

A phone upload becomes a job in the sidecar's queue; Desktop's `PhoneRecordingQueue` claims it (`hub recording claim`), transcribes it and finishes it (`hub recording finish`), reporting progress into the `recording_job` slice. The owner's switch is `hub recordings on|off` (the heartbeat's `capabilities.recordings`).

### Work alerts and pushes

- **The alert.** `slices/sources/work_alert.go` raises an `ask_alert` record (keys `ask-<id>`, `perm-<id>`, `stop-<session>-<ms>`) only while the owner is away (`platform.Away`: locked, display asleep or idle); a stop waits 20 s; alerts live 7 days. It is sealed as class `alert` under `K_alert`.
- **On CloudKit** a new alert's first save also writes its `sig-` signal (the phone's query subscription fires on it); a republish gets no new signal. A hub on CloudKit calls no `send_alert`.
- **On the relay** (Go hub plan 4) the first save hands the alert to the pusher (`slices.Config.OnAlertSaved`); the relay writes no signal. `internal/hub/alerts.Pusher` seals a `secure.Push` with `Sealer.AlertPush` (wire name `alert-push`, envelope ≤ 3021 bytes, frame padded to the 1 KiB bucket, body then title then workbench name clipped one grapheme at a time with "…" in the push only) and calls `send_alert` once per (alert key, phone) for the linked phones with a relay id that are paying and that the last accepted `set_hub_readers` names (`alerts.Eligible`, `pushTargets`). The relay's own placeholder title is the only visible text.
- **Ledger** `alert_pushes` (`00012`, index `00013`): the row is written `pending` at enqueue and settled after the request; a row still `pending` at hub start settles `expired` (`restart`) and is never resent. Outcomes: `accepted` (the relay took it, not an APNs delivery), `no_token`, `not_paying`, `forbidden` (also `HUB_NOT_VOUCHED`), `push_off` (the relay's `not implemented`: no APNs configured), `too_large`, `expired`, `failed`. Expired reasons: `freshness`, `owner_back`, `restart`, `switched`, `overflow`, `stopped`, `in_flight` (a request that may have reached the relay with no answer heard: never resent, counted as received). Pruned after 7 days.
- **Rules.** Freshness 5 minutes from the first save (`alerts.Freshness`); owner-away re-checked before every send, retries included; `RATE_LIMITED`/`TRAFFIC_LIMIT_EXCEEDED` retried after `retry_after_s` (1 s default, 60 s cap) and a relay-coded `UNAVAILABLE` on the next connect or after 30 s; `not_paying`/`forbidden` refresh the account state once. One sender per phone, 64 queued per phone (`QueuePerPhone`; more settle `expired`/`overflow`). A switch to CloudKit settles the queued pushes `expired`/`switched` and `Publisher.Resignal` saves the still-open alerts on CloudKit with their signals, skipping any (alert, phone) the ledger shows received.
- **The phone's half** (`register_push` at launch, the notification extension opening the inline envelope under `alert-push` with no network, one notification per alert key, removed when the record is deleted) is the relay client spec's Phase 4 (the neighbour's work); until a phone registers, the relay answers `no_token`.

### Known limits (phase 4)

- The push-off line appears only after a first `send_alert` (the relay offers no other signal) and goes with the 7-day prune.
- The local relay stand has no APNs: CI and local runs see only `push_off`; a real push needs the relay's staging with APNs and a phone with the relay client's Phase 4.
- `accepted` is the relay's `Ok`: the relay keeps at most 4 alerts in flight per phone and cancels the oldest, and APNs may still drop one.
- An alert raised between a phone's admission and the next readers sync, or before the first readers sync succeeded, is not pushed to that phone; it still reaches the replica.
- A crash during a switch toward CloudKit leaves queued pushes `pending`: they settle `expired`/`restart` at the next start and get no CloudKit signal.
- An alert sealed in an epoch the phone's alert material no longer holds does not open; the extension shows the generic notification.

## Kit (WatchtowerSync + WatchtowerKit)

### Kit package and wire rules (A3)

- **Port.** The sync core of the old `mobile-app` branch, re-homed as `WatchtowerSync`, with the chat seam removed. `SliceKind` keeps the branch's kinds and adds `heartbeat` and `device_grant` (later tasks add the workbench, calendar and recording kinds); `RelayRecordKind` is `action`, `heartbeat` (wire compatibility only), `recording_upload` and `device`; an unknown kind is logged once and ignored.
- **Tolerant decoding.** An unknown `ActionStatus` decodes as `pending`, an unknown `ActionReason` as nil, an unknown `RecordingUploadStatus` as `pending`, and enum-like slice fields are `OpenWireValue`s, so a record from a newer Mac never fails as a whole. `RelayCoder` is the one wire coder: snake_case keys, Unix-second dates, sorted keys, a nil optional is an absent key.
- **Payloads.** `ActionRequestPayload` gains `device_id`, `reason` and `result`; `HeartbeatPayload` (DataZone, §4.1) and `DevicePayload` (RelayZone, plain name `device-<device_id>`, opaque on the wire) carry the hub's and the phone's identity; `DeviceHello` (E2E4) is the `DevicePayload` plus the phone's public keys. `CloudRecordFactory` writes the heartbeat to DataZone, so a RelayZone copy (writable by a share participant) is never trusted.
- Tests: `RelayPayloadTests`, `ActionStatusTests`, `SliceKindTests`, `CloudRecordFactoryTests`, `KitFixtureTests`.

### Transport: scopes, errors and the local buffer (A4, C8)

- **`CloudKitTransport`** is the `CKSyncEngine` adapter behind `CloudSyncTransport`, and carries already-sealed records: `SecureTransport` sits above it (see End-to-end encryption). Engine events land in `TransportStore` (GRDB: an incoming event buffer whose local seqs are the consumers' change tokens, a pending-send queue, archived system fields, the engine state). `InMemoryCloudTransport` is the test and demo fake.
- **A fetched batch is never skipped.** CKSyncEngine counts a delivered batch as done, so a change token is saved only past a batch that reached the buffer. A batch (or poll page) is buffered in one store transaction — its events, system fields and deletions — so a failed write leaves nothing behind. When an engine batch fails to buffer (full disk, a suspended or closed store), the engine state is not saved until a `pull()`'s zone poll that started after the failure has buffered every zone up to date (the poll reads the lost records again by its own tokens), or until the next engine start, which resumes from the last good token. A poll page that fails to buffer keeps that zone's poll token, so the next pull reads it again; the other zones are still polled. Events of a stopped or replaced engine are dropped, so its late state update cannot save a token. A batch may arrive twice; consumers already take replays.
- **Scopes** (`CloudDatabaseScope`, spec §2.3). `private` — the hub, and a phone on the Mac's Apple ID; `shared(ownerName:)` — a phone on another Apple ID, which reaches the Mac's zones through accepted shares; another owner's zone is never ours. Only the hub role (`TransportRole.hub`) creates and deletes zones; a phone never does, in either scope (multi-hub spec §4.1). A store records its scope, and opening it under a different scope wipes it first.
- **Errors** (spec §9). `.limitExceeded` halves the batch (once per failure, even when it arrives both thrown and per record); a record rejected alone, or whose asset file is gone, is dropped from the queue and reported to the owner. `.requestRateLimited` / `.zoneBusy` wait out `Retry-After` (the transport keeps the start of a throttling stretch, for a "slowing down" notice after 60 s). `.quotaExceeded` pauses sends until `resume()` (`TransportEvent.quotaExceeded`). An expired change token re-fetches once. In the phone role a vanished hub zone (`.zoneNotFound`, `.userDeletedZone`, a zone-deleted event), in either scope, emits `TransportEvent.unlinked`, terminal for that transport; the phone never re-creates a hub's zone. In the hub role a deleted zone is re-registered so the pending rows re-create it. An account sign-out or switch wipes the store and relaunches the engine (`setAccountResetHandler`); in the hub role a server-deleted DataZone also fires the data-zone reset handler once.
- **Pulls** are single-flight: a `pull()` arriving meanwhile joins the running one, and fetch errors delivered while it awaits the engine are parked and handled once. `stop()` cancels and drops the engine; saves made meanwhile wait in the store.
- **Zone poll.** `CKSyncEngine.fetchChanges()` fetches only the zones a delivered push put in its unfetched-changes set (`State.zoneIDsWithUnfetchedServerChanges`, read-only); an explicit `FetchChangesOptions(scope: .zoneIDs(…))` only narrows that set, so without a push a manual fetch sends no request (seen live: a hub never read a linking phone's `device` record until its engine restarted). So after the engine fetch every `pull()` also polls each zone of its scope (`private`: this account's; `shared`: the owner's) with `CKDatabase.recordZoneChanges(inZoneWith:since:)` through the driver (`SyncEngineDriving.fetchZoneChanges`), following `moreComing` pages, with its own per-zone token in `TransportStore`'s `poll_tokens` (cleared by a wipe and a zone eviction). Pages take the engine's buffering path minus what the store already holds: a record whose change tag matches its archived system fields, and a deletion of a record without system fields. Errors: an expired poll token restarts that zone from the beginning on the next pull; a missing zone is quiet in the hub role (not created yet) and unlinks in the phone role, in either scope; throttling waits like any throttle; anything else is thrown. No poll after a failed engine fetch, while stopped, unlinked or throttled, or once the engine was replaced (an account reset). A record that fails to download inside a page is logged and skipped. The phone's push fetch (`fetchForPush`, see Fetching below) skips the poll; the phone's 60 s safety poll, pull to refresh and return to the foreground keep it.
- **Record types (E2E7, E2E15).** A record is saved as `WatchtowerEnvelope` (`CloudKitTransport.recordType`): `kind` and `modifiedAt` plain, the envelope in `encryptedValues["payload"]`, the sealed asset as `asset`. A payload-free signal is `WatchtowerSignal` (`signalRecordType`). The pre-E2E `WatchtowerRecord` type is ignored on fetch, logged once per type (`cloudRecord(from:zone:)`). A delete of a record the server never saw (`unknownItem`, e.g. a `sig-` signal) counts as success.
- **Creator.** `CloudRecord.origin.author` (`RecordOrigin`) is a fetched record's `creatorUserRecordID.recordName` (the owner's own records read `CKCurrentUserDefaultName`), kept in the buffer's `events.creator` column. It is never sent on a save; nil for a record this device built, in `InMemoryCloudTransport` unless a test sets it, and for an event buffered before the column existed. The hub's device gate reads it.
- **Assets.** `CloudRecord.assetFileURL` rides as a `CKAsset`, always a sealed file (`ChunkedAssetCipher`; its key is inside the record's envelope): a phone `recording_upload` in RelayZone, or an asset-backed slice record (a meeting transcript's `segments.json`) in DataZone. A rewrite with nil removes the asset. Fetched asset files are copied into the store's stash, because CloudKit's own files are temporary. The stash file is named by the hex SHA-256 of zone and record name (`TransportStore.stashFileName`), so a re-fetch overwrites and a server-supplied name such as `..` never becomes a path (target 149); an asset over `TransportStore.maximumStashBytes` (the phone's upload cap, sealed: `RecordingUploader.maximumSealedAssetBytes`), or whose size cannot be read, is not copied. Its event keeps CloudKit's temporary URL, so the hub answers an oversized upload with the too-large message only while that file still exists; once CloudKit purged it the hub reports the audio as missing ("did not reach your Mac") — a known v1 limit, since only a phone that bypasses its own uploader cap can send one.
- **Direct save and close.** `CloudKitTransport.saveDirectly(_:scope:hubID:)`, reached through `TransportFactory.sendDirectly` for a `HubRoute`, saves one record into a hub's zone outside any engine and store, as a compare-and-swap (`.ifServerRecordUnchanged`): a fresh record first (no change tag), and when the server refuses it (`serverRecordChanged`) once more over the server copy the refusal returned (its system fields); a second refusal is thrown, and a save cancelled while its first try ran never tries again. The phone's kept unlink farewell goes out this way (#143): it replaces only the copy it was refused for, so a farewell given up on at its cap whose request still reaches the server after a relink of the same Mac wrote this phone's `device` record is refused there instead of clobbering it (#261). (The Mac would not act on it anyway: a relink's new QR nonce salts new pairwise relay keys, so a record sealed for the old link does not open.) `TransportStore.close()` closes the store for good before its files are deleted (the phone's hub removal, #216): every later call throws, and closing again does nothing (`TransportStoreTests`).
- **Buffer retention.** `CompactingTransport.compactEvents(in:keepSince:)` drops events at or below a consumer's token: the phone's `ReplicaHydrator` compacts `.data` and its `RelayFeed` compacts `.relay` after each persisted token (best-effort, logged). Data-zone compaction also deletes the stash files of the compacted events, except a path a newer event still references, so a consumer copies an asset before it compacts past it. The hub never compacts `.relay`: its daily hygiene needs the full-zone scan, so it sweeps by age (`SweepingTransport.sweepEvents`, older than the cutoff **and** at or below the consumer token). Stash files no buffered event and no pending row references are swept at open, after a zone eviction and after a wipe.
- Tests: `CloudKitTransportErrorTests`, `CloudKitTransportScopeTests`, `CloudKitTransportPollTests`, `CloudKitTransportPushFetchTests`, `CloudKitTransportResetTests`, `CloudKitTransportStopTests`, `CloudKitTransportMappingTests`, `TransportStoreTests`, `TransportAssetTests`, `InMemoryCloudTransportTests`.

### Replica, outbox and relay feed (A3, A11)

- **`ReplicaStore`** is the phone's mirror of DataZone and holds **ciphertext** (replica format 2; a format-1 plaintext store is dropped and re-hydrated): `slice_records` (each row the hub's envelope with its wire name, `(epoch, seq)`, `needs_index`, and after indexing its plain `kind` and `plain_name`; opened and decoded on read, so a corrupt one is skipped and counted, never fails a batch), `data_seen` (the DataZone rollback guard), `relay_seen` (the relay rollback guard) and the phone's seq ceiling, `replica_meta` (the data and relay tokens, the alert watermark), the `pending_actions` overlay, the `phone_recordings` ledger with `phone_recording_marks`, and `slice_assets` (a record's sealed asset bytes, decrypted on read, or the reason it was unreadable; files over the sealed length of 20 MiB are refused unread). `apply` takes one data-zone batch in one transaction and refuses a token older than the stored one; it verifies every envelope's hub signature with the public key (so it runs while the phone is locked), refuses another hub's records and older versions, and keeps the rest unindexed until `indexPending()` opens them with the epoch keys (see The locked phone). Asset files are read before the write transaction. `resetSyncTokens()` is SPI (`@_spi(DemoTransport)`) for the demo transport only. `slice_kind_versions` (board #724) holds one change stamp per slice kind. Under E2E a stored version is readable only once indexed, so `indexPending` bumps the kind of every row it opens (once per kind per pass, in its write transaction; the hydrator indexes right after each apply, a locked phone at the unlock), and `apply` bumps only for a deletion (by the stored row's kind; a row still unindexed has none) and for a newer-format version of a row whose kind is known; a dropped stale batch bumps nothing. `ReplicaStore.keyRefusalCount` counts rows a list read skipped because their keys could not be read (locked, or an epoch's keys not here yet); `kindVersions(_:from:)` reads them (0 for a kind never written) and `kindVersionsRegion` / `pendingActionsRegion` / `phoneRecordingsRegions` are what an observation tracks. Like every replica table it is created with `CREATE TABLE IF NOT EXISTS` (the replica is not the Go goose database): an older replica starts with no stamps, so each kind reads 0 until its next write. The UI reads it through GRDB `ValueObservation` (`*(from: db)` variants for the fetch closures).
- **`ReplicaHydrator`** pulls DataZone into the replica: one cycle at a time (a caller arriving mid-cycle awaits it), `onRecordsApplied` for the records of known kinds a batch persisted.
- **`ActionOutbox`** is the phone's action producer: the action is sealed once at enqueue (`SecureTransport.seal`, p2h; a locked keychain throws before anything is sent), the transport saves that envelope (`saveSealed`), then a `pending` overlay row stores the same envelope, opened on read with the phone's own key (no plaintext action at rest; no phantom chip on a failed save). `sweepSilentPending` also prunes the relay rollback guard past 8 days. It refuses while no device id is set (`ActionOutboxError.notLinked`; a blank id counts as none). `applyEcho`: `received`/`held` mark the row (`echo_status`), `failed`/`expired`/`cancelled` flip it to failed with the echo's `reason` and `result`, `applied` removes it and tells the applied observer (once per removed row). `sweepSilentPending` fails rows the Mac never echoed within 24 h.
- **`RelayFeed`** is the phone's single relay consumer: it owns the relay token and routes `action` echoes to the outbox and `recording_upload` echoes to the uploader; a RelayZone `heartbeat` and `device` record are ignored. It reads through `SecureTransport`, which opens the hub's echoes under this phone's h2p key; a locked keychain throws `keysUnavailable`, so the token stays and the echoes replay after unlock. The token is persisted at batch end, so a throw replays the batch (routing is idempotent), and an undecodable payload is logged and left behind. The Mac reads as online while the DataZone heartbeat is under 35 min (2100 s) old (`heartbeatStaleAfter`; the Mac writes it every 15 min, board #724 owner decision Q2).
- Tests: `ReplicaTests`, `ReplicaResetTests`, `ReplicaSliceAssetTests`, `ReplicaHydratorTests`, `ActionOutboxTests`, `RelayFeedTests`, `RelayFeedRecordingUploadTests`.

### Link code, device grant and keybox (A5, E2E4)

- **`LinkPayload`** is the QR code (spec §2.3): `watchtower://link?d=<base64url(JSON)>`, unpadded canonical base64url, sorted keys; fields `v`, `container`, `hub_id`, `mac_name` (≤ 60), `owner_user`, a single-use 32-byte `nonce`, `iat`, `exp = iat + 600`, the two share URLs (absent when none), and the hub's public keys `hub_sig` and `hub_kx` (base64url of 32 bytes; a key of another length or all zero, a small-order point, is refused). `v` is 3 since the E2E build (2 was the multi-hub build, multi-hub spec §3.4) and is checked first, so a newer code reads as "Update Watchtower on this iPhone" (`.newerVersion`) and an older one (v2 without keys, or v1) as "Update Watchtower on this Mac" (`.olderVersion`, §6.7); a code for another container is refused. The codec only encodes and decodes: the expiry and nonce checks belong to the hub (`link.Center`, see Hub → Linking) and the phone's link flow (A12, [phone half](#onboarding-and-linking-phone-half-a12)).
- **`DeviceGrant`** is the hub's `device_grant-<device_id>` slice: the phone's name, `link_refused` (`used_code`, `expired_code`, `unknown_code`, `not_confirmed`, or an unknown value, still a refusal), `typing_allowed` (default false), `start_sessions_allowed` (the phone's own toggle as the hub stored it; an older phone reads it as its start permission and gets the hub's refusal, whose message says where to allow it), `start_sessions_granted` (#565, the hub's `mayStartSessions`, always written by a newer hub; the Kit's `DeviceGrant.mayStartSessions` falls back to `start_sessions_allowed` for an older hub's record), `awaiting_confirmation` (the hub read the hello and waits for the owner) and `revoked` (removed on the Mac, D9); the last two are absent otherwise.
- **`Keybox`** (E2E4) is what travels: `{grant, keys?}`, sealed to the phone (`keybox-<device_id>`). `KeyboxKeys`: `epoch`, `data_key`, `alert_key`, `meta_key` and, after a rotation, `previous_epoch`/`previous_data_key`/`previous_alert_key` (base64url of 32 bytes). The replica's keybox reader (`ReplicaStore.keybox(deviceID:from:)`) opens the whole keybox for the link flow; `device_grant` readers get the `grant` JSON as the payload, unchanged.
- **`DeviceHello`** (E2E4): `{device, signing_key, agreement_key}`, record `hello-<device_id>`, sealed to `hub_kx`.
- Tests: `LinkPayloadTests` (v2 fixtures rewritten to v3).

### Workbench slice mirrors and action params (B1)

- **Kinds.** `SliceKind` gains `workbench`, `workbench_target`, `workbench_comment`, `terminal_session`, `owner_ask`, `session_report`, `session_timeline` and `session_chat` (design §4.2–§4.9; chat: the session chat spec), and `ask_alert` (§4.7; the hub's B4 publishes it, its Kit mirror comes with A13). The phone decodes each record's payload with its `SliceMirror` in `WatchtowerKit/Models` (`Workbench`, `WorkbenchTarget`, `WorkbenchComment`, `TerminalSessionState`, `OwnerAsk`, `SessionReport`, `SessionTimeline`, `SessionChat`) through `RelayCoder` — snake_case keys, Unix-second dates, a nil optional is an absent key, unknown keys are ignored.
- **Enum-like fields** (state kind and tone, target status and priority, ask kind/status/withdrawn reason, verdict, check state, milestone kind, start mode) are `OpenWireValue`s: a value from a newer Mac decodes, keeps its raw string and reads `isKnown == false`.
- **Clipping on the wire.** `<field>_clipped` and `<list>_more` are absent unless the hub cut something, so the mirrors keep them optional (`Bool?`, `Int?`).
- **`session_report`** is the CLI's report as Go writes it (`internal/sessionreport.Report`): datetimes stay Go's UTC strings and every key may be absent, as in Core's `SessionReport`; the hub adds only `<list>_more`, `items_more` and `phases_clipped`. The other kinds carry dates as `Date`.
- **`session_timeline`** payload is `{session_id?, milestones, milestones_more?}`: `session_id` repeats the record id and may be absent. An ask's `withdrawn_reason` is absent (or `""`, read as nil) unless the ask is withdrawn.
- **`OwnerAskAnswer`** (Kit) encodes byte for byte like Core's and Go's (`internal/asks/testdata/answers`); an ask's `payload` resolves missing question and check item ids to their 1-based position, as Core and Go do.
- **Action params.** `ActionKind` gains the twelve §5.2 kinds. Each has a typed `ActionParams` struct whose `wireParams()` is the request's `params` object. Because `ask_answer` carries an object and `session_start` carries bools, `JSONValue` (WatchtowerSync) gains `.bool`, `.array` and `.object`; a row never produces them, and `databaseValue` stores them as 0/1 and JSON text.
- **Fixtures.** `WatchtowerKit/Tests/Fixtures/workbench/*.json` are the frozen payloads (`WorkbenchMirrorFixtureTests`); the hub's projection tests pin their encoder against the same files.

### App shell (A11)

- **Boot.** `WatchtowerMobileApp` builds one `AppRoot` for the app's lifetime, which owns the current `AppEnvironment` and the link flow (A12) (or shows `BootFailureView` when the boot itself fails — the Keychain, the registry; a signed build without its app group container refuses to boot rather than keep the replica elsewhere; a hub whose replica cannot open is unopened instead, above). The replica lives in the app group `group.com.aiwatchtowers.watchtower.mobile`, so the notification extensions can read it.
- **Transport switch.** A build that carries the iCloud entitlement (signed device or TestFlight) runs `CloudKitTransport` and starts empty; anything else (unsigned simulator and CI builds) runs `InMemoryCloudTransport` with `DemoSeed`. The demo pushes records through the transport as the hub would publish them, so hydration and every decode path run end to end; record names are fixed, so a re-seed upserts. **Demo tour in the signed build** (#174, App Review has no Mac): Welcome's **Try the Demo** (`EnvironmentValues.startDemoTour`, set by `ReadyRootView` over a live root only) runs `DemoTour.start(over:)`, which waits for the last tour's teardown (both use one directory and suite) and builds `AppRoot.tour()` — the same two demo Macs, every file in `Caches/demo-tour`, every setting in the `demo-tour` defaults suite, no app badge, no battery counts — shown in place of the live root under a `DemoTourBanner`. **Exit Demo** (`DemoTour.exit`) takes it off screen at once, then `endTour()` stops a demo recording, shuts the sessions down, closes their databases and removes the directory and the suite; a tour cut short by a kill is cleared by the next live launch (`clearTourLeftovers`) or tour. A `watchtower://link` URL during the tour ends it and goes to the live root (`AppRoot.forwardsLinks`); the demo offers no **Add Mac** (`MacsView.offersAdd`: a scan would run the real link flow against the owner's iCloud). A tour that cannot start shows an alert. The live root, `AppDelegate.root` and push registration are untouched meanwhile. `DemoSeed`, `DemoHubKeys` and `hubTransport` therefore ship in Release; the fixed demo keys still run only on the demo kind over `InMemoryCloudTransport` (`HubSession`'s precondition). The app and the NotifyService extension (which links WatchtowerKit) each carry a `PrivacyInfo.xcprivacy`; keep the two in step. Tests: `DemoTourTests`.
- **Fetching** (board #724, owner decision Q1: the phone fetches when something changed). Every fetch reaches CloudKit once (`RemoteFetchDepth`), then hydrates DataZone and reads RelayZone from what that buffered (the hydrator and the feed never pull on their own; an `applied` echo's re-hydrate is local). Two depths: **full** = `CloudKitTransport.pull()` (engine fetch plus the forced zone poll) for the safety poll, pull to refresh, the return to the foreground, the launch and the link flow; **push** = `CloudKitTransport.fetchForPush(since:grace:pollOnFallback:)`. CKSyncEngine keeps `automaticallySync` on (both roles: it also sends, and the Mac is unchanged) and fetches on a push by itself, so a push waits for that own run (tracked from `willFetchChanges`/`didFetchChanges`; a manual fetch's events are not a run) — a run begun at or after the push covers it, a running one is awaited for at most `max(grace, 30 s)` (`engineRunEndWait`; a run that never reports its end stalls nothing) — and fetches through the engine itself only when no run begins within 2 s (`pushEngineGrace`) of the push or the end wait runs out. That fallback adds the forced zone poll for a foreground push (the engine fetches only the zones a delivered push named, so without the poll it may send no request) and stays light (no poll) in the background. A `pull()` never waits on the engine: one arriving while a push fetch still waits takes the push over (the push's outcome is the pull's); it waits only for a push's own running fallback fetch (one manual fetch at a time). A push waiting on the engine's run returns at once, without a request, when the link ends, the account resets or the transport stops; a push under a server-requested wait or after the unlink sends nothing and throws nothing. Each own run's end is reported (`setEngineFetchedHandler`) and, while the app is active, what it buffered is applied at once (local reads only; skipped while a fetch still waits on CloudKit, since that fetch hydrates right after — a skipped apply is owed, and if that fetch fails before hydrating, the last fetch off CloudKit runs it). **Safety poll** (per `HubSession`, intervals in `SessionCadence`; roles in "Several Macs (multi-hub F2)"): one `.loop` fetch every 60 s for the session on screen (`safetyPollInterval`) on every tab; it pauses whenever the scene is not active (inactive — Control Center, the app switcher — as well as the background; the recorder's audio background mode does not keep it running), restarts from each foreground push fetch, and the launch fetch is not followed by an immediate cycle. **Return to the foreground:** an immediate full fetch unless the last successful fetch is under 5 s old (`foregroundRefetchAfter`); then only a local apply of what the engine buffered meanwhile (no network). **Active state at launch:** `AppEnvironment.isActive` is seeded from `applicationState == .active` when the environment is built (`startsActive`; tests default to active), so a launch into the background (a silent push, no scene) never starts the safety poll, applies no engine run and restarts no poll after a push; the scene's first `.active` phase sets it. **Silent push** (`content-available`, `AppDelegate` → `PushCompletion.serve` → `AppEnvironment.handlePush(at:inForeground:)`, foreground = `applicationState == .active`; the arrival is stamped in the delegate before any hop and is the light fetch's `since`): a fetch begun after the push serves it. A push that arrives before the boot has started the transport waits for the launch fetch, which serves it; the launch fetch then takes the push's light depth (no forced zone poll) when the app is not active, and the first activation afterwards fetches in full whatever the last fetch's age. A push routes by database scope (`AppEnvironment.handlePush(scope:)`): a session of another database only notes it (`HubSession.noteForeignPush`), and if that note arrived before its launch fetch began, a launch into the background skips that session's launch fetch altogether (no engine fetch, no zone poll; #219), leaving the full fetch to the first activation. Foreground and background alike it is fetched at once (leading edge); a push arriving while a fetch runs gets one follow-up fetch after it, shared by every push meanwhile (so a burst costs at most two fetches). Only a foreground push restarts the safety poll; a background one starts no poll. Every push's completion handler gets the outcome of the fetch that served it: `.newData` when the replica or the feed took something in, `.noData`, `.failed` when the data fetch failed — or, if that fetch has not ended 25 s after the push (`PushCompletion.deadline`, inside iOS's ~30 s), the deadline's `.noData` (the push's own fetch has not ended, so nothing says it failed; an unrelated earlier failure is not reported); exactly one of the two completes it, and a fetch past the deadline keeps going. At boot, after the first fetch: the 24 h silent-pending sweep, launch recovery of cut-short captures, then — only when the app is active — the upload pass with its relaunch retry; a launch into the background uploads nothing, and the first activation runs the pass (see Phone recorder and uploader). A cold launch runs one pass: the retry gate's opening runs one only after the boot, whose own pass covers a gate open when it reaches it. CloudKit fetch failures and replica hydrate failures log apart, with the trigger and depth. Tests: `FetchCadenceWiringTests`, `CloudKitTransportPushFetchTests` (Kit).

### Onboarding and linking, phone half (A12, E2E16)

- **Root.** `AppRoot` (main actor, the app's lifetime) owns the `AppEnvironment` (one `HubSession` per linked Mac, kept for good), the `HubRegistry` and `LinkingViewModel`, and is the flow's `LinkHost`. There is no environment restart any more (F2 removed `Restarter` and `retireEnvironment`): a scan builds the scanned hub's session in its own directories, a link adds its row and puts it on screen, an unlink or a removal takes one hub away, a Mac's removal freezes one, an account change removes all ("Several Macs (multi-hub F2)" below). A wipe never takes the owner's audio silently (board #63): before a session goes, a stop already saving is waited for and a running capture is stopped and saved (`PhoneRecorderController.stopForWipe`); after its shutdown (so its own launch recovery has ended) captures still `recording` are finalized from their files, and every recording whose audio is on the phone and that the Mac has not acknowledged (`waiting`, `uploading`, or a failure that offers Retry) is **held for the hub it was recorded for** (`HubSession.handOverRecordings`, `RecordingHold`): its audio moves to the recordings folder's hidden `.held` folder with a JSON manifest (hub id, the Mac's name from its last heartbeat, the row's fields and marks), out of the replica and out of the launch sweep's reach (it skips hidden files), so it survives a failed removal and a kill. A session adopts, at boot and before its sweep, only the held recordings of its own hub (`adoptHeld`: `waiting` rows again, sent once a device id is set), so **a recording never reaches another owner's Mac**; the rest are listed in Recordings as "Waiting for <Mac> — link it again to send" (`heldRecordings`, `RecordingEntryState.heldForMac`). **On an iCloud account change nothing is carried** (`keepRecordings: false`): the recordings, held ones included, were made for the old account's Mac and are reported "Not sent". A row over the size cap, or one whose audio is gone, is reported "Not sent". A ledger or manifest that cannot be read moves the remaining audio to `.held/unreadable` (kept, never sent) and the removal says so (`LocalWipe.problem`, `LinkNotice.recordingsProblem`); a held recording that cannot be adopted stays held for the next boot and is reported the same way. A removal that stopped a capture shows "The link to <Mac> ended during a recording. It's saved on this iPhone and goes to <Mac> after you link it again" (`LinkNotice.recordingKept`, naming the Mac when one hub's link ended — an account change, which ends several, keeps "your Mac" — with any "Not sent" count), in place of the removal or "Not sent" notice. Each session seals every write and opens its replica with this phone's keys for its own hub ("E2E on several Macs" below). `AppDelegate.root` (weak) reaches the environment for silent pushes. The demo root keeps its environment, is linked as `DemoSeed.device`, never onboards and ignores link URLs. `AppRootView` shows `OnboardingView` while there is no hub on screen (a live build with no row, or the last one just removed), else the tabs with the flow in a full-screen cover while a phase runs and the link notice in a bar above them.
- **`LinkStore`** (`UserDefaults`, plain JSON): the link (`LinkRecord`: `hub_id`, Mac name, `DeviceScope`, owner name, this phone's `user_record_name`, the nonce, the two share URLs in `shared` scope) and a `PendingLink` (the link, the wait's deadline, the grant the replica held before the write). Since F2 the saved links live in the registry (one row per Mac); `LinkStore` keeps the pending link, and its legacy `link.record` is only what `HubBoot.migrateF1` reads. The link's hub id is validated before any path is made from it (`HubPaths.isValidHubID`). `PendingLink` also keeps the scanned code's `iat` (the Mac's clock), which binds the answer to this scan. `DeviceIdentity`: the device id is the key-derived id (D7) read from `PhoneKeyStore.deviceID()` (the non-secret `deviceid` Keychain item, readable while locked; nil until the link flow first creates the device keys); name ≤ 60 from `UIDevice`, model, marketing version. A launch outside the link flow never creates an identity (F14). Before the first unlock since a restart (a push launch) the read throws `KeyStoreError.locked` and the boot becomes `Boot.waitingForUnlock`: "Unlock your iPhone to continue", booting again on `protectedDataDidBecomeAvailable` and every 2 s while protected data is available, until a boot gets past the lock. Main's #62 random device id (Keychain item plus `device.id` default) is deleted at every launch (`LegacyDeviceID.remove`). At launch, before anything else, every saved link (registry row, an F1 link moved in by `HubBoot.migrateF1` included) or pending link without a hub signing key (made before E2E) is dropped — the row's hub removed with its recordings held, nothing sealed for it — with "Watchtower now encrypts your data. Scan the code on your Mac again." (`dropUnencryptedLinks`, `LinkNotice.encryptionReScan`); other hubs are untouched.
- **The scan** (`LinkingViewModel.open`, spec §2.3; `ScanView`'s AVFoundation QR reader and the `watchtower://link` URL from the Camera app run the same call). Step 1: `LinkPayload.parse` (`v` above 3 → "Update Watchtower on this iPhone"; `v` below 3 → "Update Watchtower on this Mac"; any other parse failure, and a hub id that is not a UUID or keys or a nonce that do not decode (`ScannedHubKeys`) → "This code can't be used…"); expired only when `exp < now − 120 s` (`expiryGrace`, so a phone clock ahead of the Mac's does not refuse — the Mac's own check decides). Already linked to this hub with a linked grant in the replica → "Linked to <Mac>" with nothing written; a re-scan of a linked hub without one (or of a hub the Mac removed) is a re-pair: that hub's link ends first (`endLink`: its row, session, files and keys; its "Not sent" count shown), other hubs untouched, so a refused or unanswered re-pair leaves no row whose keys open nothing (E2E16 I-1; this replaces F2's "a failed rescan keeps the linked Mac", which the scan's key replacement cannot honour). Step 2: `accountStatus` not `.available` → "Sign in to iCloud on this iPhone to use Watchtower". Step 3 (R2): `owner_user` equal to the phone's `userRecordID().recordName` → `private`, share URLs ignored and never accepted; different → both URLs fetched and accepted (`CloudKitLinkAccess`: `CKFetchShareMetadataOperation`, then one `CKAcceptSharesOperation`; before the accept, `CloudKitLinkAccess.checkShares` requires exactly the zone-wide shares of the code's `hub_id` zones, each owned by `owner_user` — target 168), a missing URL, other shares or any failure → "This Mac can't share with another Apple ID right now…", then `shared(ownerName: owner_user)`. A code of another hub links beside the existing ones (no prompt: F2 dropped the switch prompt); with `HubRegistry.limit` (4) Macs linked a new hub is refused before anything is accepted or written (`LinkFailure.tooManyMacs`), and so is a `hub_id` that is not a plain name (`HubPaths.isValidHubID`). Step 4: the device keys are created if absent and the scan's `HubLinkKeys` stored; `prepare(route:hubID:fresh:)` (fresh) with the code's `hub_id` (builds the hub's session on its own empty files; a session of that hub still running is removed first with its recordings held, so an old link's rollback marks, outbox and sealed recordings go, and the new session's seqs start above the ceiling such a removal left in this process), the baseline keybox fetched, the `PendingLink` saved, then the sealed `hello-<device_id>` (`DeviceHello`: the `device` payload with `link_nonce`, `scope`, `user_record_name` and the Settings choices, plus the public keys) saved in that database. Step 5: the four-digit code (`linkCode`, `KeyDerivation.sas`) is shown: "Check that your Mac shows **7342**, then click Link on the Mac." Every 2 s (`grantPollInterval`) until the code's `exp` + 120 s (`expiryGrace`; at most a full code lifetime plus the grace from now), one fetch and a read of this phone's keybox (`LinkHost.fetchKeybox`); a keybox of the code's hub whose grant differs from the baseline answers — `awaiting_confirmation` → step 2 reads "Your Mac sees this iPhone"; any `link_refused` (`not_confirmed` included) → "This code can't be used — Show a new code on the Mac"; `linked` with keys and `linked_at` ≥ the code's `iat` → the keys join the stored ones, the link is saved in the registry (`LinkHost.linked`: the hub's row, the unlinked choices adopted, the held recordings adopted, `setLinkedDevice`, the hub put on screen; a fifth hub that raced past the scan's check is refused and its keys go), "Linked to <Mac>" (`linked` without keys keeps waiting); none → "Your Mac didn't answer — Keep Settings → Mobile open on the Mac and scan again". A scan that ends without a link removes the keys it stored and the candidate session and files (a hub with no row). A hello whose code the Mac does not know gets no answer at all (F4), so that scan ends on the wait timeout too. Step 6: **Continue** asks for notification permission and opens Now. A kill during the wait leaves the `PendingLink`: the relaunch (`resumePendingLink`) recomputes the code from the stored keys and waits for what is left of the wait in the pending scope, and never shows the phone as linked before a keybox; with the keys locked the pending link is kept for the next launch. A `PendingLink` saved before its baseline was read (`baselineCaptured` false, also for one an older build saved) wrote nothing to the Mac: the relaunch offers to scan again at once instead of taking an earlier answer in the replica (a refusal of another code) as this scan's. A session that cannot be built, or a hello the transport's store cannot queue, is "Couldn't set up sync on this iPhone" (`LinkFailure.local`), not "Couldn't reach iCloud". A code arriving while a link runs is ignored. The failure screen shows each failure's title with its hint under it (design pass O3); the waiting screen shows the three link steps, the code to compare and, after 20 s, "Keep Settings → Mobile open on the Mac." (O2). A failure to read the device keys is "This iPhone's Watchtower keys can't be read. Unlock it and scan again."
- **Several Macs.** The single-link bridge (F1: one transport on the linked hub's zones, restarted on a scope or hub change) is replaced by the registry and one `HubSession` per Mac; see "Several Macs (multi-hub F2)" below.
- **Unlink** (Settings → Macs, live builds only; per Mac, see "Several Macs (multi-hub F2)"): `unlinkHub` takes the hub's registry row before its first await (a removal or account signal arriving meanwhile — leaving the shares is what makes the Mac's zones vanish — finds no row and is ignored), then the `device` record with `unlinked: true` is sealed and queued through the hub's own session transport (the one holding the record's server state, `HubSession.saveSealing`) and is waited for until the sealed (wire-named) record has left the send queue (`FarewellDelivery`, `TransportStore.isPending`, `sendNow()` again while it waits) with a hard 10 s cap that a hung send cannot exceed. **A farewell still queued at the cap is kept** (#143): its sealed record goes into the registry's `pending_farewells` table (`PendingFarewell`: hub, route, the link's iCloud account, the wire record, when) before the wait — a kill during the wait keeps it too — and is dropped once it left the queue; the table outlives the hub's replica and files, and the removal goes on. Each time the app becomes active (the scene's `.active`, a foreground cold launch included; never a background or push launch), `AppRoot.becameActive` waits for the launch's account check and runs `LinkingViewModel.retryFarewells` inside background work (`hub-farewells`), one retry at a time (a second activation joins it). Every kept farewell is sent again (`LinkHost.resendFarewell` → `FarewellDelivery.resend` → `AppRoot.resendDirectly`: one direct save of the sealed record into the hub's zone, `TransportFactory.sendDirectly`, a compare-and-swap over the server's copy (see **Direct save and close**) — no engine, the deleted hub keys not needed — raced against the same 10 s cap; a failure or the cap keeps it). One that goes out stops being kept (only that record: a later unlink's farewell of the hub stays). One older than 7 days (`farewellLifetime`) is dropped unsent; one of another iCloud account, or of a hub linked again or being linked (`linked` drops it, a scan of the hub waits for a resend in flight), is dropped unsent too. Each farewell is decided on the state read at its turn (the registry's kept record, the links, the pending link, a code being linked) and again after its resend: a link of its hub begun while the resend was out keeps the shares, and a farewell a relink dropped meanwhile is not sent. Nothing is retried while a link flow is busy. The session's outbox items still pending, plus recordings whose audio is gone, are counted ("Not sent: N items were still waiting for your Mac"; recordings with their audio are held for their hub, above); then the session is shut down and its files deleted. In `shared` scope the zone-wide share records (`CKRecordNameZoneWideShare`) of the hub's two zones (`DataZone-<hub_id>`, `RelayZone-<hub_id>` owned by the link's owner, `CloudKitLinkAccess.leave(route:hubID:)` through `HubZones`) are deleted from the shared database after the removal — unless the farewell was kept (`LocalWipe.farewellKept`): the kept record still needs the zones, so the shares are left once it goes out or expires. Removing the hub on screen puts the next Mac on screen; the last one leaves Welcome. The hub's keys are deleted from the Keychain after the removal (`removeHubLink`, after the `unlinked` record was sealed with them); Forget and an account change delete a hub's keys too, while the Mac's removal (a freeze) keeps them so the frozen replica stays readable.
- **The link's events** (spec §9). `TransportEvent.unlinked` (`HubSession.onLinkSignal`, wired per session by `AppRoot` before the engine starts) → `removedByMac(hubID)`: the hub is frozen (below), "<Mac> removed this phone". The Mac's Remove also deletes the phone's `device_grant` (`link.Center.Keyboxes` never caps a linked phone's grant: only refusals fill the room left under 20), and that is the only removal signal a same-Apple-ID phone gets (its zones are the Mac's own and never vanish, #64). A wrongful wipe loses data, so after each successful fetch (`onFetched`) `AppRoot` reads the heartbeat and the keybox of the device id the link was made with (`LinkRecord.deviceID`, never the Keychain's current id; `ReplicaStore.keybox(deviceID:from:)`, opened with this phone's key) in one snapshot, has the keybox's epoch keys the Keychain lacks merged (`reconcileKeyboxKeys(hubID:)`, final review Phone I-1), and `LinkingViewModel.evaluate(grant:heartbeat:)` reads a removal only when all hold: the link kept its device id and its grant's `linked_at` (`LinkRecord.linkedAt`; an older link never reads one); no scan, unlink or pending link runs; the linked hub's heartbeat is there and newer than `linked_at`; and there is no linked grant for that id (absent, `linked: false` or `revoked`) on two looks at least 30 s apart (`removalConfirmAfter`) with none in between — the first look is kept on the hub's registry row (`HubRow.grantMissingSince`) across a relaunch, and a linked grant of the linked device and hub clears it in any fetch, before and whatever the heartbeat, busy and pending conditions (those gate only the missing-grant path), so a stale first look never counts as the second. A keybox stored but unreadable (a newer Mac's format, an envelope that does not open, keys locked) is never judged — unreadable is not absent — and its warning is logged once per hub until a readable one comes. A keybox indexed after the link (`keyboxChanged(hubID:)`, also from the unlock indexing) adds newer epoch keys; one that reads `revoked` is that Mac removing this phone (D9): the hub freezes, in either scope; a phone that missed it is told by the keybox's absence (#64). Then it is `removedByMac(hubID)`, whose notice carries what was left unsent. A shared phone whose participant removal failed is told the same way. The transport's account reset (any hub's) → the phone's `userRecordName` compared with the links': another account removes every hub and shows Welcome; a sign-out (or a failed check) keeps the replicas; the same check runs at launch. After each successful fetch (`onFetched`, wired per session) the Mac's heartbeat is noted on its registry row (flavor, time), and for the hub on screen no heartbeat for 24 h reads "<Mac> hasn't synced for a day — if it changed iCloud account, link again" (`LinkNotice.stale`, naming that Mac). A switch re-evaluates it for the hub it puts on screen (`AppEnvironment.onActivate` → `LinkingViewModel.activated`, from that session's last heartbeat; none read yet clears it), so one Mac's stale notice never shows over another. A removal with nothing to report (no "Not sent", no kept recording, no problem) leaves a stale notice as it is while another hub is on screen — the activation of the hub that took the screen, or the hub still on screen, set it — and clears it when no hub is left on screen; any other notice is cleared (#222). A different `hub_id` in a hub's own zone is not a case any more: each hub has its own replica (F1's "Watchtower moved to <mac_name>" notice is gone).
- **Unverified.** The `shared` scope (another Apple ID: share accept, leaving the shares, the account switch under it) runs only against fakes; nothing of it has run on a device yet. The same-Apple-ID path follows S0 (d).
- **Known limits.** The phone takes a keybox that differs from the one the replica held before the hello as the answer, a waiting one only when its `link_code_tag` names this scan's code (an older hub that sends none shows no code: fails closed), and a `linked` one only when `linked_at` ≥ the code's `iat` (a binding by time on the Mac's clock); an identical answer to a second scan (the same grant, unchanged `decided_at`) reads as no answer; a refusal carries its own time as `decided_at`, so a repeated refusal is a new answer. A removal during a capture of that hub ends the capture (stopped, saved and held, above). Audio in `.held/unreadable` is never sent; Recordings lists it to share or delete. A held recording of a hub this phone never links again waits until the owner shares or deletes it (Recordings). A rescan's session reset (`prepare`) logs a recording problem but shows no notice. An unlinked live phone runs no session at all (Welcome). A re-scan of a linked Mac ends that Mac's link (a re-pair; the Mac is not told) whenever the replica's keybox does not read as linked: absent, unlinked or revoked, and also unreadable (a newer Mac's format, an envelope that does not open, a read error) — on a re-scan an unreadable keybox counts as not granted, unlike the removal check, which never judges one. A fetch failure alone does not end it: the scan reads the keybox the replica already holds. The old link ends before the share accept, so a `shared` re-pair whose share accept fails leaves no link to that Mac. The seq floor a removal leaves is kept in memory only: a relaunch between an unlink and the next scan of that Mac restarts the phone's seqs, which the hub absorbs at the re-link (`link.Center.Confirm`).

### Several Macs (multi-hub F2)

One phone links up to `HubRegistry.limit` = 4 Macs (multi-hub spec §5–§7, plan `docs/superpowers/plans/2026-10-13-mobile-multi-hub-f2-phone.md`). Each Mac is its own `HubSession`; nothing is shared between hubs but the app-wide parts and the recordings hold.

- **Registry and paths.** `HubRegistry` (`Sources/App/Hubs/`, GRDB, `hubs.sqlite` in the app's own Application Support, *outside* the app group — a lock on an app-group file at suspension gets the app killed, 0xdead10cc, #232): one `HubRow` per Mac (`LinkRecord` as JSON, flavor, `sort_order`, state `linked`/`unlinked_by_mac`, `grant_missing_since`, last heartbeat, `linked_on`) plus the active hub id; `upsert` refuses a fifth hub (`HubRegistryError.full`), `remove`/`move` renumber. `HubPaths` per hub id: replica `<group>/hubs/<hub_id>/replica.sqlite` (in the app group so the notification extensions may read it; they do not yet), transport store `<appSupport>/hubs/<hub_id>/cloudkit-transport.sqlite`, audio `phone-recordings/hubs/<hub_id>/`; the hold `phone-recordings/.held` is shared across hubs behind `HoldGate`. A hub id is a path component, so `HubPaths.isValidHubID` (non-empty, no `/`, `\`, NUL, no leading `.`) gates every path and a removal's recursive delete. `HubPaths.prepare` creates the three hub directories class C (D8: ciphertext the background reaches after the first unlock). `HubSessionFactory.live(paths:keys:transports:)` (`transports` defaults to `.cloudKit`) builds a session (phone-role `CloudKitTransport` on the hub's own `TransportStore`, opened by `AppEnvironment.liveTransportStore`, which also protects its stash; hub replica, hub recordings folder, the shared hold; this phone's keys for the hub).
- **`HubSession` and `AppEnvironment`.** `HubSession` (`Sources/App/Hubs/`) is what `AppEnvironment` was in F1: the replica, hydrator, outbox and relay feed over one transport, the observed slices, the recorder and uploader, `DeviceSettings`, the fetch machinery (fetch depths, push follow-up, `PushCompletion`) and the safety poll. `AppEnvironment` now holds the sessions by hub id in the registry's order and the app-wide parts (navigation, recaps seen, the badge); the views read the per-hub API forwarded to the active session. `AppEnvironment.live` builds one session per registry row, the registry's active hub on screen (else the first), and none when there are no rows; a row the Mac removed is built stopped and frozen. Tests build `AppEnvironment.single(_:defaults:)`.
- **E2E on several Macs** (mobile E2E plan, "Ordering with the multi-hub work"). One device identity (`PhoneKeyStore.identity()`, the key-derived device id) for every hub; keys per hub under its hub id (`PhoneKeyStore.hubLink(hubID)`, the `CachingPhoneKeyStore` over the Keychain). Each `HubSession` builds its own sealed stack for its `hub_id` (`PhoneKeys(store:hubID:)`): an `EnvelopeReplicaOpener` replica, a `PhoneKeyProvider` `SecureTransport` for the outbox, the uploader, `DeviceSettings`, the relay feed and the link flow, its own seq ceiling in its own replica (F29; `raiseSeqFloor` carries a removed session's ceiling to a rebuilt one of the same hub), and its own unlock observer and keybox signal (`onKeyboxChanged`, `onKeysAvailable`), which `AppRoot` wires to `LinkingViewModel.keyboxChanged(hubID:)` and `reconcileKeyboxKeys(hubID:)`. A session whose hub id is not a UUID or with no device id yet runs the key-less wiring (nothing sealed, every batch refused). A session takes only its own hub's keys: `PhoneKeys` of another hub throw `HubSessionError.keysOfAnotherHub` at build (the demo's Macs share the demo pairing on purpose). **A hub without stored link keys never sends** (port review I-1): its session (`hubLink`, from the hub's public signing key copy) wipes its transport store's queue at init and never starts its CloudKit engine (`startsEngine`), and `AppEnvironment.live` builds such a row stopped, before its boot — a phone upgrading from a build before E2E may hold a bound per-hub store whose unacknowledged saves are plaintext (an action, a `device` record, a recording upload with its plain audio). The launch runs `dropUnencryptedLinks` first (before the orphan pass), which removes the hub with the re-scan notice. A Keychain that cannot say (a read error) starts no engine and wipes nothing for that launch. Unlink, Forget and an account change delete only that hub's keys; a freeze keeps them. The demo's two Macs both run on the demo pairing (`DemoSeed.phoneKeys`), each seeded through the demo hub with its own seq ceiling key (`demo.hubSeqCeiling[.<hub_id>]`). The ask-alert subscription per hub/scope (D14) belongs to A13 with F2's per-hub notifications.
- **One hub's failure stays in that hub** (spec §6.3). A row whose session cannot be built at launch (its replica or transport store will not open, `prepare` fails) is logged and gets no session: it goes into `AppEnvironment.unopenedHubIDs`, the other hubs boot, and the first row that has a session goes on screen (`activate` refuses a hub with no session). The switcher lists the row with "Couldn't open this Mac's data on this iPhone" (`HubListModel.unopenedProblem`), not selectable; Settings → Macs offers it **Forget** (`MacsModel.action`), which removes its row, its Settings keys and its Keychain keys, with no farewell (it has no transport); a linked one in `shared` scope still leaves the shares (`endLink`), since no farewell can reach its Mac and nothing else would ever remove this phone's seat in its zones. Nothing on disk is deleted, so its directories are an orphan for the next launch's pass, which builds a session, hands its recordings to the hold and keeps the files if that fails. A row that does not decode is skipped and logged by `HubRegistry.rows()` and is unopened too (#222): `HubRegistry.unreadableHubIDs()` lists it, `LinkingViewModel.unreadableHubIDs` caches it beside `links`, and the switcher and Settings → Macs show it as "Unknown Mac" with "Couldn't read this Mac's link on this iPhone" and **Forget** (`HubListModel.items(unreadable:)`), at its own place in the registry's order (the places the readable rows' `sort_order` leaves free), so a drag in Settings → Macs writes the order it shows (`MacsModel.registryMove`), which removes the row and its Keychain keys only (its scope is unknown: no share is touched); it counts toward the limit (`canAddMac`, the Settings Macs count). `HubBoot` checks the files on disk against `hubIDs()`, every row readable or not, so its files are never taken for an orphan's. **No hub on screen while the registry still holds Macs** (every row failed or is unreadable at launch, or the last Mac that opened was unlinked) never shows Welcome and never fails the boot (#222): `AppRoot.showsUnopenedMacs` puts `UnopenedMacsView` in Welcome's place (while the link flow is idle) — the Macs with their problem and **Forget**, **Try Again** (`AppRoot.reopenHubs`: each unopened readable row is built again as at launch, one that opens is wired and goes on screen, then `dropUnencryptedLinks` runs as at launch) and **Add Mac**; forgetting the last one leaves Welcome.
- **The forwarders are total.** When the last hub goes (unlink, Forget, an account change), `remove` keeps the removed active session (already shut down) as `retained` until another hub activates, and `activeSession` reads the active session, else that one, else the first session (a link being made): a view still on screen while the root turns to Welcome — the REC bar, the recorder cover, the tab badge — reads it instead of trapping. Only an environment that never held a session traps, and the root never shows the tabs for it. Once Welcome (or the unopened Macs) has replaced the tabs, the root lets go of the kept session (`releaseRetained`, on the onboarding branch's appear), so the removed hub's replica closes then, not at the next activation (#222).
- **Roles and cadence** (`SessionRole`, `SessionCadence`). The session on screen is `active`, every other `inactive` (`applyRoles` on each switch). Safety poll: active 60 s; inactive 300 s, back to 60 s while it has unsent actions or uploads (so its echoes return). Foreground return: the active session fetches at once unless its last success is under 5 s old; an inactive one only when it is at least 300 s stale. Nothing polls in the background, and every poll pauses while the app is not active (`setActive` for every session).
- **Push routing.** A silent push is routed by its origin (`PushWake.origin(ofRemoteNotification:)` → `PushOrigin`; the CloudKit wake reads the `CKDatabaseNotification` database scope) to the sessions whose `HubSession.route?.pushOrigin` equals it; with an unknown origin every session fetches, the demo always. Each fetch is the session's own `handlePush`; the outcome is `.newData` when any brought something, `.failed` when every one failed, else `.noData`, and goes through `PushCompletion` (25 s deadline) as before. `AppEnvironment.waitForBoot` waits for every session's boot.
- **Badge.** The app icon's badge is the sum of the open asks across the hubs that can answer them (`openAskTotal`; a hub the Mac removed, `writesAllowed == false`, is left out until Forget, as is it from the chip's other-Macs count), seeded silently at init so a launch never flashes 0. Per-hub notification content, `ask-alerts-<hub_id>` subscriptions and tap-to-activate belong to A13 (board #17).
- **`DeviceSettings` per hub.** The Workbench choices are keyed `hub.<hub_id>.device.*`. A choice made while no hub is linked is kept under the unlinked keys and adopted by the hub whose link completes (`adoptUnlinkedChoices`, in `LinkHost.linked`); a removal deletes the hub's keys (`removeChoices(of:)`). The legacy global keys (`typingRequested`, `startSessions`) are moved by `HubBoot.migrateF1`.
- **Link flow per hub.** A scan builds the candidate hub's session (`LinkHost.prepare`), reads its keybox (`fetchKeybox`, `refresh(.link)`), and on `linked` adds the registry row and puts the hub on screen (above, "The scan"). A fifth Mac is refused (`.tooManyMacs`) and an invalid hub id never reaches disk. `AppRoot.removeHub` is the one removal path (a second call for the same hub waits for the first and counts nothing): it takes the registry row **before its first await** (a kill afterwards leaves no row that would resurrect the hub; leftover files are an orphan the next launch clears), activates the next Mac when the hub was on screen (none → Welcome), sends the `unlinked` farewell through the hub's own session transport (10 s hard cap; kept sealed in the registry from before the wait, dropped once sent, and sent again at the next activation when still queued, #143), stops a running capture, shuts the session down, hands its recordings to the hold, closes its replica and transport store (`HubSession.closeDatabases`), drops its Settings keys and deletes its directories. A hand-over that reports a problem keeps the hub's files for the next launch's orphan pass. The close comes before the delete because a connection still open on unlinked files, touched while a new database opens at the same path (a re-link of the same Mac), breaks the new one with `disk I/O error` / `database is locked` on iOS (#216); the orphan pass closes its throwaway session the same way.
- **The Mac removes the phone = freeze.** `TransportEvent.unlinked` or the missing grant (above) marks the row `unlinked_by_mac` (`markRemovedByMac`) and `HubSession.freeze(as:)` stops the session's sync and writes — the replica stays readable, the outbox, uploader and Settings toggles send nothing (`writesAllowed: false`) — until the owner chooses **Forget**. The same freeze is applied to such a row at boot. A rescan of a frozen hub starts it again from empty files.
- **Account change.** `accountChanged` compares the phone's `userRecordName` with each link's: another account removes every hub (`keepRecordings: false`: nothing is carried, recordings are reported "Not sent"), a sign-out keeps them.
- **F1 migration** (`HubBoot.migrateF1`, before any session opens). It runs once, when the registry is empty and `link.record` holds a link: the link's replica, transport store and audio move into the hub's directories (side files `-wal`/`-shm`/`-journal` first, the database last, so a database at the target means the move finished; a failed move throws before the registry is written and the next launch retries), its Workbench choices into the hub's keys, and the link into the registry as the active hub; then the legacy link keys go. An unreadable `link.record` touches nothing. With rows present, leftover legacy keys are cleared. With an empty registry, no link and a pending one (a kill mid-link), the replica, transport store and audio move into the pending hub's directories instead, so the device record still queued in the store is sent when `resumeLink` resumes the wait (#221). The session's start keeps the moved store because F1's link restarted its transport on the pending hub, whose start bound the store to that scope and hub (`TransportStore.adoptScope`); a store bound to no hub (the single-hub build's, whose state names other zones) is wiped at the start as anywhere, its queue with it, and that wait times out (scan again). The migration does not rebind a store: it would only be a no-op or keep another build's state. With an empty registry and neither, the unlinked phone's legacy replica and transport store are deleted (the audio stays). `HubBoot.removeOrphans` then clears hub directories with no row (other than the pending link's hub): a session built on each hands its recordings to the hold, then its files go. The pass (`AppRoot.launch`, after `dropUnencryptedLinks`, before `resumeLink`) runs inside background work (`hub-orphans`; a push launch runs it too), and `LinkHost.prepare` waits for it, so a cold launch by a link URL never has the files of the hub it is linking deleted under its new session (#220); the launch sweep of loose files deletes regular files only (the hold and `hubs` folders stay).
- **Recording across hubs.** One microphone: the recorder that owns it or the recorder screen (`PhoneRecorderController.holdsMicrophoneOrScreen`: starting, capturing, paused, saving, or showing its result until closed) stays `env.recorder` after a switch and blocks `canStartCapture` on every hub until closed. A recording finishes on the hub it started on: that session saves it and its uploader sends it to that Mac; the recorder says "Recording for <Mac>" when that is not the hub on screen. The Recordings list shows the active hub's recordings plus the held ones for Macs with no session (`AppEnvironment.heldRecordings`), never another linked hub's; so the recorder's **See recordings** after a capture for another Mac puts that Mac on screen first (`showRecordings`).
- **Switcher.** `HubSwitcherChip` (Now and the Workbench list, leading toolbar slot; shown with one Mac too, as the way to Add Mac) shows the active Mac's name and the open asks on the other Macs, and opens `HubListSheet`: per Mac the name (a short hub id suffix when two share it), flavor, online dot (heartbeat under 2100 s old), "Offline N days", "Removed this phone", the last fetch's problem line and the ask count; **Add Mac** is disabled at 4 (`HubListModel`). A switch (`AppEnvironment.activate`) resets navigation to the root and rebuilds the tab content (`.id` on the `TabView`); the recorder cover, the scan cover and the banners live outside it, so a running capture survives.
- **Settings → Macs** (`MacsView`/`MacsModel`). One row per Mac: reorder (Edit, `onMove`, writes the registry through `moveHub`, blocked while a link flow is busy) and one destructive swipe action per row (`MacsModel.action`, disabled while busy) — a removed Mac offers **Forget**; a linked Mac offline for 7 days or more (`HubListModel.forgetAfterDays`) offers **Forget**, which unlinks with the farewell; otherwise **Unlink**. The demo hides the removal actions (`MacsView.offersRemoval`). Settings itself shows the active Mac's status, Last sync, accounts and Workbench choices, a **Macs** row leading here, and a button for the active Mac with the same action and copy as its row in Macs (`MacsModel.action`: **Forget <Mac>** for one that removed this phone or is long offline, else **Unlink <Mac>**).
- **Demo.** `DemoSeed.hubs` = "Acme Mac" (`demo-hub`) and "Home Mac" (`demo-hub-home`), each its own in-memory transport, replica and recordings folder; `AppRoot.demo` fills an in-memory registry from them, so the chip, switcher and Macs list run unchanged.
- **Removed in F2:** the switch prompt, the moved notice, `AppRoot.Restarter`, `LinkHost.retireEnvironment` and the farewell transport (`AppEnvironment.unlinkedHubID` is gone; `DeviceSettings.unlinkedHubID` only names the unlinked choices' keys).
- Tests: `HubRegistryTests`, `HubBootTests`, `MultiHubEnvironmentTests`, `MultiHubRecordingTests`, `HubSwitcherTests`, `MacsModelTests`, `FetchCadenceWiringTests`, `AppRootWiringTests`, `LinkingViewModelTests`.

### Workbench and Now tabs, read-only (B5)

- **One read for the app.** `AppEnvironment.workbenchReplica` observes the replica and decodes every Workbench slice (`ReplicaStore.payloads(of:from:)` + the Kit mirrors) plus the heartbeat (through Settings' logging decode) into one `WorkbenchReplicaSnapshot`. An undecodable record is skipped and counted in `skippedRecords`, logged only when the counts change. Now, Workbench and the tab badge (open-ask count) share it. Every replica observation on the phone (calendar, recordings, settings, session detail, workbench, recap) runs through `ResilientObservation`: GRDB ends an observation for good on its first error, so after one it logs, reports to `ObservationHealth`, waits 1 s (doubling to 30 s, back to 1 s after a value) and starts a fresh one; `cancel()` or release stops it for good.
- **Per-kind reads (board #724).** No observation tracks `slice_records`. Each uses `ValueObservation.tracking(regions:fetch:)` over `slice_kind_versions` plus its own sidecar tables (the workbench and Settings add `pending_actions`; recordings and the recap add `phone_recordings` and `phone_recording_marks`), and its fetch reads its kinds' stamps first. A model-owned `ReplicaDecodeCache` keeps each kind's (or single record's) decoded value with the stamp it was read at: an unchanged stamp returns it undecoded, so any write still wakes the fetch, but a heartbeat write decodes only the heartbeat (in the workbench, recordings and Settings snapshots), a calendar write never the board, a board write never the calendar; the overlay and the recordings ledger are re-read every time (small). The cache lives in the model, so a restart (an error, a resume) re-decodes only what changed — except where the observed source changes: Settings starts an empty cache when it observes another replica or device id (the link flow swaps the environment; the old Mac's heartbeat must never be served), and the recap starts one on each `observe`, so earlier transcripts' bodies are not kept for the view's lifetime. The kinds read: workbench — `workbench`, `workbench_target`, `terminal_session`, `owner_ask`, `workbench_comment`, `heartbeat`, `device_grant`; calendar — `calendar_event`, `meeting_transcript`; recordings — `recording_job`, `heartbeat`; Settings — `heartbeat`, `device_grant`; session detail — `session_report`, `session_timeline`; recap — the `meeting_transcript` stamp for its segments asset. `*Snapshot.read(from:store:)` without a cache decodes everything (tests, one-off reads). Mobile E2E: a list read skips the rows it cannot open while locked and returns the rest without throwing, so the cache keeps nothing from a read during which `ReplicaStore.keyRefusalCount` moved; the read after the unlock (every live observation restarts at `protectedDataDidBecomeAvailable`) decodes those kinds again although their stamps did not move (Review Focus 1). A read that throws `.locked` (a single record) stores nothing either.
- **Background rest (board #724).** `ReplicaObservationGate.shared` suspends every `ResilientObservation` while the app is in the background: `WatchtowerMobileApp` drives it from the scene phase (`.background` only — an inactive app is still on screen), and a launch that reads `.background` in `AppDelegate.didFinishLaunching` (a silent push, a prewarm — in a scene-based app a tap too) starts suspended; the scene's first non-background phase resumes it. A suspended observation holds no GRDB observation, so no replica write wakes or decodes anything; one created meanwhile starts on the resume. The resume starts each afresh: its first value is the latest, delivered once, decoding only the kinds written while away. Nothing background work needs is an observation: the outbox, the uploader, the relay feed and the notification paths read the store directly. The gate is not driven while the app only hosts XCTest; tests build their own gates.
- **No lock across a suspension (0xdead10cc, board #724).** The live replica sits in the shared app-group container, and iOS kills an app suspended while it holds a lock on a file there. Rule: no replica transaction may be open when iOS can suspend the app. (1) A silent push's work runs inside a background task (`BackgroundWork`, `UIApplication.beginBackgroundTask`): begun before the fetch, ended when the fetch serving the push returns — after a completion `PushCompletion` sent at the 25 s deadline too — so the app is not suspended mid-fetch. (2) The live replica opens with GRDB's `observesSuspensionNotifications` (`ReplicaStore(path:observesSuspension:)`, only the app-group replica of a `.cloudKit` environment), and `DatabaseSuspension.shared` posts `Database.suspendNotification` whenever the app is in the background (scene phase) with nothing holding it, and `resumeNotification` otherwise. Holders, each a named `BackgroundWork` (a background task plus a hold, ended once; when iOS grants no time — `beginBackgroundTask` returns `.invalid` — the hold is taken only in the foreground and released once at the end, while in the background none is taken, since no expiration would suspend the replica again; no task is ended) except the capture: a push's work (`silent-push-fetch`, from `begin` to the fetch's return, and on past it until the boot is done — `AppEnvironment.waitForBoot`, without holding back the push's completion); the boot (`app-boot`, taken in the live environment's init — before a push launching the app can end its own work — and ended when the boot's launch fetch, outbox sweep and launch recovery are done, or at once by `stop()`); every recording save (`recording-save`, through `PhoneRecorderController.beginSave`: Stop, the 3-hour cap, a long-pause auto-finish, a dead engine — a paused capture holds nothing, so a save in the background would otherwise meet a suspended replica); and a capture whose audio runs (`PhoneRecorderController.onAudioRunning`: the app stays alive in the background and writes the ledger). `AppEnvironment.holdReplica` wires the recorder's two. When the push's background task expires, the push's own hold is released and the replica rests in the background before the task ends — suspended unless other work (a running capture) still holds it; the expiration never takes another holder's hold. A suspension interrupts and rolls back an open transaction, and a later statement fails with `SQLITE_INTERRUPT` (logged by its caller) instead of taking a lock. When a push's fetch returns with the app still in the background, it rests again. The CloudKit transport's own store (`cloudkit-transport.sqlite`) cannot be suspended — CKSyncEngine writes it from its own callbacks at any moment — so the phone keeps it outside the app group, in its own Application Support (no extension reads it; `AppEnvironment.liveTransportStorePath`): an earlier build's store in the app group moves there once on launch with its `-wal`, `-shm` and `-journal` files (side files first, the database last; a failed move puts them back and opens the old path for that launch). The path is resolved once per process (`AppRoot.live` hands it to every environment and the wipe; `TransportStorePathResolver` caches it), so no move runs under a store the process has opened. Stashed assets (`transport-assets`) stay where they are, referenced by absolute path. The Mac hub's store is unchanged. Tests: `BackgroundWorkTests` (push expiration keeps a capture's hold, boot hold), `RecorderTests.testAnAutoFinishInTheBackgroundHoldsTheReplicaForTheSave`, `AppRootWiringTests` (transport store move), `ReplicaTests.testASuspendedReplicaRefusesWritesUntilResumed` (Kit).
- **Pure screen models** (`WorkbenchCardModel`, `WorkbenchMenuModel`, `SessionRowModel`, `WaitingCardModel`, `BoardModel`, `BoardTargetDetailModel`, `NowModel`) carry every string and colour a screen draws; the views only lay them out.
- **Sessions are drawn as given.** Dot tone, ring (`is_ring`) and caption come from the record (`PhoneTone(_:)` maps the five published tones to the system colours of spec §14; an unknown tone draws secondary); the record's glyph stays in the model and the phone draws the dot only (design pass §9.1). The phone adds only an age, computed on the phone so the record stays unchanged: a live session's time in its current state from `state_at` ("Needs approval · 40m"; none while `state_at` is unknown — a repeated state does not advance it, so it is not the last tool call), a session that is not live its `last_active_at` (board #516). A session row's meta line (`SessionRowModel.metaItems`): the caption in the session's tone, then `#<report_target_id> · <done>/<total>` (absent without `report_target_id`), the `report_pr_line` and "N closed" in secondary. `MetaLine` shows the longest prefix of whole items that fits, ends a shortened line in "…" and gives VoiceOver every item.
- **Now and the sessions order (2026-10-26, mockups 1, 2, 8).** `NowModel` leads with `waitingForYou` (`NowWaitingRow`: open asks with `OwnerAsk.quick` answers sent through `AskDraftStore` + `AskAnswerer.send` as the workchat does, pending permission requests, `stopped`/`finished`/`failed` sessions whose `state_at` (else `last_active_at`) is within `NowModel.endedSessionWindow`, 24 h, unless an open ask of the session is listed: one row per waiting thing, ask #622; newest first, 20 shown), then `working` (live `working`/`running` sessions, timer from `state_at`), then the next meeting (`NextMeetingCardModel.row`, a `CalendarRow`) with Record. `WorkbenchMenuModel.sections` follows the Desktop panel: Waiting for you (`waiting_on_ask`, `needs_approval`, `stopped`, `failed`, `finished` with open asks), Working, Ready to check, Not running (`not_started`), then `finished` (no open ask) folded; an open ask whose session is not listed shows on top; a row's meta adds "N asks open" in the waiting tone unless the Mac's caption already says it. Honest staleness: `MacReachability.of(heartbeat:linked:now:)` (online < 2100 s by `MacStatus.isOnline`, asleep = older heartbeat on a linked hub, offline = none or unlinked) feeds the `MacStatusChip` on Now and the Calendar, the workchat's `MacAwayBanner` and state line "as of", Now's working times and the workbench session rows (`WorkbenchMenuModel(asOf:)`), and the composer note "Waiting for your Mac". The workchat's sent-line caption "Queued" is drawn only for a Claude session (`SessionInputDelivery.resolved(for:)`), and an applied Finish shows "Finish · Sent to the session" (`SessionInputSender.finishDeliveries`, cleared by the next line).
- **Counts.** Board progress is `done_targets / (open_targets + done_targets)`, no bar at 0 of 0. "todo" is `open − in progress − blocked`. Session-state counts are the hub's `session_counts` (the Workbench cards); "not running" is not shown.
- **Board filters.** Open (`todo`, `in_progress`, `in_review`, `blocked`), In progress, Blocked and Archive. Archive shows only `archived` records and the others never do; a matching target keeps its ancestors from the same pool for context, and under Open a shown parent's done children (green check, title struck through and secondary) show only while **Show done** is on; chip counts stay match-only. **Show done (N)** / **Hide done** (`ShowDoneButton`, #1191) is one switch remembered in `@AppStorage("board.showDone")` (off by default) for the board and a target's sub-targets (`BoardModel`/`BoardTargetDetailModel` `showDone`, `doneChildCount`); the header `Sub-targets · done / all` still counts every sub-target, and Archive and an archived target show their done ones regardless. A node has a disclosure only with visible children.
- **Sibling order** is the Mac's: priority high/medium/other, then status in_progress/in_review/blocked/todo/done/other, then id (`BoardModel.boardOrder`, a third twin of Core's `WorkbenchBoardOrder` and Go's `boardSiblingOrder`; change all three together).
- **Orange only for waiting and asks.** Views paint only tones the screen models hand them. Each model lists its `ToneUse`s with a `ToneRole` decided from the data; `OrangeToneTests` runs every DemoSeed screen and fails on orange outside a waiting or ask role, and checks that the data-driven tones (status, priority, Mac chip) are never orange. The SwiftLint rule `orange_outside_phone_tone` (WatchtowerMobile only) forbids naming orange under `Sources/Features/` and `Sources/DesignSystem/` outside `Sources/DesignSystem/PhoneTone.swift` (`PhoneTone.waitingForYou`); the design layer itself gets orange only from `PhoneTone`. The project has no snapshot library.
- **DemoSeed** adds three workbenches (one without sessions and with an empty board), ten sessions covering every state kind, open REVIEW/ASK/CHECK asks plus closed ones, a board tree with archived targets and a comment thread.

### Session detail (B7)

- **Reached from** a session row on the Workbench tab or in a target's detail (`SessionRoute`). `SessionDetailModel` is the pure screen model: the header (title, target chip that opens the target, the target's branch or else the workbench's, "Claude Code · <age>", the Mac's state caption), the session's open asks newest first ("since <oldest age>"; the rows open nothing until the answer flow), "Needs approval on the Mac" for a `needs_approval` session with no published request (a Codex session, or one the hub has not published yet; a live Claude session's pending request shows the permission card instead, #517 — nothing typed from the phone answers a prompt), the report card and the timeline. No report → header and timeline only.
- **Report card.** "done / total targets" with one segment per target up to 24 (more: one segment per run, sized by its count): done green, in progress and in review accent, blocked red, the rest grey; in-progress segments are not orange (orange stays for waiting and asks). The summary is the finish summary of a finished session, otherwise "Now: …" and "Next: …" (first three each); PRs read "PR #175 open" or "<branch> · no PR".

### Phone recorder and uploader (C6, E2E9, E2E17)

- **Capture.** `PhoneRecorderController` (owned by `AppEnvironment`, so a capture survives navigation and Minimize) over the `AudioCaptureEngine` seam; on a device `AVAudioCaptureEngine` writes AAC 44.1 kHz mono 64 kbps `.m4a` (`aac-64k-mono`) as a fragmented MP4 (10 s fragments), so a capture cut short by a kill stays playable up to its last fragment. Files land in Application Support `phone-recordings/<uuid>.m4a` (`completeUnlessOpen`); the plain file and the sealed `<uuid>.enc` both stay until the Mac acknowledges the recording (ask #89 option A). An interruption (a call, Siri) pauses into the same file and the timer leaves the gap out; one that ends without `.shouldResume` stays paused like the Pause button. **A pause releases the audio** (board #724): the engine stops, the session is deactivated with `.notifyOthersOnDeactivation`, the route watch rests (the resume's format check catches a changed microphone) and the ticker stops; the resume re-activates and restarts them. So a paused capture keeps nothing running, and the `audio` background mode no longer keeps the app alive. **A capture paused for 60 min** (`PhoneRecorderController.pauseLimit`, owner decision Q5; counted from the pause or the interruption's start) is finished and saved by itself through Stop's own save and upload path: the row is marked `auto_finished`, the Saved screen shows "Finished automatically after 60 minutes paused.", a local notification says so, and the Recordings list subtitle adds "auto-finished after a 60 min pause". The wait is an injected sleeper; a suspended app's timer cannot fire, so the return to the foreground also finishes a pause past the limit. An interruption longer than the limit finishes the capture the same way, and its later end (even with `.shouldResume`) changes nothing. An auto-finish whose save fails posts "Recording could not be saved" (`onAutoFinishFailed`), since the owner is usually away. A route or configuration change (AirPods, CarPlay) ends the capture with a notice and saves what was written (POC choice). Auto-stop at 3 h with a notice 5 minutes before (a local notification when allowed). Under 1 s is discarded. An event's Record ties the capture to its event; the Calendar's mic button records a voice note (no event).
- **Screens.** `RecordingView`: REC mark, "<Meeting> | No meeting", timer, red waveform, Pause | Stop | Mark moment, Minimize; after Stop the Saved screen shows "Saved · mm:ss" and the recording's way to the Mac ("Waiting for the Mac to wake" while the heartbeat is stale, re-rendered every 30 s). Red is the recording colour.
- **Sealing at finalize** (`RecordingUploader.sealPending`, run by the recorder's stop before the upload pass, and again on unlock). A finished recording is sealed once: the audio is encrypted to `<id>.enc` under a fresh `K_asset` (`ChunkedAssetCipher`), the `recording_upload` record (asset descriptor inside) is sealed by `SecureTransport`, the envelope, its wire name and the sealed file are stored in one row update (`phone_recordings.wire_name`). The plain `.m4a` stays (D8, ask #89 option A) until the Mac confirms receipt. A locked keychain leaves the row `waiting` with its plain file, sealed after unlock. The 90 MB cap is checked on the plain size. The launch sweep keeps both files of every undelivered row. A re-seal (an envelope of an epoch the phone has moved past) writes a new file, `<id>-<n>.enc`, never the one an older queued save may still point at; the row keeps the old `sealed_path` (and the sweep the old file) until the new envelope is stored. The superseded file goes only after the new seal's save has replaced the transport's queued save of that record (the pass's successful save), or, if no save succeeds first, by the next launch sweep. A row whose save is in flight is left alone by a seal pass (`sendingIDs`), and after the save the send keeps both the file it saved and whatever seal the row stores by then.
- **Across a wipe** (main's #63 hold). The hold moves the plain `.m4a` into `.held`. The sealed copy and the stored envelope belong to the old pairing and are not carried. A held recording adopted after a re-link is registered again and sealed fresh under the new link: `RecordingUploader.register` drops its stale seal files. One that no environment adopts is swept from the recordings folder.
- **Ledger** (`phone_recordings`, `RecordingUploader` is its only writer): `recording` (row from the first second; marks are stored as tapped) → `waiting` (finalized, then sealed) → `uploading` (the stored envelope saved into RelayZone with the sealed file) → `delivered` (the hub's `received`: the plain and the sealed file are deleted, ack-then-delete) or `failed` (the hub's message; both files stay, and Retry re-sends the stored envelope unchanged, the same record name and seq). Byte identity holds within an epoch only. A `waiting`/`uploading` row whose stored envelope was sealed under an epoch older than the phone's current one has its seal dropped at the start of each pass, and is sealed again under the current epoch (`RecordingUploader.unsealStaleEpochs`, final review Kit I1). The re-seal uses the same wire name, a new envelope and a fresh asset key. Otherwise a recording sealed before two rotations, or delivered after the hub's 7-day grace, would be refused for good. A local failure (file gone, over 90 MB, no readable audio) offers no Retry. File names are stored relative to the recordings folder, which iOS may move between launches. Columns added in place for board #724: `upload_attempts`, `last_attempt_at`, `auto_finished` (the replica's `ALTER TABLE … ADD COLUMN` pattern; the CHECK rebuild carries them).
- **Bounded upload retry** (board #724). Every save handed to the transport counts an attempt (counted before the save, so an attempt the process dies in still spends its step). A new `waiting` row goes out on the next pass; a row saved before is saved again only when its backoff is due — 1 min, 5 min, 30 min, 2 h, 6 h after the latest attempt (`RecordingUploader.retryDelays`) — and at most 6 times (`PhoneRecording.uploadAttemptCap`). Past the cap the row is "Upload stuck" (`isUploadStuck`, a `waiting`/`uploading` row): the Saved screen, the Recordings list and the agenda show it as a failure with **Retry**, which resets the backoff (`resetPhoneRecordingForRetry`) and sends at once — but only while the Mac reads online: while its heartbeat is stale or absent the row reads "Waiting for the Mac to wake" whatever its attempts (`PhoneUploadStage` checks the Mac first). The backoff has no timer of its own: a due re-send goes out on the next upload pass, and passes run only on triggers — the return to the foreground (the boot's pass on a foreground launch), a capture's finish, a link (`setLinkedDevice`) and the owner's Retry. A `received` echo ends the retries (a delivered row is never sent). Re-sends happen only while the app is active: `AppEnvironment` passes the uploader a gate (`UploadRetryGate`) that follows the scene phase (`setActive`) and starts from `UIApplication.applicationState`, and each opening runs an upload pass after the boot.
- **Launch.** `recoverOnLaunch` finalizes a `recording` row from its file and deletes files no row points at. The boot's upload pass runs only in the foreground; a launch into the background (a silent push) uploads nothing — new rows included — until the first activation. An `uploading` row already sits in the transport's durable send queue, so it is re-saved (the relaunch retry, byte for byte the stored envelope; the hub's ledger absorbs duplicates) only by the first foreground pass of a process that finds the Mac online (`RecordingUploader`'s `macOnline`, which the app reads as `RelayFeed.isDesktopReachable` over the replica's heartbeat) and only when due; a background pass, or one while the Mac sleeps, makes and counts no re-save and leaves that retry armed — a recording merely waiting for a sleeping Mac never walks toward "Upload stuck". Later passes send `waiting` rows only, and overlapping passes merge. One exception: an `uploading` row this pass sealed again (its envelope was of an epoch the phone has moved past, or a pre-E2E build sent it in the clear) is re-sent by that same pass, Mac online or not, backoff or not, because its new envelope was never saved. After a transport wipe the next foreground pass re-saves `uploading` rows without waiting for the backoff or the Mac (the queue that held them is gone). Uploads wait while no device id is set.
- **Marks** stay on the phone (`phone_recording_marks`) and never travel in the upload payload (spec §5.3); the recap view shows them as jump points.

Tests: `RecordingHoldTests`, `MultiHubRecordingTests`.
- **Recap.** `RecapView`: Recap | Transcript. The summary and the lists that have entries ("N more on your Mac" for dropped ones), the speaker transcript from the `segments.json` asset (a missing or unreadable asset is said so, never drawn as an empty transcript), and the phone's marks as jump points into the transcript line they fall in. ## Building a hub-capable Mac app (A10)

The mobile hub syncs through CloudKit, so it needs a Developer ID build that carries the iCloud entitlements and an embedded provisioning profile (design §10).

- **The profile.** A Developer ID provisioning profile (developer.apple.com → Profiles → Developer ID) for App ID `com.watchtower.desktop` — the app's `CFBundleIdentifier` (`BUNDLE_ID` in `scripts/build-app.sh`), not `com.aiwatchtowers.watchtower` — on the signing identity's team, with the iCloud capability and the container `iCloud.com.aiwatchtowers.watchtower`. Point `WATCHTOWER_PROVISION_PROFILE` at the downloaded `.provisionprofile`; a relative path resolves against the project root, so the variable can live in the build profile (`.env`, or the `ENV_FILE` of a flavor).
- **Early check** (`provision-profile-check`, before the Swift build): the profile is decoded with `security cms -D`; the build fails if the file is missing or undecodable, if its `com.apple.application-identifier` is not `<its team-identifier>.com.watchtower.desktop`, or if it does not grant the container.
- **Signing** (`app-codesign`): with a real identity and a checked profile, the profile is copied to `Contents/embedded.provisionprofile` and the bundle is signed with a temporary copy of `scripts/Watchtower-cloud.entitlements` into which the profile's `com.apple.application-identifier` and `com.apple.developer.team-identifier` are merged. A hand-signed app with restricted entitlements needs both (Xcode adds them; `codesign` does not). The team id is never written in the repo.
- The cloud entitlements are the base `scripts/Watchtower.entitlements` plus `com.apple.developer.icloud-container-identifiers` = `iCloud.com.aiwatchtowers.watchtower`, `com.apple.developer.icloud-services` = `CloudKit`, `com.apple.developer.icloud-container-environment` = `Production` and `com.apple.developer.aps-environment` = `production`. Keep the base keys in sync; the test checks it.
- Every build flavor (`BUILD_FLAVOR`, e.g. `ENV_FILE=.env.corp`) uses the same bundle id and container: both are signed by the same Developer team. The signing blocks have no flavor logic.
- A real identity without a profile signs with the base entitlements and prints `WARNING: mobile hub disabled: no provisioning profile`; the app then shows "Needs a signed build" in Settings → Mobile.
- Ad-hoc signing (`make app-dev`, or no identity) always keeps the base entitlements and never embeds a profile: amfid kills an ad-hoc app that carries restricted entitlements. A set `WATCHTOWER_PROVISION_PROFILE` is still checked early, then ignored with the note `provisioning profile ignored: ad-hoc signing`. Hub logic is tested in Go on `memfake` and the `bridgefake` test bridge and needs no signing.
- Whether amfid accepts the signed bundle and CloudKit reaches Production can only be shown on a real device (the A14 device smoke).
- Covered by `scripts/tests/test-build-app-cloud.sh` (`make test-scripts`), which runs both blocks against stubbed `security` and `codesign`.

### CloudKit environments

CloudKit keeps two environments per container, Development and Production, and a record saved in one is never seen from the other. The Mac and the phone must talk to the same one, or the phone sees no hub and the hub sees no phone actions — with no error on either side.

- **Which build lands where.** The Mac's Developer ID build is Production (`com.apple.developer.icloud-container-environment` = `Production`, `aps-environment` = `production`, from `scripts/Watchtower-cloud.entitlements`). The phone run from Xcode (the Debug configuration, `WatchtowerMobile/WatchtowerMobile.entitlements`) is Development; a TestFlight or App Store phone build is Production.
- **Pairs that work.** A Developer ID Mac ↔ a TestFlight/App Store phone (Production). A Development-signed Mac ↔ a phone run from Xcode (Development). A Developer ID Mac with an Xcode-run phone never meets.
- **A Development Mac.** Build with an Apple Development identity, a macOS development provisioning profile for `com.watchtower.desktop` with the container, CloudKit and Push Notifications, and `WATCHTOWER_CLOUDKIT_ENV=Development` (environment or build profile). `build-app.sh` then rewrites `icloud-container-environment` to `Development` and `aps-environment` to `development` in the temporary signing copy; the repo's entitlements file stays Production. Any other value than `Production` or `Development` fails the build.
- **One identity per hub dir.** The Go hub keeps its identity in `<hub dir>/identity.key`, not in an app-ID keychain, so two signed builds with different app IDs no longer cut each other's link; the bridge keeps its CloudKit state in `<hub dir>/cloudkit/`. (The Swift hub's per-app-ID cut is in History.)
- **Early profile check.** Besides the App ID and the container, the profile must grant CloudKit (`com.apple.developer.icloud-services` lists `CloudKit`, or is `*`), the chosen environment (`com.apple.developer.icloud-container-environment` lists it; a Developer ID profile lists Production only), and an `aps-environment` equal to the chosen one (`production` / `development`). Otherwise the build fails before the Swift build, naming the missing grant.
- **Before the first Production run**, deploy the schema from Development to Production in the CloudKit Console (Deploy Schema Changes): Production refuses record types it has not been given, and records are created in Development first by any Development run. Only the Console can do it: `cktool import-schema` and `validate-schema` answer `endpoint not applicable in the environment 'production'` (checked 2026-10-12). `make cloudkit-check` reports what is missing.

## Known limits (POC)

- **Several hubs, one version.** An unknown `recording_upload` status reads as `pending` on both sides. An older hub next to a newer one (multi-hub phase F, or a downgrade mid-ingest) could ingest or re-echo an upload whose status the newer hub wrote (decode an unknown status as a distinct inert case on both sides if it matters).
- **Pushes over the relay** are built on the hub only (Go hub plan 4, Hub → Work alerts and pushes); the phone's `register_push` and inline open are the relay client spec's Phase 4, and a real push has not run yet (it needs the relay's staging with APNs).
- **Linking in `shared` scope is written to spec, verified only on fakes.** Spike S0(c) (does closing the public link keep the accepted phone?) was never run; only S0(d) (same Apple ID) passed on a device. The hub builds the spec's primary path (close the link, remove unbound participants) and not the F2 fallback. The bridge's `CloudKitZoneShares` and the creator values CloudKit reports are untested until the device smoke.
- **Typing request notice.** The Go hub tells Desktop of a phone's new typing request with a `typing_request` watch event (once per request; go-hub.md). The macOS notice it posts opens nothing when clicked; the owner answers in Settings → Mobile. A request that arrives while the app is in front shows only on the phone's row, and one that arrives while Desktop is not running posts no notice (the row still shows it).
- **Typing grants from before B18.** A phone allowed to type before it ever sent `typing_requested` (allowed from Settings without asking, or linked before B18) has the request stored as off, so turning its toggle off does not revoke the grant; Revoke on the Mac does. The phone sends no line while its own toggle is off.
- **Permission answers (#517, PROJ-21 limits).** A new request raises a work alert (`perm-<id>`) only while the owner is away; otherwise it reaches the phone through its slice and shows in Now and the badge. A phone's `permissions_requested` sent at link time (in its hello) is not carried in `pending_devices`, as `typing_requested` is, so it is not stored — only its later `device` rewrite is (the toggle is off by default; a re-link keeps the stored grant and request). Expiry runs on the hub's slice pass, so not while no phone is linked. A Mac answer is seen only at the tool's PostToolUse (or the turn's `waiting` after a Mac deny), so during a long command the owner already allowed on the Mac the phone still shows Needs approval with Allow once and Deny, both ignored by Claude Code, and Interrupt is refused ("A permission prompt may be open — answer it on the Mac or with Deny"; that Deny is ignored too). A subagent's tool event during a main-agent prompt closes the row `answered_on_mac` (fails safe). In the few milliseconds between Claude Code drawing a prompt and the hook writing its pending row, the session still reads Working with no pending row, so an Esc handled then could still hit the prompt. A phone clock more than 2 minutes behind the Mac makes every interrupt `expired` (the server's save date cannot stand in for the phone's `created_at`: it cannot tell a clock behind from an outbox that sent late). "Sent to the session" stays for the app run.
- **A cancel that overtakes its line.** `session_input_cancel` for a line the hub has not read yet is a no-op; the line is then handled as usual.
- **A phone's own unlink** (`unlinked: true` in its `device` record) removes it on the hub as Remove does, once the hub's mailbox pass reads the record: until then (and if the record never reaches iCloud) the phone stays in `devices`, in the list and past the device gate.
- **Shared scope: one phone per code.** The link closes when the first phone uses the code. A second phone that accepted the public link reads `used_code` ("This code can't be used — Show a new code on the Mac") if its hello reaches the Mac within the 120 s answer grace (`link.DefaultSweep`, `AnswerGrace`); one that writes it later is swept first, can no longer read DataZone, and ends on its wait timeout ("Your Mac didn't answer"). Phones scan in turn, each with its own code. A hub stop during the grace leaves the sweep to the next run's close with reason `restart` (`link.CloseRestart`), which does not wait.
- **A removed phone is told through its keybox** (D9). Remove rotates the epoch and publishes the phone's keybox as `revoked` for 7 days, which a same-Apple-ID phone (no zone vanishes for it) and a shared one both read as "This Mac removed this phone". A phone that does not fetch within those 7 days misses the revoked keybox, but then finds its keybox gone (#64): at the second fetch at least 30 s after the first one that missed it, once a heartbeat newer than the link has arrived (the hub writes one every 15 min, and at once when its accounts or `sharing` change), it reads the removal too; until then it gets no newer keys, so nothing published after the removal opens for it, and the hub drops its relay records unanswered. A link saved by a build before 2026-10-12 has no device id or link time and is told only by the revoked keybox.
- **Metadata stays visible** (spec §4): record counts and churn, coarse sizes, timing, hub and device ids in zone and fixed record names, Apple IDs and APNs tokens (see End-to-end encryption → Metadata).
- **`K_meta` is not rotated** on Remove (D5): a removed phone can still map future opaque names of kinds and ids it already knows. Rotating it needs a delete of every old-named record.
- **Relay ordering** (D4): no per-device sequence gate; replay is stopped by the wire-name ledger, the authenticated age window and the per-record `(epoch, seq)` guard.
- **Availability.** Apple or an Apple-ID attacker can delete, withhold or delay records; a RelayZone share participant can trample other phones' records until swept. The phone shows staleness; it cannot prevent it.
- **The notification extension's key.** `K_alert` (titles of ask alerts) is readable after the first unlock, by design: a low-value key, separate from `K_data`.
- **Restore to new hardware, reinstall or a new Mac** means re-pairing: no key is backed up or synced.
- **Shared-scope work alerts are best-effort** (ask #622): the phone posts them locally after a fetch, and only as often as iOS delivers the sync engine's silent pushes; private scope uses the per-hub `CKQuerySubscription` (`AlertSubscriptionRegistrar`).
- **No suspected-leak rotation in the UI**: the keyring's reason `manual` exists, nothing calls it yet.
- **One hub per sidecar.** `hub.lock` keeps a second hub out; while a hub holds it the CLI writes through `hub.sock`.
- **CloudKit environments** must match between the Mac and the phone (see above); a mismatch fails silently.

**Organization policy (2026-10-25, #608):** the MDM key `MobileSync` decides the hub. `off` keeps it off (`hub status` reason `policy_off`), keeps the owner's switch as stored and locks the Settings → Mobile toggle; the policy's off never unlinks a phone (only the owner's switch does, go-hub.md `off_delete`). `workbench_only` publishes only the workbench kinds (`sources.WorkbenchOnlyKinds`: workbenches, targets on the board, comments, sessions, reports, timelines, asks, ask alerts, permission requests, session chat, plus the heartbeat and device grants); every other kind is published empty, so the phone deletes it, and phone recording uploads are refused. See `docs/features/mdm-policy.md`.

## Keep the Mac awake (2026-10-26, ask #614)

`HubKeepAwake` (Desktop, go hub plan 3 Task 23) holds one `PreventUserIdleSystemSleep` assertion through `MacAwakeAssertion` while the Go hub runs (`hub status` state `running`), the owner's switch is on (`Constants.mobileKeepAwakeKey`, `mobileKeepAwake`, absent = on; Settings → Mobile), a board agent session is live (`HubKeepAwake.liveBoardSessions` over `TerminalCenter.liveIDs`; a plain shell does not count) and a phone was in touch in the last 24 h (`KeepAwakePolicy.shouldHold`, re-checked every 30 s). Contact comes from the Go hub: its heartbeat answer's `phone_contact_at` (`HubCenter.lastPhoneContact`), which the hub stamps for an action that passed its gates and for a linked phone's own `device` record (`min(seen_at ?? updated_at, now)`, an unlink excluded; never lowered; go-hub.md). `stop()` — a quit or a rebuilt hub center — drops the assertion, and the process end drops it too. The phone rewrites its `device` record on foreground when its last write is over an hour old (`DeviceSettings.touchIfStale`); `DevicePayload.seen_at` is written only when set. A closed lid on battery still sleeps the Mac. A headless host has no keep-awake: the daemon does not hold one.

## History: the Swift hub (until phase 3 of the Go hub)

Until go hub plan 3 Task 24 the hub was Swift code in the Desktop process (`WatchtowerDesktop/Sources/Services/MobileHub/`, started by `AppState.initMobileHub` when `mobileSyncEnabled` was on): `MobileHubService` ran it, `SlicePublisher` published the slices on a 30 s full tick, a 10 s urgent tick and a 1 s / 2 s fast lane for asks, `RelayProcessor` applied the phones' actions through its exactly-once ledger (`begun`/`done`, `outcome_unknown`) and `MobileHubCommandDispatcher`, `MobileLinkCenter` linked phones (with the pairing sheet's duplicate-name and same-code warnings of `MobileLinkSheetViewModel`), `HubKeyring` kept the keys in the data protection keychain (`KeychainHubKeyStore`), so two signed builds with different app IDs on one Mac cut each other's link, and its sidecar was `<AppSupportDir>/MobileHub/`. A pre-E2E hub, a recreated Keychain identity or unreadable stored keys ran the E2E hard cut (zones deleted, phones forgotten, fresh keys; `hub_meta.e2e_v1`). The Go hub adopted that state once (`hub adopt`, go-hub.md "Phase 3"), and the behaviour those sections described is the contract the Go hub keeps; each Swift test's Go twin is in Task 24's mapping table.
