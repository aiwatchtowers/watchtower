# Session chat feed — the dialog of a workbench session (2026-10-16, phases 1-3)

Spec: `docs/superpowers/specs/2026-10-16-session-chat-feed-design.md`. Contracts: FEED-01..05 in [docs/inventory/session-feed.md](../inventory/session-feed.md).

A workbench session's transcript holds hundreds of tool calls; the owner wants the conversation only. The feed is built on demand by a deterministic Go reader from the Claude Code transcript JSONL. No AI call, no transcript text stored anywhere, nothing written to the transcript files.

## Entry kinds (agent-neutral)

`owner`, `agent`, `ask_answer`, `watchtower` (`via` = `review` or `handoff`), `brief`, `subagent`, `separator`, `event` (`event_type` = `task` or `teammate`; `title` and `text`). Every entry has a stable `id`, an `at` time, `text` and the tab's `conversation` (agent session id).

Record rules (`parse.go`):
- `user` records with string or `text` content are `owner`. Dropped: `isMeta`, `isCompactSummary`, any record holding a `tool_result` block, `<local-command…>` wrappers, `[Request interrupted…` lines, and sidechain records outside a subagent file. `<system-reminder>` blocks are stripped; images become `[image]` (unless the text already has an `[Image #N]` marker); a slash command becomes `/name args`.
- A `user` record whose text starts with `<task-notification>` or `<teammate-message …>` is an `event`, not an owner line (a task notification: title = `<summary>`, text = one `tag: value` line per child; the same entry also carries a structured `task` object `{task_id, tool_use_id, status, summary, result, output_file, tokens, tool_uses, duration_ms, kind, exit_code?}` — `kind` is `command` for a `Background command …` summary (with `exit_code` from `(exit code N)`), else `agent`; `result` is `""` for the delivery boilerplate and is then filled in `Build` from the first paragraph (≤ 600 runes) of the matching subagent's own SubagentHandback message (sidecar transcript, meta `toolUseId`; never the parent's launch notice) — on a `--tail` read only for the entries of the returned page (`BuildTail`), never for `FindSubagent`'s marker-only build; best-effort: a sidecar that fails to read is logged and the result stays `""`; children are matched by element name (a child quoting a close tag keeps its whole text); a notification with unclosed tags has no `task` and keeps its raw text, titled by a leading complete `<summary>` when there is one; one that parses but has no recognised child (task-id, tool-use-id, status, summary, result, output-file, or a usage block with a number) has no `task` either and keeps the `tag: value` lines of its children; a message whose text blocks are all notices (Claude Code's sibling notifications) gives one event per block, the first with the record's uuid as id, the others `<uuid>#<index of the block in the message content>`; notices beside other text or an image give one event, the leading notice read within its own block (the event carries no `[image]` marker); when a `<system-reminder>` crosses a block boundary, or a notice is not complete in its own block (it continues in the next), the blocks are joined first and the record is one entry (a teammate message is complete in its block only when the block ends with its close tag; a joined text holding sibling notifications reads the first one up to its first close that parses, so its result does not run into the next one); a teammate message: title = the `summary="…"` attribute, text = the body; fallback title = first non-empty text line, else `Notice`, capped at 200 runes). Owner text before a wrapper keeps the record an `owner` line. The phone drops `event` entries: its slice keeps only `SessionFeedEntry.phoneKinds`.
- `Ask #N answered …` is `ask_answer`; the CLI joins it to `owner_asks` (title and answer text), **only for an ask of the session's own workbench** (FEED-04). An ask that cannot be read keeps the bare typed line.
- `Review round #…` and `From a Watchtower code question:` lines are `watchtower` entries (`via` review / handoff). Hook feedback is not a chat line and is dropped with the meta records.
- The start brief is not a `user` record: it is an `attachment` with `hookEvent` `SessionStart` whose `stdout` starts `Watchtower workbench #`; other SessionStart outputs are dropped. One collapsed `brief` entry.
- `assistant` records: only `text` blocks, one entry per message id, the last streamed version wins. `tool_use` and `thinking` never reach the feed (FEED-02).
- An `Agent` tool call becomes one `subagent` marker (type, description, status). Unknown record types are counted in `unknown_records`, never shown; an overlong line (over 8 MiB) or invalid JSON is skipped and counted in `skipped`; a final line without `\n` is left for the next read.

### Peer entries (multi-folder workbench, #2003 Task 17)

`peer` (`PeerRef`: `direction` in/out, `kind` message/finished/started, `session_id`, `title`, `folder`, `worktree`) is another agent of the workbench speaking. Go matches it (`internal/sessionfeed/peer.go`), never the Desktop. An owner-side line that STARTS with `[Message from #N “t” · f — another agent of this workbench, not the owner]` (body = the text under it, the `(Reply with send_to_session(…))` footer dropped) or `[Sub-session #N “t” finished · f] ` is an incoming peer entry; a `> `-quoted copy (what `sessionmsg` writes for a forged prefix) stays an owner line. The sender's own bubbles are its `send_to_session` / `start_session` tool calls (any MCP server prefix): `out` entries with the tool_use id; a `start_session` entry gets its session id, folder and worktree from the tool_result when the same parse reads it; `workbench session-feed` names an outgoing message's receiver (title, folder) from the database. The failure and typed lines (`[Message to #N not delivered …]`) stay plain owner lines. A refused call (`is_error`, or a non-JSON answer) sets `PeerRef.error`: the card reads `not started: <reason>` / `not sent: <reason>`, never started or sent. A start result read in a later pass than its call is emitted under the call's id (the store upserts; the CLI names its title from the database); a refusal read that late cannot be told from other tool errors, so that card stays `starting`. Codex rollouts: incoming lines, and outgoing from `response_item` function calls/outputs of the two tools. The Desktop draws them as cards (`PeerBubblePresentation`, mockup `feed-parent-*`); the waiting card (`⏸ Message to “t” is waiting`) is built from the sender's queued `session_messages`, its reason from the receiver's state, and the stopped-daemon line wins over every hold. The phone does not render peers in v1 (`phoneKinds` excludes `peer`).

## Cursor and upsert contract

The cursor is `<agent session id>:<byte offset after the last complete line>`. `--after C` returns the entries that follow it; an entry whose message grew after the cursor is re-emitted with the same `id` and the new text, so a caller upserts by id (the Desktop store does). A poll reads only the tail after the cursor: the cursor's conversation is parsed from its offset, later conversations from 0, earlier ones not at all. `--tail N` parses what a full read parses and trims only the printed `entries` to the last N (`--before ID`: the N before that entry, `sessionfeed.TailPage`); the cursor and `subagents` stay those of a full read, and `before` names the page's first entry (omitted at entry 0). Legacy Codex ids (`L<offset>`) can repeat across a tab's conversations, so a `--before` on a repeated id fails as ambiguous rather than skipping entries. A `subagents` item's `subagent` object carries `started_at`: the Agent call's time, else, for a marker built from `meta.json` alone (an `--after` read past the call), the meta file's mtime. `subagents` lists every subagent marker of the tab and comes from the sidecar `subagents/*.meta.json` files (tool use id, type, description, finished), not from a transcript parse.

## Subagents

`--subagent T` prints the feed of the subagent started by tool call `T`, read whole (empty cursor): its task as the first entry, its text replies, then the final report. A foreground subagent's report is the parent's `tool_result` for the `Agent` call; a background one reports through its `SubagentHandback` call (text in `input.message`). A background subagent without a hand-back has no report (the parent's result is only a launch notice). A marker known only from its sidecar `meta.json` (the launch call not in the parent transcript) opens too: the lookup searches the feed's `subagents` list. Nested subagents open the same way: the Desktop opens the feed in place in the pane (`SessionChatPath`), and a nested marker inside it opens one level deeper.

## The ledger (migration 00127)

`terminal_sessions.claude_session_id` holds only the latest id (`/clear` and resume swap it). `terminal_session_agent_sessions (terminal_session_id, agent_session_id, first_seen_at)` keeps every id the tab had, so the feed stitches the tab's transcripts in time order with a `separator` entry where a new conversation starts. Ids and times only, no text (FEED-01); rows cascade with the tab.

The rows are written by **SQL triggers on `terminal_sessions`** (`AFTER INSERT` and `AFTER UPDATE OF claude_session_id`), not by Go code: the creating INSERT is in Swift (`TerminalSessionQueries.create`), and a trigger is the one place that sees every write path. Consequences:
- A future migration that **recreates `terminal_sessions`** (the SQLite table-recreation dance) must recreate both triggers (`terminal_session_agent_sessions_ai`, `_au`), or the ledger silently stops filling.
- `internal/db/schema.sql` mirrors the table but not the triggers (only a comment points at 00127).
- The migration backfills one row per existing tab with an id (`created_at` as `first_seen_at`).

Locating transcripts: `LocateAll` finds the workbench's candidate directories (`agentfiles.CandidateDirs`, worktrees included) under `<claude dir>/projects` once per call and stats `<dir>/<id>.jsonl` for every ledger id (no directory listing: a repository's slug prefix matches every worktree's directory, thousands of files). When several directories hold an id, the first path in sorted order wins; a symlink or an id that is not a plain file name is refused. A missing transcript is skipped, not an error. The parser decodes records in parallel batches (512 lines or 4 MiB) and handles them in file order (#2065 Task 11).

## Entry points in the app

The pane is the session's **Workchat** (#711), its second mode beside the terminal (`WorkspacePane.sessionChat`/`WorkspaceView.chat` keep their raw names, so saved layouts stay valid; only titles changed):

- **Session strip toggle** (`WorkbenchSessionStrip`, since 2026-10-20, board #788; polish 2026-10-21, #846 made it one button): one button naming the mode it switches to (Terminal ↔ Workchat) swaps that pane in place — same session, same slot (`WorkspaceLayout.toggleMode`), in a single pane and in a split alike. Over a report or Branch review pane it names the session's remembered mode; it is disabled when that mode already shows in the other pane. ⌃` is unchanged. The strip's `● session ▾` menu replaces its own slot. The Board, Files and Analytics panes' pickers in a split list **Workchat**.
- **⌃`** and View → **Show Terminal** / **Show Workchat** (`WorkchatCommands`, one item titled by the mode it switches to, on while a workbench page shows a session): `WorkbenchesViewModel.toggleWorkchat(projectID:)`.
- **Session rows:** a `terminal` / `bubble.left.and.bubble.right` glyph for the mode the session opens in; the context menu's **Open in Terminal** / **Open in Workchat** record the mode and open the session like a panel click.
- **Remembered mode:** `WorkspaceLayout.workchatSessions` (decoded with `decodeIfPresent`, so a layout saved before Workchat reads as all Terminal), stored with the workbench's layout in UserDefaults, never in SQLite. Every placement of a session (`placing`: panel click, ⌘1…⌘9, the ▾ menu, Work on It, the palette) puts `pane(forSession:)` on screen. A fresh start (a new session, Start fresh) records Terminal, because a fresh agent may stop at a trust or login prompt the Workchat cannot show. A deleted session leaves the set (`forgetSession`, and `loadSessions` prunes `referencedSessionIDs`).

The pane opens scrolled to the newest message, reads the feed once when shown or when the session's state changes and every 3 s while the agent works or has background subagents (`SessionFeedStore.follow`; `SessionFeedPoller` serializes polls: a refresh asked during a run folds into exactly one more run). Any of these reads — the one on open, the one on a state change, each 3 s tick — is skipped while the main window is hidden, minimised or covered (`isTabOnScreen`), so a pane nobody sees spawns no CLI; when the app's windows come back on screen (`AppState.uiVisibility`, #731) after a skipped read, the feed is read at once (`SessionFeedStore.screenChanged`, `ForegroundRefreshGate`, board #589). The store and its CLI lookup are kept per session while the app runs (`WorkbenchesViewModel.feedStore`, #2065 below), never rebuilt on a render. It shows `watchtower` entries as the owner's bubble marked "via Watchtower". A row of the live line's 👥 list opens the subagent in place (#711; the feed draws no subagent card since #2065): the pane keeps a `SessionChatPath`, the bar shows **‹ Back** (also Esc and ⌘[) and `Workchat › <type> › …` with each part popping to its level, the subagent's feed keeps the **Task**/**Report** headings, and the read-only line "Subagents are read-only. Write to the agent in the main Workchat." stands where the composer would be. While a subagent is open the main feed's own poll stops (its `follow` runs only at the root, and **‹ Back** reads it once); the subagent is read on open and again every 3 s while its marker says `running` and the session is active (`SessionFeedStore.followSubagent`, skipped off screen), each read followed by one incremental main read (`readsMainFeed`) so the marker's status is current — the pane reads it from the store's markers (`SessionFeedSubagent.currentStatus`), not from the copy opened. Every CLI read of the store, main or subagent, waits for the one before it, so the pane runs at most one CLI process. The path resets with the pane.

## Workchat composer (#711)

The composer, the permission card and Stop make the pane a way to drive the session. `WorkchatModel` is held per session by `WorkbenchesViewModel.workchat(sessionID:)`, so the draft and the lines on their way survive pane switches; nothing is stored. The composer shows only while the session is live and not finished; a finished one shows "Session finished. The history stays readable."

- **Lines:** `send()` goes through `SessionLineDelivery.deliverLine` with key `.workchat(id)` behind `SessionControl.lineCheck` — PROJ-16's conditions (needs approval, a busy agent or one turning to a line just submitted, the owner's text in the prompt), with no device grant at the Mac. A line keeps its line breaks (owner ask #421, PROJ-12 amended): `\r\n` becomes `\n`, only the ends are trimmed, and it is pasted as one multi-line bracketed paste.
- **Hold reasons** (spec 2026-11-24-workchat-polish §6.3, T7): a line its check held carries `WorkchatOutgoing.holdReason` (`needsApproval` / `agentBusy` / `promptHasText`, read from `lineCheck`/`workchatLineCheck` when the try settles; `.awaitingApproval` sets `needsApproval`; nil behind another line). Captions: "Waiting: answer the permission prompt in the terminal", "Queued · sends in a moment" (or "… when the agent stops" for a hold-until-idle agent at work), "Waiting: the terminal prompt holds text" with the prompt's screen line under it (`WorkchatModel.holdPreview` ← `TerminalCenter.promptPreview`: the cursor row, box borders dropped; display only). Actions on their own row as quiet text buttons: **Send together** (`promptHasText` only: the line is dropped from the queue and delivered again with a gate that ignores `promptHasText`, so the host types it beside the text with no Return and `sharedPrompts` says one Return sends both) and **Cancel**. Send together retries the held entry at its place (`SessionLineDelivery.retryHeld`), only into the run it was held for (else `notSent`); the line keeps the time the override's gate let the writing try go (`sentTogetherAt`, set only once that try wrote it — typed or submitted, now or on a later try; never while it is held or queued again; #2386: the try's time, not the click's), so its echo is the one owner entry from then on that ends with it or holds it as whole words (pasted mid-draft; word boundaries, so it may sit before punctuation) — a files-only line: one that holds its path as a whole token (closing punctuation allowed; glued straight after a word without `/`; a bare path after a quote must close it) or an image marker. A sweep of the held lines tries each as the live queue holds it, so a Send together during a sweep keeps its gate. The reason comes from the try itself (`SessionLineDelivery.holdCause` plus the gate's own reason); a failed state read gives none (generic caption, no Send together). Clear and send is not built (spec C11: Claude Code 2.1.331's Ctrl+C interrupts a working turn).
- **The Mac's prompt mirror and `left_typed` (known limits).** The app's own line takes its `\` from the first of its event and reply; another client's line always leaves the `\` unknown (a Return holds). An owner key the Mac fed just before its own line's request but the host read after the paste counts as before it, so the mirror can miss a `\` the host has; the host stays the authority and still holds the line.
- **States** (`WorkchatOutgoing.State`): `sending` (the first try), `queued` (held or behind another line; **Cancel** drops it with `dropHeld` — a line whose retry is already under way is out of the queue and stays), `typed` and `copied` (waiting for the owner's Return, with **Show in Terminal**), `sent`, `notSent` (the session ended; the text goes back to an empty field).
- **Echo:** a bubble leaves once the feed shows its owner entry — same text with whitespace collapsed, dated at or after `sentAt`. A `sent` line's echo must be dated from 2 s before `deliveredAt` (`WorkchatModel.echoLead`: `deliveredAt` is set after `submitPrompt` returns) to 90 s after it (`WorkchatOutgoing.echoWindow`), so the same text typed in the terminal while the line sat queued is not its echo; past the window it stays as a plain bubble (`/clear` writes no owner entry). `typed`/`copied` lines wait however long. `claimedEntries` keeps one echo for one line.
- **Stop:** the round button while the agent or its subagents work and the field is empty (and Esc in the empty field; with text the button is Send, #2065) calls `SessionControl.interrupt` — one Esc, refused while a permission request is pending (Claude Code draws the prompt before its hook reports it). A refusal sets `stopError` above the field: "A permission prompt is open — answer it on the card or in the terminal", "The session is not running", or the failed check.
- **Permission card:** read with `SessionControl.pendingPermission` on each hook write for the session (`WorkchatModel.PermissionReadKey`: the state kind and the hook stamp), no timer. **Allow** / **Deny** go through `SessionControl.answerPermission`, PROJ-21's guarded compare-and-set, with `decided_by = "Mac"`; the hook then prints "Denied by the owner at the Mac." for a deny. The Deny-only blocks (`PermissionAllowBlock`: shortened summary, settings path) apply: the card shows its note, **Deny** and **Show in Terminal**. A read older than an answer or a newer read is dropped (`permissionReads`). A failed read shows its error on the card, or above the composer when no card is on screen. Codex writes no rows, so it has no card.
- **Show in Terminal** (`WorkbenchesViewModel.showTerminalFromWorkchat`): the Workchat's slot swaps to the session's terminal in place and Terminal is recorded; a terminal already on screen stays.
- **Ask cards:** each open ask of the session (`vm.asks.openAsks`) shows at the end of the feed with **Open Ask**, which opens the ask drawer.
- **Asks in the current mode** (polish 2026-10-21): opening an ask shows its session in the session's remembered mode (regression tests added). After an ask answer is delivered: submitted, held or queued keeps the remembered mode; typed or copied (the owner must press Return or paste) goes to the terminal with the keyboard there.

### Polish (2026-10-21, #846)

- **`queued_command` owner lines:** Claude Code records a line it took mid-turn as an `attachment` of type `queued_command` (`commandMode` `prompt`, `origin` absent or `human`, not `isMeta`). The reader makes it an `owner` entry, or an `ask_answer` entry for "Ask #N answered…". Other origins (task-notification, peer, coordinator) are ignored.
- **`transcript_dirs`** (FEED-03 additive key, #2201 T4): `{<claude conversation id>: <directory of the transcript read for it>}` on a main read (full, `--after`, `--tail`), the folder's or a worktree's project as `LocateAll` picked it; Codex conversations are absent, the key is omitted when none is left and on a `--subagent` read. The Desktop store merges it across reads (`SessionFeedStore.transcriptDirs`) and Open output binds an agent's output to it.
- **`activity`** (FEED-03 additive key): `{tool, summary, started_at, more}` or null. Read from the last 256 KiB of the last conversation's transcript (or the subagent file with `--subagent`) on every call, independent of the cursor: the newest open `tool_use` (no `tool_result` yet). Several Reads show as "N files"; the summary comes from a per-tool table, at most 120 runes, first line. Codex: `custom_tool_call` (summary = the first `cmd:"…"` in the input, else the name) and `function_call` (`command`/`cmd`), paired with their outputs by `call_id`. A missing file gives null silently; any other read error gives a stderr note and null.
- **Live line** (Desktop): a one-line caption row of fixed height (a blank line when empty) between the feed and the composer while the composer shows: tool symbol, summary, " · N more" and an `m:ss` timer from `started_at`. "Thinking…" when the session works with no open tool or after newer agent text; "Agents working · N" in the background state. The row is kept but hidden when the session is not working or while the permission card shows, and cleared when it stops working. A subagent pane keeps the same row and shows its own line only while that subagent runs (its status read from the current marker). The glyph pulses and the line animates with `Motion.toggle`, both off under Reduce Motion. Never an entry, never stored, never sent to the phone (FEED-05 test).
- **Sending while busy:** sessions whose agent `takesLineWhileWorking` (`AgentSessionCaps`: mid-turn input and every mid-turn dialog reported, i.e. Claude Code) go through `SessionControl.workchatLineCheck`: `lineCheck`, except that a working agent (Working, Agents working) does not hold the line; it keeps the hold for a session not live or with no hook state this run, needs-approval, the owner's text in the prompt, settling after the previous line and session gone. The kind is read at each send and try (a pane restored at launch is made before the sessions load); `holdsUntilIdle = !takesLineWhileWorking`, so Codex (it takes a line mid-turn, plan 2026-11-05 Task G7 spike (a), but an MCP form it opens mid-turn raises no state, spike (c)), a shell or a kind not known yet keep the busy hold. While such an agent works the composer says "<Agent> takes your message when this turn ends." above the field (U2, `WorkchatComposer.holdCaption`). A line sent while the agent works shows "Queued · the agent reads it at its next step" until its echo, and that echo has no 90 s cap. A held line reads "Queued · sends in a moment ·" (Claude) or "Queued · sends when the agent stops ·" (Codex, a shell or a kind not known yet) with **Cancel**. The phone's hub uses the same `workchatLineCheck` for its Claude sessions since 2026-10-25 (PROJ-16 amended, ask #614; its echo carries `while_busy`); `lineCheck` stays the strict check for other kinds.
- **Paste and attachments:** since #2065, ⌘V of an image or of long text becomes a token in the field (see the #2065 section below), while a pasted PDF stays a chip. A pasted image or PDF (PNG/JPEG/GIF/WebP, TIFF converted to PNG, the main chat's size limit) is saved to `<workspace>/workchat-attachments/<session id>/<yyyyMMdd-HHmmss>-<n>.<ext>` (UTC stamp; the workspace is the folder of `watchtower.db`). Finder files and drops attach their own paths, with no copy. ⌘V of an image or PDF did nothing before #2201 T5 (the confirmed cause: the plain-text field advertised no image/PDF pasteboard type, so Paste stayed disabled); `PastingTextView` now advertises them and `public.file-url` and validates Paste against its own pasteboard. A Finder-file paste was already accepted by the code; the owner's Finder failure was not reproduced, so no fix is claimed for it. What follows (chips with ✕, the quoting on send, the echo rule) applies to dropped and picked files and the saved PDF; an image token sends its saved file's quoted path in place. Chips above the field carry ✕. On send: the text, then each path on its own line, in double quotes when it has a space, `"` or `\` (those two escaped with `\`); a path with a line break is refused at attach. A paste that cannot be saved, or a refused path, shows `WorkchatModel.attachmentError` under the field (the composer's `attachmentError`) until the next attach or send — the paste inserts nothing instead. Attachments alone can be sent. Echo matching ignores `[Image #N]`/`[image]` markers and the paths. Files older than 7 days are swept at launch, once the session host's reattach is done (`WorkbenchesViewModel.sweepAttachmentsAfterReattach`), except the folders of the sessions live then — the runs that survived the restart included.

## v1 limits

- Polish (2026-10-21): Codex keeps the busy hold. Plan 2026-11-05 Task G7 verified queue-on-Return during a Codex turn (codex 0.159.2: "submitted after next tool call", `cmd/testdata/codex_hooks/SPIKES.md`), but kept the hold: an MCP form Codex opens mid-turn raises no state, so a line could answer it. The launch sweep protects only sessions running once the reattach is done: a session not running loses its pasted files older than 7 days, even if it is resumed later. The phone gets no `activity`.
- Codex sessions (2026-10-17; live agents added 2026-11-02): `sessionfeed.ParseCodex`/`LocateCodex` read the rollout (`$CODEX_HOME/sessions/*/*/*/rollout-*-<id>.jsonl`, the stored `transcript_path` first) in both owner dialects (paginated `item_completed` `UserMessage`/`AgentMessage`, legacy `user_message`/`agent_message`); user text is classified like Claude's (brief, ask answer, Watchtower line). Legacy lines carry no id, so their entry id is `L<line byte offset>`. Codex live agents open from the activity picker; historical dialog parsing remains unchanged. A zstd-compressed rollout (Codex keeps the `.jsonl` name) is read through `internal/rollout.Open`, which detects the zstd magic and decompresses in memory only, capped at 256 MiB of text (2026-11-05, S7): the dialog, live line, activity, drill-in and the terminal title read it like a plain one, and its cursor offsets count decompressed bytes. One that does not decode yields no entries (`unknown_records["<zstd>"]`; past the cap `"<zstd-too-large>"`). Codex subagents join the feed's `subagents` list from the rollout's live agents (S8), the set a drill-in opens, so an agent spawned before the 4 MiB live window is not listed; Codex writes no queued owner line, so a line typed mid-turn is an ordinary owner entry.
- No search, export or sharing. The iPhone shows the tail of a feed only (phase 3 below), no paging into older entries.
- Zero time means no time: the separator, a report entry and a meta-only subagent marker may carry `0001-01-01T00:00:00Z`; the Desktop treats it as unknown and shows no timestamp.
- `--after` and `--subagent` are mutually exclusive (the command refuses both). `skipped` and `unknown_records` count only what that call read.
- A marker whose `meta.json` is not written yet is missing from `subagents` until it appears (it is still in `entries` when its call is after the cursor); a meta-only marker has no time or parent report until its transcript part is parsed.
- A background subagent without a `SubagentHandback` has no report.
- `unknown_records` is noisy on live data (several expected Claude Code record types are not yet on the ignore list); it is a drift signal, not an error.
- An owner line's image thumbnails are read off its text (`WorkchatOwnerImages`), so an image Claude Code recorded only as an image block (no path in the text) still reads `[Image #1]` or `[image]`. A path the owner typed by hand on its own line, naming an existing image, also shows as a thumbnail.
- The in-flight CLI read is not cancelled when the pane goes away; the result is discarded.
- The format of the transcripts is undocumented: a drift degrades to skipped/unknown counts, never a failure.

## Phase 3 — the chat on the iPhone (2026-10-18, board #486)

Spec: `docs/superpowers/specs/2026-10-18-session-chat-iphone-design.md`. Contract: FEED-05; the mobile POC's I-4 is amended for this one exception (the chat crosses to the owner's iCloud, on request only). Transport: [mobile-companion.md](mobile-companion.md).

**Flow.** Opening **Chat** on a session's detail screen enqueues the relay action `session_chat_request` `{session_id?, subagent_id?, tool_use_id?}` (entity = the `terminal_session-<id>` record; `SessionChatRequestHandler` needs no grant, since it only reads). The phone repeats it every 60 s while the screen is open (`SessionChatRequester`, stop keyed by screen so a push/pop does not stop the top screen's loop). An unknown session answers `.notFound` with message `unknown_session`. A subagent request carries both ids (`subagent_id` names the record, `tool_use_id` is what the CLI's `--subagent` takes; one without the other is `invalid_params`), and a `session_id` that differs from the entity is `invalid_params`. The handler replies `.applied()` at once and tells `SessionChatRunner` to watch the session or subagent. The watch counts from when the phone asked (`created_at`): a request older than the watch applies without opening a watch, a younger one ends `created_at` + 5 min (at most now + 5 min) (`.sessionChatRequest` is a session request kind for the relay's 24 h expiry). The phone does not queue a repeat while an earlier `session_chat_request` for the same chat still waits in its outbox.

**Lifetime.** A watch lasts 5 minutes from the last request. The runner runs `watchtower workbench session-feed --session N --json` (or `--subagent <tool_use_id>`) off the main actor, every 3 s while the agent is live and once per watch for a finished session, bounded at 30 s. The result is clipped to the caps and kept **in memory only**: never in the clear on disk (not in `watchtower.db`, FEED-01; not in the hub sidecar) — only the sealed slice record waits in the hub's transport queue. When the watch expires the entries leave the slice window and the publisher deletes the record from the zone. Stopping the runner, and any time no phone is linked, drops every payload for good. `SessionChatSlice` (kind `session_chat`, record `session_chat-<session id>` or `session_chat-<session id>-<agent id>`) is an urgent kind, published after the ask kinds (asks stay first): the runner's `onChange` (a run stored a payload that differs from the last — payloads carry no clock) nudges the publisher's fast lane (`nudge(kinds: [.sessionChat])`, 1 s coalescing, 2 s spacing) and a saved or deleted record asks for the immediate send. A live chat is about 5 s behind.

**Caps** (`SessionChatPayload`, I-8): FEED-02 kinds only (a tool call, thinking or a kind a newer CLI adds is dropped before the cut and not counted), newest 300 entries (`entries_more` counts the cut ones), entry text 4000 characters (`text_clipped`), titles and subagent descriptions 200, and a payload over 600 000 bytes drops the oldest entries until it fits (counted into `entries_more`; each entry is measured once and the payload is encoded once). The payload carries no clock, so an unchanged feed is byte-identical and is not uploaded again. A subagent marker carries `tool_use_id` besides `agent_id`; the phone shows no link for a marker missing either.

**Phone.** Kit mirror `SessionChat` (`Models/SessionChat.swift`, fixtures `session_chat.json`, `session_chat_subagent.json`). Since 2026-10-26 (mobile workbench remote, Task 12) the session screen **is** the chat: `WorkchatView` (`SessionRoute`) over the pure `WorkchatModel` draws the header (workbench, title, one `StateLine` counting m:ss while working, an age while waiting, "as of" the Mac's last contact while it is away), the entries as `ChatBubble`s (owner and ask answers right, agent text left, Watchtower lines and the collapsed brief as captions, no subagent rows since #2065: the toolbar's agents button opens the agents sheet, whose rows push the subagent's own read-only `SessionChatView`), then the phone's own lines, the permission card and the session's open asks (quick answers in place, else **Open**) at the foot of the feed, and the pinned `WorkchatComposerBar` ("Message the session…"). The report and timeline moved behind the actions menu (`SessionReportView`). Waiting states: "Asking your Mac…", then after 60 s without a record "Your Mac has not sent this chat yet. Is it awake?". **The composer is on the workchat only**, and only for a device allowed to type (PROJ-16): a line typed from a subagent screen would reach the main agent, not the subagent. A line the Mac applied while a Claude agent worked (`result.while_busy`) is captioned "Queued · the agent reads it at its next step"; A Codex (or any non-Claude) session gets no composer and no Finish: the phone cannot yet tell whether its Mac takes Codex lines (since plan 2026-11-05 Task G7 a Mac takes them when Codex is idle, an older Mac refuses them; Task A5 publishes the capability), so the bar says "Write to Codex sessions on the Mac." (`TypingHint.macOnly`, final review 2026-10-26). A sent line shows as a pending bubble while it waits in the outbox, then as a local bubble after the Mac applied it, until an `owner` entry with the same text dated at or after the send arrives or 90 s pass.

## Live activity and agents (2026-11-02, #1481)

The existing Desktop caption slot above the composer now uses `WorkchatLiveLine` and the pure
`WorkchatLivePresentation`. It shows the current tool or `Last · …` (last completed tool in the
current turn), never both as separate rows. With no recorded action it says `Working…` for both
providers. The compact `person.2` count opens a click-only popover of flat agent rows; selecting one
opens its existing read-only chat in place. No extra panel, tool entries, database copies or mobile
activity publishing. Permission prompts keep hiding the whole line. The existing serialized 3 s
poll and off-screen gates are unchanged.

`session-feed --json` adds `live`, `live_ok` and optional `live_error`; `activity` retains its exact
old keys and open-call semantics (owner approval ask #932; design ask #933). The cursor-independent
snapshot contains `observed_at`, `conversation`, `turn_at`, `turn_active`, `current`, `latest`,
`agents`, `agents_state`, `agents_more`, `steps` and `steps_more`. `steps` are the current turn's
tool calls in start order (finished ones with `completed_at`), read from the same 4 MiB `LiveOf`
window and capped at the last 40 plus any still-open older step; `steps_more` counts the finished
steps cut; `[]` when the turn ended, never null. Each action has `id`, `tool`, `summary`, `started_at`,
`completed_at`, `more`; each agent has `ref` (the unchanged subagent-ref wire shape), `started_at`,
`action`, `can_open`. Arrays are always arrays. Unknown/truncated lifecycle is explicitly `unknown`,
never a zero count. A failed hint has `live_ok:false` and a short generic `live_error`; a successful
feed must not silently preserve a previous action as current. Older CLI payloads decode and display
`Activity unavailable` with Retry.

The reader bounds the main tail to 4 MiB and returns at most 32 agent records, active first; omitted
active records are counted in `agents_more`. A Claude main session's agent set comes from its
`subagents/agent-*.meta.json` sidecars (every launched agent has one; a launch refused with `is_error`
has none and counts as finished), so a transcript longer than the window does not make the count
unknown, and finished agents past the 128-candidate inspection budget are dropped without making it
unknown either; up to 1024 sidecars are read per poll, more is `unknown` (#2393). Background and foreground launches both
write a sidecar. An unfinished sidecar whose launch is outside the window and whose own transcript
(`agent-<id>.jsonl`, or the sidecar itself while that is not written yet) is silent for over an hour
is an agent killed with its process (its sidecar never gets `finished`) and is not counted; an
unreadable one makes the state `unknown`. A cut window with no sidecars at all stays
`unknown`, and so do more than 128 unfinished candidates. Codex and sidechain
reads still see agents only in the window, so a cut keeps them `unknown`. Each child hint reads at most 256 KiB, without nested
snapshot recursion. Claude tools pair by tool-use id, with subagent status from sidecar metadata;
launch tool completion does not finish a background agent. Codex supports response-item function
and custom calls, legacy `collab_agent_spawn_end`/resume/close/waiting/interaction events, and
paginated `CollabAgentToolCall` items (camel/snake field dialects). Tool-result spawn acknowledgments
are also normalized. A child's own later turn-completion event updates its status even before the
parent waits. Main-turn completion clears current/latest but retains live background agents.

Codex drill-in selectors are `codex:<UUID>` and must be discovered in the parent's lifecycle. The
reader locates the UUID only beneath the parent's sessions root and verifies the child's first
`session_meta` declares that exact parent; direct symlink files, escaped paths and unrelated child
threads are refused. Nested drill-in is limited to eight levels. The source schema was checked
against local `codex app-server generate-json-schema --experimental`; all committed tests use
synthetic events.

The store tracks live failures separately from feed failures and invalidates pending live reads on
idle/Stop, so an old read cannot reappear in the next turn. At 10 s without a successful snapshot,
the line becomes `Activity out of date · Ns ago`; a failure becomes `Activity unavailable`. Retry
uses the same poller. Both warnings remove elapsed clocks, disable the count and close an open
picker; the picker projection also returns no running rows for stale/failed data. Current calls
may pulse, Last and warnings never do, and Reduce Motion disables the pulse. The old complete
snapshot is kept only to compute its age; it never masquerades as fresh work.

**v1 limits and contracts.**
- A marker whose status is neither `running` nor `finished` (an unknown status, a status a newer Mac adds) shows in neither section, on the Mac and on the phone.
- The phone's Done holds only the markers inside the slice's newest 300 entries.
- Codex Done is what the 4 MiB live window shows (C4): an agent spawned before it is not listed.
- Codex subagent markers live only in the feed's `subagents` list (`feed.Subagents`), and the phone's slice sends only the entries, so a Codex session never shows the phone's agents button.
- Nested Done rows in a subagent screen come from that screen's markers: they have no start time and keep the CLI's order.
- A finished agent built from `meta.json` alone (an `--after` read past the Agent call) takes the file's mtime as `started_at`, which may be its finish time, so it can sort above an agent that started later.
- Legacy Codex ids (`L<offset>`) can repeat across a tab's conversations; a `--before` on such an id fails as ambiguous and paging ends quietly (a permanent refusal, not an error bar), as does an id no longer in the feed.
- Paging stops by matching the Go error texts "is ambiguous" and "no such entry" (`SessionFeedStore.refusesBefore`); both sides pin them (`TestTailPage_AmbiguousBeforeIsAnError`, `TestTailPage_UnknownBeforeIsAnError`; `SessionFeedStoreTests.testEarlierPageWithAPermanentlyBadBeforeStopsPaging`).
- A session open in a pane and in Branch review shares one store.
- A turn longer than the live window shows the steps the window holds and counts nothing for the part it never saw. No steps on the phone.
- Tokens are plain text in the field, not chips. A token is one only while its number has a payload of the same kind and the draft holds its label once: the same bracket text typed by hand is neither deleted whole nor expanded, and a typed copy of a live label turns that token literal too (its payload is dropped).
