# Owner identity (2026-09-25, decision 15 of the 2026-09-13 feature audit)

- Watchtower's only notion of "the owner" used to be `db.GetCurrentUserID()` — Slack account #1's `current_user_id`, hardcoded — so a Google-only or Jira-only install (no Slack) had no owner at all, and everything keyed on it (day plan, briefing, inbox, tracks) silently no-op'd while its UI stayed visible. `internal/db/owner.go` replaces it with one resolver: `(*DB) ResolveOwner() (Owner, error)`, a short orchestrator over one function per ladder rung plus one per enrichment field (keeps `ResolveOwner` itself under the repo's complexity gate). **Ladder, first match wins:** `slack_accounts` row `id = 1` with a non-empty `current_user_id` and `status != 'removed'` (`ID` = that value unchanged, `Source = "slack"`) → first `google_accounts` row by id with a non-empty email (`ID = "google:" + lower(email)`, `Source = "google"`) → first **enabled** `jira_accounts` row by id with a non-empty `owner_account_id` and `status != 'removed'` (`ID = "jira:" + owner_account_id`, `Source = "jira"`) → first **enabled** `linear_accounts` row by id with a non-empty `owner_user_id` and `status != 'removed'` (`ID = "linear:" + owner_user_id`, `Source = "linear"`; Linear rung added 2026-10-15, ask #162) → first `email_accounts` row (IMAP or Outlook) by id whose `email_address` contains an '@' after its first character (a bare login such as `jdoe` is no identity) (`ID = "email:" + lower(email_address)`, `Source = "email"`; added 2026-10-17, ask #307 — last, so no existing owner id changes; a CalDAV account alone still yields no owner) → `Owner{}` (unknown). **Enrichment is independent of which rung won** — `SlackUserID`/`Email`/`JiraAccountID`/`DisplayName` are each filled from whichever connected source has them (Slack user row → Google account → Jira `owner_*` columns → Linear `owner_*` columns for email and display name → the mailbox address for email; the existing `jira_user_map` Slack↔Atlassian bridge as a last resort for `JiraAccountID`; `LinearUserIDs` lists the owner's Linear user id on every enabled, non-removed Linear account), so e.g. a Slack-rung owner still gets a `JiraAccountID` when one is known. `(*DB) RequireOwner()` is `ResolveOwner` plus `db.ErrNoOwner` (`"no owner identity: connect Slack, Google, Jira, Linear or an email account first"`) when unknown, used at every user-triggered site that needs the owner. The Swift twin, `OwnerQueries.resolve(_:)` (`WatchtowerDesktop/Sources/WatchtowerCore/Database/Queries/OwnerQueries.swift`), copies the same SQL and enrichment order and names `internal/db/owner.go` in its doc comment (the `SlackAccountID.swift`/`namespace.go` dual-path precedent).
- **Profile is a singleton, not keyed by rung.** `user_profile` still has a `slack_user_id` primary key column, but it now holds `Owner.ID` of whatever shape. `GetOwnerProfile(owner)` reads the exact-key row, else the most recently updated row in the table (the single-owner app has at most one real row); `UpsertOwnerProfile(owner, p)` re-keys that fallback row to `owner.ID` inside the same write before upserting, and in that same transaction moves every briefing and day plan keyed under another id onto `owner.ID` (`UPDATE OR IGNORE`: a date the owner already has keeps its row) — so an owner switching rungs (Google connected first, Slack connected later) keeps exactly one profile row with its old content instead of orphaning it. Swift mirrors both (`ProfileQueries.fetchOwnerProfile`/`upsertOwnerProfile`). Onboarding writes before any owner exists park under the reserved key `"pending:owner"` (`ProfileQueries.pendingOwnerKey`, Swift-only — a controller ruling under the onboarding-unstick house rule: onboarding must never dead-end on a no-owner install) and are silently adopted by whichever rung resolves first, on either side, since the fallback keys on "most recently updated row," not on the literal key.
- **No silent skip (OWNER-02).** Every user-triggered CLI command that needs the owner (`day-plan generate|show|list|reset|check-conflicts`, `briefing generate|show|list`, `tracks create`, `profile`, MCP `get_today_briefing`) now exits non-zero with `db.ErrNoOwner` instead of printing "No current user set" and exiting 0. `briefing.RunForDate` returns `ErrNoOwner` instead of `(0, nil)`, so "no owner" is no longer conflated with "nothing to summarize." The daemon treats `ErrNoOwner` as a **benign** skip: no attempt-budget charge (the wave-4 `…BenignNoUserSkipDoesNotConsumeBudget` tests keep passing), and `logNoOwnerOnce` (`internal/daemon/owner.go`) logs one line per phase per UTC day instead of every ~15-minute cycle. The inbox pipeline gates on `Owner.Known()` instead of the Slack id, so a Google-only install now runs Calendar/Gmail detection that used to no-op entirely; Jira mention detection and auto-resolve match on every Atlassian id the owner maps to (`JiraAccountID` plus every `jira_user_map` id), not just the first. Desktop: Day Plan, Briefings and the empty Inbox show an explicit `NoOwnerEmptyState` ("Connect Slack, Google, Jira, Linear or an email account so Watchtower knows who you are", linking to Settings → Connections via `AppState.settingsTab`), Day Plan and Briefings hide Generate/Regenerate/Reset, and Home's Getting ready card for Inbox, Briefing or Day Plan reads `.needsSource(.ownerIdentity)` ("Connect Slack, Google, Jira, Linear or an email account to get this", with **Open Connections**; "Waiting for your Jira identity…" via `.ownerIdentityPending` while an enabled Jira/Linear account still lacks its owner id, `OwnerQueries.pendingIdentitySource`; still a card, not a Connect row, so the zone stays open) whenever `AppState.owner` (refreshed on DB open, on every Slack/Google/Jira/email account-list reload, and on appear of those three screens) is unknown; a failed Generate now surfaces the CLI's stderr instead of being discarded.
- **A freshly connected Jira account can show the no-owner empty state briefly** — `owner_account_id` is filled at connect time best-effort, but a connect-time `/myself` failure (or an account enabled without ever being freshly connected) leaves it empty until the lazy per-daemon-start fill in `wireJiraSyncers` succeeds.
- An existing Slack install sees zero behavior change: same owner id, same profile row, same day plans/briefings.
- Contracts: `docs/inventory/owner-identity.md` (OWNER-01 one owner one ladder, OWNER-02 no silent skip). Design: `docs/superpowers/specs/2026-09-25-no-slack-owner-identity-design.md`.
- **Stream digests read IMAP/Outlook mailboxes too (closed 2026-10-17, board #615).** Readiness counts `email_accounts` as mail for Stream Digests, and `ideas.runEmailDigests` now mines those mailboxes as well as Google accounts, so an IMAP/Outlook-only install gets the stream digests its card promises. See the IMAP entry in `docs/features/ideas-decisions-registry.md`.
- **A rung switch keeps today's briefing and day plan.** `(*DB) AdoptOwnerRows(ownerID)` (`internal/db/profile.go`) checks with a read whether any profile, briefing or day plan is keyed under another id and, only then, re-keys them in one write transaction. `briefing.RunForDate` and `dayplan.Pipeline.Run` call it before looking for today's row, and the daemon's `dayPlanOwner` before its own check, so an owner moving from `email:…` to `jira:…` (or losing the first mailbox) never generates a second briefing or plan for the day.
