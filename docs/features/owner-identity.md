# Owner identity (2026-09-25, decision 15 of the 2026-09-13 feature audit)

- Watchtower's only notion of "the owner" used to be `db.GetCurrentUserID()` — Slack account #1's `current_user_id`, hardcoded — so a Google-only or Jira-only install (no Slack) had no owner at all, and everything keyed on it (day plan, briefing, inbox, tracks) silently no-op'd while its UI stayed visible. `internal/db/owner.go` replaces it with one resolver: `(*DB) ResolveOwner() (Owner, error)`, a short orchestrator over one function per ladder rung plus one per enrichment field (keeps `ResolveOwner` itself under the repo's complexity gate). **Ladder, first match wins:** `slack_accounts` row `id = 1` with a non-empty `current_user_id` and `status != 'removed'` (`ID` = that value unchanged, `Source = "slack"`) → first `google_accounts` row by id with a non-empty email (`ID = "google:" + lower(email)`, `Source = "google"`) → first **enabled** `jira_accounts` row by id with a non-empty `owner_account_id` and `status != 'removed'` (`ID = "jira:" + owner_account_id`, `Source = "jira"`) → `Owner{}` (unknown). **Enrichment is independent of which rung won** — `SlackUserID`/`Email`/`JiraAccountID`/`DisplayName` are each filled from whichever connected source has them (Slack user row → Google account → Jira `owner_*` columns → the existing `jira_user_map` Slack↔Atlassian bridge as a last resort), so e.g. a Slack-rung owner still gets a `JiraAccountID` when one is known. `(*DB) RequireOwner()` is `ResolveOwner` plus `db.ErrNoOwner` (`"no owner identity: connect Slack, Google or Jira first"`) when unknown, used at every user-triggered site that needs the owner. The Swift twin, `OwnerQueries.resolve(_:)` (`WatchtowerDesktop/Sources/WatchtowerCore/Database/Queries/OwnerQueries.swift`), copies the same SQL and enrichment order and names `internal/db/owner.go` in its doc comment (the `SlackAccountID.swift`/`namespace.go` dual-path precedent).
- **Profile is a singleton, not keyed by rung.** `user_profile` still has a `slack_user_id` primary key column, but it now holds `Owner.ID` of whatever shape. `GetOwnerProfile(owner)` reads the exact-key row, else the most recently updated row in the table (the single-owner app has at most one real row); `UpsertOwnerProfile(owner, p)` re-keys that fallback row to `owner.ID` inside the same write before upserting — so an owner switching rungs (Google connected first, Slack connected later) keeps exactly one profile row with its old content instead of orphaning it. Swift mirrors both (`ProfileQueries.fetchOwnerProfile`/`upsertOwnerProfile`). Onboarding writes before any owner exists park under the reserved key `"pending:owner"` (`ProfileQueries.pendingOwnerKey`, Swift-only — a controller ruling under the onboarding-unstick house rule: onboarding must never dead-end on a no-owner install) and are silently adopted by whichever rung resolves first, on either side, since the fallback keys on "most recently updated row," not on the literal key.
- **No silent skip (OWNER-02).** Every user-triggered CLI command that needs the owner (`day-plan generate|show|list|reset|check-conflicts`, `briefing generate|show|list`, `tracks create`, `profile`, MCP `get_today_briefing`) now exits non-zero with `db.ErrNoOwner` instead of printing "No current user set" and exiting 0. `briefing.RunForDate` returns `ErrNoOwner` instead of `(0, nil)`, so "no owner" is no longer conflated with "nothing to summarize." The daemon treats `ErrNoOwner` as a **benign** skip: no attempt-budget charge (the wave-4 `…BenignNoUserSkipDoesNotConsumeBudget` tests keep passing), and `logNoOwnerOnce` (`internal/daemon/owner.go`) logs one line per phase per UTC day instead of every ~15-minute cycle. The inbox pipeline gates on `Owner.Known()` instead of the Slack id, so a Google-only install now runs Calendar/Gmail detection that used to no-op entirely; Jira mention detection and auto-resolve match on every Atlassian id the owner maps to (`JiraAccountID` plus every `jira_user_map` id), not just the first. Desktop: Day Plan and Briefings show an explicit `NoOwnerEmptyState` ("Connect Slack, Google or Jira so Watchtower knows who you are", linking to Settings → Connections via `AppState.settingsTab`) and hide Generate/Regenerate/Reset whenever `AppState.owner` (refreshed on DB open, on every account-list reload, and on appear of those two screens) is unknown; a failed Generate now surfaces the CLI's stderr instead of being discarded.
- **A freshly connected Jira account can show the no-owner empty state briefly** — `owner_account_id` is filled at connect time best-effort, but a connect-time `/myself` failure (or an account enabled without ever being freshly connected) leaves it empty until the lazy per-daemon-start fill in `wireJiraSyncers` succeeds.
- An existing Slack install sees zero behavior change: same owner id, same profile row, same day plans/briefings.
