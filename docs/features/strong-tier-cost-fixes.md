# Strong-tier cost fixes — daemon cadence gates + attempt budgets (2026-09-13)

- Audit finding H2 / owner decision 9: four daemon-side pipelines were re-running strong-tier AI calls on cadences that didn't actually check whether new work existed, or without any budget on repeated failure. No new config keys anywhere in this wave — every threshold is a code constant.
- **Daily rollup (`internal/digest/pipeline.go`'s `runDailyRollupForDate`):** previously regenerated every cycle it was reached. Now gated on new material — an existing daily row for today is left alone unless a channel digest newer than that row's `created_at` has landed since (lexical string comparison on the shared `created_at` format; a re-upserted channel digest with changed content always bumps `created_at`, so "new" and "changed" are the same signal here). `storeDigest` gained a `resetReadOnWrite bool` parameter; only the daily call site passes `true` (a new `db.ResetDigestReadAt` clears `read_at` so a regenerated rollup surfaces as unread again) — the channel and weekly call sites pass `false` and are otherwise untouched, and `false` is pinned to never clear `read_at` even across an unrelated re-upsert of the same row.
- **Day plan / briefing (`internal/daemon/daemon.go`):** a real-attempt budget, `maxDailyAIAttempts = 3` per pipeline per calendar day, persisted to `day_plan_attempts.txt`/`briefing_attempts.txt` (the `last_briefing.txt` marker-file family, so it survives a daemon restart — an in-memory-only counter would not). `shouldRunDayPlan`/`shouldRunBriefing` gain an early-return once the day's budget is spent; `runDayPlanPhase`/`phaseBriefing` record an attempt **only when the underlying `Run`/`RunForDate` call returns a real error** — a benign skip (`(0, nil)`/`(nil, nil)`, e.g. no current user, nothing to summarize) never consumes budget. A one-time "giving up for `<date>` after 3 failed attempts, will retry tomorrow" log line fires exactly when the 3rd failure spends the budget, not on every subsequent silent skip that day — an owner can now tell "not generated yet" from "gave up for today" instead of an unbounded stream of identical `pipeline_runs` error rows.
- **Next-step per-target budget (migration 00068, `next_step_attempts`/`next_step_attempted_at` on `targets`):** the daemon's next-step generator gets the same 3/day cap, but **per target** rather than daemon-wide (`internal/targets/nextstep.go`'s `nextAttemptCount`) — a target edited since its last attempt, or whose last attempt was a prior UTC calendar day, gets a fresh budget of 3 rather than one straggler call. `GetTargetsNeedingNextStep`'s eligibility predicate excludes only a target that has exhausted today's budget with no fresh edit; `GenerateAllNextSteps` now returns `(done, attempted, err)` so an all-failed batch (`attempted > 0 && done == 0`) records `pipeline_runs.status='error'` instead of the previous silent `status='done'`. **Fixed in wave 5 (2026-09-14):** the "edited since" escape hatch keys on raw `updated_at`, and `RecomputeParentProgress` used to bump a parent's `updated_at` on every call (from `CreateTarget`/`UpdateTarget`/`UpdateTargetStatus`/`DeleteTarget`/`PromoteSubItemToChild`) regardless of whether the computed average actually changed, so a parent with actively churning children could look "freshly edited" every cycle and exceed the cap. All five routes funnel through the single `recomputeParentProgressOn` implementation, which now writes the row (and bumps `updated_at`) only when the newly computed progress differs from the stored value (`AND progress != ?` on the UPDATE) — the ancestor walk itself is unchanged, so progress drift from a direct write is still repaired at every level.
- **Memory rewrite/reflect/map "done today" memo** — see the Memory section above (migration 00069, `memory_step_state`) and its paired confirm-evidence-dedupe fix.
- Left open, needing an owner call, not decided by this wave: `digest.channel` (strong) vs `digest.channel_batch` (light) tier inconsistency — see `docs/audit/2026-09-13-feature-audit/README.md`.
