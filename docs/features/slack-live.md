# Slack Live — the owner's own Claude or ChatGPT Slack connector (2026-11-14, #1709; chat #1764, automations #1765)

Spec `docs/superpowers/specs/2026-11-14-slack-full-and-live-design.md`, plan `docs/superpowers/plans/2026-11-14-slack-live-plan-a.md` (plan A; the entry into Full shipped with plan B, `docs/superpowers/plans/2026-11-17-slack-full-plan-b.md`, see [slack-full.md](slack-full.md)). Live is the Slack connector of the owner's own Claude or ChatGPT account. Watchtower ships no Slack app for it and stores nothing it returns beyond the chat transcript (decision D6, strict). It is a layer over the local copy, never a replacement: the chat and automations use local data first and the connector for gaps. Contracts: LIVE-01 (`docs/inventory/chat.md`), SLACKMODE-01 (`docs/inventory/slack-accounts.md`); AUTO-01/02 unchanged.

## The mode and the status table

- Migration `00188_slack_live.sql`: table `slack_live_status` (team id, provider `claude`/`codex`, status `ok`/`not_connected`/`needs_admin`/`no_plan`/`unavailable`, error class, `checked_at`, `connector_id`), plus `chat_conversations.live_slack_since` and `automation_runs.live_slack`. `checked_at` is fixed-width UTC RFC 3339 nanoseconds so string order is time order. `db.UpsertSlackLiveStatus` is newest-wins and keeps the stored `connector_id`; `ListSlackLiveStatus` is newest first.
- `internal/slackmode` (`Derive`, `LiveOn`) and the Swift twin `SlackMode.swift` derive Full / Live / Off from the same JSON cases (SLACKMODE-01). The mode is never stored. Go's caller is `automations.SlackMode` (the event-trigger refusal below).

## The probe (`internal/slacklive`, `watchtower slack live probe --provider --if-older --json`)

One real read call, because listing tools proves nothing (Codex lists the Slack tools before the OAuth and then fails `Unknown tool`).

- **Claude:** the chat's stream-json launch shape, waits for `mcp_status` of the claude.ai Slack connector (15 s), calls one read tool. `claudeArgs()` adds `--setting-sources project,local` and `--disallowedTools` for the six write tools; any other control request is answered with a control error. The child runs in the chat's file sandbox (`slacklive.ClaudeProbe(wrap)` with `chat.ChildSandbox.Command`, CHAT-05); no sandbox = `unavailable/sandbox`, nothing started. Before any child, `claudeSlackLiveProbe` gives a fixed `not_connected` verdict, no child, when the organization's policy (`AllowClaudeAITools`, `AllowedAIProviders`: class `policy`), the owner's connectors switch (`connectors_off`) or the Slack connector's own switch (`disabled`) keeps the connector off (`claudeSlackLiveOff`, shared with automations). Codex gets `not_connected/policy` when `AllowedAIProviders` leaves it out. The CLIs come from `claude_path`/`codex_path` when set.
- **Codex:** `codex exec` with apps on, read-only. The connector id comes from the apps cache (`cache/codex_apps_tools`) before launch. A missing cache entry costs one warm-up run with no tool callable (`codex.WarmUpAppOverrides`: `features.apps`, default tools off, every configured app and tool off), then a re-read; still missing → `connector_id_unknown`, no further run. Team ids come from `structured_content.teams[].id`. The owner's MCP servers are off in both runs (`codex.NoMCPServerArgs`).
- **Rows:** an `ok` verdict writes the identified teams (Claude: the permalink domain matched to `slack_accounts.team_domain`; Codex: T-ids) and team `''`; accounts the provider did not show get `not_connected/workspace_not_connected`. Any non-ok verdict writes `''` plus every Slack account's team id, so a stale `ok` cannot survive. A missing CLI is `not_connected/cli_missing`. Each CLI child records one `llm_calls` row (`slacklive.ProbePurpose` = `slack.live_probe`, shown in Usage as "Live Slack checks", `LLMPurposeNames`). Per-transport choices (argv, how to read the status) live in the `slackLive` row of `cmd/transport_wiring.go` (`slackLiveFor`, exact by provider id); Ollama has none. `classify` reads plan and unknown-tool wording only from tool text.
- **When:** Connections → Slack opens (`SlackLiveStatusCenter`), the first local Slack tool of a main chat (the watcher is on every main chat; it probes the session's actual provider, only one with a `slackLive` wiring) with no row newer than 24 h (one background probe), and a chat or automation use of a connector tool (writes the status; Claude `claude_ai_Slack:<name>`, Codex `codex_apps:slack.<name>`, only names in `slacklive.ReadTools`; writes never write a status). A use writes only a verdict about the connection (`slacklive.ConnectionVerdict`): an ordinary tool error (`read_failed`: a missing channel, bad arguments; or one call's `timeout`) leaves the status alone. Never from the daemon on a timer.
- **Tool lists:** `internal/slackconnector` is the one list (14 read tools, `slack_search_emojis` included, and six write tools) and the step-name prefixes; `connectorpolicy`, the probe, the chat and automations read it.

## Chat (main surface only)

- **Claude:** `connectorpolicy` rows for `claude_ai_Slack`: the 13 read tools Allow, the six write tools Ask (the normal connector approval card). `claudeSlackLive` decides when the prompt block applies (connectors on, Slack not switched off, newest Claude row `ok` or absent).
- **Codex:** apps stay on only for the main chat (`Client.SetChatApps`), only with a ChatGPT login (`codex.ChatGPTLogin`) and an `ok` probe row with a connector id (`codexSlackConnector`). The read-only allow-list is built by `codex.ReadOnlyAppOverrides(home, id, ReadTools)` from the owner's own `config.toml` (the app on with default tools off and the listed tools on; every other configured app and every unlisted configured tool of it off). A missing config adds nothing; an unreadable or invalid one is an error and the chat gets no apps and no Live promise (fails closed). App ids and tool keys must match `^[A-Za-z0-9_-]+$`. With Live only (no Full), a Codex chat cannot send to Slack: sending is Watchtower's `send_slack_message`, which needs Full (v1 limit).
- **Prompt:** `PromptOptions.SlackLive` adds `slackLiveBlock`: local tools first, `coverage` for the gaps, say which part came from Live.
- **`list_messages` (R9):** returns `{"messages":[…],"coverage":{scope,synced_through,backfill_from,channel_in_scope}}` (`db.SlackCoverage`) only on the main chat surface; every other surface keeps the bare array. `slackMessageSources` accepts both shapes. `channel_in_scope` is false for a channel with **Stop syncing** on (`channel_settings.sync_excluded`, [slack-adaptive-sync.md](slack-adaptive-sync.md)), so the chat goes to Live for it.

## LIVE-01: marked turns stay out of lasting stores

- **Writer (R10):** the Desktop turn store (the only writer of chat rows) sets `live_slack_since` to the Live turn's assistant message id when a Slack step starts (`ChatTurnStore.stepStarted`, `LiveSlackMark.markIfSlackStep`) and again at `finalizeTurn` (`markIfUsed`) as a backstop, whichever comes first; set once, never moved. Marks on the step names Go sends (`displayToolName`): `claude_ai_Slack:<tool>` and `codex_apps:slack.<tool>`, any tool of either (write tools included). The names come from `slackconnector.ClaudeStepPrefix`/`CodexStepPrefix`; `TestLIVE01_StepNamesFixture` runs every connector tool through the real Claude translator and a `codex exec` stream into `internal/slacklive/testdata/slack_step_names.json`, which the Swift guard marks against.
- **Readers:** `db.ChatNotLiveSlack` (`m.id < live_slack_since` or no mark) is applied in `ListChatTurnsForIdeas`, `ListOwnerChatTurns`, `OwnerChatTurnExists`, `ListOwnerChatTurnsSince`, `ListRecentChatTurns`; the kb `chat_artifact` source skips a marked conversation; `ChatArtifactQueries.keep` throws `ChatArtifactKeepError.liveSlack` and the panel shows the reason. `instructions remember` in a marked conversation stores a line only when it is verbatim in the owner's message (`db.LiveSlackOwnerLineOK`, code `not_owner_text`). The owner's prompt of the Live turn precedes the mark and stays readable.
- **Guards:** Go `internal/db/live01_test.go`, `TestLIVE01_KeptArtifactSkipped`, Swift `LiveSlack01GuardTests` (its reader list is file-level, not function-level).

## Automations (`slack:live`)

- **Manifest:** a verb of `slack`, unscoped (`slack:live@T1` is refused: "slack:live takes no @scope"; `capabilitySpec.unscopedVerbs`). `Manifest.SlackLive()`; `FeedsSourcesToLLM` counts it as a source. Connector writes are not granted: they go through `send_slack_message` proposals (AUTO-02).
- **Unreadable permissions:** `AutomationSlackLive` counts permissions it cannot parse as `slack:live`, so the hourly limit fails closed.
- **Hourly (D15):** the validator (`checkLiveCadence`) checks the cron's time-of-day firings (minute and hour fields, including the wrap from the last firing of a day to the first of the next; day fields ignored), then DST windows around the zone transitions of a fixed reference year (`liveCadenceRefYear`, so the verdict never depends on today's date). The executor enforces it for every trigger, dry runs counted (`liveSlackLimited` before the claim in `poll.consider` and `ExecuteInlinePinned`): a schedule or catch-up run is compared by `scheduled_for` with the previous run's; any other pair by start times with a 2-minute tolerance (`liveSlackStartTolerance`, so 58 minutes passes). Runs ended by the limit never started and do not count (`LimitQueuedLiveSlackRun`, `LastLiveSlackRunStart`). A limited run ends `cancelled`/`not_runnable` with "Live Slack: at most once an hour".
- **Built-ins:** `slack:live` is refused in built-in manifests, owner copies included (`manifest.go`, `scope.IsBuiltin()`).
- **Full triggers:** `CheckRecipePolicy` refuses a `slack:live` recipe with a `slack.*` event or reaction trigger when the Slack mode (`automations.SlackMode`) is not Full (`HasFullSlackAccount`: enabled, not removed, status ok), at save and at `save_automation` apply.
- **Sync triggers:** `slack:live` with `trigger.sync` (a watch recipe) is refused at parse, so at save: a sync-slot run runs inline every cycle, outside the hourly check. `ExecuteBuiltinInline` still applies the hourly limit as a backstop.
- **Claude child:** `ai.Client.SetStreamJSONInput`/`SetStreamJSONHooks` switch the launch to stream-json, drop `--strict-mcp-config`, bound the drain after the result to 5 s (`streamDrainGrace`), wait up to 15 s for the connector (none → the agent runs without Slack). The child runs in the chat's file sandbox (`StreamJSONHooks.Wrap` = `chat.ChildSandbox.Command`, CHAT-05); a stream-json run without a wrap is refused (`ai.ErrStreamJSONNoSandbox`), and no sandbox fails the run. Live is off before launch — today's argv, no connectors — when `claudeSlackLiveOff` says so (policy `AllowClaudeAITools`/`AllowedAIProviders`, the connectors switch, the Slack connector switched off) or the newest Claude probe is a known failure (`claudeAgentSlackLive`). Whenever a `slack:live` agent runs without the connector, the agent step's summary says why in `slack_live_unavailable` (also for Codex). The gate allows the read tools, denies other `mcp__claude_ai_Slack__*` tools ("use send_slack_message") and every other tool. Non-Live runs keep their argv byte for byte (`TestAgentRun_NoSlackLiveKeepsArgv`).
- **Codex child:** same decision and `ReadOnlyAppOverrides` as the chat, against the run home; any error means no apps (and `slack_live_unavailable`). `Client.SetToolCallObserver` marks use.
- **Marking and outputs (D14):** `MarkAutomationRunLiveSlack` sets `automation_runs.live_slack` when the agent used Live (even if the call then failed). The run's outputs stay in the Inbox; `ListAutomationOutputsSince` skips Live runs, so the briefing's FROM YOUR AUTOMATIONS block does not carry them. Denied connector writes are recorded in the agent step's summary as `slack_live_denied`.

## The screens (plan B, screens spec `docs/superpowers/specs/2026-11-15-slack-full-live-screens-design.md`)

- **Connections → Slack** (`SlackConnectionDetail` on `SettingsSection`s): the shared-app banner, **Slack mode** (`SlackModeSection`), the setup record rows, **Connect your workspace's app** (folded behind **Connect another workspace…** in Full), then the workspaces. `SlackModePresentation` owns every string: the chip (`SlackMode.derive` plus the display-only **Shared app** override, which needs an enabled, not removed, `ok` flagged account), the summary, and the Live block — one row per provider from its newest probe batch (ask #1525; `liveVerdicts`/`newestBatches`, the same reduction the chip uses), the status/error-class text, the age ("just now", N min, N h under 48 h, N d, refreshed every minute), and the block states (loading, empty, rows, busy, read failed with **Try again**, probe failed keeping **Check again**). `SlackLiveStatusCenter` keeps the probe error and the read error apart (`lastError` = read ?? probe) and gains `hasRead`.
- **`needsFullSlack`** (`ReadinessSource.fullSlack`; "Needs your workspace's Slack app. Live answers in Chats only.", **Connect workspace app** → Connections → Slack): a Slack feature, or an any-source feature with nothing else connected, while the mode is Live only; `off` still wins; a shared-app account counts as connected. `ReadinessCenter` reads the newest Live verdicts in its snapshot and re-reads at once when `SlackLiveStatusCenter`'s statuses change. Home → Getting ready shows one grouped Live-only row for these features, not a card per feature (ask #1572).
- **Sidebar:** `ConnectedSources.slackLive` (the newest-batch rule) keeps Catch-Up and Statistics visible with Live only (`SidebarSource.slackLive`); `.messages` is unchanged. Tests: `SidebarVisibilityTests` (Core: the fetch and the source) and the app-target `SidebarSlackLiveTests` (`testLiveOnlyShowsCatchUpAndStatistics`, `testLiveDoesNotCountAsMessages`, `testRefreshOnLiveStatusChange`), since `SidebarDestination` and `AppState` are not visible to Core tests.
- **Knowledge:** the Desktop has no Knowledge search screen, so the Live note ("Slack is not in Knowledge: Live answers are not kept. …") ships as `SlackModePresentation.knowledgeNote` with its test only, to be placed when such a screen exists (screens §11 B4).
- **Phone:** the hub's `DBAccounts` (`internal/hub/slices/heartbeat.go`, now over `*db.DB`) adds one `{slack, "Slack", "live"}` row when no Slack account is listed and the Live verdict is on; the phone's `AccountStatusStyle` shows "Live only — sync needs your workspace's app". It reaches no real phone while the Go hub is in phase 1.
- Setup, connect, the shared-app banner and onboarding's connect sheet are in [slack-full.md](slack-full.md).

## v1 limits

- Claude Free (does the connector exist there) is unknown.
- Codex apps in an automation's per-run `CODEX_HOME` were not verified against a real CLI; the Claude path is covered by a stub speaking stream-json.
- Codex has an open bug (`openai/codex#47839`) that can stop its apps from working in some runs; it is outside Watchtower's control.
- No Live on the phone.
- The hourly check runs before the claim, not inside it: a recipe with concurrency above 1 could start two runs in one poll.
- The Full-trigger refusal is only at save (`validate` has no database).
- A denied connector write outside the six probe-listed tools is the only one the gate can see; denials are not recorded when the agent call itself fails.
- Live Claude automation runs also start the owner's user-scoped MCP servers (no `--strict-mcp-config`); their tools are denied.
- Runtime-B agents (Ollama and the like) ignore `slack:live`.
