# Confluence page editing from the chat (2026-09-30)

- From the chat the assistant reads a Confluence page live and proposes precise edits the owner approves. Two chat tools (`internal/tools/confluence_page.go`, `confluence_page_edit.go`, `confluence_page_client.go`): `get_confluence_page` is `AccessRead`, network-live (`GET /wiki/api/v2/pages/{id}` — with `status=current,archived`, as the sync fetcher asks, so an archived page search returns is read, not reported "not found"; it carries `archived: true` and a note — or `/blogposts/{id}`, `body-format=storage`, plus the existing fetcher's `Comments()`/`Users()`) — mounted only in chat mode (`buildToolRegistry`), never on the dev-mode MCP surface, since DEV-01 stays local-read-only and this is a network call; `edit_confluence_page` is `External`, so it runs only after the owner's Approve (AGENT-03), and never edits an archived page — refused at propose time and, with no PUT, at apply time (its PUT's `status:"current"` would restore the page as a side effect nobody approved; release audit, 2026-10-01). `page` resolves a numeric id, a `/pages/<id>`/`/blog/…` URL (matched to the connected site by host), or a title looked up through `kb.Search(Sources: ["confluence"])` — an ambiguous or unmatched title returns candidates, nothing is guessed. Caps: page text 60,000 runes (truncated tail cannot be edited, enforced by `checkVisibleOnly`), 200 comments, 8,000 runes per comment body, 4 MiB of storage XHTML (refuses above with a pointer to `get_knowledge_document` or editing in Confluence directly).
- **The editable text model (`internal/confluenceedit`, a pure package — no DB, no network)** parses storage XHTML into a block model (heading/paragraph/list/table/code/opaque) and renders `Doc.Text()`: markdown for supported inline formatting (bold/italic/strike/code/links) and everything else — mentions, Jira macros, images, attachments, emoticons, status macros, `ac:link` page links, any unknown macro, and a table with anything but plain inline cells — as a `⟦k:label⟧` marker (`Marker{Ordinal, Label}`, e.g. `⟦3:jira PROJ-123⟧`, `⟦7:image diagram.png⟧`) that carries its exact original XHTML bytes verbatim; so is a table without exactly one header row of `<th>` over rows of `<td>` (headerless or column-header — a pipe table would show a header row the page lacks, R11). **Round-trip law:** `Render(Parse(x))` equals canonicalised `x` byte for byte (`TestEXT05_RichElementsSurviveUntouched`, a no-op edit round-tripping storage byte for byte, macros and mentions included). **Only what an edit changes is re-serialised:** a `replace_text` rewrites one unit's content span; a `replace_section` keeps the original bytes of every block of the section the new body leaves unchanged (R11 below, `TestEXT05_SectionRewriteKeepsUntouchedBlocksByteExact` + `FuzzApply`'s section property). Mention markers store the raw `@<accountId>`; `get_confluence_page`/`edit_confluence_page` relabel them to `@<display name>` for the model (`markerLabels`, resolved best-effort via `client.Users`; an unresolved id keeps showing as the id, reported as a note) — so the model sees an account id only in an unresolved mention's label, which it must keep as is; a resolved mention it only ever sees and writes as a name.
- **Edits (`Apply(doc, edits) (newStorage string, changes []Change, err error)`, `MaxEdits = 20`):** `replace_text {old, new}` — `old` must match `Doc.Text()` exactly once and lie within one block (paragraph/list item/table cell/heading/code block), else the edit is refused (not found, ambiguous, spans blocks); the block alone is re-serialised via a markdown-inline→XHTML converter, and markers in the new text are restored to their original bytes. `replace_section {heading, new_body}` — `heading` must match exactly one heading; the section's region runs to the next heading of the same or a higher level — an empty heading (an Enter left in heading style, `<h2/>`), which `Doc.Text()` omits, is an ordinary block of the section, kept byte-exact, never its end (release audit, 2026-10-01: it used to end the region the text showed running on, so a body repeating the text after it duplicated that text) — and is clamped to that heading's own container (a heading in a layout cell never bleeds into the next cell, R4) and additionally stops before any layout element nested directly in that container, never swallowing or splitting it (R5, `Doc.sectionRegion`); since the region stops at a layout edge, `Doc.Text()` shows every place a layout element starts or ends between two blocks as a `⟦layout boundary⟧` line (`confluenceedit.LayoutBoundary`; `get_confluence_page` adds a note explaining it when the page has one, and the edit tool's description names it), so the text never shows a section running on past where its region ends — without it, a paragraph in the next layout cell read as part of the section above, and a `replace_section` that repeated it wrote a second copy into the section while the original stayed in its cell (release audit H3, 2026-10-01). The line is not content: an edit's new text carrying it is refused, and a `replace_text` `old` quoting it spans blocks. As a backstop, a `new_body` block whose text equals a block past the region's end but before the next same-or-higher heading — and that the section itself does not also hold — is refused, naming the block (`checkNoSpill`): the safer of the two audit options is both, because a model that overlooks the line would otherwise duplicate the paragraph silently, while an edited copy of it (text no longer equal) can only be caught by the model seeing the edge; `new_body` (markdown: paragraphs, lists, pipe tables, fenced code, markers) replaces the region's content, the heading itself is kept — **merged, not re-rendered (ruling R11, `sectionmerge.go`/`faithful.go`):** the new body's blocks are matched in order to the section's original blocks by editable text (an LCS; an original whose text reads back as several blocks — two `<br/>`s — is kept when a run of new blocks joins to it); a matched block re-emits its original bytes (a centred paragraph, a table's layout, a code macro's title all survive), and so does a block the new body only moves — its text equals an unmatched original's elsewhere in the section (or, for a multi-block original, a run of new blocks elsewhere joins to its text), so it re-emits that original's bytes at its new place (ruling R13, `findMoves`); a new block is derived from the next unmatched original of its kind and rendered from markdown only if that original passes the R6/R7 skeleton guard and is representable (no attributes on p/li/ul/ol/table/heading or their structure, no `colgroup`, not noformat, no code-macro parameter but `language`, no multi-paragraph `li`, no comment, text that reads back as its own kind) — else the edit is refused naming the block (`the section's paragraph "…" cannot be rewritten without losing formatting (…); keep that block exactly as it is in new_body, or edit it in Confluence`); since the text cannot say which original a changed block came from, one post-merge check over the whole section (ruling R14, `checkLossy`, superseding R13's per-gap check) classifies every original as kept (matched or moved), derived or deleted and refuses, naming it, a deleted original markdown cannot carry faithfully (the same representability test, including text that reads back as several or other blocks) while any changed block — derived or new — of its kind is anywhere in the section (for an original whose text reads as another kind, any changed block at all): moving and editing a rich block, or deleting it while changing a same-kind block elsewhere, is refused rather than silently flattened; of two same-text, same-kind originals the rich one is the one kept (`preferLossy`); a rich block is still deleted outright when no changed block of its kind is in the section (the diff shows it); unmatched originals are deleted (the diff shows it) except an empty spacing paragraph, which is never deleted; the bytes between blocks survive. A section enclosing a section an earlier edit in the same call replaced is refused ("put both changes into one replace_section"). A marker in the new text must exist in the original page and appear at most once in the whole result; a marker present in the replaced region but absent from the new text is removed and reported in `Change.Removed`. Editing any unit that contains an HTML comment or a stray/unparsed tag (`nodeOther`) is refused outright ("this text holds markup the editor cannot keep … edit it in Confluence instead") rather than silently dropping it — in a `replace_section` too: a block kept unchanged keeps its comment in its original bytes, a changed block holding one is refused, and only a block the new body deletes takes its comment with it.
- **Two links to one address (release audit L2, 2026-10-01):** a link rewritten from markdown takes its address's original start tag, and there is one per address, so of two links to the same href with different start tags (a smart-link card `data-card-appearance` and a plain link) a rewrite would give both the first one's — a plain link silently turning into a card, invisible in the diff. A `replace_text` of a unit holding such a pair, and a `replace_section` that re-renders a block linking to an address whose links in the section differ, is refused ("this passage has two links to … with different link settings …"); kept and moved blocks keep their bytes, and two identical links stay editable.
- **Formatting-skeleton guard (R6/R7, `internal/confluenceedit/guard.go`):** page text that merely *looks* like markdown (`__init__`, `2**10`, `[1](2)`) would silently turn into real formatting the first time an unrelated edit touches the same unit — invisible in the approval diff. Before rewriting a unit, its pre-edit editable text is round-tripped through the same markdown→XHTML path and compared, as an **ordered** sequence of `(canonical tag or a+href, flattened visible text)` in document order (not a count — a count would let a lost tag and a gained tag of the same kind cancel out), against the unit's actual storage skeleton; a mismatch refuses the edit ("this passage contains characters that read as formatting …; edit that passage in Confluence" — never pointing at `replace_section`, which runs the same guard on any block it changes, R11). NBSP/Unicode spaces are moved outside emphasis delimiters before comparison so `<strong>Label:&nbsp;</strong>` round-trips faithfully.
- **Version pinning (EXT-05):** `edit_confluence_page`'s `Normalize` (propose time) fetches the live page, requires `version == base_version` ("page changed since you read it (now vN) — re-read with get_confluence_page"), runs `Apply`, and pins `{account_id, page_id, kind, title, url, base_version, base_hash, new_storage, changes, notes?}` into the stored args — `new_storage` is exactly what Execute will write, `base_hash` is the sha256 of the storage the preview was computed from (ruling R12), `notes` carries card caveats (a failed user-name lookup: "User names unavailable — mentions show account ids"). `Execute` (after Approve) re-fetches the page (`GetPageBody`, no space-key GET) and writes only if the version still equals `base_version` AND the storage still hashes to `base_hash` — else it refuses (`conflict: the page was edited after the preview (now vN); nothing was written`; at exactly `base_version + 1` with the live storage equal to `new_storage` once the `local-id`/`ac:local-id` attributes Confluence stamps on save are stripped from both — from start tags only, never from text, CDATA or HTML comments — a Retry after a first PUT that landed but whose response was lost — it writes nothing and SUCCEEDS with `{page_id, title, url, version: N, note: "this edit is already saved (vN); nothing was written now"}` (the page holds exactly the approved edit, so the action is `applied`, not `failed`; release audit, 2026-10-01; a 409 whose re-read finds the same is the same success), and at `base_version + 1` with any other storage the hedged `conflict: the page is now vN (one version after your preview) — this edit may have been saved; re-read with get_confluence_page before retrying; nothing was written now` (R13 N3: our own save may differ in ways we can't tell apart); a 409 from Atlassian is re-read and reported the same way; a grant revoked at read or PUT time names `watchtower jira login --account N --with-confluence-write`) and otherwise issues one `PUT /wiki/api/v2/pages/{id}` (or `/blogposts/{id}`) `{id, status:"current", title, body:{representation:"storage", value:new_storage}, version:{number: base_version+1, message:"Edited via Watchtower"}}` via the new `*jira.ConfluenceAPI.PutJSON` (method PUT only, shared refresh/401/429/`HTTPStatusError` handling with `GetJSON`/`Download`). Result is `{page_id, title, url, version}`.
- **Scopes:** `ConfluenceWriteScopes` (`write:page:confluence write:blogpost:confluence`, `internal/jira/scopes.go`) are opt-in, requested only by `watchtower jira login|add --with-confluence-write` (implies `--with-confluence`); `HasConfluenceWriteScopes` mirrors `HasConfluenceScopes`. `jiraReloginOptions` (`cmd/jira.go`) extends the existing "plain re-login keeps already-granted Confluence scopes" rule to the write scopes: a plain re-login of an account whose stored grant already has them (`accountUsesConfluenceWrite`) requests them again without repeating the flag. Without write scopes, `edit_confluence_page`'s Validate refuses before any network call: `Confluence editing not granted — run: watchtower jira login --account N --with-confluence-write`.
- **`watchtower confluence access [--json]`** (`cmd/confluence.go`) reports `{"read":bool,"write":bool}` for one account's stored grant alone — no network call, no fetcher. Desktop's Confluence section (Settings → Connections → Jira) reads it via `ConfluenceSpacesViewModel` and shows an **Allow editing** button when read access is present and write access is not (`showsAllowEditing`); it runs the account's re-login with `--with-confluence-write` (`allowEditing()`/`allowEditingAsync()`).
- **Desktop card (`AgentActionCardView+Confluence.swift`):** `edit_confluence_page` renders the pinned title + a link to the page, then per change its locator ("Section: <heading>" or the paragraph/list/table locator) followed by a word-level diff of `Before`→`After` (`WatchtowerCore/Utilities/WordDiff.swift`, unit-tested; removed words struck through in red, inserted words in green, a long unchanged run shortened around " … " without ever cutting a changed word) and a "Removes: <labels>" line when the change dropped a marker; pinned `notes` show as caption lines. A failure or conflict is read from `AgentAction.error` (not `result_json.error`) and shown verbatim. A proposal the card cannot read offers Reject only, never Approve (it would write a page the owner never saw). The preview is memoized per row version on a cheap key (id, created_at, status, args byte length, a head/tail byte sample carrying `base_hash`) and no other card path decodes the up-to-4-MiB args per render (`AgentAction.argsDecodes` pins it).
- **`get_action` arg elision (`internal/mcp/actions.go`):** any string value over 2,048 bytes anywhere in a proposal's echoed args is cut to its first 500 runes plus an `"… [elided: N bytes]"` marker (`elideLargeStrings`/`elideValue`) — generic, every tool, every depth, so a write tool pinning bulk material (the storage XHTML `edit_confluence_page` will write, up to 4 MiB) is never echoed verbatim back to the model; numbers keep their exact text (`UseNumber`); the stored `agent_actions` row itself is untouched, only the model-facing `get_action` view is shortened.
- **Contracts:** EXT-01 is **narrowed, not weakened** — the sync engine and `confluence.Fetcher` stay GET-only (`confluence.API` seam pinned to `{Download, GetJSON}`, `TestEXT01_FetcherCannotReachPut` proves the engine's dependency graph can't even import `internal/jira`); `*jira.ConfluenceAPI`'s exported method set widens to `{Download, GetJSON, PutJSON}`, and `PutJSON`'s one production caller is `internal/tools/confluence_page_client.go`'s `PutPage` — never `internal/confluenceedit`, which is a pure text model with no network access at all — called in turn only from `confluence_page_edit.go`'s `executeConfluenceEdit` (`TestEXT05_OnlyEditToolReachesPut`, an AST scan with a 300-file floor). New contract **EXT-05** — Confluence writes are approved, versioned and bounded: the only write path is the `External` `edit_confluence_page` tool; every write carries the base version and the storage hash the owner's preview was computed from and is applied only if both still match; a rich element is removed only when it appears in the approved diff's removal list. See `docs/inventory/external-sources.md`.
- **v1 limits (accepted):** no replying to, resolving or creating comments — comments are input only; no creating new pages, editing attachments, or moving/renaming pages; a page link (`ac:link`) and any table with non-plain cells stay opaque markers — not editable inline, so retitling a link's visible text or hand-editing one cell of a rich table isn't possible from chat; mention labels are resolved to display names for the model and translated back to `@accountId` on write, best-effort (an unresolved id shows and must be kept as the id); after a successful write there is **no immediate `ext_documents` refresh** — `extsync` has no single-document refresh path, so a Confluence edit made through chat is invisible to `search_knowledge` until the daemon's next external-sync cycle picks up the new version (R9); a `replace_section` refuses to change a block markdown cannot carry faithfully (R11: an attributed/aligned paragraph, heading, list or table, a table with column widths, a noformat block, a code block with a title or other parameters, a multi-paragraph list item, text that reads as formatting) — such a block can be kept or deleted in `new_body`, but a change to it must be made in Confluence; a section enclosing one replaced earlier in the same call is refused; swapping two multi-line paragraphs (each holding a double line break) within one gap is refused rather than reordered; deleting a paragraph whose text reads as markdown structure (`- x`, `# x`) is refused while any block of the section changes; moving a rich block between two sections with two `replace_section` edits re-renders it (the diff shows both the deletion and the addition); when a rich multi-line paragraph's text equals a run of plain paragraphs elsewhere in the section and no block changes, the merge may keep the plain run and delete the rich paragraph (textually ambiguous; the deletion shows in the diff); a block the new body deletes takes any HTML comment inside it along (not reported as a removed marker, since a comment was never one); editing any unit that contains an HTML comment or a stray/unparsed tag is refused rather than attempted; the **Allow editing** button lives inside the Confluence section, which is gated on feature `knowledge-connectors` — with Confluence sync off the button is hidden while `get_confluence_page`/`edit_confluence_page` still work, so the edit tool's refusal naming `watchtower jira login --account N --with-confluence-write` is the only path to the write grant (R10, one extra step for a sync-off user).
