# Slack Multi-Account (sub-project 2 of 3 of the multi-account initiative, 2026-07-31)

- `slack_accounts` table (migration 00048) replaces the single-org `workspace.current_user_id`/`search_last_date` fields: one row per connected Slack organization (`team_id`, `team_name`, `team_domain`, `label`, namespaced `current_user_id`, `status`/`error`, `enabled` soft on/off, its own `search_last_date` search-sync watermark). `workspace.current_user_id`/`search_last_date` columns are dropped; `workspace.id/name/domain` stay as a frozen legacy snapshot of account #1 (nothing reads them by key). **Namespaced string ids, not a composite PK** (unlike `gmail_messages`): `channels.id`/`users.id`/`messages.channel_id`/`messages.user_id` — and every table that copies those values (digests, `tracks`, `situations`/`situation_signals`, `feedback`, `channel_settings`, `jira_slack_links`, memory `""`-scheme provenance) — hold `"<accountID>:<rawSlackID>"` (the `gmail:<acct>:...`/`imap:<acct>:...` precedent). Column types are unchanged, so every downstream query treating these as opaque unique strings keeps working with zero signature changes; only live-Slack-API callers and cross-account-ambiguous renderers resolve the account. `slack.Namespace(accountID, rawID)` / `slack.SplitAccountID(id)` (`internal/slack/namespace.go`) are the single pack/unpack points.
- A pre-multi-account install migrates in place: the goose migration seeds account #1 from the `workspace` row and rewrites every scalar TEXT id column to the `"1:"` prefix; `ensureLegacySlackAccount` (`cmd/slack.go`/`cmd/slack_test.go`) finishes it in Go (moves the `config.yaml` `workspaces.<team>.slack_token` into `slack_token_1.json`, blanks the config token) and is idempotent — called from daemon sync wiring, `slack add` (seed-then-create), and the `auth login`/`auth logout` legacy aliases (now thin wrappers over account #1). **A fresh install has no `workspaces.<name>` block at all** — `saveAuthResult` writes only `active_workspace` + defaults — so nothing on the sync path may require one: `runSync`'s `validateSyncConfig` (`cmd/sync.go`) validates a legacy config token only when present (the 2026-09-11 "Failed to start daemon (exit code 1)" over an empty daemon.log). The same incident found `ConfigService.save()` deleting `active_workspace` (a nil assigned to a dictionary subscript removes the key; `save()` no longer writes the key at all — the CLI owns it, the Desktop only displays it) and the two halves disagreeing on such a config: the Desktop opens the first workspace directory holding a `watchtower.db` (`DatabaseManager.resolveDBPath`) while every CLI command failed with "active_workspace is required". **`config.Load` now resolves an empty `active_workspace` from the data directory when exactly one workspace holds a database** (`resolveActiveWorkspace`, the one place config is loaded, running BEFORE the `WATCHTOWER_SLACK_TOKEN` binding that keys on the workspace name — no repair write); several candidates stay unresolved on purpose (a guess could aim the daemon's writes at a different DB than the one on screen) and surface as the `ValidateWorkspace` error naming the candidates and `config set active_workspace`. `Constants.activeWorkspaceDir()` (sync progress, memory vault, skills dir) applies the same single-candidate rule — a deliberate dual-path (`singleWorkspaceWithDatabase` ↔ `workspaceDirsWithDatabase`), pinned on both sides — so the DB path and the workspace dir agree on such a config. `DatabaseManager.resolveDBPath` decides on the same candidate set (`Constants.workspacesWithDatabase`, 2026-09-26): an explicit `active_workspace` opens only its own database (missing → not found, never another workspace's), one candidate opens, and several throw `ambiguousWorkspace` — launch then shows `AmbiguousWorkspaceView` (the candidates, `config set active_workspace <name>`, Try Again) instead of the first sorted match. Tests that assert a "config required" error must run under an isolated `HOME` (`cmd`'s `TestMain` sets one package-wide; `internal/config` uses `t.Setenv`), or the resolver finds the developer's real workspace.
- Per-account token store `slack_token_<id>.json` (0600, `internal/slack/token_store.go`) — secrets out of the DB and out of argv, matching `google_token_<id>.json`. `wireSlackSyncers` (`cmd/sync.go`) iterates `ListEnabledSlackAccounts` and builds one `sync.Orchestrator` per account (`NewOrchestrator(database, client, cfg, accountID)`, namespacing at every DB write, stripping the prefix only at live-Slack-API call sites) — one account's auth failure records only *its* `status`/`error` via `SetSlackAccountAuthState` and never blocks the others (the `wireImapSyncers` fan-out pattern); zero-accounts is a clean no-op.
- CLI: `watchtower slack add [--label L] [--no-open] [--app-return]` (OAuth → new row + token file), `slack login --account <id>` (re-consent), `slack accounts` (list), `slack enable <id>`/`slack disable <id>` (soft on/off — disabled skips sync, synced data stays queryable), `slack remove <id>`. **`slack remove` is NON-destructive** (deliberate departure from `google remove`'s cascade): it deletes the token file and sets `status='removed'`/`enabled=0` but keeps the `slack_accounts` row (for label/domain attribution of historical permalinks) and does NOT cascade-delete channels/messages/digests/tracks/situations/memory (guarded by SLACK-01, `docs/inventory/slack-accounts.md`).
- Inbox: Slack inbox items reference `messages.channel_id` directly, so namespacing is inherited for free (no special channel_id construction, unlike Gmail) — but detection queries still need an explicit account-scoping predicate on top of that shape. The four trigger detectors (`FindPendingMentions`/`FindPendingDMs`/`FindThreadRepliesToUser`/`FindReactionRequests`, `internal/db/inbox.go`) take an `accountID` and add `m.channel_id LIKE ? || ':%'`; `internal/inbox/pipeline.go`'s `detectSlackAccounts` runs `detectSlackTriggers` once per `ListEnabledSlackAccounts()` row, passing that account's own `current_user_id` rather than a single pinned identity, and joins per-account errors so one account's failure never silently drops a sibling account's items. Auto-resolve (`autoResolveSlack`) matches the same way for `mention`/`dm`/`thread_reply` items — each pending item's account is derived from its own `channel_id` prefix and checked against that account's own `current_user_id` (via `ListSlackAccounts`, including disabled accounts, since disable/remove leave already-synced items resolvable) — but not for `reaction` items: `FindReactionRequests` sets `trigger_type="reaction"`, which `autoResolveSlack`'s switch does not list (it lists `"reaction_request"`, a value the `inbox_items.trigger_type` CHECK does not even permit), so reaction items have never auto-resolved and still do not — a pre-existing gap, not something the account-scoping work introduced or closed. The separate ambient stream-candidate path (ordinary channel traffic considered for triage, not the four triggers) was removed with stream triage in the 2026-09-14 inbox demolition (see Attention detection) — `db.ListOwnerSlackUserIDs()` and `ListStreamCandidatesSince` no longer exist. The system prompt lists all connected workspaces via `db.FormatConnectedWorkspaces` (`internal/ai/context_builder.go`); permalink/deeplink rendering resolves each message's account from its `channel_id` prefix (`ai.response_renderer.go`). See `docs/inventory/inbox-pulse.md` INBOX-09 for the shared-watermark and per-account detection notes.
- **Documented v1 identity-scoping decisions (deliberate, not oversights):** (1) **Superseded 2026-09-25 by the owner-identity resolver** (see "Owner identity" below) — `db.GetCurrentUserID()` is deleted; every former caller (Jira detection, style-sample, people-card lookup, `cmd/profile.go`) now goes through `db.ResolveOwner()`/`db.RequireOwner()` (`internal/db/owner.go`), whose ladder is Slack account #1 → first Google account → first enabled Jira account, mirrored in Swift by `OwnerQueries.resolve` (`internal/db/owner.go` ↔ `WatchtowerDesktop/Sources/WatchtowerCore/Database/Queries/OwnerQueries.swift`, OWNER-01/02). (2) Migration 00048 rewrote only scalar TEXT id columns; the JSON-embedded ones — `tracks.channel_ids`/`participants`, `user_profile.reports`/`peers`/`starred_channels`/`starred_people` — stayed bare until migration 00054 backfilled all six (in `tracks.participants`, only each object's `$.user_id`). What still stays bare: the memory vault's markdown files, AI-generated text written before its source pipeline re-ran post-migration, and `messages.text` — Slack's own mention markup (`<@U123>`) is source data no migration rewrites, so it never carries the namespaced form at all. Concretely, `digest_topics.situations`/`key_messages` carry raw (non-namespaced) Slack ids even though the prompt shown to the model uses namespaced ones (0 of 7334 `digest_topics` rows carried a namespaced id on a live database), so any comparison between a stored id and model-authored text must check both forms; a comparison against raw message text instead reduces the stored id to its raw form (`slack.MentionPatterns`/`slack.MentionTag`, `internal/slack/namespace.go`), since only that form ever appears there. (3) `slack remove` non-destructive (above). (4) `internal/db/memory.go`'s `TrackSubjectRefs` (feeding `internal/memory/chat_ingest.go`'s `trackSubjects`/`targetSubjects`) is a seventh consumer of `tracks.channel_ids`/`participants[].user_id` whose output shape changes under 00054 too — a vault entity alias seeded/frozen bare before the multi-account migrations ran will now miss a ref the backfill turned namespaced, silently losing the belief-subject match. Dark by default (`memory.enabled`). (5) Desktop link rendering has joined the "resolves the account" side (2026-09-24): every `slack://channel`/`slack://user` builder goes through `SlackLinkResolver` (per-account `slack_accounts.team_id`, falling back to the frozen `workspace.id` for a bare id, an unknown account, or an empty team id) and `SlackDeepLink` strips the namespace for the `slack.com/archives`/`app_redirect` family — a deliberate dual path with `internal/ai/slack_link.go` (the fallback ladder) and `internal/slack/permalink.go` (the link shapes). Still open: the three chat prompt templates (`ChatViewModel`, `TargetChatViewModel`, `TrackChatView`) hand the model account #1's team for `slack://` links it formats itself.
- Desktop: Settings → Slack is greenfield (no prior account-management screen) — `SlackAccountsViewModel` + `SlackAccountQueries` (GRDB) drive an account list (row = label/team + status + Enable/Disable + Remove); "Add Slack Account" sheet (`AddSlackAccountView`) runs `slack add --app-return` through the same in-app WKWebView OAuth flow Google/Gmail use.
- Design/plan: `docs/superpowers/specs/2026-07-31-slack-multi-account-design.md`, `docs/superpowers/plans/2026-07-31-slack-multi-account.md`. Non-goals (v1): cross-account message/channel dedup, concurrent OAuth flows, per-account sync schedules, cascading deletion on removal. Unrelated to the pre-existing `active_workspace` mechanism (fully-isolated Watchtower profiles keyed by team name), which is left untouched. **Slack-less start (onboarding v2, 2026-10-02):** `watchtower workspace init [--name default] [--json]` (`cmd/workspace.go`) creates the workspace directory and migrated database and records `active_workspace` without any Slack login (idempotent: an existing or single-resolved workspace is kept; several databases with none selected is refused via `config.ErrNoWorkspace` vs the ambiguity error). A later Slack login reuses that workspace instead of naming a new one after the team (`slackLoginWorkspace`, `cmd/auth.go`) when its database has no Slack account yet (and no unmigrated legacy config token) or its account #1 is already the same team; a login into a different team while account #1 is live is refused with a pointer to `watchtower slack add` (owner decision 2026-10-03, #279 — it used to fork a team-named workspace silently), since re-consenting account #1 with another team's token would mix two teams under the `1:` namespace. `--workspace <name>`, a removed account #1, or an unmigrated legacy config token keep the old team-named workspace.
