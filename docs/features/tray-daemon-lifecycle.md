# Menu-Bar Tray + Daemon Lifecycle + CLI Binary Store (2026-08-07)

- `MenuBarExtra` tray scene (status line + Open/Quit) plus `TrayAppDelegate` (`NSApplicationDelegateAdaptor`) own the app's lifecycle: closing the last visible window switches activation policy to `.accessory` — Dock icon gone, tray stays, daemon keeps running (before this change the app stayed `.regular`, keeping a Dock icon with no window); Dock reopen / tray "Open Watchtower" switches back to `.regular` (`ActivationPolicyDecision.becomeRegularAndActivate`). Settings and Pipeline Progress count as visible windows for the policy, but only the main `WindowGroup` window (matched via its SwiftUI-assigned `NSWindow.identifier`, which — unlike the frame autosave name — is set before the content mounts) is the one a login launch closes. Cmd+Q and tray "Quit Watchtower" both route through `TrayAppDelegate.terminateDecision` → `QuitCoordinator`, which stops the daemon via `DaemonManager.stopDaemonBounded()` (bounded `terminateLater` wait, terminates anyway on timeout) and confirms first if `MeetingRecorderCenter.isBusy` (a capture OR any non-failed transcription job). Login-item autostart (`SMAppService.mainApp`, registered once per bundle path via the `tray.loginItemRegisteredBundlePath` UserDefaults latch, so a dev build cannot lock the real install out) launches straight into accessory mode, no window.
- Launch bootstrap is window-independent: `AppState` is a singleton (`AppState.shared`, which the App struct's `@State` is seeded from) and `applicationDidFinishLaunching` runs `initialize()` + wires `NotificationDelegate.sharedAppState` on the survivor instance, so a login launch with no window still gets migrations, the DB, the CLI store sync and the daemon. The window's `onAppear` keeps its (now idempotent) call.
- `CLIBinaryStore` copies the bundled CLI to `~/Library/Application Support/Watchtower/bin/watchtower` (SHA256 compare, atomic rename, daemon stopped before replace) so `make app` / app updates never overwrite the file backing a live daemon process (the `SecPolicyCreateSSL` incident class from rebuilding under a running binary). The store is user-writable, so it is handed out only while it matches the bundled CLI: `CLIBinaryStore.installedPath` validates size + SHA256 against the bundle, `resolvedInstalledPath()` adds a code-signature check pinned to the running app's Team ID and caches the combined verdict keyed by both files' on-disk identity (device, inode, size, mtime, ctime — re-`stat`ed on every call, and dropped whenever `sync` changes the store), because `Constants.findCLIPath()` has ~50 call sites, several on the main actor: an unchanged store costs two `stat`s, while a file rewritten or renamed over after launch misses the cache and is re-verified before its next spawn (the TOCTOU guard; a file that changes mid-verification is neither cached nor handed out). A definite rejection (size/hash mismatch, failed signature) is cached the same way; an unreadable file is not, and a build with no Team ID skips the hashing outright. `AppState` primes the verdict off the main actor right after the launch sync and logs when the store does not verify. With no bundled CLI at all (`swift run`/`swift test`) the store is ignored entirely and resolution falls through to PATH. `Constants.findCLIPath()` resolves store → bundle → PATH; the sync runs at the top of `AppState.initialize()`.
- **Manual sync trigger + live sync status (2026-08-19):** the daemon's poll loop gains a third `select` arm next to the ticker and `wakeCh` — `WatchTrigger` (`internal/daemon/trigger.go`) forwards `SIGUSR1` (`daemon.TriggerSignal`), and `watchtower sync --now` sends it to the pid in `daemon.pid` (`runSyncNow` in `cmd/sync.go`, the `runSyncStop` shape). The CLI never falls back to syncing in-process: the daemon holds the exclusive `sync.lock` flock, which is exactly what a second syncer must not race. Sends are non-blocking, so a burst of triggers collapses into one queued sync; a trigger arriving mid-sync runs after the current one finishes (`runSync` is called synchronously from the loop). `d.triggerCh` is only wired when nil, so a test can inject its own channel.
- **Sync heartbeat:** `phaseSlackSync` publishes `sync_progress.json` (`internal/sync/heartbeat.go`, atomic tmp+rename, every 3 s while a sync runs, `IdleProgress` at the end) next to the existing `last_sync.json` — that file records finished runs, this one answers "is a sync running right now, and how far along". **Dual-path with Swift** (`WatchtowerCore/Models/SyncProgress.swift`): field names, the 2-minute `StaleAfter`/`staleAfter` window and the "active but stale ≠ syncing" rule must move on both sides at once — a daemon killed mid-sync leaves `active: true` behind forever, so freshness, not the flag, decides. The tray's status line renders it (`TrayMenuContent.statusText`: "Syncing: Messages · 34/105 channels" / "Daemon running · idle" / "Sync daemon not running") and gains a "Sync Now" item (`DaemonManager.syncNow`, disabled without a daemon). `phaseSlackSync` is also wrapped in `trackedPipelineRun("slack-sync", …)`, so the Slack sync finally appears in `pipeline_runs` and the Desktop's Pipeline Progress window — it was the one phase that ran untracked.
- **Slack HTTP timeouts (2026-08-19):** `slack.New` gets a bounded client (`newHTTPClient`, `internal/slack/client.go`): whole-request `Timeout` 30 s (matching jira/gmail/calendar/caldav/imap), `ResponseHeaderTimeout` 10 s for HTTP/1.1, and the h2 keepalive (`ReadIdleTimeout` 30 s, `PingTimeout` 10 s) via `http2.ConfigureTransports` — slack.com negotiates HTTP/2, where `ResponseHeaderTimeout` never fires. Before this, slack-go's default un-timed client let a socket killed by a laptop sleep hang until the OS TCP timeout (~24 min measured), because Go's monotonic clock stops during sleep and the idle-conn pool therefore never expires such a socket.
- **Slack sync API budget (2026-09-26):** every Slack call goes through one global 40 req/min token bucket (`internal/slack/ratelimit.go`, `NewRateLimiter` — `sync.workers` does not change it), so a cycle's wall time is its call count divided by 40. On a real install a cycle took a flat 10 minutes for 402 calls, of which the messages themselves (`search.messages`, 30 pages) were 50 s — the rest was auxiliary state refreshed every cycle: `syncInboxReactions` (one `reactions.get` per pending inbox item, 196 calls), `syncChannelReadState` (one `conversations.info` per channel with any unread digest, 158 calls back to March), and the full `users.list` roster (17 pages). Now: inbox reactions come from **one** `reactions.list` under the owner's token (auto-resolve only ever reads the owner's reaction — `CheckUserReplied` filters on it — so the listing is exactly the needed set; other reactors on a listed message are still written, a pending message the owner never touched is left alone — and since this phase was the search path's only reaction writer for pending messages, a colleague-only reaction on such a message now never reaches the `reactions` table's other readers either: `GetReactionsForMessages` in the digest and guide pipelines, and the reactions_to/from pairs in `user_analyses` — accepted narrowing); the read-cursor refresh runs at most **hourly** and the roster **daily** (`readStateRefreshInterval`/`rosterRefreshInterval` behind an injectable `Orchestrator.now` clock; the read-cursor stamp is in-memory per daemon process — a restart refreshes it on its first run — while the roster stamp is persisted on the account row, `slack_accounts.roster_synced_at` (00099, 2026-10-02), because `sync --users-only` (the onboarding people picker: team, current user and `users.list` only, no search/channels/messages/AI, ignores the throttle, takes no `sync.lock` so it runs beside the daemon, `--account <id>` or every enabled account) fetches the roster from another process and the next regular cycle must not refetch it — the 40 req/min bucket is per process, so a users-only run beside the daemon can push the token past Slack's limit and draw 429s, which the client retries; both stamps record the pass's START time and are written on success only — `syncChannelReadState` returns an error when it could not list its channels or updated none of them — so a failed pass retries next cycle instead of waiting out its interval; a partial pass (≥1 cursor updated) counts as a refresh on purpose, or one dead archived channel would defeat the throttle and bring the per-cycle cost back). Consequence: `AutoMarkReadFromSlack` (digests/tracks marked read from the Slack cursor) and a new user's real name (search sync stubs them with the search username) can lag by up to an hour / a day — a tray **Sync Now** goes through the same throttle (open owner call: whether a manual trigger should force the refresh). Open follow-up: `reactioncmd.processAccount` lists the same owner reactions again right after this phase in the same cycle (≤20 Tier-3 pages twice); a shared per-cycle listing would remove the duplicate. Separately, the daemon loop's shutdown had a select spin: `WatchWake`/`WatchTrigger` close their channel on ctx cancel and a closed channel is always ready, so `runSync` re-entered on the dead ctx until the random pick hit `ctx.Done()` (5 "context canceled" `pipeline_runs` rows and a bogus `last_sync.json` per stop) — the loop now drops a closed watcher via the receive's `ok`.
- **Search-sync gap-day fix (2026-09-29):** `searchWindow` (`internal/sync/search_sync.go`) computed the catch-up gap by subtracting a UTC-midnight `time.Parse` anchor of the stored `search_last_date` watermark from `now` in the local zone — a real-instant diff mixing a UTC-midnight anchor with a local time-of-day/offset residual, which silently truncated to an off-by-one gap-day count in a positive-UTC-offset zone (or late in the day in a negative one) and could shift the 30-day clamp decision. Fixed by re-anchoring `now` at its own calendar date's UTC midnight before subtracting, so the diff is always a whole number of days regardless of timezone; pinned by `TestSearchWindow_DeterministicAcrossUTCOffset`, which overrides `time.Local` directly (mutation-checked against the pre-fix formula).
- Settings' daemon Start/Stop toggle is removed — status stays read-only; the tray is now the only manual daemon control surface. Go side unchanged.
- **`sync stop` escalation (2026-09-25, daemon-shutdown-hang incident):** `runSyncStop` (`cmd/sync.go`) sends one SIGTERM and polls up to `syncStopGracePeriod` (10 s); on timeout it names the PID and prints `still shutting down; run 'watchtower sync stop --force' to kill it` and returns non-zero — no escalation without `--force`. `watchtower sync stop --force` sends a second SIGTERM (which, after `cmd/shutdown.go`'s `notifyShutdownContext` fix below, terminates outright any command built on it — a plain `signal.NotifyContext` never re-arms after the first signal, so a second one used to be silently swallowed while a ctx-blind step ran), waits up to `syncStopForceGracePeriod` (5 s), and only then sends SIGKILL — removing the stale pid file once the process is confirmed gone and reporting which signal ended it. **Before each of those two escalated signals**, `verifyDaemonAlive` re-resolves the pid via `daemon.FindProcess` and refuses to escalate against a pid that has since exited or been reused by an unrelated process (the pid was resolved once, up to 10s+5s ago) — stopping quietly and reporting "already exited" instead. SIGKILL is never the default stop path. `notifyShutdownContext` itself is adopted at every long-running `signal.NotifyContext` site in `cmd/` (daemon, `targets_ai.go`, `inbox.go`, `ideas.go`, `ai.go` ×3, `ask.go`, `logs.go`): the first signal still just cancels ctx (normal graceful shutdown, defers run); a background goroutine unregisters the signal the instant that happens, so a repeat signal kills instead of queuing. See `docs/incidents/2026-09-25-daemon-shutdown-hang.md` for the incident this fixes (root cause: `EvictEpisodes` re-walking the entire memory vault git history per eviction candidate — see `internal/memory/evict.go`'s owner-edit memo).
- **App updates (2026-10-01):** `UpdateService` checks on every launch and every `UpdateService.checkInterval` (6 h — the public channel is the unauthenticated GitHub API, 60 req/h per IP) while running, announces a found version once (`lastAnnouncedUpdateVersion` memo; notification + tray item "Update to <v> available…" → Settings → System), and installs **in-process** (stage next to the bundle, Security.framework signature check pinned to the running app's Team ID, bounded daemon stop, `FileManager.replaceItemAt`, then a detached waiter that only runs `open` after `TrayAppDelegate.requestQuit`) — never a post-exit shell script, which macOS App Management blocks with a TCC prompt. The quit is posted to the main run loop (`UpdateService.performOnRunLoop`), never called inside the MainActor task: `NSApp.terminate` there spins `.terminateLater`'s nested run loop inside a main-queue block, which never drains the main queue, so the quit path's reply and the quit-grace timer starved and the app hung on "Restarting…" (Cmd+Q, a run-loop event, was unaffected). A translocated bundle (quarantined, never moved by the Finder) is resolved to its original via `SecTranslocateCreateOriginalPathForURL` (looked up with `dlsym` — not in the Security module map) so the swap and relaunch target the user's copy. A background check that finds a new version also opens the **Software Update** window (`UpdateAvailableView`, release notes as markdown) once per version (`lastPresentedUpdateVersion` memo, separate from the notification memo); not while `isBusy()`, not before a scene wires `presentUpdateWindow` — both retry on the next check; a manual check only marks the version seen. The `.disabled` channel starts no loop.
