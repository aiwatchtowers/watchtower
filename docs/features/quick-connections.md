# Quick Connections — owner-managed external MCP servers (2026-09-09)

- Three connection tiers: native integrations (Tier 1 — full sync, migration, daemon phase; Slack/Jira/Gmail/Calendar), Quick Connections (Tier 2, this feature — an owner-added external MCP server surfaced in chat on demand, nothing synced or persisted beyond the connection row itself), and a future Tier 3 pipeline bridge (not built) for a source the owner wants passively observed in the background. `external_connections` table (migration 00064, `internal/db/external_connections.go`) is the registry — one row per server (`name`/`kind` stdio|http/`command`+`args` or `url`/`enabled`/`status`), always created disabled so enabling is a deliberate per-connection act. A secret (env vars for stdio, headers for http) never lives in the table: it's a `0600` file per connection (`internal/externalmcp.SecretStore`, `mcp_secret_<id>.json` — the `google_token_<id>.json` precedent). `internal/ai.Client.SetExternalMCPServers` merges each enabled connection into the chat's `buildMCPConfig` `mcpServers` object alongside the built-in `watchtower` server and extends `--allowedTools` with one `mcp__<name>` token per connection (`allowedToolsFlag`) — zero connections renders byte-identical to today. When any connection carries a secret, the whole mcp-config JSON (not just the secret value) is written to its own `0600` temp file and passed via `--mcp-config <path>` instead of inline argv (`writeMCPConfigTempFile`), since a secret embedded in the config would otherwise sit on the process's command line, visible to any other process via `ps`. External tools are **read-only in v1**: they're dispatched by the vendor CLI's own tool loop, not `internal/tools`' `Registry.Propose`/`Apply`, so there is no approval-card path for an external write yet — that rides runtime B (the Go-owned in-process tool loop), which can route an external write through the registry like any other `External` tool. Reachable only from tool-mode chats (main + target, the same surfaces AGENT-04 already gates) since only tool-mode chats call `buildMCPConfig` with chat servers at all; draft-only chats see no external tools by construction. CLI: `watchtower connections add|list|enable|disable|remove` (secret via `--secret-stdin`, never a flag). Desktop: Settings → Connections gains a "Quick Connections" card (`ConnectionService.quickConnections`, `ExternalConnectionsViewModel`, `QuickConnectionsDetail`/`AddExternalConnectionView`). **v1 limitation:** external connections are wired only for the claude provider (`*ai.Client.SetExternalMCPServers`, `cmd/generator.go`'s `newQueryClient`) — codex and the ollama/runtime-B path ignore every configured connection. Since 2026-09-10 this is surfaced rather than silent: `connections add`/`enable` print a non-fatal stderr warning under a non-claude configured provider and the Desktop card shows a matching caption (`QuickConnectionsProviderNotice`); the add-sheet also gained a kind-adaptive key/value secret editor (`ExternalConnectionSecretBuilder`, still delivered via `--secret-stdin`) and a quote-aware args tokenizer (`CommandArgsTokenizer`).
- **OAuth sign-in (2026-09-10):** a new `internal/mcpoauth` package is a generic MCP-spec OAuth client — authorization-server discovery with RFC 9728/8414 fallbacks, dynamic client registration with a BYO client-id/secret fallback, PKCE S256 authorization-code flow over a plain-HTTP loopback on `127.0.0.1` ports 18541-18550, refresh, and revoke — used only for http-kind connections. The resulting grant lives in the connection's existing `mcp_secret_<id>.json` under an additive `oauth` key (`internal/externalmcp.Secret.OAuth`), never a new table or column. `cmd/generator.go`'s `loadExternalMCPServers` runs a pre-launch refresh (`mcpoauth.EnsureFresh`) before every chat launch: a still-fresh grant costs zero network calls, an expiring one is refreshed and the rotated tokens are persisted **before** the new access token is used, and a grant that cannot be refreshed is dropped from that launch with `status='revoked'` (only a new sign-in fixes it: `invalid_grant`, `invalid_client`/`unauthorized_client`, expiring with no refresh token, or a rotated token that could not be saved) or `status='error'` (transient: network, 5xx, lock wait) + `error` written to the connection row — surfaced in Settings, never a silent stale bearer on the wire (contract **QC-04**, `docs/inventory/quick-connections.md`). Since 2026-10-01 the load→refresh→save runs under a per-connection cross-process `flock` (`mcp_secret_<id>.json.lock`, `SecretStore.Lock`) and re-reads the grant once the lock is held, so parallel chat launches refresh a rotating token once; `connections oauth` saves its new grant under the same lock. CLI: `watchtower connections oauth <id> [--app-return] [--no-open] [--client-id] [--client-secret-stdin]` runs the sign-in; `connections list` gains an `auth` column (`oauth`/`static`/`none`); `connections remove` best-effort revokes the grant via the server's `revocation_endpoint`, when advertised, before deleting the secret. Desktop: the add sheet offers a "Sign in with OAuth" path for http connections (creates the row, then runs `connections oauth --app-return`), and a `revoked` connection's card shows "Sign in again" driving the same command. Known limitation: the refresh is sequential and synchronous, up to 30 s per stale connection (`httpClient.Timeout`), so several dead connections can delay a chat launch — bounded, never unbounded.
- **Per-tool allowlist (2026-10-01, QC-02):** a connection is never granted whole. Each connection's `tools/list` is cached in `external_connection_tools` (migration 00093) by `connections enable`, `connections oauth`, `connections tools <id> --refresh`, or — for a connection never listed — once at the next chat launch (`internal/externalmcp.ListTools`, go-sdk client, 30 s bound). `externalmcp.ResolveTools` allows a tool when the server annotates it `readOnlyHint: true`, or, when the server sends no annotations for it, when its name's leading word is get/list/search/read/fetch/query/find/describe/lookup; an annotated tool without the hint is a write (the MCP default). The owner's explicit list (`connections tools <id> --allow a,b`, `tools_allow_json`) replaces that default. `--allowedTools` then carries `mcp__<name>__<tool>` per allowed tool and `--disallowedTools` hides every other listed tool; a connection never listed, whose listing failed, or with no allowed tool is not mounted at all (fail closed). A tool the server added after the last listing is in neither list: visible but never approved (headless chats cannot prompt) until the next `--refresh`. v1 limits: no Desktop per-tool toggle (CLI only; the Settings card carries a caption), annotations are the server's self-declaration, and the name heuristic can only err toward denying.
- Contracts: `docs/inventory/quick-connections.md` (QC-01..04 — native untouched, read-only/no auto-execute, secrets never on argv, fresh-or-visible).
