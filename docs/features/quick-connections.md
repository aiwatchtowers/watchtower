# Quick Connections — owner-managed external MCP servers (2026-09-09)

- Three connection tiers: native integrations (Tier 1 — full sync, migration, daemon phase; Slack/Jira/Gmail/Calendar), Quick Connections (Tier 2, this feature — an owner-added external MCP server surfaced in chat on demand, nothing synced or persisted beyond the connection row itself), and a future Tier 3 pipeline bridge (not built) for a source the owner wants passively observed in the background. `external_connections` table (migration 00064, `internal/db/external_connections.go`) is the registry — one row per server (`name`/`kind` stdio|http/`command`+`args` or `url`/`enabled`/`status`), always created disabled so enabling is a deliberate per-connection act. A secret (env vars for stdio, headers for http) never lives in the table: it's a `0600` file per connection (`internal/externalmcp.SecretStore`, `mcp_secret_<id>.json` — the `google_token_<id>.json` precedent). `internal/ai.Client.SetExternalMCPServers` merges each enabled connection into the chat's `buildMCPConfig` `mcpServers` object alongside the built-in `watchtower` server and extends `--allowedTools` with one `mcp__<name>` token per connection (`allowedToolsFlag`) — zero connections renders byte-identical to today. When any connection carries a secret, the whole mcp-config JSON (not just the secret value) is written to its own `0600` temp file and passed via `--mcp-config <path>` instead of inline argv (`writeMCPConfigTempFile`), since a secret embedded in the config would otherwise sit on the process's command line, visible to any other process via `ps`. External tools are **read-only in v1**: they're dispatched by the vendor CLI's own tool loop, not `internal/tools`' `Registry.Propose`/`Apply`, so there is no approval-card path for an external write yet — that needs runtime B (the Go-owned in-process tool loop, `internal/agentloop` — shipped, but it drives only the ollama provider and does not proxy external servers yet), which can route an external write through the registry like any other `External` tool. Reachable only from tool-mode chats (main + target, the same surfaces AGENT-04 already gates) since only tool-mode chats call `buildMCPConfig` with chat servers at all; draft-only chats see no external tools by construction. CLI: `watchtower connections add|list|enable|disable|remove` (secret via `--secret-stdin`, never a flag). Desktop: Settings → Connections gains a "Quick Connections" card (`ConnectionService.quickConnections`, `ExternalConnectionsViewModel`, `QuickConnectionsDetail`/`AddExternalConnectionView`). **v1 limitation:** external connections are wired only for the claude provider (`*ai.Client.SetExternalMCPServers`, `cmd/generator.go`'s `newQueryClient`) — codex and the ollama/runtime-B path ignore every configured connection. Since 2026-09-10 this is surfaced rather than silent: `connections add`/`enable` print a non-fatal stderr warning under a non-claude configured provider and the Desktop card shows a matching caption (`QuickConnectionsProviderNotice`); the add-sheet also gained a kind-adaptive key/value secret editor (`ExternalConnectionSecretBuilder`, still delivered via `--secret-stdin`) and a quote-aware args tokenizer (`CommandArgsTokenizer`).
- **OAuth sign-in (2026-09-10):** a new `internal/mcpoauth` package is a generic MCP-spec OAuth client — authorization-server discovery with RFC 9728/8414 fallbacks (since 2026-10-14 the metadata's `issuer` must be the issuer it was fetched for, RFC 8414 §3.3 — a lone trailing slash aside — so one authorization server cannot speak for another), dynamic client registration with a BYO client-id/secret fallback, PKCE S256 authorization-code flow over a plain-HTTP loopback on `127.0.0.1` ports 18541-18550, refresh, and revoke — used only for http-kind connections. The resulting grant lives in the connection's existing `mcp_secret_<id>.json` under an additive `oauth` key (`internal/externalmcp.Secret.OAuth`), never a new table or column. `cmd/generator.go`'s `loadExternalMCPServers` runs a pre-launch refresh (`mcpoauth.EnsureFresh`) before every chat launch: a still-fresh grant costs zero network calls, an expiring one is refreshed and the rotated tokens are persisted **before** the new access token is used, and a grant that cannot be refreshed is dropped from that launch with `status='revoked'` (only a new sign-in fixes it: `invalid_grant`, `invalid_client`/`unauthorized_client`, expiring with no refresh token, or a rotated token that could not be saved) or `status='error'` (transient: network, 5xx, lock wait) + `error` written to the connection row — surfaced in Settings, never a silent stale bearer on the wire (contract **QC-04**, `docs/inventory/quick-connections.md`). Since 2026-10-01 the load→refresh→save runs under a per-connection cross-process `flock` (`mcp_secret_<id>.json.lock`, `SecretStore.Lock`) and re-reads the grant once the lock is held, so parallel chat launches refresh a rotating token once; `connections oauth` saves its new grant under the same lock. CLI: `watchtower connections oauth <id> [--app-return] [--no-open] [--client-id] [--client-secret-stdin]` runs the sign-in; `connections list` gains an `auth` column (`oauth`/`static`/`none`); `connections remove` best-effort revokes the grant via the server's `revocation_endpoint`, when advertised, before deleting the secret. Desktop: the add sheet offers a "Sign in with OAuth" path for http connections (creates the row, then runs `connections oauth --app-return`), and a `revoked` connection's card shows "Sign in again" driving the same command. Known limitation: the refresh is sequential and synchronous, up to 30 s per stale connection (`httpClient.Timeout`), so several dead connections can delay a chat launch — bounded, never unbounded.
- **Secrets only over TLS (2026-10-14, security review #163):** an http connection's headers (static or the OAuth bearer) never go to a remote host over plain http — `internal/netsec.RequireSecureURL` allows https, or http only to a loopback host (`localhost`, `127.0.0.1`, `::1`). `connections add` refuses headers on such a URL before any row or secret file exists; a connection stored earlier is not mounted and nothing is sent, OAuth refresh included (`connectionServer` → `errInsecureTransport`, `status='error'` with a `transport: ` reason that no tool-policy change clears; `connections tools --refresh` reports it rather than "sign in again"). `internal/mcpoauth`'s https rule leaves its http decision to the same `netsec.RequireSecureURL` (any other scheme stays refused; a refused http URL wraps `netsec.ErrCleartext`). The Desktop add sheet applies the rule inline (`ExternalConnectionTransportRule`: Add disabled, a red caption; a URL it cannot parse counts as refused, as in Go). The same rule guards CalDAV Basic auth (`caldav.DialCalDAV`, so both `caldav add` and the sync — and every redirect hop: `netsec.SecretRedirect` refuses one that downgrades to plain http to a non-loopback host or leaves the host, since Go re-sends the Authorization header on a same-host redirect) and IMAP `--security none` (`imap.Dial` → `netsec.RequireTLS`, refused unless the host is loopback). Every refusal wraps `netsec.ErrCleartext`, and the exemption lives in one place (`netsec.allowsCleartext`), so a later per-account override is a change there. The rule is strict by owner decision (2026-10-14, ask #118): a server on the LAN or a Tailscale address needs TLS, or a localhost tunnel (e.g. an SSH port forward) so Watchtower talks to a loopback host. An account the sync stops this way records `status='error'` with a `transport: ` error (`netsec.StatusMessage`, from the syncers' `recordAuthResult`); Settings → Calendar/Email show it under the account as a red "Stopped syncing …" line (`CleartextRefusal`), the add sheets refuse inline (CalDAV http URL, IMAP "None" to a remote host), and an unmounted Quick Connection shows its reason as a caption under its row (`QuickConnectionsDetail.reason`), the plain-http one reading "Uses plain http, so its headers (a secret) would be sent unencrypted — remove it and add it again with an https URL."
- **Per-tool allowlist (2026-10-01, QC-02):** a connection is never granted whole. Each connection's `tools/list` is cached in `external_connection_tools` (migration 00094) by `connections enable`, `connections oauth`, `connections tools <id> --refresh`, or — for a connection never listed — once at the next chat launch (`internal/externalmcp.ListTools`, go-sdk client, 30 s bound). `externalmcp.ResolveTools` allows a tool when the server annotates it `readOnlyHint: true`, or, when the server sends no annotations for it, when its name's leading word is get/list/search/read/find/describe/lookup and no later word is a conjunction or a write verb (`getOrCreateIssue` is a write); an annotated tool without the hint, or with `destructiveHint: true`, is a write (the MCP default). `query` and `fetch` are deliberately not read verbs (arbitrary SQL can write; an arbitrary-URL fetch is the exfiltration channel `WebFetch` is hidden for). The owner's explicit list (`connections tools <id> --allow a,b`, `allow_json`) replaces the name heuristic, but only for listed tools the server does not annotate as a write (`--allow` refuses a declared write or an unlisted name; `ResolveTools` denies both), and applies only once the tools are listed. `--allowedTools` then carries `mcp__<name>__<tool>` per allowed tool and `--disallowedTools` hides every other listed tool; a connection never listed, whose listing failed, or with no allowed tool is not mounted at all (fail closed) and its row gets `status='error'` with the reason and the command to run, so Settings shows it (the CLI also prints it; the Desktop ignores exit-0 output). A failed launch-time listing (10 s bound) is not retried by launches for an hour (`list_failed_at`); `connections tools <id> --refresh` retries at once. A tool the server added after the last listing is in neither list: visible but never approved (headless chats cannot prompt) until the next `--refresh`. v1 limits: annotations are the server's self-declaration; the name heuristic is a best effort (an unannotated write named like a read — `get_token` that rotates it — would pass); the cache is never refreshed on its own, so a tool whose annotation changes on the server keeps its old verdict until `--refresh`.
- **Codex chat + import (2026-10-17, board #594, review #546 F1):** the codex chat (`ai session`, `ai query --tools chat`) no longer reads the owner's `~/.codex/config.toml`. Every `codex.Client` run that mounts the watchtower server (a database path, not `SetNoTools`/`SetReadFolder`) gets its own 0700 `CODEX_HOME` (`internal/codex/home.go` `newRunHome`, removed after the run, also the `--cd` root): a 0600 `config.toml` with `web_search = "disabled"`, the watchtower server and the enabled Quick Connections, and a symlink to the owner's `auth.json` — the codex twin of the claude chat's `--strict-mcp-config`. `codex.Client.SetExternalMCPServers` writes one `[mcp_servers.<name>]` table per connection (stdio `command`/`args`/`env`, http `url`/`http_headers`) with `enabled_tools` = the QC-02 allowed list, so with approvals off a denied or never-listed tool stays hidden; secrets sit only in that 0600 file (QC-03). The automation `agent()` codex child uses the same home (its `codexAgentHome` is gone). Values are TOML-escaped by `tomlString` (strconv.Quote is not TOML). `warnIfProviderIgnoresConnections` and the Desktop caption now warn for ollama only. Since the owner's own codex servers drop out of the chat, `watchtower connections import [--json] [name...]` (`cmd/connections_import.go`, `externalmcp.DiscoverImports`) brings them back: without names it lists the servers of `CODEX_HOME/config.toml` (else `~/.codex/config.toml`) and Claude Code's `~/.claude.json` user-scope `mcpServers` (`CLAUDE_CONFIG_DIR/.claude.json` when set; project scopes ignored) with a `skip` reason for any it cannot take (SSE, codex `cwd`, an unset `env_vars`/`bearer_token_env_var`/`env_http_headers`/`${VAR}` variable, plain-http headers to a remote host, a `watchtower*` name, a name already a connection); with names it adds each row, saves env/headers to `mcp_secret_<id>.json`, enables it (lists its tools) and reports `sign_in` for an http server with no headers whose listing failed. JSON: list `{servers:[{name,source,kind,command,args,url,has_secret,skip}],warnings:[]}` (never a secret), import `[{name,id,status,error,sign_in}]`. A Claude server with the name of a codex one is dropped when it is the same server, else renamed `<name>-claude`. Desktop: **Import from ~/.codex and ~/.claude…** in Settings → Quick Connections opens `ImportExternalConnectionsView` (every importable server ticked, Go's reason on the others), `ExternalConnectionsViewModel.loadImportCandidates`/`importConnections` (names after `--`), then the OAuth sign-in for each `sign_in` row. v1 limits: the per-run home drops the owner's other codex settings (custom `model_providers`, profiles, a keyring-stored sign-in), as `agent()` already did; the `--read-folder` run and the codex digest generators still read `~/.codex/config.toml`.
- Contracts: `docs/inventory/quick-connections.md` (QC-01..04 — native untouched, read-only/no auto-execute, secrets never on argv, fresh-or-visible).
- **Desktop per-tool toggles (2026-10-02, QC-02):** each Quick Connections row in Settings → Connections has a **Tools** disclosure (`QuickConnectionToolsView`) that renders `connections tools <id> --json` — the verdicts stay Go's (`ExternalConnectionTools` only decodes them; the JSON gained `write` = `externalmcp.IsAnnotatedWrite`). Read-only and unmarked tools toggle; a tool the server declares a write has no toggle (owner decision 2026-10-02: write tools cannot be allowed). A toggle re-reads the list, then writes the whole set as `--allow=<name>` per tool (`--allow=` alone allows none), or `--default` when the set equals the read-only default, so later-listed read-only tools keep following the default. **Refresh list** runs `--refresh`, **Use defaults** `--default`; a refusal shows the CLI's error (its last stderr line) under the list, a toggle for a tool a re-listing dropped or turned into a write writes nothing, and the row's Enabled, Sign in and Remove wait while a tools command runs, and the connection rows reload after every tools command (an empty set marks the row `error`).
- **Stale tool caches (2026-10-02, QC-02):** every cached tool now stores `destructive_hint`, false included; a cached list with a tool lacking the key predates the destructive mark (#109) and reads as never listed (`ToolsStale`), so a launch re-lists it before mounting (one-hour back-off and fail closed as for a never-listed connection), and `connections tools <id>` (text and `--json` `stale`, shown by the Desktop Tools list) says the list is stale; a failed re-listing names the stale cache in the row error.
