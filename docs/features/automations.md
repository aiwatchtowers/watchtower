# Automations (P1 core + P2 writes + P3 authoring and Desktop + P4 events + P5 workbench + P6 `mcp()`/`agent()` + templates, 2026-10-17 — P1–P6 shipped; open follow-ups are listed in this note)

Owner-written recipes the daemon runs on a schedule or on demand: a Markdown file with a strict YAML frontmatter (trigger, permission manifest, outputs, budget) and one synchronous JavaScript block, executed in a goja sandbox whose only world is the automation SDK. Spec: `docs/superpowers/specs/2026-10-14-automations-design.md` (decisions §20 ask #270, §20.1 asks #271–#273/#277, §20.2 asks #280/#287); business spec `…-business.md`; plans `docs/superpowers/plans/2026-10-14-automations-p1.md` … `-p6.md`. Contracts AUTO-01..13: `docs/inventory/automations.md`. Board #753.

P1 ships the core: recipe + manifest parser and hashes, the goja sandbox with the P1 SDK (`llm`, read `tool`, `state`, `output.inbox`/`report`, `log`), the run/step journal, the cron scheduler and the run executor in the daemon, per-run token and time budgets, the automation read tools, and the `watchtower automations` CLI. P2 adds writes (see "Writes (P2)" below): `tool()` writes and `output.target`/`output.slack` through the registry on the `automation` surface, per-automation auto grants with `automations auto`, `output.briefing` and the briefing's FROM YOUR AUTOMATIONS section. P3 adds authoring and the Desktop (see "Authoring and the Desktop (P3)" below): the `create-automation` skill, `draft_automation`/`save_automation` and the `automation_editor` surface, the Automations tab with its card, history, edit form, Monaco recipe editor, save and confirmation sheets, the "change it in words" editor chat and the New automation sheet, Inbox labels and output cards, and quick run (**Run Automation…** on ⌃⌘R, the tray's **Run automation ▸**, a finish notice). P4 adds event triggers (see "Event triggers (P4)" below): the daemon's event bus, content-free events published by the Slack, mail, calendar, Jira and Confluence sync phases, `where` filters, and one event run per automation per sync cycle. Automations are always on since 2026-10-18 (board #671, ask #372): there is no feature switch — a recipe-less install spends nothing, and a recipe runs only after the owner confirms it (see "Always on" below).

## Recipes and folders

- **Personal:** `<config.WorkspaceDir()>/automations/*.md` (`automations.PersonalDir`, D8) — inside the workspace data dir, never a TCC-protected folder. **Workbench:** `<workbench folder>/.watchtower/automations/*.md` (`WorkbenchDir`; the scope and the scheduler's workbench rescans are P5 — in P1 the CLI's `rescan --workbench N`, `save --path` and `dry-run --file` already accept that folder).
- The filename stem is the **slug** (`^[a-z0-9][a-z0-9-]{0,63}$`); other stems and other extensions are skipped (reported by `rescan`). A slug already used in the scope by a row at another path (a removed row included) is skipped with a message naming that automation, never a raw UNIQUE error.
- **Symlinks and special files are never read.** The indexer lists a folder with lstat semantics; only a regular file named `*.md` is a recipe. A symlink (inside, outside or dangling) or a FIFO/socket/device named `*.md` is skipped with "symlinks and special files are not read; put the recipe file itself in the folder" and never opened; a recipe replaced by a symlink is marked removed; a directory named `*.md` is ignored silently. A regular file is read Lstat → `open(O_NOFOLLOW|O_NONBLOCK)` → fstat (still regular, same inode). The folder path itself is canonicalised (`filepath.Abs` + `EvalSymlinks` on the deepest existing ancestor, `automations.CanonicalDir`), so a symlinked workspace dir still indexes. `automations.ReadRecipeFile(path)` is the same read for the CLI. P5 follows the same policy.
- **Shape:** frontmatter keys `name` (1–80), `trigger` (exactly one of `schedule` — strict 5-field cron, no `@descriptors`, no `TZ=` —, `button {label 1–24, confirm}`, `event {type, where}`, `manual: true`; `manual: false` is an error), `missed` (`run_once`|`skip`), `concurrency` (1–4), `permissions`, `outputs` (`inbox`, `briefing`, `report`, `target`, `slack`), `budget {tokens 1000–2000000, minutes 1–60}` (defaults 50000 / 5; a `usd` key is a parse error, D4), `pause_timeout_hours` (1–168, default 72). Unknown keys and a `workbench:` key (D15) are parse errors. Exactly one ```` ```js ````/```` ```javascript ```` block (also `~~~` fences, case-insensitive info string); zero, two or an **empty** block is a parse error (stricter than spec §2.2's "exactly one"). Text outside the block is the description. Max 256 KiB; CRLF, lone CR and a UTF-8 BOM are normalised (same `approval_hash` as the LF twin); invalid UTF-8 is a parse error. A parse error is indexed with `parse_error` set (not runnable); `ParseError{Line, Msg}` prints `line N: msg` (line 0 prints the message only).
- **Hashes:** `content_hash` = sha256 of the file bytes (change detection; streamed over the whole file even when only `MaxRecipeBytes`+1 bytes are kept). `approval_hash` = sha256 of canonical JSON `{"permissions":[sorted normalised],"outputs":[sorted],"scope":"personal"|"workbench:<id>","script":"<exact js block>","trigger":<trigger>,"missed":"<policy>","budget":{"tokens":N,"minutes":M},"concurrency":N}` in that key order, no whitespace, no HTML escaping (`approvalCanonical`; `canonicalTrigger` is the `trigger_spec` shape from `triggerSpecOf` minus the button's cosmetic label, `confirm` kept). A schedule, missed-policy, budget or concurrency edit therefore needs the owner's confirmation again (D26, ask #294, amending D5); name, description, a button's label and pause timeout do not change it. **Upgrade note:** D26 re-hashes every recipe once, so every recipe confirmed before it shows Needs your confirmation until the owner confirms it again.
- **Index** (`automations` table, migration 00113): `Indexer.RescanPersonal`/`RescanFolder(ctx, scope, dir)` parse every recipe and upsert the row by `path`, storing the parsed copy in `recipe_text`; the executor runs that copy, never the file. An insert never sets `confirmed_hash`/`enabled`; an upsert never touches them or `last_scheduled_for`; a missing file → `removed_at`; a missing folder = empty. `Indexer.Changed(dir)` is an lstat fingerprint of the folder (names, types, sizes, mtimes, ctimes) plus `db.AutomationScopeGeneration` (count / max id / max `updated_at` of the scope's rows), so a CLI delete that frees a slug triggers the next tick's rescan.
- **Runnable** = parsed, `enabled`, not removed, `confirmed_hash != ''` and `= approval_hash` (`db.Automation.Runnable()`). `confirmed_hash` is written only by `db.ConfirmAutomation(id, hash, now)` (refuses any hash but the current `approval_hash` with `ErrHashMismatch`; missing row `ErrAutomationNotFound`). In P1 its callers are `automations confirm` and `automations save --confirm-hash`, both refused under AI-agent markers (AGENT-07); P3's `save_automation` apply is the third (§2.5).

## Permission manifest

- Grammar (`ParsePermission`, `ParseManifest`): `capability:verb[@scope]` | `tool:<name>` | `mcp:<server>/<tool-glob>` | `shell:"<exact command>"`. Capabilities: `slack`/`gmail`/`jira`/`linear`/`calendar`/`confluence` (`read`/`write`, scope required: account label or address, Jira project key, Linear team key, Confluence space key, `*` = all); `targets`/`tracks`/`ideas`/`digests`/`people`/`transcripts` (`read`/`write`, no scope); `meetings`/`dayplan` (`read` only, ask #277); `llm` (`light`/`strong`, strong implies light); `agent:run`; `ask:owner`; `session:start[@claude|codex]`. There is no `knowledge`, `inbox` or `memory` capability (`knowledge:read` is a parse error naming the three `tool:` entries to use, D21). `shell:`/`session:`/`ask:` in a personal recipe are parse errors (D7). Scopes containing whitespace are refused. Normalisation: lower-case capability/verb/scope, Jira, Linear and Confluence scopes upper-case, duplicates folded, sorted.
- Matching (AUTO-01): `ToolCapabilities` maps each registry tool to `{Capability, Verb, ScopeArg, ScopeOf}`; a call is admitted by `tool:<name>` or by the capability+verb when every scope unit of the call is covered (case-insensitive equality or `path.Match` glob; any of a unit's `Values` — e.g. an account's label or its address — may match). A scope argument absent from the call is covered only by `@*`; a scope key spelled in another case (`PROJECT`, `Key`, `Account`) is not read as the scope, so the call needs `@*`. The tool must also be visible on the `automation` surface. A `ScopeOf` lookup failure is a `PermissionDenied` naming `<cap>:<verb>@*` (with the cause), never a panic.
- Scopes worth knowing: Linear (2026-10-18, #694) by team key — `list_linear_issues`/`list_linear_cycles`/`create_linear_issue` by `team`, `get_linear_issue`/`get_linear_status_history` and the four issue writes by the issue's current team (`ScopeOf` reads `GetLinearIssueByKey`, previous keys included), `list_linear_teams` unscoped; Jira reads by their own `project`/key prefix — a project grant covers the linked issues of other projects that the tool returns with that project's issues (ask #287); `get_jira_time_in_status` by `project`, else its `issue_keys` prefixes, else absent; `list_jira_sprints` by `project` or the project of its `board_id`; `list_emails`/`get_email` by the resolved account (label or address); `list_calendar_events` by `account` (absent → `calendar:read@*`); `send_slack_message` (P2) by the resolved `account_id`. `list_messages` and `list_upcoming_events` are **always unscoped** — only `slack:read@*`/`calendar:read@*` or `tool:<name>` admits them (D22, ask #273; both readings owner-confirmed in ask #280). `digests:read` covers `list_digests`/`get_digest`/`get_today_briefing`, `people:read` covers `find_experts` (ask #287). `tool:`-only: `search_knowledge`, `get_knowledge_document`, `get_task_context` (D21), `list_inbox`, `memory_recall`/`memory_open`/`memory_map`, `get_writing_style` (D23).
- `Covers(old, new)` returns the entries of `new` not covered by `old` (`*` covers every scope of the same capability+verb, `llm:strong` covers `llm:light`, shell entries byte-exact) — the widening list. `ClampListLimit(t, args)` injects `limit` 50 / clamps to 200 for a tool whose schema has `limit` (values owned by `tools.DefaultListLimit`/`tools.MaxListLimit`).

## Sandbox and SDK (P1)

- One fresh goja runtime per run. No `require`, `console`, timers, promises, `async`/`await` (`PreParse` fails the recipe with "the script API is synchronous", naming the script line); no `eval`/`Function`, and every function prototype's `.constructor` throws `EvalError`; a script that breaks out of its wrapper function is a parse error (AUTO-07). Globals: the SDK, a read-only `trigger` (`{kind, run_id, scheduled_for?, catch_up?, button?, events?, truncated, dry_run}`; `events` only on an event run, or on a dry run whose row carries an event payload — the events an event recipe's dry run plays), and the ECMAScript builtins.
- **Hardening** (goja has no heap limit and native builtins are not preemptible): **memory budget**: `watchHeap` checks the Go heap every 10 ms while a run's script executes and stops the run with an uncatchable `RangeError` "the automation used too much memory" (failed, `script`, no disable) once its live heap passes the run's limit = baseline + `RunHeapBudget` (1 GiB, one variable). Live bytes come from `/gc/heap/live:bytes` (garbage never counts), which only updates at a GC; when the continuously updated `/memory/classes/heap/objects:bytes` passes the limit first, a GC is forced for an exact live reading (at most once per quarter budget of growth), so a growing heap cannot outrun the check by pushing the next GC further out. The heap is the whole daemon's, so nothing is read while the run waits (meter paused), and the baseline moves up to the heap's current objects reading (garbage included, erring towards the run) when the run resumes and whenever another run starts or ends: one run's growth is not charged to another. The baseline never rises more than one budget above the run's starting reading, however many waits and sibling runs come and go, so the limit is at most start + 2 × `RunHeapBudget`; a run is stopped within about one poll of its live heap passing its limit, plus one native step still running (the per-builtin caps below keep single steps small). Measured on the review's churn probe (+250 MB/s with a sibling run every 300 ms): stopped at about 2.2 GB of heap; without siblings at about 1.2 GB. The baseline (at the start too) is the objects reading, so a run is never charged for what a sibling allocated just before it started. A run stopped for memory whose script then stays stuck in a native call past `AbandonGrace` is abandoned like any runaway (`RunInterrupted{Reason: memory, Abandoned: true}`, failed, disabled). Regex calls through `test` and the RegExp @@ methods that run ≥ `RegexpMatchTimeout` (2 s) throw `RangeError` "regular expression took too long" (those are fixed, non-writable). `RegExp.prototype.exec` stays goja's own (replacing it takes every String/RegExp method off goja's fast path); instead the compiler rewrites every direct `x.exec(…)` / `x["exec"](…)` call into the global `$__automationExec(x, …)` (`rewriteExecCalls`, a name scripts may not use), which times a RegExp's exec the same way. `super.exec(…)` (a RegExp subclass calling its parent), anything inside an optional chain (`a?.b.exec(x)`, `r?.["exec"](x)`: it must stay `undefined` on a nullish receiver) and an aliased exec (`var f = re.exec; f.call(re, s)`) are not rewritten and reads a timed-out match as "no match" (v1 limit). Deleting `RegExp.prototype.exec` makes the RegExp methods throw a catchable `TypeError` (`execMissing`), never a Go panic. Wrappers are installed as methods with the builtin's name and length (not constructors) and read an array-like's `length` once (`lengthOnce`); allocation caps `MaxBuiltinAlloc` = 16 Mi chars/elements on `repeat`, `padStart`/`padEnd`, `concat`, `String.raw`, `join`, `toLocaleString` (arrays and typed arrays; locales/options reach each element, ECMA-402), `fill`, `Array(n)`, `Array.from(array-like)` (the global `Array` is a capped function sharing `Array.prototype`), array/typed-array/`ArrayBuffer` lengths (a typed array built from an array-like: its length), the receiver length of `toSorted`/`toReversed`/`toSpliced`/`with`/`splice`/`sort` and the `slice` count (goja copies an array-like of length up to 2^53 − 1 into a list of that length), the argument list of `Function.prototype.apply`/`Reflect.apply`/`Reflect.construct`, typed-array `join`/`toString` (goja's join when 25 characters per element plus the separator fit, else counted), `normalize` (NFKD expands up to 18×: measured in Go with `norm.Iter` when 18× the length would not fit), `encodeURI`/`encodeURIComponent`/`escape` (up to 9×: an upper bound measured in Go when 9× would not fit), the text `replace`/`replaceAll`/`RegExp@@replace` insert, `Object.entries`/`keys`/`values`/`getOwnPropertyNames` and `Reflect.ownKeys` of a string, array or typed array (≤ `MaxListing` = 256 Ki entries: an entry costs goja ~650 bytes), the arrays and objects one `JSON.parse` builds (≤ `MaxJSONContainers` = 256 Ki, ~600 bytes each), the pieces of a string `split` (≤ 256 Ki, counted with `indexOf` for a long subject), `Array.from` and `Object.assign` of a string (≤ 256 Ki characters), the matches of a global `match` of a standard RegExp on a long subject (≤ 256 Ki, counted with goja's `test` from `lastIndex`, nothing collected), `flat`/`flatMap` results (holes count) and the `JSON.stringify` result; nesting depth ≤ `MaxJSONDepth` (1000) for `JSON.stringify`, `JSON.parse` and `flat`, and a bound function's name ≤ 10 000 characters (each bound name is "bound " + the target's, so a `bind` chain — through Proxies too — grows quadratically). goja's own `JSON.parse`/`flat` recurse on the Go stack: a deep enough input (`"[".repeat(16e6)`) was a `fatal error: stack overflow` no recover catches, so the daemon died and crash-looped on the recipe (security review #5, board #561). How each is held: `JSON.parse` text is scanned in Go (`jsonNestsDeeper`, which follows the JSON grammar exactly — numbers, escapes, raw control characters — up to the first syntax error, where goja's parser stops too, so text that is not JSON gets goja's `SyntaxError`); a reviver walk runs as JS; `flat` runs as one native `flatMap` pass per level; `replace`/`replaceAll` dispatch like goja (an object search with its own `@@replace` gets the script's own value; subject, search, then replacement are converted in goja's order) and hand goja's string or RegExp path a counting replacer that mirrors goja's `$` substitution — a replacement whose only `$` patterns are `$$` and `$&`, for a string search or a RegExp whose `exec` is goja's own (`standardExec`: matches are non-overlapping substrings), goes as it is when its bound fits (`simpleBound`), so a plain global replace stays on goja's fast path; `JSON.stringify` estimates each value in its replacer (escaped string and key lengths — control characters and lone surrogates 6, quote/backslash/short escapes 2 —, Number/String/Boolean objects unwrapped to their primitive once, right after the replacer, as stringify does, the indent: a number, string, or Number/String object as `space`). **Every size or depth limit throws a catchable `RangeError`** (no disable: data from outside — a Slack message, an email, an MCP result — must never switch an owner's automation off); the regex timeout and the default-sort cap too. The memory budget is the exception: it ends the run (the memory must be released), still without a disable. Guards: `TestSandbox_NativeBombsEndTheRunNotTheProcess` (each bomb, in process), `TestSandbox_HeapBudgetStopsTheRun`, `TestSandbox_WrappedBuiltinsMatchGoja` (results and side-effect order match bare goja), `TestSandbox_JSONParseNotJSONIsASyntaxError`, `TestJSONNestsDeeper`. A script stuck in a native builtin past `AbandonGrace` (2 s) after an interrupt is **abandoned**: its run ends with that reason, it is logged, and its automation is disabled (run error "…; the automation was disabled: runaway script — check and re-enable"; `DisableRunawayAutomation` also records it in `disabled_reason` / `disabled_at`, #584). The executor stops claiming while `automations.AbandonedRuns() >= 2` (abandoned goroutines still running; the count drops when one returns). The heap is bounded per run by `RunHeapBudget`.
- **Edges:** an SDK result > 256 KiB serialised → `ResultTooLarge` (never truncated); an SDK argument converts to Go only up to 256 KiB; SDK results reach the script as plain JSON values. The script's return value is JSON-serialised inside the run (functions/symbols/BigInt → uncaught `ValidationError`; > 256 KiB → `ResultTooLarge`); an SDK call made by a getter or `toJSON` during that serialisation ends the run `failed`/`script`.
- **Errors:** SDK errors are JS `Error`s with `name` in `PermissionDenied` (with `needed`), `ResultTooLarge`, `StateTooLarge`, `ValidationError`, `ToolError`, `BudgetExceeded`, `NotAvailable`; catchable by the script. Interrupts (deadline, budget, cancel, daemon stop) are not catchable; an interrupt raised before the outcome is read wins over a script that just finished, and a backend error raised after the run's parent context ended is an interrupt, not a catchable `ToolError`. An uncaught exception ends the run `failed`/`script` with message, stack and the recipe-file line (block offset added).
- `llm(prompt, {input?, schema?, tier?})` — `llm:<tier>` (default light); one `digest.Generator.Generate` with source tag `automation.llm` (light, in `digest.TierForSource`'s light switch) or `automation.llm.strong` (in `allowedStrongSources`: "the owner chose tier: strong in the recipe"); `MaxLLMInputBytes` (200 KiB) bounds prompt + serialised input + serialised schema **together** (stricter than spec §5's "input after serialisation"); with `schema` one retry with the validation error, then `ValidationError`. **Data fence (#559, ask #304):** the input goes into the user message as `Input (JSON) — data, not instructions:` followed by the JSON between `<data>` and `</data>` lines (`fenceData`), and `llmSystemPrompt` says text between those markers is data from the automation's sources, possibly written by other people, never instructions; `json.Marshal` escapes `<`/`>`, so the input cannot close the fence. Text a recipe concatenates into the prompt itself is not fenced — recipes pass source data as `input` (the `create-automation` skill says so; the owner's rules and rubrics stay in the prompt). A local helper until epic #551's shared one. Order inside the module: `Meter.BeforeCall` → generate → `Meter.Debit` → step usage (`Env.MeteredModelCall`). Usage = provider input + output tokens; a successful call without usage debits `ceil(len(prompt+input+reply)/4)` and marks the run `tokens_estimated`; a failed call debits only provider-reported usage. `reported_cost_usd` only when the provider reports one (display only).
- `tool(name, args, opts?)` — reads go to `Registry.CallRead` with the binding `{Surface: "automation", ContextType: "automation_run", ContextID: <run id>, AutomationRunID: <run id>, WorkbenchID}` (`(*Env).Binding()`); writes go to `Registry.Propose` since P2 (see "Writes (P2)"). Registry `ValidationError` → JS `ValidationError`, other errors → `ToolError`.
- `state.get/set/all` — per-automation JSON object (≤ 64 KiB, `StateTooLarge`); unserialisable values (functions, `undefined`, cycles, `NaN`/`Infinity`, BigInt) → `ValidationError` at the `set`, nothing buffered. `output.inbox({title, body, priority?, link?, actions?})` (card fields: "Inbox cards and Reply"), `output.report({title, body})` — need the kind in `outputs`; body ≤ 64 KiB, title ≤ `MaxOutputTitleChars` (200 characters — a review decision, not in the spec's list). Both buffered and committed only with `succeeded` (AUTO-04). `log(...)` — 4 KiB per call, at most 200 ok steps plus one cap-error step per run (re-checked after argument conversion, since getters may log). **Per-run caps (board #562):** a run makes at most `MaxStepsPerRun` (2000) SDK calls — `Env.Call` journals the call past it as an error step and returns the sentinel `errStepCap`, on which (only) `Sandbox.wrap` aborts with a `RangeError` `*ScriptError` (`errTooManySteps`), so the script cannot catch it and the run ends `failed`/`script`; `CommitBuffer.AddOutput` refuses the buffered output past `MaxOutputsPerRun` (50; inbox, report, briefing — not the `output.target`/`output.slack` proposals) with a catchable `ValidationError`; `session()` refuses the call past `MaxSessionCalls` (10 sessions started per run — `sessionsStarted` counts the run's `session` steps that are not `error`/`denied`, so refused, invalid and failed-launch calls do not count; dry run included) with a `ValidationError` step, since every session's wait pauses the minutes budget. 10 rather than the 3 first proposed: the `pr-review-rounds` template starts one session per changed pull request, and a busy round needs more; the template now lists at most 200 open pull requests (`gh pr list --limit 200`), starts at most 10 sessions per round and keeps the rest. State: `last_round` = the start of the last round that left no pull request behind (set only then); `reviewed` = PR number → when its review session ended, kept for open pull requests while newer than `last_round`, so a review's own comments never bring the PR back and a PR updated after its review is reviewed again. A session that threw (`not started`) or ended `error` is not marked and counts as left over, so it is retried next round (`TestPRReviewRounds_MorePRsThanTheSessionCap`, `TestPRReviewRounds_CarryOverEdgeCases`). The `create-automation` skill's example mirrors it and names the three caps. Recipes installed from the earlier template keep the earlier script (and permission) until reinstalled.
- **Dry run:** `output.*` and `state.set` steps record `dry_run` and nothing commits; `llm` and reads run for real (AUTO-12). `DryRunInMemory(ctx, Backends, *Recipe, DryRunOptions)` runs with a memory journal and writes no row at all (P3's `draft_automation`).
- **Seam for later phases:** `Module`/`Definer` (a later `Define` of the same path replaces the earlier), `SDKFunc`, `Env` (`Call(kind, name, args, fn)` — a step closed inside `fn` is re-closed as an error if the result fails to encode; `MeteredModelCall`), `DefaultModules(Backends)`, `(*OutputMod).RegisterOutputKind`, `Backends{DB, Generator, Registry, Clock, Shell, Workbench}` (Shell/Workbench nil until P5; a module needing a nil backend throws `NotAvailable`).

## Scheduler, executor, wake

- **Daemon wiring** (`cmd/automations_daemon.go`): `wireAutomations` builds the indexer over the personal folder, the executor on `buildAutomationRegistry` and the daemon's generator (`ExecutorOptions{Logger}`), and the scheduler (`SetLogger` with the daemon logger, `wake` = the executor's `Wake`); `Daemon.Run` runs both as goroutines beside the sync loop (never a sync phase) and cancels/waits for them before removing the PID file. It is always called, after the one-time upgrade step (`runAutomationsUpgradeStep`, "Always on" below); only a failed step leaves it out for that process (fail closed).
- **Wake (D1):** `SIGUSR2` (`daemon.AutomationWakeSignal`, `WatchAutomationWake`) feeds only the scheduler and executor; `SIGUSR1` keeps meaning "sync". The watcher is installed at the top of `Run` even when automations are not wired; a wake is then dropped. When `Run`'s context ends the watcher leaves `SIGUSR2` ignored (`signal.Ignore`, never `signal.Stop`) until the process exits, so a CLI that read the caps file just before the daemon removed it gets an explicit no-op (a Go process ignores an unwatched `SIGUSR2` anyway — the default disposition never kills it). The caps file tells the CLI whether this daemon actually runs the automations wake: an older daemon, or one that wired no automations (a failed upgrade step), silently ignores `SIGUSR2`, so a run would just wait for its next poll. The daemon writes `<pidfile>.caps` right after the PID file (first line its pid, then capability lines, `daemon.AutomationWakeCapability` = `automations-wake`; removed with the PID file) — only when the scheduler and executor are wired (`Daemon.automationsActive`). The CLI's `wakeAutomations(cfg)` signals only a confirmed daemon that advertises it (`daemon.HasCapability`); one that does not — older, or one that could not start automations — is never signalled (`errDaemonCannotWake`: "the running daemon is older, or could not start automations (see its log), and can't be woken; restart it … — the run starts on its next poll", exit 0).
- **Always on (2026-10-18, #671, ask #372):** there is no `automations` feature any more — no registry entry, no `automations.enabled` config field, no FEAT-03 hook, no gate in the daemon, the CLI (`run`/`cancel`/`wake`) or the authoring tools. A recipe-less install spends nothing; a recipe runs only after the owner confirms and enables it. **One-time upgrade step** (`cmd/automations_upgrade.go`, `pauseAutomationsTurnedOff`): `runSyncDaemon` runs it after `MigrateFeatureGates` and before `wireAutomations`. An install counts as off when `config.yaml` has `automations.enabled: false` (`config.LegacyAutomationsOff`) or this start's `MigrateFeatureGates` reported a legacy `digest.enabled=false` install — that migration still writes `automations.enabled: false` (`legacyDigestOffFeatureKeys`), so a step that fails later still sees the key on the next start. Then, in every workspace database (`config.WorkspaceDirsWithDatabase`), one transaction each (`db.PauseAutomationsForUpgrade`): every enabled automation gets `enabled = 0`, `disabled_reason` = "Paused by the update: Automations was turned off. Turn it on to run it again." and `disabled_at` = now (Desktop's failure watch posts the notice), and every queued run except dry runs is cancelled with that reason. Then the key is removed (`config.RemoveLegacyAutomationsKey`, a YAML node edit through `patchConfigYAML` that keeps comments; the `automations` block goes too when the key was its only entry), so the next start is a no-op. Any failure (config read, a database, the key removal) is logged, keeps the key so the next start retries, and wires no automations for that process (fail closed); databases already paused stay paused. Each workspace whose pause committed gets `<workspace dir>/automations-upgrade-paused` (atomic, RFC 3339 time; a write failure fails that database), a retry skips those workspaces so a recipe the owner re-enabled there stays on, and the markers are removed (best effort) after the key is. It runs under an agent marker too: it only turns recipes off. The owner re-enables a recipe as before (`SetAutomationEnabled` clears the reason and restarts the schedule from now). A leftover `automations.enabled` key still loads. Tests: `TestPauseAutomationsTurnedOff_*`, `TestMigrateFeatureGates_LegacyDigestOffLeavesTheUpgradeSignal`, `TestPauseAutomationsForUpgrade_PausesEnabledAndCancelsQueued`, `TestLegacyAutomationsOff`, `TestRemoveLegacyAutomationsKey_*`.
- **Scheduler** (`automations.NewScheduler(d, ix, clock, wake)`): ticks at every minute boundary and on `Wake`; each tick rescans the personal folder when `Changed`, then for every runnable `schedule` automation finds the due times in `(last_scheduled_for, now]` in the local zone. The latest one within `ScheduleGrace` (2 min) of now → one `schedule` run (older missed ones are folded into it); otherwise `run_once` → one `catch_up` run for the latest missed time, `skip` → none (AUTO-10). `last_scheduled_for`/`next_run_at` advance in the same transaction as the insert, as a compare-and-set (`EnqueueRequest.AdvanceScheduleTo` + `ExpectLastScheduledFor`; a row changed since it was read → `db.ErrScheduleChanged`, the row is skipped for that tick).
- **No catch-up for a window the automation could not run:** first index of a schedule automation, enable (`SetAutomationEnabled`), a confirm that changes `confirmed_hash` (`ConfirmAutomation`; re-confirming the same hash keeps the point), a rescan that makes the row runnable again — only by the file reverting to the confirmed text, since the trigger is in `approval_hash` (D26) (`db.PrimeAutomationSchedule`, which writes only while the row is not a runnable schedule, so a stale indexer cannot rewind the scheduler) all set `last_scheduled_for = now`.
- **Time zone and DST:** the local zone is re-read every tick (`/etc/localtime` link → `time.LoadLocation`; `TZ` set or an unreadable link → `time.Local`), so a zone change applies without a restart. An hour field without `*` is a wall-clock appointment: a time repeated by a fall-back fires once (first occurrence); a time in the skipped spring-forward hour fires once at the jump (02:30 → 03:00). An hour field with `*` follows elapsed time (both passes of the repeated hour; the skipped hour has no due times). Deliberate deviations from Vixie cron: only the hour field decides (`* 2 * * *` is wall-clock; Vixie treats a minute-or-hour wildcard as a wildcard job), and DST comes from the zone database, not from the size of a clock jump.
- **Clock steps:** clock stepped back → nothing fires until the clock passes `last_scheduled_for` again (no duplicate); `last_scheduled_for` more than a day ahead of now (set under a bogus future clock) → restart from now, no catch-up.
- **Executor** (`automations.NewExecutor(d, Backends, ExecutorOptions)`): `Run` first ends every `running`/`waiting` run `failed`/`interrupted` (restart, D6) — except a live CLI dry run (its `started_at` + budget minutes + 1 min grace still ahead) and a waiting run that can resume (see **Resume after a restart**) — then polls every 10 s or on `Wake`. Each poll sweeps dry runs past that deadline (`db.MarkStaleDryRuns`), cancels queued runs of non-runnable automations (`not_runnable`), resumes ready waits and runs kept for a resume into free slots first, then claims the oldest queued runs under the per-automation `concurrency` and the global `MaxConcurrentRuns` = 2 running (waiting runs do not count; `ClaimAutomationRunWithin`). `db.NextQueuedAutomationRuns` never returns a `dry_run` row. The claim snapshots `recipe_text`/`approval_hash`/budgets; the run re-parses the snapshot with the scope rebuilt from the index row (`scope` + `project_id`) — never the file. A finished run wakes the executor.
- **Run end:** success → `FinishAutomationRun(succeeded, commit)` — also when the journal lost a write (`Journal.Err`): the script's registry writes and `shell()` commands already happened, so failing the run would drop its state and make the next run repeat them; the run's `error` then starts "the run succeeded, but its journal is incomplete: " (board #562). A finish the database refuses is retried three times (1 s, 2 s, 3 s pauses, `Executor.writeFinish`) — not for a run that is gone or no longer active, not for `db.ErrInvalidRunFinish` (a refusal before anything is written: zero time, non-terminal status, commit on failure, invalid state JSON), and not once the executor's ctx is done (the daemon stopping; the restart sweep ends the run). A finish **with a commit** that still fails is then written as `failed`/`backend` ("the run could not be finished as <status>: …") without the commit, so the run never keeps its concurrency slots until the next restart; a finish without a commit keeps its own status, error kind and error (it is already the minimal write). When that last write fails too, the restart sweep ends the run; summary = the last `output.report` title, else the returned value (a string as is, other values as JSON — never `[object Object]`/`undefined`; no return value = `""`), clipped 1 KiB. Uncaught error → `failed`/`script`; uncaught `PermissionDenied` → `failed`/`permission`; deadline → `timed_out`; budget → `budget_exceeded`/`budget`; cancel → `cancelled`; daemon stop during a run, or during a wait that cannot resume → `failed`/`interrupted` ("the daemon stopped…"; a CLI dry run: "the dry run was stopped…"); a daemon stop during a resumable wait leaves the run `waiting`; malformed `event_json` → `failed`/`backend` before the script starts. Ending a run closes its open steps in the same transaction (step `error`: "the run ended (<status>) before this step finished"). Every time-stamping writer refuses a zero time.
- **Waiting** (`(*Executor).Waiter()`, used by P2/P5): sets the run `waiting` with a reason, pauses active time, polls `ready` every poll or on wake, honours cancel and `pause_timeout_hours` (→ `expired`); a ready wait resumes only while running < `MaxConcurrentRuns` (`db.ResumeAutomationRunIfSlot`). `SetAutomationRunWaiting` from `waiting` changes only the reason (P5's `app` → `session`).

## Resume after a restart (2026-10-21, board #795)

A run that waits on the owner — `ask()`, a write tool's `{wait: true}`, `session()` — survives a daemon stop, update or crash (owner decision ask #463, spec `docs/superpowers/specs/2026-10-21-automation-wait-survives-restart-design.md`, AUTO-08 amended).

- **Replay log** (migration 00146, `automation_run_replay`): every completed SDK call of a live (non-dry) run writes one row with its step's close, in the same transaction — kind, name, sha256 of the whole args JSON, the whole result (`result_json`, not clipped; `NULL` = undefined) or the thrown error (`error_json` `{name, message, needed}`), and the `Date.now()` values the script read since the previous call. The call the run waits in gets a `pending` row when its step is marked `waiting`. A trigger deletes the log, and clears `resume_pending`, when the run reaches any terminal status. A result over 1 MiB (`MaxReplayResultBytes`), a log over 16 MiB (`MaxReplayLogBytes`) or more than 10 000 clock reads between two calls set `automation_runs.not_resumable`; such a run ends at a restart as before.
- **Determinism:** the sandbox's clock (`Date.now()`, `new Date()`, `Date()`) reads through the run's `Replay` (whole milliseconds, recorded live, played back in order); `Math.random` is a PCG seeded with `automation_runs.random_seed` (set at claim) and the run id. The regex timer keeps the real clock. Trigger and event payloads are already on the run row.
- **Stop:** a wait whose ctx ends because the daemon stops returns `errDaemonStopping` when the run could resume (it records its log, the log is complete, its last step is the open waiting step with its pending row): the step stays open, the ask stays open, the proposal and session stay as they are, the run stays `waiting` (its active time so far is added to `active_ms`) and the log says "run N stays waiting; the next daemon start resumes it". Any other run — running, or waiting outside a journaled call — ends `failed`/`interrupted` as before.
- **Start:** `MarkInterruptedAutomationRuns` sets `resume_pending = 1` on every waiting run that `resumableRunSQL` admits (not a dry run, not `not_resumable`, the last step the only open one and `waiting`, a record for every earlier step and a pending one for it, the automation runnable and still confirmed at the run's `recipe_hash`) and ends every other active run as before. `sweepAsks` only touches ended runs, so a kept run's ask stays in the stack.
- **Claim:** each poll first claims the kept runs (`ClaimResumeAutomationRun`: oldest first, before queued runs, under the same running-slot bound; the run already holds its per-automation slot). A kept run whose automation is no longer runnable or is confirmed at another hash is ended `failed`/`interrupted` ("…the recipe or its confirmation changed, so the run was not resumed").
- **Replay:** the run re-executes its `recipe_snapshot`. Each call is checked against its record (kind, name, args hash, and that the script read the clock exactly as often before it; `agent()` and `session()` are checked by what the script asked — `Env.CallWithReplayKey` — since their step args hold a carved budget, the provider's name or the workbench's default agent, which may differ after the restart; a resumed `session()` keeps the agent and title it started with); a match returns the recorded result or rethrows the recorded error, with no backend call and no new step (AUTO-11). `state.set` and the buffered outputs run again on a scratch step (`Env.CallBuffered`) so the commit buffer is rebuilt (AUTO-04; the base is the automation's state at the resume). At the waiting call the step is adopted (`Step.Resumed()`): `ask()` waits on the ask it filed, `tool(…, {wait: true})` on its action, `session()` on its step's session; the pause timeout counts from that step's `started_at`. The log says "run N resumed after restart (replayed K steps)". The meter starts with the run's recorded tokens and active time; replayed calls spend nothing.
- **Divergence:** a mismatch, a clock read past the record, or a script that ends before its waiting call ends the run `failed`/`script` with "the recipe ran differently after the restart (step N); it was not resumed"; nothing was executed, and the next poll withdraws its open ask. A deadline, budget, memory or cancel interrupt during the replay keeps its own end. A stop during the replay (before the waiting call) records that life's active time and puts the run back to `waiting` with its old reason; the next start judges it again. The 16 MiB log cap counts the records of earlier daemon lives.
- **v1 limits:** a crash during a replay leaves the run `running`, and the next start ends it `interrupted`. The base state of a resumed run is the committed state at the resume (another run of the same automation may have committed meanwhile). Guards: `TestAuto08_ResumeAtAskWait`, `TestAuto08_ResumeAtApprovalWait`, `TestAuto08_ResumeAtSessionWait`, `TestAuto08_DivergenceEndsTheRunWithoutExecuting`, `TestAuto08_ChangedRecipeIsNotResumed`, `TestAuto08_LargeResultMakesTheRunNotResumable`, `TestAuto08_TimeAndRandomReplay`, `TestAuto08_ResumedTokensNotDoubleCounted`, `TestAuto08_ResumedWaitKeepsItsPauseTimeout`, `TestAuto08_StopWhileRunningStillInterrupts`, `TestAuto08_ResumeAfterAgent`, `TestAuto08_ResumeAfterDefaultAgentChanged`, `TestAuto08_StopDuringReplayReturnsToWaiting`, `TestAuto08_DeadlineDuringReplayKeepsItsEnd`, `TestAuto08_ClockReadOverflowMakesTheRunNotResumable`, `TestAuto08_KeptRunChangedBeforeItsClaimIsNotResumed` (`internal/automations/replay_test.go`), `TestAuto08_ReplayLogCapCountsTheStoredLog` (`replay_internal_test.go`); `TestAuto08_RestartKeepsResumableWaitingRun`, `TestAuto08_ReplayLogDeletedOnFinish` (`internal/db/automation_run_replay_test.go`).

## v1 limits

- `list_messages`/`list_upcoming_events` have no per-account scope (only `@*` or `tool:`); the broad knowledge tools, `list_inbox`, the memory tools and `get_writing_style` only by `tool:<name>`; `get_confluence_page` not offered.
- `show --json` `widening` is `[]` for a confirmed recipe and **every** current normalised permission otherwise: the index keeps only `confirmed_hash`, not the confirmed permission list, so the card's "new since your confirmation" marks every permission of an unconfirmed recipe. `draft_automation`/`save_automation`, `validate --against` and `show`'s **Changed** block reach the confirmed text (`automations.ConfirmedRecipe`, P3).
- The memory budget watches the whole process's heap: a sync (not a run) growing it by 1 GiB while a run executes can still stop that run, and the overshoot is bounded only as described under Hardening. A RegExp `split` and `[...string]` spread are bounded by the budget alone. Native builtins are not preemptible — a stuck one is abandoned at deadline + 2 s and its automation disabled; while two abandoned goroutines are still alive the executor claims nothing (the count drops when one finally returns, or at a daemon restart).
- No BigInt (owner decision, ask #331): its `**` and `<<` operators build a result of any size in one native step, which no wrapper can reach. The compiler refuses a BigInt literal (`10n`, `0xffn`; `bigIntRefusal` walks the parsed program, so a literal hides nowhere — not after a regex literal holding a quote either) with "BigInt is not available in automations" (a parse error on the recipe's line; a run of such a recipe fails before it starts), and the lockdown deletes `BigInt`, `BigInt64Array`, `BigUint64Array` and DataView's `get/setBigInt64`/`get/setBigUint64`; `BigInt.prototype.constructor` throws, so nothing else yields one.
- Linear expansions stay uncapped: `toUpperCase`/`toLowerCase` (≤ 3×), and every builtin whose output is at most proportional to an input that already exists.
- The size/depth limits cover the builtins listed under Hardening; anything else is bounded by the memory budget. A regex timeout in an aliased or optional `exec` call reads as "no match" (goja's behaviour; see Hardening). Compiling a RegExp at run time (`new RegExp(pattern)` with a huge or pathological pattern) is native and not preemptible: it is bounded only by the abandon net (deadline + `AbandonGrace`, then the automation is disabled). `flat(depth)` makes one `flatMap` pass per level, so an Array subclass's species constructor runs once per level instead of once.
- Clock jumps: a clock set forward by less than a day holds the schedule until real time catches up (the slot in between is lost); one stepped back by more than a day restarts from now (a due time may repeat).
- A CLI killed mid dry run leaves a `running` dry-run row until the daemon sweeps it past its deadline + 1 min.
- Environment markers (`WATCHTOWER_AUTOMATION_RUN_ID`, the AI-agent markers, `WATCHTOWER_TERMINAL_SESSION_ID`) are not a boundary against a same-user process that forges them. The run-bound server (`mcp --surface automation --automation-run N`) also refuses to start with `WATCHTOWER_TERMINAL_SESSION_ID` set — `agent()` children get an allowlisted env that never carries it, so a terminal session's agent that copies the run's marker is turned away (`TestAgentMCPServer_RefusedInsideATerminalSession`); a process that forges both still gets only that server, whose writes stay pending proposals (`Binding.AutomationAgent`).
- TCC: a workbench folder may sit under a protected location (`~/Documents`, `~/Desktop`, `~/Downloads`, iCloud Drive, `/Volumes`), so neither the daemon (personal folder only) nor the CLI touches a workbench folder a command is not about. `save --path`, `dry-run --file` and `delete` match a path to a workbench lexically against its stored (symlink-resolved) folder and canonicalise only that one workbench's recipe folder (or, for `delete`, the automation's own scope; `rescan --workbench N` only N's). ## mcp() and agent() (P6 part 1, 2026-10-16)

Results are plain JSON values capped at 256 KiB (`ResultTooLarge`). One journal step per call. In a dry run of a saved recipe `mcp()` is real (reads only); in a `draft_automation` dry run (`Env.InMemoryDraft`, shared with `agent()`) it calls nothing — after the manifest check the first call closes its step `dry_run` with a note and ends the draft with `dry_run.status: "stopped"` (`automations.DryRunStopped`, an `InterruptDraftStop` interrupt, so a script reading the result never fails on a stub; the Draft panel shows the note and points to the card's **Dry run**). Needs `agent:run` plus an `llm:` tier; `wait` is refused. Inner tool calls are summarised in the one `agent` step (AUTO-11).

- **Dry run of an event recipe.** An event trigger has no event on a dry run unless `EnqueueRequest.EventJSON` carries one: `triggerInfo` decodes a dry run's `event_json` like an event run's (an `AutomationEventPayload`, every event an object), and the script's `trigger.events` is that payload. `TestTemplates_DryRunE2E` plays a `gmail.new_messages` event for `new-mail-summary` this way.
- **`new-mail-summary` paging and done ids** (board #799, 2026-10-21: replaces the per-mailbox time cursor, which silently skipped mail synced after a newer message was summed up — rule 1 of the skill's "Reliable recipes"). State `mail = {base, boxes: {mailbox: {done: {message id: minute}, floor?}}}`, every minute counted from `base` (the window start of the run that saved it), so an entry costs its id plus at most 8 bytes. Each run lists the mailbox's last **two days** newest first (`since` = the window start, a whole minute) and pages older with `before` (+ 1 s, skipping the ids already listed this run, so a second split across pages loses nothing); a message is new unless its id is in `done` or its minute is before `floor`, so mail synced late — a slow sync, a mailbox connected later, an IMAP catch-up after the Mac slept — is summed up if it is inside the window when it syncs (two days rather than one so mail synced after a night or a day off still is). It sums up at most 600 messages per mailbox per run, **the oldest first**, in `llm()` calls of 200, and marks only those done, after their summary is filed: past the cap the summary is titled `N of M messages` and says how many newer messages are left for the next run. Ids older than the window are pruned. **State bound:** the `done` entries of all mailboxes share 56 KiB of JSON under `MaxStateBytes` — about 2,400 Gmail ids (16 characters) in all, so one mailbox alone reaches it at about 1,200 messages a day. The budget is split fairly (the smallest mailboxes keep all they hold, the rest split what is left), so a mailbox holding no more than budget / mailboxes is never cut; a mailbox over its share drops its oldest **whole minutes** and its `floor` moves just past the last one dropped — the floor never splits a minute, so no dropped id is summed up again, and the mail a run left for the next one (newer than all it summed up) is passed only when the share cannot hold the entries from its minute on; then that mail, and late mail older than the floor, is skipped. **Migration:** an old `cursors` map is re-keyed through the `list_emails` name probe (a cursor stored under the address is found by an event run naming the mailbox by label; a key whose mailbox can no longer be read is kept and logged); a mailbox's first run marks every message before the cursor's date, and those at it whose id is in `ids`, done instead of summing them up, then drops the cursor (`cursors` is set to `null` once none is left); no time mark stays behind. **Known limits:** more than 200 messages in one second (one `list_emails` page) cannot be listed past the first 200 of that second, the rest of that second is skipped; an IMAP mailbox whose UIDVALIDITY changes gets new ids for every message, so its window is summed up again once (`TestTemplates_RunE2E` burst, same-second, split-second, run-cap, late-mail, cursor-migration, cursor-by-label, state-budget and eviction-floor cases).
- **Production-size inputs.** `list_jira_issues` returns lean rows on every surface (no `RawJSON`, no `CustomFieldsJSON`, description clipped at 512 bytes with `DescriptionTruncated`; `get_jira_issue` keeps the whole issue — `TestListJiraIssues_LeanRows`), and the two reports pass `llm()` only the fields they need (issues as key/title/status/assignee/dates, time in status as totals — plus compact intervals in the Jira report —, one latest people card per person with long fields clipped, up to 12 messages per person clipped at 240 characters, halved until the input fits 190 KiB). `TestTemplates_ProductionSizeReports` runs both over 200 issues with 20 KiB raw payloads, 40 full people cards and 2 KiB messages to success, with tokens estimated (bytes/4) inside the recipes' budgets.

## Event triggers (P4, 2026-10-17)

Spec §8. Board #753, plan `docs/superpowers/plans/2026-10-14-automations-p4.md`. No migration (00113 already has `event_cycle`, `event_json` and the unique `(automation_id, event_cycle)` index) P3 already renders event triggers; the one Swift change is the edit form's **On an event** choice, which P3 had disabled (Event v1 limits below).

- **Event types and fields** (`automations.EventTypes`, `EventFields`) — ids, labels, enums and counts only, never message text, subject, summary, title or body (`TestBus_EventsCarryNoContent` runs every source over fixtures whose content carries a marker):

  | Type | Fields (`count` is carried, not matchable) | Published by |
  |---|---|---|
  | `slack.new_messages` | `account`, `channel`, `channel_id`, `count` | `phaseSlackSync` (`SlackSource`) |
  | `gmail.new_messages` | `account`, `provider` (`gmail`/`imap`), `count` | `phaseGmailSync`, `phaseImapSync` (`MailSource`, one per account syncer) |
  | `jira.issue_changed` | `account`, `key`, `project`, `field` (`status`/`assignee`/`priority`/`comment`/`other`) | `phaseJiraSync` (`JiraSource`) |
  | `calendar.event_changed` | `account`, `event_id`, `change` (`created`/`updated`/`cancelled`) | `phaseCalendarSync` + `phaseCalDAVSync` under one snapshot (`CalendarSource`) |
  | `confluence.page_changed` | `space`, `page_id` | `phaseExternalSync` (`ConfluenceSource`) |
  | `slack.reaction_added` | `account`, `channel_id`, `emoji` (bare name, no colons); `message_ts` is carried, not matchable | `phaseReactionCommands` (`reactioncmd.Pipeline`, straight into the cycle's bus, no snapshot) |

  `account` is the account's label, else its team domain (Slack), address (mail), site name (Jira), email (Google calendar) or, for a CalDAV/ICS account, its username, else `<provider>:<id>` (never its URL). One Slack event per channel whose newest stored message moved forward (`SlackChannelNewestTS`, the `messages` table itself — the default search sync never writes `sync_state`), counting only messages newer than the channel's newest before the phase; one mail event per account sync that stored messages dated after the account's news floor (counted from the table, so also after a `Sync` that returned an error); one Jira event per changed field, in the order status, assignee, priority, comment (the comment count grew), or one `other` when only `updated_at` moved or the issue is new to a project that already had issues; one calendar event per changed event (a row gone whose end is still ahead reads `cancelled`, one whose end has passed left the window — nothing); one Confluence event per page stored new or at a higher version.
- **Owner-message rule:** a Slack event counts only the new, non-deleted messages not written by the owner (the account's namespaced owner id, `SlackEventLabels` through `GetSlackAccount`, OWNER-01); a channel whose only new messages are the owner's publishes nothing.
- **Backfill is not news:** a Slack channel with no stored message before the phase (and any message older than the channel's newest before it — a history backfill, a thread fill), a mail account's first sync (watermark unset before its syncer ran, `MailWatermarkSet`) and, on every later sync, any message not dated after the account's news floor read before the syncer (`MailNewsFloor`: the later of the account's `created_at` — when it was connected — and its newest stored message date; `CountMailAfter` counts the rest), so the backlog a capped first sync (`MaxMessagesPerSync` over the 7-day window, oldest first) drains over later cycles and the known mail an IMAP UIDVALIDITY change stores again under new uids never fire, a Jira project with no issues before the phase, a calendar with no events before the phases, and a Confluence space whose backfill was not done before the phase (or that was selected during it) publish nothing. History backfill (`phaseHistoryBackfill`, the last phase, after the pipelines) is never observed.
- **Daemon wiring** (`internal/daemon/automation_events.go`, `cmd/automations_daemon.go`): `wireAutomations` builds an `automations.Bus` beside the scheduler and executor (wake = the executor's `Wake`); when the upgrade step failed nothing is wired: no bus, no snapshots. `runSync` calls `Begin` once per cycle (loads the runnable event automations); `observePhase` takes a source's read-only `Before` snapshot, runs the phase, then diffs `After` and publishes — only when the cycle's bus `Wants` that type, so a type nobody subscribes to costs no snapshot. A snapshot or diff error is logged and never skips the phase; the snapshot reads ignore cancellation. `Flush(cycleID)` runs once per cycle right after `phaseExternalSync` (before `phaseAgentAnalytics` and the pipelines), also on a cancelled context; `cycleID` = `syncStart` in RFC 3339 UTC with nanoseconds (`time.RFC3339Nano`; trailing zeros dropped), so two cycles in one second — the startup calendar pass and the first `runSync` — never share an id. `Run`'s startup calendar pass ahead of the first `runSync` (#740) is its own event cycle (`startupCalendarSync`: `Begin`, `CalendarSource` around both calendar phases, `Flush` keyed by the pass's start), so a calendar change made while the daemon was stopped still fires; with no bus it only syncs. `phaseReactionCommands` keeps its place (right after `phaseSlackSync`, before the `Flush`) and publishes `slack.reaction_added` into the cycle's bus (reaction events below).
- **One run per automation per cycle (AUTO-09):** `Flush` only queues — per automation with at least one match, one `trigger='event'` row through `db.EnqueueAutomationRun` with `event_cycle` and `event_json` (`AutomationEventPayload{cycles, events ≤ 100, count, truncated}`; `count` = every match, `truncated` past `MaxEventsPerRun`). If a run already carries the cycle (its `event_cycle` or `event_json.cycles`), nothing is written; if a still-queued event run of an earlier cycle exists, the new cycle is merged into it (`db.MergeQueuedAutomationRunEvents`: cycles appended, events capped at 100, idempotent per cycle, refused once the run was claimed — then Flush enqueues once more). One automation's error is logged and does not stop the others; `wake` is called once when anything was queued or merged. The daemon logs one summary line per cycle that did anything. The executor decodes `event_json` into `trigger.events` (each event flat, `{"type": …, <fields>}`) and `trigger.truncated`.
- **`where`:** every key must match (AND); keys are the type's matchable fields (an unknown key or a malformed glob is a parse error — new in P4: an event recipe that parsed before with such a `where` is now refused at validate/index time; nothing is lost, since event triggers never fired before P4); a value matches case-insensitively by equality or as a `path.Match` glob — `*` does not cross `/`. An empty `where` matches every event of the type. Matching is a filter, never a permission: the recipe still needs its manifest for whatever it reads.
- **Cost:** a cycle takes snapshots only for the types some runnable event automation subscribes to. Jira's and the calendar's snapshots are whole-table reads of ids, enums and timestamps (the Jira one reads every issue on each side of the phase), and they run even when the phase's own interval gate then skips the sync. Slack's snapshot (`MAX(ts)` per channel) walks the whole messages primary-key index on each side of the phase.

### Reaction events (2026-10-18, rules in Automations)

Spec `docs/superpowers/specs/2026-10-18-rules-in-automations-design.md`, plan `docs/superpowers/plans/2026-10-18-rules-in-automations.md`; owner approvals: asks #346, #347 (direction), #350 (design), #353 (plan). This reverses P4's "reactions are not an event source".

- **Event.** `slack.reaction_added` (`automations.ReactionEvent`): `account` (P4 Slack rule), `channel_id`, `emoji`, `message_ts`. No channel name, message text or author (`TestBus_EventsCarryNoContent`). A recipe that wants the message reads it through the usual automation reads (`list_messages` under `slack:read@*` or `tool:list_messages`).
- **Gates.** The event needs the daemon's bus (wired unless the upgrade step failed) and `reaction_commands.enabled` (the feature owns the Slack poll; off = zero API calls, FEAT-01).
- **Ledger.** Migration 00138: table `reaction_events(account_id, channel_id, message_ts, emoji, seen_at)`, same identity as `reaction_commands`, plus `slack_accounts.reaction_events_seeded_at`. `reaction_commands` and REACT-01..05 are untouched. `FilterUnseenReactionEvents` is a read before any insert, so a quiet poll writes nothing. An event is published only for rows actually inserted: removing and re-adding a reaction does not fire again.
- **Which reactions are read.** When the cycle's bus `Wants` the type, every owner reaction is read (`where` is applied later by `Publish`); otherwise only dictionary emoji, and with an empty dictionary and no subscriber there is no `reactions.list` call. A dictionary emoji that is also subscribed does both, through the two independent ledgers.
- **Seeding, never replay.** The first poll a recipe wants records the current reactions without publishing and stamps `reaction_events_seeded_at`. The stamps are cleared when the daemon's bus does not want the type (no wired bus gives a no-bus sink, or no runnable subscriber) and when `reaction_commands` is off, so the next subscriber reseeds instead of replaying the gap. The CLI `reaction-commands poll` passes no sink and leaves the event state alone.
- **Message-time cutoff (ask #366).** After seeding, a reaction fires only when its message was posted at or after the account's seed stamp (`postedSince`; a `message_ts` that does not parse counts as old). `reactions.list` returns only the latest window, so removing fresh reactions slides old, never-recorded ones into it; the message time is what tells them apart. The cost: a fresh reaction on a message from before the seed (or before a reseed) never fires. Old reactions are not written to the ledger, so the filter stays a read.
- **Loss window.** `Publish` is in memory until `Flush`. A crash between the ledger insert and the `Flush` loses the event; it is never replayed (at-most-once, the same window P4's snapshot events have).
- **Volume.** No own budget: the bus caps a run at 100 events (`truncated`), and AUTO-09 bounds runs per cycle. STRIP-01 holds: a run started by the owner's reaction is gesture-gated.
- **Tests.** `TestDaemon_ReactionCommandsPublishToCycleBus` (replaces `TestDaemon_ReactionCommandsUnchangedByBus`), `TestDaemon_ReactionPollWithoutBusResetsEventSeeds`, `TestDaemon_ReactionCommandsOffResetsEventSeeds`, `TestEventAutomation_ReactionEndToEnd` (`internal/daemon/automation_events_e2e_test.go`), and `internal/reactioncmd/events_test.go` (seeding, exactly once, both handlers, no `reactions.list` without a listener, `TestRun_ReactionOnMessageOlderThanSeedNeverFires`).
- **Desktop.** The Automations tab has a segmented section picker (Automations / Reactions / Tracks), reachable with zero recipes. Reactions: an off banner with **Turn on**, the dictionary editor (moved from Settings → Slack, unchanged logic), "Automations that listen to reactions" (emoji from `where.emoji`) and **New reaction automation**. Tracks: shown only while the `tracks` feature is on (since C1, 2026-10-22: the Tracks sidebar destination is gone, and `AutomationsView` computes the gate in one place); a load error is shown, not an empty list; a track opens its card in the Inbox's Tracks filter (`AppState.navigateToTrack` → `openInbox`). Settings → Slack shows only a pointer (ask #366): **Open** (the Reactions section; no Turn On Automations since board #671). The edit form hints when reaction commands are off. ### Event v1 limits

- Events are diffs of the database around a phase: a change made and reverted within one sync interval is invisible.
- **Jira `comment`** needs Jira comment sync, which runs only while Stream Digests is on (`streams.enabled`, `jiraCommentSyncEnabled` in `cmd/sync.go`; off there means no comment events) and covers at most `ideas.max_comment_issues_per_sync` (default 50) issues per pass; the first comment fetch of an issue can count its old comments as new ones.
- **"No rows before the phase" stands for "just connected":** an empty calendar or a project with no issues never announces its first item (the same holds for a Slack channel until it holds a message).
- **Mail:** a message is news only when dated after the account's connect and its newest stored message, so mail delivered with an older date than one already stored is not counted; Gmail turned on long after its Google account was connected (calendar first) can read the part of its backlog dated after the connect as new once the first sync was capped. Owner-sent mail is counted.
- **Calendar:** an event rescheduled beyond the sync window reads `cancelled`; widening the window (`SyncDaysAhead`) reads the newly visible events as `created`; a failed upsert can read as `cancelled` then `created`. A cancelled event confirmed again publishes nothing.
- **Not event sources:** Linear (spec §8 lists none), history backfill. Comment-only Confluence changes (`children_changed_at`), blog posts and attachments are not events.
- `where` globs use `path.Match`: `*` does not cross `/`.
- **Reaction events:** a reaction on a message posted before the account's seed stamp never fires, even when it is fresh (the message-time cutoff above). The dictionary path does not have the cutoff: removing recent reactions can still let older dictionary reactions slide into `reactions.list`'s capped window (20 pages of 100 items) and run as new. The `emoji` `where` value is stored without surrounding colons (`:eyes:` = `eyes`).
- The Desktop edit form picks **On an event** and its type, and edits or removes existing `where` rows; a new `where` key is written in the recipe text (Monaco editor, Change in words, a template).

## Inbox cards and Reply (2026-10-21, plan B of the panel and Inbox work)

- **Migration 00149:** `automation_runs.trigger` gains `'reply'` (table rebuilt with ids, the AUTOINCREMENT mark and the 00146 columns/trigger carried; a reply run is outside the queued-coalesce partial index). `automation_outputs` gains `link`, `actions_json` (default `[]`), `done_at`, `pressed_action`, `pressed_run_id`, `pressed_at`; existing read cards get `done_at = read_at`.
- **`output.inbox({title, body, priority?, link?, actions?})`** (`sdk_output_card.go`): `link` and an `open` action take `http`, `https` or `watchtower-nav://` only (at most 2048 bytes), refused at write time and checked again when pressed. At most 4 `actions`, each `{label (≤ 40 chars), primary?}` plus exactly one kind: `open` (Link), `chat` (first message, ≤ 4 KB), `agent: {task (≤ 4 KB), workbench?}`, `reply: "<value>"` (≤ 100 chars) with optional `data` object (≤ 8 KB JSON; only on a reply). The first action is primary; `primary` may only be set to `false`, on the first action. Violations are a catchable `ValidationError`. A `chat` message and an `agent.task` are instructions the chat or the agent follows, so a recipe writes them as fixed text and never builds them from email, Slack, tool or `llm()` output (the `create-automation` skill says so); untrusted material goes in the card `body`, which the chat gets attached and the agent gets after the task, fenced as data (`InboxCardTexts.agentActionTask`). The Agent button's help shows the workbench it goes to (or "the workbench you pick") and the task, up to 600 characters (`InboxCardTexts.agentActionHelp`).
- **`inbox:reply`** (manifest capability, `Manifest.AllowInboxReply`): a Reply action without it is a `PermissionDenied`; it requires `outputs: [inbox]`, is part of `approval_hash` (adding it needs a new confirmation) and is never a trigger — a recipe keeps exactly one trigger. The executor re-checks it for every reply run (also a resumed one) against the run's snapshot; a snapshot without it fails before its script runs.
- **One press = one run:** `db.PressInboxOutputAction(output, index, now)` records the press and queues one `trigger='reply'` run in one transaction, never merged with another run, never through the event bus. A card is pressed once (`pressed_at` set, a second press gets `AlreadyPressedError{RunID}`); a done or dismissed card, a non-Reply action or a non-inbox output is refused. The script sees `trigger.kind === "reply"` and `trigger.reply = {output_id, action, value, data, card: {title, link}}`; `data` is read from the stored output, never from the Desktop.
- **`watchtower automations reply --output <id> --action <index> [--json]`:** refused under every AGENT-07 marker, otherwise `confirmWithOwner` (the Desktop's own launch is granted with no window); refuses before asking when the card, the automation (`notRunnableReason`) or the confirmed recipe (no `inbox:reply`) cannot take the press. Queues only (AUTO-09) and wakes the daemon; pinned `--json` keys `run_id`, `daemon_running`; text form "Queued run #N.".
- **Desktop states:** opening a card writes `read_at`, **Done** writes `done_at`, **Dismiss** writes `dismissed_at`; the unread dot counts `read_at IS NULL` among cards neither done nor dismissed (the sidebar badge counted them too until C1, which left automation cards out of it — see the next section). A pressed Reply card shows "Sent — run #N".
- **Skill:** `create-automation` documents the four kinds, the limits, `inbox:reply` and the `trigger.kind === "reply"` branch, with a "Mail summary with a mute button" example.
