# Automations (P1 core + P2 writes + P3 authoring and Desktop + P5 part 1 workbench + P6 part 1 `mcp()`/`agent()`, 2026-10-16)

Owner-written recipes the daemon runs on a schedule or on demand: a Markdown file with a strict YAML frontmatter (trigger, permission manifest, outputs, budget) and one synchronous JavaScript block, executed in a goja sandbox whose only world is the automation SDK. Spec: `docs/superpowers/specs/2026-10-14-automations-design.md` (decisions §20 ask #270, §20.1 asks #271–#273/#277, §20.2 asks #280/#287); business spec `…-business.md`; plans `docs/superpowers/plans/2026-10-14-automations-p1.md` … `-p6.md`. Contracts AUTO-01..13: `docs/inventory/automations.md`. Board #753.

P1 ships the core: recipe + manifest parser and hashes, the goja sandbox with the P1 SDK (`llm`, read `tool`, `state`, `output.inbox`/`report`, `log`), the run/step journal, the cron scheduler and the run executor in the daemon, per-run token and time budgets, the automation read tools, and the `watchtower automations` CLI. P2 adds writes (see "Writes (P2)" below): `tool()` writes and `output.target`/`output.slack` through the registry on the `automation` surface, per-automation auto grants with `automations auto`, `output.briefing` and the briefing's FROM YOUR AUTOMATIONS section. P3 adds authoring and the Desktop (see "Authoring and the Desktop (P3)" below): the `create-automation` skill, `draft_automation`/`save_automation` and the `automation_editor` surface, the Automations tab with its card, history, edit form, Monaco recipe editor, save and confirmation sheets, the "change it in words" editor chat and the New automation sheet, Inbox labels and output cards, and quick run (**Run Automation…** on ⌃⌘R, the tray's **Run automation ▸**, a finish notice). The `automations` feature (default on, D12) gates all of it; its Settings → Features description still calls it a preview managed with `watchtower automations` (the registry text was not rewritten in P3 — a follow-up).

## Recipes and folders

- **Personal:** `<config.WorkspaceDir()>/automations/*.md` (`automations.PersonalDir`, D8) — inside the workspace data dir, never a TCC-protected folder. **Workbench:** `<workbench folder>/.watchtower/automations/*.md` (`WorkbenchDir`; the scope and the scheduler's workbench rescans are P5 — in P1 the CLI's `rescan --workbench N`, `save --path` and `dry-run --file` already accept that folder).
- The filename stem is the **slug** (`^[a-z0-9][a-z0-9-]{0,63}$`); other stems and other extensions are skipped (reported by `rescan`). A slug already used in the scope by a row at another path (a removed row included) is skipped with a message naming that automation, never a raw UNIQUE error.
- **Symlinks and special files are never read.** The indexer lists a folder with lstat semantics; only a regular file named `*.md` is a recipe. A symlink (inside, outside or dangling) or a FIFO/socket/device named `*.md` is skipped with "symlinks and special files are not read; put the recipe file itself in the folder" and never opened; a recipe replaced by a symlink is marked removed; a directory named `*.md` is ignored silently. A regular file is read Lstat → `open(O_NOFOLLOW|O_NONBLOCK)` → fstat (still regular, same inode). The folder path itself is canonicalised (`filepath.Abs` + `EvalSymlinks` on the deepest existing ancestor, `automations.CanonicalDir`), so a symlinked workspace dir still indexes. `automations.ReadRecipeFile(path)` is the same read for the CLI. P5 follows the same policy.
- **Shape:** frontmatter keys `name` (1–80), `trigger` (exactly one of `schedule` — strict 5-field cron, no `@descriptors`, no `TZ=` —, `button {label 1–24, confirm}`, `event {type, where}`, `manual: true`; `manual: false` is an error), `missed` (`run_once`|`skip`), `concurrency` (1–4), `permissions`, `outputs` (`inbox`, `briefing`, `report`, `target`, `slack`), `budget {tokens 1000–2000000, minutes 1–60}` (defaults 50000 / 5; a `usd` key is a parse error, D4), `pause_timeout_hours` (1–168, default 72). Unknown keys and a `workbench:` key (D15) are parse errors. Exactly one ```` ```js ````/```` ```javascript ```` block (also `~~~` fences, case-insensitive info string); zero, two or an **empty** block is a parse error (stricter than spec §2.2's "exactly one"). Text outside the block is the description. Max 256 KiB; CRLF, lone CR and a UTF-8 BOM are normalised (same `approval_hash` as the LF twin); invalid UTF-8 is a parse error. A parse error is indexed with `parse_error` set (not runnable); `ParseError{Line, Msg}` prints `line N: msg` (line 0 prints the message only).
- **Hashes:** `content_hash` = sha256 of the file bytes (change detection; streamed over the whole file even when only `MaxRecipeBytes`+1 bytes are kept). `approval_hash` = sha256 of canonical JSON `{"permissions":[sorted normalised],"outputs":[sorted],"scope":"personal"|"workbench:<id>","script":"<exact js block>","trigger":<trigger>,"missed":"<policy>","budget":{"tokens":N,"minutes":M},"concurrency":N}` in that key order, no whitespace, no HTML escaping (`approvalCanonical`; `canonicalTrigger` is the `trigger_spec` shape from `triggerSpecOf` minus the button's cosmetic label, `confirm` kept). A schedule, missed-policy, budget or concurrency edit therefore needs the owner's confirmation again (D26, ask #294, amending D5); name, description, a button's label and pause timeout do not change it. **Upgrade note:** D26 re-hashes every recipe once, so every recipe confirmed before it shows Needs your confirmation until the owner confirms it again.
- **Index** (`automations` table, migration 00113): `Indexer.RescanPersonal`/`RescanFolder(ctx, scope, dir)` parse every recipe and upsert the row by `path`, storing the parsed copy in `recipe_text`; the executor runs that copy, never the file. An insert never sets `confirmed_hash`/`enabled`; an upsert never touches them or `last_scheduled_for`; a missing file → `removed_at`; a missing folder = empty. `Indexer.Changed(dir)` is an lstat fingerprint of the folder (names, types, sizes, mtimes, ctimes) plus `db.AutomationScopeGeneration` (count / max id / max `updated_at` of the scope's rows), so a CLI delete that frees a slug triggers the next tick's rescan.
- **Runnable** = parsed, `enabled`, not removed, `confirmed_hash != ''` and `= approval_hash` (`db.Automation.Runnable()`). `confirmed_hash` is written only by `db.ConfirmAutomation(id, hash, now)` (refuses any hash but the current `approval_hash` with `ErrHashMismatch`; missing row `ErrAutomationNotFound`). In P1 its callers are `automations confirm` and `automations save --confirm-hash`, both refused under AI-agent markers (AGENT-07); P3's `save_automation` apply is the third (§2.5).

## Permission manifest

- Grammar (`ParsePermission`, `ParseManifest`): `capability:verb[@scope]` | `tool:<name>` | `mcp:<server>/<tool-glob>` | `shell:"<exact command>"`. Capabilities: `slack`/`gmail`/`jira`/`calendar`/`confluence` (`read`/`write`, scope required: account label or address, Jira project key, Confluence space key, `*` = all); `targets`/`tracks`/`ideas`/`digests`/`people`/`transcripts` (`read`/`write`, no scope); `meetings`/`dayplan` (`read` only, ask #277); `llm` (`light`/`strong`, strong implies light); `agent:run`; `ask:owner`; `session:start[@claude|codex]`. There is no `knowledge`, `inbox` or `memory` capability (`knowledge:read` is a parse error naming the three `tool:` entries to use, D21). `shell:`/`session:`/`ask:` in a personal recipe are parse errors (D7). Scopes containing whitespace are refused. Normalisation: lower-case capability/verb/scope, Jira and Confluence scopes upper-case, duplicates folded, sorted.
- Matching (AUTO-01): `ToolCapabilities` maps each registry tool to `{Capability, Verb, ScopeArg, ScopeOf}`; a call is admitted by `tool:<name>` or by the capability+verb when every scope unit of the call is covered (case-insensitive equality or `path.Match` glob; any of a unit's `Values` — e.g. an account's label or its address — may match). A scope argument absent from the call is covered only by `@*`; a scope key spelled in another case (`PROJECT`, `Key`, `Account`) is not read as the scope, so the call needs `@*`. The tool must also be visible on the `automation` surface. A `ScopeOf` lookup failure is a `PermissionDenied` naming `<cap>:<verb>@*` (with the cause), never a panic.
- Scopes worth knowing: Jira reads by their own `project`/key prefix — a project grant covers the linked issues of other projects that the tool returns with that project's issues (ask #287); `get_jira_time_in_status` by `project`, else its `issue_keys` prefixes, else absent; `list_jira_sprints` by `project` or the project of its `board_id`; `list_emails`/`get_email` by the resolved account (label or address); `list_calendar_events` by `account` (absent → `calendar:read@*`); `send_slack_message` (P2) by the resolved `account_id`. `list_messages` and `list_upcoming_events` are **always unscoped** — only `slack:read@*`/`calendar:read@*` or `tool:<name>` admits them (D22, ask #273; both readings owner-confirmed in ask #280). `digests:read` covers `list_digests`/`get_digest`/`get_today_briefing`, `people:read` covers `find_experts` (ask #287). `tool:`-only: `search_knowledge`, `get_knowledge_document`, `get_task_context` (D21), `list_inbox`, `memory_recall`/`memory_open`/`memory_map`, `get_writing_style` (D23).
- `Covers(old, new)` returns the entries of `new` not covered by `old` (`*` covers every scope of the same capability+verb, `llm:strong` covers `llm:light`, shell entries byte-exact) — the widening list. `ClampListLimit(t, args)` injects `limit` 50 / clamps to 200 for a tool whose schema has `limit` (values owned by `tools.DefaultListLimit`/`tools.MaxListLimit`).

## Sandbox and SDK (P1)

- One fresh goja runtime per run. No `require`, `console`, timers, promises, `async`/`await` (`PreParse` fails the recipe with "the script API is synchronous", naming the script line); no `eval`/`Function`, and every function prototype's `.constructor` throws `EvalError`; a script that breaks out of its wrapper function is a parse error (AUTO-07). Globals: the SDK, a read-only `trigger` (`{kind, run_id, scheduled_for?, catch_up?, button?, events?, truncated, dry_run}`; `events` only on an event run), and the ECMAScript builtins.
- **Hardening** (goja has no heap limit and native builtins are not preemptible): regex calls that run ≥ `RegexpMatchTimeout` (2 s) throw `RangeError` "regular expression took too long" (`RegExp.prototype` exec/test/@@match/@@matchAll/@@replace/@@search/@@split are fixed, non-writable); allocation caps `MaxBuiltinAlloc` = 16 Mi chars/elements on `repeat`, `padStart`/`padEnd`, `String.raw`, `join`, `fill`, `Array(n)`, `Array.from(array-like)` (the global `Array` is a capped function sharing `Array.prototype`); `JSON.stringify` depth ≤ `MaxJSONDepth` (1000). A script stuck in a native builtin past `AbandonGrace` (2 s) after an interrupt is **abandoned**: its run ends with that reason, it is logged, and its automation is disabled (run error "…; the automation was disabled: runaway script — check and re-enable" — there is no `disabled_reason` column). The executor stops claiming while `automations.AbandonedRuns() >= 2` (abandoned goroutines still running; the count drops when one returns). The heap itself is not bounded — sizes are capped at every edge instead.
- **Edges:** an SDK result > 256 KiB serialised → `ResultTooLarge` (never truncated); an SDK argument converts to Go only up to 256 KiB; SDK results reach the script as plain JSON values. The script's return value is JSON-serialised inside the run (functions/symbols/BigInt → uncaught `ValidationError`; > 256 KiB → `ResultTooLarge`); an SDK call made by a getter or `toJSON` during that serialisation ends the run `failed`/`script`.
- **Errors:** SDK errors are JS `Error`s with `name` in `PermissionDenied` (with `needed`), `ResultTooLarge`, `StateTooLarge`, `ValidationError`, `ToolError`, `BudgetExceeded`, `NotAvailable`; catchable by the script. Interrupts (deadline, budget, cancel, daemon stop) are not catchable; an interrupt raised before the outcome is read wins over a script that just finished, and a backend error raised after the run's parent context ended is an interrupt, not a catchable `ToolError`. An uncaught exception ends the run `failed`/`script` with message, stack and the recipe-file line (block offset added).
- `llm(prompt, {input?, schema?, tier?})` — `llm:<tier>` (default light); one `digest.Generator.Generate` with source tag `automation.llm` (light, in `digest.TierForSource`'s light switch) or `automation.llm.strong` (in `allowedStrongSources`: "the owner chose tier: strong in the recipe"); `MaxLLMInputBytes` (200 KiB) bounds prompt + serialised input + serialised schema **together** (stricter than spec §5's "input after serialisation"); with `schema` one retry with the validation error, then `ValidationError`. Order inside the module: `Meter.BeforeCall` → generate → `Meter.Debit` → step usage (`Env.MeteredModelCall`). Usage = provider input + output tokens; a successful call without usage debits `ceil(len(prompt+input+reply)/4)` and marks the run `tokens_estimated`; a failed call debits only provider-reported usage. `reported_cost_usd` only when the provider reports one (display only).
- `tool(name, args, opts?)` — reads go to `Registry.CallRead` with the binding `{Surface: "automation", ContextType: "automation_run", ContextID: <run id>, AutomationRunID: <run id>, WorkbenchID}` (`(*Env).Binding()`); writes go to `Registry.Propose` since P2 (see "Writes (P2)"). Registry `ValidationError` → JS `ValidationError`, other errors → `ToolError`.
- `state.get/set/all` — per-automation JSON object (≤ 64 KiB, `StateTooLarge`); unserialisable values (functions, `undefined`, cycles, `NaN`/`Infinity`, BigInt) → `ValidationError` at the `set`, nothing buffered. `output.inbox({title, body, priority?})`, `output.report({title, body})` — need the kind in `outputs`; body ≤ 64 KiB, title ≤ `MaxOutputTitleChars` (200 characters — a review decision, not in the spec's list). Both buffered and committed only with `succeeded` (AUTO-04). `log(...)` — 4 KiB per call, at most 200 ok steps plus one cap-error step per run (re-checked after argument conversion, since getters may log).
- **Dry run:** `output.*` and `state.set` steps record `dry_run` and nothing commits; `llm` and reads run for real (AUTO-12). `DryRunInMemory(ctx, Backends, *Recipe, DryRunOptions)` runs with a memory journal and writes no row at all (P3's `draft_automation`).
- **Seam for later phases:** `Module`/`Definer` (a later `Define` of the same path replaces the earlier), `SDKFunc`, `Env` (`Call(kind, name, args, fn)` — a step closed inside `fn` is re-closed as an error if the result fails to encode; `MeteredModelCall`), `DefaultModules(Backends)`, `(*OutputMod).RegisterOutputKind`, `Backends{DB, Generator, Registry, Clock, Shell, Workbench}` (Shell/Workbench nil until P5; a module needing a nil backend throws `NotAvailable`).

## Scheduler, executor, wake

- **Daemon wiring** (`cmd/automations_daemon.go`): with `automations.enabled` on, `wireAutomations` builds the indexer over the personal folder, the executor on `buildAutomationRegistry` and the daemon's generator (`ExecutorOptions{Logger}`), and the scheduler (`SetLogger` with the daemon logger, `wake` = the executor's `Wake`); `Daemon.Run` runs both as goroutines beside the sync loop (never a sync phase) and cancels/waits for them before removing the PID file. Off, nothing is built (FEAT-01); the gate is read at daemon start and the Desktop restarts the daemon after a toggle. Enabling the feature runs the `automations` fast-forward hook (`db.FastForwardAutomations`, FEAT-03): every schedule restarts from now and runs queued while it was off are cancelled (queued dry runs are kept — they belong to a live CLI). The legacy "all AI off" mapping (`ApplyLegacyDigestOff`) also turns `automations.enabled` off.
- **Wake (D1):** `SIGUSR2` (`daemon.AutomationWakeSignal`, `WatchAutomationWake`) feeds only the scheduler and executor; `SIGUSR1` keeps meaning "sync". The watcher is installed at the top of `Run` even with the feature off; a wake is then dropped. When `Run`'s context ends the watcher leaves `SIGUSR2` ignored (`signal.Ignore`, never `signal.Stop`) until the process exits, so a CLI that read the caps file just before the daemon removed it gets an explicit no-op (a Go process ignores an unwatched `SIGUSR2` anyway — the default disposition never kills it). The caps file tells the CLI whether this daemon actually runs the automations wake: an older daemon, or one with automations off, silently ignores `SIGUSR2`, so a run would just wait for its next poll. The daemon writes `<pidfile>.caps` right after the PID file (first line its pid, then capability lines, `daemon.AutomationWakeCapability` = `automations-wake`; removed with the PID file) — only when the scheduler and executor are wired and `automations.enabled` is on (`Daemon.automationsActive`). The CLI's `wakeAutomations(cfg)` signals only a confirmed daemon that advertises it (`daemon.HasCapability`); one that does not — older, or started with automations off — is never signalled (`errDaemonCannotWake`: "the running daemon is older, or was started with automations off, and can't be woken; restart it … — the run starts on its next poll", exit 0).
- **Feature off in the CLI:** with `automations.enabled` off, `run` refuses and queues nothing ("automations are turned off in Settings → Features; turn them on, then run it again" — no executor would claim it, and enabling the feature cancels queued runs); `wake` prints "automations are turned off in Settings → Features; the daemon was not woken — a queued run stays queued and is cancelled when you turn them on" and signals nothing; `cancel` still cancels and skips the wake. `dry-run` runs in the CLI process and is not gated.
- **Scheduler** (`automations.NewScheduler(d, ix, clock, wake)`): ticks at every minute boundary and on `Wake`; each tick rescans the personal folder when `Changed`, then for every runnable `schedule` automation finds the due times in `(last_scheduled_for, now]` in the local zone. The latest one within `ScheduleGrace` (2 min) of now → one `schedule` run (older missed ones are folded into it); otherwise `run_once` → one `catch_up` run for the latest missed time, `skip` → none (AUTO-10). `last_scheduled_for`/`next_run_at` advance in the same transaction as the insert, as a compare-and-set (`EnqueueRequest.AdvanceScheduleTo` + `ExpectLastScheduledFor`; a row changed since it was read → `db.ErrScheduleChanged`, the row is skipped for that tick).
- **No catch-up for a window the automation could not run:** first index of a schedule automation, enable (`SetAutomationEnabled`), a confirm that changes `confirmed_hash` (`ConfirmAutomation`; re-confirming the same hash keeps the point), a rescan that makes the row runnable again — only by the file reverting to the confirmed text, since the trigger is in `approval_hash` (D26) (`db.PrimeAutomationSchedule`, which writes only while the row is not a runnable schedule, so a stale indexer cannot rewind the scheduler) — and the feature's enable hook all set `last_scheduled_for = now`.
- **Time zone and DST:** the local zone is re-read every tick (`/etc/localtime` link → `time.LoadLocation`; `TZ` set or an unreadable link → `time.Local`), so a zone change applies without a restart. An hour field without `*` is a wall-clock appointment: a time repeated by a fall-back fires once (first occurrence); a time in the skipped spring-forward hour fires once at the jump (02:30 → 03:00). An hour field with `*` follows elapsed time (both passes of the repeated hour; the skipped hour has no due times). Deliberate deviations from Vixie cron: only the hour field decides (`* 2 * * *` is wall-clock; Vixie treats a minute-or-hour wildcard as a wildcard job), and DST comes from the zone database, not from the size of a clock jump.
- **Clock steps:** clock stepped back → nothing fires until the clock passes `last_scheduled_for` again (no duplicate); `last_scheduled_for` more than a day ahead of now (set under a bogus future clock) → restart from now, no catch-up.
- **Executor** (`automations.NewExecutor(d, Backends, ExecutorOptions)`): `Run` first ends every `running`/`waiting` run `failed`/`interrupted` (restart, D6) — except a live CLI dry run (its `started_at` + budget minutes + 1 min grace still ahead) — then polls every 10 s or on `Wake`. Each poll sweeps dry runs past that deadline (`db.MarkStaleDryRuns`), cancels queued runs of non-runnable automations (`not_runnable`), resumes ready waits into free slots first, then claims the oldest queued runs under the per-automation `concurrency` and the global `MaxConcurrentRuns` = 2 running (waiting runs do not count; `ClaimAutomationRunWithin`). `db.NextQueuedAutomationRuns` never returns a `dry_run` row. The claim snapshots `recipe_text`/`approval_hash`/budgets; the run re-parses the snapshot with the scope rebuilt from the index row (`scope` + `project_id`) — never the file. A finished run wakes the executor.
- **Run end:** success → `FinishAutomationRun(succeeded, commit)`; summary = the last `output.report` title, else the returned value (a string as is, other values as JSON — never `[object Object]`/`undefined`; no return value = `""`), clipped 1 KiB. Uncaught error → `failed`/`script`; uncaught `PermissionDenied` → `failed`/`permission`; deadline → `timed_out`; budget → `budget_exceeded`/`budget`; cancel → `cancelled`; daemon stop during a run or wait → `failed`/`interrupted` ("the daemon stopped…"; a CLI dry run: "the dry run was stopped…"); malformed `event_json` → `failed`/`backend` before the script starts. Ending a run closes its open steps in the same transaction (step `error`: "the run ended (<status>) before this step finished"). Every time-stamping writer refuses a zero time.
- **Waiting** (`(*Executor).Waiter()`, used by P2/P5): sets the run `waiting` with a reason, pauses active time, polls `ready` every poll or on wake, honours cancel and `pause_timeout_hours` (→ `expired`); a ready wait resumes only while running < `MaxConcurrentRuns` (`db.ResumeAutomationRunIfSlot`). `SetAutomationRunWaiting` from `waiting` changes only the reason (P5's `app` → `session`).

## Budgets

Tokens, never dollars (D4). Per run: `budget.tokens` and `budget.minutes` of active time (snapshotted on the run). `BeforeCall` refuses a model call with `BudgetExceeded` when the remainder is ≤ 0; a call that crosses it interrupts the run (`budget_exceeded`). No daily cap across runs (D25, ask #294, which retired `automations.daily_budget_tokens`; a leftover key in `config.yaml` is ignored, and `error_kind='daily_cap'` stays in the CHECK but is no longer produced): each run is bounded only by its own token and time budget.

## Automation read tools (D2, D23)

All `AccessRead`, `Surfaces: ["automation"]`, **not** in `tools.ReadTools()` (dev-mode MCP never mounts them, DEV-01), local store only (constructors take no client), list `limit` default 50 / max 200, arrays never `null`:
- `list_emails` / `get_email` (`internal/tools/emails.go`) — `gmail_messages`/`imap_messages` only, never the live API, no per-flavour gating (D2); `account` = label, address, or a store-qualified `gmail:<id>`/`imap:<id>` ref when a label or address is ambiguous; a Google account without Gmail enabled is refused; body clipped to `tools.MaxEmailBodyBytes` (32 KiB) with `truncated` — `gmail:read@<account>|*`.
- `list_inbox` — `tool:` only; `list_calendar_events` — `calendar:read@<account>|*`; `list_meeting_recaps`, `get_meeting_recap`, `list_meeting_notes` — `meetings:read`; `list_day_plans`, `get_day_plan` (the owner via `db.ResolveOwner`, OWNER-01/02) — `dayplan:read`; `list_reminders` — `targets:read`; `list_jira_sprints`, `list_jira_releases` — `jira:read@<PROJECT>|*` (`internal/tools/automation_reads.go`).
- Existing tools admitted: `memory_recall`/`memory_open`/`memory_map` (added by `buildAutomationRegistry` with no shadow handle; `memory_open` skips its access bump on the `automation` surface — automation reads write nothing), `get_writing_style` (gains the `automation` surface), `list_jira_projects` (surface-less, `jira:read@*`) and the surface-less dev reads. `get_confluence_page` is **not** offered (a live read; D23 is local store only). Trust is a write-tool setting: read tools take none on any surface; since P2 the ten write tools take a level on `automation` too (see "Writes (P2)").
- `buildAutomationRegistry(cfg, db)` (`cmd/automations_registry.go`) = `buildToolRegistry` + the three memory tools — the one registry every automation path uses (daemon executor, CLI dry run, P3's `draft_automation`, P6's runtime B). Shared helpers exported for later phases: `tools.ClipUTF8Bytes`, `tools.DefaultListLimit`/`MaxListLimit`.

| `wake` | sends the wake through `wakeAutomations` (shipped in P1 — P3 does not add it again); open under markers (changes nothing) |

Every `--json` array is `[]`, never `null`; later phases may add keys, never rename or drop one. Agent markers: `CLAUDECODE`, `CODEX_THREAD_ID`, `CODEX_SANDBOX`, `WATCHTOWER_TERMINAL_SESSION_ID`, `WATCHTOWER_AUTOMATION_RUN_ID` (`automations.RunEnvMarker`, new — Go `agentEnvMarkers` and Swift `Constants.agentEnvMarkers`).

- **Agent permissions (D24, ask #293):** under markers `confirm`, `save --confirm-hash`, `dry-run` of an unconfirmed recipe, `enable` and `delete` are refused — the last two before anything is read or written, with the hint "enable and delete are owner-only" (after `refuseUnderAgent`'s own "the owner decides in Watchtower Desktop (or runs this from a plain Terminal)") (`refuseOwnerOnlyAutomationVerb`, guard `TestAutomationsCLI_EnableDeleteRefusedUnderAgentMarkers`). `disable`, `run` (of a confirmed, enabled recipe), `cancel`, `rescan` and a plain `save` stay open: they only reduce activity or run what the owner already confirmed. A plain `save` that changes the trigger, missed policy, budget or concurrency changes `approval_hash` (D26, ask #294), so the recipe stops running until the owner confirms it again. Removing a recipe file by hand is outside the CLI and not guarded; the next rescan marks the row `removed_at`.

A recipe folder reached only through a symlink inside the workbench folder must be named by its stored spelling.
- No events, no workbench Desktop scope (P5 part 2), no templates yet (`mcp()`/`agent()`: see P6 below; the Desktop: see P3 below; workbench recipes in the daemon: see P5 part 1 below).
- P2 refused every write of a workbench automation's run (`workbenchAutomationGate`, `ErrWorkbenchAutomationWrite`); P5 lifted it (spec §6.1, §13): `Registry.automationWorkbench` resolves the workbench from run → `automations.project_id` at Propose, Approve and every Apply (inline and `actions apply`), `WorkbenchAlive` and the tool's `Scope` check it, a binding naming another workbench is refused, and a row whose run no longer exists fails closed with `tools.ErrAutomationRunGone` (`NotAvailable` to the script). ### v1 limits (P3)

- The draft cache is never cleaned beyond its 5-line cap, and leftover `automation_draft` conversations (one per started draft) stay in `chat_conversations`; the cache file holds the dry-run journal, clipped mail included.
- The confirmation sheet's author line knows only the assistant's `save_automation` saves; a plain `automations save` or a hand edit reads "Changed outside Watchtower" (R-P3-18).
- An unselected row's detail line cannot say "schedule changed" (Ruling A); the card's "new since your confirmation" marks every permission of an unconfirmed recipe (`show --json` `widening`).
- `agent()` is not previewed in a draft dry run (Ruling K); dry-run the saved recipe from its card.
- Workbench recipes: read-only in the form, `save_automation` refuses them, no workbench template install UI — all until P5.
- The form drops comments inside the frontmatter it rewrites; a Monaco edit typed in the 300 ms before a form change can undo that form change (the form then says so).
- The palette's "last run" may describe a dry run.
- Manual checks left for the phase gate: ⌃⌘R with the keyboard in the SwiftTerm terminal, the Monaco Files pane and the Settings window; tray run → finish notice → click opens the run; the edit form's "Change it in words instead" hand-off to the chat sheet.

## mcp() and agent() (P6 part 1, 2026-10-16)

Plan `docs/superpowers/plans/2026-10-14-automations-p6.md` (Tasks 1–7, 11), spec §5, §6.5, §14.7, decisions D3, D20 (ask #272), D21/D22 (ask #273). Contracts: guards added to AUTO-01/07/08/11/12 (`docs/inventory/automations.md`), QC-02 amended (`docs/inventory/quick-connections.md`), AGENT-01/02/03 notes (`docs/inventory/agent-actions.md`). Templates and the gallery CLI (`templates`, `install-template`) follow in a later P6 part.

- **`mcp(server, tool, args)`** (`internal/automations/sdk_mcp.go`, backend `cmd/automations_backends.go`): the manifest is checked first (`mcp:<server>/<tool>`, server exact then glob), then a Go-side `externalmcp.CallTool` (`internal/externalmcp/call.go`) on the enabled Quick Connection named exactly `server`, only for a tool in `externalmcp.ResolveTools`' allowed (QC-02) list of its cached listing. It never lists a connection (a never-listed one is `NotAvailable` until the chat's launch-time listing or `connections tools --refresh`), never goes through the registry, resolves credentials only after the tool check (secrets travel in the child's environment or an OAuth bearer, never argv or the script), and is bounded to 30 s (a call that runs out says it hit the 30 s `mcp()` limit). A `NotAvailable` error keeps its cause in the message and the journal step (no such connection, never listed with the `connections tools N --refresh` hint, unusable credentials, no allowed tool); a failure to read the connections is a `ToolError`, not `NotAvailable`. Results are plain JSON values capped at 256 KiB (`ResultTooLarge`). One journal step per call. In a dry run `mcp()` is real (reads only).
- **`agent(instruction, opts)`** (`internal/automations/sdk_agent.go`) returns `{text, actions}` (actions = the `agent_actions` rows the loop proposed). Needs `agent:run` plus an `llm:` tier; `wait` is refused. The **effective tool set** is the manifest's tool grants intersected with the run's tool surface (`TestAgent_ToolSetIsIntersection`; D21/D22 scopes as in `tool()`); no Quick Connection tool is ever in it, and a dry run drops every write tool. The loop is capped at 12 model calls. **Budget carving:** the call gets min(`opts.budget`, what remains of the run) in tokens and minutes; the model calls meter against both the carve and the run (`Hooks`), the carve spent throws a catchable `BudgetExceeded` (also for a carved minutes deadline), the run's own budget or deadline interrupts the run uncatchably (AUTO-08). Inner tool calls are summarised in the one `agent` step (AUTO-11).
- **Runtimes.** Provider `claude` or empty (`""` runs the claude CLI) and `codex` run a headless CLI child bound to `watchtower mcp --chat --surface automation --automation-run N --automation-tools a,b,c` (`--allowedTools` = the effective set plus `get_action`; no Quick Connection config). The server command also carries `--config <this process's config file>` and `--workspace <active workspace>`, since the child's env drops `WATCHTOWER_CONFIG_PATH`: under a dev/verification config or `automations dry-run --config/--workspace` the server opens the same workspace as the run. Any other provider (ollama and other HTTP providers) runs the in-process runtime-B loop (`internal/agentloop`) over the same effective set. Both gate every call with `automations.GateAgentCall` (offered, in the manifest's scope, `AutomationAgent` binding so a write is always a pending proposal, never executed, even under an auto grant) and refuse a result over 256 KiB (`CheckAgentResult` per tool result on runtime B; `internalmcp.WithResultCheck` on the server).
- **The `--surface automation` server** (`cmd/mcp.go`, chat mode): refuses to start unless `WATCHTOWER_AUTOMATION_RUN_ID` (the AGENT-07 marker, D3) equals `--automation-run` and that run is `running` (`TestAgentMCPServer_RefusesWithoutMatchingMarkerOrRunningRun`); mounts only the effective set plus `get_action`; re-checks the manifest on each call; refuses calls once the run ended; its `get_action` shows only the bound run's own rows. `--workbench N` together with `--surface automation`, `--automation-run` or `--automation-tools` is refused (`TestMCP_WorkbenchWithAutomationFlagsRefused`). The main-chat and target servers are unchanged (`TestMCP_MainAndTargetUnchanged`).
- **CLI child environment and process group.** The child gets PATH (rich), HOME, LANG, USER and the run marker only, and runs in its own process group; cancel or a deadline kills the group, with `ai.GroupKillGrace` = 1 s (not the default grace) so it dies inside the 2 s `AbandonGrace` and the automation is not disabled as a runaway. When the wait returns, a still-pending group SIGKILL is sent at once and its timer stopped (`ConfigureChild`'s reap), so no timer signals the group id after the call.
- **codex.** The child runs with a per-run temporary `CODEX_HOME` (0700, removed after the run): its `config.toml` declares only the watchtower automation-run server (with `env_vars = ["WATCHTOWER_AUTOMATION_RUN_ID"]`, as does the `--cd` folder's `.codex/config.toml`: codex starts MCP servers with a filtered environment, and without the marker the server refuses to start) and `web_search = "disabled"`, and the owner's `auth.json` is symlinked, not copied, so the owner's `~/.codex/config.toml` MCP servers and web search, both outside the effective set, never reach it.
- **Metering and v1 limits.** A CLI agent's tokens are known only when the child exits: they are metered once then (provider usage, or `ceil(len/4)` estimated; a child that fails or is killed at a deadline or cancel debits `ceil(len(instruction)/4)` estimated), so one `agent()` call can overshoot its carved budget: it then throws a catchable `BudgetExceeded` and its reply is not returned, or, past the run's budget, the run is interrupted (runtime B meters per model call). A CLI child whose bound server never started is not a success: the runner passes `--automation-ready-file <per-run temp path>` and the server creates that file only after `mcpAutomationOptions` accepted the binding (the run's own marker, the run running) and the server is built, just before it serves stdio; a child that exits without the file fails `agent()` with `ToolError` "agent(): the watchtower tools never connected (the bound MCP server did not start)", its usage still debited (`TestAgent_CLIServerNeverStartedIsToolError`, `TestAgentMCPServer_ReadyFileOnlyOnAcceptedStart`). `--automation-ready-file` without `--chat --surface automation`, or with `--workbench`, is refused. No DB write. codex has no turn cap, only time and tokens. An owner whose codex login lives in the keyring, or who relies on custom `model_providers`/profiles, gets a `ToolError` from `agent()` on codex (the scrubbed home has only `auth.json`). Tokens are metered, not dollars (D4): `reported_cost_usd` only when a provider reports one (claude's `total_cost_usd`; codex reports none).

## Workbench automations (P5 part 1, 2026-10-16)

Plan `docs/superpowers/plans/2026-10-14-automations-p5.md` (Tasks 1–7), spec §6.1, §13, §15, decisions D7, D9, D19 (ask #272), R-P5-2..R-P5-6. Migration 00122 adds `automation_run_id` to both `owner_asks` and `terminal_sessions`.

- **Recipes and indexing.** A workbench recipe lives in `<workbench folder>/.watchtower/automations/*.md`. The daemon's scheduler rescans every workbench whose folder is not protected (`fsutil.PrivacyProtected`) and never stats a protected one (`TestScheduler_NeverStatsProtectedWorkbench`); a recipe path reached through a symlink — the folder, any ancestor of it, `.watchtower` or `automations` — is skipped too, lstat only (`fsutil.NoSymlinkComponents`; `TestScheduler_NeverFollowsALinkIntoAProtectedFolder`, `TestScheduler_NeverFollowsAnAncestorLink`). Those workbenches are indexed by the Desktop in part 2. A recipe that arrives by `git pull` is indexed unconfirmed ("Needs your confirmation", `TestRescan_WorkbenchRecipeNeedsConfirmation`); its `approval_hash` carries the workbench id.
- **`shell(cmd)`** (`sdk_shell.go`, `NewProcessShellRunner`): runs only a command byte-equal to a `shell:` manifest entry, `/bin/sh -c` in the workbench folder, in its own process group (killed on the deadline or cancel), with an environment of PATH, HOME, LANG, USER and `WATCHTOWER_AUTOMATION_RUN_ID` only; PATH is the daemon's resolved rich PATH (`claude.RichPATH`, as for every other child — a Desktop-started daemon has launchd's minimal PATH, without Homebrew's `gh`/`make`). A protected-folder workbench gets `NotAvailable` (D9), and so does a folder path whose folder or any ancestor is a symlink, refused after lstats only, before any stat or process (`fsutil.NoSymlinkComponents`, `TestShell_RefusedWhenTheFolderPathHasALink`). Each stream keeps its last 256 KiB; oversized output is truncated to fit the 256 KiB result limit and marked `truncated: true`, never a failure (D19). A non-zero exit is a result, not an error. A dry run returns `{status:"dry_run"}`.
- **`session({prompt, agent?, title?, wait?})`** (`sdk_session.go`): the step is marked waiting for the app, then for the session once the Desktop attached it, and the run resumes when the session finished, failed, was deleted or stopped (`wait:"none"` returns `{session_id}` at attach). The Desktop reports through `watchtower automations session-launched --step N --session M` and `session-ended --step N --status stopped|launch_failed [--error …]`, both refused under AGENT-07 markers (only the Desktop reports) and followed by a `SIGUSR2` wake. `prompt` + `agent` + `title` must fit the 4096-byte step args (R-P5-2; title at most 80 runes). A launch the Desktop could not make throws `NotAvailable` (R-P5-4). The Desktop launch center itself is part 2.
- **`ask({kind, title, summary?, questions?, checklist?})`** (`sdk_ask.go`): `check` or `question` only (a review needs a document and a session, R-P5-5); `ask:owner` in a workbench recipe only. The ask is filed on the workbench with no session and the run's id, the run waits (`waiting_reason` ask) and gets the answer; the run, not a terminal, marks it delivered. No session reader ever sees it (`TestAutomationAsks_InvisibleToSessionReaders`), a cancel or pause timeout withdraws it, and deleting the automation or its workbench deletes it (R-P5-6, `TestProj02_DeleteRemovesAutomationRows`). A dry run files nothing.
- **Workbench writes.** The P2 write gate is lifted: `Registry.automationWorkbench` resolves the run's workbench at Propose, Approve and every Apply, and a run context whose id does not parse fails closed with `ErrAutomationRunGone` (`TestWorkbenchAutomation_UnparsableRunContextFailsClosed`).
- **Fixtures.** `internal/automations/testdata/workbench/{pr-review-rounds,release,deploy-test,deploy-stage}.md` run end to end in `workbench_e2e_test.go`; a failed command throws with the stderr tail in the run error (a failed run commits no outputs, AUTO-04). P6 moves them into the templates.
- **v1 limits / part 2.** Pending: workbench saves and the PROJ-03 amendment (Task 8), the Desktop session launch center, header buttons, ask labels and delivery exclusion, Desktop rescans of protected workbenches, `docs/app-guide.md` and `docs/features/workbench.md` paragraphs. A session an automation starts is an ordinary session; "stopped" for the run means the process ended, reported by the Desktop (R-P5-3). **Part-1 limit:** nothing launches a `session()` step's session yet, so a workbench recipe's `session()` waits for the app until its pause timeout ends the run — the Desktop launch center (part 2) is the consumer of `PendingAutomationSessionSteps` and `terminal_sessions.automation_run_id`. **v1 limit:** a daemon killed with `SIGKILL` while a `shell()` command runs leaves that command's process group running (the group kill is the daemon's; nothing reaps it after the daemon is gone).
