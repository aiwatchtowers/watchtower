# Incident — daemon ignored SIGTERM for ~3 hours after `sync stop` (2026-09-25)

**Severity:** operational (no data loss; ~3 h of burned CPU and a forced SIGKILL by the owner). No customer-facing surface — single-user desktop daemon.
**Detected by:** owner, while stopping the daemon during work on the memory vault.
**Root cause package:** `internal/memory` (`EvictEpisodes` calling `Vault.OwnerEdited` per candidate) + `cmd`'s signal handling (`signal.NotifyContext` never re-registering after the first signal).
**Fix branch:** `fix/daemon-shutdown-hang`.

## Root causes

Two independent bugs, found together because the second made the first fatal instead of merely slow.

### 1. `EvictEpisodes` re-walked the entire vault git history per candidate

`internal/memory/evict.go` called `Vault.OwnerEdited(rel)` once per eviction candidate. `OwnerEdited` (`vault.go`) runs `repo.Log(&git.LogOptions{FileName: &rel})`, which is go-git's `commitPathIter`: for **every** commit from HEAD back to the root, it decodes both that commit's tree and its parent's tree and runs a full, non-path-limited `DiffTree`, filtering by name after the fact. For a file an owner-edit commit never touched — true of nearly every episode — this walks the *entire* commit history every single call. On this vault (tens of thousands of commits, an `episodes/` tree with tens of thousands of entries, all loose objects) each call cost tens of milliseconds to minutes; an evict pass scans candidates without the count itself being bounded (only *evictions* are capped, not the scan), so ~10-20 warm candidates was enough to produce hours of wall-clock time.

The fix — `OwnerEditedFiles`/`ownerEditedMemo` (one history pass, reading only commit headers, computing the exact same fact) — already existed in the same file for other callers; `EvictEpisodes` was the one remaining production caller of the expensive per-call form.

### 2. `runSemantic` and its post-belief steps had no cancellation checks

Once inside the semantic tier's later steps (age, evict, reflect, render), nothing checked `ctx.Err()`. A go-git call itself takes no context (only `Fetch`/`Pull`/`Push` do in go-git v5.19.1) and its `ForEach` callback only fires on a *matching* commit, so a single `OwnerEdited`/`Status`/`Commit` call is, once started, uninterruptible from the outside. Cancelling the daemon's own root context had no effect on a loop that never re-checked it between candidates.

### 3. A second SIGTERM did nothing — `signal.NotifyContext` never re-armed

`cmd/sync.go` (daemon path) ran `ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)` with `defer cancel()`. Go's `signal.Notify` registers a channel for the given signals; while it stays registered, the runtime treats the signal as "handled" — a second SIGTERM is queued into the one-slot channel (nobody is reading it, since nothing checks ctx again) and every subsequent one is silently dropped. `stop()` (which un-registers and restores the default disposition) only runs when the deferred `cancel()` finally executes, and that never happens while the process is stuck inside an uninterruptible git call. Net effect: SIGTERM #1 cancelled a context nothing was checking; every SIGTERM after that was absorbed and discarded. Only SIGKILL — which cannot be caught, blocked, or ignored — ended the process.

### 4. `sync stop` had no escalation path

`runSyncStop` sent one SIGTERM, polled for 10 s, and on timeout printed an error and gave up — no second signal, no SIGKILL, no operator-facing next step beyond reading the source.

## Why this is a time bomb, not a one-off

The duration scales with vault history, not just file count. A fresh or recently-reset vault (`memory reset-to`) has few eviction candidates and the same pass completes in seconds; a healthy vault after a couple of months of active use (tens of thousands of commits from the ~5-10 vault commits per active daemon cycle × 96 cycles/day) already costs tens of seconds to minutes per warm candidate — meaning `EvictEpisodes` risked running for **hours on every cycle**, not just at shutdown, on any install with memory + the semantic tier enabled. The bloated vault that triggered this incident just got there first.

## Follow-ups (not fixed by this branch)

1. **`Reconcile` (index rebuild) now stops between files on cancel — fixed by commit 1 above, not left open.** It took 7.5 h on the bloated vault (02:14→09:43) before the stop was even requested; `internal/memory/index.go`'s `reconcile` now checks `ctx.Err()` before each directory entry in its per-subdirectory loop and returns early, before the deletion loop and phase B, once cancelled. Two residuals remain, by design (see the function's own doc comment): a single file's parse/upsert work is still uninterruptible once started (the per-file call itself takes no ctx), and a partial reconcile leaves the files it did touch without phase B's importance-score refine (`refineImportance` never runs on a cancelled pass) until the next complete reconcile or `memory reindex`.
2. **`AgeEpisodes` candidate scanning is still uncapped** (only `EvictEpisodes`' *evictions* are capped, not either step's *scan*) — cheap after fix (1), but worth a bound on principle for a large backlog's first run.
3. **`memory reset-to` on a bloated vault is itself slow and not resumable.** The owner's `memory reset-to <commit>` on this vault ran roughly 100 minutes, CPU-bound (~8 files/s), because go-git's hard reset walks and rewrites every file against the loose-object store rather than a packed one. Worse: if that run is interrupted (killed, crashed, or simply cancelled) after the ref has already moved but before `features.FastForward` and the reindex run, re-running `watchtower memory reset-to <commit>` against the *same* target commit hits the early-return in `cmd/memory.go` (~line 393): `plan.Head == plan.Target` prints `"HEAD is already at the target commit — nothing to reset."` and returns **without** running the reindex or fast-forwarding the extraction watermarks. There is currently no way to resume an interrupted reset short of manually invoking the reindex/fast-forward steps by hand. No code change in this task; recorded here as a follow-up for the memory recovery tooling.
4. **`digest.channel` vs `digest.channel_batch` tier inconsistency** and other pre-existing audit follow-ups are unrelated to this incident and tracked separately (`docs/audit/2026-09-13-feature-audit/README.md`).
5. **Several mechanical `Pipeline.Run` steps are still entirely ctx-blind — not the hang class, but not covered by fix (1) either.** `PromoteConcepts` (semantic tier) and `SeedEntities`/`runCalendarIngest`/`runOperationalMirrors`/`runJiraIngest` (the mechanical steps ahead of extraction, `runMechanicalAndExtraction`) don't take a `ctx` parameter at all, so none of them can honour a shutdown mid-call. `PromoteConcepts` and `SeedEntities` are pure local SQL/vault-file work with no unbounded git-history walk — the specific shape that made `EvictEpisodes` hang for hours — so they're a minor "shutdown waits a bit longer than ideal" risk, not a repeat of this incident. `runCalendarIngest`/`runOperationalMirrors`/`runJiraIngest` are similarly local/bounded per their own per-source caps. Recorded here as a follow-up, not fixed by this branch.
